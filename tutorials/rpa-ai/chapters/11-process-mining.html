11. Process Mining & Discovery

Chapter 11

The Discovery Problem

Most automation programs fail to scale not because bots are hard to build, but because they run out of good candidates. Teams ask: "What should we automate?" Relying on intuition and self-reported process walkthroughs produces bad picks — automations of already-broken processes, or of processes nobody actually follows. Process mining and task mining solve this by using data to see what really happens.

Process Mining vs Task Mining

TechniqueData SourceWhat It Reveals
Process miningEvent logs from systems (ERP, CRM, workflow tools)How work flows through systems end-to-end: steps, handoffs, waits, variants, bottlenecks, deviations
Task miningScreen recordings / UI telemetry from desktopsWhat individual workers actually do: clicks, keystrokes, app switches, manual copy-paste

Together they give a data-driven picture of both the system-level process and the desk-level work — which is exactly what you need to find automation opportunities.

Process Mining: How It Works

  1. Extract event logs: pull data from systems in the standard XES or CSV format. Each event has a case ID, activity name, timestamp, and attributes.
  2. Reconstruct the process: software (Celonis, UiPath Process Mining, ProcessGold, etc.) draws the process graph from actual events.
  3. Analyze variants: the system shows every path the process actually takes — often hundreds of variants, with the "happy path" being only a fraction.
  4. Measure: cycle times, wait times, rework, handoffs, costs, and SLA adherence per step and per variant.
  5. Identify opportunities: spot bottlenecks, manual steps, and high-variation areas — the best automation targets.
Why it matters: Most organizations believe they follow their documented process. Process mining usually shows the opposite: the actual process is a web of shortcuts, rework loops, and exceptions. Automating the "documented" process automates a fiction. Process mining grounds automation in reality.

Task Mining: Seeing the Desk Work

Task mining captures worker behavior with screen recording and UI analytics:

  • What it records: application usage, copy-paste between systems (the swivel-chair), repeated patterns, manual data entry.
  • What it finds: the hidden "manual glue" between systems — precisely the work RPA targets.
  • Privacy consideration: recording workers' screens requires consent, transparency, and data minimization. Task mining is workforce surveillance if mishandled — design it as an opt-in improvement tool, not monitoring.

From Discovery to a Prioritized Pipeline

Discovery produces a candidate list. Prioritization turns it into a roadmap. A standard scoring approach:

FactorHow to Score
Business valueFTE/hours saved, error reduction, cycle-time improvement, risk reduction
Volume & frequencyTransactions per day/month
FeasibilitySystems accessible, stability, exception complexity
RiskCompliance, data sensitivity, irreversibility
Strategic alignmentFits program goals and executive priorities
Cost to implementBuild, licensing, support

Score each candidate and build a prioritized automation backlog with a target benefit per automation. Review the backlog quarterly as the business changes.

The Process Definition Document (PDD) Revisited

Once a process is selected, the discovery data feeds the PDD (Chapter 4): the real variants, exception rates, and screens captured from task mining replace guesswork. A discovery-driven PDD is dramatically more accurate than one written from a workshop alone.

Common Discovery Mistakes

  • Automating the happy path only: ignoring the variants that process mining reveals; the bot fails on the real world.
  • Skipping process redesign: automating a process with 20 steps when a redesign would make it 6. Fix the process first.
  • Surveillance-style task mining: destroying trust and creating legal risk. Get consent, minimize data, focus on aggregate patterns.
  • Analysis paralysis: mining endlessly without picking targets. Run discovery in sprints tied to decisions.
  • One-time discovery: processes drift; re-run mining periodically to refresh the pipeline.

Continuous Improvement Loop

Mature programs run discovery continuously:

  1. Mine the process portfolio → identify opportunities.
  2. Prioritize → select the next automations.
  3. Build → automate to standard.
  4. Run → monitor live bots with run data.
  5. Measure → track benefits and exceptions.
  6. Re-mine → find the new bottlenecks and the next wave.
Process mining as a service: Vendors increasingly embed process mining into RPA suites so that the same platform discovers, selects, builds, and monitors automation. This "closed loop" is the backbone of hyperautomation.

Case Study: Finding the Right Target

An insurance company had automated a claims-intake step but saw disappointing adoption. Process mining on claims event logs revealed the real bottleneck was elsewhere: the rework loop where data was re-entered when a claim bounced between systems, plus a 2-day wait in a manual validation step. Task mining on the underwriting team confirmed hours of copy-paste between the CRM and the claims system. The team re-prioritized and automated the rework and data-entry glue instead — getting 10x the benefit of the original automation.

Practice Task: Pick a process you know well (or one of the book's examples). List the systems it touches, the steps, and where you believe the waits and rework are. Then design a simple process-mining analysis for it: what event log columns would you need (case ID, activity, timestamp), and which three metrics would you compute first? Which steps would you prioritize for automation, and why?
