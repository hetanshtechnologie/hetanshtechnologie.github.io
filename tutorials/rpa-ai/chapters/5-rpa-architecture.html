5. RPA Architecture & Governance

Chapter 5

Anatomy of an RPA Platform

Production RPA is a client-server architecture. The design tools, the runtime runners, and the control plane are distinct components that must be deployed, secured, and operated deliberately:

ComponentRoleWhere It Runs
Studio / Design toolBuild workflows, selectors, and libraries; publish packagesDeveloper machines
Robot runtime (runner)Execute published workflowsUser desktops (attended) or servers/VMs (unattended)
Orchestrator / Control RoomSchedule, trigger, monitor, license allocation, queues, logsServer / cloud
Credential vaultStore and inject secrets securely into bot sessionsServer / dedicated vault
Logging / analyticsCapture run data, exceptions, KPIsServer / SIEM or data warehouse

Deployment Topologies

  • On-premises: full control, common in regulated industries; higher ops burden and cost.
  • Cloud/SaaS: vendor-hosted orchestrator; faster to adopt, easier scaling; data governance must be reviewed.
  • Hybrid: cloud orchestrator with on-prem runners (common when bots must touch on-prem systems or Citrix).
Design guidance: Choose topology by where your data and target applications live, your compliance requirements, and latency. A pure cloud RPA suite can still run runners on-premises; the reverse (on-prem orchestrator) is less common.

High-Availability and Scale

As automation scales, the platform must be engineered like any enterprise system:

  • Multiple runners per queue: run many bots in parallel, scaled by workload.
  • Orchestrator HA: redundant orchestrator instances, load-balanced, with database HA.
  • Disaster recovery: automated backups, restore procedures, and documented RTO/RPO.
  • Versioned packages: publish workflows as versioned artifacts; roll back quickly.
  • Capacity planning: model the peak (e.g., month-end) and provision runners for it.

The Automation CoE (Center of Excellence)

The CoE is the governance body that turns pilots into a sustainable program. A well-functioning CoE owns:

  • Standards: naming conventions, workflow structure, error-handling patterns, selector guidelines.
  • Processes: intake, assessment, prioritization, delivery, change management, decommissioning.
  • Security and compliance: credential management, access control, audit trails, data handling.
  • Platform ownership: infrastructure, licensing, upgrades, monitoring.
  • Value tracking: benefits realization, capacity utilization, cost per automation.
  • Skills and training: developer certification, business analyst enablement, citizen development governance.

Security in RPA

Bots hold powerful credentials and touch sensitive data. Security must be designed in:

  • Credential vaulting: never hardcode passwords; the orchestrator injects them at runtime.
  • Least privilege: bots get the minimum access needed — dedicated service accounts, scoped permissions.
  • Segregation of duties: the developer who writes the bot should not hold the production credentials.
  • Encryption: at rest and in transit; protect logs that may contain data.
  • Audit trails: full record of bot actions, who ran what, when, with which version.
  • Data masking: mask sensitive values in logs and screenshots.
  • Change control: production workflows deploy through a controlled pipeline, not ad-hoc edits.
Common risk: a shared "god account" used by many bots. Compromise of one bot means compromise of everything it can touch. Scope accounts per process or per domain, and rotate credentials regularly.

The Automation Lifecycle and Change Management

Automations are living systems. Govern them like applications:

  1. Intake and assessment: register the idea, score feasibility and value.
  2. Build: develop to standards, in a source-controlled environment.
  3. Test: integration testing and UAT sign-off.
  4. Release: deploy through a controlled pipeline with versioning.
  5. Operate: monitor run health, exceptions, and SLAs; handle incidents.
  6. Change: when the underlying process or applications change, review and update the automation.
  7. Retire: decommission when the process ends, with data retention handled.

Measuring the Program

Run the automation program on metrics, not anecdotes:

MetricMeaning
Automation count & coverageNumber of live automations and processes automated
Hours / FTE savedEstimated time returned to the business
Cost savings vs cost of programNet financial benefit (net of licenses, build, support)
Run success rate% of scheduled runs completing successfully
Exception rate% of work items needing human attention
Runner utilization% of licensed capacity actually used
Break-fix volumeAutomations failing due to environment/UI changes
Time-to-valueAverage time from intake to production deployment
Reality check: The #1 reported challenge in enterprise RPA is scaling past the first wave of pilots. The cause is almost always missing governance: bots built ad-hoc, no standards, no monitoring, no change management. The CoE is not bureaucracy — it is the thing that makes scale possible.
