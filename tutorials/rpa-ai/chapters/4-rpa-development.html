4. RPA Development: Building Your First Bot

Chapter 4

From PDD to Working Bot

Building a bot starts long before you open the studio. The disciplined order is: document the process, then automate the green path, then handle exceptions. This chapter walks through the full build of a small, realistic bot so you understand the mechanics regardless of which tool you use. The concepts — selectors, variables, error handling, debugging — are universal across UiPath, Power Automate, Automation Anywhere, and Robocorp.

The Process Definition Document (PDD)

A PDD is the source of truth for what the bot must do. A good PDD contains:

  • Process overview: goal, owner, frequency, volume, current pain points.
  • Step-by-step procedure: numbered actions a human performs, with screenshots.
  • Inputs and outputs: exact data sources, formats, and destinations.
  • Business rules: every decision and its conditions (e.g., "if amount > 5000, route to manager").
  • Exception matrix: known failure points and how each should be handled.
  • Compliance notes: audit, retention, and security requirements.
Golden rule: If the PDD has ambiguity, the bot will fail in production. Ambiguity must be resolved in the PDD, not discovered by the bot.

Selectors: How Bots Find UI Elements

Selectors are the heart of RPA reliability. A selector is a description of a UI element's identity — like its CSS selector in web terms. A selector typically includes the element's type, and attributes such as its name, ID, or position in the hierarchy.

<ctrl name='OK' role='push button' />   (classic UI)
div[class='btn primary'][text='Submit']   (web)
input[data-qa='order-total']              (web with stable attributes)

Reliable selectors prefer stable attributes (IDs, names, labels) over positional or text-based ones. UI automation breaks when selectors drift — for example, when the application adds a dynamic suffix like an auto-generated ID.

Selector hygiene: Avoid selectors that depend on screen coordinates, window titles with dynamic text, or element index. Where possible, configure the app under automation with stable accessibility attributes (ARIA, control names). Selector maintenance is the #1 cost of running bots over time.

Variables, Data Types, and Arguments

Workflows pass data around with variables (local to a workflow) and arguments (passed between workflows or from the orchestrator). Common types: String, Int, Boolean, DateTime, DataTable, List, and dictionaries. When you invoke another workflow, you map arguments (In/Out/InOut) so data flows cleanly.

Conventions matter at scale:

  • Name variables clearly: invoiceTotal, isDuplicate, not var1.
  • Define the scope of variables tightly — avoid mega-variables passed everywhere.
  • Keep sensitive data in the credential vault, never in variables logged or shown.
  • Use typed variables; convert explicitly to avoid subtle bugs.

Building the Green Path First

Build the happy path end-to-end before handling exceptions:

  1. Record or scaffold: use the recorder to capture initial steps, then refactor the generated workflow for clarity.
  2. Add data handling: read inputs, structure them, prepare outputs.
  3. Add loops and conditions: process every item in the input.
  4. Add logging: log key milestones with context (order ID, amounts) so runs are auditable.
  5. Test on realistic data: run against a small but representative sample, including a few rows that touch every branch.

Error Handling and Recovery

Production bots fail — the question is how gracefully. A robust bot design:

  • Try/Catch around fallible steps: file reads, logins, UI interactions, external calls.
  • Retries with backoff: transient errors (network, app busy) often clear on retry.
  • Exception queues: route unhandled items to a human task queue instead of stopping the run.
  • Global exception handler: catch unexpected failures, log, notify, and decide whether to continue or stop.
  • Checkpoint design: keep a "last processed row" so a crashed run resumes rather than restarts.
Pattern: For each work item: try to process; if success, record status "processed"; if recoverable error, retry; if not, record status "escalated" with a readable reason and send to the human queue. Never let one bad row kill the whole batch silently.

Debugging Techniques

  • Step-through: run the workflow one activity at a time and inspect variable values.
  • Breakpoints: pause at a specific activity to inspect state.
  • Watch windows: track the values of variables and arguments live.
  • Highlight / slow motion: visually watch the bot's clicks to spot wrong targets.
  • Logs: use the platform's log viewer; add your own structured log lines.
  • Screenshots on failure: capture the screen when an exception occurs — invaluable for diagnosing.

Testing the Bot

A bot is software; test it like software:

  • Unit-level: test individual workflows with controlled inputs.
  • Integration: test against a staging or sandbox copy of the target apps.
  • Edge cases: empty files, duplicate rows, unexpected formats, missing fields, special characters.
  • Re-run tests: confirm idempotency — running twice yields the same correct end state.
  • UAT: let a business user run the bot on real scenarios and sign off.
Never test against production data with write access. Use sandboxed systems or synthetic data. Where sandboxes are impossible, use read-only validation runs and a human review step.

Case Study: Building a Simple Invoice-Check Bot

Scenario: a bot that reads invoices from an inbox folder, validates that each has a vendor, an amount, and a date, and moves valid invoices to a processed folder while flagging invalid ones.

  1. PDD: define the folder paths, required fields, and rules (amount > 0, date not in future, vendor non-empty).
  2. Green path: get files from inbox, for each: read Excel, validate fields, copy to processed folder, log summary.
  3. Exceptions: invalid file → move to "invalid" folder with a reason note; missing folder → retry once then fail with notification.
  4. Logging: log each file name and outcome (processed/invalid).
  5. Test: create 10 invoices: 7 valid, 3 invalid in different ways; confirm outcomes and that nothing is lost.
Practice Task: Using the free Community Edition of your chosen RPA tool (or Robocorp open-source), build a bot that: reads a small Excel file of names and amounts, opens a text editor or notepad, types each line "Name: Amount", and saves the file. Add logging and a Try/Catch that writes a readable error if the source file is missing. Test it by deleting the source file once.
