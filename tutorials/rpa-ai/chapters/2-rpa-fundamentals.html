2. RPA Fundamentals

Chapter 2

What is RPA?

Robotic Process Automation (RPA) is software that configures digital "bots" to automate business processes by interacting with applications the way a human would — clicking buttons, typing into fields, reading screens, and moving data. RPA operates at the user-interface (UI) layer, which is why it can work across systems without changing the underlying applications or needing APIs.

An RPA bot is not a physical robot. It is a software program that follows a defined sequence of steps called a workflow. The key characteristics of classic RPA are:

  • UI-level interaction: The bot drives existing applications through their screens.
  • Rules-based: The workflow encodes explicit, repeatable instructions.
  • Deterministic: Given the same input, the bot performs the same steps.
  • Configurable, not coded from scratch: Most workflows are built with drag-and-drop design tools, though scripting is available for advanced cases.

How a Bot Works

Under the hood, an RPA bot is a program that performs a sequence of operations:

  1. Read input: pull data from an Excel file, CSV, database, email, or screen.
  2. Navigate: open applications (ERP, CRM, web portals), log in, and move between screens.
  3. Interact: use selectors to locate UI elements, then click, type, or select.
  4. Extract: read values from the screen or documents.
  5. Manipulate: apply logic — conditions, loops, calculations, data transformations.
  6. Write output: save results to systems, databases, files, or notifications.
  7. Handle errors: detect failures and follow recovery paths, such as retries or escalation to a human.
Analogy: RPA is like recording a macro — but far more robust. A macro works only inside one application (e.g., Excel). RPA works across any combination of applications and systems because it operates at the UI layer and uses "selectors" that reliably identify interface elements.

RPA vs APIs vs Scripting

RPA is one of several ways to automate. Choosing the right mechanism matters:

ApproachHow It WorksStrengthWeakness
API integrationDirect programmatic calls to an application's servicesFast, reliable, scalable, well-supportedRequires the system to expose APIs and development effort
Scripting (Python, PowerShell)Code that drives files, databases, or CLI toolsPowerful, flexible, freeHard to maintain; no UI interaction or governance out of the box
RPAUI-level automation with design tools, orchestrator, governanceWorks with legacy/no-API systems; business-friendly; auditableFragile against UI changes; slower; not ideal when APIs exist
Best practice: Use APIs first when the system supports them. Use RPA to bridge the gaps — legacy systems, vendor portals, Citrix environments — and to orchestrate work across many systems in one workflow. This "API-first, RPA-to-fill-gaps" approach is the standard in mature automation teams.

Characteristics of a Good RPA Candidate

Not every process should be automated with RPA. Good candidates share most of these traits:

  • High volume: Executed frequently (daily, hourly, or continuously).
  • Rules-based: Steps and decisions are explicit and stable.
  • Digital inputs: Data is accessible electronically (files, screens, databases).
  • Low exception rate: Few edge cases requiring judgment; exceptions are known and handleable.
  • Stable environment: The applications and screens do not change often.
  • Manual, error-prone today: The current process is slow, inconsistent, or swivel-chair.

RPA's Limitations

Understanding where RPA fails is as important as knowing where it shines:

  • Fragility: Bots break when applications change their UI, layouts, or authentication flows.
  • No understanding: Classic RPA cannot read a scanned document, interpret meaning, or handle ambiguity.
  • Speed ceiling: UI automation is slower than API calls; not suited to high-performance integrations.
  • Maintenance burden: Bots need ongoing monitoring and upkeep; a large bot estate without governance decays.
  • Not a strategy: Automating a broken process just makes the broken process faster. Process design comes first.
Common failure mode: Teams automate a messy process "as-is" and are surprised when the bot fails at the same exception-prone steps the humans struggled with. Always simplify and standardize the process before automating it — the classic "automate the green path, handle exceptions deliberately" approach.

The RPA Development Lifecycle

A disciplined RPA project follows a lifecycle:

  1. Identify: discover and prioritize candidate processes (see process mining, Chapter 11).
  2. Assess: feasibility, ROI, complexity, and risk of the process.
  3. Document: produce a Process Definition Document (PDD) — step-by-step, with screenshots and rules.
  4. Develop: build the workflow in the RPA tool, from a small pilot slice first.
  5. Test: validate against test data, edge cases, and error paths; run in a staging environment.
  6. Deploy & run: schedule on the orchestrator, with logging and monitoring.
  7. Maintain & improve: monitor exceptions, tune, and re-assess as the process evolves.

Case Study: The Swivel-Chair Process

A classic RPA win is the "swivel-chair" process. An order-entry clerk receives an email with an order file, opens the ERP, searches for the customer, enters each line item, saves, and replies with the order number — repeating this 200 times a day. Each transaction takes 6 minutes with a typo rate of about 3%. An RPA bot:

  • Watches a shared inbox for order emails.
  • Extracts the attached file and validates the format.
  • Logs into the ERP, creates the order, and enters each line.
  • Checks a "reject" list and routes matching orders to a human queue.
  • Posts the confirmation email and logs the full transaction for audit.

The same transaction now takes under a minute, runs 24x7, has near-zero error rate, and every action is logged. The clerk moves to handling exceptions and customer questions — higher-value work.

Practice Task: Take one task from your list in Chapter 1 and write it out as a numbered, step-by-step workflow, exactly as you would instruct an RPA bot. Include where data comes from, which applications are touched, and what should happen if a step fails. This is your first draft of a Process Definition Document (PDD).
