The Assistant at Work: Chats, Projects, Artifacts, and Controls

Chapter 1 oriented you to the workspace. This chapter turns that orientation into working practice. An assistant is not one single thing: it is a conversation, a place to keep recurring context, a panel where outputs take shape, and a set of controls that change how answers are produced. A candidate who understands only the chat box will handle simple requests but will struggle with scenario questions that hinge on where work should happen or which control should be used.

The organizing idea is simple. Different kinds of work belong on different surfaces, and different controls adjust different parts of the result. A short question belongs in a chat. A recurring responsibility with a stable body of background material belongs in a project space. A deliverable that you expect to revise several times belongs in an artifact. Once you can make that match, the rest of the chapter's features become tools you reach for deliberately rather than switches you flip at random.

Learning objectives

After studying this chapter, you should be able to:

  • Explain the conversation as a working surface, including turns, attachments, and why a clean thread improves results.
  • Distinguish a one-off chat, a persistent project space, and an iterable artifact, and choose among them for a given task.
  • Describe what response controls change and how they differ from the prompt itself.
  • Recognize the accuracy limits of voice and dictation entry and the role of scheduled or recurring tasks.
  • Explain research-oriented modes, memory features, sandboxed code execution, and packaged skills at a principle level.
  • Identify privacy and verification implications of each feature so you can answer judgment-based exam questions.

Key concepts

The conversation as a working surface

The conversation is the most familiar surface, but it is worth examining precisely. A turn is one exchange: a message you send and the assistant's reply. Each turn is not isolated. The assistant reads the current message together with earlier turns in the thread, so a conversation accumulates context as it grows. This is why a thread behaves like a shared workspace rather than a stack of independent questions.

That accumulation is useful and risky in equal measure. It is useful because you can refer back to earlier decisions without restating them: "apply the same tone as the first draft" works when the first draft is in the thread. It is risky because irrelevant early material stays present and can pull later answers off course. A thread that began with a discussion of pricing and later turns into a drafting task may carry pricing assumptions into the draft unless you explicitly narrow the scope.

Attachments are files or other material you add to a turn. They give the assistant source content to work from: a spreadsheet to summarize, a policy document to interpret, a set of notes to reorganize. An attachment changes what the assistant can see, but it does not automatically change what the assistant should do. The instruction in your message still has to say what to produce from that material. A common beginner error is to upload a document and write only "thoughts?" — the attachment supplies content while the prompt supplies no task.

A clean thread is one whose accumulated context supports the current request rather than competing with it. Three habits keep a thread clean:

  • Start a new conversation when the subject genuinely changes. Carrying unrelated history forward is rarely helpful.
  • Restate the essential constraints near the point where they matter, even if they appeared earlier.
  • Remove or ignore side threads that no longer apply, and say so explicitly when continuing a long conversation.

Exam note: Scenario questions often contrast "continue the existing thread" with "start a fresh conversation." The deciding factor is whether the earlier context helps or contaminates the new task. There is no universal rule that continuing is better.

Consider an analyst who spends twenty turns refining a budget memo, then asks the assistant to draft a customer-facing announcement. The budget figures and internal cautions in the thread are not appropriate for the announcement. A fresh conversation, or an explicit instruction to disregard prior material, is the safer choice.

Project spaces: persistent context with uploaded knowledge

A chat is built for a conversation. A project space is built for an ongoing responsibility. It persists beyond a single thread and can hold several things a chat cannot hold well: a stable set of background documents, standing instructions that apply to every conversation inside it, and a history of related work.

Think of a project as a container with three layers. The first layer is purpose — a plain statement of what this space is for. The second is knowledge — uploaded files that the assistant can draw on when working inside the project. The third is instructions — standing guidance about role, scope, format, and boundaries that should apply without being repeated in every message.

A support team maintaining a product FAQ might keep the current help articles, the tone guide, and the escalation policy in one project. New conversations inside that project inherit the same background. A coordinator does not need to re-upload the policy each time or remind the assistant of the house style. That is the practical value of persistence: consistency across many sessions with less repeated setup.

Persistence is not the same as perfection. Uploaded knowledge can become stale, two documents can disagree, and standing instructions can drift away from current policy. A project needs an owner who decides what belongs inside it and when material should be updated. If the FAQ changes but the uploaded copy does not, the project will confidently reproduce outdated guidance. Chapter 14 treats project maintenance in depth; for now, the exam-relevant point is that a project is a governed space, not a dumping ground.

A short set-up sketch makes the structure concrete:

PROJECT: Quarterly customer briefing
PURPOSE: Produce a consistent briefing note from approved sources.

KNOWLEDGE TO UPLOAD
- Current product overview (approved version, with date)
- House style and terminology guide
- Prior briefing notes marked "approved"

STANDING INSTRUCTIONS
- Role: assistant to a briefing coordinator
- Use only uploaded knowledge for factual claims
- Format: short executive summary, then three sections, then risks
- Flag anything the sources do not support; do not fill gaps
- Do not include pricing figures unless they appear in an uploaded source

TEST BEFORE USE
- Ask one real request and check: scope, format, sourcing, omissions

Try it: After sketching a project, write one representative request and one deliberately awkward request. If the standing instructions hold up under both, the set-up is probably sound. If they collapse under the awkward one, the instructions need sharper boundaries.

Artifacts: separately rendered, iterable outputs

An artifact is an output that is rendered as its own object rather than living only inside a message. It can be opened, viewed, and revised as a distinct thing. Common forms include a document, a block of code, a visual draft, and a simple interactive view that a user can click through.

The distinction matters because a chat reply and an artifact support different working styles. A reply is excellent for an answer you will read once. An artifact is excellent for a deliverable you will iterate. When the assistant produces a document as an artifact, you can ask for a change to a specific section, compare versions, and keep the surrounding conversation as the record of decisions. The object evolves while the thread explains why.

Artifact types vary in what they are good for:

  • Documents suit structured prose that will be edited, reviewed, and shared.
  • Code suits a script or snippet that will be run, inspected, or pasted into a repository.
  • Visual drafts suit layouts, diagrams, and mockups where shape and arrangement carry meaning.
  • Simple interactive views suit small tools or demonstrations where a user needs to try inputs and see results.

An artifact is not automatically correct. Rendering something neatly can create a false sense of finish. A polished document artifact that contains an unsupported claim is still an unsupported claim. Treat an artifact as a convenient workspace for refinement, not as evidence of quality. The verification habits in Chapters 6 and 7 apply to artifacts every bit as much as to chat replies.

Common mistake: Asking for "a better version" of an artifact without naming what should change. Iteration works when feedback is specific: shorten the summary, replace the generic closing, align the table headings with the source. Vague feedback produces vague revision.

Choosing the right surface

Many exam items are really matching problems. The candidate must notice the shape of the work and select the surface that fits. The table below maps common task types to a recommended surface and the reason behind the choice.

Task type Best surface Why this surface fits
One quick question about a term Chat The need is a single answer; setup would cost more than the task.
A long discussion that changes direction midway A new chat for the new direction Fresh context prevents earlier assumptions from leaking into the new topic.
Weekly report built from the same approved sources Project space Persistent knowledge and standing instructions keep output consistent across sessions.
A proposal you expect to revise five times Artifact (document) The output is a distinct object that supports targeted iteration and version comparison.
A small calculation or file transformation Chat plus sandboxed code execution The tool does the mechanical work; the chat explains the result.
A mockup of a simple screen flow Artifact (visual or interactive draft) Shape and interaction carry information that prose cannot convey.
Research that must show where claims came from Chat with a research-oriented mode Source gathering and citation are the point of the task.
A snippet that will be pasted into a codebase Artifact (code) Code is easier to inspect, copy, and revise when rendered on its own.

Two patterns are worth memorizing. First, recurrence points toward a project: if the same background and the same rules will be needed again, persistence saves effort and improves consistency. Second, iteration points toward an artifact: if the output will be shaped repeatedly, give it a surface of its own. A chat remains the default for everything else.

Response controls: shaping the answer without rewriting the prompt

Response controls are settings that influence how the assistant presents an answer: length, verbosity, tone, and format. They differ from the prompt itself in an important way. The prompt says what to produce; controls say how to present it. A prompt might ask for a comparison of two options. A control might make that comparison terse and formal rather than long and conversational.

This distinction is tested because controls are often treated as a substitute for clear instructions. They are not. If a prompt is vague about the decision to be made, no length setting will make the answer useful. Controls tune delivery; they cannot repair missing substance. Conversely, a well-specified prompt can still arrive in an unhelpful shape if the delivery does not fit the reader. Used together, they work well.

Control What it changes What it does not change
Length or verbosity Amount of detail and expansion in the reply Whether the underlying facts are correct or complete
Tone Register and style, such as formal, neutral, or conversational Authority; a confident tone is not accuracy
Format Structure such as bullets, table, or short sections Whether the structure matches the reader's actual next step
Reasoning depth How much step-by-step explanation is surfaced Access to facts the assistant does not have

A useful way to think about controls is as a second filter. First write a prompt that states the task, constraints, and required content. Then set controls to match the audience. A briefing for a busy reviewer might be short and structured. The same findings prepared for a training session might be longer and more explanatory. The underlying analysis is unchanged; the packaging differs.

Exam note: If a scenario asks how to make an answer shorter without changing its meaning, the answer is usually a response control or a revision instruction. If the scenario asks how to make an answer correct, the answer is verification against sources, not a control adjustment.

Voice, dictation, and scheduled tasks

Not all input arrives as typed text. Voice entry and dictation let a user speak a request or transcribe spoken words into text. These entry points improve speed, especially on mobile devices or while a user is away from a keyboard. They also introduce accuracy limits worth naming on an exam.

Speech recognition can mishear domain terms, numbers, product names, and homophones. Punctuation and structure often disappear, which can turn a carefully phased request into an ambiguous run of words. Background noise, accents, and fast speech raise the error rate. The practical response is to treat dictated input as a draft: check names, figures, and technical terms before sending, and add structure if the transcription flattened it. A dictated prompt containing the wrong number is still the wrong number when the assistant answers it faithfully.

Scheduled or recurring tasks run a request at a set time or on a repeating schedule. At a principle level, they automate routine information work: a morning digest, a weekly summary of changes, a periodic check that a source has been updated. The value is consistency and the removal of a repeated manual step.

Scheduling also raises the stakes of setup. A one-off prompt can be corrected after you read the answer. A recurring task repeats whatever instruction it was given, including any flaw. Before scheduling, confirm three things: the source is stable and authorized, the instruction is unambiguous, and someone will review the output. A recurring task that pulls from a stale document will keep producing stale results until someone intervenes. An output that no one reads is automation in name only.

SCHEDULED TASK SKETCH
Name: Monday source freshness check
Trigger: weekly, Monday morning
Request: list items in the uploaded source index whose "verified" date
         is older than 30 days; return a table with item, date, owner role
Review: coordinator reads output before any update is made
Stop condition: pause if the source index cannot be read

Research-oriented modes

A research-oriented mode is a mode in which the assistant is directed to gather material from sources and present claims with references rather than answer purely from its own generated content. The defining features are source gathering and citation, not speed or cleverness.

Used well, such a mode changes the kind of answer you get. Instead of a fluent summary with no traceable basis, you receive claims attached to sources you can inspect. That makes verification possible. It also makes verification necessary: citations must be checked, because a source marker is not proof that the source says what the answer claims. Chapter 6 covers source triangulation in detail.

Three exam-relevant limits are worth keeping in view. First, a cited answer can still misrepresent a source through a wrong attribution or an overbroad summary. Second, a source can be current in one area and outdated in another. Third, a research mode does not decide what counts as evidence for the decision at hand — that judgment remains with the person framing the request. When the stakes are high, the mode is a starting point for review, not a replacement for it.

Memory features and privacy implications

Memory features let an assistant retain certain facts or preferences across conversations. At their simplest, they record preferences such as a preferred format or level of detail. At their broadest, they may store information about a user's role, projects, or recurring constraints.

The convenience is obvious. A user does not need to restate a preference in every thread. The privacy implications are equally real. Memory turns a preference into stored data, and stored data raises questions: what was saved, who can see it, how long it is kept, and how it can be removed. In an organizational setting, a preference recorded in one context may be inappropriate in another. A detail shared in a casual drafting session should not quietly follow a user into a confidential workflow.

A few principles keep memory use defensible:

  • Save preferences that genuinely generalize, not one-off details tied to a single task.
  • Treat anything sensitive as unsuitable for memory, even if it would be acceptable inside a single controlled conversation.
  • Assume that retained material may be reviewed under organizational policy, and act accordingly.
  • Know how to inspect and delete stored items; convenience without control is a poor trade.

Privacy note: A frequent exam distractor suggests that because a conversation feels private, its contents are automatically protected. Feeling private is not a control. Policy, permissions, and retention rules decide how data is handled.

Code execution as a sandboxed tool

Some assistants can run code in an isolated environment, often called a sandbox. This gives the assistant a way to do exact mechanical work: calculate a figure, sort a list, transform a file, or test a small piece of logic. The sandbox is separated from your own machine and from organizational systems, which limits the damage a mistake can cause.

The key insight is the division of labor. Language models are not reliable arithmetic engines; a sandbox can add, aggregate, and transform with precision. But the sandbox only does what the generated code tells it to do. The instruction still has to describe the correct operation, and the result still has to be checked against the input. A beautifully executed wrong formula is still wrong.

Good candidates for code execution include recalculating totals, converting formats, deduplicating records, and checking a rule against a list. Poor candidates include tasks where the decision depends on judgment, context, or information the sandbox cannot access. Code execution is a tool for computation and transformation, not a source of truth about the world.

Two limits matter for the exam. First, execution in a sandbox does not imply access to external systems unless a connector or tool explicitly grants it. Second, a successful run is not validation: the code may run cleanly while implementing the wrong rule. Ask for the assumptions behind the calculation and spot-check a small input before trusting a large output.

Skills: packaged instructions the assistant can draw on

A skill is a reusable package of instructions that gives the assistant a defined way to handle a class of tasks. Rather than pasting the same detailed guidance into every prompt, a user can make that guidance available as a packaged capability the assistant draws on when it fits.

The analogy to a checklist is useful. An organization might have a standard way to review a contract, format a release note, or structure a weekly report. Encoding that approach as a skill makes the method repeatable. When a request matches, the assistant applies the packaged steps and conventions without the user restating them each time.

Skills differ from a project's standing instructions in scope and portability. Project instructions belong to one space and apply to everything inside it. A skill is typically invoked for a particular kind of task and can be used wherever that task arises. They also differ from a response control: a skill changes the procedure followed, while a control changes how the answer is presented.

Three cautions keep skills in their proper place. A skill does not guarantee correctness; the underlying instructions may be flawed or outdated. A skill should be checked against the current request, because a method that fits one situation may mislead in another. And a skill does not transfer authority: if a task requires human approval, packaging it as a skill does not remove that requirement.

Worked scenario

An operations coordinator needs a dependable way to produce a monthly service summary. Each month, the same three approved source files are reviewed, a short summary is written for a leadership audience, and a table of open issues is maintained. The first attempt was a single long chat that mixed source questions, drafting, and formatting requests. By the third month, the thread had grown unwieldy, some figures reflected an older source version, and the summary's tone varied from month to month.

The coordinator considers four options and reasons through each.

Option A — keep extending the original chat. This is tempting because the history contains useful decisions. But the thread also contains outdated figures and abandoned drafts. Continuing would carry stale context into a task that depends on current sources. Rejected.

Option B — create a project space with the three approved files, standing instructions for audience and format, and a separate conversation for each month. This matches recurrence: the same background and rules are needed every cycle. Uploaded knowledge can be version-labelled, and standing instructions keep the tone consistent. Each monthly conversation stays clean because it begins fresh inside a stable container. Selected.

Option C — rely only on memory features. Memory could retain a format preference, but it would not hold the approved source files or enforce a sourcing rule. It also risks storing details that should not persist. Rejected as insufficient.

Option D — use a scheduled task with no review step. A recurring task could assemble a draft automatically, but the source files change and the summary goes to leadership. Without a named review step, an outdated source would reach the audience unchecked. Rejected.

The resolution combines surfaces rather than relying on one. A project space holds the approved files and standing instructions. Each month begins a new conversation inside that project. The summary itself is produced as a document artifact so it can be revised section by section after review. A scheduled task sends a reminder to check source dates; it does not publish anything. Response controls are set to keep the leadership summary short and neutral, while the project instruction requires every figure to be traceable to an uploaded file.

The result is a workflow whose structure encodes the lessons of the chapter: persistent context where the work recurs, a clean thread for each cycle, an artifact where iteration happens, controls for presentation, and a human review point before anything is sent.

Exam note: When a scenario presents several features, the strongest answer often combines them in a way that assigns each feature a clear job. Be wary of options that solve one problem while creating a new risk, such as automation without review.

Common mistakes

  • Treating a project space as a larger chat and uploading documents without labelling versions or assigning an owner.
  • Expecting response controls to fix factual errors; controls shape presentation, not accuracy.
  • Continuing a long thread after the subject changes, allowing irrelevant context to influence the new task.
  • Uploading an attachment without stating what should be done with it.
  • Assuming that a neatly rendered artifact has been verified.
  • Trusting dictated input without checking names, numbers, and technical terms.
  • Scheduling a recurring task before confirming that its source is stable and that someone reviews the output.
  • Storing sensitive details in memory because they were convenient in one conversation.
  • Believing that a citation in a research-mode answer proves the claim; the source still needs checking.
  • Assuming that code running successfully in a sandbox means the correct operation was performed.

Chapter summary

  • The conversation is a cumulative working surface; turns build context, attachments supply material, and clean threads protect against contamination.
  • Project spaces persist knowledge and standing instructions, making them the right choice for recurring work with stable background.
  • Artifacts render outputs as distinct objects suited to iteration: documents, code, visual drafts, and simple interactive views.
  • Match surface to task: chat for one-offs, project for recurrence, artifact for iteration, and a fresh thread when the subject changes.
  • Response controls adjust length, verbosity, tone, and format; they do not fix weak prompts or verify facts.
  • Voice and dictation are fast but error-prone with names and numbers; scheduled tasks repeat instructions faithfully, flaws included.
  • Research modes gather and cite sources but still require checking; memory stores preferences with privacy consequences.
  • Sandboxed code execution handles calculation and transformation precisely, provided the rule is right; skills package reusable instructions without transferring authority.
  • Across every feature, the exam favors the answer that names the risk and keeps a human review point where it matters.

Checkpoint questions

  1. An analyst has discussed pricing for twenty turns and now wants a short internal announcement that must not mention pricing. What is the best first step?

A. Continue the same thread and ask the assistant to ignore earlier pricing.

B. Start a fresh conversation and state the restriction explicitly.

C. Lower the verbosity control and reuse the thread.

D. Move the work into an artifact without changing the thread.

  1. Which combination best fits a weekly report built from the same approved sources and revised section by section after review?

A. A chat with a short prompt and high verbosity

B. Memory features with a scheduled task and no review

C. A project space for knowledge and instructions, plus a document artifact for the report

D. A research mode with no sources supplied

  1. What does a response control such as tone change?

A. The facts available to the assistant

B. The register and style in which the answer is presented

C. The permissions granted to a connector

D. The amount of memory retained across chats

  1. A dictated request contains a misheard figure. The assistant answers using that figure. Who is responsible for catching the error before the answer is used?

A. The sandbox, because it validates all input automatically

B. The response control, because it checks numeric accuracy

C. The user, who should review dictated input before relying on it

D. The project space, because it rejects incorrect numbers

  1. Which statement about research-oriented modes is most accurate?

A. A citation guarantees that the source supports the claim.

B. They remove the need to judge what counts as evidence.

C. They gather sources and present claims with references, which still require checking.

D. They are useful only for tasks that need no verification.

  1. A recurring task pulls from a document that is updated monthly. What is the safest setup at a principle level?

A. Schedule the task and publish its output with no review.

B. Include a freshness check, a clear instruction, and a named review of the output.

C. Store the document's contents in memory and stop checking the source.

D. Use a longer response so errors become less likely.

  1. What is the main difference between a project's standing instructions and a skill?

A. Standing instructions apply within one space; a skill packages a reusable method for a task type.

B. Skills control tone; standing instructions control length.

C. Standing instructions run code; skills cannot contain instructions.

D. There is no difference; the terms are interchangeable.

Answers and rationale

  1. B. A fresh conversation removes the pricing material that could contaminate the announcement, and stating the restriction explicitly makes the boundary unambiguous. A is weaker because asking a model to ignore material it can still see is less reliable than removing that material from context. C changes presentation only; lower verbosity does not remove outdated assumptions. D changes the output surface but leaves the contaminated thread in place.

  2. C. The project holds recurring knowledge and instructions, while the artifact supports section-by-section revision after review. A lacks persistence and treats verbosity as a quality control. B introduces exactly the risk the scenario must avoid: no review and memory used as a substitute for source files. D describes research without supplying sources, which defeats consistency.

  3. B. Tone governs register and style. A is wrong because controls do not add facts or grant knowledge. C confuses response controls with connector permissions, which are a separate access question. D confuses presentation settings with memory retention policy.

  4. C. Dictation is error-prone with figures, so the user must check input before relying on the result. A is wrong because a sandbox executes code; it does not validate the intent or the numbers typed into a prompt. B is wrong because response controls never check numeric accuracy. D is wrong because a project space stores context, not a numeric validation gate.

  5. C. Research modes gather and cite sources, and the citations still require verification against the source text. A is a classic distractor: a citation marker is not proof of support. B is wrong because judging evidence remains a human responsibility. D reverses the purpose of the mode, which exists precisely for tasks where verification matters.

  6. B. Freshness checks, unambiguous instructions, and human review address the two failure modes of recurring work: stale sources and unchecked output. A automates the risk by publishing without review. C replaces a living source with retained data that will age. D mistakes length for accuracy.

  7. A. Project instructions are scoped to a space; a skill packages a method that can be reused when the matching task appears. B assigns control-like roles to both and is incorrect. C misdescribes both features. D ignores a real distinction in scope and portability that scenario questions often test.
