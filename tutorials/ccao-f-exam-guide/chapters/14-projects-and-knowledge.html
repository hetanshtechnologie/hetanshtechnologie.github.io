Building Projects: Knowledge, Instructions, and Maintenance

A single chat handles one question and then ends. A project is a durable working space: a body of knowledge, a set of standing instructions, and a history of work that help the assistant behave consistently across conversations. Many exam scenarios are really tests of whether the candidate sees that a task has outgrown a chat.

This chapter treats a project as a system with three moving parts: the knowledge supplied, the instructions governing how it is used, and the habits that keep both trustworthy. A weakness in one part undermines the others. Careful instructions cannot rescue contradictory documents, and good documents lose value when nobody removes superseded copies.

Learning objectives

By the end of this chapter, you should be able to:

  • Decide when a recurring task warrants a project space instead of a one-off chat.
  • Set up a project around a clear purpose, defined scope, and named owner.
  • Organize uploaded knowledge so that retrieval is predictable and authoritative sources win.
  • Write project instructions that state role, scope, format, and boundaries.
  • Test instructions with representative prompts and revise them deliberately.
  • Recognize stale or conflicting documents and act on them before they affect output.
  • Apply least-privilege permissions and a realistic maintenance cadence to a shared project.

Key concepts

When a project space beats a one-off chat

The question is not whether a task matters — important one-off tasks belong in chats — but whether it is recurring, grounded in shared material, and expected to produce a consistent answer. A project earns its keep when several conversations need the same background, house style, and boundaries.

Summarizing one contract that just arrived needs no prior context, no recurring format, and no reuse by others; a chat is enough. A team that reviews contracts weekly against the same policy, produces the same summary structure, and hands the result to a reviewer needs a project. The policy, template, and review rules are loaded once and applied every time.

Four signals point toward a project: repetition, shared context, consistency of output, and continuity so later work can build on earlier decisions without re-uploading everything.

Signal One-off chat is sufficient A project space is better
Frequency Single, isolated request Recurring or repeated request
Source material Supplied inside the prompt Shared documents reused across tasks
Output Free-form, unique each time Repeatable format or house style
Audience One person, one moment A team or a recurring review process
Memory need None beyond the current exchange Prior decisions and terminology must persist
Risk profile Error affects one answer Error propagates into many deliverables

Exam note: When a scenario mentions repeat work, a shared document set, and a required output format together, the correct choice is almost always to establish a project with knowledge and instructions, not to keep rewriting longer prompts in separate chats.

Projects are not automatically better; they carry setup cost and require upkeep. If material changes daily, one person is involved, or every request is unique, a well-written chat prompt is simpler. Use the lightest structure that solves the recurrence problem.

Defining the project's purpose before adding anything

A project without a stated purpose becomes a storage folder with a chat attached. Define the deliverable, audience, authoritative material, and limits before uploading anything.

"Help with customer questions" invites answers to everything from billing disputes to product roadmaps. A tighter purpose — "draft responses to standard product questions from the approved handbook and current release notes; hand refunds and legal claims to a reviewer" — shows which documents belong and what the assistant should refuse to decide.

A practical setup record contains five fields:

  1. Purpose: the deliverable and the consumer of that deliverable.
  2. Scope: the topics covered and, explicitly, the topics excluded.
  3. Sources of truth: which documents outrank others when they disagree.
  4. Owner: the role accountable for content and instructions.
  5. Review point: the date or event that triggers a freshness check.

The exclusion list is the field most often skipped. Stating what the project will not do keeps outputs predictable and gives the assistant a handoff path instead of a guess. "Out of scope: pricing exceptions, contract interpretation, and personal data" beats a general warning to be careful.

Organizing knowledge so retrieval is predictable

Uploading files is easy. Making them retrievable is a design problem. The assistant can only draw on material that is distinct, discoverable, and internally coherent. When two documents cover the same subject with slightly different wording, retrieval may surface the wrong one, and the resulting answer can look confident while being based on an outdated rule.

Start with one topic per document. A single file that mixes a return policy, a shipping schedule, and a contact directory is harder to interpret than three focused files. Give each document a title that states its subject, its status, and its effective date. A name such as returns-policy-v3-effective-2026-04.txt communicates more than policy-final-final.txt. Avoid vague labels like "latest," "updated," or "copy," because they age badly: today's "latest" becomes tomorrow's competing source.

Add a short header inside each document repeating the subject, effective date, owner role, and status; it helps both the assistant and the reviewer. Use consistent headings for recurring subtopics so sections line up across documents. If one file says "Eligibility" and another says "Who qualifies," comparisons become needlessly hard.

Prefer a canonical source plus derived summaries. The canonical document is the one authoritative copy; a summary exists to make retrieval easier, not to replace the source. Mark summaries clearly as summaries, and state which document they derive from. When the policy changes, the canonical file is updated first and the summary is refreshed or removed.

Do not upload an entire archive simply because it is available. Label historical records as such and keep them apart from current guidance; old versions searchable beside current rules lead to answers quoting retired policies.

Common mistake: Treating the knowledge upload as a one-time event. A project's document set is a living collection; without an intake rule for new material, duplicates accumulate and retrieval quality decays.

Knowledge types and freshness risk

Freshness risk is the probability that a document is no longer correct and that using it would cause a meaningful error. Two factors drive it: how often reality changes, and how much damage a wrong answer causes. A contact list may change monthly with little harm; a regulatory summary may change rarely but cause serious harm.

Knowledge type Typical example Change pattern Freshness risk Maintenance action
Policy and procedure Expense approval rules Occasional, formal revisions High Link to effective date; retire prior version on approval
Product specifications Device dimensions, compatibility Changes with each release Medium to high Tie to release number; review at every launch
Pricing and offers Discount tables, fee schedules Frequent, sometimes unannounced High Short review cycle; remove expired tables promptly
Contact and ownership data Team directories, escalation routes Frequent small changes Medium Named owner; quick check before sensitive handoffs
Templates and writing standards Report skeleton, tone guide Stable for long periods Low Version on revision; keep examples aligned
Historical records Past decisions, archived audits Never meant to change Low for accuracy, high for misuse Label clearly as historical; exclude from current guidance
Training examples Sample dialogues, annotated cases Rarely changed Low Refresh when house style or policy changes
Legal or regulatory summaries Sector rules, retention duties Infrequent but high consequence Very high Expert review on every trigger event; never rely on memory

The table is a starting point, not a fixed ranking: a stable document becomes dangerous if it contradicts a newer rule. The defense is to make freshness visible — dates, version labels, status, and owner role on every file that could influence an answer.

Exam note: If a scenario contrasts an older, detailed document with a newer, shorter notice that changes one rule, the newer authoritative notice wins. The candidate should expect the answer to involve updating or retiring the old material, not merely adding the new document beside it.

Writing project instructions: role, scope, format, and boundaries

Project instructions are standing directions for every conversation in the space. They are not a substitute for knowledge or a place to paste whole policies; they describe how the assistant should work with the knowledge. Four components do most of the work.

Role states perspective and audience: "Act as a support-drafting assistant for a product team; write for an informed non-specialist." Describe behavior, not credentials. Telling an assistant to act like a lawyer does not make it one; such wording invites overconfident output.

Scope tells the assistant which sources to use and in what order. This is where the source-of-truth decision from the setup record becomes operational: "Use the current approved handbook first; use release notes for product-specific details; ignore archived folders unless explicitly asked." Scope also covers time boundaries, such as "treat any figure without an effective date as unverified."

Format defines the expected output. State the sections, the approximate length, the tone, and whether citations or document names should appear. Most importantly, state what to do when information is missing: "If the handbook does not cover the question, write 'Not covered in current sources' and stop rather than filling the gap."

Boundaries state what the assistant must not do and where to hand off: invention, unverified commitments, personal data, external actions, and excluded topics. Pair each boundary with a path, such as "For refund exceptions, do not propose an amount; mark the draft for reviewer decision."

The template below can be adapted to almost any project. Replace the bracketed text and keep the four sections distinct.

PROJECT INSTRUCTIONS — [project name]

1. ROLE
You assist with [specific deliverable] for [audience].
Write in a [tone] register. Do not claim credentials or authority
that you do not have.

2. SCOPE AND SOURCES
Use only the materials in this project plus the user's current request.
Source priority: [authoritative source] > [secondary source] > [examples].
Ignore [archived or excluded material].
Treat content without an effective date as unverified.

3. OUTPUT FORMAT
Produce: [section 1], [section 2], [section 3].
Keep to approximately [length]. Name the sources used in [location].
If a required fact is absent, write "Not covered in current sources"
and do not guess.

4. BOUNDARIES AND HANDOFF
Do not [specific prohibited action, e.g. invent figures or promise refunds].
For [listed exception categories], stop and mark the item
"Reviewer decision required" with a one-line reason.
Do not take external actions; drafting only.

Try it: Take a project you use often and read its instructions against the four headings above. If "boundaries" is missing, add one rule and one handoff path, then check whether outputs change.

Keep instructions short; long text reduces compliance. Move detailed explanations into knowledge documents and reference them from the instructions.

Testing instructions with representative prompts

Instructions are a hypothesis until tested. A small, repeatable prompt set turns them into something measurable. Build the set from four categories:

  • Typical prompts that represent the majority of real work. These confirm that the normal path still works.
  • Edge prompts with unusual phrasing, missing details, or mixed topics. These reveal whether the format holds under pressure.
  • Conflict prompts that rely on two documents disagreeing. These reveal whether source priority is obeyed.
  • Out-of-scope prompts that touch excluded topics or sensitive data. These reveal whether boundaries and handoffs fire.

For each prompt, decide in advance what a good answer looks like: correct source used, required sections present, proper date stated, and the right handoff triggered where relevant. Run the set after any change to instructions or knowledge. Change one variable at a time; if you edit the format rule and the source-priority rule together, a later failure cannot be traced to either one.

Record the prompt category, instruction version, pass or fail, and a one-line note. That evidence supports claims such as "the new policy did not break the standard summary" and catches regression, where fixing one behavior silently breaks another.

Keeping knowledge current when policies change

A policy change is a project event, not just a document edit. When a rule changes, work through the full chain: the authoritative document, every derived summary, the instructions that reference the rule, the test prompts built around the old rule, and any examples that demonstrate it.

Start by locating all copies. Search the project for the old term, the old number, and the old effective date. Replace or retire each occurrence. Retiring is safer than deleting without a trace: mark a document "Superseded by [new document], effective [date]" so that anyone reviewing the project understands why it is there. If the interface allows removal, remove it from the active knowledge set and keep the archived copy outside retrieval.

Next, check whether instructions encode the old rule. A boundary such as "do not approve refunds above the stated limit" may still be correct, but a scope line naming a specific policy version will not be. Update the version reference and re-run the conflict and edge prompts. Finally, communicate the change to the people who use the project, because they may have copies of old outputs in circulation.

Exam note: A policy update question usually has more than one correct action, but the best answer is the one that addresses both knowledge and instructions. Updating the document while leaving a version-specific instruction unchanged is incomplete.

Versioning and ownership of shared projects

Shared projects need a history: a version number on the instructions, a date on each file, and a short changelog. They answer three questions later — what was in force when an output was produced, who approved the change, and why.

Use a simple scheme: major version for structural changes, minor for wording. Record the change, date, approving role, and trigger. After a bad change, restore earlier instructions instead of layering corrections; accumulated patches are harder to reason about.

Ownership should be singular and explicit. "The support team" is not an owner in the operational sense. Assign a role — a team lead, a knowledge coordinator, or a designated reviewer — who is accountable for approving changes. Contributors can propose updates without holding approval rights. This separation matters most in team spaces where many people can upload files but only a few should decide which file becomes authoritative.

Plan for departure too: adjust access promptly and reassign documents that one person alone maintained. An unowned document is a maintenance risk even while its content is correct.

Permissions in team spaces

Permissions determine who can see, change, and govern a project. Follow least privilege: give each role the access it needs and no more. Distinguish reading knowledge from changing instructions; someone who consults a knowledge base does not need to rewrite the rules everyone follows.

Role Typical access What that enables Risk if over-granted
Consumer Read knowledge, use chat Draft work from approved material Low; limited to output quality
Contributor Read, propose or upload drafts Add new material for review Drafts may be treated as authoritative
Editor Maintain approved knowledge files Keep content current Unreviewed changes can alter answers
Instruction owner Change project instructions, approve sources Control behavior and source priority A single edit changes every user's output
Administrator Manage membership and settings Onboard, offboard, configure access Errors affect the whole project

Let a broad group read, a narrow group edit, and fewer still change instructions. If the tool separates "upload" from "publish," let uploads land in a draft area until reviewed; otherwise compensate with naming conventions and visible status labels.

Permissions also shape accountability: when everyone edits everything, no one knows which version was approved. Restricted approval lets a wrong answer be traced to a change and reversed, which matters when outputs feed external work.

Common mistake: Granting edit access to entire project instructions so that a contributor can fix one sentence. The safer path is to send the proposed wording to the instruction owner and have the change recorded once.

Recognizing stale or conflicting documents

Conflicts rarely announce themselves. They appear as two figures that differ by a small amount, a policy with no effective date, a document titled "draft" that everyone still cites, or a summary that disagrees with its own source. Train yourself to notice these signals before the assistant has to choose between sources.

Warning signs include:

  • Two documents on the same topic with different dates and no statement of which is current.
  • Version labels that conflict, such as "v4" in the title and "revised March" in the body.
  • Missing owner role or missing effective date on a rule that changes decisions.
  • Wording such as "temporary," "draft," or "for discussion" on material used in production.
  • References to a document that is no longer present in the project.
  • Examples that demonstrate a rule the current policy has replaced.

Do not ask the assistant to pick the more convincing document. Treat the conflict as governance: identify authority, confirm the effective date, mark or remove the losing document, and record the decision. If authority is unclear, escalate to the policy owner and pause the rule. An assistant asked to reconcile a contradiction often produces a fluent compromise wrong in both directions.

A maintenance cadence

Maintenance works when it is scheduled rather than remembered. A light cadence with recorded evidence is more reliable than an ambitious policy that nobody follows. Match the rhythm to the freshness risk identified earlier: volatile knowledge gets short cycles, stable material gets longer ones, and any significant policy event triggers an immediate review.

Trigger Activity Owner role Evidence to keep
Each product release or policy notice Review affected knowledge, retire old versions, re-test conflict prompts Knowledge coordinator Changelog entry and test note
Weekly during active use Scan new uploads and drafts; promote or remove them Editor Short intake log
Monthly Check dates, ownership labels, and broken references Team lead Freshness checklist
Quarterly Review instruction set end to end; run full prompt set Instruction owner Version bump and results
On team membership change Adjust access; reassign unowned documents Administrator Access change record
After a reported wrong answer Trace source, fix cause, add regression prompt Reviewer Incident note and updated test set

Keep the record simple. A single table with date, change, owner role, and reason is enough to reconstruct most decisions. The point of a cadence is not paperwork for its own sake; it is that a reader can tell, at a glance, whether the project is currently trustworthy.

Worked scenario

A product support team has been using individual chats to answer questions about a device. Answers vary between colleagues, refund quotes conflict, and a recent policy notice shortened the return window without anyone updating the handbook. The team lead proposes creating a project. Walk through the decision and the setup.

Step 1: Choose the structure. Recurring work, shared material, and a consistent response format for an external audience: three project signals at once. Retire the individual chats.

Step 2: Define purpose and scope. The project purpose is drafted as: "Draft responses to standard product questions using the approved support handbook and current release notes; flag refund exceptions and legal claims for a reviewer." Exclusions are listed explicitly: pricing exceptions, contract interpretation, and questions involving personal data. The team lead is named owner, and a monthly review point is set.

Step 3: Triage the knowledge. The inventory turns up the handbook, two release notes, an old return policy, a new notice, and a spreadsheet treated as a summary. The old policy is marked superseded and removed from active knowledge. The new notice is rewritten as a canonical policy file with an effective date and owner role. The spreadsheet is replaced by a short summary that names the policy file it derives from. Product specifications are kept with release numbers in their titles.

Step 4: Write instructions. The instruction set states a drafting role for an informed customer, source priority of approved handbook then current release notes then examples, a three-section output format with source names, and a boundary that forbids proposing refund amounts. The boundary includes a handoff: "mark Reviewer decision required with a one-line reason."

Step 5: Test. Five prompts are used: a standard question, an ambiguous one needing clarification, a question anchored to the old return window, a pricing exception, and a request containing personal data. The conflict prompt initially produces the old window because a stale summary is still present. The summary is removed, the test is repeated, and the correct window with its effective date appears. The out-of-scope prompts trigger the handoff as intended.

Step 6: Set permissions and cadence. Most support staff receive read access. Two editors may update knowledge files. Only the team lead can change instructions or approve a source. New uploads land in a draft area until reviewed. The changelog records the version of the instructions, the policy change that triggered the update, and the test results.

Resolution. Six weeks later a new policy revision arrives. Because the project has a single owner, dated sources, a changelog, and a test set, the change is absorbed in one controlled pass. No one has to search old chats to discover which rule was previously applied, and the answer about refunds still stops at the review boundary.

Common mistakes

  • Creating a project for a single question that never recurs.
  • Uploading every available file, including superseded drafts and personal notes.
  • Using filenames such as "final" or "updated" that lose meaning over time.
  • Writing instructions that restate document content instead of governing how it is used.
  • Omitting the "what to do when information is missing" rule.
  • Adding a new policy without removing or clearly marking the old one.
  • Giving all team members permission to edit instructions.
  • Asking the assistant to reconcile conflicting sources instead of fixing the sources.
  • Changing instructions and knowledge together, then being unable to trace a failure.
  • Letting a maintenance cadence exist only in memory rather than in a calendar.

Chapter summary

  • A project is justified by repetition, shared material, consistent output, and continuity; otherwise a chat is simpler.
  • Define purpose, scope, sources of truth, owner, and review point before loading content.
  • Predictable retrieval comes from one topic per document, distinctive names, visible dates, and a clear canonical source.
  • Freshness risk depends on both change frequency and the consequence of a wrong answer.
  • Project instructions have four parts: role, scope and sources, output format, and boundaries with handoffs.
  • Test instructions with typical, edge, conflict, and out-of-scope prompts; change one variable at a time.
  • A policy change requires updates to knowledge, instructions, examples, tests, and users.
  • Version records, singular ownership, least-privilege permissions, and a scheduled cadence keep a shared project trustworthy.

Checkpoint questions

  1. A coordinator answers the same type of intake question every day using a shared policy manual and a required three-section response format. What is the best structure?

A. Continue using separate chats, but write a longer prompt each time. B. Create a project containing the manual, standing instructions, and a defined output format. C. Ask the assistant to memorize the manual in one chat and reuse that chat forever. D. Upload the manual to a project but leave the format to each individual user.

  1. Which upload practice most improves retrieval predictability?

A. One file named "all-policies-complete.txt" containing every rule. B. Several files with similar names so that multiple sources appear for each topic. C. Separate, clearly titled files with effective dates, status labels, and one canonical source each. D. Keeping only the newest file and deleting all historical context without a record.

  1. Which knowledge type generally carries the highest freshness risk?

A. A stable writing-style template used for internal reports. B. An archived record of decisions from a completed project. C. A current regulatory summary that changes rarely but drives external disclosures. D. A set of annotated training examples for tone.

  1. Which item belongs in the boundaries section of a project instruction set?

A. The section order of the expected response. B. The rule that figures without an effective date must be labeled unverified. C. The instruction to mark refund exceptions for reviewer decision instead of proposing an amount. D. The name of the audience the output is written for.

  1. After instructions are revised, which testing approach gives the most useful evidence?

A. Reuse one familiar prompt and stop if it still works. B. Run a repeatable set covering typical, edge, conflict, and out-of-scope prompts, changing one variable at a time. C. Ask the assistant whether it thinks the new instructions are clearer. D. Test only the exact rule that changed and ignore everything else.

  1. In a shared project, which permission arrangement best reflects least privilege?

A. Everyone can edit instructions so that fixes happen quickly. B. Consumers can read knowledge, editors maintain content, and only an instruction owner changes behavior rules. C. Only the administrator may read any content, which prevents all errors. D. All contributors may publish files directly into active knowledge with no review.

  1. Two documents in a project disagree about the return window. What should happen first?

A. Ask the assistant to split the difference and quote an average. B. Use whichever document is longer, because it contains more detail. C. Identify the authoritative source and effective date, then mark or remove the superseded document. D. Add a third document repeating both values so that the assistant has more context.

  1. A policy notice changes a rule that appears in a knowledge file, a derived summary, an instruction example, and a test prompt. What is the most complete response?

A. Update the knowledge file only. B. Update the knowledge file and the derived summary, then re-run the affected tests. C. Update every occurrence, align instructions and examples, re-test, and record the change in the changelog. D. Delete the project and start again with the new notice.

Answers and rationale

  1. B. Recurring work, shared material, and a required format are the classic signals for a project with knowledge and standing instructions. A is weaker because long prompts must be rewritten and cannot be governed centrally. C relies on a single chat as pseudo-memory and gives the team no shared control. D captures the benefit of shared documents but discards the consistency that instructions provide.

  2. C. Focused files with distinctive titles, dates, and an explicit canonical source make it easier for retrieval to select the right material. A creates one undifferentiated blob that is hard to interpret. B deliberately creates competing sources, which increases ambiguity. D may remove a conflict but destroys audit history; archiving with clear labels is safer than silent deletion.

  3. C. A rule that rarely changes but drives external disclosures has severe consequences when wrong, giving it very high freshness risk. A and D are stable and low consequence. B is historical by design; its risk lies in misuse rather than in the record becoming inaccurate.

  4. C. Boundaries state what the assistant must not do and where it hands off; this option does both. A belongs to format. B belongs to scope and source rules. D belongs to the role statement.

  5. B. A varied repeatable set reveals whether normal work, unusual phrasing, source conflicts, and excluded topics all behave correctly, and isolating changes makes failures traceable. A checks only one path. C substitutes self-report for evidence. D risks regression in untested behavior.

  6. B. Access is matched to need: reading for consumers, content maintenance for editors, and behavior control for one instruction owner. A over-grants the most powerful change type. C is impractical and creates workarounds. D removes the review step that keeps drafts from becoming de facto policy.

  7. C. Conflicts are resolved by determining authority and effective date, then removing or clearly marking the losing source; the assistant should not arbitrate. A invents a number that matches neither policy. B treats length as authority, which is unreliable. D adds noise and leaves the contradiction unresolved.

  8. C. A policy change propagates through canonical content, summaries, instructions, examples, and tests, and the change should be recorded so later decisions are traceable. A and B are partial. D is disproportionate and loses the accumulated structure and history that made the project useful.
