Accuracy, Completeness, and Hallucination Detection

Learning objectives

  • Define accuracy and completeness in the context of an assistant's response, and tell the two apart.
  • Judge completeness relative to the specific request, not to a general impression of usefulness.
  • Check systematically that every requested part is actually present in an answer.
  • Explain why a fluent, confident answer is not evidence that it is correct.
  • Recognize the main categories of hallucination and pair each with a detection tactic.
  • Spot warning signs that a response may contain fabricated or unsupported content.
  • Ground requests in supplied material and ask for quotations or citations that can be checked.
  • Ask an assistant to mark what it does not know, and interpret that admission correctly.
  • Use source triangulation and a two-minute verification checklist before accepting or sharing an answer.

Key concepts

Accuracy and completeness are separate standards

When a reviewer says an answer is "good," that word can hide two judgments. The answer may be accurate — its claims match reality and the available evidence — or complete, covering everything the request asked for. These are independent. An answer can be accurate but incomplete, correctly stating one figure while ignoring three others requested. It can also be complete but inaccurate, addressing every part while getting one key fact wrong. Only one combination is useful: an answer that is both.

The distinction matters because the two failures call for different fixes. Inaccuracy is fixed by verification: checking claims against evidence, grounding the request, and cross-referencing sources. Incompleteness is fixed by requirement checking: comparing the response against the request line by line and asking for the missing pieces. A candidate who treats every bad answer as a fact-checking problem will miss questions where the real defect is an omitted section.

Accuracy also has layers: a statement can be true yet misleading because it lacks context or uses an outdated figure, and a number can be arithmetically correct but based on the wrong baseline. Verification is therefore a short investigation into whether each claim is supported as the answer implies.

Completeness means completeness relative to the request

Completeness is not fixed; it is a relationship between the answer and the specific request. A one-sentence reply can be complete for "What is the capital city?" and grossly incomplete for "Compare the two cities' transport systems." The same text can be adequate in one context and not another.

Reviewers therefore keep the original request visible while reading. It is easy to be impressed by a long, organized answer and forget to ask whether it did what was requested. Length is a weak proxy: a response can devote paragraphs to unasked-for background while omitting the one deliverable — the comparison table or the list of risks.

Requests often contain several parts wrapped into one sentence. Consider: "Summarize the report, list the three main risks, and recommend a next step." That line carries three deliverables. An answer that summarizes well and recommends a next step but never lists the risks is incomplete, even though most of it is accurate. The failure is easy to overlook precisely because so much of the answer is good.

Completeness also includes the format and scope the requester needed. If someone asked for "a table with columns for cost, owner, and deadline," a prose paragraph containing the same facts is complete in content but incomplete in form. When a request specifies a structure, a count, a time frame, an audience, or a level of detail, those are all part of the completeness contract.

Exam note: When a question asks whether a response is complete, return to the exact wording of the request. The correct answer checks the response against every stated requirement, not the one that praises it for being thorough.

Checking that every requested part is present

The reliable completeness check is mechanical rather than impressionistic. Before reading, break the request into a short list of requirements. Then read the answer once with only that list in mind, marking each requirement present or missing. This takes under a minute and catches omissions a general read will miss.

A useful habit is to turn each requirement into a question answerable with yes or no:

  • Did it name the three risks, or only discuss risk in general terms?
  • Did it give dates, or only relative phrases such as "next quarter"?
  • Did it use the requested format, or substitute a different one?
  • Did it cover the named regions, or only the first one?

The last question points to a second kind of incompleteness: an answer can omit part of the request by substituting a different task. If a reviewer asks for a risk assessment and receives a general introduction, the response has answered the wrong question. Substitution is common when a prompt is ambiguous or the answer begins with boilerplate the model never moves beyond.

Count items where the request sets a count. If it asked for five examples, count them; if for two paragraphs, check the structure. Models sometimes merge items, list four instead of five, or repeat one item with different wording. A physical count defeats this.

Try it: Before forwarding any response, write the original request at the top of your notes, list its requirements underneath, and tick each one off. If you cannot tick a requirement, the response is not ready to forward.

The mechanism of confident fabrication

An assistant generates an answer by predicting what text is likely to follow the prompt, guided by patterns learned from training material. It does not look up a fact in a database, and it has no built-in sense of certainty about each statement it produces. The result is a system very good at producing text that looks like a well-formed answer, with no automatic mechanism for guaranteeing it is true.

Fabrication arises from this design. With strong evidence in its training or supplied context, output is likely to align with reality. With weak evidence, the model still produces the most plausible continuation it can. Plausibility and truth overlap often enough to be useful, but they are not the same. A fabricated detail is not random nonsense; it is the kind of detail that would fit naturally in that position. That is what makes it dangerous.

Confidence is a feature of writing style, not a measurement of correctness. The model has no separate uncertainty signal that it reliably translates into hedging. The opposite can happen: a made-up figure is often stated more cleanly and decisively than a careful, qualified truth, because the training signal rewards complete, authoritative-sounding answers. "The figure is 47 percent" can be entirely invented, while "I could not verify the figure from the material provided" may be the more accurate statement.

That is why fluency is not evidence. A smooth, well-structured answer gives the reader a feeling of competence, and that feeling is regularly transferred from the writing to the facts. The transfer is a human reaction, not a property of the output. The reader must interrupt it with a deliberate verification step.

Fabrication is likelier for niche or recent information, very specific detail, prompts inviting the model to fill a gap, or answers with no supplied source material. It is less likely when the answer is grounded in inspectable material and the model is permitted to say it does not know.

Common mistake: Assuming that a detailed answer with precise numbers must be based on real data. Precision in phrasing is not proof of precision in the underlying information.

Categories of hallucination and how to detect them

For verification purposes, it helps to sort fabrications into practical categories. These are not a theory of the model's inner workings; they are a checklist of what commonly goes wrong and what to look for.

Hallucination type What it looks like Detection tactic
Invented source A citation to a report or document that does not exist Search the exact title; check publisher and date; treat unfindable sources as fabricated
Wrong attribution A real quote or idea credited to the wrong person, organization, or document Verify the quote against the original; confirm who actually said or published it
Plausible number A statistic that sounds reasonable but has no basis in the supplied data Recompute from source figures; check whether the number appears in the material
Incorrect date or name A specific year, deadline, or name that is wrong Cross-check against a calendar, timeline, or authoritative record
Fabricated detail An invented example or case used to illustrate a point Ask whether the instance appears in the source; demand a citation for it
False synthesis A conclusion presented as following from sources that do not support it Read the cited passages directly and test whether they justify the conclusion

The first four rows are the classic exam categories; the last two are common in practice and easy to miss. A false synthesis is especially slippery: every source may be real and accurately quoted, yet the conclusion drawn from them is not warranted.

Nearly every detection tactic goes back to something external — the source document, a search result, a calendar, a dataset. You cannot reliably verify an answer using only itself. Internal consistency is a useful first filter, but a fabrication consistent with the rest of a fabricated answer will pass it.

Warning signs in a response

Some answers carry signals that warrant a closer look. No single sign proves fabrication, but each lowers the verification threshold.

Vague sourcing is common. Phrases such as "studies show" without a named source shift the burden of proof onto the reader. A related sign is a citation that looks specific but cannot be located: an unusual title, a missing publisher, or a page number that leads nowhere.

Uneven specificity is another tell. An answer may give exact figures in one paragraph and wave vaguely in the next, or state precise percentages for familiar facts while becoming vague exactly where the question was hardest. Fabricated details cluster at the point of maximum difficulty, where grounding is weakest.

Over-completeness deserves attention too. If an answer supplies a number for every metric and a date for every event, ask whether the source really contained all that. Real documents are patchy; a suspiciously exhaustive answer may be filling gaps with inventions.

Watch for answers that never acknowledge limits: no hedging and no note about what could not be confirmed presents a uniform confidence the situation rarely justifies. Finally, note internal contradictions — if the summary says costs fell while the body says they rose, at least one part is wrong. Inconsistency does not say which part, but it says the answer has not been checked.

Exam note: Warning signs trigger verification; they do not prove an answer is wrong. The correct response is usually "investigate further," not "reject the entire answer."

Grounding a request in supplied material

The most effective way to reduce fabrication is to give the assistant material to work from and require it to stay within that material. This is grounding. Instead of a broad question that invites the model to draw on everything it has seen, provide a document, extract, table, or set of notes and instruct the model to use only that content.

A grounded request does three things: it narrows the possible answers to something inspectable; it makes unsupported additions obvious, since any claim not traceable to the supplied text stands out; and it turns verification from a research task into a comparison against the provided material.

Grounding is not foolproof: a model can still misread a passage or add a detail from memory despite the instruction. That is why it is paired with a requirement to show the evidence. But it changes the odds and makes verification far faster.

When you supply material, say what to do when it is insufficient. Without that instruction, the model may quietly fall back on general knowledge to fill the gap. A clear instruction — "if the extract does not contain the answer, say so" — closes that escape route. This is where grounding and the practice of marking unknowns reinforce each other.

Asking for quotations and citations

A grounded answer is much easier to check when the model points to where each claim came from. Ask for a short quotation beside each key statement, or a reference to the section, row, or paragraph. The quotation is not decoration; it is the evidence trail that lets a reviewer confirm the claim quickly.

Two forms are useful. A quotation reproduces exact words and is ideal when wording matters — whether a policy says "must" or "should." A citation points to a location such as a section or page, ideal when the reviewer wants to read around the claim. Many tasks benefit from both: a citation to find the passage, a quotation to confirm it.

Ask for quotations to be short, exact, and attached to the specific claim each supports rather than collected in a block at the end, so the reader moves from claim to evidence without guessing.

A subtle failure mode: a quotation can be accurate while its interpretation is not. A source may say a condition "may increase risk," and the answer report that it "causes" the problem. The quote checks out, but the conclusion overstates it. Verification requires reading claim and evidence together, not merely confirming the quoted words appear.

Asking the assistant to mark what it does not know

A useful instruction in any verification-focused prompt is to permit — better, require — the assistant to identify gaps. Something as simple as "if you cannot find this in the material, write 'not stated in the source'" gives the model a legitimate way to decline to answer. This reduces the pressure to produce a complete-looking answer at all costs.

The instruction works best when specific about what counts as unknown. Ask the model to distinguish three cases: information present in the source, absent from it, and present but ambiguous or conflicting. That is more useful than a blanket "I don't know," because it shows where the problem lies — an absent figure can be sought elsewhere; a conflicting pair needs a decision about which is authoritative.

Interpret the admission correctly. When an assistant says a fact is not in the supplied material, that is a statement about the material, not the world — the fact may be true and available elsewhere. Conversely, confident delivery is not proof the fact was in the material. The admission is itself a claim to check, like any other, but a conservative one that is safer to act on.

A model may still fail to flag its own uncertainty: marking unknowns reduces fabrication but does not eliminate it. The reviewer's checklist still applies to answered parts.

Common mistake: Treating an assistant's "I don't know" as a definitive statement that no such information exists anywhere.

Source triangulation and the limits of one answer

Triangulation means checking a claim against more than one independent source. A single generated answer is one artifact; even if fluent, cited, and internally consistent, it is one pass at the problem and can carry a single error all the way through. Independent sources break that dependency: a mistake in one place is unlikely to recur in the same way elsewhere.

Triangulation takes several forms. A reviewer can ask the assistant to answer the same question twice with different framing and compare results, check a claim against the original document, or consult a second reference for external facts. The goal is the same — see whether the claim survives a route independent of the first answer.

Independence is the key word. Asking the same assistant to "double-check" its previous answer often produces a restatement, especially if the original wording remains in view. Better is to clear the context, present the question afresh, and require the model to work from the source again — or check by a different route entirely, such as reading the source directly.

Triangulation also has limits. Multiple sources can repeat the same error, especially when they draw on the same original material; two generated answers can agree because they share training patterns. Agreement raises confidence but does not guarantee truth. What it does is expose disagreement: when two independent routes produce different figures, that conflict is a reliable signal that something needs investigation. Exam framing therefore emphasizes the limits of a single answer rather than claiming that multiple answers settle the matter.

A verification checklist you can apply in two minutes

Verification need not be elaborate. A short, repeatable routine applied every time catches most serious problems; it must be fast enough to actually get used and structured enough not to depend on mood or attention.

The checklist below suits a two-minute review of a typical business answer. Longer or higher-stakes outputs need more time, but the same sequence applies.

Step Check Action if it fails
1 Restate the request; list its requirements Stop and rewrite the prompt if the request was unclear
2 Confirm every requirement appears in the answer Ask for the missing parts before accepting
3 Scan for warning signs: vague sourcing, uneven specificity, no limits Mark suspicious claims for deeper checking
4 Verify each key claim against the supplied source Correct or remove unsupported claims
5 Check every number, date, and name against a record Recompute or confirm before sharing
6 Confirm citations resolve and quotations match Treat unfindable sources as fabricated
7 Triangulate the highest-risk claim by a second route Resolve disagreements before acting

Two habits make this work. First, verify in order of risk: with only one minute, spend it on the claim that would cause the most harm if wrong — usually a number, date, or recommendation. Second, write down the result. A quick note of what was checked creates an audit trail and prevents anyone assuming a check happened when it did not.

The checklist is skeptical without being cynical. Most answers are broadly correct; the goal is not to find fault for its own sake but to catch the few confident errors that would otherwise reach a decision or a message to someone else.

Below is a reusable prompt pattern combining grounding, explicit evidence, and permission to report gaps. It is written generically so it can be adapted to any subject area.

Use only the material supplied below to answer the request.
Do not add facts from outside this material.

For each key claim:
- give a short exact quotation from the material, and
- name the section, row, or paragraph where it appears.

If the material does not contain an answer, write "not stated in the source".
If the material contains conflicting statements, list both and say they conflict.
Do not guess a number, date, or name.

Request: [paste the exact request here]
Material: [paste the source text here]

This prompt fixes the evidence boundary, requires a traceable citation for each claim, gives legitimate ways to report absence or conflict, and blocks the most common fabrication types. It does not remove the need for the checklist — the quotations still have to be verified — but it makes verification much faster.

Try it: Apply the two-minute checklist to an answer you generated earlier this week. Note how many steps change your assessment. If the number is more than zero, the checklist is doing its job.

Worked scenario

An analyst asks an assistant to prepare a short briefing from a supplied internal document. The exact request is: "Using the attached policy extract only, summarize the approval rules in three bullet points, state the effective date, and list the name of the responsible office." The analyst pastes the extract and adds the grounding instruction from the prompt pattern above.

The assistant returns a confident answer: three bullets describing the rules, a statement that the policy "took effect on 1 March," and a specific office named as responsible. One bullet says: "All requests over 5,000 units require two approvals, as confirmed in Section 4 of the policy." The answer is well written and free of hedging.

A reviewer applies the checklist.

Step 1, restate the request: three deliverables — the bullets, the effective date, and the responsible office. Step 2, presence: all three are present, so the answer is not incomplete. Step 3, warning signs: the answer is uniformly confident, and "as confirmed in Section 4" is very specific, making it a candidate for checking. Step 4, source check: the bullets match the extract closely. Step 5, number, date, and name: the extract has a "5,000 units" threshold but says nothing about "two approvals" — it requires one additional sign-off. It gives no effective date, only a "draft" label. And the named office does not appear; the extract says only "the issuing department."

Step 6, check citations: the extract has only three sections, and Section 4 does not exist. Step 7, triangulate: the reviewer opens the original document and confirms that the figure and the office name came from the model's general knowledge, not the supplied text.

The answer appears complete but contains several defects: a fabricated citation, a plausible number attached to the wrong rule, an invented effective date, and a wrong office name. The fluent writing created an impression of reliability the source did not support.

The fix is to re-prompt and verify again. The reviewer asks the assistant to remove any claim unsupported by the extract, to write "not stated in the source" for the date and office, and to correct the approval rule. The revised answer is shorter and less polished, but every claim can be traced to the extract — less impressive to read, far safer to act on.

The first answer was not useless — its summary of the approval rules was accurate. But accuracy in the easy parts does not certify the hard parts, and the parts most likely to be fabricated — numbers, dates, names, and citations — are exactly the ones that must be checked against a record.

Exam note: In a scenario question, look for the option that verifies specific details against the supplied source and accepts "not stated" where evidence is absent. Options that trust the answer because it is detailed or well structured are usually wrong.

Common mistakes

  • Judging completeness by length or confidence instead of by the requirements in the request.
  • Assuming that fluent, precise phrasing means the underlying facts are reliable.
  • Accepting a citation or quotation without confirming it resolves to a real, matching source.
  • Asking the same assistant to "check its own answer" while that answer stays in view.
  • Treating agreement between two generated answers as proof of truth rather than as risk reduction.
  • Forgetting to verify numbers, dates, and names, which are the most common fabrication targets.
  • Ignoring the instruction to mark unknowns, then acting on a guess the model should have flagged.

Chapter summary

  • Accuracy and completeness are independent: an answer can be correct yet incomplete, or thorough yet wrong.
  • Completeness is measured against the exact request, including counts, formats, scope, and time frames.
  • A mechanical requirement-by-requirement check catches omissions a general read misses.
  • Fabrication comes from producing plausible text without a built-in guarantee of truth; confidence in tone is not evidence.
  • Key hallucination categories include invented sources, wrong attribution, plausible numbers, and incorrect dates or names, plus false synthesis and fabricated detail.
  • Warning signs include vague sourcing, uneven specificity, suspicious exhaustiveness, absence of limits, and internal contradiction.
  • Grounding in supplied material, asking for short exact quotations, and permitting "not stated in the source" all reduce fabrication and speed verification.
  • Triangulate important claims by an independent route; agreement helps, but multiple sources can still share an error.
  • A two-minute checklist — requirements, presence, warning signs, source check, detail check, citation check, triangulation — makes verification fast and repeatable.

  • A. The date is probably correct because the answer is detailed

  • C. The date should be kept because the assistant wrote it confidently
  • D. The extract must be wrong and should be discarded
  1. In the two-minute verification checklist, why is the highest-risk claim checked first?
  • A. Because it is always the shortest claim
  • B. Because checking it first removes the need to check anything else
  • C. Because limited time should be spent where an error would cause the most harm
  • D. Because high-risk claims are always fabricated

Answers and rationale

  1. B. Accurate but incomplete. The content present is correct, so accuracy is met; the missing table violates a stated requirement, so it is incomplete. A is wrong because a requirement is missing. C is wrong because nothing says the content is inaccurate. D is wrong because the content is described as correct.

  2. C. Confidence is a feature of style, not a measurement of correctness. The model produces plausible text without a guarantee of truth, so tone cannot certify facts. A is wrong because length is not the issue. B is wrong because fabrication is not deliberate or constant. D is wrong because citations help verification but do not make fluency a measure of truth, and can themselves be fabricated.

  3. A. Invented source. A citation to a document that cannot be located is an invented source. B concerns who said something, not whether the source exists. C is wrong because no date is at issue. D concerns a conclusion unsupported by genuinely cited passages.

  4. B. "If the material does not contain the answer, write 'not stated in the source'." This gives the assistant a legitimate way to report a gap instead of guessing. A and D increase pressure to produce content and can encourage fabrication. C affects style only and does not constrain the source of facts.

  5. B. It is likely to reproduce the original answer rather than check it independently. With the original text visible, the model tends to restate it rather than re-derive the answer. A is wrong because the approach is quick. C is an irrelevant side effect at most. D confuses dependence with material availability.

  6. C. Recompute or confirm the figure against the source data. A plausible number must be tested against underlying data, not the answer containing it. A and B examine writing rather than fact. D is wrong because a citation can be invented or point to a source that does not support the figure.

  7. B. The date is unsupported and should be removed or marked as not stated. The supplied extract is the controlling evidence and contains no effective date. A and C wrongly treat confidence and detail as evidence. D wrongly assumes the extract is mistaken.

  8. C. Limited time should be spent where an error would cause the most harm. Risk-based prioritization makes a short review useful. A is irrelevant. B is wrong because checking one claim does not clear the rest. D is wrong: high-risk claims are not automatically fabricated, just costlier to get wrong.
