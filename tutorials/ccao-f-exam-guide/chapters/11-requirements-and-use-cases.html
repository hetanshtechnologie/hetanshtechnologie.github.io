Requirements, Use Cases, and Fit Assessment

A business request rarely arrives in a form that can be built against. It arrives as a sentence in a meeting or a line in a ticket, often in the language of solutions: "We need an assistant that handles customer questions," or "Can the model just write our reports?" The work begins before any tool is opened. It begins with turning that sentence into something precise enough to test, deciding which situations genuinely suit an AI assistant, and recording boundaries so everyone agrees on what the project is and is not.

This chapter covers that front-end discipline: converting a vague ask into testable requirements, separating the requested solution from the real problem, choosing a first use case that can succeed, and compressing the understanding into a one-page brief.

Learning objectives

After this chapter you should be able to:

  • Convert a vague request into requirements that can be tested and accepted.
  • Ask clarifying questions before proposing a tool or a design.
  • Separate a requester's proposed solution from the underlying need.
  • Classify requirements as functional or non-functional and explain why both matter.
  • Define success metrics and acceptance criteria that are measurable and hard to game.
  • Select initial use cases that are low-risk, repetitive, and measurable.
  • Screen out use cases needing real-time systems, privileged actions, or unverifiable facts.
  • Build a requirements matrix and a fit-assessment matrix.
  • State explicit non-goals and assemble a one-page brief.

Key concepts

From a vague request to a testable requirement

A vague request is not wrong; it is unfinished. "Make support faster" cannot be built or accepted because it has no scope, threshold, or way to tell when it is achieved. A testable requirement is precise enough that a reviewer can write a check and get a clear pass or fail.

Compare these:

  • Vague: "The assistant should give good answers."
  • Testable: "For a sample of fifty common product questions, the answer must include the correct policy value in at least forty-five cases and must never state a value that contradicts the current policy document."

The second names a population, a behavior, a threshold, and a failure condition. Anyone can run the check and agree on the result.

Four questions convert the first kind into the second:

  1. What is the trigger or context? When does this apply?
  2. What exactly happens? Describe observable behavior, not intention.
  3. How will we know? Name the evidence or measurement.
  4. What threshold counts as success? Give a number, bound, or binary condition.

If you cannot answer all four, the statement belongs on an open-questions list, not in a specification. Untestable requirements become disputes later, when a stakeholder says the result is not what they meant and there is no agreed standard to settle it.

Exam note: A foundations question may present a soft request and ask what to do first. The strongest answer is usually to clarify and make it testable — not to choose a model, draft a prompt, or start building.

Clarifying questions come before solutions

The common early mistake is solution jumping: hearing a request and immediately naming a tool or feature. It feels productive because it produces something concrete, but it locks in assumptions before the problem is understood. A tool chosen against an unclear need is judged against a moving target.

Clarifying questions are cheap — they cost a conversation; the wrong design costs weeks. Useful families include:

  • Outcome: What would be different if this worked? What is being improved?
  • Current state: How is the task done today, by whom, with what handoffs?
  • Users: Who interacts with the result, and what do they already know?
  • Data and sources: What information is needed, where does it live, how current is it?
  • Constraints and risk: What budgets, policies, or deadlines bound the work? What happens if an answer is wrong?
  • Measurement: How would success be observed, and is there a baseline?

Ask open questions first. Closed questions that suggest an answer ("Would a chatbot be useful?") produce agreement rather than information. "What happens today when a customer asks that?" is more revealing.

Also distinguish clarifying questions, which resolve stated ambiguity, from discovery questions, which surface what no one mentioned — exception cases, undocumented approval steps, the spreadsheet that is the real system of record. A set built only from clarifying questions can be internally consistent and still miss the workflow.

Sometimes the need turns out not to be an AI problem. That is a successful outcome. Being willing to recommend a template, a better search index, or a process change is responsible practice: an assistant should be chosen because it fits the need, not because the conversation began with the word "AI."

Try it: Take a request such as "summarize our meetings." Write six questions — at least two about outcome and two about risk — before writing any prompt.

Separating the ask from the need

What a person requests and what they need are different objects. The request is a proposed solution, often borrowed from something they have seen. The need is the problem that solution was meant to solve. Confusing them produces elegant answers to the wrong question.

A manager might ask for an assistant that "automatically replies to all customer emails." Taken literally, that is unattended external action with no review: wrong answers sent out and reputational exposure. The underlying need might be narrower — "the team spends the first hour each day typing the same acknowledgment and routing instructions." The right answer could be reviewed draft generation, saved replies, or an email template. None is the system requested, and all may serve better.

Treat the ask as a hypothesis about the need and probe downward:

  • What does this let you do that you cannot do today?
  • What happens immediately before and after this step now?
  • Why is the step painful — slow, repetitive, error-prone, or unclear?

The last question matters because the cause determines the remedy. Delay caused by waiting for approval is an authority problem, not a text-generation problem. Delay caused by retyping the same content is repetition, and generation may help. Delay caused by missing information is a data problem, and no assistant can safely invent the missing fact.

Common mistake: Listing "build a chatbot" as a requirement freezes the design before the problem is understood. Record the ask in the brief, but record the need as the requirement.

Functional and non-functional requirements

Functional requirements describe what the system does: behaviors, transformations, outputs. Non-functional requirements describe how well: the qualities and constraints governing performance, safety, and acceptability. Both are necessary, and for an assistant the non-functional class often carries more risk.

A functional requirement for a support assistant might be: "Given a product question and the current knowledge base, produce a draft answer that cites the source section used." A corresponding non-functional requirement might be: "Never state a policy value absent from the supplied source," or "Return the draft within ten seconds," or "Every draft is reviewable before sending."

The distinction matters because non-functional qualities are easy to omit from a demo. A prototype can produce plausible text while failing on accuracy, privacy, latency, or auditability. If those were never written down, nobody tests them until a real user is affected.

Common non-functional categories:

  • Accuracy and groundedness: answers supported by supplied sources; uncertainty expressed, not hidden.
  • Privacy and data handling: sensitive inputs are not exposed or retained beyond need.
  • Latency and throughput: responses fit the workflow's time budget.
  • Consistency and tone: output matches organizational voice and terminology.
  • Auditability: outputs can be traced, reviewed, and reproduced.
  • Availability and fallback: the workflow degrades gracefully when the assistant is unsure or unavailable.

Quantify wherever possible. "Fast enough" is not testable; "under ten seconds for ninety percent of pilot requests" is. Where a quality resists a number, define an observable test such as a reviewer checklist for tone.

The requirements matrix

A requirements matrix turns scattered statements into something trackable. Each row is one requirement; columns capture what is needed to test, prioritize, and govern it.

ID Requirement Type Source / reason Acceptance test Priority Risk / notes
R1 Draft an answer to a product question using only the current knowledge base Functional Support need: repetitive first-hour replies On 50 questions, 45+ cite the correct source section High Verify source freshness
R2 Express uncertainty when the knowledge base lacks the answer Functional Risk of confident wrong answers On 10 unanswerable cases, 9+ state no source found High No invented values
R3 No draft states a policy value absent from supplied sources Non-functional / accuracy Compliance constraint Scan plus reviewer check finds zero unsupported values High Blocking requirement
R4 Return a draft within 10 seconds for 90% of requests Non-functional / latency Fits the support queue Measure 50 requests; 45+ under 10 seconds Medium Depends on retrieval size
R5 Every draft is labeled and human-reviewed before sending Non-functional / auditability External-communication policy Review log shows 100% of pilot drafts approved High Enforced by workflow
R6 Mask customer identifiers before processing Non-functional / privacy Data handling policy Sample inputs contain no direct identifiers High Test all fields

The identifier gives each requirement a stable reference. The source column preserves the reason so competing priorities can be weighed. The acceptance test converts intent into a check. Priority forces a decision; risk records where attention is needed. Rows can carry statuses such as "proposed," "met," or "deferred." The value lies in the habit of keeping each row testable and each reason visible.

Exam note: If a matrix contains "be helpful and accurate," the flaw is that it is untestable: no population, threshold, or evidence.

Success metrics and acceptance criteria

Two ideas are often confused. Acceptance criteria are the conditions a deliverable must satisfy to be accepted, usually tied to one requirement. Success metrics are the broader business measures showing whether the project was worth doing. Acceptance asks "did this pass?" Success asks "did this help?"

An acceptance criterion might be "at least forty-five of fifty drafts cite the correct source." A success metric might be "average handling time for the target category fell twenty percent against baseline." The first is a component gate; the second judges the initiative.

Good metrics are:

  • Baseline-able: the current state can be measured before the change.
  • Attributable: improvement can reasonably be connected to the intervention.
  • Bounded: a defined population, window, and calculation rule, so two people get the same number.
  • Resistant to gaming: a speed measure is paired with a quality measure.
  • Balanced: at least one quality or risk measure accompanies any efficiency measure.

A useful pattern pairs a leading indicator, which moves quickly and gives early feedback (percentage of drafts accepted without edits), with a lagging indicator, the eventual business outcome (customer satisfaction or resolution time). Leading indicators allow correction during a pilot; lagging indicators confirm value afterward.

Write acceptance criteria when requirements are written, not afterward. Defining the threshold after seeing thirty-eight correct answers and then setting the bar at thirty-eight is not acceptance — it is redefining the goal to escape a failure.

Common mistake: Measuring only volume — drafts generated, summaries produced. Volume shows activity, not value; a system producing many unusable drafts scores well on volume and badly on usefulness.

Choosing initial use cases

A first use case should be chosen for its chance of succeeding and being evaluated, not for the impressiveness of the vision. Three properties dominate: low-risk, repetitive, and measurable.

Low-risk means a wrong output has small consequences and can be caught before harm. Internal drafting of a routine summary is safer than publishing directly to a customer. Reversible, reviewed actions beat irreversible ones. If an error requires a correction notice or refund, the case is not a first pilot.

Repetitive means the task happens often enough to form a pattern and yield measurable volume. High-frequency, similar instances let a team build a representative sample and spot recurring failures. A task done twice a month with wide variation offers little signal.

Measurable means there is a baseline and a comparison. There is a current way of doing the task with an observable cost — time, errors, steps. If nobody can describe today's method, there is no baseline.

Look also for: usable, current, bounded source data; an available reviewer; a scope narrowed to a defined category; outputs verifiable by someone with domain knowledge; and a clean stopping point.

A good first case is a thin slice — one category, one team, one channel, one clear check — deliberately smaller than the ambition. Success on a thin slice produces evidence and real examples from which a broader design can be argued. A case chosen for breadth ("all customer contacts") fails because no single measure fits and no failure mode can be isolated.

Exam note: Favor the narrow, high-volume, reversible, reviewable option over the broad, strategic, visible one.

Screening use cases out

Saying no is a core skill. Some cases are unsuitable regardless of prompt quality. Three categories deserve attention.

Real-time dependence. If correctness depends on live state the assistant cannot reliably obtain — current inventory, a changing schedule, live status — a plausible answer may be stale when read. Adding a fresh data feed turns the case into an integration project with its own reliability demands. If the workflow needs a sub-second answer and freshness cannot be guaranteed, this is not a first pilot; a direct query against the system of record is often the right answer.

Privileged or irreversible actions. Tasks that move money, alter accounts, send external messages unattended, or change records carry consequences a probabilistic system should not own. The issue is authority as much as accuracy: if the action goes wrong, who is accountable, and can it be reversed? An assistant may draft the action or prepare a checklist, but execution belongs with an authorized human or deterministic system.

Unverifiable facts. With no reliable source to check against, correctness cannot be enforced. Fluent text is easily mistaken for accuracy. Cases built on undocumented exceptions or "what everyone knows" are dangerous. Grounded work requires every factual claim to be traced to a supplied source or marked uncertain; where no source exists, the honest design declines to answer.

Other signals — high-stakes decisions about people, regulated determinations, licensed professional judgment — are not always permanent exclusions, but they demand controls that make them poor early pilots.

The fit-assessment matrix

Where screening is a set of filters, a fit-assessment matrix compares several candidates on common criteria. It turns "this one feels more useful" into an explicit, reviewable judgment. The value is the conversation about weights and scores, which exposes hidden assumptions.

Score each criterion from 0 (poor) to 2 (strong), apply weights, and total. Decision bands translate totals into "advance," "revise," or "defer."

Criterion Weight Draft support replies Live status answers Unattended account changes
Clarity of need 2 2 (4) 1 (2) 1 (2)
Repetition / volume 2 2 (4) 2 (4) 1 (2)
Verifiability of output 3 2 (6) 0 (0) 1 (3)
Data freshness and availability 2 2 (4) 0 (0) 1 (2)
Low consequence of error 3 2 (6) 1 (3) 0 (0)
Human review feasible 2 2 (4) 1 (2) 0 (0)
Measurability / baseline exists 2 2 (4) 1 (2) 1 (2)
Weighted total 32 / 36 11 / 36 11 / 36
Decision Advance Defer — real-time Exclude — privileged

Two cautions. A score is a decision aid, not a decision maker: a single veto condition, such as an irreversible external action, overrides a high total. And scores must be justified — an unexplained "2" is an opinion wearing a number, so some teams require a one-line reason for each low score. Weights reflect organizational context, so agreeing on them is often the most valuable part of the exercise.

Explicit non-goals

A non-goal is a capability the project deliberately will not pursue. Stating non-goals is scope control, not negativity. Without them, each stakeholder assumes their favorite feature is included, and the disagreement surfaces only at delivery.

Non-goals prevent scope creep, reduce risk, sharpen communication, and protect the pilot's evaluation criteria from expanding midway. They should be specific: "will not handle billing disputes" beats "keep scope reasonable." Examples for a support-drafting pilot:

  • The assistant will not send anything externally; a human approves every draft.
  • It will not answer outside the three selected categories.
  • It will not access or display payment details.
  • It will not make commitments about delivery dates or refunds.

Non-goals often trace directly to screened-out cases and high non-functional requirements. That overlap is intentional. Mark the horizon clearly: "not in this pilot" differs from "not ever."

Exam note: If stakeholders are confused about coverage, document explicit non-goals and confirm them — do not add features or requirements.

Building the one-page brief

The one-page brief gathers this thinking into an alignment artifact. A reader should grasp the problem, scope, success measures, and boundaries in one sitting. It leads with the problem, records the original ask and the interpreted need, summarizes requirements by reference to the matrix, names a few metrics, lists non-goals, and surfaces risks and assumptions — the things believed true but unverified, and the likeliest source of surprise.

ONE-PAGE BRIEF — [working name]

1. Problem and original ask
   - Friction today: ...   Original request: ...
2. Interpreted need
   - Underlying problem: ...   Why it differs from the ask: ...
3. Users and context
   - Primary users: ...   Where output enters the workflow: ...
4. Scope (this pilot)
   - Included categories / channels / teams: ...   Thin slice: ...
5. Requirements summary
   - Key functional: ...   Key non-functional (accuracy, privacy, latency, audit): ...
6. Success metrics and acceptance criteria
   - Baseline: ...   Leading indicator and target: ...
   - Lagging indicator and target: ...   Acceptance gate: ...
7. Non-goals (explicit)
   - Will not do: ...   Horizon: pilot only / indefinite
8. Constraints, assumptions, risks
   - Constraints: ...   Unverified assumptions: ...   Top risks and mitigation: ...
9. Open questions and owners
   - Question: ...   Who answers: ...   Needed by: ...
10. Next steps
   - Immediate actions and decision point: ...

A brief that is hard to fill in is diagnostic. Blank metrics mean the need is still vague; blank non-goals mean nobody faced the risky parts; blank open questions after one conversation suggest the discovery was not deep enough. Treat the brief as a diagnostic instrument as much as a communication document.

Worked scenario

An operations team requests: "We want an assistant that answers all our branch questions so we can stop relying on the head office." Several stakeholders have already pictured one tool covering every topic. An analyst is asked to make it evaluable.

Rather than discussing models, the analyst asks about the current state. Branch staff send about sixty questions a week; roughly three quarters fall into three categories — completing a standard form, finding a current policy document, and routing a request to the right department. The rest are unusual exceptions requiring judgment and a documented decision. Answers take about one business day, and no one has measured the interruption cost.

Ask and need now separate. The ask is "answers all branch questions." The need is "reduce the daily delay and head-office interruption caused by a small set of repeated, documented questions, while keeping judgment-heavy exceptions with accountable people." That reframing removes the dangerous word "all."

The analyst drafts requirements. Functional ones cover producing a draft from the current policy set for the three categories and flagging out-of-scope questions. Non-functional ones dominate the risk column: no answer states a value absent from supplied documents, every answer names its section, drafts stay internal until a head-office reviewer approves them, and the tool is not customer-accessible. The core acceptance test is a fifty-question sample from real requests: at least forty-five correct, sourced answers and zero unsupported policy values.

For metrics, the baseline is one business day. The leading indicator is the share of reviewer approvals without edits, targeted at eighty percent; the lagging indicator is median response time for the three categories, targeted below two hours. Pairing speed with quality prevents faster-but-wrong answers from counting as success.

Screening removes candidates. "Is this account in compliance?" depends on live records and yields a consequential determination, so it is excluded. Unattended form approval is excluded as a privileged action. Undocumented local exceptions are excluded because no authoritative source exists. The three documented categories advance because they are repetitive, sourced, reviewable, and measurable.

A fit-assessment matrix confirms the ranking: drafts score strongly on verifiability, data availability, low error consequence, review feasibility, and baseline; live compliance questions fail freshness and verifiability; unattended approvals score zero on consequence and review. The totals are almost unnecessary — veto conditions already decided it — but recording them makes the reasoning visible to stakeholders attached to the broad vision.

The brief states non-goals: no undocumented exceptions, no external sending, no account-specific data, no compliance determinations, nothing outside the three categories. Each traces to a screening decision, so the boundary is visibly analytical rather than arbitrary caution.

Two assumptions are flagged: that policy documents are current and consistent, and that a reviewer has daily time to check drafts. Both become open questions with an owner and deadline. The recommendation is a narrow pilot on form-completion questions using a fixed sample, with a decision point reviewing acceptance results against the agreed threshold.

The outcome is not a grand system but a small, testable first step whose boundaries everyone accepts before work begins. A well-scoped first case produces evidence; an oversized one produces arguments.

Common mistakes

  • Proposing a tool, model, or prompt before the need is understood.
  • Recording the requester's solution as the requirement.
  • Writing untestable requirements such as "be accurate."
  • Omitting non-functional requirements, then meeting accuracy, privacy, or latency problems in real use.
  • Defining thresholds after seeing results, turning a failed test into a relaxed goal.
  • Measuring activity volume instead of outcome, or speed without a quality companion.
  • Choosing a first case that is broad, visible, and irreversible because it sounds strategic.
  • Ignoring veto conditions because a weighted total looks attractive.
  • Leaving non-goals unstated and allowing scope to expand mid-pilot.
  • Carrying unverified assumptions silently into the brief.

Chapter summary

  • Vague requests become usable when given a context, observable behavior, evidence, and threshold.
  • Clarifying and discovery questions precede solutions and expose outcome, current state, users, data, constraints, risk, and measurement.
  • A request is a hypothesis about a need; probing the cause often yields a smaller, better answer — sometimes no assistant at all.
  • Functional requirements describe behavior; non-functional requirements describe qualities that usually carry greater risk.
  • A requirements matrix gives each requirement an identifier, reason, acceptance test, priority, and risk note.
  • Acceptance criteria judge a component; success metrics judge the initiative. Pair a leading and lagging indicator, with a quality measure.
  • First cases should be low-risk, repetitive, and measurable — a thin slice with a baseline and reviewer.
  • Screen out real-time-dependent, privileged, and unverifiable cases; veto conditions override high scores.
  • Explicit non-goals and a one-page brief keep scope, expectations, and assumptions visible.

Checkpoint questions

  1. A stakeholder says, "The assistant should give reliable answers." What is the best first response?

A. Select a model known for accuracy. B. Ask what "reliable" means and define a test with a threshold. C. Draft a prompt telling the assistant to be accurate. D. Start a pilot across all question categories.

  1. A manager asks for a tool that sends replies to every customer email unattended. What does this illustrate?

A. A non-functional requirement needing a latency target. B. A success metric lacking a baseline. C. A proposed solution that should be probed for the underlying need. D. A low-risk use case ideal for a first pilot.

  1. Which is a non-functional requirement?

A. Produce a summary of each request. B. Flag questions outside covered categories. C. Return a response within ten seconds for ninety percent of requests. D. Add the source section to every drafted answer.

  1. Which use case is the strongest first pilot?

A. Approving benefit claims unattended to reduce headcount. B. Reporting live system status to customers within one second. C. Drafting internal answers to three common, documented question types with reviewer approval. D. Explaining undocumented exceptions only long-serving staff understand.

  1. A fit matrix gives a case a high total, but it sends external messages with no human approval. What should the analyst do?

A. Advance it because the score is high. B. Lower its priority but keep it in the pilot. C. Treat the privileged action as a veto and exclude unattended sending. D. Remove the weight column so the total changes.

  1. Why should a brief include explicit non-goals?

A. To list every feature the team hopes to add eventually. B. To set boundaries, prevent scope creep, and make risk decisions visible. C. To replace success metrics with qualitative statements. D. To avoid asking clarifying questions.

  1. Which statement best distinguishes an acceptance criterion from a success metric?

A. They are the same thing under different names. B. An acceptance criterion judges whether one requirement passes; a success metric judges whether the initiative helped the business. C. An acceptance criterion is always numerical; a success metric is always qualitative. D. Success metrics are written after launch; acceptance criteria are written before.

Answers and rationale

  1. B. "Reliable" is undefined and untestable; clarifying it and attaching a measurable threshold creates a usable requirement. A jumps to a solution before the standard is known. C relies on an instruction instead of an observable check, so pass or fail is subjective. D starts broad before scope and acceptance criteria exist, making evaluation meaningless.

  2. C. The manager stated a solution — unattended external replies — that may not match the real problem. Probing may reveal a narrower need, such as reducing repetitive drafting, served by a safer design. A misreads the request as a quality attribute when the issue is action and authority. B misidentifies it as a measurement problem; no metric was proposed. D is wrong on risk: unattended external communication is high consequence and unfit for a first pilot.

  3. C. Latency is a quality attribute and is quantified, so it is non-functional and testable. A describes a behavior, so it is functional. B describes a decision the system makes, so it is functional. D describes what the answer contains — a functional output requirement, not a cross-cutting quality.

  4. C. It is repetitive, sourced, reviewable, reversible, and tied to a baseline — the combination that gives a pilot a clean evaluation. A is a privileged, consequential action that should not be unattended. B depends on real-time data and strict latency, adding freshness and integration risk. D relies on facts with no authoritative source, so correctness cannot be verified.

  5. C. Certain risks are veto conditions; an irreversible external action overrides a favorable total, so exclude unattended sending and consider a reviewed alternative. A treats arithmetic as authority and ignores the veto. B retains a high-risk activity despite the concern. D changes the scoring to avoid the real issue and does nothing about the risk.

  6. B. Non-goals set boundaries, discourage scope creep, and make earlier risk decisions visible to readers. A describes the opposite: non-goals exclude work rather than list desired features. C is wrong because non-goals complement, not replace, metrics. D is wrong because non-goals follow clarification rather than remove the need for it.

  7. B. Acceptance criteria are component-level gates tied to requirements, while success metrics assess the broader business outcome of the initiative. A is false — conflating them loses the ability to tell a passing component from a worthwhile project. C is false because both can be numerical; the distinction is scope, not format. D is false because success metrics should be defined before the pilot, with a baseline, so that value can be judged against a plan.
