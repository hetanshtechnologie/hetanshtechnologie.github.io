Clinics: From Vague Task to Verified Answer

Learning objectives

  • Convert an underspecified request into a precise, testable instruction without changing the requester's intent.
  • Apply a repeatable verification pass to every answer before it is forwarded or acted upon.
  • Choose the smallest fitting assistant feature and model tier for a given task, and explain the trade-off.
  • Distinguish what a tool can do from what it should do in a given context.
  • Diagnose common failure patterns in generated answers and apply a targeted repair.
  • Recognize the scenario patterns that recur in the exam and respond with a defensible sequence of steps.

This chapter is a set of clinics rather than a survey of new material. A clinic takes an ordinary, slightly messy situation, names what is wrong with it, and shows the corrected move. The four skills below are the ones that decide most scenario questions: making a request clear, checking the answer, selecting the right capability, and judging appropriateness while repairing defects. Each appears on the exam in disguise, so the goal is to recognize the shape of the problem rather than memorize a script.

A single rhythm ties the clinics together. Before you accept any task, clarify what is being asked; choose a capability that fits; produce the answer; then verify and repair it. Keep that loop visible in your mind even when a question seems simple, because the exam frequently hides a verification or suitability problem inside an otherwise ordinary request.

REUSABLE FOUR-STEP CHECKLIST

1. CLARIFY  — Restate the goal, audience, format, constraints, and a test for success.
2. CHOOSE   — Pick the smallest feature and model tier that can do the job well.
3. PRODUCE  — Ask for the answer, requesting reasoning or sources where useful.
4. VERIFY   — Check correctness, scope, and safety; repair before sending.

Exam note: When two answers differ only in whether verification happens, the one that includes a check before use is almost always the stronger choice.

Key concepts

Each clinic below follows the same pattern: a starting situation, a diagnosis, a corrected approach, and a short drill with answers. Treat the four as one continuous workflow rather than independent tricks.

From fuzzy request to precise instruction

Starting situation. A team lead says, "Get me something on our quarterly numbers." An analyst pastes that line into an assistant and receives a long, generic essay about the industry. Nothing in the answer is wrong, yet nothing is usable. The request named a topic but not a decision, an audience, or a format.

Diagnosis. A vague request leaves the assistant to guess. Guessing is not a defect in the tool; it is the expected result when essential parameters are missing. The four parameters that most often go missing are context (what situation this sits in), role (whose voice and depth), deliverable (a summary, a comparison, a draft message, a table), and success test (what a good answer must contain or avoid). When any of these is absent, the assistant fills the gap with plausible defaults, and plausible defaults rarely match a specific business need.

A second issue is hidden intent. "Something on our quarterly numbers" may actually mean "identify which product line declined and draft three sentences I can paste into a status update." The literal request and the real goal are different. Correcting the wording without uncovering the goal produces a tidy answer to the wrong question.

Corrected approach. Rewrite the request so that a colleague could answer it without asking follow-up questions. State the decision the answer must support, the audience, the required shape, and any boundaries such as length, tone, or data the assistant must not invent. If the underlying goal is uncertain, ask one focused clarifying question rather than guessing. Silence is not agreement; when the brief could reasonably mean two different things, a single question is faster than a wrong deliverable.

The table below shows how a rough request is tightened. Notice that the correction adds constraints; it does not add a new topic.

Vague element What is missing Tightened version
"something on numbers" Deliverable and decision "a three-bullet summary of revenue by product line"
"our quarterly" Context and source "using the figures in the attached table for the last quarter"
no audience Voice and depth "written for a non-financial manager"
no boundary Scope and honesty "do not estimate any figure that is absent; say it is missing"

Here is the tightened instruction as a reusable pattern. It is deliberately plain; clarity does not require elaborate phrasing, only complete information.

Context:     We are preparing a status update for non-financial managers.
Task:        Summarize revenue by product line in three bullets.
Source:      Use only the figures in the supplied table.
Constraints: No invented numbers; flag any missing figure; neutral tone.
Success:     A manager could paste the bullets into the update unchanged.

Try it: Before sending any important request, read it once and ask, "Could two different people interpret this differently?" If yes, tighten it first.

Drill. An analyst receives: "Check this policy and tell me if it is fine." Name the two fastest clarifications that would turn this into a usable task, and explain why each matters.

Drill answers: First, clarify the standard — "fine" for compliance, clarity, tone, or length are different tests, and naming the test determines which issues count as problems. Second, clarify the deliverable — a pass or fail verdict with reasons, a list of problems, or a rewritten version produce very different work. Both matter because they remove the two largest guesses: what "good" means and what form the answer takes. Without them, any answer the assistant gives is a guess about the analyst's intent.

Inspecting the answer before you send it

Starting situation. A support agent asks an assistant to draft a reply to a customer about a delayed shipment. The draft is warm, fluent, and confident. It also promises a delivery date the company has not confirmed and cites a policy that changed last month. The agent copies it into the message and sends it. Two follow-ups later, the error is obvious and the agent must walk it back.

Diagnosis. Fluent writing is not evidence of correctness. An answer can be well-structured, grammatical, and completely wrong on the facts that matter. This is the verification gap: the moment between receiving a draft and using it is skipped. Three specific risks hide in that gap. First, plausible fabrication — details that fit the pattern but were never supplied. Second, staleness — facts that were once true but have changed. Third, scope drift — the answer quietly addresses a nearby question rather than the one asked.

The exam tests this by offering an option that says, in effect, "send the draft as written because it reads well." That option fails on principle. Polish is a presentation quality, not a correctness check.

Corrected approach. Run a short, fixed inspection. Compare every factual claim to an authoritative source available to you. Check that each requirement from the clarified request appears in the answer. Look for details that were not in your inputs — dates, names, numbers, references — and treat them as unverified until confirmed. Finally, judge tone and audience fit. If the answer fails any check, repair it before use rather than merely appending a disclaimer.

The inspection is fast because it is structured. You do not reread the whole answer aimlessly; you check specific categories in order. A fixed order also prevents a common failure: spending all your attention on wording and never reaching the factual claims. Start with facts, since those carry the most risk, and end with tone, which is the cheapest to fix.

Common mistake: Adding "please verify this information" to a flawed answer and forwarding it. The reader is not the verification step; you are. A caveat does not convert an unchecked claim into a checked one, and it can even make the claim look more credible by surrounding it with caution.

A practical way to make verification stick is to ask the assistant itself for a support trail: which statements came from the supplied material, which are inferences, and which are unknown. That does not remove your responsibility, but it makes gaps visible so you can examine them quickly. When the stakes are high, cross-check against a primary record rather than trusting the assistant's own account of its sources. An assistant can describe its reasoning persuasively and still be wrong about the underlying fact.

Verification check What you look for Passing condition
Source agreement Each fact traced to supplied or authoritative material No unsupported dates, figures, or references
Requirement coverage Every constraint from the clarified task All named constraints appear
Scope Answer addresses the actual question No substitution of a nearby question
Safety and policy No commitments or claims beyond your authority Wording stays within approved bounds
Audience fit Tone and depth suit the reader Reader could act on it without translation

In a scenario question, the correct option often names one of these checks explicitly. Recognizing the category tells you whether the option is a genuine verification step or a decorative one, such as asking for a second draft without checking either version.

Drill. A draft answer states that a service "always meets its target" and quotes a response time, but the source you supplied contains only a weekly average. Identify the verification failure and the repair.

Drill answers: The failure is an unsupported absolute plus a figure that does not match the source. "Always" overstates what a weekly average can show, and the quoted response time is not present in the material. The repair is to replace the claim with the supported statement — that the source reports a weekly average — and remove or re-source the specific figure before the draft is used. This is a source-agreement failure first and a wording failure second.

Matching the feature and model to the task

Starting situation. A candidate is given a scenario: a team needs to extract dates and amounts from a batch of scanned invoices and place them in a spreadsheet. The proposed solution is to use a general conversational assistant with the largest available model, pasting each document into the chat window one at a time. The scenario asks for a better approach.

Diagnosis. The proposal treats every task as a chat task and every improvement as a bigger model. Both assumptions are costly. Chat is a poor fit for a repetitive, structured extraction over many files; a document-processing or structured-output capability is designed for that shape of work. A larger model does not compensate for using the wrong feature, and it adds latency and cost. This is a capability mismatch, not an intelligence shortfall.

The reverse error is equally common. Choosing the smallest, cheapest option for a task that needs careful reasoning or strict adherence to a long instruction saves little and produces rework. A team that routes a complex analysis to a weak tier often ends up repeating the work, correcting errors, or escalating it anyway. Selection is about fit across three axes: the nature of the task, the need for external or private information, and the tolerance for error.

There is a fourth axis that scenario questions like to test: whether the task needs a tool at all. If the answer can be looked up exactly or calculated deterministically, a language model is an unnecessary middle step. Recognizing that boundary is part of choosing well, and it is the reason the exam frames some questions around "which approach" rather than "which model."

Corrected approach. Describe the task in terms of its shape, then map that shape to a capability. Repetitive extraction of fields into a schema calls for structured output on a document pipeline. Questions about private documents call for a retrieval feature that grounds answers in those documents. Open-ended drafting or brainstorming suits a general chat interface. Multi-step analysis with strict rules suits a reasoning-oriented mode. Only after the feature is chosen does model tier matter: use a smaller, faster tier for well-bounded work and a stronger tier for multi-step reasoning, long instructions, or high-consequence answers.

The table gives a compact mapping you can reuse in scenario questions.

Task shape Fitting capability Model tier tendency
Extract fields from many documents Document processing with structured output Smaller tier is usually enough
Answer from private or changing material Retrieval grounded in a defined source set Mid tier, with source checks
Draft, brainstorm, or rewrite prose Conversational assistant Mid tier for style control
Multi-step analysis or strict rule-following Reasoning-oriented mode Stronger tier, with verification
Deterministic calculation Calculator or code, not language generation Not a model choice at all

Exam note: If a task is deterministic — arithmetic, exact lookups, rule-based validation — the best answer may be a non-generative tool. The exam rewards recognizing when a language model is the wrong instrument.

Two additional filters refine the choice. Ask whether the assistant needs information it cannot see; if so, supplying the right source through a retrieval feature is more reliable than relying on memory. Ask what happens if the answer is wrong; higher consequence justifies a stronger tier and a verification step, not a larger prompt alone.

Cost and speed enter the decision only after fit is settled. Among capabilities that can do the job, prefer the smaller tier that meets the quality bar, because it makes iteration cheaper and verification faster. That is a practical preference, not a rule that overrides accuracy; a high-consequence answer earns the stronger tier precisely because the cost of being wrong is larger than the cost of running it.

Drill. A team wants a short summary of a single paragraph that a colleague already pasted into the request. Which feature and tier are appropriate, and why?

Drill answers: A general conversational assistant at a small or mid tier is appropriate. The source is already in the request, so retrieval is unnecessary; the task is a simple transformation, so a stronger reasoning tier adds no value. Choosing the smaller fitting option is correct because the work is bounded and the cost of a wrong summary is low, leaving room for a quick human check. If the summary will be forwarded to a large audience, the same feature is still right, but the verification step becomes more important.

Can versus should, and repairing weak answers

Starting situation. An assistant is technically able to draft a message that implies a guarantee the company has not approved. A teammate argues that because the tool "can generate it," using it is efficient. Another scenario involves an assistant asked to draft an internal note that rates colleagues' performance from incomplete chat logs. Both requests are possible. Neither is obviously appropriate.

Diagnosis. Capability and appropriateness are different questions. "Can it produce the text?" is a technical fact. "Should it be produced, and by this means?" is a judgment about authority, fairness, privacy, and consequence. Conflating them is the most dangerous error in the clinics because it tends to appear in polished, confident answers. A tool that can draft a persuasive message can also overstate a promise; a tool that can summarize private conversations can also turn incomplete fragments into a pseudo-evaluation that looks authoritative.

Appropriateness depends on context: who is authorized to make the claim, whose data is involved, whether the affected people can review it, and whether a human with accountability will sign off. When any of those is unclear, the correct move is to narrow the task or escalate, not to generate and hope. The exam encodes this as the difference between an answer that merely completes the request and an answer that notices the request itself should be reshaped.

Corrected approach. Pause and ask two questions before generating: is this claim or action within my authority, and would I be comfortable if the affected person saw exactly how it was produced? If either answer is uncomfortable, constrain the request — remove the guarantee, anonymize and aggregate the data, or hand the decision to a responsible reviewer. Then produce the narrower output and verify it as before.

When an answer is already weak, repair it by category rather than by rewriting from scratch. The diagnostic table below is the shared tool for this clinic. It turns a vague sense of "this looks off" into a named problem with a first move. Naming the problem matters because different defects need different repairs: adding length helps almost nothing, while removing an invented reference fixes the answer completely.

Symptom in the answer Likely cause First corrective move
Confident citations or figures that do not exist Fabrication from plausible patterns Remove them; re-answer from supplied sources only
Correct facts in the wrong format Deliverable not specified Restate the required shape and regenerate
Vague hedging everywhere Over-caution or missing success test State the decision and the test explicitly
Refusal on a safe, ordinary task Misread intent or missing context Reframe with purpose and constraints
Compliance with an unsafe or unauthorized request "Can" mistaken for "should" Narrow scope or escalate to a reviewer
Long answer that misses the point Nearby question substituted for the real one Restate the actual goal and trim to it
Internally inconsistent numbers Reasoning drift across a long answer Recompute with a deterministic tool and align

Common mistake: Treating a refusal as a failure to be pushed through. Sometimes the boundary is correct. The right response is to examine why the task was refused and reformulate it legibly, not to insist on the same request in different words until the system gives in.

The last row of the table deserves special attention. Inconsistent numbers within one answer are a sign that the model drifted as it generated a long response. The fix is not to ask for a more careful tone but to recompute the figures with a deterministic tool and then make the prose match. This is another instance of the capability lesson: some corrections belong outside the language model entirely.

Drill. An assistant produces a flawless-looking summary of a customer complaint that recommends a refund without any policy basis. State the diagnosis and the repair.

Drill answers: The diagnosis is an unauthorized commitment produced from an incomplete basis — a "can versus should" problem, not a writing problem. The repair is to strip the recommendation, ground the summary strictly in the complaint text, and route the refund decision to the team that owns that authority. The prose may be excellent; that is precisely why the content error is easy to miss. A second acceptable observation is that the missing policy basis should be supplied or the conclusion should be flagged as unsupported.

Worked scenario

A regional manager asks for help preparing a ten-minute briefing to the leadership group on why customer satisfaction fell in the last quarter. The available material is a dashboard export with three months of scores, a folder of support notes, and a draft the assistant produced earlier. The manager wants the briefing by afternoon and says, "Just make it convincing."

The candidate begins with the clarify step. "Convincing" is not a success test; the briefing must be accurate and useful to a leadership audience. The candidate restates the request: identify the two largest drivers of the decline supported by the supplied material, present each with one figure and one anonymized example, flag any conclusion the data cannot support, and keep it to three slides. This converts a rhetorical goal into a checkable deliverable and gives the manager a clear chance to correct the interpretation before work begins.

Next comes the choose step. The scores are structured; the support notes are unstructured text. The candidate uses a document-reading capability grounded in the two supplied sources rather than asking a general assistant to recall industry trends. A mid-tier model is sufficient because the work is summarization with light pattern-finding, not deep reasoning. Deterministic percentages are computed directly from the export, not generated by the model, because exact figures should never be left to a generative step.

The produce step yields a draft with three claims. One claim attributes the decline to a policy change; the dashboard shows a timing correlation but the support notes do not confirm causation. A second claim quotes a precise satisfaction drop for a region whose sample size is small. A third claim includes a promise that a fix will ship next month, drawn from the earlier draft rather than any current source. Each claim is plausible enough that a rushed reader would accept it.

The verify pass catches all three. The causal claim is rewritten as a correlation with an explicit note that the data cannot establish cause. The regional figure is replaced with a range and a caveat about sample size. The shipping promise is removed because it is an unauthorized commitment. Each repair maps to a row in the diagnostic table: unsupported inference, unsupported precision, and authority overreach. The candidate also checks that every constraint from the clarified request appears in the final slides.

Finally, the can-versus-should check considers the support notes. They contain identifiable customer details. The briefing will use anonymized, aggregated examples only, and the candidate declines to include names even though the assistant could reproduce them from the notes. The finished briefing is accurate within its sources, appropriately cautious, and ready for the manager to deliver with an honest note about what the data does not show.

Exam note: The strongest answer in a scenario is rarely the one that generates the most text. It is the one that produces a bounded, checked, appropriately scoped result and says what was deliberately left out.

Common mistakes

  • Treating a fluent answer as a verified answer. Readability is not accuracy.
  • Choosing a larger model to compensate for the wrong feature. Fit the capability first.
  • Using a conversational tool for deterministic work such as exact calculations.
  • Asking for "more detail" when the real problem is an unclear deliverable.
  • Assuming a refusal is always a tool failure; sometimes the boundary is correct.
  • Forwarding an answer with a "please verify" note attached, which shifts your check onto the reader.
  • Allowing generated text to make commitments, guarantees, or judgments beyond your authority.
  • Repairing a weak answer by adding length instead of naming the specific defect.
  • Letting a colleague's urgency replace the clarify step; speed does not make a vague request clear.

Chapter summary

  • A vague task becomes usable when you supply context, role, deliverable, and a success test.
  • Verification is a fixed sequence: source agreement, requirement coverage, scope, safety, and audience fit.
  • Select the capability by task shape and information source, then pick the smallest fitting model tier.
  • Deterministic work belongs to deterministic tools, not to language generation.
  • "Can" is a technical fact; "should" is a judgment about authority, fairness, and consequence.
  • Diagnose bad outputs by category so the repair is targeted rather than cosmetic.
  • In every scenario, clarify, choose, produce, and verify before the answer leaves your hands.

Checkpoint questions

  1. An analyst receives the request "summarize the report." What is the best first move?

A. Ask the assistant to produce a longer summary so nothing is missed. B. Clarify the audience, length, and decision the summary must support. C. Choose the largest model to ensure the summary is accurate. D. Produce a summary and add a note asking the reader to verify it.

  1. A draft answer includes a precise date that does not appear in any supplied source. Which check catches this first?

A. Audience fit. B. Requirement coverage. C. Source agreement. D. Tone consistency.

  1. Which task best fits a document-processing capability with structured output?

A. Brainstorming names for a new product. B. Extracting dates and amounts from a batch of invoices into a table. C. Writing an encouraging note to a colleague. D. Deciding whether to approve a refund.

  1. A request is technically possible but would let a draft imply an unapproved guarantee. What should happen?

A. Generate it, since the tool can do it. B. Generate it with a disclaimer attached. C. Narrow the request to remove the guarantee or escalate to the owner of that decision. D. Ask a stronger model to phrase the guarantee more carefully.

  1. Which statement best expresses "can versus should"?

A. If an assistant can produce an answer, using it is appropriate. B. Capability answers what is possible; appropriateness answers what authority and context permit. C. Stronger models remove the need to ask whether a task is appropriate. D. Refusals always indicate a mistake in the assistant.

  1. An answer lists several impressive references that turn out not to exist. What is the likely cause and first repair?

A. Cause is over-caution; repair by adding more hedging. B. Cause is wrong model tier; repair by using a larger model. C. Cause is fabrication of plausible details; repair by removing them and re-answering from supplied sources. D. Cause is a scope drift; repair by shortening the answer.

  1. For a scenario requiring exact percentages from a spreadsheet export, which approach is strongest?

A. Ask a language model to estimate the percentages. B. Compute the percentages directly from the export and use the model only to explain them. C. Use the largest model and request step-by-step reasoning. D. Skip the numbers and describe the trend qualitatively.

Answers and rationale

  1. B. Clarifying audience, length, and purpose supplies the missing success test, which is the essence of the first clinic. A is wrong because a longer summary does not fix an undefined goal and may add noise. C is wrong because model size does not resolve ambiguity in the request. D is wrong because it skips verification and pushes that duty onto the reader.

  2. C. Source agreement traces each fact to supplied or authoritative material, so an unsupported date is caught immediately. A concerns tone and depth, not factual support. B checks that constraints appear, not that facts are grounded. D is a subset of audience fit and would not flag an invented date.

  3. B. Repetitive field extraction into a defined structure is exactly the shape document processing with structured output is built for. A is open-ended drafting, which suits a conversational tool. C is a short prose task with no structured requirement. D is a decision about authority and policy, not an extraction task.

  4. C. Narrowing the request or escalating respects that the guarantee is not yours to make; appropriateness, not capability, governs. A confuses technical ability with permission. B does not cure an unauthorized claim — a disclaimer still leaves the claim in the reader's hands. D merely polishes the same inappropriate commitment.

  5. B. This states the distinction cleanly: capability is about what a system can produce, while appropriateness is about what context, authority, and fairness allow. A is the conflation the clinic warns against. C wrongly assumes a stronger model removes judgment. D is wrong because some refusals are correct boundaries.

  6. C. Invented but plausible references are a classic fabrication pattern, and the first move is to remove them and rebuild the answer from supplied sources. A misdiagnoses the problem as excessive confidence rather than invented content. B treats a source problem as a capacity problem. D addresses focus, not falsity, so the fake references would remain.

  7. B. Deterministic figures should be computed with a deterministic tool, and the assistant used only to interpret them; this is the capability-matching principle. A and C ask a generative model to produce exact arithmetic, which invites error. D avoids the question rather than answering it.
