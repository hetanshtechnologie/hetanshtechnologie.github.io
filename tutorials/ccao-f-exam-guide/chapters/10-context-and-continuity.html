Context Windows, Memory, and Session Continuity

A conversation with an AI assistant feels unlimited until it is not. Early on, the assistant seems to remember every detail and apply every instruction. After a long exchange, the same assistant may forget a decision made at the start, drop a formatting rule, or contradict an earlier definition. Nothing mysterious has happened. The session has simply outgrown the space available to hold it.

This chapter explains that space, called the context window, and the discipline of working within it. You will learn what fills the window, how to recognize that it is nearly full, and the three recovery strategies that keep long work coherent. You will also learn how memory features differ from an organized external record, what temporary modes do and do not promise, and how to carry preferences and decisions between chats. These are foundational exam topics because they sit at the boundary between what the model can do and what the user must manage.

Learning objectives

By the end of this chapter you should be able to:

  • Describe the context window as a single shared budget for instructions, conversation history, documents, tool output, and the answer itself.
  • Identify the practical signs that a conversation is approaching its context limit.
  • Explain why early decisions and instructions tend to get lost in long conversations.
  • Compare the restart, summarize, and persist recovery strategies and state when each is correct.
  • Compose a handoff summary that preserves the facts needed to continue work without the original thread.
  • Distinguish built-in memory features from a governed external record of key facts.
  • State what incognito or temporary modes do and do not guarantee.
  • Apply a continuity checklist to keep preferences, decisions, and obligations intact across sessions.

Key concepts

The context window as one shared budget

The context window is the finite amount of text that the model can consider while producing any single response. It is helpful to picture it as one desk surface with limited room. Everything relevant to the current reply competes for space on that desk: the system and developer instructions, the user's standing preferences, the entire visible conversation history, any documents pasted or attached, the output returned by tools, and the answer being written. These items are not stored in separate compartments. They share one budget.

This sharing has an important consequence. Space spent on one item is space unavailable for another. A long pasted report leaves less room for the conversation that follows it; a verbose tool output can crowd out the reasoning the task needs. Because the answer is generated within the same window, a request that consumes almost all the available space leaves too little room for a complete reply, and the response may be cut short or lose its ending.

It is tempting to think of the context window as a storage device that remembers the session. It is more accurate to think of it as working memory reassembled for each turn. On every new message, the relevant text is gathered again. Older material may be compressed or dropped when the total grows too large. The assistant has a window into a selected portion of the session, not a perfect permanent transcript.

Key idea: Context is a budget to be allocated, not a container that holds everything. Manage it the way you would manage a limited supply: spend it where it changes the answer and reclaim it where it does not.

What consumes the budget

Different kinds of content draw on the same budget in different ways. Understanding the categories helps you see where waste accumulates and where it is worth spending.

Category What it includes Typical behavior What the user can control
Standing instructions System rules, developer rules, saved preferences Present on every turn; usually highest priority Phrase preferences clearly; avoid duplicating them
Conversation history All prior user and assistant turns in the session Grows with every exchange; oldest parts may be compressed or dropped Remove tangents, close settled topics, start fresh when useful
Documents and pasted content Reports, tables, code, transcripts, reference text Enters the window in full when attached or pasted Supply only the relevant excerpt; summarize large sources first
Tool output Search results, file reads, query results, generated artifacts Can be large and verbose; accumulates across steps Request narrow results; discard raw dumps after extracting facts
The answer The response being generated Needs room reserved in advance Ask for concise output; reserve headroom for the final reply

Two patterns waste the most budget. The first is carrying raw material forward after its useful facts have been extracted; keeping a long source in the thread consumes space on every later turn. The second is repetition. Restating the same background each message, or requesting a full answer when only a correction is needed, adds cost without adding information.

Position matters too. Material at the very start of a long conversation is the most likely to be compressed away, and material in the middle of a long block can receive less attention than material near the beginning or end. This is not a precise rule, but it explains why a constraint buried in paragraph forty of a huge paste may be honored less reliably than one restated briefly at the point of use.

Exam note: A common exam trap is to treat the prompt you type as the only thing in the window. The instructions, the whole history, the documents, the tool results, and the answer all share the same space. If a scenario describes an answer that trails off or loses its conclusion, suspect that too much input left too little room for output.

Signs that a conversation is approaching its limit

There is no universally reliable counter a user can read. Instead, watch for behavioral signals that, taken together, are a strong hint.

  • Repeated clarification of settled facts. Assistant replies begin asking for information that was provided earlier, or they use an outdated version of a value that was later corrected.
  • Lost instructions. A formatting rule, tone requirement, or definition given at the start stops being followed even though it was never withdrawn.
  • Contradictions within a reply. The answer uses two incompatible definitions of the same term, or applies a rule one way in the first half and another way in the second half.
  • Drift toward generic output. Responses become shorter, vaguer, or more template-like, with fewer references to the specific details of the task.
  • Premature conclusions or truncated endings. The reply stops mid-thought, omits the requested summary, or fails to complete a list, especially when the input was very large.
  • Ignored recent corrections. A change you just requested is acknowledged but not reflected, suggesting earlier text is outweighing the newest instruction.
  • Degradation after a large attachment. Quality drops sharply immediately after a big document or a verbose tool result enters the thread.

When several of these appear, the right response is not to keep pushing harder with longer prompts. The right response is to change strategy: reduce what must be held in the window at once.

Common mistake: Assuming the assistant is malfunctioning and simply restating the request at greater length. Longer restatements add more text to an already crowded window and usually make the problem worse.

Why early decisions get lost in long conversations

Long projects accumulate decisions. A team agrees on a name, a scope boundary, or an approval rule in the first few messages. Dozens of exchanges later, the assistant may behave as though those decisions never existed, for several reasons.

First, as text volume grows, earlier turns must be compressed or removed to keep recent ones, and compression preserves the gist rather than the exact wording of a constraint. A nuance such as "exclude draft records from this count" can disappear while the general topic "records and counts" survives.

Second, later messages can overshadow earlier ones. A casual question in message thirty may read as revisiting a decision fixed in message three, especially without an explicit "keeping the earlier decision in place." Third, corrections stack: if a value changes three times, the thread holds four competing versions, and an older one can resurface.

The lesson is that important decisions should be restated where they matter and recorded somewhere that does not depend on the window. A short standing-decisions note, refreshed as the project evolves, is more reliable than the original conversation.

Recovery strategy one: restart with a distilled brief

Restarting means opening a new session and supplying a compact, self-contained description of the task and its current state. This is correct when the old conversation has accumulated noise, the topic has changed, or the thread is too degraded for reliable summarization.

A good brief states the goal, fixed decisions, work completed, open questions, constraints, and the exact next action. It should be short enough to read in a minute. Because the user writes it, its accuracy does not depend on the assistant having understood earlier turns.

The strength of restarting is cleanliness: the new session starts with high-value context and no clutter. The limitation is omission. If a crucial detail was never written down, abandoning the old thread loses it. Restart works best when key facts are already captured externally or the task is simple enough to restate completely.

Try it: Before closing a thread, write a five-line brief: goal, fixed decisions, work done, open issues, next step. If you cannot fill those lines from memory, the thread still holds information you need, and you should extract it before restarting.

Recovery strategy two: summarize the thread

Summarizing means asking the assistant for a condensed account of the conversation, then continuing from it. This is correct when the thread is long but coherent, the details are spread across many turns, and you want continuity without reconstructing the background yourself.

A useful summary captures decisions, constraints, definitions, deliverables, and outstanding items, and is explicit about what is settled versus open. It should preserve exact values such as dates, file names, numeric targets, and agreed wording, because approximate summaries blur precisely the details that cause errors later.

There is a subtle risk. If the assistant has already dropped a detail from its window, it cannot summarize it; a summary reflects what the model can currently see. For high-stakes work, review it against your own notes before relying on it. Also, a summary that merely restates the thread in slightly shorter form frees little space. It must be genuinely condensed.

Produced near the end of a session, a summary can double as the handoff artifact for the next one, making summarization a natural habit at milestones.

Recovery strategy three: persist key facts externally

Persisting means recording important facts outside the conversation: a project note, a shared document, a checklist, or a knowledge base. This is correct when work spans sessions, people, or tools, or when facts must be auditable or corrected in one place.

External persistence is the most durable strategy because it does not depend on the window. A written decision can be read fresh into any new session and can be reviewed, versioned, and approved. The tradeoff is effort: someone must maintain the record and keep it current. A stale record can be as misleading as a lost conversation.

The most effective approach combines all three: keep a compact external record, use summarization to close out a productive session, and restart from a brief that points to the record. They are complements, not rivals.

Choosing among the three strategies

The following comparison brings the decision into focus. Use the row that matches the situation rather than defaulting to one habit for every case.

Strategy Best used when How it works Main strength Main limitation
Restart with a distilled brief The thread is noisy, the topic has shifted, or quality has degraded badly Open a new session and write a compact, self-contained statement of goal, decisions, and next step Clean context with no accumulated clutter Detail can be lost if it was never recorded
Summarize the thread The thread is long but still coherent and the details are spread across turns Ask for a condensed account of decisions, constraints, deliverables, and open items, then continue Preserves distributed detail without manual reconstruction Cannot recover facts already dropped from the window; weak summaries save little space
Persist key facts externally Work spans sessions, people, or tools, or facts must be auditable Record stable facts in an external note, document, or knowledge base and read them into new sessions Durable, reviewable, independent of any single chat Requires ongoing maintenance and ownership

Exam note: If a scenario emphasizes that work must continue next week with a different colleague or system, favor persistence. If it emphasizes a single messy thread that is already producing contradictory answers, favor restarting. If it emphasizes a long but healthy thread that simply needs compaction, favor summarizing.

What belongs in a handoff summary

A handoff summary is a compact record that lets work continue without the original conversation. It is the bridge between sessions and the product of all three recovery strategies. It should answer the questions a capable newcomer would ask: What are we trying to do? What have we decided? What is finished? What is still open? What should happen next?

Include the goal, fixed decisions, constraints and definitions, deliverables produced, open questions or blockers, and a clear next action. Preserve exact values, mark uncertainty as uncertainty rather than guessing, and keep the document short enough to actually be pasted into a new session.

The template below can be copied and filled in. Placeholders are shown in brackets and should be replaced with the specific facts of the task.

HANDOFF SUMMARY

Goal:
[One or two sentences describing the outcome the work is meant to produce.]

Fixed decisions:
- [Decision 1, stated as a rule that still stands.]
- [Decision 2, including any version, date, or value that matters.]

Definitions and constraints:
- [Term] = [agreed meaning]
- [Constraint, tone rule, format rule, or exclusion that must be honored]

Work completed:
- [Deliverable or milestone finished, with its location if stored externally]
- [Deliverable or milestone finished]

Open items and blockers:
- [Question not yet answered, with who or what is needed to answer it]
- [Known risk or dependency]

Sources and references:
- [Document, dataset, or note that should be consulted, and where it lives]

Next action:
[The single next step, stated specifically enough to begin without further briefing.]

Write the summary while the work is still fresh, and separate settled facts from open questions visibly, because a reader who cannot tell the difference may reopen a closed decision or treat a guess as an agreement.

Memory features: convenience versus governed data store

Many assistants offer a memory feature that automatically retains facts about the user or the work and reuses them later. This is convenient: it can remember a preferred format or a standing constraint, reducing repeated setup.

Convenience is not governance. An automatic memory feature is designed to help the assistant sound consistent, not necessarily to be a system of record. Its facts may be inferred rather than confirmed, updated without a clear audit trail, and hard to inspect, correct, or export in full. The user may not know exactly what was retained.

A governed external record is explicit, reviewed, owned, and versioned, with deliberate corrections and policy-limited access. When a fact must be accurate, traceable, or shared, the governed record is the source of truth, with automatic memory treated only as a convenience layer.

Dimension Automatic memory feature Governed external record
How facts enter Often inferred from conversation Written and reviewed deliberately
Visibility May be only partly visible to the user Explicit and inspectable
Correction Quick, but may lack an audit trail Deliberate, versioned, and reviewable
Best use Preferences and low-risk continuity Decisions, definitions, and anything requiring accuracy
Risk Confident reuse of a wrong or outdated fact Staleness if nobody maintains it

Common mistake: Treating an assistant's confident reference to a "remembered" preference as proof that the fact is correct and current. Verify important facts against the record you control.

Incognito and temporary modes

Some interfaces provide a temporary or incognito mode in which a conversation is not retained in the normal history or is discarded afterward. These modes suit exploratory thinking or drafts that should not linger in the chat list.

What they do is specific: they typically prevent saving to the usual history and may prevent updating a persistent memory feature. What they do not do is guarantee anonymity, erase all copies of the text, or override an organization's logging and retention policies. The text still passes through the service to be processed, and applicable terms continue to apply.

This distinction is a frequent exam topic because it tests whether the candidate confuses conversation visibility with data-handling guarantees. Treat temporary mode as a housekeeping feature, not a security boundary. Sensitive material still needs policy, access controls, and an approved environment, regardless of the mode selected.

Managing writing preferences across chats

Continuity includes style. A user may want concise answers, a level of formality, a standard structure, or plain language. Repeating these preferences each session wastes context and invites inconsistency.

Keep a short preference note to paste into new sessions or store in an approved memory feature when policy allows. State each preference as a rule, not a history lesson: "Use short paragraphs and plain language" beats "Last time you were too formal." Avoid contradictions by deciding which rule wins when two conflict.

Preferences deserve the same governance thinking as facts. A style rule affecting public documents may need approval, and a preference encoding a legal or brand requirement belongs in the controlled source, not only in memory. Keep the note brief so it leaves room for the work.

Exam note: When a scenario describes inconsistent tone across chats, the best answer is usually to establish a single concise, reusable statement of the preference rather than repeatedly correcting the assistant after the fact.

A continuity checklist

Continuity is the discipline of keeping a piece of work coherent across time, sessions, and context limits. The following checklist can be applied at the start of a project, at natural stopping points, and whenever the warning signs appear.

  1. State the goal and the fixed decisions in one place that is not the chat itself.
  2. Capture exact values, definitions, and constraints; avoid relying on approximate recollection.
  3. Separate settled decisions from open questions in every record.
  4. Extract useful facts from large documents or tool output, then drop the raw text from the active thread.
  5. Restate critical constraints near the point of use, not only at the start of a long session.
  6. Watch for warning signs and act early rather than after answers become unreliable.
  7. Choose restart, summarize, or persist deliberately according to the situation.
  8. Write a handoff summary at every natural stopping point.
  9. Keep one concise, reusable statement of writing preferences.
  10. Match the tool to the policy: temporary mode for tidy history, governed storage for anything sensitive or auditable.

Used consistently, this checklist turns context management from a reaction into a routine.

Worked scenario

An analyst has worked for hours on a policy comparison. Early in the session the team fixed three decisions: use only published sources, present results in a two-column table, and exclude draft internal notes. A long report was pasted into the thread, followed by verbose tool output. By late afternoon, the latest tables include a draft note, the format has become three columns, and a previously rejected source has reappeared.

The analyst considers typing a longer correction, then realizes it would consume more of the scarce space. The signs point to a context problem, not an instruction problem.

The analyst checks the external project note, which holds the goal and the three decisions but not the full source list. Because those details are spread across a still-coherent thread, the analyst asks for a condensed summary of decisions, constraints, and sources accepted or rejected, then reviews it against the project note and corrects one blurred classification.

With the report's conclusions extracted, the raw text is no longer needed, so the analyst does not continue in that thread. Instead, a handoff summary is filled in using the template: goal, fixed decisions, definitions and constraints, the two-column rule, completed and remaining sections, the source list, and the single next action of finishing the final section. It is saved to the project note as the governed record.

A fresh session opens with that handoff summary. The assistant produces the final section in two columns, using only published sources and no draft notes. The next day, a follow-up again starts from the saved summary rather than a memory feature. The work stays consistent because controlling facts live outside any single window.

Notice how the three strategies combined: persistence supplied the stable record, summarization recovered distributed detail, and restarting restored a clean context. No single strategy would have handled the situation as well.

Exam note: The strongest answer in a continuity scenario is often the one that combines strategies and verifies a summary against an independent record, rather than trusting a single automated action.

Common mistakes

  • Treating the context window as unlimited storage instead of a budget shared by instructions, history, documents, tool output, and the answer.
  • Responding to degraded answers with longer prompts, which adds more text to an already crowded window.
  • Assuming a summary contains everything ever said, when it can only reflect what the assistant can currently see.
  • Using automatic memory as a system of record for facts that must be accurate, auditable, or shared.
  • Believing that temporary mode guarantees privacy or erases all copies of the text.
  • Burying a critical constraint in a large paste instead of restating it near the point of use.
  • Abandoning a thread before capturing details that exist nowhere else.
  • Keeping a preference note that contradicts itself or is too long to be reused.

Chapter summary

  • The context window is one shared budget; every extra token of input leaves less room for the answer.
  • Warning signs of a full window include lost instructions, repeated questions, contradictions, generic output, and truncated endings.
  • Early decisions get lost because older text is compressed, later messages overshadow them, and corrections stack.
  • Restart with a distilled brief when a thread is noisy or degraded; summarize when it is long but coherent; persist externally when facts must survive across sessions or people.
  • A handoff summary records the goal, fixed decisions, definitions, constraints, completed work, open items, sources, and the next action.
  • Automatic memory is a convenience; a governed external record is the source of truth for important facts.
  • Temporary mode affects conversation retention, not data handling guarantees or organizational policy.
  • A continuity checklist and a short reusable preference note keep long projects coherent.

A. Restarting from memory alone.

B. Persisting key facts in a governed external record.

C. Asking the assistant to remember the format.

A. Summaries are always longer than the original thread.

B. The assistant cannot summarize a fact that has already dropped out of its window.

D. Reviewing a summary disables the memory feature.

  1. Which statement about incognito or temporary mode is correct?

A. It guarantees that the text is never transmitted to the service.

B. It erases all copies of the text from every system.

C. It typically limits retention in the normal history but does not override processing or organizational policy.

D. It permanently increases the size of the context window.

  1. Which item belongs in a handoff summary?

A. Every message exchanged during the session, copied verbatim.

B. Only the assistant's opinions about the work.

C. Fixed decisions, constraints, completed work, open items, and the next action.

D. A list of unrelated background facts to maximize context.

Answers and rationale

  1. B. The answer is correct because input and output share one budget; a huge document and a request for a long reply can leave too little space to finish. A is incorrect because the reply began well, showing the document was used. C is incorrect because a formatting error in source text would not normally stop generation mid-answer. D is incorrect because temporary mode affects retention, not response length.

  2. A. These three signals together, asking for already-provided facts, dropping a standing rule, and contradicting definitions, are classic indicators of a crowded context. B describes a concise answer, which is not a warning sign. C describes an ordinary action with no bearing on the limit. D describes good practice, not degradation.

  3. C. When a thread is long but still coherent, summarization consolidates distributed detail, and verification catches anything the model can no longer see. A is incorrect because a coherent thread still holds useful detail and needless restarting can lose it. B is incorrect because summarization often does help and can feed the external record. D is incorrect because temporary mode does not selectively remove older turns.

  4. B. Cross-session, cross-person, auditable continuity requires a governed external record that does not depend on any chat window. A is incorrect because restarting from memory alone is unreliable and unauditable. C is incorrect because an automatic memory feature is not a controlled source of truth. D is incorrect because shortening prompts without recording facts guarantees loss.

  5. B. A summary can only reflect content currently visible to the model, so a detail already dropped cannot be recovered from it. A is incorrect because summaries are meant to be shorter. C is incorrect because a good summary explicitly lists open questions. D is incorrect because reviewing a text has no effect on memory settings.

  6. C. Temporary mode generally limits retention in the ordinary history while the text is still processed and organizational policies still apply. A is incorrect because the text must be transmitted to be processed. B is incorrect because no such universal erasure is guaranteed. D is incorrect because the mode does not change window capacity.

  7. C. A handoff summary is built from fixed decisions, constraints, completed work, open items, sources, and the next action. A is incorrect because a verbatim transcript defeats the purpose of compaction. B is incorrect because opinions are not reliable continuity facts. D is incorrect because unrelated background wastes the budget and obscures what matters.
