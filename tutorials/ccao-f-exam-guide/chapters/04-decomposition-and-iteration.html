Decomposing Work: Step Chains and Iteration

Learning objectives

  • Explain why one large request usually produces weaker and harder-to-check work than a sequence of smaller requests.
  • Break a goal into ordered steps, each with a defined input, action, and output.
  • Build a chain in which one step's output becomes the next step's input.
  • Decide how many steps a task needs and place checkpoints where they catch the most risk.
  • Tell which steps can run in parallel and which have a fixed order.
  • Refine output with specific, named feedback instead of "make it better," keep a log of prompt versions, and measure whether iteration helped.

Key concepts

Why a single large request often fails

It is tempting to hand an assistant one enormous instruction: research a market, compare the options, write a recommendation, and format it as a one-page brief. The request sounds reasonable, but it concentrates several different kinds of work into a single turn, and each kind has its own standard. Research wants sources and dates. Comparison wants one criterion applied evenly to every option. A recommendation wants a decision rule. A brief wants a defined audience and format. When all of these are asked for at once, the response typically satisfies some and silently drops others — sources go undated, criteria shift between options, or the recommendation arrives without a stated reason.

The second problem is inspection. A single block of text gives you a result but no diagnostic trail. If the brief is unconvincing, you cannot tell whether the research was shallow, the criteria were weak, or the writing buried the point. The usual response is to rewrite the whole request and hope for a better result, which is slow and unreliable.

The third problem is error propagation. In an unbroken answer, an early mistake is carried forward silently. If the first paragraph misstates a figure, every later sentence inherits it, and fluent writing makes the error harder to notice. Splitting the work does not prevent errors, but it exposes each one at the moment it is made, before it spreads.

Decomposition is an inventory exercise, not a clever trick: list the distinct jobs hidden inside a request, then give each its own turn so it can be done and checked on its own terms. The candidate who builds this habit will find that many exam scenarios become straightforward, because the correct option is usually the one that isolates a checkable piece of work rather than bundling it with everything else.

Exam note: A scenario describing a long, multi-part request with a disappointing result is almost always testing decomposition. Choose the option that separates the work into ordered, checkable steps, not the one that merely rewrites a longer single prompt.

What decomposition actually means

Decomposition turns one goal into a small set of ordered steps, each with three things: an input it consumes, an action it performs, and an output it produces. That definition gives you a test for whether you have decomposed well. If you cannot say what a step consumes and what it produces, the step is still too vague.

Consider the goal "prepare a summary of a research topic for a team briefing." A weak decomposition would be "gather information, then write the summary," because the first step hides most of the difficulty. A better version names the outputs:

  1. Collect candidate sources, noting origin and date for each.
  2. Screen for relevance and reliability, discarding the rest.
  3. Extract key claims and supporting figures from what remains.
  4. Group the claims into themes and note where sources disagree.
  5. Draft a short summary organized around those themes.
  6. Check the draft against the extracted claims for unsupported statements.

Each step produces something tangible: a source list, a screened list, a claim set, a theme map, a draft, and a checked draft. The steps are not only smaller; they are different in kind. Collecting differs from screening, screening from extracting, extracting from writing. That difference is what makes separate steps worthwhile. Splitting one action into ten identical fragments adds overhead without adding control.

A reliable rule is to split where the success criterion changes. Screening is judged by relevance and reliability; drafting is judged by clarity and audience fit. Because the standards differ, the activities deserve separate instructions and separate checks. When the standard stays the same, keep the activities together. This also shows why decomposition is not the same as length control. Asking for shorter paragraphs is a formatting instruction; asking for the source list first, then the screened list, then the claims, creates intermediate artifacts that can be inspected.

Chaining steps: output becomes input

Once work is split, the steps must be connected. In a prompt chain, the output of one step becomes the input of the next. That is the defining feature of chaining and what turns a list of tasks into a pipeline.

The connection matters twice. It preserves context without repetition: the second step receives the curated output of the first rather than being told the whole background again. And it creates a stable handoff: each step gets a bounded, named input, which clarifies its job and makes its output easier to evaluate.

A three-step chain for a research-to-summary task can be sketched like this:

STEP 1 — COLLECT
Input:  topic statement plus any supplied documents
Action: list candidate sources with title, origin, and date; flag unsigned items
Output: SOURCE LIST (one line per candidate)

STEP 2 — SCREEN AND EXTRACT
Input:  SOURCE LIST from Step 1
Action: keep only relevant, dated sources; extract two or three strongest claims
        from each; mark any claim the source does not clearly support
Output: CLAIM SHEET (claim | source | date | confidence label)

STEP 3 — DRAFT AND CHECK
Input:  CLAIM SHEET from Step 2
Action: write a 200-word summary by theme; use only claims on the sheet; append
        a list of anything the sheet could not support
Output: DRAFT SUMMARY plus SUPPORT GAPS

Each step names its input and output, so the handoff is unambiguous, and the outputs carry labels that later steps can reference precisely. The final step is limited to claims on the sheet, which keeps the summary grounded in what was actually collected. It also produces a second artifact — the support gaps — that records where the evidence ran out. A well-designed chain delivers not only an answer but a description of the answer's limits.

Chaining changes how you write each prompt too. Because the input is already curated, later prompts can be short and narrow; you point at a named artifact and give one instruction. This is why chains often use fewer words overall than one enormous prompt, despite taking more turns.

Try it: Take a request you would normally send in one message. Write down the intermediate artifact you would want after each stage. If you cannot name the artifact, you have not yet found the real step boundary.

Deciding how many steps are enough

More steps are not automatically better. Each one adds a turn, a handoff, and a chance to introduce a copying error. The goal is the smallest number of steps that makes the risky parts of the work individually checkable.

Three signals help you decide. The first is heterogeneity: are the activities genuinely different in kind? Collecting and screening are, so they justify separate steps; screening and underlining important lines are not. The second is checkability: would you want to inspect the intermediate result before continuing? A bad source list would ruin everything downstream, so it earns its own step and checkpoint. The third is branching: does the next action depend on a decision made in the previous one? If the summary structure depends on which themes emerged, theme-building must finish before drafting starts.

When all three signals are absent, one step is enough. When all three are present, a separate step is warranted. Most tasks fall between the two, and the right answer is usually three to six steps rather than two or twenty.

A related idea is the "smallest checkable unit." Comparing three options could mean one extraction step per option followed by a comparison, or one step extracting all three with shared criteria. Decide by asking whether a mistake in one option would be hard to spot among the three. If it would, separate them; if the extractions are mechanical and uniform, keep them together and spend the saved step checking the comparison.

Over-decomposition has a cost that exam questions like to test. A chain of fifteen micro-steps can lose the overall goal, with nobody responsible for whether the pieces still answer the request. If a chain grows long, add a final assembly step whose only job is to confirm that the outputs add up to what was asked.

Checkpoints between steps

A checkpoint is a deliberate pause at which a person inspects an intermediate output before it is passed forward. Checkpoints make a chain safe. Without them, chaining merely moves an error downstream; with them, the error is caught close to its source.

Not every step needs one. Ask instead: "If this output is wrong, how expensive is it to fix after the next step has used it?" An error in a source list is cheap to fix when the list is produced and expensive after a summary has been written from it, so that is a high-value checkpoint. A formatting choice is cheap to fix at any time and needs no formal pause.

Checkpoints should be tied to a specific test, not to a feeling that things look fine. Effective tests are short and objective:

Step Main risk Checkpoint test Checked by
Collect sources Missing dates, invented titles Every line has an origin and a date Analyst
Screen and extract Unsupported claims Each claim traces to a source line Analyst
Compare options Criteria drift Same criteria applied to all options Reviewer
Draft summary Ungrounded sentences No sentence lacks a claim-sheet entry Team lead
Assemble final brief Original goal lost Brief answers each part of the request Team lead

A checkpoint with a written test is repeatable: a colleague can apply it, and the same test can be used on the next run of the pipeline. The "checked by" column matters as much as the test. A checkpoint performed by the person who produced the output is useful for mechanical errors but weaker for judgment calls. When a decision is consequential, assign the check to a different role, applying the human review boundary inside the chain rather than only at its end.

Common mistake: Treating a checkpoint as a quick glance. Without a written test, a checkpoint tends to become a rubber stamp, especially late in a long chain when the reviewer wants to move on.

Order versus parallelism

Some steps must run in sequence; others can safely run together. Knowing which is which shortens a workflow without weakening it.

Order is fixed when one step consumes another's output. You cannot screen a source list before it exists, or draft from claims not yet extracted. These are dependencies, and no scheduling removes them. Ignoring a dependency produces invented inputs, which is worse than producing nothing.

Parallelism is safe when steps consume the same input and produce independent outputs. Extracting the same fields from three documents uses shared criteria and no step feeds another, so the three extractions can run together and be merged later. Checking a draft for tone and checking it for factual support are likewise independent reviews of one fixed text.

The trap is assuming independence where a hidden dependency exists. "Summarize each report, then identify contradictions between them" allows the summaries in parallel, but the contradiction check cannot start until all summaries exist. Sending all four tasks at once produces a contradiction analysis built on incomplete or guessed content. The safe pattern is: parallelize where inputs are fixed and outputs independent, and keep the sequence wherever one output feeds another.

Situation Parallel? Reason
Extract the same fields from several documents Yes Shared criteria, no output feeds another
Screen sources, then draft from the screened set No Drafting depends on the screening result
Check tone and factual support of one draft Yes Two independent reviews of fixed text
Build themes, then organize a summary around them No Structure depends on the themes
Translate one brief into three languages Yes Each uses the same source
Translate, then check consistency across versions No Consistency check needs all versions

Parallelism also helps verification. When independent steps use the same criteria, disagreement between their outputs is informative: one extraction reporting a figure the others contradict is a signal to investigate. Sequential chains offer fewer such cross-checks, because each step sees only what the previous one passed along.

Iterative refinement: feedback that names the gap

A chain moves work forward through different activities; iteration improves one output by cycling back to it. Both take several turns, but they solve different problems. Chaining answers "what comes next?" Iteration answers "what exactly is wrong with this, and how should it change?"

The quality of iteration is determined almost entirely by the quality of feedback. "Make it better," "improve this," and "try again" supply no usable signal. They may produce a different version, but different is not the same as better, and there is no way to tell whether the real problem was addressed. Compare two pieces of feedback on a draft summary:

  • Weak: "This isn't quite right. Make it better."
  • Strong: "In the second paragraph, remove the 30 percent figure — the claim sheet does not contain it — or label it unsupported. Then shorten the opening from four sentences to two."

The strong version does three things: it points to a location, identifies a defect, and gives a corrective action with a limit. The revision is verifiable by looking at the second paragraph and counting the opening sentences.

A dependable structure for feedback has four parts: location, observation, instruction, constraint. "In the comparison table, the third row uses a different unit from the first two. Convert it to the same unit and keep the table to five rows." Location is the table, observation the unit mismatch, instruction the conversion, constraint the row limit.

Iteration works best when feedback is anchored to a standard outside the response. A rubric, a set of required sections, a source document, or the original request all provide that anchor. "Make it more concise" is subjective; "reduce it to 150 words and keep the three headings" is objective. Convert subjective preferences into measurable properties wherever possible.

There is also a limit. After two or three rounds with no clear improvement, the problem is usually in the instruction or the underlying material, not the drafting. That is the moment to step back and check whether an earlier step supplied the wrong input. Polishing a broken foundation is a common way to waste time.

Exam note: When a question asks how to improve a weak response, prefer the option giving specific, bounded feedback over the one requesting a general improvement. Specificity is the hallmark of good iteration and is easy to test.

Keeping a change log

When a prompt or chain is revised more than once, it is easy to lose track of what changed and why. A change log is a short record of versions, reasons, and effects. It prevents accidental regression by letting you return to an earlier version, supports reuse by showing which version produced the accepted result, and makes measurement possible by letting you compare outcomes instead of relying on memory.

A minimal log records four fields: version, what changed, why, and what happened. The last field should be as concrete as the evidence allows — an error count, a word count, a pass or fail against a checklist — rather than a general impression.

PROMPT: Screening step for source list
V1  Prompt: "Keep the relevant sources."
    Result: 8 of 12 retained; no reasons for exclusion.
V2  Added date filter and one exclusion reason each.
    Why: undated sources in V1 could not be audited.
    Result: 5 of 12 retained; every exclusion explained.
V3  Added: flag sources with no named organization.
    Why: two V2 sources were anonymous posts.
    Result: one more flagged for a human decision.

Each version builds on the observed weakness of the last, which is the log's deeper purpose: it forces you to state a reason, and a revision without a reason is usually a guess. For chains, also log changes to the handoff between steps. Changing a step's output format from a table to prose can break the next step even when its prompt looks fine.

Measuring whether iteration improved the result

Iteration costs time and attention, so it is worth asking whether it paid off. Define a small checklist and score each version against the same items. For a summary, that might be: required sections present, no unsupported figures, correct length, correct register, and a stated uncertainty note. A change that lifts the score from three to five is clearly useful; a change that leaves it at three but improves prose may still help, but only if polish was the goal.

When one output is hard to score, compare two candidates side by side against a rubric. The comparison makes differences that are invisible when judging each alone. Treat the assistant's own self-assessment as a clue about omissions, not as independent evidence.

Measure the right thing. A revision that improves readability while introducing a factual error is a net loss for most work tasks, so keep accuracy checks separate from style checks. Not every inconsistency should be "fixed": if two credible sources genuinely disagree, forcing agreement creates a cleaner answer and a worse one. The correct refinement labels the disagreement. A measurement system that rewards smoothness alone pushes toward the wrong edit.

One-shot, chained, and iterative approaches compared

The three approaches are not rivals; each fits a different situation, and a mature workflow often combines them.

Aspect One-shot Chained Iterative
Structure One request, one response Ordered steps with named handoffs Repeated revisions of one output
Best for Simple, low-risk, well-specified tasks Multi-stage work with distinct activities Refining against a known standard
Main strength Fast and cheap Checkable intermediate artifacts Targeted improvement
Main weakness Hard to diagnose when wrong More turns and copying effort Can polish a fundamentally wrong answer
Error visibility Low — one block of text High — each step inspected Medium — only the revision is seen
Verification point Only at the end At each checkpoint After each revision

One-shot requests trade control for speed, chains trade speed for visibility, and iteration trades speed for refinement. The choice depends on the cost of being wrong and the number of distinct activities hidden in the task. A low-stakes formatting change suits one shot; a research pipeline with consequential figures suits a chain; a draft that is accurate but aimed at the wrong audience suits iteration. Many real tasks combine all three, and exam questions tend to reward recognizing that combination rather than insisting one method is universally best. Treat any answer claiming a single approach is always correct as a warning sign.

Exam note: High-stakes decisions, untrusted sources, or tasks with several distinct activities point to a chain with checkpoints. A single output that misses a known requirement points instead to iteration with specific feedback.

Worked scenario

Situation. An analyst is asked to prepare a one-page briefing for a team lead on whether a proposed process change is worth piloting. Three documents arrive: an internal proposal, a spreadsheet of historical results, and informal meeting notes. The analyst's first attempt is one long prompt asking for "a briefing with a recommendation based on the attached files." The result reads well but contains a figure absent from every document and treats the meeting notes as settled fact.

Diagnosis. The single prompt mixed four activities — reading, separating evidence from opinion, weighing options, and writing — while offering no way to inspect any of them. The invented figure appeared during drafting, where the model tried to make the narrative complete. The notes were treated as facts because nothing asked for their status to be labeled. Neither error could be located in a single block of text.

Redesign. The analyst rebuilds the work as a short chain with checkpoints:

1. INVENTORY: list each document, its date if shown, and whether its contents
   are data, proposal, or opinion.  -> MATERIAL MAP
   Check: every document accounted for; opinion labeled.

2. EVIDENCE: extract only claims and figures actually written in the documents;
   record the source and status of each; infer no numbers.  -> EVIDENCE TABLE
   Check: each figure traced to a document; no invented figures.

3. DECIDE: state a rule for recommending a pilot, apply it, and list supporting
   evidence and blockers.  -> DECISION NOTE
   Check: rule stated before the recommendation.

4. BRIEF: write one page for a team lead; recommendation first; evidence and
   "what we do not know" sections; use only evidence-table claims.
   -> DRAFT BRIEF plus OPEN QUESTIONS

Execution and refinement. Step 1 reveals that the meeting notes are undated and mostly opinion. Step 2 yields eleven claims, of which four are data, five are proposals, and two are opinion; the invented figure never appears because inference is forbidden. At Step 3 the analyst sees that the proposed rule — one improving data point is enough — is too weak, and revises it before applying it, logging the change with its reason. The first draft is accurate but buries the recommendation in paragraph three. The analyst iterates with named feedback: "Move the recommendation to the first sentence, cut the background from 180 words to 60, and leave the 'what we do not know' section unchanged."

Result. The team lead receives a brief whose recommendation traces to a stated rule and a small evidence table, with open questions listed separately. When asked where a figure came from, the analyst points to the evidence table rather than reconstructing the conversation. The process took four steps, one upstream rule change, and one targeted revision — far easier to audit than the original prompt.

Why this matters for the exam. The scenario combines familiar exam features: multiple documents, a mix of fact and opinion, a consequential recommendation, and a fluent but wrong first attempt. The remedy is to isolate risky activities, make their outputs inspectable, and give feedback that names a specific gap. Notice that the analyst corrected the decision rule rather than endlessly rewriting the final brief. Knowing when to go upstream is a higher-level skill than polishing downstream, and it is frequently tested.

Common mistakes

  • Sending one large request for a multi-stage task and hoping the result is internally consistent.
  • Splitting a task into steps without naming what each produces, leaving handoffs vague.
  • Chaining steps in the wrong order, forcing a later step to use an input that does not exist.
  • Running dependent steps in parallel and accepting a result built on guessed inputs.
  • Treating checkpoints as a quick glance rather than applying a short, written test.
  • Using "make it better" as feedback, which supplies no usable direction.
  • Iterating on wording when the real problem is an unsupported claim or flawed rule upstream.
  • Judging improvement by impression instead of applying the same checklist to each version.
  • Adding more steps when one step's instruction is actually unclear.

Chapter summary

  • One large request mixes different standards, hides diagnosis, and lets early errors spread silently.
  • Decomposition creates ordered steps with a defined input, action, and output; split where the success criterion changes.
  • In a chain, each step's output becomes the next step's input, so prompts stay short and grounded in a named artifact.
  • Use the smallest number of steps that makes risky work checkable, and add an assembly step if a long chain might lose the goal.
  • Place checkpoints where errors would be costly later, and attach a specific test and a checker to each.
  • Parallelize only steps with fixed inputs and independent outputs; preserve order wherever one step depends on another.
  • Refine with feedback naming a location, observation, instruction, and constraint.
  • Log versions with reasons and effects, including changes to handoff formats.
  • Measure each version against the same checklist, keeping accuracy separate from style.
  • One-shot, chained, and iterative methods suit different tasks; mature workflows combine them.

Checkpoint questions

1. An analyst asks the assistant to review five contracts and flag unusual clauses. The result summarizes all five but defines "unusual" differently for each. What is the best fix?

A. Ask for a more concise summary. B. Restate the request with a stronger warning to be careful. C. Define one criterion for "unusual," then apply it to each contract in a separate step and compare. D. Combine the five contracts into one document and ask again.

2. Which is the clearest example of a prompt chain?

A. Asking for a draft, then a shorter version of the same draft. B. Asking for sources, passing that list into a prompt that extracts claims, then passing the claims into a drafting prompt. C. Asking for three different summaries of one article in a single message. D. Asking for a summary and a critique in the same response.

3. A workflow has four steps: collect sources, screen sources, draft a summary, check the draft for tone. Which pair can safely run in parallel?

A. Collect and screen sources. B. Screen sources and draft the summary. C. Draft the summary and check its tone. D. Check tone and check factual support of the same finished draft.

4. Which refinement feedback is most likely to produce a useful revision?

A. "Make this better." B. "Improve the tone and try to be more accurate." C. "In paragraph two, remove the unsourced figure, then reduce the introduction to two sentences." D. "Rewrite the whole thing from scratch."

5. What is the main purpose of a checkpoint between two steps?

A. To make the response sound more polished. B. To inspect an intermediate output before an error spreads. C. To reduce the number of steps in the workflow. D. To let the assistant grade its own work.

6. After three revisions a draft is smoother but still rests on a flawed rule set in an earlier step. What should the analyst do?

A. Keep refining the wording until it reads well. B. Ask for a different draft using the same rule. C. Revisit and correct the earlier step, then rebuild what depends on it. D. Accept the draft because polish is the main goal.

7. Which change-log entry is most useful to a later reviewer?

A. "V2 — improved." B. "V2 — changed the prompt; looks better." C. "V2 — added a date filter and a reason for each exclusion; V1 had undated sources; retained sources fell from eight to five." D. "V2 — the assistant suggested this version."

8. A colleague claims chaining is always better than a single prompt. What is the best response?

A. Agree, because more steps always produce better answers. B. Disagree, because simple low-risk tasks may not justify the overhead and the method depends on the task. C. Agree, but only when the chain has more than ten steps. D. Disagree, because iteration is always superior to chaining.

Answers and rationale

1. Correct answer: C. A shared standard applied consistently is exactly what a lack of common definition calls for, and separate steps make the application auditable. Option A addresses length, not the problem. Option B adds emphasis without a standard, so the inconsistency likely returns. Option D changes the input format but leaves the definition undefined.

2. Correct answer: B. Each step consumes the named output of the previous one: sources feed extraction, extraction feeds drafting. Option A is iteration on one output. Option C produces parallel independent summaries, not a connected sequence. Option D combines two activities in one response, the opposite of decomposition.

3. Correct answer: D. Both checks consume the same finished text and neither needs the other's result. Option A fails because screening needs the collected sources. Option B fails because drafting depends on which sources survive screening. Option C fails because a tone check needs the finished draft as input; it can be paired with a support check only after drafting ends.

4. Correct answer: C. It names a location, an observation, an instruction, and a constraint, and the result can be verified. Option A gives no signal. Option B is subjective with no test for "more accurate." Option D discards useful work and says nothing about what was wrong.

5. Correct answer: B. The point is to catch an error near its source before later steps build on it. Option A confuses a checkpoint with polishing. Option C is wrong because checkpoints add pauses rather than remove steps. Option D is wrong because a meaningful checkpoint is a human inspection against a test.

6. Correct answer: C. When the defect sits in an earlier step, fix it upstream and rebuild what depends on it; polishing cannot repair a flawed rule. Option A wastes effort on surface features. Option B reproduces the same flawed structure with new words. Option D accepts a known defect and mistakes polish for correctness.

7. Correct answer: C. It records what changed, why, and the observed effect, so a reviewer can understand and reproduce the decision. Option A records almost nothing. Option B gives neither reason nor outcome. Option D treats a suggestion as justification, which is not evidence the change helped.

8. Correct answer: B. Method choice depends on the task: simple low-risk requests can be handled in one shot, while multi-stage consequential work benefits from a chain. Option A makes an absolute claim ignoring overhead. Option C invents an arbitrary threshold. Option D makes the opposite absolute claim, which the comparison table rejects.
