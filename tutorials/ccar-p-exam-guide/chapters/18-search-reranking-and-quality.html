Chapter 18 — Search Strategies, Reranking, and Retrieval Quality

Learning objectives

  • Select and combine search strategies to match different query types and information needs.
  • Explain how candidate retrieval, fusion, and reranking work together in multi-stage retrieval pipelines.
  • Apply query transformation and filtering techniques to improve relevance and precision.
  • Measure retrieval quality with appropriate signals and diagnose common failure modes.
  • Balance relevance, latency, cost, and safety when tuning retrieval behavior.

Key concepts

From query to evidence: the retrieval pipeline

Query-time retrieval transforms a user need into a set of evidence candidates that can support a response. In simple cases, a single search pass may suffice. In more demanding systems, retrieval is a pipeline: interpret or transform the query, retrieve candidates from one or more indexes, filter by constraints, optionally rerank for relevance, and select a final context set for generation. Each stage offers opportunities to improve quality and opportunities to introduce latency or errors. Understanding the pipeline helps architects diagnose whether poor answers stem from missing candidates, poor ranking, irrelevant context selection, or downstream generation behavior.

Retrieval goals are often summarized as recall and precision. Recall asks whether relevant information is found at all; precision asks whether retrieved items are actually useful. Early stages typically prioritize recall—casting a wide enough net to include likely evidence—while later stages improve precision by filtering and ranking. Over-optimizing for one can harm the other: overly narrow retrieval misses key facts, while overly broad retrieval floods the context with noise and increases cost.

Query intent matters. A request for a specific identifier favors exact matching; a conceptual question favors semantic similarity; a constrained request may require filtering by product, region, time, or permission. Effective systems adapt strategy to intent rather than applying one method uniformly to all queries.

Exam note: Treat retrieval as multi-stage when needed: maximize recall for candidates, then improve precision with filtering and reranking before adding context to the prompt.

Search strategies: lexical, semantic, and hybrid

Lexical search matches query terms against indexed text, often using scoring methods that reward term relevance and rarity. It is strong for exact phrases, codes, proper names, and cases where users know the vocabulary in the source. Semantic search uses vector similarity to find passages with related meaning, helping when users paraphrase or when relevant content uses different wording. Each has blind spots: lexical search can miss synonyms, while semantic search can overlook exact tokens or return topically related but not specifically relevant passages.

Hybrid search combines lexical and semantic retrieval to cover more query types. Results from different methods can be merged through fusion techniques that balance scores or ranks. Hybrid approaches are common in enterprise settings because user queries vary widely. However, hybrid retrieval introduces tuning decisions: how many candidates to fetch from each source, how to weight methods, and how to handle queries where one method is clearly more appropriate. Without evaluation, added complexity may not yield better outcomes.

Structured filtering complements these strategies. Metadata constraints—such as access scope, document type, recency, or language—can be applied before or after candidate retrieval depending on system design. Filtering is essential for correctness and governance, not merely optimization: retrieving unauthorized or obsolete content is a quality failure even if the text seems relevant.

Query type Likely strong strategy Helpful complement Common pitfall
Exact code, ID, or name Lexical/keyword Field filters, exact match boosts Semantic-only search misses literal token
Conceptual “how/why” question Semantic or hybrid Reranking for answer relevance Retrieving topically similar but unhelpful text
Policy question in specific domain/version Hybrid + metadata filters Recency/version constraints Ignoring scope and returning outdated policy
Ambiguous short query Query reformulation + hybrid Clarification or diversified candidates Overconfident retrieval from sparse intent

Query transformation and candidate expansion

User queries are often incomplete, ambiguous, or phrased differently from source documents. Query transformation techniques aim to bridge this gap. Normalization handles spelling, casing, or terminology variants. Expansion adds related terms or synonyms. Rewriting reformulates a query into a clearer or more retrieval-friendly form. Decomposition breaks a complex question into subqueries that can be answered from different sources or sections. These techniques can improve recall but must be applied carefully to avoid drifting from the user’s intent.

In conversational or multi-step systems, the effective query may need to incorporate relevant context from prior turns—such as the entity being discussed—while excluding irrelevant history. Poorly managed context can cause retrieval to chase outdated topics or include sensitive details unnecessarily. When transformation is model-assisted, it should be evaluated like any other component: helpful rewrites improve evidence quality, but hallucinated or over-specific rewrites can degrade it.

Candidate set size is another tuning lever. Retrieving too few candidates risks missing the right evidence; retrieving too many increases reranking cost and can introduce noise. A common pattern is to retrieve a moderately broad set, apply filters, rerank, and pass only the top relevant passages into the generation context. The optimal numbers depend on corpus size, query diversity, and latency budget.

Common mistake: Passing many weakly relevant chunks into the prompt. Excess context can dilute key evidence, increase cost, and lead to confused or unfocused responses.

Reranking and final context selection

Initial retrieval methods optimize for efficient search over large indexes, but their top results are not always the best evidence for answering a specific question. Reranking applies a more selective relevance assessment to a candidate set, reordering items so the most useful passages appear first. Rerankers may consider query-passage interaction more deeply than first-stage retrieval, improving precision at additional computational cost. Because reranking operates on a limited candidate set, it complements rather than replaces broad retrieval.

Final context selection decides what the model will actually see. Selection should consider relevance, diversity, freshness, and token budget. Including multiple near-duplicate chunks wastes space, while including diverse supporting passages can improve completeness. Selection logic may also enforce constraints such as “include at least one authoritative source” or “prefer current version.” Provenance should be preserved so generated answers can cite or reference sources.

Reranking and selection policies should be evaluated end to end. A reranker that boosts semantically fluent but factually irrelevant passages can harm groundedness. Likewise, strict filtering that removes all candidates may force the system to answer without evidence unless fallback behavior is defined. Safe fallback options include asking for clarification, broadening search within allowed bounds, or stating that sufficient evidence was not found.

retrieval_pipeline:
  query_stage:
    normalize: true
    rewrite: "when_ambiguous"
    decompose: "for_multi_part_questions"
  candidate_stage:
    lexical_top_k: 20
    semantic_top_k: 20
    filters: ["access_scope", "language", "current_version"]
  fusion: "rank_blend"
  rerank:
    enabled: true
    input_candidates: 30
    output_top_k: 6
  context_selection:
    max_chunks: 5
    prefer: ["high_relevance", "source_diversity", "freshness"]
  fallback:
    if_no_evidence: "state_not_found_and_request_clarification"

Try it: For a set of failed answers, inspect which stage failed: were relevant documents absent from candidates, ranked too low, filtered out, or excluded from final context?

Measuring and tuning retrieval quality

Retrieval quality should be measured with representative queries and labeled expectations where feasible. Useful signals include whether relevant sources appear in top results, how highly they rank, whether unauthorized or outdated sources appear, and whether selected context supports correct answers. Offline evaluation with curated query-document pairs helps compare strategies systematically. Online signals—user feedback, reformulation rates, escalation rates, and groundedness outcomes—provide additional evidence but can be noisy.

Diagnosis benefits from stage-level instrumentation. Logging query transforms, candidate counts, filter effects, reranker scores, and final selected chunks (with appropriate safeguards) makes it possible to see where evidence was lost. Tuning should be iterative and controlled: changing chunking, embeddings, fusion weights, or reranking together obscures causality. Because improvements on one query class can regress another, evaluations should cover diverse intents and constraints.

Symptom Likely cause Investigation Possible adjustment
Relevant doc never appears Recall or ingestion issue Check index presence, chunking, query terms Improve chunking, hybrid retrieval, query rewrite
Relevant doc appears low Ranking/reranking weakness Inspect scores and candidate set Tune fusion, add reranker, adjust boosts
Irrelevant docs dominate Precision/filtering issue Review filters and semantic drift Stronger filters, smaller/noisier candidate set

Worked scenario

Context

A product support assistant uses retrieval to answer troubleshooting questions from a large knowledge base. Users report mixed results: queries containing exact error codes sometimes return generic articles, while broad “how do I fix…” questions sometimes miss the most relevant procedure. The system currently relies on semantic search only, retrieves the top ten chunks, and passes all of them into the prompt. Content is tagged by product area and version, but these tags are not consistently applied during retrieval.

Analysis

The symptoms indicate mismatched strategy and weak precision controls. Semantic-only search can underperform on exact error codes where lexical matching is strong. Passing ten uncurated chunks may include marginally related content, diluting the signal for generation. Ignoring product and version metadata risks retrieving irrelevant or outdated procedures, especially in a multi-product environment. The system needs better recall for literal queries, better precision in final context, and consistent constraint enforcement.

A multi-stage pipeline can address these issues: hybrid candidate retrieval to cover both exact and conceptual queries, metadata filters for product and current version, reranking to prioritize the most useful passages, and tighter final selection to fit the context budget. Evaluation should separately assess error-code queries and conceptual troubleshooting queries to ensure improvements do not trade one class for the other.

Resolution

The architect introduces hybrid retrieval with lexical and semantic candidates, then applies mandatory filters for product area and supported version based on request context. A reranker scores the merged candidates, and the top five diverse, high-relevance chunks are selected for generation. Queries containing recognized error-code patterns receive an additional lexical boost. Fallback behavior is defined: if filtered results are insufficient, the assistant requests clarifying details rather than answering from weak evidence.

Instrumentation captures candidate sources, filter removals, reranked positions, and final context. Testing on labeled queries shows improved retrieval of exact-code articles and better focus for conceptual questions. Support feedback indicates fewer irrelevant responses and clearer citations. Ongoing tuning uses stage-level metrics to adjust candidate counts and selection rules as the knowledge base evolves.

Common mistakes

  • Using a single search method for all query types despite differing retrieval needs.
  • Skipping metadata filters, leading to irrelevant, unauthorized, or outdated evidence.
  • Treating first-stage ranking as sufficient and overloading the prompt with weak candidates.
  • Applying query rewrites without evaluating whether they preserve user intent.
  • Tuning retrieval without stage-level measurements, making failures hard to diagnose.

Chapter summary

  • Retrieval pipelines balance recall and precision through candidate search, filtering, reranking, and context selection.
  • Lexical, semantic, and hybrid strategies have complementary strengths that should match query intent.
  • Query transformation and metadata constraints can improve relevance but require careful control and evaluation.
  • Reranking and selective context assembly improve evidence quality within latency and token budgets.
  • Stage-level measurement and diagnosis enable targeted tuning and safer fallback behavior.

Checkpoint questions

  1. What is the primary role of reranking in a retrieval pipeline?

    A. To replace indexing entirely
    B. To improve precision by reordering a candidate set for relevance
    C. To guarantee freshness without metadata
    D. To increase the number of chunks sent to the prompt

  2. Which strategy is most appropriate for a query containing an exact error code?

    A. Semantic-only search with no lexical matching
    B. Lexical matching, often complemented by hybrid retrieval and filters
    C. Random candidate selection
    D. Ignoring the code and using only topic similarity

  3. Why can adding more retrieved chunks reduce answer quality?

    A. Because context windows never have limits
    B. Because irrelevant or redundant chunks can dilute key evidence and add noise
    C. Because reranking requires empty context
    D. Because filters stop working with large sets

  4. What is a benefit of metadata filtering during retrieval?

    A. It ensures only contextually and policy-appropriate content is considered
    B. It removes the need for evaluation
    C. It makes query intent irrelevant
    D. It guarantees perfect recall

  5. A relevant document is indexed but never appears in candidates. What is the best next step?

    A. Only rewrite the final answer prompt
    B. Investigate recall issues such as query strategy, chunking, or indexing representation
    C. Increase generation temperature
    D. Remove all filters without analysis

  6. How should query rewriting be treated in a high-quality system?

    A. As always correct and exempt from testing
    B. As a component to evaluate for intent preservation and retrieval impact
    C. As a replacement for source metadata
    D. As useful only for lexical search

Answers and rationale

  1. Correct: B. Reranking refines candidate ordering to improve relevance of selected evidence. A, C, and D misstate its purpose.
  2. Correct: B. Exact codes favor lexical matching, often strengthened by hybrid methods and constraints. A and D miss literal precision, and C is nonsensical.
  3. Correct: B. Excess or low-quality context can obscure important evidence and increase cost. A, C, and D are incorrect.
  4. Correct: A. Filters enforce relevance and governance constraints such as scope and version. B, C, and D overclaim.
  5. Correct: B. Absence from candidates indicates a recall-side problem to investigate. A and C address the wrong stage, and D may violate constraints.
  6. Correct: B. Rewrites can help or harm and must be evaluated for intent and outcomes. A, C, and D are incorrect assumptions.
