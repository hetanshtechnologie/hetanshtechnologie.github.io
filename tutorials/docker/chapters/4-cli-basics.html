Docker CLI Basics: run, ps, stop, rm

This chapter is the command reference you will actually use daily. Every section pairs the command with a real invocation and a "what to check next." By the end you can run, debug, and clean up containers without looking anything up.

4.1 The lifecycle in one line

pull --> create --> start --> (attach) --> stop --> start --> ... --> rm
   \__docker run is create + start + attach in one shot__/

Diagram (described in text): the container state machine. pull/download feeds create; create builds the writable layer (state: created); start makes it running; running can pause, or stop to exited; exited can start again or be removed by rm. From any state, docker rm -f jumps straight to removed.

4.2 docker run — the master command

# name + detach + port map + remove-on-exit, all at once
docker run -d --name web -p 8080:80 --rm nginx

# interactive shell for exploration (auto-removes when you exit)
docker run -it --rm ubuntu:24.04 bash

# environment variables + a named volume + a memory cap
docker run -d --name api \
  -e DATABASE_URL=postgres://user:pass@db:5432/app \
  -v pgdata:/var/lib/postgresql/data \
  -m 512m \
  postgres:16-alpine

# a one-shot job that exits when done
docker run --rm busybox echo "hello from a container"
FlagMeaning
-dDetached: run in background
-itInteractive + pseudo-TTY: for shells
-p host:containerPublish a container port to the host
--nameGive it a stable name (easy logs/stop)
--rmDelete container automatically after stop
-e KEY=valueEnvironment variable
-v / --mountPersistent storage (Ch. 6)
-m / --cpusMemory / CPU limits
--networkWhich network (Ch. 7)
When run fails, the error message is the feature. "port is already allocated", "bind: address already in use", "no such image", "Dockerfile not found" — each maps to a fix in Ch. 11. Read the first line before guessing.

4.3 docker ps — what is running

docker ps                  # running containers only
docker ps -a               # including exited ones
docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}'   # table you actually want
# alive containers: name, image, command, ports, names

If a container isn't in ps -a, it either never existed or was --rm'd.

4.4 stop, start, restart

docker stop web            # SIGTERM, 10s grace, then SIGKILL
docker stop -t 30 web      # extend the grace period
docker start web           # restart a stopped container (same writable layer)
docker restart web         # stop then start
docker pause web           # freeze processes (SIGSTOP)
docker unpause web

4.5 rm — cleanup

docker rm web              # remove a stopped container
docker rm -f web           # force: SIGKILL then remove (running containers)
docker rm $(docker ps -aq)             # remove ALL containers
docker system prune -f                # dead containers + unused images + build cache
Prune danger: docker system prune -a also removes unused images and stopped containers everywhere on the host — fine on your laptop, surprising on a shared CI box.

4.6 exec, logs, inspect, stats

docker logs web            # stdout/stderr of the container
docker logs -f --tail 100 web
docker exec -it web bash   # shell inside the running container
docker exec web ps aux     # look, don't touch
docker inspect web         # full JSON: State, NetworkSettings, Mounts, ...
docker inspect -f '{{.State.Status}} {{.NetworkSettings.IPAddress}}' web
docker stats --no-stream   # live CPU/mem snapshot across containers
docker top web             # host-view process list

Use docker logs before docker exec: 90% of "why is it failing" answers are in the logs. docker inspect is the truth source for every runtime detail (mounts, network, health).

4.7 port, cp, diff, events

docker port web           # host:container mapping in use
docker cp web:/etc/nginx/nginx.conf ./my-nginx.conf   # copy OUT
docker cp ./index.html web:/usr/share/nginx/html/     # copy IN (dev-only)
docker diff web           # what the writable layer changed
docker events --filter container=web   # live stream of lifecycle events

4.8 Putting it together: the 30-second runbook

docker run -d --name api --rm -p 3000:3000 myapp:1.0.0   # run
docker ps                                   # confirm running
curl -sf http://localhost:3000/healthz     # smoke test
docker logs -f api                          # watch it live
docker exec -it api bash                    # poke inside
docker stop api                             # stop + auto-remove (--rm)
docker system prune -f                      # keep the box tidy

Summary

run (create+start+attach), ps (observe), stop/start/restart (control), rm/prune (clean), and logs/exec/inspect/stats (debug) cover the container lifecycle. Attach names to everything, use --rm for one-shots, and let error messages drive your diagnosis.

Checklist

  • ☐ I ran a detached container with a name, port map, and env var.
  • ☐ I started, stopped, restarted, and removed that container.
  • ☐ I streamed logs and exec'd into a container.
  • ☐ I used docker inspect -f '{{.State.Status}}' on a container.
  • ☐ I can clean up everything with docker system prune -f.
