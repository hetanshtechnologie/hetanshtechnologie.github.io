Best Practices: Image Optimization, Security, and Tagging

Anyone can make a container run; production teams make images that are small, secure, and traceable. This chapter is the pressure-test: tiny images, non-root process, scanned and signed content, and a tagging scheme that survives audits and rollbacks.

9.1 Image optimization

  1. Pick a small base: alpine (~5 MB), debian:*-slim, or distroless instead of full ubuntu. Small bases = faster pulls, smaller attack surface, less disk.
  2. Multi-stage builds (Ch. 5): compilers and dev deps never reach the runtime stage.
  3. Combine RUN steps and clean as you go: apt/npm caches and temp files die in the same layer they were created.
  4. Context discipline: .dockerignore keeps node_modules, .git, .env out of both the context and the image.
  5. Layer hygiene: dependency-claim order (Ch. 5.5) so rebuilds reuse layers; don't create layers that contain secrets (Ch. 9.2).
# minimal apache example: single logical RUN, cache cleaned inline
FROM debian:stable-slim
RUN apt-get update && \
    apt-get install -y --no-install-recommends apache2 && \
    apt-get autoremove -y && rm -rf /var/lib/apt/lists/*
COPY --chown=www-data:www-data html/ /var/www/html/
USER www-data
EXPOSE 80
CMD ["apache2ctl", "-DFOREGROUND"]

9.2 Security hardening

Run as non-root. The daemon's default is root; one USER instruction removes an entire class of host-escape problems:

RUN groupadd -r app && useradd -r -g app app   # or use the official "node"/"www-data"/"postgres" users
USER app

Secrets never in layers. An image layer is permanent and inspectable via docker history. Never ARG a secret or COPY a .env. Options:

  • BuildKit secret mounts: RUN --mount=type=secret,id=key ... with --secret id=key,src=./key at build time — the value never lands in a layer.
  • Runtime secrets: env files / vault / Docker secrets / k8s secrets (Ch. 8.4, 12).
# scan your images before they meet production
docker scout cves nginx:latest          # Docker Desktop's built-in scanner
trivy image --severity HIGH,CRITICAL myapp:1.0.0
# block on findings in CI (Ch. 12): trivy returns non-zero when HIGH/CRITICAL found

Pin base images by digest, and update deliberately: FROM node:20-alpine@sha256:abc.... Continuous rebuilds of latest silently change supply chain risk; scanning + renovate-style PRs keep you current on your schedule.

Don't hand the docker socket around: /var/run/docker.sock = root control of the host (Ch. 2 note). Never mount it into a container and never expose it to CI runners you don't fully trust.

9.3 Tagging strategy

SchemeExampleNotes
latestmyapp:latestMutable, ambiguous — dev convenience only
Semantic versionmyapp:1.4.2Release identity; the tag you deploy
Git commitmyapp:1.4.2-8f31ab6Traceability: which commit shipped
Environmentmyapp:stagingMutable pointer to the current env build — point it at a version, don't rebuild into it
Digestmyapp@sha256:…Immutable truth — what the pod actually runs

The workable policy: tag every CI build with <version>-<sha>, additionally tag promotions to stable version tags, deploy by digest, and let latest die a quiet death (or repoint it to the last stable build). For rollback you always know exactly what's on a node.

9.4 Runtime limits and health

docker run -d --name api --cpus 0.5 -m 512m --memory-swap 512m \
  --pids-limit 256 \
  --health-cmd "wget -qO- http://localhost/healthz || exit 1" \
  myapp:1.4.2-8f31ab6

Limits stop one container from starving a host (Ch. 10's Compose has the same knobs via deploy.resources on single-host, and k8s in Ch. 12). A healthcheck makes depends_on: condition: service_healthy (Ch. 8) and orchestrators' restarts actually meaningful.

9.5 The production go/no-go list

  • ☐ Image under ~100 MB (context-dependent, but the direction matters).
  • ☐ Runs as non-root (USER set).
  • ☐ No secrets in layers (docker history clean).
  • ☐ Base pinned by digest; scanner shows 0 HIGH/CRITICAL.
  • ☐ Tagged with version+sha; deploy by digest.
  • ☐ Has a healthcheck and resource limits.

Summary

Production-grade images are small (multi-stage, slim bases, clean layers), hard to compromise (non-root, scanned, no secrets, digest-pinned bases), and unambiguous (version+sha tags, digest deploys). Apply runtime limits and healthchecks on top, and every image from your pipeline hits the checklist before it ships.

Checklist

  • ☐ My main image uses a slim base and a multi-stage build.
  • ☐ No secret ever touches an image layer; I use BuildKit secret mounts.
  • ☐ I scanned an image and know my HIGH/CRITICAL count.
  • ☐ I pin bases by digest and tag releases as version+sha.
  • ☐ My containers run as non-root and have limits + a healthcheck.
