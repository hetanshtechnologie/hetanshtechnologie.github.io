Advanced Topics: Registries, CI/CD Integration, and Orchestration Basics

You can now build, run, and persist containers — the last three skills take what you built and make it team-scalable: pushing images to registries, building them automatically in CI, and letting an orchestrator run them across many machines.

12.1 Registries: where images live and move

A registry stores and serves images. Docker Hub is the public default; your own images should live in a private registry — GitHub Container Registry (GHCR), GitLab, ECR, ACR, GCR, or a self-hosted registry.

# login once (token as password)
docker login ghcr.io -u YOUR_GITHUB_USER -p $GITHUB_TOKEN

# tag so the name points at your registry, then push
docker tag myapp:1.0.0 ghcr.io/your-org/myapp:1.0.0
docker push ghcr.io/your-org/myapp:1.0.0

# digests again: what your orchestrator will actually pin
docker inspect ghcr.io/your-org/myapp:1.0.0 --format '{{index .RepoDigests 0}}'

Diagram (described in text): a horizontal flow — CI (left) builds and pushes → a central registry in the middle → on the right, three machines all `pull` the same image tag and run containers. The arrow from each machine back to the registry is labeled "pull with @digest".

Registry hygiene: set retention (delete stale tags), enable vulnerability scanning on private repos, use pull-through caching for shared bases, and treat registry credentials as secrets with minimal scope (read-only for deploy, write-only for CI).

12.2 CI/CD: build, scan, push, cache

CI should produce the exact image production will run — in this GitHub Actions workflow, notice the secure login, digest pinning, layer caching via cache-to, and the scan gate:

name: build-and-push
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/setup-buildx-action@v3
      - name: Build & push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ format('ghcr.io/me/app:{0}-{1}', github.ref_name, github.sha) }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
      - name: Scan the pushed image
        run: |
          docker run --rm aquasec/trivy image \
            --severity HIGH,CRITICAL --exit-code 1 \
            ghcr.io/me/app:${{ github.sha }}

Key production habits: tag with branch-sha (immutable trace back to a commit), use the type=gha cache so rebuilds reuse your layers (Ch. 5.5), and fail the pipeline on critical scan findings before anything deploys (Ch. 9.2).

12.3 Orchestration: from one host to many

Compose tells one host "run these N containers." Orchestrators tell a fleet "keep this many replicas healthy across these nodes, replace failed ones, route traffic, and upgrade without downtime."

ScopeSingle host, local/devMulti-node, simpleMulti-node, cloud-scale
Declarecompose filecompose file (swarm-aware)YAML manifests (Deployment, Service, Ingress...)
Self-healingrestart policies onlyYesYes (richest)

Swarm — Compose-like, multi-host (your climb step):

docker swarm init            # you are a manager node
docker network create -d overlay web
docker service create --name web --network web --publish 80:80 nginx:alpine
docker service scale web=3   # three replicas across the cluster
docker service ls && docker service ps web
docker service update --image nginx:1.27 web    # rolling update

Kubernetes — the industry standard: the same Flask image from Ch. 10 becomes a Deployment (desired state: 3 replicas of the image), a Service (stable DNS), and k8s reconciles reality to that state — the exact "Git is truth, controller enforces" model you met in Ch. 9 of the DevOps book. Orchestrators care about your image quality (Probes/limits/non-root) more than Compose ever did.

12.4 What makes an image "orchestrator-ready"

  • Stateless pods: data in volumes/object stores, not container disk (Ch. 6).
  • Graceful shutdown: catch SIGTERM, stop accepting work, drain in-flight (orchestrators send SIGTERM first, SIGKILL after grace).
  • Readiness + liveness probes in terms an orchestrator understands (Ch. 8 healthcheck pattern).
  • Resource requests/limits so the scheduler can pack correctly (Ch. 9 limits).
  • Non-root + pinned digests — CHAP 9 hardening is exactly what multi-tenant clusters demand.

Summary

Registries make images portable (tag for your registry, push, pin by digest); CI builds and scans them on every commit with layer caching and secure logins; orchestrators replace "run containers" with "keep this desired state alive across a fleet." Your Compose stack is now untethered from a single host — and your images are ready to serve at any scale.
