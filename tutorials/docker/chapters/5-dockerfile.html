Building Custom Images with Dockerfile

A Dockerfile is a recipe that describes your image, one instruction per line, each becoming a layer. You write it, then docker build turns it into an image. This chapter covers the instructions you need, the build context, .dockerignore, caching, and multi-stage builds — the technique that most shrinks real images.

5.1 Anatomy of a Dockerfile

FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY package*.json ./
RUN npm ci --omit=dev
EXPOSE 3000
USER node
CMD ["node", "dist/server.js"]

Diagram (described in text): the left column is the "build stage" — base with deps, install, compile — and the right column is the "runtime stage", a fresh minimal base receiving only the compiled output via COPY --from=build. The runtime stage is what ships.

5.2 The core instructions

InstructionWhat it does
FROM imageBase image (every image starts here; can appear multiple times for multi-stage)
WORKDIR /appSet working directory (creates it). Always use it — never rely on inherited dirs
COPY src dstCopy files from the build context into the image
ADD src dstLike COPY but auto-extracts tar and supports URLs — prefer COPY unless you need those
RUN cmdExecute a command at build time (install deps, compile)
ENV K=vSet environment variables baked into the image / container
ARG vBuild-time only variable (visible to RUN, not to the running container)
EXPOSE 3000Documentation only — records the port; does NOT publish it
USER nodeRun as non-root (do this in production images)
CMD ["app"]Default command, overridable at docker run
ENTRYPOINT ["app"]Fixed entrypoint; CMD args get appended to it

5.3 CMD vs ENTRYPOINT (the classic confusion)

# ENTRYPOINT is the binary; CMD is its default args.
# Docker run can replace CMD, but not ENTRYPOINT (without --entrypoint).
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
--> docker run mynginx                        # runs: nginx -g "daemon off;"
--> docker run mynginx -v                    # runs: nginx -v

For your own apps: put the app in ENTRYPOINT, its default options in CMD. That lets operators tweak flags without knowing your launch script.

5.4 Build context and .dockerignore

The build context is the folder you send to the daemon (docker build .). Everything in it is visible to COPY. Sending node_modules or .git makes builds slow and images polluted — filter them:

# .dockerignore
node_modules
.git
*.log
.env
dist

Diagram (described in text): your project folder on the left; the arrows into the daemon on the right showing only the allowed files passing the .dockerignore filter; the excluded heavy folders stop at the gate.

5.5 Layer caching — order is strategy

Each instruction that doesn't change reuses its cached layer. Pure strategy rules:

  1. Copy dependency manifests first (package*.json, requirements.txt), run the install, then copy source. Code changes never re-trigger dependency installs.
  2. Put rarely-changing steps (base, tools, deps) near the top; hot files (source) last.
  3. One logical RUN per concern, but avoid dozens of tiny layers that fragment caching.
docker build -t myapp:dev .
docker build --no-cache -t myapp:dev .      # when behavior drifts, rebuild fresh
docker build --cache-from ghcr.io/me/myapp:cache .   # CI reuse pattern

5.6 Multi-stage builds (the size killer)

Build toolchains (Go, gcc, node_modules for builds) are huge. Multi-stage lets you build in one stage and copy only the result into a slim runtime stage — your shipped image has no compilers, no dev deps.

# Go example: dev stage has the toolchain; runtime stage is bare
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /bin/app .

FROM gcr.io/distroless/static-debian12
COPY --from=build /bin/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

Result: a ~10 MB image instead of ~900 MB, no shell for attackers to find, and a static binary that runs anywhere — this pattern also shows up in Ch. 9 and 12.

5.7 Build the image and verify

docker build -t myapp:1.0.0 .
docker images | grep myapp
docker run --rm -p 3000:3000 myapp:1.0.0
docker history myapp:1.0.0     # see the layer list, size per layer
docker image inspect myapp:1.0.0 --format '{{.Config.User}}'   # expect non-empty user

Summary

A Dockerfile is an ordered recipe: pick a base, copy manifests before code for caching, compile/install, and copy only runnable output into a slim runtime stage. Use COPY not ADD, USER not root, ENTRYPOINT+CMD for your app, a .dockerignore, and multi-stage builds to keep images small and drama-free.

Checklist

  • ☐ I have a Dockerfile that uses FROM, WORKDIR, COPY, RUN, EXPOSE, USER, and CMD/ENTRYPOINT.
  • ☐ I have a .dockerignore excluding node_modules/.git/.env.
  • ☐ Dependency manifests are copied before source (caching works).
  • ☐ I ran a multi-stage build and saw the final image size drop.
  • ☐ I know when to use CMD vs ENTRYPOINT.
