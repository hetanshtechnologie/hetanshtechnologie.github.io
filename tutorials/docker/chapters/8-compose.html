Docker Compose: Multi-Container Applications

Running three containers with eleven flags each is how apps stop being reproducible. Docker Compose describes the whole stack — services, networks, volumes, env — in one docker-compose.yml, and one command brings it up and tears it down. It is the standard way to run multi-container apps locally and in small-to-medium CI.

8.1 Your first compose file (app + redis)

services:
  web:
    build: .
    ports:
      - "5000:5000"
    environment:
      REDIS_URL: redis://cache:6379
    depends_on:
      cache:
        condition: service_healthy
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  redisdata:

Diagram (described in text): a compose file box on the left spawning three lanes: the "web" service (builds from ., port 5000), the "cache" service (redis image with a healthcheck), and a named volume "redisdata" the cache writes into. A dotted arrow labeled "depends_on healthy" runs from web to cache.

Modern compose = no "version" key. Older tutorials put version: "3.8" at the top — current Compose warns about it; omit it. Also note the service name cache is usable as a hostname on the default compose network, exactly like Ch. 7's custom network.

8.2 The daily commands

docker compose up -d              # build + create + start everything, detached
docker compose ps                 # status per service
docker compose logs -f web        # tail one service's logs
docker compose exec web sh        # shell into a service
docker compose down               # stop + remove containers (keeps named volumes)
docker compose down -v            # ALSO delete volumes — data loss, use with care
docker compose config             # validate + pretty-print the resolved file
docker compose up -d --build      # rebuild changed services, keep the rest

Everything you did in Ch. 4 with docker run has a compose equivalent: restart, environment, volumes, ports, --network (top-level networks:), --rm (there's no Compose default; use profiles or run --rm). The win is that the file, not your memory, carries the flags.

8.3 Ordering and health checks

depends_on alone just starts a container first — it does not wait for it to be ready. The modern form couples it with a healthcheck, so a database that takes 20 seconds to accept connections doesn't make your app crash at startup:

services:
  web:
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: dev-password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 10
    volumes:
      - dbdata:/var/lib/postgresql/data

8.4 Environment and secrets handling

services:
  web:
    env_file:
      - .env            # plain KEY=value file (never commit!)
    environment:
      NODE_ENV: production
      # prefer env_file for secrets; inline "environment" for non-secret config

Compose automatically reads .env for variable substitution too: ports: ["${WEB_PORT:-5000}:5000"]. For real secrets in prod, Ch. 9's guidance applies — env files are a dev convenience, not a vault.

8.5 Networking in compose

services:
  api:
    networks: [api-net]
  db:
    networks: [api-net]
  public:
    image: nginx
    ports: ["80:80"]
    networks: [edge]     # db & api cannot see the public web service

networks:
  api-net:
  edge:

By default all services share one network (fine for most stacks). When you separate them, you get the boundary behavior from Ch. 7 — this is how a public proxy is boxed away from the database net.

8.6 Scaling and one-off jobs

docker compose up -d --scale worker=3     # 3 replicas of "worker"
docker compose run --rm web npm test      # one-off command in a service's image
docker compose ps --format '{{.Name}} {{.Status}}'

Compose scales by running N containers of a service — great for worker pools and load-testing. It is not an orchestrator (no self-healing across hosts); that's Ch. 12's job (Kubernetes/Swarm).

8.7 Profiles — services that only come up on demand

services:
  backup:
    image: postgres:16-alpine
    profiles: ["tools"]
    command: ["pg_dumpall"]                    # only started with --profile tools
# docker compose --profile tools run backup ...

Summary

Compose turns a multi-container stack into one declarative file and one command. Model every service with image:/build:, wire readiness with healthchecks + condition: service_healthy, isolate traffic with networks, and persist data with named volumes. For local/dev/CI, this file is your deployment.

Checklist

  • ☐ I wrote a compose file with at least two services, a healthcheck, and a named volume.
  • ☐ I can run, log, exec, validate, and tear down with the five daily commands.
  • ☐ My app waits for db readiness, not just db startup.
  • ☐ I know what down -v destroys.
  • ☐ I separated networks where isolation matters.
