Images and Containers

Everything in Docker is built on one idea: images are immutable templates; containers are their running, read-write instances. This chapter makes that relationship — and the layer system underneath it — concrete, because every later chapter (Dockerfiles, volumes, networks, Compose) builds on it.

3.1 The image is a stack of layers

An image is not one blob of files. It is an ordered stack of layers, each layer being the diff between one build step and the previous. When the engine runs a container from an image, it stacks the layers in order, then adds a thin read-write layer on top for the running process.

Diagram (described in text): a vertical stack — bottom layer "base OS (ubuntu)" on top of it "add curl" above that "copy app code" and finally the white top layer labeled "container writable layer". Separate small diagram beside it: two containers sharing the same bottom three layers but each with its own writable top layer.

3.2 Why layers matter (three consequences)

  • Shared storage: ten containers from the same image all share the base layers; only the writable layer is per-container. That's why hundreds of containers fit on one host.
  • Speed: docker pull downloads only layers you don't already have. If another image uses the same ubuntu base, those bytes are reused.
  • Build caching: when you rebuild, unchanged steps reuse cached layers (Ch. 5). Layer order in a Dockerfile is therefore a design decision, not trivia.

3.3 Names, tags, and digests

registry/repository:tag
# registered name form: ghcr.io/n8n-io/n8n:1.2.3
# Docker Hub prefix "docker.io/library/" is implied:
ubuntu:24.04          # == docker.io/library/ubuntu:24.04
nginx                                        # == nginx:latest (default tag)
postgres@sha256:abcd1234...                  # immutable digest — the true identity

A tag is a mutable nickname for an image; a digest is the cryptographic fingerprint of the image content. Production systems pin by digest (Ch. 9) so "latest moved under me" can never happen silently.

3.4 The image catalog: local and registry

docker pull nginx:alpine        # fetch from the registry (Docker Hub by default)
docker images                   # images stored on this host (REPOSITORY, TAG, IMAGE ID, SIZE)
docker image inspect nginx:alpine
docker rmi nginx:alpine         # remove image (fails if a container uses it)
docker rmi nginx:alpine --force # you almost never want --force
Image ID vs image name: the IMAGE ID (e.g. 1fa43dd296d2) is derived from the top layer's digest. Two tags pointing at the same content share one ID. Commands accept the ID or a unique prefix of it.

3.5 from image to container: the run-time layers

When you run a container, the engine adds the writable layer and starts your process (CMD/ENTRYPOINT, Ch. 5). The container gets:

  • its own filesystem (base layers + writable layer),
  • its own network namespace (Ch. 7),
  • its own process namespace — PID 1 is your app, not a shell,
  • resource limits if you request them (CPU/memory flags).
docker run -dit --name box ubuntu:24.04 bash      # interactive, detached
docker exec box whoami                             # your process, inside the namespace
docker exec box cat /etc/os-release | head -1      # same Ubuntu, isolated view
docker stop box && docker rm box

Diagram (described in text): a container as a fenced area. Outside the fence: host kernel, host processes, host network. Inside the fence: your app (PID 1), its private filesystem, its private network interface, and its resource quota.

3.6 Containers end; images remain

The single most important behavioral rule: stopping or deleting a container never touches the image, and deleting a container throws away its writable layer — unless data sits in a volume (Ch. 6).

ActionImageContainer writable layerVolumes
docker stopUnchangedKeptKept
docker rmUnchangedDeletedKept (unless -v)
docker rmiDeleted (if unused)n/aKept

3.7 Register your own image names early

From Ch. 5 onward you will build images. Get the naming habit now — the name you build under is what you push to a registry:

docker build -t my-app:1.0.0 .
docker tag my-app:1.0.0 ghcr.io/my-org/my-app:1.0.0     # later, push under your registry

Summary

Images are immutable, layered templates; containers add a throwaway writable layer and a process namespace on top. Layers give you shared storage, fast pulls, and build caching. Tags are mutable nicknames, digests are the identity, and deleting a container never touches its image or volumes.

Checklist

  • ☐ I can draw the layer stack (base → deps → code → writable).
  • ☐ I can run exec into a container and explain which namespace I entered.
  • ☐ I know the difference between tag and digest, and when to use a digest.
  • ☐ I can explain why docker rm loses container data but not volume data.
  • ☐ I named and tagged a first image (docker tag).
