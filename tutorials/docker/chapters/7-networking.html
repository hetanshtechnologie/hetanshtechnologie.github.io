Networking in Docker

Every container has its own network namespace: its own IP, its own loopback, its own port space. Docker networks are the bridges and walls between containers — who can talk to whom, and how traffic reaches the outside world. Three network types will cover almost everything you do: bridge (default), host, and overlay (multi-host).

7.1 The three network drivers

DriverScopeDefault?Use for
bridgeSingle hostYes (per-run)Most apps: NAT'd internal net + published ports
hostSingle hostNoPerformance-sensitive processes that must bind host ports directly
overlayMulti-host (swarm)NoServices spanning a swarm cluster
noneIsolatedNoOffline jobs, strict isolation testing

Diagram (described in text): one host machine showing three networks. "Bridge net A" contains containers web1 and api1 talking to each other by name; "Bridge net B" contains worker1 alone; "host net" shows a container binding directly to the host's port 80; and an "overlay" box spans two hosts with a service reachable on both.

7.2 Bridge networking and published ports

# container gets its own private IP (172.17.x.x by default on the default bridge)
docker run -d --name web -p 8080:80 nginx
docker inspect -f '{{.NetworkSettings.IPAddress}}' web    # 172.17.0.2
curl http://localhost:8080     # host -p 8080 -> container 80

The container's private IP is only reachable inside the host. -p 8080:80 creates the published port rule: anything hitting the host's 8080 is forwarded to the container's 80. Without -p (or up to Docker Cloud -P pushing all EXPOSEd ports), nothing on your laptop can reach the container.

-p vs EXPOSE: EXPOSE in a Dockerfile is documentation (Ch. 5). Only -p/-P at run time — or their Compose equivalent — publishes traffic. Teams that forget are the ones who "can't connect" (Ch. 11, issue #3).

7.3 Container-to-container: use the network, not IPs

The default bridge gives you connectivity but no name resolution between containers (only by legacy --link). Create a custom bridge and Docker gives every container a DNS alias for free:

docker network create app-net
docker run -d --name api --network app-net myapp
docker run -d --name db  --network app-net -e POSTGRES_PASSWORD=secret postgres:16-alpine
# the app connects to "db" — not an IP — because they share app-net:
docker exec api getent hosts db          # resolves to db's IP on app-net
docker network inspect app-net           # see members + IPs

Diagram (described in text): a custom bridge network as a horizontal bus; api and db each have an interface plugged into it and can address each other by name; nginx on the default "bridge" network is drawn off to the side, unable to see them.

Shared but isolated: containers on the SAME network reach each other freely; containers on DIFFERENT networks cannot reach each other at all (unless published via the host). Design network membership as a security boundary, not an afterthought.

7.4 Host networking — bind directly

docker run -d --network host myapp        # no -p; app binds host:3000 directly
curl http://localhost:3000
# Pros: near-zero overhead, port is real. Cons: no port mapping, no isolation,
# and two host-network containers can't both bind 3000.

Use host networking for local perf-sensitive things (some proxies, benchmarks). In Compose/Kubernetes it's the exception, not the rule.

7.5 Overlay networking (multi-host)

Overlay lets service name = network location across many machines. It's the network of Docker Swarm mode and the basis of "the same Compose stack, spread across a cluster":

docker swarm init
docker network create -d overlay --attachable my-overlay
docker service create --name web --network my-overlay -p 80:80 nginx
docker service ls     # replicated across hosts, all reachable via "web"

You'll revisit this in Ch. 12 with orchestration; for a single machine today, "bridge + custom network" is your entire inner loop.

7.6 Managing networks

docker network ls                     # list (bridge, host, none are built-ins)
docker network create -d bridge mynet --subnet 172.20.0.0/16   # carve your own range
docker network connect mynet other    # attach a running container to another net
docker network disconnect mynet other
docker rm mynet                       # fails if containers are attached

7.7 DNS and the outside world

  • Outbound: containers NAT through the host by default — internet works out of the box.
  • DNS inside: /etc/resolv.conf is managed by Docker; on non-default networks use --dns 1.1.1.1 if a vpn/company DNS fails inside.
  • Hostname/IP stability: rely on names + DNS, never hard-coded container IPs (they change on recreate).

Summary

Containers live on isolated networks. Bridge (default, per-run) gives NAT + published ports; a custom bridge adds automatic DNS so services reach each other by name — your default for multi-container apps; host gives direct binds; overlay spans swarm nodes. Publish with -p, resolve by name, and treat network membership as a security boundary.

Checklist

  • ☐ I published a port (-p) and reached the container from the host.
  • ☐ I created a custom network and connected two containers to it.
  • ☐ I confirmed containers resolve each other by name on the same network.
  • ☐ I know when host vs bridge is the right call.
  • ☐ I inspected the network to see its members.
