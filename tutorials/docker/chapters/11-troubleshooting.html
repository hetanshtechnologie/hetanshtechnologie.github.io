Troubleshooting Common Issues

Containers fail in remarkably predictable ways. This chapter is a symptom → diagnosis → fix playbook for the failures you are most likely to meet, plus the diagnosis loop that handles everything else. Rule #1: read the actual error before changing anything. Rule #2: docker logs beats guessing, always.

11.1 The diagnosis loop

1. docker ps -a            # is it running? exited? restarting?
2. inspect state: docker inspect --format '{{json .State}}' <name>
3. docker logs --tail 50   # the app's own voice (the 90% answer)
4. docker events           # live lifecycle events while you reproduce
5. narrow by layer: daemon vs image vs app vs network vs storage
6. apply cheapest fix, verify with data, then retro: why was it possible?

11.2 Symptom: "port is already allocated" / "address already in use"

Something already owns the host port you asked to publish.

docker ps -a                 # another container mapped that port?
netstat -ano | grep 8080     # host process on 8080 (Windows: netstat -ano | findstr 8080)
# fix: pick a different host port, or free the port
docker run -d -p 8081:80 nginx

11.3 Symptom: image issues — "manifest unknown", pull denied, pull hangs

  • "manifest unknown" / "not found": the tag doesn't exist — check the spelling; latest may be omitted where a version is expected.
  • "pull access denied": either the image doesn't exist, or it's private — add credentials with docker login / docker login ghcr.io -u ... -p $TOKEN.
  • hang / slow: a registry or proxy issue; try docker pull --platform linux/amd64 to rule out platform confusion, or retry after network check.
docker pull nginx:alpine          # sanity: a registry round-trip
docker search "official nginx"    # confirm names exist

11.4 Symptom: container starts then exits immediately ("status Exited (1)")

A container exits when its PID 1 process finishes or crashes. The cause is almost always in the logs, or one of:

  • No long-running process: a base image like ubuntu has no service to keep running — the container exits instantly. Fix: run a foreground process (CMD ["nginx", "-g", "daemon off;"] or your app).
  • App crashed: missing env, bad config, dependency burned a compile step. docker run -it --rm myapp (foreground) shows the trace directly.
  • OOMKilled: docker inspect --format '{{.State.OOMKilled}}' <name> → true means raise the memory limit or fix the leak.
docker logs --tail 50 <name>      # first move
docker run -it --rm myapp         # foreground + tty: you SEE the crash
docker inspect --format '{{.State.ExitCode}} {{.State.Error}}' <name>

11.5 Symptom: can't connect to a service ("connection refused", timeout)

Check which side of the story is true: host→container, container→container, or container→internet.

# host -> container: did you publish? is the app listening on 0.0.0.0?
docker ps                    # look at the PORTS column — 0.0.0.0:8080->80/tcp? 
curl http://localhost:8080
docker exec <name> curl -s http://localhost:80   # is the app alive INSIDE?

# container -> container: same network? DNS-resolvable name?
docker network inspect <net>         # members and IPs
docker exec api getent hosts db      # resolves?

# container -> internet: NAT through host — what fails?
docker run --rm busybox wget -qO- https://www.google.com
"Connection refused" almost never means "firewall blocked". It means "nothing is listening at that address:port." Firewalls and networks typically cause timeouts instead. Listen for that word, it directs you: refused → the app/port/publish layer; timeout → the network layer.

11.6 Symptom: "permission denied" on the Docker socket

# error: Get "http://unix/.../docker.sock": dial unix ... permission denied
sudo usermod -aG docker $USER   # then LOG OUT and back in
sudo systemctl restart docker   # also restarts the daemon cleanly

11.7 Symptom: "no space left on device" (Windows WSL2 edition)

Docker's data lives in the WSL2 VHD which grows but rarely shrinks. Since you can't just delete AppData files:

# inside WSL2: reclaim disk after pruning
docker system prune -a --volumes        # reclaim what you can (!! deletes un-backuped data)
wsl --shutdown                          # PowerShell, releases the VHD for compaction
# then compact via `optimize-vhd -Path docker-desktop-data.vhdx -Mode Full` (admin)
# longer-term: docker desktop settings can `Disk image size` cap; use .dockerignore

11.8 Symptom: exec format error / wrong platform arch

"exec format error" = the binary's CPU architecture doesn't match the runtime (e.g., built on Apple Silicon, run on amd64).

docker build --platform linux/amd64 -t myapp .
docker run --platform linux/arm64 myapp
# or push multi-arch: docker buildx build --platform linux/amd64,linux/arm64 -t me/app --push .

11.9 Symptom: volume/file permission mismatch (UID wars)

Biggest surprise on Linux: the container's user (e.g. UID 999 for postgres, 33 for www-data) can't write to a directory owned by your host user.

docker run -d --user "$(id -u):$(id -g)" -v "$(pwd)/data:/data" myapp
# or in Compose: user: "1000:1000", or chown the dir in the image
docker compose exec db ls -la /var/lib/postgresql/data   # observe ownership

11.10 Symptom: Compose says "no such service" / "service depends on undefined service"

  • Missing services: indentation — the #1 YAML mistake (use docker compose config to validate).
  • A depends_on naming a service that isn't defined in this file (works in docker compose ... --profile footguns).
  • Different Compose versions: plugin vs 1.x standalone (docker compose vs docker-compose); the plugin is current.

Summary

Most failures live in nine buckets: port conflicts, image pulls, instant-exit, connectivity, socket permissions, disk, architecture, permissions, and compose/YAML. Each has one defining diagnostic (logs, PORTS column, OOMKilled flag, getent, config). Follow the loop, read the error, and let the layer that speaks first point you to the fix.

Checklist

  • ☐ I ran docker logs before changing anything at least once today.
  • ☐ I can debug a "can't connect" between four layers (host, app-internal, cross-container, internet).
  • ☐ I can explain why "connection refused" ≠ firewall.
  • ☐ I know the OOMKilled check and the exec format + platform fix.
  • ☐ I validated a compose file with docker compose config.
