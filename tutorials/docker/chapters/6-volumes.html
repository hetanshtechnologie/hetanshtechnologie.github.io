Volumes and Persistent Storage

Remember the rule from Ch. 3: docker rm deletes the container's writable layer — including your database writes, uploaded files, or logs stored in it. Volumes are storage that survives the container. If your container writes anything you don't want to lose, put that path on a named volume.

6.1 The three storage options

OptionWhere data livesUse for
Named volumeManaged by Docker (/var/lib/docker/volumes/<name>)Databases and app state — your default
Bind mountA path you choose on the hostConfig files, dev code, watching host tools
tmpfs mountRAM, in-memory onlyScratch/temporary, secrets you never want on disk

Diagram (described in text): a container on the left with three arrows to the right: one down into "Docker's volume area" (named volume), one across into a literal host directory like /home/you/app (bind mount), and one up into "RAM" (tmpfs). The container's lifecycle (oval) flows around all three without touching them.

6.2 Named volumes — the default choice

# create + attach a named volume in one run line
docker run -d --name pg -v pgdata:/var/lib/postgresql/data postgres:16-alpine

docker volume ls                 # you see "pgdata"
docker volume inspect pgdata     # where it lives + mountpoint
docker run -it --rm -v pgdata:/data alpine sh -c 'echo persisted > /data/note.txt'
docker rm -f pg                  # delete container — volume survives
docker run --rm -v pgdata:/data alpine cat /data/note.txt   # still there

Named volumes are portable, shareable between containers, and backup-able. Prefer them whenever a service needs its own data — most database images even declare the volume for you.

6.3 Bind mounts — host paths, dev speed

# live-code mount: edit on the host, container sees it instantly
docker run -d --name dev -v "$(pwd)/src:/app/src" -p 3000:3000 myapp:dev

# read-only bind for configs (container can't edit its own config)
docker run -d --name conf -v ./nginx.conf:/etc/nginx/nginx.conf:ro nginx
Bind mount gotchas: (1) On Windows, paths become C:\path and the parser is picky — prefer $(pwd) or relative paths. (2) A bind mount hides everything already in the container at that path — mounting an empty host dir over /app hides your image's /app. (3) Check file permissions: UID/GID mismatch on Linux is the #1 surprise; fix with :ro, --user, or chown in the image.

6.4 tmpfs — memory-backed scratch

docker run -d --tmpfs /tmp:rw,noexec,nosuid,size=64m myapp
# fast, ephemeral, gone with the container — ideal for caches/sockets, never for data

6.5 Sharing data between containers

# two containers, one named volume, mounted at different paths
docker run -d --name writer -v shared:/data alpine sh -c 'while true; do echo tick >> /data/log.txt; sleep 5; done'
docker run -it --rm -v shared:/read alpine cat /read/log.txt
docker rm -f writer

This is how a metrics scraper shares a scratch directory with a worker, or how an app shares uploads with a thumbnailer — without either knowing the other's filesystem details.

6.6 Backup and restore

# backup: mount both the source volume and a host target dir
docker run --rm -v pgdata:/data:ro -v "$(pwd):/backup" alpine \
  tar czf /backup/pgdata-$(date +%F).tar.gz -C /data .

# restore into a fresh volume
docker volume create pgdata_restored
docker run --rm -v pgdata_restored:/data -v "$(pwd):/backup" alpine \
  tar xzf /backup/pgdata-$(date +%F).tar.gz -C /data

For real databases, prefer the vendor tool (pg_dump, mongodump) over raw file copies — but the pattern above is fine for file stores and shows the essential trick: a throwaway helper container with both mounts.

6.7 Cleanup discipline

docker volume ls -f dangling=true     # volumes nobody references
docker volume prune                   # delete the orphans (check first!)
docker rm -v mycontainer              # remove container AND its anonymous volumes
Anonymous vs named: -v /data (no name) creates an anonymous volume — auto-removed with --rm, orphaned otherwise. Always name volumes for anything you care about.

Summary

Containers are ephemeral by design, so anything you must keep goes on a volume: named volumes for app/database state (default), bind mounts for host configs and live dev, tmpfs for throwaway speed. Back up with a helper container (or the DB's own tool), prune orphans, and always give real data a named volume.

Checklist

  • ☐ I created a named volume and proved data survives docker rm -f.
  • ☐ I used a bind mount for live code and a :ro mount for config.
  • ☐ I moved data between two containers via a shared volume.
  • ☐ I backed up and restored a volume with a helper container.
  • ☐ I understand that tmpfs is memory-only, not persistence.
