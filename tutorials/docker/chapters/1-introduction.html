Introduction to Docker

Docker packages an application together with everything it needs to run — code, runtime, libraries, and configuration — into a single artifact called a container image. You build the image once, then run identical containers on any machine that has Docker installed. It is the closest thing software has to "it works on every machine, in the same way."

1.1 The problem Docker solves

Before containers, every deploy story sounded like this:

  • "It works on my machine" — different OS, different library versions, missing dependencies.
  • Teams keep a fat, hand-edited "deployment checklist" for each environment; anything untested breaks.
  • Virtual machines give isolation but waste resources: each VM carries its own full OS (gigabytes) and boots slowly.
  • Scaling means copying whole servers, not fine-grained application instances.

The container answer: package the app and its environment into one immutable unit, run many of them cheaply on one host, start/stop them in seconds, and get the same behavior everywhere.

1.2 Containers vs. virtual machines

Virtual machineContainer
Isolation boundaryVirtualized hardware (hypervisor)OS-level namespaces + cgroups
Guest OSFull separate OS per VMShares the host kernel
SizeGigabytesMegabytes
Boot timeMinutesMilliseconds to seconds
Density on one hostTens at bestHundreds+
Security boundaryStrong (hardware)Good if configured (see Ch. 9)

Diagram (described in text): a single host with one hypervisor hosting three VMs, each with its own full OS kernel, libraries, and app. Beside it, the same host running a single host kernel with three containers, each holding just the app + libraries, all sharing that kernel.

The trade-off to remember: containers share the host kernel, so a Linux container needs a Docker setup that can host Linux containers (native Linux, or Windows/macOS via a Linux VM — which Docker Desktop provides). You cannot run a Windows-only library inside a Linux container.

1.3 What the Docker platform includes

  • The Engine (daemon): the background service (dockerd) that builds, runs, and manages containers.
  • The client: the docker CLI you type commands into; it talks to the daemon over a socket/API.
  • Images and containers: images are the templates; containers are running instances (covered in Ch. 3).
  • Registries: servers that store and share images — Docker Hub by default, plus private registries and GitHub Container Registry (Ch. 12).
  • Docker Compose: defines and runs multi-container apps from a YAML file (Ch. 8).
  • BuildX / BuildKit: the modern builder for efficient, parallel image builds (Ch. 5).

1.4 The mental model (read this twice)

An image is immutable — think of it as a frozen, versioned snapshot of your app and its environment. A container is the image running as a live, isolated process with its own tiny file system. You can run many containers from one image, each independent. When a container is deleted, its changes are gone unless you saved them to a volume (Ch. 6). That "throwaway by design" property is exactly what makes containers reproducible.

# The first two commands of this entire tutorial (after install):
docker run -d --name demo -p 8080:80 nginx
# downloads nginx image, starts a container named "demo",
# maps host port 8080 to container port 80
open http://localhost:8080     # you are serving nginx from a container

1.5 When to use Docker (and when not to)

Use it for: web services, worker jobs, databases in development, delivering consistent dev/staging/prod environments, CI runners, and bundling CLI tools that need specific dependencies.

Think twice before: desktop GUI apps you must ship to non-technical users (native packaging still wins), CPU-native performance-critical HPC code (kernel sharing has small overheads), or Windows-only software on Linux hosts.

1.6 Hands-on quick win (once Docker is installed)

docker version            # client + server versions (server side = the daemon OK)
docker run hello-world    # official smoke test image
docker ps                 # list running containers (empty now: hello-world exits fast)
docker ps -a              # include exited containers; hello-world is still there
docker rm hello-world     # delete the container record

That's the whole loop of container dev life: pull → run → observe → remove. The rest of this tutorial makes every step precise, production-safe, and deliberate.

Summary

Docker packages an application with its environment into an immutable image, and runs that image as isolated containers on a shared kernel. It removes "works on my machine," radically reduces overhead compared to VMs, and gives you one artifact that behaves identically everywhere. The platform is engine + client + images + registries + Compose + BuildKit.
