Containerization: Docker Fundamentals

A container is an isolated process (not a full OS) that bundles your application with its runtime, libraries, and configuration. Because the filesystem is layered and the runtime is shared with the host kernel, containers start in milliseconds and use a fraction of a VM's memory. Docker is the tooling that makes containers approachable; this chapter covers images, Dockerfiles, registries, and the security foot-guns every engineer steps on.

4.1 Images vs containers vs registries

ConceptAnalogyReality
ImageA class / recipe / snapshotImmutable filesystem layers + metadata
ContainerAn instance / a cake bakedA running image with an isolated process tree, network, and mounts
RegistryA package storeStores and distributes images (Docker Hub, GHCR, ECR, ACR, GCR)

4.2 Anatomy of a good Dockerfile

# ---- builder stage: compile the app ----
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                      # install deps exactly (lockfile)
COPY . .
RUN npm run build               # produces dist/

# ---- runtime stage: small, non-root, only artifacts ----
FROM node:20-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build /app/package*.json ./
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
RUN addgroup -S appgroup && adduser -S appuser -G appgroup   # (busybox adduser)
USER appuser
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
CMD ["node", "dist/server.js"]

This Dockerfile encodes five rules: multi-stage build (builder stays fat, runtime stays tiny), pin base images, copy artifacts not sources, run as a non-root user, and declare a health check. Together they make images small (~50 MB vs ~1 GB), secure, and observable.

4.3 Building, tagging, scanning, and pushing

docker build -t myapp:1.2.3 .
docker build --no-cache -t myapp:1.2.3 .            # forced rebuild (suspicious cache)
docker scout cves myapp:1.2.3                       # or: trivy image myapp:1.2.3
docker tag myapp:1.2.3 ghcr.io/team/myapp:1.2.3
docker login ghcr.io
docker push ghcr.io/team/myapp:1.2.3
docker run --rm -p 3000:3000 -e LOG_LEVEL=debug ghcr.io/team/myapp:1.2.3

Diagram (described in text): build pipeline feeding a registry. A Dockerfile is compiled into layers; each layer is a diff. The registry serves these layers to any machine that runs docker pull. Because layers are cached and shared, pushing and pulling transmit only changed layers — that is why distroless and alpine images move so fast.

4.4 Running containers properly

docker container run -d --name api \
  -p 8000:8000 --restart unless-stopped \
  -v api-data:/var/lib/app        \
  --read-only                     \
  --cap-drop ALL                  \
  --memory 512m --cpus 1          \
  ghcr.io/team/api:1.2.3
  • -d detach, --name name, -p publish ports.
  • -v name:/path named volume (survives container restarts).
  • --restart unless-stopped basic self-healing on a single host.
  • --read-only + --cap-drop ALL hardening, not paranoia.
  • --memory/--cpus resource limits (the kernel enforces them).
docker ps -a
docker logs --tail=50 -f api
docker exec -it api sh
docker inspect api | jq '.[0].State'
docker stats                     # live CPU/mem of all containers
docker system prune -f           # reclaim disk (be careful in prod)
Container facts beginners misremember: containers are not lightweight VMs (no independent kernel, no systemd, no SSH server by default). They are also not a security boundary by themselves — container isolation assumes kernel hardening, so in production treat containers as untrusted-ish and enforce seccomp/AppArmor, resource limits, and no privileged mode. And never docker exec -it --privileged anything you do not intend to give root on the host to.

4.5 Multi-service apps with Docker Compose

Compose is the single-machine orchestrator: one YAML = one environment stack, perfect for local dev, staging, and lab environments.

# docker-compose.yml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}      # from .env, never committed
    volumes: [ "dbdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
    environment:
      DATABASE_URL: postgres://postgres:${DB_PASSWORD}@db:5432/postgres
    ports: [ "8000:8000" ]
volumes:
  dbdata:
docker compose up -d --build
docker compose ps
docker compose logs -f api
docker compose down              # teardown (add -v only to destroy volumes!)

4.6 Registry and image management best practices

  • Tag immutable-ly: myapp:1.2.3 and myapp:<sha> are good; myapp:latest as the only tag is a time bomb. Never redeploy from latest.
  • Scan before push (CI): Trivy, Grype, or Snyk gate on fixable CVEs; block critical/high on the image path to prod.
  • Sign images: cosign sign (+ SBOM via syft) lets your runtime and supply-chain policy verify provenance. See Chapter 8.
  • Private registry + pull-through caching to cut egress and avoid rate limits at scale.
  • Retention policies: keep N months of images, auto-prune untagged; registries are the #1 silent storage consumer.
  • Distroless/scratch for production: fewer binaries = smaller attack surface = fewer CVEs.

4.7 Cost optimization quick wins

  • docker system df weekly; prune dangling build cache in CI agents.
  • Use --mount=type=cache (BuildKit) for package caches across builds.
  • Share base layers: one org base image per runtime saves multiplatform layer pull time.
  • Right-size agents: most "slow CI" is bloated images plus cold caches, not weak CPUs.

Summary

Docker turns applications into immutable, versionable artifacts via layered images. The craft is in the Dockerfile (multi-stage, non-root, small, healthy), the discipline is in the pipeline (scan, sign, immutable tags), and the security contract is understanding that a container isolates a process — not a host.

Checklist

  • ☐ My Dockerfile uses multi-stage builds and a minimal runtime image.
  • ☐ My container runs as a non-root user with dropped capabilities.
  • ☐ Images are scanned in CI and signed with cosign before deployment.
  • ☐ Tags are immutable (version + SHA-based), never only latest.
  • ☐ Secrets come from env/config at runtime, never baked into the image.
