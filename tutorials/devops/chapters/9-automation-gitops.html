Automation Strategies & GitOps

Automation is the raw material of DevOps; GitOps is the operating system for automation — using Git as the single source of truth and a controller that continuously enforces it. This chapter moves you from "scripts that someone runs" to "systems that reconcile themselves."

9.1 The automation ladder

1. Manual clicks        (under review — kill these)
2. Scripts              (bash/PowerShell on a schedule or trigger)
3. Task runners         (Makefile, Taskfile, npm scripts, rake)
4. CI/CD pipelines      (GitHub Actions, Jenkins — event-driven)
5. GitOps controllers   (Argo CD/Flux reconcile the cluster to Git)
6. Self-driving ops     (auto-remediation, auto-scaling, AI-assisted — ch. 13)

Rule: each rung makes the previous one reviewable, reproducible, and versioned. The goal is not "no humans" — it is "no humans doing steps the machine can verify."

9.2 Scripting discipline (bash + PowerShell)

Patterns that separate "useful scripts" from "Monday's 3 a.m. call": exit codes, set-safe flags, logging, and tested failure paths.

#!/usr/bin/env bash
# deploy.sh — run from CI, not from a laptop
set -euo pipefail                 # exit on error, unset var, pipeline failure
trap 'echo "FAILED at line $LINENO"' ERR
log() { echo "[$(date -Iseconds)] $*"; }

IMAGE="$1"; [ -n "$IMAGE" ] || { echo "usage: deploy.sh <image-tag>"; exit 1; }

log "rolling out $IMAGE"
kubectl -n production set image deploy api api="$IMAGE"
kubectl -n production rollout status deploy api --timeout=180s
log "smoke: ${HEALTH_URL}"
curl -fsS --retry 5 --retry-all-errors "${HEALTH_URL}/healthz"
# cleanup.ps1 — Windows/on-prem equivalent discipline
$ErrorActionPreference = "Stop"
param([Parameter(Mandatory)] [string]$EnvName)
Get-AzResourceGroup -Name "rg-$EnvName" -ErrorAction SilentlyContinue |
    ForEach-Object {
        Write-Host "Deleting $($_.ResourceGroupName)..."
        Remove-AzResourceGroup -Name $_.ResourceGroupName -Force
    }
  • Bash: set -euo pipefail; PowerShell: $ErrorActionPreference = "Stop". Non-negotiable defaults.
  • Take the minimal secrets: a script that pulls deploy creds from a vault and never stores them beats one with a key in the file.
  • Scripts are great for packaging (Makefile/Taskfile wrap long commands). They are not great where state or confidentiality matters — that is pipeline/controller territory.
Makefile pattern: `make check` = fmt + lint + tests; `make package` = build/test artifact; `make deploy-env` calls the pipeline. You get a single entrypoint for humans and the same commands are what CI runs — one less copy-paste divergence.

9.3 Pipelines as automation: event-driven everything

Prefer event triggers over schedules where possible: on: push, workflow_dispatch, webhooks, and ChatOps commands are all events. Scheduled jobs are the exception (nightly prod-database snapshot, security scans). A small but complete automation catalog for a platform team:

9.4 GitOps: the cluster syncs itself to Git

Classic deploy = a human/CI runs kubectl apply. GitOps = a controller in the cluster watches a Git repo (manifests/) and reconciles: if the repo changes, the cluster converges to it; if someone sneaks in a kubectl edit, drift is detected and reverted. Your manifests become the only truth.

# Argo CD Application — "this app lives in this repo path, auto-sync"
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: api, namespace: argocd }
spec:
  project: production
  source:
    repoURL: https://github.com/team/manifests
    path: apps/api/overlays/production
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true        # delete resources removed from Git
      selfHeal: true     # revert drift to Git
    syncOptions:
    - CreateNamespace=true
# Flux (the lighter alternative) — kustomize-based
# kustomization.yml + source kustomization with `kubectl apply -k`-style ingresses

Why teams standardize on GitOps (evidence-based, not fashion):

  • Audit trail: every cluster change is a commit with an author, a message, and a diff.
  • Rollback = revert a commit (or argocd app rollback to a synced revision), not "what did I delete?".
  • Review = PR before merge: the exact same review discipline as code, including policies (Chapter 8).
  • Multi-cluster: one repo + one controller per cluster = identical environments by construction.
GitOps trap: "we put YAML in a repo and still apply by hand." The controller must own sync. If your workflow is "hey run this file" instead of commit-and-wait, you have a repository, not GitOps. Discipline: write access to prod manifests ✕ anyone's laptop = zero.

9.5 Making automation measurable

Automation without telemetry is wishful thinking. Track per automation: how often does it run, how often does it fail, how much human time does it save, and what's its MTTR impact? Ship a dashboard (per Chapter 6) for "automation coverage": jobs split by trigger type, failure rate per job, and seconds from commit to green. That dashboard becomes the weekly ops review.

Summary

Automation moves up a ladder from scripts to self-reconciling controllers; GitOps is the top rung where Git is the truth and a controller enforces it. Script everywhere, trigger by events, and let the cluster pull its own state — then measure each automaton so you can tell value from busy-work.

Checklist

  • ☐ All deploy/cleanup scripts use strict error handling and vault-injected secrets.
  • ☐ Manual "click in console" steps are catalogued and being replaced in priority order.
  • ☐ Cluster manifests live in Git; Argo CD/Flux owns sync (selfHeal + prune on).
  • ☐ No human has write-execute on prod besides the controller path.
  • ☐ Automation coverage has a measurable dashboard (runs, failures, time saved).
