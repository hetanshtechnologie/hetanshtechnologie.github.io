Monitoring & Logging: Prometheus, Grafana, and the ELK Stack

Monitoring answers "is it up, and how healthy?" — metrics and alerts. Logging answers "what actually happened?" — granular, searchable records. They are different data types, different pipelines, and different tools; conflating them ("we have logs, so we're covered") is the most common observability failure. Real teams do both plus tracing (OpenTelemetry) — this chapter builds the metrics and logs halves.

6.1 Golden signals and the four types of metric

Start instrumenting around the RED/USE methods and the four golden signals:

SignalQuestionExample metric
LatencyHow fast? (success vs error, separately)http_request_duration_seconds
TrafficHow much demand?http_requests_total
ErrorsHow much failing?http_requests_total{code="5xx"}
SaturationHow full? (the first to signal trouble)CPU, memory, queue depth, connections

Metric cardinality rule: keep label sets small and bounded. request_id or user_email as a label explodes the metric space and kills Prometheus. Identifiers go in logs, not labels.

6.2 Prometheus: pull-based metrics with PromQL

Prometheus scrapes HTTP /metrics endpoints on a schedule, stores time-series, and evaluates PromQL. Exporters convert system signals (node_exporter, kube-state-metrics, cAdvisor) into that format.

# prometheus.yml (minimal)
global:
  scrape_interval: 15s
scrape_configs:
- job_name: node
  static_configs:
  - targets: [ "node-exporter:9100" ]
- job_name: app
  kubernetes_sd_configs:
  - role: pod
  relabel_configs:
  - source_labels: [ __meta_kubernetes_pod_annotation_prometheus_io_scrape ]
    action: keep
    regex: "true"

PromQL that pays the rent

# error rate over 5m, windows 5 min
sum(rate(http_requests_total{code=~"5.."}[5m]))
    / sum(rate(http_requests_total[5m]) or on() vector(0))

# p95 latency
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))

# saturation (CPU)
100 * (1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m])))

# percentage of pods ready
sum(kube_deployment_status_replicas_ready) / sum(kube_deployment_status_replicas)

6.3 Alerting that does not go to voicemail

# alerting rule — one alert, tuned thresholds, a runbook URL
groups:
- name: app.rules
  rules:
  - alert: ApiHighErrorRate
    expr: |
      sum(rate(http_requests_total{job="api",code=~"5.."}[5m]))
        / sum(rate(http_requests_total{job="api"}[5m])) > 0.05
    for: 10m                     # must hold continuously — kill the flapping
    labels: { severity: page, team: platform }
    annotations:
      summary: "API error rate above 5% for 10 minutes"
      runbook: "https://wiki.example.com/runbooks/api-hi-error-rate"

Alert hygiene: alert on symptoms (user-visible) not causes; use for: to require persistence; every alert needs an owner + runbook; and route by severity (ticket vs page). Alertmanager then deduplicates, groups, and routes to Slack/PagerDuty/email.

# alertmanager.yml (snippet)
route:
  group_by: [ "alertname", "cluster" ]
  group_wait: 30s
  repeat_interval: 4h
  routes:
  - match_re:
      severity: "page"
    receiver: pagerduty-critical
  - receiver: slack-warnings
receivers:
- name: slack-warnings
  slack_configs:
  - channel: "#alerts-warn"
Alert anti-patterns that create "alert fatigue": alerting on rate(...) > 0 for anything noisy; alerting on every pod restart (restarts are by design sometimes); no for: window (flapping pages at 2 a.m.); and dashboards that page people. Dashboards inform humans; alerts call them.

6.4 Grafana: dashboards from the data you already collect

Grafana is the visualization layer over Prometheus (and logs/Traces via their own data sources). The pattern that scales:

  • Dashboards as code (JSON in Git), provisioned on startup — never hand-built in a fragile way on the live instance.
  • One dashboard per service tier with the RED panel set; one cross-service "wallboard" for golden signals.
  • Variables (namespace, pod, job) so one panel set serves every team.
  • Annotate dashboards from deploy events (kubectl/CJ hooks) so you can see "what changed at 09:12?" — the single biggest time-saver.
# grafana provisioning example: datasource + folder pre-created
apiVersion: 1
datasources:
- name: Prometheus
  type: prometheus
  url: http://prometheus:9090
  access: proxy
  isDefault: true

6.5 Logging: the ELK stack

app (stdout) --> Filebeat (shipping agent) --> Logstash (parse/transform) --> Elasticsearch (store/index) --> Kibana (search/dashboard)

Diagram (described in text): a log pipeline. Filebeat tails logs from files or containers and ships them; Logstash buffers, parses, and enriches; Elasticsearch indexes them for fast query; Kibana gives humans the UI. In K8s, the agent is usually a DaemonSet so every node has one shipper.

# Filebeat input (container logs)
filebeat.inputs:
- type: container
  paths:
  - /var/log/containers/*.log
processors:
- add_kubernetes_metadata:
    host: ${NODE_NAME}
output.elasticsearch:
  hosts: [ "elasticsearch:9200" ]
  username: ${ELASTIC_USER}
  password: ${ELASTIC_PASSWORD}
# Logstash parsing (grok the messy lines into fields)
filter {
  if [app] == "api" {
    grok {
      match => { "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} %{GREEDYDATA:msg}" }
    }
    date { match => [ "ts", "ISO8601" ] }
  }
}

6.6 Structured logging — do it from day one

JSON logs make parsing trivial and aggregations real. Example in Node/Python:

# never this
console.log("user " + id + " failed login on " + host + ": " + reason);

# always this — structured fields, correlation id
console.log(JSON.stringify({
  event: "login_failed",
  user_id: id,
  reason: reason,
  request_id: req.id,       # correlates logs + traces
  ts: new Date().toISOString()
}));

Kibana queries then become trivial: event:login_failed AND user_id:123. Searching free-text is what you do on a legacy monolith; structured fields are what make a log lake usable at scale.

6.8 Cost & scale best practices

  • Cardinality controls save TB/hour — the single highest-leverage monitoring fix.
  • Downsample/retention tiers: hot index 7d, warm 30d, cold 90d+; logs biggest cost chart in most orgs.
  • Prometheus retention budget tied to disk; use remote-write/VictoriaMetrics/Thanos only when single-node retire hits you.
  • Sample: capture 100% of errors, a slice of success (tail-based sampling for traces).
  • Alert reliability budget: measure each alert's precision (how often was it a page-worthy incident?). Kill low-precision alerts.

Summary

Observability = metrics (numbers on a timeline) + logs (searchable records) + traces (request journey). Prometheus/Grafana own the numbers with PromQL and alert routing discipline; the ELK stack (or Loki) owns the logs with structured fields. Instrument around golden signals, alert on symptoms with windows, and treat dashboards as code.

Checklist

  • ☐ Services expose RED-style metrics; granularity matches golden signals.
  • ☐ Alerts have for: windows, severity, owners, and runbook URLs.
  • ☐ Dashboards are provisioned from Git, with deploy annotations.
  • ☐ Logs are structured JSON with correlation IDs; parsing uses fields, not text search.
  • ☐ Retention tiers and cardinality limits are enforced (cost under control).
