Collaboration Tools: Git Workflows, ChatOps, and Agile

DevOps is a collaboration technology. Git gives you versioned change; code review gives you shared ownership; ChatOps moves operations into the conversation people already live in; and agile ceremonies give operations a rhythm. Tools amplify whichever culture you already have — so this chapter shows both the patterns and the commands.

10.1 Git workflows: choose one, commit to it

WorkflowShapeGood for
Trunk-basedEveryone merges to main daily, short-lived branchesDevOps teams, CD, DORA elite trajectory
GitHub Flowmain + feature branch PR per changeCAAS teams shipping often
Git Flowdevelop/release/hotfix linesRegulated/versioned releases, monorepo SDK releases
MonorepoMany services in one repo + path-scoped CILarge orgs wanting atomic cross-service changes

Whatever you pick, the mechanical invariants are the same:

# keep main deployable at all times
git switch -c feat/cart-cache origin/main
# ... small commit(s), then:
git push -u origin feat/cart-cache
# open a PR with a template; CI must be green before merge
gh pr create --title "cache product cards" --body "Closes #312"
gh pr merge --squash --delete-branch
# trunk-based churn: everyone pulls main and merges often
Why review discipline matters more than branch names: a PR that is only "looks fine" is a rubber stamp. DevOps-heavy orgs treat review as ownership transfer: it is the point where the other person must be able to operate the change. That is why the best reviews check tests, rollback, and observability — not just style.

A PR review template for operations-minded teams (paste this into the repo's PULL_REQUEST_TEMPLATE.md):

## What does this change?
## Why?
## Tests added/changed?
## Deploy/rollback plan (how do we go back?)
## Operability
 - [ ] Metrics / logs nothing new needed (state which)
 - [ ] Secrets required? Where injected from?
 - [ ] Backward compatible? DB migration steps run?
## Screenshots / links from staging

10.2 Code review that catches things: a checklist

  • Behavior: does it do what the linked ticket says, and does it fail loudly otherwise?
  • Tests: did new logic get coverage, and do existing tests still mean anything?
  • Security: are inputs validated, secrets absent, permissions least-privilege?
  • Operations: is it observable, reversible, and does it degrade gracefully?
  • Deployment: is the deploy plan explicit and is rollback a single action?

10.3 ChatOps: operations inside the conversation

ChatOps turns chat into the control/debugging surface: deploys, rollbacks, statuses, and runbooks all reachable with a message — everything a human orchestrates is recorded in the same channel. Bot frameworks: Hubot (legacy), mattermost/rocket bots, GitHub Actions webhooks-to-slack, Slack Bolt, or lightweight /slash commands.

# Botkit/express example: "/deploy api" from Slack
const { createEventAdapter } = require('@slack/events-api');
app.command('/deploy', async ({ command, ack, respond }) => {
  await ack();
  const [ , env = 'staging', image ] = command.text.split(/\s+/);
  runPipeline(env, image).then(
    msg => respond(`:ok: deploy ${image} to ${env} started — #ops-{env}`),
    err => respond(`:x: deploy failed: ${err.message} (see trace)`));
});

What ChatOps really buys you: every action is a logged, shared, auditable side-effect of a conversation — the "who ran that?" question disappears, and the on-call wiki lives beside the command.

10.4 Agile ceremonies wired for operations

CeremonyOps lens
Daily standupAsk "what is blocking the pipeline?" — treat a red build like a fire.
Sprint planningInclude reliability work (alerts debt, cluster upgrades, runbook fixes) as first-class stories — it always loses in the backlog otherwise.
Review/demoDemo the deployment, not just the feature: what did this take to ship, what will it take to run?
RetrospectiveBlameless incident retro feeds improvement items; velocity only counts if stability holds.
On-call handoffThe "seam" between shifts is where tribal knowledge dies — write the 5-line state of the world, not a link to the wiki.
Ways of working that scale (not ceremonial fluff): (1) Small batches: story ships Monday, not Friday. (2) Definition of done includes observability + rollback. (3) Shared on-call rotation: devs rotate for the services they write — "you built it, you run it" is the collaboration tool that makes the culture real. (4) Pause the train for the red build — five minutes wasted now beats an hour of batch fixes later.

10.5 Documentation as collaboration artifact

Doc-as-code is the quiet cousin: runbooks, architecture, and "how we do X" should live in git and deploy like code (mkdocs/docusaurus/generic-stack), with a link from every alert and every release note back to the runbook. A runbook template that on-call actually reads:

# Runbook: API high error rate
## Symptoms
  "ApiHighErrorRate" page; p95 > 2s; 5xx > 5% for 10m.
## Impact
  All API consumers; checkout refuses.
## First actions (2 min)
  1. Open Grafana: /d/api-latency ; check for deploy-markers in last 30m.
  2. If a deploy is recent: `argocd app rollback api' or `kubectl rollout undo deploy/api`.
  3. Check DB saturation + queue depth dashboards.
## If still broken (10 min)
  ...escalation path, who to call, what to say...
## Post-incident
  File retro; attach alert id; update this file with what you learned.

Summary

Collaboration is the operating layer on top of the pipelines. Choose a Git workflow and hold its invariants, review for operability not just style, move operations into chat for auditability, run agile ceremonies with an ops lens, and treat docs as deployed code that every alert links to.

Checklist

  • ☐ Team uses one documented Git workflow; main is always deployable.
  • ☐ PR template includes rollback and operability sections; reviews check them.
  • ☐ Deploys/rollbacks can be triggered from chat with a full audit trail.
  • ☐ On-call rotation includes service owners; runbooks exist per alert and are linked.
  • ☐ Reliability work is scheduled (not only "when it breaks").
