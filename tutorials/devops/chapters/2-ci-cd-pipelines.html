CI/CD Pipelines: Concepts and Tools

Continuous Integration (CI) is the practice of merging every developer's changes into a shared trunk frequently and verifying the result with an automated build and test suite on every push. Continuous Delivery (CD) extends this: every change that survives CI is automatically built into a releasable artifact and staged; Continuous Deployment goes one step further and ships it to production automatically. The difference between Delivery and Deployment is the single manual approval (or not) before the final stage.

2.1 The pipeline as a value stream

commit --> lint --> unit tests --> build artifact --> container image --> scan -->
staging deployment --> integration/e2e tests --> [approval] --> production deployment --> smoke checks

Diagram (described in text): a linear pipeline. Every stage gates the next. Stages early in the loop are cheap and fast (seconds); later stages are slower and more realistic. You want failures to surface as early and as cheaply as possible, so you deliberately keep the delta between staging and production as small as possible.

Design rules that separate good pipelines from decoration:

  • Fail fast: run the fastest checks first; a lint error should not wait behind the e2e suite.
  • Single source of truth: the artifact built in CI is the exact artifact deployed to prod. Never rebuild at deploy time.
  • Idempotent stages: re-running a stage must be safe and produce the same result.
  • Environment parity: staging injects real config, real queue, close-to-real data. If staging differs from prod, your pipeline gives you false confidence.
  • Traceability: every deployment is tied to a commit SHA and a build number, so you can say "exactly this code is live".

2.2 GitHub Actions — the fastest path to a modern pipeline

Workflows live in .github/workflows/ as YAML. Here is a complete CI + CD pipeline for a Node.js service that deploys to a container platform:

# .github/workflows/deploy.yml
name: build-test-deploy
on:
  push:
    branches: [ main ]
  pull_request:

env:
  IMAGE: ghcr.io/${{ github.repository }}:${{ github.sha }}

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm test

  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write          # needed to push to GHCR
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $IMAGE .
      - run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
      - run: docker push "$IMAGE"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production    # can add required reviewers here
    steps:
      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: deploy
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            docker pull "$IMAGE"
            docker service update --image "$IMAGE" myservice
      - name: Smoke check
        run: curl -fsS https://example.com/healthz

Key mechanics to internalize:

  • on defines triggers (branches, tags, PRs, schedules, manual via workflow_dispatch).
  • needs creates a DAG; if conditionals gate stages.
  • environments give you environment-scoped secrets and optional approval gates.
  • ${{ secrets.* }} and ${{ github.* }} are contextual substitutions — never hardcode credentials.
  • Matrix builds let one workflow run the same job across versions/platforms.

2.3 Jenkins — the extensible classic

Jenkins shines where compliance, plugins, and on-prem infrastructure are involved. Modern Jenkins is Jenkins as Code with the Jenkinsfile in the repo, using declarative pipeline syntax:

// Jenkinsfile
pipeline {
    agent any
    environment {
        IMAGE = "myregistry/${env.JOB_NAME}:${env.GIT_COMMIT}"
    }
    stages {
        stage('Checkout')   { steps { checkout scm } }
        stage('Test') {
            steps {
                sh 'npm ci'
                sh 'npm test'
            }
        }
        stage('Build Image') {
            steps {
                sh 'docker build -t ${IMAGE} .'
            }
        }
        stage('Push') {
            when { branch 'main' }          // CD: only on main
            steps {
                sh 'docker push ${IMAGE}'
            }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps {
                // declarative steps, or call a shared library function
                sh 'ansible-playbook -i inventory deploy.yml -e image=${IMAGE}'
            }
        }
    }
    post {
        failure { slackSend channel: '#deploys', message: "Build failed: ${env.BUILD_URL}" }
    }
}
Jenkins hygiene: run the controller with a persistent volume, keep plugins pinned and upgraded, use the Jenkins shared-library pattern for reusable pipeline code, and never store secrets in the Jenkinsfile — use Jenkins Credentials (bound as credentials('id')). Jenkins controllers that drift into "tribal knowledge" are the #1 maintenance trap.

2.4 Azure DevOps — the integrated Microsoft stack

Azure Pipelines uses azure-pipelines.yml, supports Microsoft- or self-hosted agents, and integrates naturally with Azure, GitHub repos, and ARM/Bicep:

# azure-pipelines.yml
trigger:
  branches: { include: [ main ] }
pool:
  vmImage: ubuntu-latest
variables:
  imageName: 'myapp'
  tag: '$(Build.BuildId)'
steps:
- task: UseNode@1
  inputs: { version: 20 }
- script: |
    npm ci
    npm test
  displayName: 'Install and test'
- script: |
    docker build -t $(imageName):$(tag) .
  displayName: 'Build image'
- task: Docker@2
  inputs:
    command: push
    containerRegistry: 'acr-service-connection'
    repository: $(imageName)
    tags: $(tag)
  displayName: 'Push to ACR'
- task: AzureWebAppContainer@1
  inputs:
    azureSubscription: 'pay-as-you-go'
    appName: 'my-webapp'
    imageName: 'myregistry.azurecr.io/$(imageName):$(tag)'
  displayName: 'Deploy to App Service'

Azure DevOps couples three products: Azure Pipelines (CI/CD), Azure Repos (Git), and Azure Boards (work items) — plus test plans and a marketplace of tasks. The pipeline YAML is portable to any agent OS, and service connections handle credential management to your subscription.

2.6 Security & cost best practices for pipelines

  • Least-privilege credentials: grant a deploy token only the scopes needed for one environment; rotate them; never put secrets in logs (gate with ::add-mask:: in Actions or Jenkins credential masking).
  • Pin third-party actions: reference by full SHA (uses: actions/checkout@sha) instead of a floating tag; review what you pull in.
  • Gate PRs from forks: never run secrets-bearing jobs on untrusted code unless you re-approve.
  • Cache deliberately: caching speeds builds but bloats; set expiry and only cache immutable stuff (deps, not build outputs).
  • Right-size runners and use concurrency limits — CI cost is the largest hidden cloud line-item; cap parallel jobs per repo.
  • Make deploys reversible: every CD stage should have a one-command rollback (previous image or tag).

Summary

CI makes every commit verifiable; CD makes every verified commit releasable. A good pipeline is a fast, idempotent, traceable value stream with early failure and environment parity. GitHub Actions, Jenkins, and Azure DevOps all implement the same model; pick on fit, not hype, and harden secrets and supply chain regardless of platform.

Checklist

  • ☐ My latest commit on main triggers a build, test, and artifact creation automatically.
  • ☐ The artifact built in CI is identical to what deploys (no rebuild at deploy).
  • ☐ Secrets come from a vault/secret store, never the pipeline file or logs.
  • ☐ Every deployment is traceable to a commit SHA and has a documented rollback.
  • ☐ Third-party pipeline actions/plugins are pinned and reviewed.
