Security in DevOps: DevSecOps

DevSecOps is security as a first-class pipeline stage, not a separate team that audits at the end. You move security left — into commit, build, and deploy — so that problems are found where they are cheapest to fix, and you automate enforcement so humans review exceptions rather than everything. The three pillars are: shift-left scanning, secrets management, and supply-chain trust, wrapped in policy as code.

8.1 Where security checks live in a pipeline

commit --> [secret scan, IaC scan, SAST] --> build --> [dependency scan, container scan] -->
packaging --> [sign, generate SBOM] --> deploy --> [DAST/pen test, runtime policy] --> observe --> [threat feed]

Diagram (described in text): security stages interleaved with CI/CD stages. Static checks (secrets, IaC, SAST) run in the commit/build phase; dependency and container scans gate the artifact; signing + SBOM happen at packaging; runtime checks (DAST, admission policy) guard the deploy, and threat signals flow back into the pipeline.

# GitHub Actions: gate the merge on security
- name: Secret scan
  run: gitleaks detect --source . --redact --report-format=json
- name: IaC scan
  run: checkov -d terraform/ --framework terraform --compact --download-external-modules False
- name: Dependency scan (fails on high+)
  run: trivy fs --scanners vuln --severity HIGH,CRITICAL --fail-on-vuln --exit-code 1 .
Priority note for your team: IaC misconfigs and leaked secrets are the two findings that recur most in production breaches — and both are solvable in PR. SAST/DAST matter, but cover the top of the funnel first.

8.3 Secrets management (the practice everyone gets wrong once)

The pipeline needs secrets at three points: CI (deploy credentials), runtime (DB passwords, API keys), and IaC (provisioning values). Use the right tool at each:

  • CI: the platform's secret store (GitHub secrets.*, Jenkins Credentials, Azure variable groups) populated from a human-approved vault — never committed, never echoed.
  • Runtime: a vault with dynamic secrets: HashiCorp Vault, or cloud-native (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager), or K8s Secrets with encryption-at-rest via KMS — in that order of preference from "most done" to "minimum."
  • Config-as-files: SOPS (encrypt only the values in Git with age/KMS) so application config with secrets can still be versioned.
# Vault: dynamic, expiring DB credentials (databases/creds)
vault read database/creds/app@5m
# > connection string valid 5 minutes — no static passwords to rotate
# SOPS: encrypt values inside a normal YAML, decrypt at deploy
sops -e -k ark:<key> secrets/app.yaml > secrets/app.enc.yaml
sops --decrypt secrets/app.enc.yaml | kubectl apply -f -
Static-secret reality check: if you cannot do Vault yet, at minimum: (1) never bake secrets into images or IaC, (2) enable KMS encryption at rest on whatever store you use, (3) rotate/expire by policy, (4) revoke immediately on a leak — and treat base64 in K8s as "encoded," not "encrypted."

8.4 Supply chain: SBOMs, signing, provenance

# syft: make an SBOM (software bill of materials) at build time
syft image ghcr.io/team/api:1.2.3 -o spdx-json > sbom.json
# cosign: sign the image + attest like "git-sha: <x>"
cosign sign --key cosign.key ghcr.io/team/api:1.2.3
cosign verify --key cosign.pub ghcr.io/team/api:1.2.3

SBOM answers "what is actually inside my image that I must track when the next big CVE drops?" Signing ensures the image your runtime pulls is the image your pipeline built. Provenance (SLSA attestation) ties artifact to build logs, so a compromised image is traceable. This is the current frontier of DevSecOps and where every serious platform team is investing.

8.5 Policy as code: enforcement, not hoping

Admission controllers can block bad manifests at deploy time. The standard is none of the tool choices as much as the placement: policies evaluated by the cluster, not by memory.

# Open Policy Agent (Gatekeeper) constraint: block privileged containers
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sPSPPrivilegedContainer
metadata: { name: no-privileged-containers }
spec:
  match:
    kinds: [{ apiGroups: [""], kinds: ["Pod"] }]
  enforcementAction: deny

Equivalent checks on the IaC side: Checkov/OPA on terraform plan can automatically block "storage bucket public-read" before it ever reaches a cloud. The dream outcome: humans review exceptions; machines enforce the rules.

8.6 Runtime hardening on Kubernetes

  • Pod Security Standards (baseline/restricted) or Gatekeeper in your namespaces — no running as root, no privileged.
  • NetworkPolicies default-deny east-west; allow only declared pairs (see Chapter 5).
  • Runtime security (Falco, cloud-native agents) detects odd behavior at runtime: shells in web containers, file tampering.
  • ImagePullPolicy + admission scan: ratify/sigstore policy "pull only signed images."

8.7 DevSecOps workflow in one commit (your template)

git push main            # 1. push the MR
# 2. repo triggers: gitleaks, checkov, semgrep, dependabot
# 3. on merge: build, trivy scan (fail on HIGH/CRITICAL), syft sbom, cosign sign
# 4. deploy to staging behind a slack "review my env" gate
# 5. cluster admission policy rejects privileged/unsigned images
# 6. ZAP/DAST runs weekly against staging; findings become tickets
# 7. every release ships with sbom attached to the release notes

Summary

DevSecOps makes security continuous and automatic: scan early in the funnel, manage secrets through a vault with short-lived credentials, sign and SBOM every artifact, and enforce policy as code at the admission/apply boundary. Security becomes a property of engineering practice instead of a gate at the end.

Checklist

  • ☐ PRs run gitleaks + checkov + a dependency scan that can block the merge.
  • ☐ No secret exists in Git, images, or IaC; runtime secrets come from a vault/KMS-backed store.
  • ☐ Images are signed (cosign) and ship with an SBOM.
  • ☐ Admission policy blocks privileged/unsigned workloads; NetworkPolices enforce default-deny.
  • ☐ Access permissions are least-privilege and reviewed; no long-lived admin credentials in use.
