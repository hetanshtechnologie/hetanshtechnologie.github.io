Pitfalls, Troubleshooting & Interview Q&A

The difference between a DevOps engineer and a DevOps admin is whether you debug systems by reading them, not by praying. This chapter gives you the failure modes to recognize instantly, a diagnostic loop that works, and the interview questions you will actually be asked — with answers you can build from.

12.2 The diagnostic loop that ends incidents

1. Describe the SYSTEM: what was the last change? (deploys, config, traffic, provider incident)
2. Establish a BASELINE: is this new, or always been broken?
3. Narrow with FIFTH discipline: logs --> metrics --> traces --> config --> capacity
4. Form a HYPOTHESIS; verify with the cheapest check first
5. Apply the FIX or a mitigation (scale/flag-off/rollback); confirm with data
6. Retro: why was it possible? add alert/runbook/policy so it cannot recur silently

Diagram (described in text): a loop, not a ladder — after the fix you re-enter at step 1 for confirmation, and the retro feeds improvements back into monitoring ("add an alert here") so the next loop is faster.

Forensic commands per layer

# K8s layer
kubectl get events --sort-by=.metadata.creationTimestamp
kubectl describe pod <name> | grep -A5 Events
kubectl logs <pod> --previous

# Container layer
docker inspect <id> | jq '.[0].State'
docker stats --no-stream

# Network / service layer
kubectl get endpoints; dig +short svc.default.svc.cluster.local
kubectl exec -it <pod> -- curl -v http://<svc>/

# Resource/capacity layer
kubectl top nodes; kubectl top pods
df -h / /var/lib; journalctl -u kubelet -n 100 --no-pager

# IAM/cloud layer (did permissions change?)
aws iam list-role-policies --role-name the-role; az role assignment list
The #1 debugging failure mode: jumping to "fix" without "what changed?" first. Most incidents map to a change in the last 30 minutes (deploy, config, dependency, cloud quota). Get the deploy-marker, the last ConfigMap edit, and the traffic spike on one screen before touching anything.

12.3 Interview Q&A (the questions that actually come up)

Q: What is the difference between Continuous Delivery and Continuous Deployment?
CD-delivery: every change is automatically built, tested and release-ready, but a human/process may promote it. CD-deployment: every change that passes goes straight to production automatically. Delivery keeps a rollout gate you can use for peak hours or compliance; deployment removes it — the gate then lives in feature flags and metrics.

Q: A pod is CrashLoopBackOff. Walk me through your diagnosis.
Order: (1) events for the why (ImagePullBackOff? OOMKilled? start failure?), (2) describe the pod + previous logs, (3) check mounts/secrets/config referenced by the pod, (4) check resource limits vs observed usage, (5) `kubectl exec` for a shell only if the app boots enough. The fix follows the layer that answers first — wrong image tag, missing secret, command crashing, or OOM.

Q: How do you make a deployment reversible without "reverting code"?
Every release should have two levers: the artifact (roll back the image tag — rollout undo or GitOps `app rollback`) and the behavior (feature flags — turn the slow path off). Reverting code is the bluntest and slowest of the three; the raw onboarding move is to rehearse both so you know which knobs exist before traffic breaks.

Q: Terraform sometimes complains state mismatches reality. What do you do?
State ls —> state show —> plan to see the diff. If a resource exists out-of-band, `import` it rather than forcing replacement; if it was deleted elsewhere, `state rm` the gone key and plan/create. Never fix by running `apply` blind or deleting state; lock state and review the plan. The durable fix is drift detection in CI.

Q: Your monitoring shows 5-minute peaks of CPU but SLO latency is still fine. Act?
That's a saturation signal — correlate deploy/time-of-day/batch jobs with the peaks, add limits if a burst is pathological, and distinguish "alert-worthy" (latency/errors) from "trend-worthy" (CPU). Scale decisions go to HPA on the request-relative metric, not raw CPU; resize the node pool or add autoscaler only if capacity, not spikes, is the constraint.

Q: What does "shift left" mean concretely?
Move security/quality checks back into the branch: lint, secret scan, SAST, IaC scan, dependency scan on the PR; image sign + SBOM at build; admission policy at deploy. Cost of a finding multiplies by ~10x per stage you let it pass — shift-left is a cost-of-incident argument, not a slogan.

Interview meta-tip: the answers above are templates of structure, not scripts. Interviewers probe how you order steps, so practice the diagnostic loop and the "what changed → verify → fix → confirm → retro" shape. Structure proves judgment; memorized trivia proves nothing.

Summary

The pitfalls are all the same root: process ran ahead of automation, or automation ahead of process. Troubleshooting is a disciplined loop anchored on "what changed," then cheapest-first layers. And interviews, like incidents, reward ordered thinking over flat facts.

Checklist

  • ☐ I recognize all ten pitfalls and can state the fix for each.
  • ☐ I can run the diagnostic loop from memory (change→baseline→layers→hypothesis→fix→retro).
  • ☐ I can answer the six interview questions with ordered reasoning (not only example traces).
  • ☐ I have rehearsed at least one real rollback in staging.
