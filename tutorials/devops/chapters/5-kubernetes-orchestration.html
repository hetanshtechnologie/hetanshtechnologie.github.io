Kubernetes Orchestration: Deployments, Services, Scaling

Kubernetes is the operating system for containers: a control plane that constantly reconciles the desired state you declare in YAML with the actual state of the cluster. If a pod dies, a replica is made. If traffic spikes, the HPA adds replicas. If a node fails, workloads are rescheduled. This chapter gives you the production-shaped version of the core objects and the mental model to debug them.

5.1 The object model in one diagram

            +------------------ Ingress (hostname routing) -------------------+
            |                                                                 |
   (clusterIP) Service  ----> selects pods by label ----> Pods (many replicas)
            ^                                                                 |
            |                                                        managed by
        kubectl ---> API server ---> Deployment ---> ReplicaSet               |
                                               (declares N replicas,     +----+
                                                rolling update strategy)  |PV/PVC|
                                                                          +----+

Diagram (described in text): kubectl talks to the API server to create a Deployment, which manages a ReplicaSet that owns N Pods. A Service selects those pods by label and gives them one stable address; an Ingress routes hostnames/paths to that Service. Pods mount PersistentVolumeClaims for stateful data. Everything is declared, nothing is hand-scheduled.

5.2 A production-shaped Deployment (this is the template you will copy)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: production
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxUnavailable: 0, maxSurge: 1 }   # zero-downtime
  selector:  { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      serviceAccountName: api-sa
      containers:
      - name: api
        image: ghcr.io/team/api:<commit-sha>
        ports: [ { containerPort: 8080 } ]
        resources:
          requests: { cpu: "250m", memory: "256Mi" }
          limits:   { cpu: "1",    memory: "512Mi" }
        readinessProbe:
          httpGet: { path: /healthz, port: 8080 }
          periodSeconds: 5
          failureThreshold: 3
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          periodSeconds: 20
          timeoutSeconds: 3
        envFrom:
        - configMapRef: { name: api-config }
        - secretRef:    { name: api-secrets }
        securityContext:
          runAsNonRoot: true
          allowPrivilegeEscalation: false
          capabilities: { drop: ["ALL"] }

Read this Deployment like an auditor: immutable image tag, resource requests and limits, readiness + liveness probes, config and secrets injected declaratively, non-root security context, zero-downtime rollout strategy. Every one of those lines is a production incident avoided.

5.3 Services: giving pods a stable front door

apiVersion: v1
kind: Service
metadata: { name: api, namespace: production }
spec:
  selector: { app: api }                 # find pods by label
  ports:
  - port: 80            # Service port
    targetPort: 8080    # container port
  type: ClusterIP       # default; internal-only

# --- NodePort (for tests): add nodePort: 30080 under ports ---
# --- LoadBalancer: change type to LoadBalancer — cloud provisions a real LB ---

kubectl get svc -n production
kubectl describe svc api                 # shows the endpoint slice = real pod IPs
kubectl get endpoints api

Rule: ClusterIP for service-to-service calls, LoadBalancer for public single-service exposure, NodePort for the rare case of a bare-metal static port, and Ingress for everything that wants hostnames, paths, and central TLS.

5.4 Scaling: manual, HPA, and scheduling concerns

kubectl scale deploy api --replicas=5                 # quick/imperative
kubectl autoscale deployment api --cpu-percent=70 --min=3 --max=20   # HPA (CPU)

# hpa.yaml — better: multiple metrics
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api, namespace: production }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
  - type: Resource
    resource: { name: memory, target: { type: Utilization, averageUtilization: 80 } }
  behavior:
    scaleDown: { stabilizationWindowSeconds: 300 }    # avoid flapping
Scaling gotchas: HPA needs requests set (it scales on usage vs request). CPU-only autoscaling lags under latency-bound loads — add memory/P95 latency or queue depth. And if your nodes are full, HPA produces pending pods: you also need cluster autoscaling (CA-as-a-service on every cloud — Karpenter on EKS is currently the strongest).

5.5 Rolling updates and rollback (the release mechanics)

kubectl set image deploy/api api=ghcr.io/team/api:<new-sha> --record
kubectl rollout status deploy/api          # wait for health
kubectl rollout history deploy/api         # every version + cause
kubectl rollout undo deploy/api            # one-command rollback
kubectl rollout restart deploy/api         # reload config (no image change)

With maxSurge: 1 / maxUnavailable: 0, rollout never drops capacity below the target and one new pod must become healthy before the next starts. This is why readiness probes exist: a missing probe makes K8s call a crashing pod "ready" and the rollout stalls silently instead of failing.

5.6 Storage: PersistentVolumes and PVCs

# pvc.yaml — dynamic provisioning via a StorageClass on the cloud
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data, namespace: production }
spec:
  accessModes: [ "ReadWriteOnce" ]
  storageClassName: gp2                       # EBS on EKS; check your cluster
  resources: { requests: { storage: 10Gi } }
apiVersion: apps/v1
kind: StatefulSet        # for databases: stable name + one PVC per replica
metadata: { name: postgres, namespace: production }
spec:
  serviceName: postgres
  replicas: 3
  selector: { matchLabels: { app: postgres } }
  template:
    metadata: { labels: { app: postgres } }
    spec:
      containers:
      - name: postgres
        image: postgres:16
        volumeMounts: [ { name: data, mountPath: /var/lib/postgresql/data } ]
  volumeClaimTemplates:
  - metadata: { name: data }
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: gp2
      resources: { requests: { storage: 10Gi } }

Use Deployments for stateless workloads and StatefulSets when each replica needs identity + its own persistent volume (databases, queues). Preserve RWO/RWX semantics: a shared RWX volume for a single-writer database is a corruption bug waiting to happen.

5.7 Namespaces & policies for sane multi-team operation

kubectl create namespace production
kubectl create namespace staging
kubectl config set-context --current --namespace=production
# then enforce with a ResourceQuota and LimitRange so teams can't starve each other
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: ResourceQuota
metadata: { name: quota, namespace: staging }
spec:
  hard:
    requests.cpu: "8"
    limits.cpu: "16"
EOF

5.8 Debugging workflow (the part beginners skip)

kubectl get events --sort-by=.metadata.creationTimestamp     # narrative of reality
kubectl describe pod <name>                                    # why is it CrashLoop?
kubectl logs <pod> --previous                                 # last crash's output
kubectl exec -it <pod> -c <container> -- sh                    # get inside
kubectl top pods -n production                                # resource pressure
kubectl get pvc,pv -n production                              # wait: claim/image Lost?

Order matters: events first (scheduling failures), then describe (image pulls, probes), then logs (code), then exec (symptoms), then resource queries (pressure). This order eliminates 80% of "why is my pod not healthy" cases in minutes.

5.9 Best practices: scale, security, cost

  • Pin versions, run workloads as code: all YAML lives in Git; apply via GitOps (Chapter 9), never kubectl apply from a laptop.
  • Set requests/limits on every container; use VPA in "recommendation" mode to tune them before committing to numbers.
  • Use network policies / RBAC / pod security standards (defaults in Chapter 8).
  • Cost: right-size requests (over-requesting = idle paid nodes), use spot/preemptible nodes for stateless and bursty work, add the HPA + cluster autoscaler pair, and let the autoscaler scale down to zero for batch jobs.
  • Logs to stdout/stderr so the platform collects them; never rely on kubectl logs for the archive — ship to the stack from Chapter 6.

Summary

Kubernetes converts deployment correctness into a property of YAML plus probes. Deployments own rolling updates, Services own discovery, HPA owns throughput, StatefulSets+PVCs own state, and namespaces/policies own multi-team sanity. Master the reconcile-and-debug loop and the rest is vocabulary.

Checklist

  • ☐ Every workload has probes, requests/limits, non-root security context.
  • ☐ Rollouts are zero-downtime and rollbackable (rollout undo proven once).
  • ☐ HPA + cluster autoscaler cover throughput; scaling is not "click instances".
  • ☐ Databases use StatefulSets with per-replica PVCs (not shared RWX).
  • ☐ Manifests are reviewed in Git and applied through GitOps, not ad hoc.
