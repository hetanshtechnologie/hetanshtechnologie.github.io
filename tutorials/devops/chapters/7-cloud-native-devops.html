Cloud-Native DevOps: AWS, Azure, and GCP

Cloud providers do not change DevOps principles; they change vocabulary, CLIs, and the half of the stack they run for you. This chapter teaches the pattern that transfers everywhere — IAM first, managed Kubernetes, cloud-native CI/CD, and active cost control — with concrete AWS/Azure/GCP commands so you can map your skills to all three.

7.1 The universally applicable cloud model

Git --> CI/CD (cloud-native pipelines) --> repositories --> managed Kubernetes --> observability --> budget alerts
        |                                      ^
        └----> IaC (AWS CDK / Bicep / Terraform) --> networks, IAM, databases, storage

Diagram (described in text): one loop. Code flows right into cloud CI/CD, then into artifact repositories, then to a managed Kubernetes cluster. Instructions for the supporting infrastructure flow through IaC into the control plane. Observability and budget alerts feed back to the developer loop on the left.

7.2 The identity layer (get this wrong and nothing else matters)

  • AWS: IAM users/roles; power users use IAM Roles Anywhere or OIDC-federated workloads, never static AK/SK on a server.
  • Azure: managed identities for Azure resources + service principals; RBAC via built-in or custom role assignments.
  • GCP: service accounts + IAM roles; workload identity federation for K8s/GitHub Actions.

Least-privilege policy (AWS; equivalents exist everywhere):

aws iam create-role --role-name deploy-role --assume-role-policy-document file://trust-oidc.json
aws iam put-role-policy --role-name deploy-role --policy-name deploy \
  --policy-document '{"Version":"2012-10-17","Statement":[
    {"Effect":"Allow","Action":["s3:PutObject"],"Resource":"arn:aws:s3:::artifacts/*"}
  ]}'
The #1 cloud leak: a long-lived admin key committed to a repo or pasted into a build log. Fix it permanently with workload identity federation: GitHub Actions OIDC / Azure workload identity / GCP WIF — GitHub then mints short-lived tokens for your pipeline, and there is nothing to rotate.

# GKE — one command to a managed multi-node cluster
gcloud container clusters create prod --region us-central1 \
  --num-nodes 3 --machine-type e2-standard-4 \
  --enable-autoscaling --min-nodes 3 --max-nodes 30 \
  --workload-pool prod.svc.id.goog

# AKS — equivalent
az aks create -g prod-rg -n prod --enable-cluster-autoscaler --min-count 3 --max-count 30 \
  --enable-managed-identity --zones 1 2 3

# EKS via eksctl
eksctl create cluster --name prod --region ap-south-1 \
  --nodegroup-name workers --node-type t3.medium --nodes 3 --managed
Cluster-upgrade rhythm (the quiet killer): each cloud deprecates minor versions (~14 months). Budget 2 hours/month: test a minor upgrade in staging, run kubectl get nodes & conformance smoke, then upgrade prod. Teams die by "we'll do it next quarter" until the API server goes EOL on an emergency.

7.5 Multi-cloud/portability notes

  • Containerize first, abstract later: portable images run everywhere; don't hide provider APIs behind a heavy abstraction until a cloud is a real constraint.
  • Keep provider-specific things at the edge: bucket/queue/KMS inside a small "cloud adapter" package; the app core stays provider-agnostic.
  • Terraform/Pulumi with provider blocks per env: your IaC is portable if the only env-delimited diffs are provider config lines.
  • Cost symmetry: the big three all bill you for sort-of-the-same things (compute, storage, egress, managed services) — the cheapest stack is usually managed services that match your team's skills, not the cheapest list price.

7.6 Cost control as a DevOps practice (not a finance panic)

# AWS — tag your world, then query costs
aws resourcegroupstaggingapi get-resources --tag-filters "Key=Environment,Values=staging"
aws ce get-cost-and-usage --time-period Start=$(date +%Y-%m-01),End=$(date +%Y-%m-%d) \
  --granularity MONTHLY --metrics UnblendedCost --group-by Type=TAG,Key=Environment

# Azure
az cost management query --type ActualCost --timeframe MonthToDate --scope "/subscriptions/$SUB"

# GCP
gcloud billing projects describe $PROJECT --format='value(budgetAmount)'

Then wire budget alerts (AWS Budgets, Azure Cost Alerts, GCP budget notifications) at 50/80/100% with a Slack hook — before the invoice, not after. And the dullest but most effective lever: dev/test/staging environments shut down at night and on weekends; one cron + one start/stop script on non-prod clusters routinely cuts 30-50% of a platform bill.

7.7 Best practices recap: scale, security, cost

  • Scale: use the managed cluster autoscaler + pod autoscaler pair; enable spot/preemptible for stateless; right-size via metrics, not guesswork.
  • Security: workload identity everywhere; no long-lived keys; CIS-benchmark the managed node image; enable VPC/NSG/private-cluster networking; use cloud KMS for secret encryption at rest.
  • Cost: tags on 100% of resources, budget alerts, non-prod auto shutdown, and quarterly rightsizing review driven by usage data.

Summary

Cloud-native DevOps is the same loop — code, CI/CD, registry, managed Kubernetes, observability, budget — mapped onto IAM, CLIs, and managed services. The transferable asset is the pattern, not the commands; the discipline that survives all clouds is identity-first security and active, data-driven cost management.

Checklist

  • ☐ All workload identity is short-lived/federated; no static keys in repos or logs.
  • ☐ Managed cluster is provisioned via IaC and has a version-upgrade calendar.
  • ☐ Deploys go through a registry + GitOps; provider-native deploy is avoided.
  • ☐ Everything is cost-tagged; budget alerts at 50/80/100% reach a chat channel.
  • ☐ Non-prod environments have an automatic off-hours shutdown.
