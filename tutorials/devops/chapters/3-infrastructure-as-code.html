Infrastructure as Code

Infrastructure as Code (IaC) means managing your infrastructure — networks, instances, load balancers, databases — through machine-readable definition files instead of clicking in a web console. Two philosophies exist, and knowing which one you're using matters more than the brand name:

Declarative (Terraform, Pulumi, cloud native)Imperative (Ansible, shell)
You stateDesired end stateSteps to get there
Idempotent?Yes, by construction (converges)Only if you write it to be (plugins help)
Drift handlingDetected on every plan/applyRe-runs steps; drift not always surfaced
Best forProvisioning cloud resourcesConfiguring machines/apps (Day-2)
Mental model"What should exist?""What should I do?"

3.1 Terraform: declarative provisioning with state

Terraform (HashiCorp) describes resources in HCL. The heart of Terraform is the state: a record of what actually exists. Treat state as a liability — keep it in a remote backend (S3 + DynamoDB, Terraform Cloud, Azure Blob, GCS) with locking, never in the repo alone.

A minimum-but-real module layout:

.
├── main.tf         # resources
├── variables.tf    # inputs with descriptions + defaults
├── outputs.tf      # useful values after apply
├── versions.tf     # provider + backend constraints
├── backend.tf      # remote state config

# versions.tf
terraform {
  required_version = ">= 1.5"
  backend "s3" {
    bucket         = "my-org-tfstate"
    key            = "prod/vpc/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "terraform-locks"   # prevents concurrent applies
    encrypt        = true
  }
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}
# main.tf — a network + autoscaling web tier
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = { Name = "prod-vpc", Environment = "prod" }
}

resource "aws_subnet" "public" {
  count                   = 3
  vpc_id                  = aws_vpc.main.id
  cidr_block              = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index)
  availability_zone       = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = true
}

resource "aws_launch_template" "web" {
  image_id      = "ami-0abcdef1234567890"   # source from a variable per environment
  instance_type = var.instance_type
  user_data = base64encode(<<-USERDATA
    #!/bin/bash
    systemctl enable --now nginx
  USERDATA
  )
}

resource "aws_autoscaling_group" "web" {
  vpc_zone_identifier = aws_subnet.public[*].id
  desired_capacity    = 2
  min_size            = 1
  max_size            = 6
  target_group_arns   = [aws_lb_target_group.web.arn]
  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest"
  }
  tag {
    key                 = "Name"
    value               = "web-asg"
    propagate_at_launch = true
  }
}

resource "aws_lb" "web" { name = "prod-web-alb" }
resource "aws_lb_listener" "web" {
  load_balancer_arn = aws_lb.web.arn
  port              = 443
  protocol          = "HTTPS"
  default_action { type = "forward", target_group_arn = aws_lb_target_group.web.arn }
}
resource "aws_lb_target_group" "web" { port = 80, protocol = "HTTP", vpc_id = aws_vpc.main.id }

The workflow is the discipline:

terraform init                       # download providers, init backend
terraform plan -out=tfplan           # diff desired vs state (review this!)
terraform apply tfplan               # only after humans (or policy) approve
terraform fmt / validate / tflint    # linting gate in CI
terraform state list                 # inspect what exists
Apply discipline: enforce the rule "never apply alone, always from a reviewed plan." Put terraform plan in your MR pipeline, feed it to a plan review step, and use terraform apply -parallelism=10 with locking. A deploy that deletes the production VPC is a state-management incident, not a Terraform incident.

3.2 Ansible: configuration management, agentless

Ansible connects over SSH, pushes tasks (modules), and can bootstrap machines, deploy apps, and enforce config. It is agentless and imperative-but-idempotent because modules test state before changing it.

# inventory/production.yml
all:
  hosts:
    web1: { ansible_host: 10.0.1.10 }
    web2: { ansible_host: 10.0.1.11 }
  vars:
    ansible_user: ubuntu
    ansible_ssh_private_key_file: ~/.ssh/id_ed25519
# playbooks/web.yml
- name: Configure web servers
  hosts: web
  become: true
  vars:
    app_release: "1.2.3"
  tasks:
    - name: Install nginx
      apt: { name: nginx, state: present, update_cache: true }
    - name: Deploy config from template
      template:
        src: templates/nginx.conf.j2
        dest: /etc/nginx/sites-available/app
      notify: reload nginx
    - name: Enable site
      file:
        src: /etc/nginx/sites-available/app
        dest: /etc/nginx/sites-enabled/app
        state: link
    - name: Deploy application version
      get_url:
        url: "https://releases.example.com/app-{{ app_release }}.tar.gz"
        dest: /opt/app/app.tar.gz
  handlers:
    - name: reload nginx
      service: { name: nginx, state: reloaded }
ansible-playbook -i inventory/production.yml playbooks/web.yml --check

--check is a dry run; --diff shows changes. Run both in CI before touch production.

Composition pattern: Terraform provisions the VM and passes its IP to an inventory; Ansible configures the VM. This "Terraform raises the building, Ansible moves in the furniture" split is the most common production architecture in the wild — and it maps cleanly to two teams owning different risks.

3.3 Pulumi: IaC with real programming languages

Pulumi is declarative (it still converges to desired state) but written in TypeScript/Python/Go/C#. That buys you loops, conditionals, functions, and your language's type system — at the cost of a little extra runtime. Same workflow: preview, then up.

// pulumi/typescript/s3.ts — actual program, not a template
import * as aws from "@pulumi/aws";
import * as pulumi from "@pulumi/pulumi";

const config = new pulumi.Config("app");
const env = config.require("environment");

const bucket = new aws.s3.Bucket("app-assets", {
  acl: "private",
  tags: { Environment: env },
});

const policy = aws.iam.getPolicyDocument({
  statements: [{
    actions:   ["s3:GetObject"],
    resources: [pulumi.interpolate`${bucket.arn}/*`],
    principals: [{ type: "*", identifiers: ["*"] }],
  }],
});

new aws.s3.BucketPolicy("app-policy", {
  bucket: bucket.id,
  policy: policy.apply(JSON.stringify),
});

export const bucketName = bucket.id;
export const region = aws.getRegion().then(r => r.name);
pulumi preview                 # diff
pulumi up --yes                # apply
pulumi stack select production # switch environments
pulumi stack output bucketName

3.4 Best practices across any IaC tool

  • One backend, locked: remote state + state lock + encrypted. Never apply with a local stale state in a team.
  • Environments as separate states/stacks (dev, staging, prod) so a bad change is containable.
  • Variables everywhere, no hardcoded values: drive region, size, and count from inputs; change size in one line.
  • Tag everything for cost: CostCenter, Environment, Owner tags are the prerequisite for both cost allocation and drift queries.
  • Plan gating in CI: run plan/preview in pipelines, attach it to the MR, and let policy-as-code (OPA/Sentinel/Checkov, see Chapter 8) block dangerous diffs.
  • Minimize blast radius: module count intentionally; a giant all-in-one state file makes review impossible and change dangerous.
  • Per-environment secrets: wire references to a secrets manager, never values, into your IaC.

3.5 Fixing a drift incident (workflow)

terraform plan                     # shows what drifted vs state
terraform state list               # confirm the resource actually exists
terraform import aws_instance.web i-0abc123   # adopt an out-of-band resource
terraform apply                    # converge
# prevention: AWS Config / Azure Policy / GCP Config Controller + periodic drift scans in CI

Summary

IaC turns infrastructure into a reviewable, versioned, reproducible artifact. Declarative tools (Terraform, Pulumi) own provisioning with stateful convergence; imperative tools (Ansible) own configuration. Neither replaces the other; both replace the console clickers and the "I must have created it in 2019" incidents.

Checklist

  • ☐ All cloud resources are defined in code, versioned in Git.
  • ☐ State is remote, locked, encrypted — never a local-only file.
  • ☐ Environments are separate states; plan/preview is gated in CI for review.
  • ☐ All resources carry cost/ownership tags.
  • ☐ Secrets are referenced from a vault, not embedded in IaC.
