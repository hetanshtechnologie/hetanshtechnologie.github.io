Core Features: Everyday Pair Programming

Now that Copilot is running, this chapter is about the three tools you will use constantly: inline completions, the Copilot Chat panel, and inline chat — plus the built-in editor commands that turn problems into code.

1. Inline code completions (ghost text)

Completions appear as you type. They work best when the model has signal — a function signature, a docstring, a comment, or an example. Common tricks that dramatically improve suggestions:

  • Write the signature first: def fetch_user_balance(user_id: int) -> Decimal: followed by a blank line. Copilot fills the body.
  • Use comments as mini-specs: write what the code should do, one line at a time, and let Copilot complete each piece.
  • Provide a precedent: if you already wrote one SQL query in the file, the next similar query will follow that pattern.
  • Cycle through alternatives with Alt+] when the first guess is wrong.
Biggest beginner mistake: accepting a suggestion you do not understand. Always read the suggestion, and if any line is a surprise, reject it with Esc and write it yourself or ask chat to explain it.

2. Copilot Chat

Chat is a conversational interface to the same models. Open it with Ctrl+Alt+I (Windows/Linux) or Cmd+Alt+I (macOS). You can:

  • Ask questions about code: "why does this parse fail for empty strings?" with the selection in context.
  • Generate whole pieces: "write a FastAPI endpoint that validates an email and returns 422 on invalid."
  • Iterate: "make it async", "add pydantic validation", "use a repository pattern".
  • Explain and fix: paste an error stack trace (better: use /explain and /fix).
  • Convert / translate: JavaScript to TypeScript, pytest to unittest, CSV parsing to pandas.
  • Apply a plan: start with "I want to: ..." a list of requirements — chat drafts an implementation plan and code you can review.

To give the model context, select the relevant code before chatting. Code outside the selection is only included if the model can find the symbols, so select generously but deliberately.

3. Inline chat (Ctrl+I)

Inline chat is a small input that appears right at your cursor. It is ideal for a single focused change to the current file:

# Press Ctrl+I with the mean() function selected (or just at the cursor)
> make it skip NaN values without breaking existing callers
> /fix  # attach to a selected error/red squiggle

It either inserts new code at the cursor (choose Insert) or edits the selected code in place (the diff applies to the selection). Inline chat is where most of the productivity lives — you never leave your file.

4. Editor commands you will live in

CommandWhat it does
/explainExplains the selected code (or the whole file) in plain language.
/fixGiven a selected error, exception, or lint problem, proposes a corrected version.
/testsGenerates unit tests for the selected code (pytest, jest, MSTest, etc. based on the project).
/docAdds documentation comments to the selection.
/generateGenerates a feature (a component, a function, a test file) from a description.
/optimizeSuggests performance improvements.
Quick Fix → Fix using CopilotApplies Copilot to the red squiggle under your cursor (Ctrl+.).
Copilot Make the change …Ask for a specific change from the Quick Fix menu.

Type / anywhere in chat to see the full list installed with your version.

5. A realistic daily loop

  1. Write a comment or signature describing the next unit of work.
  2. Let completions draft the body; Tab accept, Esc reject, Alt+] cycle.
  3. For anything bigger, open inline chat (Ctrl+I) with a precise instruction.
  4. Run the tests. When something fails, select the error and run /fix.
  5. Use /tests to keep coverage honest, then review the generated tests for sneaky assumptions.
Do not paste secrets or proprietary code blindly. Everything you send to Copilot is processed by GitHub's service. Keep credentials, IP, and customer data out of prompts unless your organization has explicitly configured a policy that allows and commits it. Details in Chapter 5.
✏️ Exercise: Pick a small real function from your codebase (15–40 lines). First, from memory, write a one-sentence comment describing it. Watch Copilot regenerate it and diff against your original. Then use /explain on your version and verify the explanation matches what the code really does. Try /tests and see if any test captures a bug you know about.
