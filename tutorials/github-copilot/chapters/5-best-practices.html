Best Practices, Security & Responsible AI

Copilot can make you faster, and it can also make you sloppy. This chapter is the difference between "accepted a ghost" and "shipped code you own." Four themes: prompting, context, security, and review discipline.

1. Prompting strategies that actually work

  • Name the problem. "write a retry helper" vs. "with exponential backoff, jitter, and a circuit breaker" — specificity pays.
  • Give constraints up front. Language, version, dependency availability, style, output shape. "Using only Python stdlib" beats "parse this CSV".
  • Show don't tell for patterns. One existing example of the shape you want (a schema, a route, a test) transfers far better than adjectives.
  • Split big asks. Ten small precise prompts beat one huge vague prompt, because each keeps context small and reviewable.
  • Iterate on output, not on luck. "No, like the other function", "that's still leaking — use a context manager" — treat chat like pairing with a junior dev.

2. Context is your superpower

Copilot only knows what you show it. The three levers:

  1. Open the right files/tabs. Relevant open editors are the strongest free context for both completions and @workspace.
  2. Select the code you want the answer to be about before chatting.
  3. Point the model at the ground truth. Tell it where things live: "in src/db/users.ts there is a getByEmail we should reuse."

If a suggestion looks "close but not quite," 90% of the time it lacked one concrete fact about your project. Add the fact, not more words.

3. Security: what you must never do

Never paste secrets. API keys, tokens, passwords, .env contents, private customer data, and internal IP go nowhere near Copilot. Segregate: repositories with such data should be treated as needing explicit, auditable policy.
  • If you must work with secrets, generate them via key vaults/secret managers and reference them at runtime — never embed them in chat.
  • Organizations: enable zero data retention + no training on your code if your plan supports it, and require "suggestions matching public code" as wanted by your legal team.
  • Prompt injection: if you paste untrusted text (web scrapes, traces, emails) into prompts, an attacker could inject instructions. Sanitize or quote untrusted content, and never auto-run AI output with shell privileges.
  • Audit dependencies generated by AI just like any other dependency.

4. Licensing and public-code matches

Copilot's training includes public code. Two facts to internalize:

  • Suggestions matching public code: Copilot can reference snippets resembling public code it saw. GitHub offers a detection/filtering option ("Code Referencing": GitHub Copilot's feature that attaches matching public code references, and the ability to block suggestions that match public code). Check your plan's settings and your company's policy; for proprietary products an opt-in setting that blocks public-code matches — where available — is the conservative choice.
  • You own the code you ship: in most jurisdictions, AI-generated code is subject to the same review as any code merged by you. The human who merges it is accountable for it. Keep provenance notes and a review step in your workflow.

5. Built-in quality habits

  1. Run tests after every accept batch — do not get 100 lines deep before compiling.
  2. Make /fix part of the loop: select the failure, ask why and how before applying what.
  3. Keep a "no-AI" core: architecture, security reviews, and anything irreversible stays in human hands.
  4. Pair the tool with your own invariants: the AI proposes; your tests, your reviewers, and your understanding dispose.
