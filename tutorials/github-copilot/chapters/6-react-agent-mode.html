React & Next.js: Agent Mode and Vibe Coding

This is the frontier chapter. Until now you steered Copilot one task at a time. Here you hand it a goal, and Copilot plans, edits, runs, and fixes across multiple files until the goal is met — a mode called agent mode. You will scaffold a real React/Next.js project, build a paginated employees table, fetch data the right way, and document components, all while keeping yourself in the review seat.

1. Scaffold a React project with Copilot

Bootstrapping is the easiest win: the generator is a well-known shape, so the model is on home turf. Tell it exactly which stack and which choices you want:

Terminal prompt (or chat):
> I want a new Next.js 15 project called "team-dashboard" with:
>   - TypeScript, App Router, src/ directory, Tailwind CSS
>   - no ESLint config prompt, no turbopack
>   - app/ layout that includes a simple header nav
>   - give me the exact create-next-app command with all flags, then the
>     npm run dev command and the URL to open.

Notes that save you destruction rounds:

  • Ask for the command as a single copy-paste with all flags — npx create-next-app@latest team-dashboard --ts --app --src-dir --tailwind --eslint --no-turbopack — so interactive prompts never stall you.
  • Pin the major version ("Next.js 15") or the AI may hit a brand-new release you have never seen either. If the generated skeleton differs from your expectation, you know the version bumped.
  • Run the scaffold yourself in a terminal. Scaffolding is a "trust but verify" moment; generator output changes frequently and you must read it.
Agent mode vs. one-shot scaffold: in agent mode the model can run the generator and then fix the errors it produced. Beginners often prefer a manual scaffold first so they can compare. Either way, the prompt above keeps the decisions in your hands.

2. What Agent Mode is (and is not)

Agent mode turns Copilot from a respondent into an executor with a plan. Given a goal, it will:

  • Read the files it needs (your codebase, your repo) to ground the work.
  • Plan file-level steps and show you the checklist before acting.
  • Edit files, run commands (build, tests, linters), observe failures, and iterate.
  • Stop at the goal boundary or when it cannot satisfy a constraint — and ask you.

Agent ≠ unsupervised. Agent mode is a fast pair programmer, not a delegator. It can guess wrong (esp. on naming, auth, or "fix" loops that patch symptoms). Read every diff, run the app, and keep git as your undo button.

3. Build a paginated employees table

The classic exercise: a table that fetches employees, sorts, and pages. This is a perfect agent-mode goal because it spans a component, a data layer, and styles. Give the model a tight brief:

Agent mode, new task:
> In team-dashboard, build an employees page at /employees that:
>   - is a Server Component page that reads employees from the included
>     employees.json fixture (id, name, email, department, role, salary)
>   - renders a table with sortable columns (name, department, salary)
>   - paginates client-side at 10 rows per page with Prev/Next buttons
>     and a "Page X of Y" indicator
>   - salary formatted as Indian Rupees via Intl.NumberFormat('en-IN', ...)
>   - follows the existing src/ App Router structure and Tailwind classes
>   - then run npm run build and fix any lint/type errors it finds.
> Constraint: keep it dependency-free (no react-query, no table library).

Why this prompt shapes up well:

  • Goal, not code: "build … that …" with bullets reads as acceptance criteria.
  • Concrete fixture: it neither invents a DB nor asks you for one.
  • Explicit "no library": otherwise the model may pull in a table package and double your dependency count.
  • "Fix what it finds": closes the loop so it self-checks with npm run build.
Review checklist after an agent run: (1) did it add the fixture you referenced or invent a different shape? (2) is pagination state client-side but the data source server-side? (3) does sorting reset the page index? (4) did npm run build actually pass after it claimed it did? Re-run the build yourself.

4. Call APIs the right way (React data fetching patterns)

Beginners ask Copilot "fetch the data and show it" and get a useEffect + fetch with no loading state, no error state, and a memory leak. Ask for the pattern instead:

Chat (in a new RSC-or-client context):
> All of these are for the /employees page. Recommend one pattern and justify:
>   A. fetch directly in a Server Component (async) — default for this app.
>   B. client component + useEffect + fetch.
>   C. Next.js route handler (app/api/employees/route.ts) called from the client.
> Then implement your recommendation with:
>   - an isLoading and an error state that renders a message with the HTTP status;
>   - a retry button;
>   - AbortController cleanup in the effect;
>   - typed responses (Employee type) and no 'any'.
> Add a note explaining when pattern B is actually justified.

What the good answer will contain:

  • Server Component by default: data that is not user-specific belongs at the server — no loading flicker, no client round-trip.
  • Client fetch only for interactivity (search-as-you-type, live updates) — and then it must handle loading, error, and AbortController cleanup so an unmounted page cannot set state.
  • Route handlers when you need client auth, caching rules, or to hide an upstream service.
# The sketch you should be able to recognize and review:
async function Employees() {
  const rows: Employee[] = await getEmployees();   // typed, server-side
  if (!rows) throw new Error("no employees returned");
  return <table>{rows.map((e) => <Row key={e.id} e={e} />)}</table>;
}
Do not cargo-cult skeletons. Copilot happily generates the latest tutorial pattern and can mix paradigms (RSC page that also uses useEffect). Read the generated file top-to-bottom once and ask it to explain any line you cannot justify.

5. Document React components

Components outlive chats. Get Copilot to leave documentation behind so the next reader (future you) benefits:

Select the EmployeesTable component, then:
/doc -- "add a JSDoc-style comment: what the component renders, its props table
         (name, type, required), state and effects, when it re-renders,
         and one usage example. Keep it under 15 lines."

Then in the same thread:
> Also generate a typed example page usage and a 3-line README section titled
> "Employees" that says where the fixture lives and how pagination behaves.

Documentation prompts worth making routine:

  • Prop contracts: ask for a TS interface for every component prop — required vs. optional, and the runtime defaults — the same explicitness the course has demanded all along.
  • Story usage: "show two minimum examples, happy path and empty-list path."
  • Architecture notes: ask for a short // Why comment on the trickiest 3 lines — those are the lines your future self will blame.
Back in the CashTrack context: everything from Chapter 4's prompt template applies unchanged to components. Add props shape to the Context block and re-render behavior to the DO list, and the template becomes a component brief.

6. Vibe coding, done responsibly

"Vibe coding" is the practice of describing a feature in plain language and letting the AI write nearly all the code, often iterating on natural-language feedback. Agent mode is the tool that makes this feel real. Use it like this:

  1. Scope the vibe: define the boundary ("one page", "one refactor", "one data source"). Unbounded vibes become unreadable, unreviewable diffs.
  2. Read what it writes. You feel the vibe; you must also understand the diff. If you cannot explain a change, reject or rewrite it.
  3. Keep the tests honest. Ask agent mode to write tests alongside, then run them and inspect for coverage of the gaps you know about.
  4. Commit small. Agent output should come back as reviewable chunks, with git commits you can bisect when something breaks.
The trap: the vibe is addictive exactly because you stop reading. A codebase built purely by vibe accumulates duplicate utilities, magic numbers, dead imports, and three ways to do the same thing — and nobody can certify it. Review is not optional; it is the whole job now.
