Copilot Chat: Prompt Engineering & Everyday Superpowers

This is the meat of the course: the exact situations Copilot Chat handles best, and the prompting habits that turn a decent autocomplete into a genuine pair programmer. Each subsection is one real task you will hit within a week of professional work.

1. Why Copilot is most useful for these tasks

Almost every "wow" moment with Copilot falls into a small set of task shapes. If a request fits one of these, expect magic; if it does not, expect to steer harder:

Task shapeExampleWhy Copilot wins
Generate one kind of artifacta regex, a test, a JSON fixtureWell-trodden; high-consensus output
Transform existing coderefactor, convert, rename with touchYou supply the input; the output is bounded
Explain something you can point ata confusing function, a stack traceFacts live in the selection, not in the model's head
Fill a repetitive shape you demonstratefollow-on queries, rows in a tableIt pattern-matches your last example
Draft code for a described speca new endpoint, a controllerIt converts prose to structured code fast

Spend your steering energy precisely where the task is open-ended and under-specified — that is where the model needs your intent the most.

2. Providing context to Copilot Chat

Copilot only knows what you show it. Context, in priority order:

  1. Select relevant code. The single strongest signal; most chat answers are only as good as your selection.
  2. Open the right files. Other open editors are picked up automatically and beat prose descriptions.
  3. Name the file and language. "In auth/users.ts…" removes guesswork.
  4. Attach artifacts. Use the paperclip / @file to pin stack traces, logs, or requirements.
  5. State the constraint in the sentence, not the follow-up. "Using only the standard library" works far better up front.
Calibration: if a reply is "close but wrong shape," 9 times out of 10 you omitted one concrete fact about your project (a function, a naming convention, a dependency). Add the fact — do not rephrase the whole question.

3. The one prompt to use before every code-generation ask

Before any "write…" request, front-load a mini brief. This one template covers most of it:

Write the missing CODE for this DO and DON'T.

Context (facts the code depends on):
- stack / language and version (e.g. Node 22 + Express 4)
- file it belongs in and what already exists there
- inputs and expected outputs (types, shapes, units)
- any dependency limits (only stdlib, no ORM, etc.)

DO:
- behavior the implementation must guarantee
- conventions to follow (naming, error handling, style)

DON'T:
- things to avoid (side effects, global state, breaking changes)

Then produce the code with a one-paragraph explanation of the risky parts.

Templates like this cost thirty seconds to type but remove an entire round of "no, that's not what I meant." Keep a tame-version in a snippet (Section 12) so it is one keystroke away.

4. Generate unit tests

Tests are where Copilot is genuinely gifted, because the shape is fixed. Select the function and ask:

/tests -- "table-driven cases for parse_amount(): valid '₹1,234.50', decimals, negatives,
       empty string (return 0), and a malformed input (throw TypeError).
       Use Node's built-in node:test, no external framework."
  • Specify the framework (pytest / vitest / MSTest) or tell it "no external framework" — this is the most common mismatch.
  • Demand boundary values (empty, zero, negatives, unicode, huge numbers). AI defaults to happy-path tests.
  • Always run the suite after. Plan on its tests failing the first run and it fixing them if you show the error (Section 5).

5. Explain code and fix terminal errors

Two of the highest-ROI commands in the tool:

# Select confusing code, then in chat:
/explain -- "walk through what this does for a junior dev, step by step, and
             name the riskiest assumption it makes"

# Paste the whole stack trace (or select it in the terminal), then:
/fix -- "this throws in CI on Windows only. Find the root cause, not a try/catch patch."

For terminal errors, paste the full trace, not "it broke." Include the command you ran and the working directory if it matters. Then verify the fix actually changes behavior — /fix occasionally produces correct-looking but semantically wrong patches.

6. Generate commit messages

Your staged or un-staged diff is perfect context. In the chat panel:

@workspace -- "read the current git diff and write a concise conventional commit message
              (type(scope): subject) plus a 1-3 line body summarizing what changed and why.
              Group related changes; ignore lockfile noise."

Better than auto-generating: ask for three candidate messages at different levels of detail (one-liner / summary / changelog) and pick the right one per merge. If your team uses a changelog, add your conventions to copilot-instructions.md (Section 15).

7. GitHub Copilot in the mobile app

Copilot also rides in the GitHub mobile and desktop apps. You can send questions from a phone or use it while browsing a repo — but it is bounded by the same rule as everywhere: it sees what you share with it. Useful, quick loops: "explain this function" from a PR diff, or "suggest a regex for this" while a laptop is away. Store heavy, multi-file work for the editor, where context is free.

8. See which public code Copilot references

Sometimes a suggestion strongly resembles public code. Two controls matter:

  • View referencing code: in newer extensions you can ask Chat "show the public-code match for this suggestion" / surfacing a referencing notice; the UI links to the public repository it matched.
  • Block public-code matches: an organization/admin setting can filter out suggestions that match public code — the conservative default for proprietary products. Ask your org admin before assuming it is on.

Even enabled, you remain the reviewer (Chapter 7 covers the licensing judgment).

9. Refactor JavaScript and HTML

Refactoring is transform-with-input: Copilot keeps the behavior if you describe the target shape clearly.

JavaScript (select the callback soup):
> Refactor these chained .then() callbacks into async/await.
> Extract the retry logic into a helper retry(fn, retries=3).
> Do not change public behavior or thrown error messages.

HTML (select the repeating card markup):
> Convert this repeated product-card markup into a reusable
> Web Component , keeping the same classes and data-attributes
> so the existing CSS keeps working.

Afterward, diff carefully: refactors drift on edge cases (error paths, this binding, event listener teardown). Prompt for "also add a smoke test that invokes both versions and compares" to catch the drift.

10. Detect vulnerabilities with Copilot Chat

Review pass for security issues — a modern replacement for a sleepy manual review:

@workspace /review -- "scan this repository's entry points for OWASP ASVS-level issues:
   SQL/NoSQL injection, unsafe deserialization, missing auth checks, secrets in code,
   XSS sinks, and OS command injection. Report as table: severity / location / issue /
   concrete fix. Do not edit files, just report."

Treat the results as a shortlist to verify, not a verdict. AI misses app-specific logic and can flag false positives. Pair it with a real dependency scanner for the deep audit.

11. Get creative with Copilot Chat

Beyond "make it work," Copilot is a cheap idea engine:

  • Design alternatives: "three UX layouts for the settings page, trade-offs for each."
  • Meetings and docs: turn bullet notes into a spec, a README, or an RFC sketch.
  • Brainstorm code: "edge cases for a subscription-billing calc no one usually handles" — its lists are surprisingly good.
  • Learning: "teach me how async generators differ from for await with a tiny example" — an instant tutor, on your terms.

12. Generate dummy data and build prompt snippets

Dummy data is a favorite: the model says patterns for free.

/generate -- "10 realistic users for a restaurant app: name, email (unique, camel-case-ish),
   city, joined_at (ISO, spread over 2024-2025), loyalty_points (0-5000), favorite_dish.
   Return as a JSON array suitable for seeding a Postgres table."

Prompt snippets: create VS Code snippets for your most-used commands so the "always use this" template and friends are one keypress away. In copilot-snippets.code-snippets:

{
  "copilot brief": {
    "prefix": "cobrief",
    "body": ["Context: $1", "DO: $2", "DON'T: $3", "Generate: ${4:the code}"],
    "description": "Structured brief for Copilot code generation"
  },
  "copilot gen test": {
    "prefix": "cotest",
    "body": ["/tests -- $1 (${2:framework}) as ${3:table-driven} cases, include edge values"],
    "description": "Fast unit-test prompt"
  }
}

13. Prompt shortcuts and documentation generation

Shortcuts: every plan/tier ships a set of slash commands (/explain, /fix, /tests, /doc, /generate, …); type / in the chat input to list yours. Learn ten; that is 80% of daily use. You can define custom ones via prompt files (Section 15).

Documentation:

/doc -- "JSDoc every exported function in this module: params with types, return shape,
       @throws, and a 1-line example. Keep @param lines terse."
# For files: "/generate -- a README section explaining installation, env vars, and API."

Docs also extend to architecture: ask for // Why comments on tricky selections, or an ADR-style note capturing a decision the code embodies.

14. Changing the model (completions and chat)

You can often pick the brain behind the tool:

  • Completions model: usually set implicitly by plan; in VS Code the model picker appears when a suggestion is shown.
  • Chat model: dropdown at the top of the chat panel. Bigger/newer models = better reasoning but slower; smaller models = faster but dumber. Switch per task: heavy architecture reasoning → big, tiny refactor → fast default.
  • Plan limits: free tiers cap completions and chat messages per month; paid tiers raise or remove them and unlock more models.

15. Agents, custom instructions, prompts & multi-file edits

Agents (at-mentions)

Prefix a message with an agent to specialize Copilot: @workspace (whole-repo questions), @terminal (shell), @vscode (editor). You can also define your own agents as .github/copilot-agents/<name>.md with a role and optional tools.

Custom instructions

.github/copilot-instructions.md lets whole teams encode conventions Copilot should follow (naming, error style, test framework, commit format). Repo-level; honored by chat and completions when supported.

Reusable prompts

.github/prompts/*.prompt.md becomes a team-wide slash command (e.g., /review-api) — a named prompt with a description, invoked with /review-api in chat. The structure is plain markdown with a YAML-ish front-matter description.

Copilot Edits (multi-file)

For changes that touch several files, Copilot Edits keeps a working set and applies planned changes with your approval per change:

Ctrl+Shift+I → start "Edits" mode. Add files to the working set, then:
/ -- "rename the data model from Customer to Account across the API, store, and tests;
      keep a deprecated alias in the store for one release cycle."

You review each diff before accepting. This is the closest thing to working sessions Copilot ships today, and the natural home for feature-sized requests.

Spec-driven work

For a full feature, write a short spec (Do / Don't block) and feed it to Create from spec or the specs CLI: Copilot turns it into a plan of file-level tasks, then code — a structured alternative to cooking everything in one prompt.

16. Stay safe: the rules that never change

  • No secrets in prompts. Keys, tokens, .env, customer PII go nowhere near Copilot.
  • Sanitize untrusted text (web scrapes, traces, emails) — prompt injection is a real attack.
  • Review AI output like a stranger's PR, and run the tests.
  • Beware public-code matches in proprietary repos; know your org's filtering policy.
  • Zero-retention / telemetry policies are plan-and-org settings: turn them on where your plan permits and your security team cares.
