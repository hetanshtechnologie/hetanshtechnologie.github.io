1. Introduction to Data Engineering

Chapter 1

What is Data Engineering?

Data engineering is the discipline of designing, building, and maintaining the systems that collect, store, process, and make data available for analysis and machine learning. Data engineers build the pipelines and platforms that move data from source systems (databases, files, SaaS apps, streaming events) into storage and analytics systems where analysts, data scientists, and BI tools can use it.

In a typical organization, the data engineering layer sits between source systems (the operational systems that create data) and consumers (analysts, dashboards, ML models, applications). This book focuses on doing that work on Google Cloud Platform (GCP), with a complete tour of AWS-to-GCP migration for teams coming from the AWS world.

The Data Engineering Lifecycle

Modern data engineering is commonly described as a lifecycle with four stages:

StageWhat HappensExample Tools (GCP)
GenerationSource systems produce data: transactions, logs, events, filesDatabases, SaaS APIs, IoT, application events
IngestionData is moved from sources into a landing areaCloud Storage (GCS), Pub/Sub, Storage Transfer Service, connectors
TransformationData is cleaned, structured, joined, and modeled for useDataflow, Dataproc (Spark), Cloud Composer (Airflow), dbt, BigQuery SQL
ServingData is made available for analytics, BI, ML, and applicationsBigQuery, Bigtable, Cloud SQL, Looker, Vertex AI

Around this cycle sit the "undercurrents": orchestration (scheduling and dependency management), data governance (quality, lineage, cataloging, security), and observability (monitoring, alerting, SLAs). A pipeline that runs but is not orchestrated, monitored, or governed is not production-ready.

Data Warehouses, Data Lakes, and Lakehouses

Storage and analytics architecture has evolved through three major patterns:

  • Data Warehouse: structured, relational, highly optimized for SQL analytics. Data is cleaned and modeled before loading. (Example: BigQuery, Amazon Redshift.)
  • Data Lake: stores raw data of any format (structured, semi-structured, unstructured) at low cost. Flexible but can become a "data swamp" without governance. (Example: Amazon S3, Google Cloud Storage.)
  • Lakehouse: a modern hybrid — a data lake's cheap storage combined with warehouse-style SQL querying and management. Open table formats like Apache Iceberg, Delta Lake, and Hudi are the technical foundation. BigQuery (with BigLake and external tables) and Dataproc (with Iceberg/Delta) support lakehouse patterns.

Key Trend: The boundary is blurring. BigQuery can query files directly in GCS (external tables), Dataproc can read and write BigQuery, and open formats like Iceberg let a single dataset serve both Spark and BigQuery. Modern teams design for this flexibility rather than picking one silo.

Batch vs Streaming

Data arrives on two rhythms, and the architecture usually serves both:

AspectBatchStreaming
CadenceHourly, daily, or scheduled chunksContinuous, event-by-event
LatencyMinutes to hoursSeconds to minutes
Typical sourcesFiles, database exports, APIs on scheduleClickstreams, IoT, CDC from databases
GCP toolsDataflow batch, Dataproc, Cloud Composer schedulesPub/Sub, Dataflow streaming, Kafka via Confluent, Flink on Dataproc
ChallengesScheduling, dependencies, reprocessingOrdering, exactly-once semantics, backpressure

A common pattern is lambda (batch + streaming serving the same view) or the modern kappa architecture (one streaming pipeline that can also reprocess history). BigQuery supports both: streaming inserts for near-real-time and scheduled batch loads for bulk history.

ETL vs ELT

  • ETL (Extract, Transform, Load): data is transformed before being loaded into the warehouse. Historically necessary when the warehouse could not transform at scale. Tools: Dataproc/Spark, Dataflow.
  • ELT (Extract, Load, Transform): raw data is loaded first, then transformed inside the warehouse. The rise of massively parallel warehouses (BigQuery, Snowflake, Redshift) made this the default. Tools: dbt, BigQuery SQL, Stitch/Fivetran-style loaders.
Why ELT won: cheap storage + fast SQL engines meant loading raw data and transforming it in SQL is simpler, faster to iterate, and more auditable. dbt formalizes ELT by treating transformations as versioned code. This book covers both, but the ELT/dbt model gets the deepest treatment.

The Modern Data Stack

The "modern data stack" describes the current generation of cloud-native data tools. A representative stack:

  • Ingestion: Fivetran/Stitch/Airbyte, GCS + Storage Transfer, Pub/Sub.
  • Storage: cloud object storage (GCS) and warehouses (BigQuery).
  • Orchestration: Airflow / Cloud Composer, Dagster, Prefect.
  • Transformation: dbt, Spark (Dataproc), Dataflow.
  • Visualization/BI: Looker, Looker Studio, Tableau, Power BI.
  • ML: Vertex AI, BigQuery ML.
  • Governance: Data Catalog, Dataplex, OpenMetadata, data quality tools.
