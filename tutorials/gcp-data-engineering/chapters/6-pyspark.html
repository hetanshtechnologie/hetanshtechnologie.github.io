6. PySpark for Data Engineering

Chapter 6

What is PySpark?

PySpark is the Python API for Apache Spark, the open-source unified engine for large-scale data processing. PySpark lets you write Python code that runs distributed across a cluster, processing data that is too big for a single machine. On GCP, PySpark runs on Dataproc (or Dataproc Serverless).

The Spark Execution Model

Understanding Spark's model explains most performance behavior:

  • Driver: runs your main program, builds the execution plan, schedules tasks.
  • Executors: worker processes on cluster nodes that run tasks and store cached data.
  • Tasks: units of work, one per partition; the parallelization unit.
  • Stage: a group of tasks that can run without shuffling data.
  • Shuffle: redistribution of data across partitions (e.g., for group-by or join) — the expensive operation to minimize.
  • Lazy evaluation: transformations build a plan; nothing runs until an action (collect, count, write) forces execution. This lets Spark optimize the plan.

DataFrames: The Main API

For data engineering, you use the DataFrame API — a distributed table with named columns, similar in feel to pandas/SQL but distributed.

from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("sales_etl").getOrCreate()

# Read Parquet from GCS
df = spark.read.parquet("gs://my-bucket/sales/*.parquet")

# Transform
result = (
    df.filter(F.col("amount") > 0)
      .withColumn("year_month", F.date_format(F.col("sale_ts"), "yyyy-MM"))
      .groupBy("year_month", "region")
      .agg(
          F.sum("amount").alias("revenue"),
          F.countDistinct("customer_id").alias("customers")
      )
      .orderBy("year_month")
)

# Show (action) and write (action)
result.show(10)
result.write.mode("overwrite").parquet("gs://my-bucket/agg/monthly_sales/")

RDDs and the Low-Level API

Before DataFrames, the API was RDDs (Resilient Distributed Datasets). DataFrames are the modern default (optimized via the Catalyst optimizer and Tungsten execution). RDDs are still useful for low-level control and custom operations, but prefer DataFrames/SQL for data engineering:

# RDD example (rarely needed, but good to recognize)
rdd = spark.sparkContext.textFile("gs://my-bucket/logs/*.log")
counts = rdd.flatMap(lambda line: line.split(" ")) \
            .map(lambda word: (word, 1)) \
            .reduceByKey(lambda a, b: a + b)
for w, c in counts.take(10):
    print(w, c)

Spark SQL: The Engine's SQL

Spark SQL lets you register DataFrames as tables and query them with SQL — the sweet spot when logic is clearer in SQL:

df.createOrReplaceTempView("sales")

result = spark.sql("""
    SELECT date_format(sale_ts, 'yyyy-MM') AS year_month,
           region,
           sum(amount) AS revenue
    FROM sales
    WHERE amount > 0
    GROUP BY year_month, region
    ORDER BY year_month
""")
result.write.mode("overwrite").saveAsTable("analytics.monthly_sales")

DataFrames, Spark SQL, and PySpark code all compile to the same optimized physical plans — pick whichever expresses the logic best.

Optimization Fundamentals

  • Minimize shuffles: group/join by aligned partition keys, use coalesce instead of repartition when shrinking.
  • Choose file formats well: Parquet (columnar, compressed) over CSV/JSON for most workloads.
  • Bucketing: pre-bucket tables on join keys so joins become shuffle-free.
  • Broadcast small tables: broadcast(df_small) avoids shuffling a big table in joins.
  • Filter early: push predicates down; Spark pushes filters into file readers (Parquet) automatically.
  • Avoid per-row Python UDFs on hot paths — use native SQL functions; use Pandas UDFs (pandas_udf) for vectorized operations.
  • Manage partition counts: too few partitions under-utilize the cluster; too many create scheduling overhead. ~100-200MB per partition is a good rule of thumb.
Join strategy example: joining a 1 billion-row fact table with a 1 million-row dimension — broadcasting the dimension avoids a full shuffle. Joining two huge tables requires aligning bucketing or letting Spark choose sort-merge join. Understanding this trade-off is the #1 Spark performance skill.

Reading and Writing with GCP Services

# GCS (native)
spark.read.parquet("gs://bucket/path")
df.write.format("csv").option("header", True).mode("append").save("gs://bucket/out/")

# BigQuery via the Spark BigQuery connector
df = spark.read.format("bigquery").option("table", "myproj.analytics.orders").load()
df.write.format("bigquery") \
  .option("table", "myproj.analytics.orders_clean") \
  .option("temporaryGcsBucket", "gs://tmp-bucket") \
  .mode("append").save()

# Reading from a database via JDBC (e.g., Cloud SQL, or external DBs)
jdbc_df = spark.read \
  .format("jdbc") \
  .option("url", "jdbc:postgresql://HOST:5432/db") \
  .option("dbtable", "public.orders") \
  .option("user", "svc_user") \
  .option("password", "") \
  .load()
Security: never hardcode database credentials in Spark code. Pass secrets via Dataproc secret references, Secret Manager, or Dataproc Metastore/Vault integrations.

PySpark Project Structure and Best Practices

project/
├── src/
│   └── etl/
│       ├── __init__.py
│       ├── main.py          # entry point with argparse (date, mode, project)
│       ├── jobs/
│       │   ├── sales_agg.py # pure transform functions (testable)
│       │   └── customer_dim.py
│       └── utils/
│           └── io.py        # read/write helpers (bigquery, gcs)
├── tests/
│   └── test_sales_agg.py
└── requirements.txt

Best practices: keep business logic in pure functions that take and return DataFrames (testable without a cluster), separate I/O from transforms, use argparse for parameters, log with the Python logging module, and pin library versions.

Testing PySpark

Test transforms with a local SparkSession on small sample data (pytest + a spark-session fixture). You can test pure functions and even whole jobs locally against a few rows:

# conftest.py (pytest fixture)
import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    return SparkSession.builder.master("local[2]").getOrCreate()

# test example
def test_sales_agg(spark):
    data = [("2026-01-01", "US", 100.0), ("2026-01-01", "EU", 50.0)]
    df = spark.createDataFrame(data, ["sale_ts", "region", "amount"])
    out = agg_revenue(df)          # your pure function
    assert out.filter("region='US'").select("revenue").collect()[0][0] == 100.0

Monitoring and Debugging

  • Check the Spark UI (via Dataproc component gateway) for stage timing, shuffle size, and executor memory.
  • Watch for data skew (one partition much larger) and spilled memory.
  • Enable event logging and review failed task reasons.
  • Use Cloud Logging to centralize driver logs; Cloud Monitoring for cluster metrics.

Common Pitfalls

  • collect() on huge DataFrames (pulls everything to the driver — OOM).
  • Repeated actions in a loop (each action re-executes the full lineage).
  • Using a driver-global SparkSession inside UDFs.
  • Shuffling huge data in default configuration without tuning spark.sql.shuffle.partitions.
  • Running PySpark on a single machine with big data — use Dataproc and let it scale.
Practice Task: On Dataproc (single-node cluster is fine): (1) load a public CSV from GCS into a DataFrame, (2) clean it (drop nulls, normalize dates), (3) join it with a small broadcast dimension, (4) aggregate and write Parquet + a BigQuery table, (5) write 3 pytest tests for your transform functions and run them locally. Then use the Spark UI to find the stage with the most shuffle and explain why.
