12. AWS Data Services & GCP Mapping

Chapter 12

Why Map AWS to GCP?

Many teams run data platforms on AWS and need to migrate to GCP — or simply want to understand both clouds. The concepts are nearly identical; the services and APIs differ. This chapter maps the AWS data services you are most likely to meet — S3, Glue, Redshift, EMR, Kinesis — to their GCP counterparts, with the differences that actually matter when migrating.

S3 → Cloud Storage (GCS)

S3 and GCS are both object stores with buckets, objects, prefixes, versioning, and lifecycle policies. The differences that matter:

  • Naming and access: s3://bucket/key → gs://bucket/object. AWS IAM roles → GCP IAM + service accounts; S3 ACLs/bucket policies → IAM and object-level ACLs; signed URLs → GCS signed URLs.
  • Consistency: both are strong-consistency object stores now.
  • Storage classes: Standard/IA/Glacier → Standard/Nearline/Coldline/Archive.
  • Tools: aws s3 cli → gsutil; boto3 → google-cloud-storage.

Redshift → BigQuery

Redshift is a massively parallel (MPP) warehouse; BigQuery is a serverless warehouse. Both speak SQL, so this is the most mechanical migration — but the mental models differ:

AspectRedshiftBigQuery
InfrastructureClusters you size and scale (nodes, slices)Serverless; pay per query + storage
ScalingAdd/remove nodes; distribution keys matterAutomatic; optimize partitions/clustering instead
Sort/dist keysDISTKEY + SORTKEYPartitioning + clustering
SQL dialectPostgres-flavoredGoogleSQL (ANSI + extensions)
CompressionCompression encodings per columnAutomatic (columnar, Capacitor)
StreamingCOPY + STL system tablesStreaming API / Storage Write API

Unload from Redshift (UNLOAD to S3 as Parquet/CSV) then load into BigQuery via bq load or the Transfer Service. Rewrite DISTKEY/SORTKEY-heavy SQL as partitioning/clustering and let BigQuery's optimizer handle the rest.

EMR → Dataproc

EMR and Dataproc both run Spark/Hadoop clusters on cloud VMs. Migration is mostly the same open-source stack in a new management plane:

  • Cluster config: EMR instance types/spot → Dataproc machine types + preemptible workers.
  • Filesystems: s3:// → gs:// (Dataproc reads GCS natively).
  • Jobs: spark-submit stays the same; gcloud/API replace aws CLI.
  • Bootstrap: EMR bootstrap actions → Dataproc initialization actions.
  • Metastore: EMR Hive metastore → Dataproc Metastore (managed Hive metastore) or external.
  • Best practice: Dataproc ephemeral clusters (create per job, delete after) — a pattern EMR supports but teams rarely adopt as aggressively.

Glue → GCP

Glue is AWS's ETL service with three distinct parts, each mapping differently:

  • Glue Jobs (Spark ETL): a managed Spark environment. On GCP, run the same Spark ETL on Dataproc (more control) or Dataflow (if you rewrite to Beam). Glue's PySpark code ports to Dataproc PySpark with small changes (filesystems, session bootstrap).
  • Glue Data Catalog + Crawlers: schema discovery and metadata. GCP equivalent is Data Catalog plus Dataplex for governance; schema discovery can be scripted or done via Dataproc/BigQuery auto-detect.
  • Glue Data Quality: automated quality rules → Dataplex data quality / dbt tests.

Kinesis → Pub/Sub

  • Kinesis Data Streams (retained, replayable stream) → Pub/Sub (with message retention and replay) — both are pull/push event buses.
  • Kinesis Data Firehose (load streams into S3/Redshift) → Dataflow streaming to GCS/BigQuery, or Pub/Sub subscriptions writing to BigQuery.
  • Kinesis Analytics (SQL on streams) → Dataflow SQL / Dataflow with Beam SQL.

Athena → BigQuery External / BigLake

Athena queries files in S3 directly. On GCP, the equivalent is querying files in GCS via BigQuery external tables and BigLake — same idea (schema-on-read, serverless SQL over object storage), stronger warehouse integration.

MWAA (Managed Airflow) → Cloud Composer

Both are managed Airflow. If you use MWAA today, your DAGs port to Composer with minimal change — update provider packages (boto3/aws operators → google provider operators), adjust connections/secrets handling, and redeploy the same DAGs to the Composer bucket.

Conceptual Differences That Trip People Up

  • IAM vs IAM: AWS policies on resources (JSON) vs GCP roles bound to principals. Mindset shift, not a hard change.
  • Regions/AZs vs regions/zones: similar; data residency rules differ per cloud.
  • Billing: AWS and GCP both consumption-based, but warehouse pricing differs sharply (Redshift = reserved cluster compute; BigQuery = per-byte-scanned analysis + storage). Migration changes the cost shape and requires query redesign to stay cheap.
  • Networking: VPC + security groups → VPC + firewall rules; PrivateLink → Private Service Connect.

Dual-Cloud Patterns

Not every migration is "rip out AWS." Many teams run dual-cloud: data lives in both (via replication), or GCP is used for analytics while AWS remains the operational source. Tools like BigQuery Omni and GCS's S3/Azure interop make reading AWS S3 data from BigQuery possible without copying. Decide your pattern — full migration, parallel run, or dual-cloud — before touching infrastructure.
