13. AWS to GCP Migration in Practice

Chapter 13

Migration Strategies

There are four levels of migration, in increasing order of change:

StrategyApproachEffortBenefit
Lift and shiftSame architecture, same scripts, GCP services swapped one-for-oneLowFast; limited cloud-native gains
Re-platformUse managed services (S3→GCS, Redshift→BigQuery) with code translationMediumOperational simplicity, right tools
Re-architectRedesign pipelines for serverless/ELT (Composer + dbt + BigQuery)HighFull value: cost, scale, speed
RebuildNew data platform from scratch on GCPHighestCleanest outcome; most risk

Most successful migrations do re-platform first, re-architect gradually. Move data and SQL now; optimize architecture in waves.

Phase 0: Discovery and Inventory

  • Inventory all data sources: S3 buckets (sizes, classes), Redshift tables (row counts, sizes, dependencies), Glue jobs, EMR workloads, streaming streams, and downstream consumers.
  • Map dependencies: which tables feed which dashboards, models, and reports.
  • Assess data volume and growth; estimate GCP storage and query costs.
  • Identify blockers: data residency requirements, encryption keys, third-party tool integrations, existing SLAs.

Phase 1: Prepare the Target

  • Create GCP project hierarchy with dev/staging/prod isolation.
  • Design IAM: service accounts per workload, least privilege.
  • Create GCS buckets matching your S3 layout (or better — a bronze/silver/gold design).
  • Provision BigQuery datasets with partitioning/clustering plans.
  • Set up Cloud Composer (or port MWAA DAGs) and the CI/CD pipeline for DAGs and dbt.

Phase 2: Move the Data

S3 → GCS

Options, in order of preference:

  • Storage Transfer Service — the managed, resumable service for copying S3→GCS (handles huge volumes, scheduling, and progress tracking).
  • gsutil rsync — simple CLI sync for smaller, one-time transfers.
  • BigQuery Omni / interop — read S3 from BigQuery directly when full copy isn't needed yet.
# One-time S3→GCS sync
gsutil -m rsync -r s3://my-bucket/raw gs://my-bucket/raw
# (or set up Storage Transfer Service with a schedule for ongoing sync)

Redshift → BigQuery

  1. UNLOAD Redshift tables to S3 as Parquet (or CSV for non-Parquet-able types).
  2. Transfer S3 → GCS.
  3. Load into BigQuery via bq load or the Data Transfer Service.
  4. Migrate views/models as BigQuery SQL; replace DISTKEY/SORTKEY with partitioning/clustering.
-- Redshift: unload to Parquet
UNLOAD ('SELECT * FROM analytics.orders')
TO 's3://bucket/unload/orders'
IAM_ROLE 'arn:aws:iam::...:role/UnloadRole'
FORMAT AS PARQUET PARALLEL OFF;

-- BigQuery: load the Parquet
bq load --source_format=PARQUET \
  myproj.analytics.orders \
  gs://bucket/unload/orders/*.parquet

Glue / EMR → Dataproc

  • Port Glue PySpark scripts to Dataproc jobs: change s3:// → gs://, replace Glue DynamicFrame idioms with standard Spark DataFrames where possible, and submit via Composer's DataprocSubmitPySparkJobOperator.
  • Migrate Hive tables/metastore via Dataproc Metastore or re-create schemas in BigQuery.
  • Use ephemeral clusters to control cost from day one.

Phase 3: Migrate the Pipelines and Orchestration

  • MWAA → Cloud Composer: port DAGs, swap AWS operators for Google providers, move connections to Secret Manager backend.
  • Data Pipeline / Step Functions → Composer: rewrite the orchestration as Airflow DAGs.
  • Glue triggers / cron → Composer: schedule loads and transformations centrally.
  • dbt: switch the adapter from dbt-redshift to dbt-bigquery; most models run unchanged if SQL is portable (watch for Redshift-specific functions).

Phase 4: Validation and Cutover

  • Parallel run: run both platforms for a period and reconcile outputs (row counts, sums, freshness) before switching consumers.
  • Reconciliation queries: compare key metrics table-by-table.
  • Cutover window: freeze writes, sync the final delta, flip DNS/consumer connections, and monitor aggressively.
  • Rollback plan: keep the AWS environment alive for 1-2 weeks (or per SLA) with a tested way to flip back.

Cost Control During Migration

  • Run parallel platforms only as long as needed — double cost is temporary.
  • Archive the old platform after cutover (don't keep paying for idle Redshift).
  • Design BigQuery tables with partitioning/clustering to keep query costs low from day one.
  • Monitor spend weekly during the transition.
Top migration mistakes: (1) copying Redshift's distribution-key design blindly into BigQuery; (2) forgetting data residency/compliance before moving; (3) migrating SQL that uses vendor-specific functions without translation; (4) no reconciliation step — "we think it's the same data"; (5) decommissioning AWS before the GCP pipeline has proven itself under real traffic.

Case Study: A Realistic Migration

  • Before (AWS): S3 raw files → Glue PySpark jobs → Redshift; MWAA schedules; dbt-redshift models; Tableau reads Redshift.
  • Migration: Storage Transfer Service copies S3→GCS; Glue jobs ported to Dataproc ephemeral clusters; Redshift unloaded to Parquet and loaded into partitioned BigQuery tables; dbt adapter switched to BigQuery; MWAA DAGs moved to Composer; Tableau pointed at BigQuery.
  • After (GCP): GCS bronze lake → Composer-orchestrated Dataproc for heavy transforms + dbt for modeling → BigQuery gold → Looker/Tableau.
  • Outcome: infrastructure removed (no clusters to size), faster ad-hoc analytics, and cost shifted from idle cluster hours to per-use.

Cloud Migration Framework (Google's 4 R's + T)

Google's guidance: Rehost (lift-shift), Replatform (swap services), Refactor (re-architect), Rebuild, or Retire (decommission) applications — and Retain the ones that must stay. Apply it per workload, not to the whole estate at once.
