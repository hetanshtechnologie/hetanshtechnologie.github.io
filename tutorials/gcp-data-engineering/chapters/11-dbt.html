11. dbt: The Data Build Tool

Chapter 11

What is dbt?

dbt (data build tool) is the industry-standard tool for transformations inside the warehouse — the "T" of ELT. Instead of writing transformation code in Spark or scripts, dbt lets you define transformations as SQL models, version-controlled in git, with automatic dependency management, testing, and documentation. It connects to BigQuery (and Redshift, Snowflake, Postgres, etc.), compiles your models, and runs them in dependency order.

dbt is the tool that made ELT and "analytics engineering" a real discipline: transformations become reviewable, testable code that lives with the team.

Core Concepts

ConceptDescription
ModelA SQL file (.sql) that defines a table or view — the core unit of transformation
MaterializationHow a model is built: view, table, incremental, ephemeral
SeedA CSV loaded as a table (for small reference data)
SnapshotType-2 history of slowly changing data
TestAssertions about data quality (unique, not_null, relationships, custom)
SourceExternal tables dbt reads but doesn't own
Macro / JinjaTemplating for DRY SQL (loops, conditionals, reusable logic)
PackageReusable macros/models shared across projects (e.g., dbt-utils)

Project Structure

my_project/
├── dbt_project.yml          # project config, model paths, materializations
├── profiles.yml             # connection profiles (targets: dev/prod)
├── models/
│   ├── staging/             # stg_* models: clean, rename, standardize
│   ├── marts/               # business-ready models
│   └── sources.yml          # declares source tables
├── seeds/                   # CSV reference data
├── tests/                   # custom generic tests
├── snapshots/               # type-2 history models
└── macros/                  # reusable Jinja macros

A First Model

-- models/staging/stg_orders.sql
SELECT
  order_id,
  customer_id,
  TIMESTAMP(order_ts) AS order_ts,
  SAFE_CAST(total_amount AS NUMERIC) AS total_amount
FROM {{ source('sales', 'orders') }}
WHERE order_ts IS NOT NULL
# models/marts/marketing/customer_revenue.sql
-- This model depends on stg_orders automatically
WITH orders AS (
  SELECT * FROM {{ ref('stg_orders') }}
)
SELECT
  customer_id,
  DATE(order_ts) AS day,
  SUM(total_amount) AS revenue
FROM orders
GROUP BY customer_id, DATE(order_ts)

{{ ref() }} is the magic: dbt parses these to build the dependency graph and runs models in the correct order. {{ source() }} declares upstream data sources with tests and freshness checks.

Materializations

MaterializationBehaviorUse When
viewA view; re-queries upstream each timeLightweight, cheap, staging
tableBuilt as a table each runModels used repeatedly or with heavy logic
incrementalBuilds full first time, then inserts/merges new rowsLarge append-only or slowly changing data
ephemeralInlined into dependents; not materializedReusable logic that shouldn't exist as a table
# dbt_project.yml — set default materialization
models:
  my_project:
    staging:
      +materialized: view
    marts:
      +materialized: table

Incremental Models in BigQuery

{{
  config(
    materialized='incremental',
    partition_by={'field': 'order_date', 'data_type': 'date'},
    cluster_by=['customer_id']
  )
}}

SELECT
  order_id, customer_id, order_ts, total_amount,
  DATE(order_ts) AS order_date
FROM {{ source('sales', 'orders') }}
WHERE order_ts IS NOT NULL
{% if is_incremental() %}
  AND order_ts > (SELECT MAX(order_ts) FROM {{ this }})
{% endif %}

The is_incremental() guard adds the watermark predicate only on incremental runs, so the first run builds full history and later runs only process new data. Combined with BigQuery partitioning, incremental models are the standard for large tables.

Tests: Data Quality as Code

# models/marts/marketing/_customer_revenue.yml
version: 2
models:
  - name: customer_revenue
    columns:
      - name: customer_id
        tests:
          - not_null
          - unique
      - name: revenue
        tests:
          - not_null
    tests:
      - dbt_utils.accepted_range:
          column_name: revenue
          min_value: 0
# Source freshness — alert if a source stops updating
sources:
  - name: sales
    tables:
      - name: orders
        freshness:
          warn_after: {count: 24, period: hour}
          error_after: {count: 48, period: hour}
        loaded_at_field: order_ts

dbt test runs every configured assertion. Custom generic tests and singular tests let you encode arbitrary business rules.

Jinja and Macros

Jinja templates make models DRY — generate SQL for many tables, handle environments, and reuse logic:

-- macros/generate_schema_name.sql — standard multi-env schema handling
{% macro generate_schema_name(custom_schema_name, node) -%}
  {% if target.name == 'prod' and custom_schema_name %}
    {{ custom_schema_name | trim }}
  {% elif custom_schema_name %}
    {{ target.schema }}_{{ custom_schema_name | trim }}
  {% else %}
    {{ target.schema }}
  {% endif %}
{%- endmacro %}
Guidance: start with plain SQL models and add Jinja only when repetition actually hurts. Over-templating makes models unreadable. The dbt-utils package covers most common needs (pivot, date spine, surrogate keys) without writing custom macros.

Seeds and Snapshots

  • Seeds: CSV files loaded with dbt seed — ideal for small mapping/reference tables.
  • Snapshots: type-2 slowly-changing-dimension handling built in — track history of dimension attributes over time (e.g., customer tier changes).

dbt + BigQuery + Airflow Together

The production pattern on GCP:

  1. Airflow/Composer schedules: load raw data → BigQuery (bronze).
  2. Composer triggers dbt run (in a container or worker) building silver/gold models.
  3. Composer runs dbt test after the run; failure blocks downstream consumers.
  4. dbt docs (lineage graph, catalog) published for the team.

dbt integrates with BigQuery via the dbt-bigquery adapter, which supports partitions, clustering, table/clone materializations, and BigQuery-specific incremental strategies (merge, insert_overwrite).

dbt vs Alternatives

ToolApproachTrade-off
dbtSQL transformations, code-first, warehouse-centricRequires a warehouse; SQL only
Spark/PySparkDistributed transforms outside the warehouseMore power, more infrastructure, slower iteration
DataformGCP-native SQL transformation (now part of BigQuery tooling)Closer Google integration, smaller ecosystem
SQLMesh / TPCAlternative transformation frameworksNewer; dbt has the larger community

Use dbt for everything that can live as SQL in BigQuery. Reserve Spark for complex, non-SQL, or very-large-scale processing. This split — "SQL if possible, Spark when needed" — is the modern default.

Getting Started Checklist

  • Install dbt-core + dbt-bigquery; configure profiles.yml with dev/prod targets.
  • Declare sources; add freshness checks.
  • Build a staging layer (stg_* views), then marts (tables).
  • Add tests to every column that matters.
  • Version control everything; run dbt in CI on a dev database.
  • Generate docs and share lineage.
Practice Task: Create a dbt project against the public dataset (or a small dataset you load into BigQuery). Build: (1) two staging models that clean sources, (2) one incremental fact model partitioned by date, (3) one dimension model with a seed, (4) tests (not_null, unique, accepted_values), (5) a snapshot of a slowly-changing dimension. Run dbt build, fix failures, and review the docs site with its lineage graph.
