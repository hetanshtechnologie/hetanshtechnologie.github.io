3. BigQuery Fundamentals

Chapter 3

What is BigQuery?

BigQuery is Google Cloud's serverless, petabyte-scale data warehouse. "Serverless" means there are no servers to provision, patch, or scale: you write SQL, and Google's infrastructure runs it on a massively parallel compute fabric. You pay for what you query and store, not for capacity you reserve (unless you choose the flat-rate/slots model).

Architecture: Why It's Fast

BigQuery's speed comes from three Google-internal systems:

  • Colossus: the distributed file system that stores data in compressed, columnar format (Capacitor) on replicated storage. Storage is decoupled from compute.
  • Dremel: the query execution engine that shards queries across thousands of workers, giving near-linear scaling. This is what makes petabyte scans possible in seconds.
  • Jupiter: the high-speed network fabric connecting compute and storage — a single query can use over 1 Tbps of network bandwidth.

Two consequences shape everything you do: columnar storage (reading a few columns is much cheaper than reading whole rows) and separation of storage and compute (storing data is cheap; scanning it is what you pay for).

Loading Data into BigQuery

Several loading patterns:

  • Batch load jobs from GCS (Avro, Parquet, ORC, JSON, CSV) — fast, atomic, recommended.
  • Streaming inserts (or the newer BigQuery Storage Write API) for near-real-time.
  • Data Transfer Service for Google services (Google Ads, Ad Manager, etc.).
  • External tables that query files in GCS directly without loading (see next chapter).
# Load from GCS using bq
bq load --source_format=PARQUET \
  myproj.analytics.orders \
  gs://my-bucket/orders/*.parquet \
  orders_schema.json

BigQuery SQL Essentials

BigQuery uses GoogleSQL (ANSI-compliant). Key syntax points:

-- Basic query with SELECT
SELECT
  order_id,
  customer_id,
  total_amount
FROM
  `myproj.analytics.orders`
WHERE
  order_date >= '2026-01-01'
ORDER BY
  order_id DESC
LIMIT 100;

-- Aggregation with GROUP BY
SELECT
  DATE(order_ts) AS day,
  COUNT(*) AS orders,
  SUM(total_amount) AS revenue
FROM
  `myproj.analytics.orders`
WHERE
  order_ts >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
GROUP BY
  day
ORDER BY
  day;
  • Backticks around fully-qualified table names containing project/dataset.
  • Support for structs, arrays, JSON, geography, and ML types.
  • Window functions, CTEs (WITH), and scripting (DECLARE, FOR, IF) for multi-step logic.

Partitioning: The #1 Cost and Performance Lever

Partitioning physically divides a table into segments by a column (usually a date or timestamp). Queries that filter on the partition column scan only the relevant segments instead of the whole table — dramatically cutting cost and improving speed.

  • Partition by DATE/TIMESTAMP column, ingestion time (_PARTITIONTIME), or an integer range.
  • Daily is most common; hourly and monthly are possible.
  • Partition pruning happens automatically when the WHERE clause filters on the partition column.
CREATE TABLE myproj.analytics.orders (
  order_id INT64,
  order_ts TIMESTAMP,
  total_amount NUMERIC
)
PARTITION BY DATE(order_ts)
OPTIONS (partition_expiration_days = 365);

-- This query scans only the single day partition:
SELECT COUNT(*) FROM myproj.analytics.orders
WHERE DATE(order_ts) = '2026-08-01';

Clustering

Clustering sorts data within partitions by one or more columns and stores them in blocks by sort key. It helps when queries filter on non-partition columns, and it helps join/group performance. Clustering adds no extra storage cost and can substantially reduce bytes scanned for selective filters on the cluster columns.

CREATE TABLE myproj.analytics.orders
PARTITION BY DATE(order_ts)
CLUSTER BY customer_id
OPTIONS (partition_expiration_days = 365);
Rule of thumb: Partition by a high-cardinality time column used in most queries; cluster by columns used in filters and joins (customer, product, region). Keep cardinality in mind — clustering on a near-unique column like order_id provides little benefit.

Pricing Model

BigQuery bills two things:

  • Analysis (query) cost: on-demand pricing charges per TiB of data scanned by each query. Filter early, partition, cluster, and select only needed columns to control this.
  • Storage cost: per GB per month, with a sliding discount as tables age. Active (last modified 90 days) is full price; long-term storage is cheaper.
# Estimate bytes a query will scan (dry run)
bq query --dry_run \
  "SELECT * FROM myproj.analytics.orders WHERE DATE(order_ts) = '2026-08-01'"

BigQuery also supports flat-rate pricing (commit to slots) for predictable heavy usage. As of modern pricing, you can also use editions (Standard, Enterprise, Enterprise Plus) that bundle features like BI Engine and multi-query statements with slot commitments.

Materialized Views and Approximate Aggregations

  • Materialized views: precomputed results refreshed automatically; the engine serves queries from them when possible. Great for repeated aggregates over big tables.
  • Approximate functions: APPROX_COUNT_DISTINCT, HyperLogLog++ — near-exact results at a fraction of the cost for large distinct counts.

Query Performance Best Practices

  • Select only columns you need; avoid SELECT * in production.
  • Filter on partition and cluster columns.
  • Push down predicates and joins (BigQuery does this automatically with the right table design).
  • Use WITH CTEs sparingly — each reference may be materialized.
  • Use IN over OR chains; prefer WHERE col = value over functions on the column that block pruning.
  • Limit heavy joins; use denormalization (arrays/structs) where analytics patterns demand it.
Anti-pattern: Wrapping the partition column in a function — e.g., WHERE DATE(order_ts) = '2026-08-01' on an unpartitioned table scans everything. On a partitioned table it prunes fine; on an unpartitioned table the function prevents any columnar pruning. Design partitions first.
Practice Task: Using the public dataset (e.g., bigquery-public-data.samples.gsod or any public dataset you choose): (1) write a query that counts rows by date and confirm the bytes scanned, (2) create a partitioned, clustered copy of a small public table, (3) run the same query against the raw and the optimized copy and compare bytes processed. Document the savings.
