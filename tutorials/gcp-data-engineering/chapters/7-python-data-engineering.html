7. Python for Data Engineering

Chapter 7

Why Python?

Python is the de facto language of data engineering. It is the scripting layer for orchestration (Airflow DAGs are Python), distributed processing (PySpark), ingestion (client libraries), transformation (dbt custom tests, Airbyte), and ML. A strong Python foundation multiplies everything else in this book.

Python Fundamentals You Actually Use

  • Data structures: dicts, lists, tuples, sets; comprehension and generator patterns for transforming data.
  • Functions and typing: well-typed signatures with type hints; dataclasses for row-like structures.
  • Iterators and lazy processing: reading files line-by-line without loading all into memory.
  • Exceptions and logging: structured try/except, the logging module, never bare except.
  • Context managers: with open(...) for safe resource handling.
  • Virtual environments and dependency management: venv/pip and lock files (uv, pip-tools).
from dataclasses import dataclass
from typing import Iterator
import logging

logger = logging.getLogger(__name__)

@dataclass
class OrderRow:
    order_id: int
    customer_id: int
    amount: float

def parse_orders(path: str) -> Iterator[OrderRow]:
    with open(path) as f:
        for line in f:
            parts = line.strip().split(",")
            try:
                yield OrderRow(int(parts[0]), int(parts[1]), float(parts[2]))
            except (ValueError, IndexError) as e:
                logger.warning("Skipping bad line %r: %s", line, e)

# Usage
for row in parse_orders("orders.csv"):
    print(row.order_id, row.amount)

Cloud Client Libraries and Application Default Credentials

The Google Cloud Python libraries authenticate via Application Default Credentials (ADC): on GCE/GKE/Airflow workers they use the metadata server; locally they use gcloud auth application-default login; in CI they use service account keys or Workload Identity Federation.

from google.cloud import storage, bigquery

# GCS
client = storage.Client(project="my-data-project")
bucket = client.bucket("my-bucket")
blob = bucket.blob("raw/orders_20260801.csv")
blob.upload_from_filename("orders_20260801.csv")

# BigQuery: run a query
bq = bigquery.Client()
query_job = bq.query("SELECT COUNT(*) AS n FROM myproj.analytics.orders")
print(query_job.result().to_dataframe())

Writing Robust Scripts

  • Entry points with argparse: every job takes parameters (date, environment, project) — no hardcoded values.
  • Retries: wrap flaky API calls in retry logic with exponential backoff (tenacity or manual).
  • Idempotency: the script should produce the same result whether run once or re-run (overwrite, upsert, or partitioned writes).
  • Logging: structured, queryable logs with enough context to debug (job id, parameters, timings).
  • Exit codes: fail loudly with non-zero exit codes so the orchestrator (Airflow) can detect and retry.
import argparse
import logging
from google.cloud import bigquery

logger = logging.getLogger("load_orders")
logging.basicConfig(level=logging.INFO)

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--source", required=True)
    parser.add_argument("--destination", required=True)
    parser.add_argument("--date", required=True)
    args = parser.parse_args()

    logger.info("Starting load: %s -> %s (%s)", args.source, args.destination, args.date)
    client = bigquery.Client()
    # ... do the work ...
    logger.info("Completed")

if __name__ == "__main__":
    main()

Packaging for Dataproc and Composer

Distributed jobs should be packaged and versioned:

  • Build a wheel of your code (pip wheel .) and reference it in the Spark submit.
  • Ship a requirements.txt or container image with pinned versions for reproducibility.
  • Use Dataproc custom images or initialization actions to install your package on clusters.
  • For Cloud Composer, install custom Python packages into the environment or use an airflow worker with dependencies preloaded.
# Build and submit a packaged job to Dataproc
pip wheel --no-deps -w ./wheels .
gcloud dataproc jobs submit pyspark \
  --cluster=my-cluster --region=us-central1 \
  --py-files=gs://my-bucket/wheels/my_etl-1.0-py3-none-any.whl \
  gs://my-bucket/src/main.py -- --date=2026-08-01

Testing and Code Quality

  • Unit-test pure logic with pytest; mock cloud clients for I/O paths.
  • Use mypy for type checking and ruff/black for style — cheap insurance on a shared codebase.
  • Run tests in CI (GitHub Actions / Cloud Build) on every push.
  • Test against real (small) cloud resources in a dev project before production.

Security in Python Data Code

  • Never commit secrets; use Secret Manager, environment variables, or Airflow connections.
  • Sanitize inputs; avoid eval/exec on external strings (dangerous in DAG code).
  • Use least-privilege service accounts; keep credentials out of logs (redact in logging).
  • Scan dependencies (pip-audit, Dependabot) for vulnerabilities.

Python + SQL: The Practical Combination

Most production data work is a mix: Python orchestrates, extracts, and glues; SQL transforms. dbt (Chapter 11) uses Python + Jinja to manage SQL models. PySpark gives SQL a distributed engine. Mastery means knowing when to reach for each — Python for control flow and I/O, SQL for set-based transformation.

Package it as a wheel and submit it to Dataproc. Note: use a dev project or the free tier to avoid costs.
