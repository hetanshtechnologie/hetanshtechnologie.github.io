4. BigQuery Advanced & Optimization

Chapter 4

Time Travel and Snapshots

BigQuery keeps deleted or overwritten data accessible for a rolling window (7 days by default, configurable). You can query the table as it existed at a point in time:

-- Query a table as of 1 hour ago
SELECT * FROM myproj.analytics.orders
FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR);

Table snapshots freeze a table at a point in time as a durable, cheap copy — ideal for disaster recovery, audit, and release management.

CREATE SNAPSHOT TABLE myproj.analytics.orders_snapshot_20260801
CLONE myproj.analytics.orders;

Cloning (via CREATE TABLE ... CLONE) creates a zero-copy reference that becomes a real table only when you write to it. This makes staging, dev environments, and "copy for analysis" nearly free until you modify them.

Streaming and Real-Time Data

For near-real-time ingestion BigQuery offers two paths:

  • Legacy streaming inserts (tabledata.insertAll): per-row inserts with 90-day retention of streaming buffer. Simpler but limited (no exactly-once, no automatic retry).
  • BigQuery Storage Write API: the modern path — high throughput, exactly-once semantics, schema auto-detection, and default-on transactionality. Use it for production streaming.

Recommended production architecture: Pub/Sub → Dataflow (or Dataproc streaming) → Storage Write API → BigQuery. Dataflow provides exactly-once processing, autoscaling, and backpressure handling.

External Tables and BigLake

BigQuery can query data that lives in Cloud Storage without loading it, using external tables. Modern capabilities:

  • BigLake tables: external tables over GCS (or AWS S3 / Azure ADLS) with BigQuery's query engine, row-level security, and fine-grained access. Great for lakehouse patterns and when you can't (or shouldn't) copy data into BigQuery.
  • Open table formats: BigQuery supports Apache Iceberg and Delta Lake tables, unifying lake and warehouse.
  • Query federation: query data in Cloud SQL, Spanner, and other sources without loading.
# Create an external table over Parquet files in GCS
CREATE OR REPLACE EXTERNAL TABLE myproj.analytics.ext_events
WITH CONNECTION myproj.us.ext_conn
OPTIONS (
  format = 'PARQUET',
  uris = ['gs://my-bucket/events/*.parquet']
);

BigQuery ML: ML in SQL

BigQuery ML (BQML) lets you train and run ML models using SQL — no separate ML platform needed for many use cases:

-- Train a linear regression model predicting order amount
CREATE OR REPLACE MODEL myproj.analytics.revenue_model
OPTIONS (model_type = 'LINEAR_REG', input_label_cols = ['total_amount']) AS
SELECT
  customer_tenure_days,
  order_count,
  total_amount
FROM myproj.analytics.customer_features;

-- Predict
SELECT * FROM ML.PREDICT(MODEL myproj.analytics.revenue_model,
  (SELECT customer_tenure_days, order_count, 0 AS total_amount
   FROM myproj.analytics.new_customers));

BQML supports linear/logistic regression, classification, clustering (k-means), time series (ARIMA), matrix factorization, and importing external models (TensorFlow, XGBoost). It is the fastest way to get an ML model from a warehouse table to production without leaving SQL.

Performance Optimization: Slots and Query Shape

BigQuery executes queries in stages. Optimization focuses on reducing bytes scanned and avoiding skew:

  • Predicate pushdown: filter as early as possible; the engine pushes filters down to storage.
  • Join order: put the largest table first; the engine chooses join strategy automatically, but skewed keys cause stragglers.
  • Avoid cross joins; use window functions where possible.
  • Use approximate aggregates for huge distinct counts.
  • Cache: BigQuery caches query results (for 24h) — identical queries are free if cached.
  • BI Engine: in-memory acceleration for Looker/dashboard workloads.
Optimization workflow: (1) dry-run to see bytes scanned, (2) check the query plan's "most expensive stage", (3) eliminate unnecessary columns and filters, (4) verify partitioning/clustering match the filter pattern, (5) consider a materialized view for repeated aggregates.

Cost Optimization Playbook

  • Partition + cluster every large table; expire partitions you don't need.
  • Prefer Parquet/Avro over JSON/CSV for loads (smaller, faster).
  • Use flat-rate slots for steady heavy workloads; on-demand for spiky.
  • Set dataset-level default table expiration for non-production data.
  • Monitor with INFORMATION_SCHEMA.JOBS_BY_PROJECT and tag expensive queries.
  • Use data governance (Dataplex) to flag unused tables and drop them.
# Find your most expensive queries (bytes scanned)
SELECT
  query,
  total_bytes_processed / 1024 / 1024 / 1024 AS gb_scanned,
  creation_time
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE job_type = 'QUERY'
ORDER BY total_bytes_processed DESC
LIMIT 20;

Table Cloning for Development

A common production pattern: clone production tables into a dev project (zero-cost until written), develop and test dbt models or queries there, and never pay to store duplicated data.

bq cp --no_clobber \
  source_project.analytics.orders \
  dev_project.analytics.orders_clone

Data Governance and Lineage

  • Data Catalog: searchable metadata, tags, and lineage (via Dataplex lineage).
  • Dataplex: central data governance — policies, quality checks, lineage, and lifecycle.
  • Row-level and column-level security: apply access policies on BigLake tables.
  • Masking rules: control column exposure by role.
Practice Task: Using the public dataset of your choice: (1) create a clone of a table and run a query on the clone — verify it is zero-cost until written; (2) query a table with FOR SYSTEM_TIME to see a historical version; (3) create a simple BQML linear regression or ARIMA model and run ML.PREDICT; (4) use INFORMATION_SCHEMA to identify the top 3 most expensive queries in your session and propose one optimization for each.
