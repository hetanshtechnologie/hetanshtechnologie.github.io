Core Platform Concepts

Before building pipelines, you must understand GCP's organizational model:

  • Organization: the root of your GCP hierarchy (your company).
  • Projects: the fundamental unit of isolation and billing. Resources (buckets, datasets, clusters) live inside projects. Every API call is scoped to a project.
  • Folders: organize projects hierarchically (e.g., by business unit, environment).
  • Regions and zones: resources are created in a specific location. Data residency and latency depend on this choice.
  • IAM (Identity and Access Management): who (principal) can do what (role) on which resource. Principles include least privilege and separation of duties.
# Setting project and region in gcloud
gcloud config set project my-data-project
gcloud config set compute/region us-central1
gcloud config set compute/zone us-central1-a

Service Accounts and Application Default Credentials

Pipelines rarely authenticate as a human. They use service accounts — machine identities with IAM roles. Best practices:

  • One service account per workload/pipeline, with least-privilege roles.
  • Prefer short-lived credentials; rotate keys; use workload identity federation where possible.
  • Never store keys in code or DAGs; use the metadata server (on GCE/GKE), Workload Identity (on GKE), or a secret manager for keys.

Data Residency and Regions

Choosing regions matters for:

  • Compliance: some data must stay in a country/region (GDPR, industry rules).
  • Performance: keep compute near storage near consumers.
  • Availability: multi-region storage options replicate across regions.
  • Cost: data egress (leaving GCP or crossing regions) is billable — keep data movement inside a region when possible.

BigQuery has regional and multi-regional locations (e.g., us, eu). Cloud Storage supports regional, dual-region, and multi-region classes.

Cost Model Essentials

GCP pricing is consumption-based. For data engineering the biggest cost drivers are:

  • BigQuery: you pay for analysis (queries) and storage. The flat-rate (slot) option is for heavy, predictable usage; on-demand pricing charges per amount of data scanned per query. Designing for fewer scanned bytes is a core optimization skill.
  • Dataproc: you pay for cluster VMs (per-vCPU/hour) plus a small Dataproc surcharge. Ephemeral clusters (create for the job, delete after) keep costs low.
  • Cloud Storage: per GB stored per month, by storage class (Standard, Nearline, Coldline, Archive). Data access has additional charges.
  • Cloud Composer: a monthly base cost plus worker/scheduler VMs and storage.
  • Network egress: data leaving GCP is the hidden cost — minimize unnecessary egress.
Cost mindset: In the cloud, you pay for what you use, so engineering decisions (schema design, partition granularity, query patterns, cluster sizing) directly move the bill. A "cost-aware" data engineer is more valuable than one who just writes working SQL.

Security and Networking for Data

  • VPC: private networks for Dataproc clusters, Composer environments, and BigQuery (via private service connect).
  • Cloud KMS / CMEK: customer-managed encryption keys for buckets, datasets, and clusters.
  • Data Loss Prevention (DLP): detect and redact PII in transit.
  • VPC Service Controls: restrict data exfiltration — important for regulated data.
  • Logging and monitoring: Cloud Logging + Cloud Monitoring for pipeline telemetry; audit logs for governance.

A Reference Data Architecture on GCP

Sources (SaaS, DBs, files, events)
   │
   ├─ batch files ──────────────► Cloud Storage (GCS) ──► BigQuery (load / external)
   │
   ├─ streaming events ─────────► Pub/Sub ──► Dataflow ──► BigQuery / Bigtable
   │
   └─ database changes ─────────► CDC tool ─► Pub/Sub ──► BigQuery

Cloud Composer (Airflow) orchestrates all scheduled steps.
dbt runs warehouse transformations; Looker/BI consume BigQuery.

This is the pattern most teams converge on: a lake in GCS, a warehouse in BigQuery, streaming through Pub/Sub + Dataflow, orchestration via Composer, and transformation via dbt or Spark.
