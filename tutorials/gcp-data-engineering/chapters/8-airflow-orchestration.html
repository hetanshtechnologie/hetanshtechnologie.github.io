8. Apache Airflow & Orchestration

Chapter 8

Why Orchestration?

A data platform is many jobs: loads, transformations, quality checks, model refreshes. If jobs are run by cron and people, dependencies break silently, retries are ad-hoc, and nothing is auditable. Workflow orchestration solves this: it schedules jobs, manages dependencies between them, retries failures, and records what ran when.

Apache Airflow is the industry-standard open-source orchestrator. It turns workflows into Python code (DAGs) with dependencies, schedules, retries, and monitoring. On GCP, Airflow is offered as the managed service Cloud Composer (next chapter).

Core Concepts

ConceptDescription
DAGDirected Acyclic Graph — the workflow definition in Python: tasks and their dependencies
TaskA single unit of work in a DAG (e.g., run one SQL query)
OperatorClass that defines what a task does (PythonOperator, BigQueryInsertJobOperator, DataprocSubmitJobOperator, etc.)
SensorSpecial task that waits for a condition (e.g., a file to appear in GCS)
SchedulerComponent that decides when tasks run based on schedule and dependencies
ExecutorRuns tasks (local, Celery, Kubernetes executor)
DAG runAn execution instance of a DAG for a specific schedule interval
Task instanceAn execution of one task in a specific DAG run

A Minimal DAG

# dags/hello_gcp.py
from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.providers.google.cloud.operators.bigquery import BigQueryInsertJobOperator

def say_hello():
    print("Hello from Airflow")

with DAG(
    dag_id="hello_gcp",
    start_date=datetime(2026, 1, 1),
    schedule="@daily",
    catchup=False,
    default_args={"retries": 2, "retry_delay": timedelta(minutes=5)},
) as dag:
    t1 = PythonOperator(task_id="say_hello", python_callable=say_hello)

    t2 = BigQueryInsertJobOperator(
        task_id="run_query",
        configuration={
            "query": {
                "query": "SELECT COUNT(*) FROM myproj.analytics.orders",
                "useLegacySql": False,
            }
        },
    )

    t1 >> t2   # t2 depends on t1

Schedule Semantics: Know Your Catchup

Airflow schedules by data interval: a run for day D executes after the interval closes (start at 00:00, runs at 00:05+). The start_date plus schedule defines which intervals run, and catchup determines whether missed past intervals are backfilled. The template variables {{ ds }} (data date) and {{ execution_date }} are the bread and butter for parameterizing jobs per day.

# Use the data interval date to build GCS paths
"gs://my-bucket/raw/orders/{{ ds }}/*.csv"
"{{ ds_nodash }}"  # e.g. 20260801
Common gotcha: catchup=True on a newly created DAG with a distant start_date can fire hundreds of runs at once. Set catchup=False or backfill deliberately. Also remember Airflow's default timezone is UTC — set timezone and start_date explicitly to avoid off-by-one-day surprises.

Operators for GCP

The apache-airflow-providers-google package provides operators for almost every GCP service. The ones data engineers use most:

  • BigQuery: BigQueryInsertJobOperator, BigQueryCreateEmptyDatasetOperator, BigQueryDeleteTableOperator.
  • Dataproc: DataprocCreateClusterOperator, DataprocSubmitPySparkJobOperator, DataprocSubmitSparkSqlJobOperator, DataprocDeleteClusterOperator — the ephemeral-cluster pattern.
  • Cloud Storage: GCSCreateBucketOperator, GCSObjectCreateSensor, GCSToBigQueryOperator, GCSToGCSOperator.
  • Dataflow: DataflowStartFlexTemplateOperator, DataflowCreateJavaJobOperator.
  • Pub/Sub: PubSubCreateSubscriptionOperator, PubSubPublishMessageOperator.
  • Cloud SQL: CloudSQLExecuteQueryOperator.

Sensors: Waiting for Conditions

from airflow.providers.google.cloud.sensors.gcs import GCSObjectExistenceSensor

wait_for_file = GCSObjectExistenceSensor(
    task_id="wait_for_orders_file",
    bucket="my-bucket",
    object="raw/orders/{{ ds }}.csv",
    timeout=6 * 60 * 60,
    poke_interval=60,
    mode="reschedule",
)

Sensors are essential when sources are unpredictable. Use mode="reschedule" to free worker slots while waiting.

Retries, Timeouts, and Error Handling

  • retries / retry_delay: per-task default for transient failures.
  • execution_timeout: kill a task that runs too long.
  • Branching: BranchPythonOperator lets the DAG take different paths based on a decision (e.g., skip downstream steps when no data arrived).
  • ShortCircuitOperator: stop downstream tasks conditionally.
  • SLAs / alerts: notify when tasks run too long or DAGs fail.
Design principle: DAGs should be idempotent — re-running a failed day must be safe. Write to date-partitioned destinations, use overwrite semantics, and make "rerun yesterday" the standard recovery procedure rather than manual patching.

DAG Patterns That Matter

  • Fan-in/fan-out: one task spawns many (map), they run in parallel, and results merge (reduce).
  • Checkpointing: a data-quality check between load and transform that fails the run early.
  • Dynamic DAGs: generate tasks from a list of configs — powerful but keep it simple; avoid over-engineering.
  • TaskGroups and SubDAGs: group related tasks visually (TaskGroups preferred over SubDAGs).
  • External sensors: wait on DAGs in other environments (ExternalTaskSensor) for cross-team dependencies.

Environment Isolation and Testing DAGs

  • Keep DAG code in git; CI tests: import the DAG (catches syntax/import errors), validate with airflow dags list, and run unit tests on helper functions.
  • Test with airflow tasks test <dag_id> <task_id> <date> on a local environment.
  • Use per-environment variables and Connections; never hardcode credentials.
  • Limit each DAG's blast radius: no monolithic DAGs with a hundred tasks that are hard to reason about.

Airflow remains the default choice on GCP because Cloud Composer is fully managed — you get Airflow without running the infrastructure.
