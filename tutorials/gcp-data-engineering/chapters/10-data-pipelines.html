10. Building Reliable Data Pipelines

Chapter 10

Reliability Is the Job

Anyone can write a query that works once. Data engineering is the discipline of making it work every day, on schedule, correctly, and observably. This chapter turns the pieces from earlier chapters — BigQuery, Dataproc, Airflow/Composer, Python — into a systematic approach to building pipelines that don't break (and when they do, fail loudly and recover cleanly).

Pipeline Design Patterns

PatternDescriptionWhen to Use
Incremental loadLoad only new/changed data (by timestamp or ID)Default for high-volume tables; minimizes cost and runtime
Full load / snapshotReplace the whole table each runSmall tables, dimensions, reference data
Append-only with partitionsAdd a new partition per run, never touch historyEvent/fact data, immutable logs
Merge (upsert)Insert new rows and update changed onesMutable operational data (orders, profiles)
Landing → staging → curatedLayered lake: raw, cleaned, modeledLakehouse architectures; keeps raw data for reprocessing

The Medallion / Layered Lake Pattern

Data lands raw, is cleaned, then is modeled for consumption:

  • Bronze (raw/landing): exactly as received, immutable, in GCS (Parquet/Avro/JSON).
  • Silver (cleaned/trusted): validated, deduplicated, standardized schema, still granular.
  • Gold (curated/consumption): aggregated, joined, business-ready for BI and ML.

This layering makes reprocessing safe (raw is never destroyed), makes lineage clear, and matches the dbt model philosophy (Chapter 11).

Idempotency: The Golden Rule

An operation is idempotent if running it twice has the same effect as running it once. Pipelines that fail partway and get re-run are inevitable, so every step must be idempotent:

  • Write to date-partitioned destinations; write with overwrite per partition.
  • Use merge/upsert instead of blind append for mutable data.
  • Deduplicate before load (or dedupe at read time in the modeling layer).
  • Avoid global "truncate table then load" patterns that break when the load fails.
# BigQuery: idempotent partition overwrite
bq query \
  --replace \
  --destination_table=myproj.analytics.orders_daily \
  --range_partitioning=order_date,0,1,1 \
  "SELECT ... FROM myproj.analytics.orders WHERE DATE(order_ts) = '{{ ds }}'"

Error Handling and Retry Strategy

  • Classify failures: transient (network blip, quota) → retry with backoff; permanent (bad schema, bad data) → fail loudly, alert, do not retry blindly.
  • In Airflow: task-level retries + retry_delay, plus trigger_rule for downstream handling.
  • Use dead-letter queues / quarantine tables for bad records instead of failing whole batches.
  • Log the input path, job parameters, and error in every failure so debugging starts fast.

Data Quality Checks

Automated checks are the difference between "pipeline ran" and "pipeline ran correctly." Build a checks layer between stages:

  • Completeness: row counts match expected ranges; no unexpected nulls.
  • Freshness: data for the expected date/time actually arrived.
  • Uniqueness: primary keys are unique.
  • Validity: values within allowed domains (dates parse, amounts positive).
  • Consistency: sums match upstream vs downstream (e.g., revenue in staging equals revenue in gold).
-- Example: freshness + count check as a SQL query that must return 0 rows
SELECT 'missing partition' AS check, 1 AS flag
WHERE NOT EXISTS (
  SELECT 1 FROM myproj.analytics.orders
  WHERE DATE(order_ts) = CURRENT_DATE - 1
);

dbt (next chapter) has built-in test types (unique, not_null, accepted_values, relationships) that formalize exactly these checks.

Observability: Logging, Monitoring, Lineage

  • Structured logs: JSON logs with job id, dates, counts, and durations; shipped to Cloud Logging.
  • Metrics: record row counts, bytes, run durations to Cloud Monitoring; alert on anomalies (a 50% drop in rows is an incident).
  • Alerting: Airflow failure alerts, freshness SLA alerts, quality-check failures.
  • Lineage: Dataplex lineage shows which job produced which table — essential for incident response and audits.
  • Dashboards: a "pipeline health" dashboard for the team (success/fail per DAG, MTTR for failures).

Testing Pipelines

  • Unit: pure functions, SQL snippets against small fixtures.
  • Integration: run a DAG against a dev BigQuery/GCS with sample data.
  • Contract tests: validate schemas between producer and consumer stages.
  • Replay/reconcile: re-run a completed day in a sandbox and diff outputs — catches non-determinism and drift.

Backfilling and Reprocessing

When logic changes, you must rebuild history. Design for it:

  • Parameterize every job by date (--start_date --end_date).
  • Keep raw (bronze) data so you can rebuild any layer.
  • Use Airflow backfill (airflow dags backfill or a trigger with start/end) for controlled reprocessing.
  • Prefer partition-level rebuilds over full-table rebuilds.

A Reference Reliable Pipeline

DAG: daily_orders_etl (schedule 06:00, data date {{ ds }})
  ├─ wait_for_raw_files (GCS sensor)
  ├─ load_raw (CSV → BigQuery bronze partition)
  ├─ quality_raw (row counts > 0, no null order_id)
  ├─ transform (dbt run / BigQuery SQL → silver + gold)
  ├─ quality_gold (sums reconcile, uniqueness on PK)
  └─ notify (success summary to Slack; on failure → alert + page)
Retries: 2 with 5-min backoff on load/transform; no retry on quality fail.
Idempotency: partition overwrite everywhere; merge for mutable tables.
Design review checklist: Is every step idempotent? Can I re-run one day without touching others? Do I alert on freshness and counts, not just failures? Is raw data preserved for rebuilds? Do checks run between stages, not just at the end? If yes to all, the pipeline will survive contact with reality.
