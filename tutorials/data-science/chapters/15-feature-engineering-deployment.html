15. Feature Engineering & Model Deployment

Chapter 15

Features Decide Performance

Better features usually beat better algorithms. Feature engineering is creating columns that make the pattern easier for the model to see: dates → weekday/holiday, IDs → counts/frequencies, free text → sentiment, raw numbers → ratios and interactions.

A Feature Engineering Toolkit

# Dates -> calendar features
df["weekday"]  = df["date"].dt.dayofweek
df["hour"]     = df["date"].dt.hour
df["is_weekend"] = df["weekday"] >= 5
df["month"]    = df["date"].dt.month

# Counts from IDs (frequency encoding)
df["city_freq"] = df["city"].map(df["city"].value_counts())

# Ratios & interactions
df["spend_per_ticket"] = df["spend"] / (df["support_tickets"] + 1)
df["spend_per_month"]  = df["spend"] / (df["tenure"] + 1)

# Aggregates (rolling features for time series)
df["spend_7d_avg"] = df.groupby("customer_id")["spend"].transform(lambda s: s.rolling(7).mean())
Target leakage in features: never create a feature from information that wouldn't be available at prediction time — e.g., "spend_next_month" as a feature, or a rolling average computed over the future. Leaky features make great offline scores and broken production systems.

sklearn Pipelines & ColumnTransformer

Combine preprocessing and modeling into one artifact that cannot leak:

from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.impute import SimpleImputer
from sklearn.ensemble import RandomForestRegressor

num_cols = ["age", "spend", "support_tickets"]
cat_cols = ["city", "plan"]

pre = ColumnTransformer([
    ("num", Pipeline([
        ("impute", SimpleImputer(strategy="median")),
        ("scale", StandardScaler())
    ]), num_cols),
    ("cat", OneHotEncoder(handle_unknown="ignore"), cat_cols)
])

model = Pipeline([
    ("pre", pre),
    ("rf", RandomForestRegressor(n_estimators=300, random_state=42))
])
model.fit(X_train, y_train)

This whole object can be saved with joblib and reused in production unchanged:

import joblib
joblib.dump(model, "model/spend_model.joblib")
# later / elsewhere:
loaded = joblib.load("model/spend_model.joblib")
prediction = loaded.predict(new_data)

Feature Stores

In a real product, the same features are needed for training and for live scoring. A feature store (Feast, Databricks Feature Store, BigQuery ML features) is the shared catalog that serves both, so online and offline features never drift apart.

ProblemFeature store answer
Same feature computed differently in train vs serveOne definition, served everywhere
Stale features in productionOnline/offline consistency checks
Teams re-inventing the same featuresShared, documented catalog with owners

# A minimal real-time serving API (FastAPI)
# pip install fastapi uvicorn joblib
from fastapi import FastAPI
from pydantic import BaseModel
import joblib, pandas as pd

app = FastAPI()
model = joblib.load("model/spend_model.joblib")

class Input(BaseModel):
    age: float
    spend: float
    support_tickets: float
    city: str
    plan: str

@app.post("/predict")
def predict(x: Input):
    row = pd.DataFrame([x.model_dump()])
    return {"predicted_spend": float(model.predict(row)[0])}

Monitoring in Production

Deploying is the beginning, not the end. Monitor:

  • Data drift — the input distribution changes over time (compare live inputs to training data).
  • Concept drift — the relationship you learned stops holding (retrain schedules, performance probes).
  • Performance — when ground truth arrives late, track it over time.
  • Operational health — latency, error rates, and staleness of features.

Tools: Evidently (data drift), Prometheus/Grafana (operations), simple dashboards over logged predictions.
