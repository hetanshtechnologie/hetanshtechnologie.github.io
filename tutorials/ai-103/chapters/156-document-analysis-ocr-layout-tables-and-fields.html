Document Analysis - OCR, Layout, Tables, and Fields

Document analysis is the work of converting a page — whether it is a born-digital PDF or a photograph of a paper form — into structured text and data. Azure Content Understanding approaches this in layers. First it recognizes the characters on the page (OCR). Then it understands how those characters are organized (layout). It detects tables and reconstructs their structure, and finally, when you define fields, it pulls out the specific values your application cares about. Each layer builds on the one before it, and together they turn a messy document into clean JSON.

The Layers of Document Analysis

Think of document analysis as a pipeline with four stages. Later stages depend on the results of earlier ones, and errors tend to flow forward — if the OCR is wrong, the fields extracted from that text will be wrong too.

OCR: Recognizing the Text

Optical Character Recognition (OCR) reads the visible characters in an image or scanned page. The model finds words, determines their position on the page as bounding boxes, and estimates their order. The result includes the text itself plus spatial metadata: each word and line carries coordinates so you know exactly where it appeared on the page.

Content Understanding handles both typed and printed text and works with digital documents, where the text is already embedded in the file, and scanned images, where the text must be read from pixels. The service also recognizes handwriting to a degree, which makes it useful for forms that people fill out by hand.

For digital PDFs the underlying text is usually perfect, but OCR is still valuable because it gives you geometry — where each word sits on the page. That geometry is what enables layout analysis, table reconstruction, and bounding-box-level field extraction.

Layout: Understanding Structure

Raw text is not enough. The phrase "Total: $1,250" only means something if you know that "Total" is a label and "$1,250" is the value next to it. Layout analysis groups OCR output into meaningful blocks: paragraphs, section headings, list items, and standalone figures. It also determines the reading order of the page, so the extracted text reads top to bottom and left to right the way a human would read it.

For multi-page documents, layout analysis keeps the structure consistent across pages. Each paragraph is associated with the page it came from, which matters when you later chunk the text for search indexing and want to preserve document provenance.

Tables: Reconstructing Grids

Tables are the hardest structure to read automatically. In a PDF, a table often has no real grid — just text positioned at different coordinates — so the analyzer must infer which text belongs to which row and column. Content Understanding reconstructs tables by grouping nearby cells, identifying header rows, and spanning them into a grid with row and column indices. The extracted table can be delivered as structured data your code can convert into arrays, data frames, or database rows.

Multi-page tables are a known challenge: a table can split across page boundaries, and the analyzer must keep the column structure consistent. Pro mode is designed to handle these harder cases more reliably, and a later chapter in the course covers advanced parsing for exactly this scenario.

Fields: Extracting the Values You Need

Fields are the top layer and the part most applications actually consume. A field is a named data point you want extracted, such as invoice_number, vendor_name, or amount_due. In a custom document analyzer you define the list of fields and their expected types — string, number, date, currency, and so on — and the analyzer searches the document for each one, returning the value and the region of the page where it was found.

Field extraction relies on everything below it. The analyzer uses the recognized text and layout to locate the label, associates the value with it, and applies type rules to validate the result. Because the fields are defined by you, the output is exactly the schema your downstream system expects.

A field's confidence score tells you how sure the model is that it extracted the right value. Low-confidence fields are worth flagging for human review. In production pipelines it is common to accept high-confidence values automatically and route the rest to a manual queue.

A Practical View of the Output

When a document analyzer finishes, you receive a JSON document containing the recognized content. At a high level the response includes:

  • Per-page results with text and coordinates.
  • Paragraphs, headings, and figures organized in reading order.
  • Reconstructed tables with cell positions and row/column indices.
  • The extracted field values with confidence scores and the bounding boxes where each value was found.

That combination — text plus geometry plus structure plus typed values — is what makes the output usable by real applications rather than just readable by a human.

Summary

Document analysis in Azure Content Understanding works in layers: OCR provides the text, layout gives it structure, tables restore the grid data, and fields extract the specific values your system needs. Each layer feeds the next, and the final JSON contains both the raw content and the spatial metadata that makes it actionable.
