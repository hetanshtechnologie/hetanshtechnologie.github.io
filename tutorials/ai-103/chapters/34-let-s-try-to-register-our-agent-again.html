Let's try to register our agent again

If you ran the previous lab's script twice, you now have two agents named trip-planner. That is the natural result of a script that only knows how to create. Real registration code must be safe to run again and again — the same outcome each time, no duplicates, no errors. In this chapter you will think about registration as an idempotent operation and change your script to "register our agent again" correctly.

The Problem with Create-Only Registration

A registration script with a single create_agent call behaves like a button that is only safe to press once. Rerunning it duplicates the agent, which pollutes the project, wastes storage, and confuses anyone later looking for "the" trip-planner agent. The failure mode is silent: nothing errors, you just end up with a pile of near-identical agents.

The fix is to decide what register means. Instead of "create one now," the script should mean "make sure exactly one agent with this name exists and has the right configuration." That is idempotency: running the operation any number of times produces the same end state.

The Register-Or-Reuse Pattern

The safest version of the pattern has three steps:

  1. Look up whether an agent with the target name already exists.
  2. Reuse it if it does, and optionally update its configuration.
  3. Create it only when nothing matching was found.

This turns the script from a fragile action into a repeatable tool that a team can run in any environment — a developer laptop, a staging pipeline, a fresh project — and trust to converge on the same state.

The pattern also makes deployment safe. If your project is deleted and recreated, the first registration run rebuilds the agent. If the project already contains it, the run simply confirms it and moves on. That resilience is what you want from infrastructure automation.

Updating vs. Replacing Configuration

Reusing an existing agent raises a second question: should you overwrite its instructions every run? For code-managed agents the answer is usually yes. The instructions in your repository are the source of truth, so each registration run should push the current instructions, model, and name onto the existing agent. That way, when a pull request changes the prompt, the next registration run deploys that change to the project.

Create onlyErrors or duplicates on a second runOne-off setup scripts
Create or reuseLeaves existing agent untouchedAgents edited in the portal
Create, reuse, or updatePushes repository config every runCode-managed agents and CI/CD

A Safer Registration Flow

The improved script lists existing agents, filters for the target name, and decides what to do based on what it finds. The idea applies regardless of the exact SDK calls you use.

existing = project_client.agents.list_agents()

match = next(
    (a for a in existing.data if a.name == "trip-planner"),
    None,
)

if match is None:
    agent = project_client.agents.create_agent(
        model="YOUR_DEPLOYMENT_NAME",
        name="trip-planner",
        instructions=load_instructions(),
    )
    print(f"Created new agent: {agent.id}")
else:
    agent = project_client.agents.update_agent(
        match.id,
        model="YOUR_DEPLOYMENT_NAME",
        instructions=load_instructions(),
    )
    print(f"Updated existing agent: {agent.id}")

Wrap the registration in a small function that takes the project client and the agent definition, and returns the final agent. Both your manual scripts and your pipeline can call the same function, which keeps the "only one trip-planner exists" rule enforced everywhere.

Handling the Human Factor

Idempotent code cannot fix every mess. If you already created several duplicate agents by hand, the script will happily reuse the first one it finds while the duplicates remain. Before adopting the pattern, spend a few minutes tidying the project: decide which agent is canonical, delete the copies from the portal, and let the script manage exactly that one from then on.

Deleting an agent removes its run history and traces. If you are cleaning up duplicates, first confirm none of them is being called by an application or pinned by a published version.

Summary

Registration code must be safe to run repeatedly. By moving from create-only to a look-up, reuse, and update flow, you make your agent definitions reproducible, your pipelines idempotent, and your repository the single source of truth for configuration. With a stable, registered agent in place, the next lab shows how to talk to it — invoking your agent exactly the way a production application would.
