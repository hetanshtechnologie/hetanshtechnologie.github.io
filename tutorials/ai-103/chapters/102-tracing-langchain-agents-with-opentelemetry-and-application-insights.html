Tracing LangChain Agents with OpenTelemetry and Application Insights

An agent that calls tools in a loop is hard to debug by reading its code alone. When a request goes wrong — the wrong tool selected, a failed call, a truncated answer — you want to see exactly what happened, in order, with timing. That is the job of tracing. This chapter explains how LangChain agents emit traces, how OpenTelemetry standardizes those traces, and how you can stream them into Application Insights on Azure for a queryable view of every agent run.

Why Agent Tracing Is Hard

A single user request can involve several model calls, multiple tool invocations, and a chain of prompt-and-response round trips. The pieces are nested: one tool call happens inside one model step, which happens inside the overall agent invocation. Without instrumentation, the only evidence you have is the final answer. If that answer is wrong, you cannot tell whether the model misread the question, a tool returned bad data, or the prompt steered it wrong.

Tracing solves this by recording the whole journey as structured data: each step, its inputs, its outputs, its duration, and its parent step. You can then replay a failed request and see the exact sequence that produced it.

The OpenTelemetry Model

OpenTelemetry is an open, vendor-neutral standard for collecting telemetry. Two concepts matter most for tracing:

  • A trace represents one logical unit of work — here, one agent invocation. It has a unique ID.
  • A span is a single operation inside the trace — one model call, one tool run. Spans are nested, with a parent and children, forming a tree that mirrors the agent loop.

Because OpenTelemetry is a standard, the spans emitted by LangChain can be consumed by any tool that understands it. The exporter decides where the data goes: Jaeger, Zipkin, Azure Monitor, or any OTLP-compatible collector.

ConceptMeaning in an agent run
TraceThe entire user request, end to end
Root spanThe invoke of the agent executor
Child spanA single LLM call or a single tool execution
AttributesModel name, tool name, prompt text, token counts
EventsSignificant moments, such as a tool starting or finishing

You already met OpenTelemetry's ideas in the earlier chapter on Foundry observability. The difference here is that LangChain lives in your own application process, so your code must produce the spans — the model endpoint in Foundry does not see the agent loop at all.

Instrumenting LangChain

LangChain publishes an instrumentation package, langchain-opentelemetry, that automatically creates spans for chains, models, tools, and agents. Install it and it hooks the framework at key points:

pip install langchain-opentelemetry

Once installed, every LangChain component that supports the tracing protocol starts emitting spans when an exporter is configured. The spans appear for invoke, stream, and the agent loop, so you get the full picture without touching your agent code.

LangChain also has a cloud-hosted tracing service, but in this course we keep telemetry in Azure. Pointing the OpenTelemetry exporter at Application Insights gives you the same span tree inside a service you already use.

Exporting to Application Insights

Application Insights is Azure's application monitoring service, and it accepts OpenTelemetry data through its Azure Monitor exporter. The configuration is a few lines in Python:

from azure.monitor.opentelemetry.exporter import AzureMonitorTraceExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

exporter = AzureMonitorTraceExporter(
    connection_string="InstrumentationKey=YOUR_INSTRUMENTATION_KEY"
)
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(exporter))
from opentelemetry import trace
trace.set_tracer_provider(provider)
pip install azure-monitor-opentelemetry-exporter opentelemetry-sdk

The connection_string comes from your Application Insights resource. To create one, go to the Azure portal, search for Application Insights, create a resource in the same subscription you have been using, and copy the Instrumentation key from the resource overview.

What You See in the Portal

Once requests flow, open your Application Insights resource and explore:

  • Transaction search / End-to-end transaction details: find an agent run by its trace ID and see the span tree — the agent root, each LLM call, each tool run, with timings.
  • Failures: any span that errored appears here, which is invaluable when a tool raised an exception you never saw at runtime.
  • Performance: latency by component tells you whether the slow part is the model, a tool, or the loop overhead.
  • Logs (KQL): query spans directly, filter by operation name, tool name, or response code, and build dashboards over time.

Trace data can include prompt text and tool inputs, which may contain personal data. Decide what you are willing to store and consider redacting sensitive attributes at the exporter before they leave your network. Retention and filtering matter as much as collection.

Correlating with Foundry Telemetry

Foundry already records model calls on the server side. Combining that with your client-side LangChain trace gives you both halves of the picture: the server log shows one model request with token counts, while the Application Insights trace shows how that request fit into the agent's decision loop. The two views answer different questions — the first "how much did this call cost?", the second "why was this call made?" — and together they cover most debugging scenarios.

Summary

Agent tracing records the nested series of model calls and tool runs behind a single user request. OpenTelemetry provides the standard span model, LangChain emits the spans automatically, and the Azure Monitor exporter streams them into Application Insights, where you can search failures, measure performance, and query the full trace tree.
