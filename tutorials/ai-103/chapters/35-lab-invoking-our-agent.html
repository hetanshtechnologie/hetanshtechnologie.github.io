Lab - Invoking our agent

Your agent now exists and is registered in the Foundry project. In this lab you will invoke it the way a production application would: open a conversation, send a message, wait for the run to finish, and read the agent's answer. By the end you will have a small client script you can reuse any time you need to talk to your agent from Python.

Objectives

  • Connect to your Foundry project and load the agent you registered.
  • Create a thread and send a user message.
  • Poll the run until it completes and retrieve the agent's replies.

Step 1: Load the existing agent

Create a new script in the same project folder. Instead of creating an agent from scratch, look up the one you registered so the script works no matter how many times it has been run.

Set up invoke_agent.py

import os
import time
from dotenv import load_dotenv
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

load_dotenv()

project_client = AIProjectClient.from_connection_string(
    credential=DefaultAzureCredential(),
    conn_str=os.getenv("PROJECT_CONNECTION_STRING"),
)

agent = next(
    a for a in project_client.agents.list_agents().data
    if a.name == "trip-planner"
)
print(f"Using agent: {agent.id}")

The agent's ID is stable across calls, but it differs from project to project. Looking it up by name keeps your scripts portable, at the cost of assuming the name is unique — which is exactly what the previous chapter's idempotent registration guarantees.

Step 2: Start a conversation

Agent conversations happen in threads. Create a thread, then post the first user message into it. A single thread can hold many messages, and the agent uses the whole thread as context for each run.

Create the thread and send a message

thread = project_client.agents.create_thread()
print(f"Thread created: {thread.id}")

message = project_client.agents.create_message(
    thread_id=thread.id,
    role="user",
    content="Plan a 3-day trip to Paris for two people.",
)
print(f"Message posted: {message.id}")

Step 3: Run the agent and wait

Sending a message does not generate an answer by itself. You must create a run — the execution unit that feeds the thread to the model — and poll it until it reaches a finished state. The same run object later tells you whether any tools were called and whether the run completed cleanly.

Create the run and poll for completion

run = project_client.agents.create_run(
    thread_id=thread.id,
    agent_id=agent.id,
)

while run.status in ("queued", "in_progress", "requires_action"):
    run = project_client.agents.get_run(
        thread_id=thread.id, run_id=run.id
    )
    time.sleep(1)

print(f"Run finished with status: {run.status}")

The requires_action status is important: it means the model has requested a tool call and is waiting for your application to execute it and return the result. In this lab the agent has no tools, so the run should pass through the other statuses and complete on its own.

Step 4: Read the agent's answer

After the run completes, the thread contains the assistant's messages. Retrieve them and print the text content of the latest reply.

Retrieve and display the response

messages = project_client.agents.list_messages(thread_id=thread.id)

for item in reversed(messages.data):
    if item.role == "assistant" and item.content:
        for part in item.content:
            if hasattr(part, "text"):
                print(part.text.value)

Run the script and confirm you see a full itinerary reply. Then experiment:

  • Post a second message into the same thread and run the agent again to see it remember the first exchange.
  • Ask a clarifying question you know the instructions force, such as a trip with no budget, and confirm the agent asks before answering.

Each run consumes tokens and generates trace data in your project. During testing, keep runs short and remember to clean up demo threads you do not need, so your project stays tidy and your bill stays predictable.

Summary

You invoked your registered agent from code using the standard pattern: load the agent, create a thread, post a message, run, poll, and read. This client loop is the same one you will build on when the agent gains tools — at that point the run will occasionally pause at requires_action and hand control back to your application to execute a function.
