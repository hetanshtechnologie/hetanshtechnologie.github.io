Diagnostic Settings and Resource-Level Monitoring

So far you have seen monitoring through the Foundry portal and through Application Insights attached to your agent. Both views draw from the same raw material: telemetry emitted by Azure resources. This chapter explains diagnostic settings — the configuration that decides where that telemetry flows — and shows how resource-level monitoring gives you the platform health view that complements your application-level view. Understanding this layer lets you keep logs, metrics, and traces for compliance, debugging, and cost analysis even after a resource is gone.

The Two Levels of Monitoring

Azure separates monitoring into two layers that answer different questions:

  • Resource-level monitoring reports on the platform resource itself: requests, errors, latency, tokens consumed, quota, and deployment health. For a model deployment this tells you how the endpoint is performing.
  • Application-level monitoring reports on your code and prompt flows: what the agent did with each request, which tools it called, and what the user experienced. Application Insights is the home of this telemetry.
LayerSeesTypical questions
Resource levelEndpoint metrics, logs, quotaIs the deployment healthy? How many requests? Any throttling?
Application levelTraces, prompts, tool calls, sessionsWhy did this answer go wrong? Which tool ran?

You need both. Resource metrics tell you the platform is up; application traces tell you whether your agent is doing a good job on top of it.

What Are Diagnostic Settings

A diagnostic setting is a rule attached to a resource that says: send this resource's logs and metrics to these destinations. Every Azure resource that produces telemetry can have one or more diagnostic settings. Without a diagnostic setting, a resource's platform logs are retained only briefly and are hard to query historically; with one, the telemetry flows somewhere durable.

The destinations you can choose from are:

  • Log Analytics workspace — for querying logs and metrics together with KQL.
  • Storage account — for cheap, long-term archival, often for compliance.
  • Event Hub — for streaming telemetry into another system such as a SIEM or a data pipeline.
  • Partner solutions — third-party monitoring tools that integrate through the Azure Monitor partner program.

You can create several diagnostic settings on the same resource. A common pattern is one that streams to Log Analytics for interactive queries and a second that archives to storage for retention and compliance. The two settings run in parallel and do not interfere.

Metrics vs Logs

Diagnostic settings carry two broad kinds of telemetry, and it helps to keep them straight:

  • Platform metrics are numeric measurements collected at regular intervals — requests, latency, error counts, token usage. They are lightweight, always on, and excellent for dashboards and alerts.
  • Resource logs are detailed records of events — audit entries, authentication failures, throttle events. They are verbose, may be disabled by default, and are best for investigations.

Setting Up a Diagnostic Setting

You can create a diagnostic setting in the portal or with the Azure CLI. Either way you choose the resource, the destination, and the log categories to forward. A CLI example that routes metrics and logs to a Log Analytics workspace looks like this:

az monitor diagnostic-settings create \
  --resource YOUR_RESOURCE_ID \
  --name "to-loganalytics" \
  --workspace YOUR_WORKSPACE_ID \
  --metrics 'category="AllMetrics" enabled=true' \
  --logs 'category="Audit" enabled=true'

Replace YOUR_RESOURCE_ID with the full Azure resource ID of the deployment or hub you are monitoring, and YOUR_WORKSPACE_ID with the resource ID of your Log Analytics workspace. You can find both in the Azure portal under the resource's Properties and the workspace's Overview.

Once the setting exists, telemetry arrives in the workspace after a short delay. You can then query it directly:

AzureDiagnostics
| where ResourceProvider == "MICROSOFT.OPENAI"
| where OperationName == "InferenceRequest"
| summarize Count = count(), AvgTokens = avg(TokenCount_s) by Resource, bin(TimeGenerated, 5m)
| render timechart

Resource-Level Views in Foundry

In the Foundry portal, the Monitoring or Metrics tab of a deployment shows the resource-level picture immediately: request counts, error rates, latency, and token throughput, rendered as charts you can set alerts against. These are platform metrics, so they work even before you configure any diagnostics — but to keep history longer than the default retention, or to join them with your agent's traces in one workspace, you route them through a diagnostic setting as shown above.

Diagnostic settings do not capture the content of model prompts and completions unless you explicitly enable request/response logging, and those payload logs can contain personal data. Enable payload capture only when you genuinely need it, protect the workspace with access controls, and be aware of the privacy and compliance implications for your data.

Summary

Resource-level monitoring reports on the health of the platform resource, while application-level monitoring reports on your agent's behaviour. Diagnostic settings connect the two by streaming resource metrics and logs to durable destinations such as Log Analytics, storage, or Event Hubs. You configured a diagnostic setting with the CLI, queried the resulting telemetry, and saw where resource metrics appear in Foundry.
