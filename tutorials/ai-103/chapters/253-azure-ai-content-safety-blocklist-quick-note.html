Azure AI Content Safety - BlockList - Quick note

Azure AI Content Safety gives you several layers of protection, and the blocklist feature is one of the most direct. While the built-in severity classifiers judge how harmful a piece of text is based on trained models, a blocklist lets you define your own exact list of words, phrases, or terms that should always be flagged. This chapter is a quick reference for what blocklists are, how they behave, and how you manage them through code.

What Is a BlockList

A blocklist is a curated collection of terms that you want the moderation service to detect, regardless of how the built-in severity models would score them. Every entry is a short string — typically a word or a short phrase — that your organization considers unacceptable.

Blocklists are useful for domain-specific concerns that a general-purpose classifier cannot know about:

  • Internal product names or competitor names you do not want mentioned.
  • Slang or local terms that carry a harmful meaning in your community.
  • Legal or compliance terms that must never appear in public output.
  • Known abuse patterns specific to your application.

Each blocklist is a named object that belongs to a Content Safety resource. You can create several blocklists on the same resource, and a moderation request can reference one or more of them.

How BlockLists Work

When you submit text for analysis, the service evaluates the content against the configured blocklists in addition to the machine-learned severity categories. A match against a blocklist term is reported separately from the severity result, so you can tell exactly which rule fired.

The important behaviors to remember:

  • Matching is applied to the text as submitted. The service looks for occurrences of each blocklist term inside the supplied text.
  • A hit is reported with the matched term and where it was found, so your application can decide how to respond.
  • Blocklist results come back in a dedicated blocklistsMatch array that is easy to inspect in your code.
  • Blocklist detection runs independently of the severity analysis, so even very mild content can be blocked if it contains a forbidden term.

Think of severity scores and blocklists as two separate gates. The severity model answers "how harmful is this by general standards?" while a blocklist answers "does this contain something we specifically banned?" Your policy can treat a blocklist hit as a hard rejection and a high severity score as a risk that needs review.

Managing BlockLists with the SDK

Blocklists are managed through the Content Safety administrative API. The SDKs expose a client that you use to list, create, update, and delete blocklists, and to add or remove the terms inside them.

The standard sequence is:

  1. Create a BlocklistClient using your endpoint and key.
  2. Create or retrieve a blocklist by name.
  3. Add terms to the blocklist, either one at a time or in a batch.
  4. Reference the blocklist name in moderation calls so its terms are applied.
  5. Delete terms (or the whole blocklist) when they are no longer needed.

A conceptual code outline:

from azure.ai.contentsafety import BlocklistClient
from azure.core.credentials import AzureKeyCredential

client = BlocklistClient(
    endpoint="YOUR_ENDPOINT",
    credential=AzureKeyCredential("YOUR_KEY"),
)

blocklist_name = "MyBlocklist"

client.create_or_update_text_blocklist(
    blocklist_name=blocklist_name,
    options={"description": "Terms banned for our app"},
)

client.add_or_update_blocklist_items(
    blocklist_name=blocklist_name,
    blocklist_items=[
        {"text": "forbidden-phrase-one"},
        {"text": "forbidden-phrase-two"},
    ],
)

Using a BlockList in a Moderation Call

Once the blocklist exists, you pass its name to the text analysis call. The moderation response then contains both the severity results and any blocklist matches.

from azure.ai.contentsafety import ContentSafetyClient
from azure.core.credentials import AzureKeyCredential
from azure.ai.contentsafety.models import AnalyzeTextOptions

client = ContentSafetyClient(
    endpoint="YOUR_ENDPOINT",
    credential=AzureKeyCredential("YOUR_KEY"),
)

result = client.analyze_text(
    options=AnalyzeTextOptions(
        text="Your sample text goes here.",
        blocklist_names=["MyBlocklist"],
    )
)

if result.blocklists_match:
    for match in result.blocklists_match:
        print("Blocked term:", match.blocklist_item_text)
else:
    print("No blocklist matches found.")

The blocklists_match collection is empty when nothing matched. Each entry tells you which term matched and the blocklist it came from, which is handy for logging and audit trails.

Practical Notes and Limits

  • Terms are case-insensitive matches in the moderation call; entering "BADWORD" also catches "badword".
  • There are limits on the number of blocklists per resource and the number of items per blocklist — check the current service documentation for the exact quotas.
  • Blocklists take effect shortly after you update them; give the change a moment to propagate before load testing.
  • Blocklists complement, but do not replace, the severity classifiers. Use both for defense in depth.

Use blocklists for terms that must always be rejected with a deterministic rule. Use the severity classifiers for the gray areas where judgment, thresholds, and human review are more appropriate.

Summary

Blocklists give you precise, deterministic control over content filtering: you define the terms, the service finds them, and your code reacts. They are managed through a dedicated SDK client and referenced by name in moderation requests. Together with the severity classifiers, blocklists form a practical, layered approach to keeping AI-generated content safe.
