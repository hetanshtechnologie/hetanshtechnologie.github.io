Connecting Azure AI Search to an Agent

A search index is only useful if something can query it at the right moment. In a chat application, that something is an agent: it decides when the user's question needs your data, runs a search, and writes an answer grounded in the results. This chapter explains the two ways an agent can reach Azure AI Search — a direct index tool and a knowledge-base connection — and the design decisions that make retrieval helpful rather than noisy.

Why an Agent Needs Search as a Tool

A chat model cannot see your index. Everything it knows came from training. To answer questions about your documents, the agent must fetch context at query time — which is exactly the RAG loop you built in the previous labs. The difference is who triggers the fetch:

  • In a simple RAG script, your code always searches before calling the model.
  • In an agent, the model decides whether a question requires a search, which terms to use, and whether one search is enough.

That flexibility is what makes agents better for open-ended questions. A question like "which models support vision?" triggers a search; a follow-up like "summarize what you found" may not need another one.

Two Connection Patterns

Foundry and Azure AI Agent Service offer two ways to connect an agent to a search index:

PatternHow it worksBest for
Index toolThe search index is exposed as a tool the agent calls during a conversationExplicit control, multiple indexes, model-driven query crafting
Knowledge-base connectionThe index is registered as the agent's data source; retrieval runs automaticallyFast setup, consistent grounding, less plumbing

Both end in the same place: retrieved chunks are injected into the model context, and the model answers from them. They differ in how much control you have over the retrieval step.

Whatever the pattern, retrieval quality still comes from the index. A skillset that produced poor chunks will produce poor answers no matter how the agent is connected. Treat the index itself as the contract: if the right content is not in the top results, no agent wiring will fix it.

What a Search Tool Gives the Model

When you attach an index as a tool, the agent receives a description of what the tool does and how to call it — for example, the index name, the searchable fields, and whether to search keywords, vectors, or both. The model uses that description to:

  • Recognize when the question is answerable from the index.
  • Compose a good query from the user's words.
  • Decide how many results to request and which fields matter.

This is why the tool description is so important. A vague description like "search the index" invites the model to skip it or misuse it; a precise one like "Search the course manual index for pages that describe setup steps. Returns the top matching chunks with their source file names." produces far more reliable calls.

Hybrid Search Is the Default You Want

For a general-purpose agent, hybrid search — keyword plus vector, combined and ranked together — is the strongest setting. It matches exact product names a user types verbatim, while still finding conceptually related content when the wording differs. Most agent connectors let you choose the query mode:

Query modeBehaviorWhen to choose it
KeywordExact term matchingPrecise identifiers and codes
VectorSemantic similarity over embeddingsParaphrased, conceptual questions
HybridBoth, reranked togetherDefault for open-ended assistant questions

Add a filter when the index spans categories — for example, restrict results to a product line or a date range before ranking. Filters applied at the tool level keep the agent from retrieving from the wrong slice of data.

Grounding and Citations

Grounding is the guarantee that the model answered from the retrieved chunks. The pattern in this course: the system prompt instructs the model to answer only from the provided context and to cite the source when it uses one, and the search results carry metadata_storage_path and metadata_storage_name so citations can point at real files.

Grounding is an instruction, not a hard guarantee. The model can still answer from training knowledge if the prompt allows it. For strictly regulated content, add a verification step that rejects answers whose cited chunks do not actually contain the claim, or use content safety and evaluation to catch drifting responses.

Secrets, Identity, and Permissions

The agent process needs permission to read the index. The simplest lab setup uses a search key in the connection configuration, but production systems should use a managed identity — the agent's identity is assigned a role such as Search Index Data Reader on the search service, and no key ever travels with the code. You will apply exactly this role assignment in the capstone project's permissions chapter.

Summary

Agents reach Azure AI Search either through an index tool the model calls deliberately or through a knowledge-base connection that retrieves automatically. Precise tool descriptions, hybrid query mode, and metadata filters shape retrieval quality, while grounding instructions and citations keep answers honest.
