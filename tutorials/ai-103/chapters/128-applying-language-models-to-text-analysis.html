Applying Language Models to Text Analysis

Text analysis is one of the most common jobs for generative AI in the real world. Support teams need to know whether a message is angry, researchers need to pull names and dates out of articles, and product teams need to summarize what customers are talking about. This chapter explains how a large language model performs these jobs by prompting, what each task looks like, and — just as importantly — when a general-purpose LLM is the right tool and when a specialized service such as Azure AI Language is a better fit.

Why Text Analysis Is a Natural Job for LLMs

Language models are trained to recognize patterns in written text, so analyzing text plays directly to their strengths. No feature engineering, no per-task training data, and no bespoke model per job are needed. The same deployment that writes a summary can also detect sentiment, extract entities, or translate — the difference is only the prompt. This one-model-many-jobs property is what makes an LLM such a flexible foundation for text pipelines.

Most text-analysis tasks fall into a small set of categories:

  • Extraction: pull specific facts out of text — people, places, dates, product names, contract clauses.
  • Classification: assign a category or label — sentiment, topic, intent, language.
  • Transformation: change the text — translate it, simplify it, rephrase it in a style.
  • Summarization: compress a long passage into a short statement of the key points.
  • Structured output: reshape free text into JSON or tables that downstream code can consume.

Entities and Topics

Entity extraction asks the model to find specific things mentioned in a passage. People, organizations, locations, dates, monetary amounts, and product names are all entities. A support desk can extract the product name and ticket number from an email; a news pipeline can extract the politicians and companies mentioned in an article.

Topic detection is a coarser question: what is this text about overall? Instead of listing individual mentions, the model assigns one or more thematic labels such as "billing", "returns", or "privacy". Topics are useful for routing, tagging, and clustering large collections of documents.

Both tasks come in two flavors. Naive prompting just asks the model to "find the entities" or "list the topics" and lets the model choose its own format. Structured prompting constrains the format — for example, always returning JSON with fixed field names — which makes the output much easier to parse in code.

Sentiment and Tone

Sentiment analysis assigns a polarity — positive, negative, or neutral — to a piece of text. Tone goes further and characterizes the emotional register: frustrated, sarcastic, appreciative, urgent. A chat model can do both in one pass and, unlike a simple polarity scorer, can explain why it reached its conclusion by quoting the words that triggered the judgment.

Because a language model reasons over the whole sentence rather than a bag of words, it handles context far better than early keyword-based sentiment systems. The phrase "this is not bad" trips up a naive dictionary — the words "not" and "bad" are both negative — but an LLM reads the whole clause and correctly reports a mildly positive meaning.

When you need an explanation alongside the score, prompting wins. When you need to score millions of messages per day at minimal cost, a dedicated sentiment service is usually faster and cheaper per call.

Translation

Translation is another task where prompting is nearly trivial: hand the model a passage and the target language, and it returns the translation. Models trained on multilingual corpora handle dozens of languages, preserve tone and formality, and can even be asked to adapt a translation to a specific audience, such as a more formal register for business correspondence.

The trade-offs matter at scale. General-purpose models produce fluent, context-aware translations, but specialized translation services are typically cheaper, faster, and tuned on far more parallel text. The chapter on Azure Translator shows the service approach; the translation lab shows the prompting approach.

Structured Output as the Glue

An analysis is only useful if the rest of your application can consume it. Most of the tasks above end in a structured result — a list of entities with types, a sentiment label with a confidence, a set of topics with scores. Modern chat APIs support JSON mode, which guarantees the model replies with valid JSON, letting you parse the analysis into native Python objects without fragile string parsing.

import json
from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint="YOUR_ENDPOINT",
    api_key="YOUR_KEY",
    api_version="2024-06-01",
)

response = client.chat.completions.create(
    model="YOUR_DEPLOYMENT_NAME",
    response_format={"type": "json_object"},
    messages=[
        {"role": "system", "content": "Return a JSON object with keys entities and topics."},
        {"role": "user", "content": "Our refund for order 4821 was declined last week."},
    ],
)

data = json.loads(response.choices[0].message.content)
print(data["entities"], data["topics"])

LLM Prompting vs. a Specialized Service

Both approaches extract information from text, but they are built for different situations. The table below is the decision aid you will use throughout this section:

FactorChat model promptingAzure AI Language
FlexibilityHandles any task you can describeFixed set of prebuilt capabilities
Output formatFully controllable via prompt and JSON modeFixed, documented response schemas
ExplanationsCan justify its analysis in wordsReturns scores and spans, not prose
Cost per callHigher; billed per tokenLower; billed per document or call
LatencyHigher; generates many tokensLower; typically single-pass analysis
Best forUnusual tasks, prototypes, deep reasoningHigh-volume, well-defined, well-specified tasks

A sensible architecture uses both: an LLM for the tasks that need judgment and explanation, and a specialized service for the high-volume classification and extraction work where its fixed schemas are an asset rather than a limitation.

Summary

Text analysis by LLM is prompting in disguise: extraction, classification, transformation, and structured output are all achieved by describing the job and parsing the answer. This approach is flexible and explainable, but specialized services such as Azure AI Language offer lower cost and deterministic schemas for well-defined tasks.
