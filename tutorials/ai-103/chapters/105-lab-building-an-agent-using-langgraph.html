Lab - Building an agent using LangGraph

In this lab you will implement the LangGraph agent designed in the previous chapter: a stateful, graph-based agent that can call tools, remember the conversation, and answer naturally. This is the point where LangGraph's ideas stop being vocabulary and become working code on your machine.

Prerequisites

  • Your Python virtual environment with langchain and langchain-openai installed.
  • Your Foundry chat deployment details in a .env file.
  • Install LangGraph in the activated environment:
pip install langgraph

LangGraph has its own versioning and depends on LangChain core. If you get import errors after installing, upgrade both packages together: pip install -U langgraph langchain langchain-openai.

Step 1: Define a Tool

Exercise 1: Create a weather tool and the state

Create graph_agent.py and start with the imports, state, and tool:

import os
from typing import Annotated, TypedDict

from dotenv import load_dotenv
from langchain_core.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import InMemorySaver
from langchain_openai import AzureChatOpenAI

load_dotenv()

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

@tool
def get_weather(city: str) -> str:
    """Return a sample weather summary for a city."""
    return f"Sunny, 24 degrees Celsius in {city}."

@tool
def get_local_time(city: str) -> str:
    """Return a sample local time for a city."""
    return f"Currently 14:30 local time in {city}."

Two tools makes the tool-calling decision visible. Watch whether the model picks the right tool for the right question — that is the behavior you are really testing.

Step 2: Build the Nodes and Graph

Exercise 2: Wire the model, nodes, and conditional edges

Continue the same file:

model = AzureChatOpenAI(
    azure_endpoint=os.getenv("AZURE_OPENAI_ENDPOINT"),
    api_key=os.getenv("AZURE_OPENAI_API_KEY"),
    api_version=os.getenv("AZURE_OPENAI_API_VERSION"),
    deployment_name=os.getenv("AZURE_OPENAI_DEPLOYMENT_NAME"),
    temperature=0,
)

tools = [get_weather, get_local_time]
model_with_tools = model.bind_tools(tools)
tool_node = ToolNode(tools)

def agent_node(state: AgentState) -> dict:
    return {"messages": [model_with_tools.invoke(state["messages"])]}

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)

graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", tools_condition)
graph.add_edge("tools", "agent")

app = graph.compile(
    checkpointer=InMemorySaver(),
    recursion_limit=20,
)

Everything here mirrors the implementation chapter: the agent node invokes the bound model, the ToolNode runs requested tools, and tools_condition routes back to tools or to the end.

Step 3: Run the Agent

Exercise 3: Test single and multi-turn conversations

Add a test block to the bottom of the file:

if __name__ == "__main__":
    config = {"configurable": {"thread_id": "thread-demo"}}

    first = app.invoke(
        {"messages": [("user", "What is the weather in London?")]},
        config,
    )
    print("Answer 1:", first["messages"][-1].content)

    second = app.invoke(
        {"messages": [("user", "And what time is it there?")]},
        config,
    )
    print("Answer 2:", second["messages"][-1].content)

Run it from the activated environment:

python graph_agent.py
  1. The first question should route through the tools node — you can see it if you enable verbose printing on the model — and produce a weather answer.
  2. The second question relies on memory: the checkpointer restored thread-demo, so the model knows "there" means London. Answer 2 should mention London's time.
  3. Try both questions with a fresh thread ID. The second answer will not know about London, because the new thread starts with an empty history.

Contrast this with the LangChain AgentExecutor lab. There, memory required an external chain to manage history. Here, state persistence is built into the graph — the checkpointer is the memory. That is the core architectural difference you are experiencing.

Step 4: Inspect the State at Each Step

You can peek at the graph's internal reasoning by printing the full state after a run:

for msg in first["messages"]:
    role = getattr(msg, "type", msg.__class__.__name__)
    content = msg.content if isinstance(msg.content, str) else str(msg.content)[:120]
    print(f"[{role}] {content}")

You will see the full message trail: the user question, the model's tool-call request, the tool message with the weather result, and the final natural-language answer. This trail is exactly what the OpenTelemetry tracing from the earlier chapter would record as spans.

Step 5: Raise the Complexity Safely

Try pushing the agent in controlled ways to see how the graph behaves:

  • Ask for weather in two cities at once. The model may request two tool calls in one message; the ToolNode runs both.
  • Ask a question with no tool involved. The conditional edge routes straight to the end — one step, no tools.
  • Temporarily remove recursion_limit or lower it to 2 and ask a multi-step question. You will see the guard rail in action: LangGraph stops the run instead of looping forever.

Lowering the recursion limit intentionally forces a run to hit its ceiling. When it does, invoke raises an error rather than returning a partial answer. In production, wrap your invocations in a try/except and return a graceful message when the limit is reached.

Summary

You implemented the full LangGraph agent: a two-node graph with conditional routing, a tool node, an in-memory checkpointer, and a recursion limit. You verified single-turn tool use, multi-turn memory across thread IDs, and the state trail behind each run. You also probed the safety rails by testing parallel tool calls and the recursion ceiling.
