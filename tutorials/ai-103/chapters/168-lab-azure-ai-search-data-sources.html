Lab - Azure AI Search - Data sources

In the previous lab you staged documents in blob storage and created a search service. Now you will teach the search service where those documents live by defining a data source. This is the first component of the indexing pipeline, and it establishes the connection the indexer will use in later labs.

What You Need Before Starting

  • The storage account and its connection string from the previous lab.
  • The Azure AI Search service name and its admin key from the previous lab.
  • The Azure CLI, signed in, and your resource group variable still set.
  • The search extension for the Azure CLI, installed with az extension add --name azure-search.

Step 1 - Set Connection Variables

Set the variables the commands will use. Replace the placeholders with your resource names and the admin key from the last lab:

$rg = "rg-ai103"
$searchName = "srch-ai103-<yourname>"
$adminKey = "YOUR_ADMIN_KEY"

$conn = az storage account show-connection-string `
  --name "saai103<yourname>" `
  --resource-group $rg `
  --query connectionString -o tsv

Step 2 - Understand What a Data Source Defines

A data source is a JSON object with three key parts:

  • name — how you will refer to the data source when creating the indexer.
  • type — the connector, in this case azureblob.
  • credentials — how the service authenticates to the storage account (here, the connection string).
  • container — which container (and optional path) to read from.

Save the following as datasource.json:

{
  "name": "docs-datasource",
  "type": "azureblob",
  "credentials": {
    "connectionString": "YOUR_CONNECTION_STRING"
  },
  "container": {
    "name": "docs"
  }
}

The connection string in the JSON file is a secret. Never commit datasource.json to a repository. In a real deployment you would use a managed identity instead of a shared key; the labs use the connection string for simplicity.

Step 3 - Create the Data Source

Before calling the API, replace the connection string placeholder in the file. In PowerShell, inject the value directly:

$json = Get-Content -Raw datasource.json
$json = $json.Replace("YOUR_CONNECTION_STRING", $conn)
$json | Set-Content datasource.local.json

az search datasource create `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey `
  --name docs-datasource `
  --type azureblob `
  --connection-string $conn `
  --container-name docs

A successful call prints the data source definition, including the assigned @odata.etag. The data source now points at the docs container.

If the az search datasource command is not recognized, install the extension first:

az extension add --name azure-search

Step 4 - List and Inspect Data Sources

Verify the data source exists on the service:

az search datasource list `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey -o table

You can also list data sources through the REST API to see the full definition:

az rest --method get `
  --uri "https://$searchName.search.windows.net/datasources?api-version=2023-11-01" `
  --headers "api-key=$adminKey"

Step 5 - Test the Connection Before Indexing

Creating a data source does not read any files, so it cannot fail from a bad container name at creation time. To confirm the connection actually works, list blobs from the storage side and compare with what the container name expects:

az storage blob list --container-name docs --connection-string $conn --query "length(@)" -o tsv

You should see a number greater than zero. If the container were empty or the connection string wrong, the indexer in the next lab would produce an empty index — checking now isolates the problem early.

A common mistake is pointing the data source at a container that does not exist. Azure Blob data sources accept the container name exactly as it appears in the storage account — case-sensitive, no leading slash.

Summary

You defined a blob-storage data source on your search service, verified it through both the CLI and the REST API, and confirmed the underlying container holds documents. The search service now knows where its content lives. With the data source in place, the next labs add the index schema and the indexer that turns those blobs into searchable documents.
