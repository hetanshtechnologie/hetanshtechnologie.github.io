Quick Tour of Microsoft Foundry

A tool you do not know how to navigate is a tool you will not use. This chapter is a guided tour of the Microsoft Foundry portal — the screens you will visit repeatedly, what each one is for, and how they connect to one another. Think of it as a map of the building before you start running labs in it.

Portal Areas at a Glance

The Foundry portal groups its functionality into a few broad areas. Once you know which area owns which job, you can find almost anything by reasoning, rather than by hunting through menus:

AreaJob it ownsYou go there to...
Project overviewIdentity and settingsFind endpoints, keys, and project info
BuildPrompts, agents, flowsCreate and test prompt-based applications
Model catalogModel discoveryBrowse and deploy available models
DeploymentsEndpoint managementCreate, inspect, and manage model endpoints
DataData and connectionsConnect storage and view indexed data
EvaluateQuality measurementRun and view evaluation results
MonitorProduction visibilityTrack cost, latency, errors, and safety

The Project Overview Page

Every project opens to an overview page that acts as its home. Here you will find the project name and ID, the connected resource, and the quick actions for common tasks. Two details matter for your later code work:

  • The project endpoint — the base URL your applications call.
  • The authentication information — where keys and managed identities are managed.

Get into the habit of opening the overview page when you start a coding session, because the connection values you copy there change if you move a project to a different resource.

The Model Catalog

The model catalog is the shelf of models you can deploy. It spans models from Microsoft and a wide range of partners, covering chat, code, embedding, vision, and more. Each catalog entry includes a model card with details on capabilities, context length, and typical pricing. You can filter by provider, family, task, and license type.

During the tour, open the catalog and search for a couple of model families you will use later, such as a general chat model and a small model for simple tasks. The point of this exercise is not to deploy anything yet — it is to learn how the filter controls work so the deployment lab feels familiar.

Bookmark the model catalog in your memory as the place to start every new project. Good practice is: open the catalog, filter by your task, read the model cards, and only then decide what to deploy. The deploy step is fast; choosing the right model is the actual work.

Deployments: Where Models Get Endpoints

The Deployments page lists every endpoint in the project and its status, model, region, and pricing tier. From here you can create a new deployment, pause one, change its settings, or delete it. A deployment is what your application actually talks to — the model card in the catalog is just a description until you deploy it.

Notice the deployment's name. That name becomes part of the URL your code calls, so choose names that are short and stable. Renaming a deployment later means updating every place that calls it.

Build: Prompts and Agents

The Build area is where models become applications. It hosts the prompt playground, where you test model behavior with different instructions and sampling settings, and the tools for constructing agents — model-powered assistants that can call functions and use tools. This is also where prompt flows live: multi-step workflows that combine a model with logic and external calls into a single runnable pipeline.

For this course, the most important part of Build is the playground, because it lets you experiment without writing code. Later chapters will show you the equivalent workflows in Python.

Data and Connections

Many AI applications need to answer from the organization's own documents. The Data area connects your project to sources such as blob storage and search indexes, and lets you view the documents that are available to your models. Connections are the reusable links between projects and external services — one connection can be shared across many projects.

You will not need deep data work until the retrieval chapters, but knowing where connections live now saves you from hunting later.

Evaluate and Monitor

The Evaluate area measures model quality with automated metrics, test datasets, and human review. The Monitor area tracks the production behavior of deployed models: cost per request, latency, error rates, and content-safety violations. These two areas are the difference between "I think it works" and "I know it works," and this course treats them as core skills rather than afterthoughts.

The tour intentionally skips many screens. Do not let the density of the portal intimidate you: most of them exist for scenarios you will not touch in this course. If a page is not in the table at the start of this chapter, you almost certainly do not need it yet.

Navigating Between Azure and Foundry

A common point of confusion is moving between the Azure portal and the Foundry portal. The rule is simple: Azure manages the resources (billing, regions, RBAC), and Foundry manages the work (projects, models, evaluations). When you need to delete a resource or check spending, go to Azure. When you want to test a prompt or view a deployment, go to Foundry. Both portals point at the same underlying objects, so changes in one appear in the other after a refresh.

Summary

Microsoft Foundry's portal is organized around a small set of areas: project overview, build, model catalog, deployments, data, evaluate, and monitor. Each owns a specific job, and knowing which area to visit is the foundation for every lab in this course. In the next chapter you will learn how model deployment actually works in Foundry.
