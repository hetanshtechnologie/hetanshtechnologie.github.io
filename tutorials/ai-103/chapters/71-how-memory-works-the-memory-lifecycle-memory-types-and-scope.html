How Memory Works The Memory Lifecycle, Memory Types, and Scope

An agent that cannot remember anything is reset on every single turn. Each time a user sends a message, the agent would start from a blank slate, unaware of what was said two minutes earlier. Memory is what turns a stateless model call into something that feels like a conversation partner. In this chapter you will look under the hood at how memory works in agent systems: the lifecycle that every stored fact passes through, the different types of memory you can give an agent, and the scopes that control which agent, user, or conversation can see which memories.

The Memory Lifecycle

Memory in an agent system is not a single operation but a repeating cycle of five stages. Understanding the cycle helps you decide what to persist, how long to keep it, and where failures are most likely to happen.

  • Capture: The agent notices a piece of information worth remembering — a user's name, a preference, a decision, or a fact from the conversation — and extracts it from the dialogue.
  • Store: The extracted information is written to a durable location, such as a memory store, a vector index, or a file, so it survives beyond the current request.
  • Retrieve: On a later turn, the agent pulls back the memories that are relevant to the current question. Retrieval is almost never "give me everything"; it is a targeted lookup based on the user, the session, and the topic.
  • Update: When the user changes their mind — a new shipping address, a different budget — the stored memory is refreshed rather than duplicated, so the agent always answers from the latest information.
  • Forget: Memories expire or are removed: data-retention policies, stale records, and privacy rules all drive cleanup. Forgetting is a feature, not an afterthought.

Most real-world memory failures happen at capture and retrieval. If the agent never saves the fact, nothing else matters. If retrieval returns the wrong or stale memory, the agent answers confidently with outdated information. When you build agents, spend as much effort on what gets remembered as on how it gets recalled.

Types of Memory

Agent systems typically separate memory into two broad categories that behave very differently.

Short-term memory is the working context of the current exchange. It is the conversation history: the list of messages exchanged so far in a session, the user's current goal, and the intermediate state of the task. Short-term memory lives inside the model's context window and is discarded when the session ends. It is fast, always present, and limited by token capacity.

Long-term memory is persistent knowledge that survives between sessions. It lives in an external store and is loaded into the context window only when needed. Long-term memory is what lets a customer support agent remember that this customer is on the enterprise plan, even when the customer returns a week later and opens a brand new chat.

Memory Scope

Memory does not exist in a vacuum — every memory is attached to a scope that defines who can see it. Scope is the access-control boundary of memory, and it protects users from seeing each other's data.

  • Conversation scope: The memory is visible only inside a single chat thread. Useful for the current task and nothing else.
  • User scope: The memory follows a specific user across all their conversations. The agent remembers your preferences no matter which chat you open.
  • Agent scope: The memory belongs to one agent, so a billing assistant and a technical-support assistant keep separate worlds even when they share the same users.
  • Project or organization scope: Shared knowledge available to many agents — company policy documents, product catalogs, or a common knowledge base.

Mixing scopes is a common source of data-leakage bugs. If a memory store keyed by agent instead of by user is queried without filtering by user, one customer's preferences could appear in another customer's conversation. Always verify that your retrieval query respects the user boundary.

How the Model Consumes Memory

Whatever the type or scope, memory reaches the model the same way: as text inside the context window. On every turn the agent assembles a prompt from three parts: the system instructions, the retrieved memories and context, and the running conversation history. The model has no built-in storage of its own — its only "memory" is whatever text you place in front of it.

This has a practical consequence: memory consumes tokens. The larger the history and the more retrieved facts, the smaller the budget left for the actual answer, and the longer the latency and the higher the cost. Systems manage this with techniques such as summarization of old turns, sliding windows that drop the oldest messages, and retrieval that returns only the top few relevant memories rather than the entire store.

Treat the context window like a working desk, not a warehouse. Keep the desk tidy: summarize old dialogue, trim verbose tool output, and pull only the most relevant long-term memories per turn. The warehouse of facts lives in your storage layer, not in the prompt.

Storing Long-Term Memory

When you decide to persist memories, you have several storage options, each suited to a different pattern:

  • Vector stores with semantic search: Memories are embedded into vectors and retrieved by meaning rather than by keyword. Best for free-form facts and knowledge that users might ask about in many phrasings.
  • Key-value or record stores: Structured facts — account number, plan tier, last order date — stored as fields that can be looked up exactly. Fast and precise, but brittle to paraphrase.
  • Files or documents: Larger reference material such as policies or manuals, retrieved whole or in sections. Simple, but with coarse granularity.
  • Conversation transcripts: The raw history of past sessions, often stored and searched when a user asks "what did we discuss last time?"

In Microsoft Foundry, agents can be connected to a memory store and given a memory search tool so that the agent itself decides when to look something up. That pattern is the subject of the next chapter's lab.

Summary

Memory is what makes an agent conversational rather than transactional. It follows a lifecycle of capture, store, retrieve, update, and forget; it comes in short-term and long-term forms; and it is always scoped to a conversation, user, agent, or project. Whatever the storage, the model ultimately reads memory as tokens in its context window, which is why retrieval precision and token discipline matter so much.
