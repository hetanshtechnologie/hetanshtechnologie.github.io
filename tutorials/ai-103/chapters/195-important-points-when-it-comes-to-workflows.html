Important points when it comes to workflows

Workflows are where agents stop being demos and become processes. A workflow turns a multi-step job — triage an invoice, extract its data, check it against policy, approve or reject — into a defined sequence of steps with explicit inputs, outputs, and failure handling. This chapter gathers the important points you need to keep in mind when designing, building, and operating such workflows, drawing on the patterns used throughout the CloudXeus project.

What a Workflow Is

A workflow is a chain of steps where each step consumes the previous step's output and produces the next step's input. Each step can be an LLM call, a tool invocation, a retrieval, a condition, or plain code. Unlike a single prompt, a workflow makes the process inspectable: you can see which step ran, what it decided, and where it failed.

The difference between an agent and a workflow is control. An agent decides its own path at runtime, which is flexible but harder to audit. A workflow fixes the path, which is predictable and auditable. Use agents when the path is unknowable in advance; use workflows when the steps are stable and must be controlled.

Design with Single-Purpose Steps

The most important design rule is to keep steps small and single-purpose. A step that extracts fields does one thing; a step that checks policy does another. Single-purpose steps give you three benefits:

  • Reuse: the same extraction step can serve other workflows.
  • Testing: each step is testable in isolation with its own fixtures.
  • Debugging: when output is wrong, the failing step is the one that produced it.

Define the Data Contract Between Steps

Every step needs a clear interface: a defined input shape and a defined output shape. For the invoice workflow, the extraction step always outputs a JSON object with fields like invoice_number and total_amount — never free-form text. Consequences of a good contract:

  • Steps compose without guesswork; the policy check reads total_amount because it is guaranteed to exist.
  • You can validate each step's output and fail fast instead of propagating garbage.
  • You can swap an LLM step for a code step without changing the rest of the chain.

Validate at the boundaries. After the extraction step, check that the required fields are present and that amounts are numbers. Catching a bad shape here is far cheaper than discovering it three steps downstream.

Plan for Errors, Retries, and Timeouts

Every step can fail, and most failures are transient. Decide per step:

  • Retry policy: network blips and throttling usually recover on retry — retry with backoff.
  • Max attempts: cap retries so a stuck step does not burn budget forever.
  • Timeouts: LLM calls and long document analyses should have explicit limits.
  • Fallback output: define what a step emits on terminal failure — often an error payload that later steps understand, rather than an exception that crashes the whole flow.

Do not let an error surface as a hallucinated answer. If the policy-check step fails, the workflow must end in an explicit "needs manual review" state — not quietly emit a decision nobody can trust.

Use Conditionals for Branching

Not every document follows the same path. Conditionals route based on step output: if the extraction confidence is low, send the document to human review; if the total exceeds a threshold, escalate for approval; if the document was not an invoice, terminate. Each branch is a first-class path with its own outcome, so the workflow produces clear, inspectable results for every input class.

Make the Flow Observable

A workflow you cannot inspect is a workflow you cannot trust. Log the essentials for each run:

  • The input and output of every step.
  • The decision taken at every conditional.
  • Token usage and latency per LLM call.
  • The final outcome and any manual-review flags.

Foundry tracing shows this automatically for agent runs; apply the same discipline to hand-built workflows so every execution has a story you can replay.

Watch Cost and Performance

Workflows multiply costs: a six-step flow calls a model several times per document. Keep the economics visible:

  • Use small models for simple steps and large models only where reasoning demands them.
  • Short-circuit: if a step's output makes later steps unnecessary, branch out early.
  • Cache stable results — a policy decision that does not change should not be recomputed for every document.
  • Monitor per-step latency; a slow step hides the real cost center of your flow.

Review the Important Points

When you design a workflow, check it against this list:

  • Is each step single-purpose and reusable?
  • Does every step have a defined input and output contract?
  • Are outputs validated at step boundaries?
  • Does every step have retries, a cap, and a timeout?
  • Is every failure path an explicit outcome, not a crash?
  • Do conditionals cover every document class you expect?
  • Is the whole flow traceable and logged?
  • Are model choices and costs deliberate per step?

Summary

Workflows turn multi-step jobs into inspectable processes. The important points are consistent: keep steps single-purpose, define contracts between them, plan for failure explicitly, branch with conditionals, log everything, and watch cost per step.
