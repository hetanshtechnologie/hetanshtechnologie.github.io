The Authentication Methods for OpenAPI Tools

An OpenAPI tool is a remote call your agent makes with real credentials. How those credentials travel to the API is decided by the authentication method you configure on the agent connection. This chapter explains the methods Foundry supports, when each is appropriate, and how to choose for a service like the CloudXeus orders API.

Why the Agent Connection Needs Authentication

Your function app accepts anonymous requests today, which means anyone can list and cancel orders. To make the API private you must do two things: require a credential at the API side, and teach the agent connection how to present that credential on every call. The authentication method is the bridge between the two.

The Methods at a Glance

API Key in a Header

For a function app guarded by keys, the header method is the natural fit. Azure Functions expects a key in the x-functions-key header:

  • Configure the connection with header name x-functions-key and value YOUR_FUNCTION_KEY.
  • Every request the agent makes automatically includes that header.
  • The key is stored in the agent's connection settings, not in the OpenAPI document.

Because the key lives in the connection configuration rather than the spec, you can rotate keys or point the connection at a new environment without touching the OpenAPI file. Keep that separation clean and rotating secrets stays a one-field change.

API Key in a Query Parameter

Some services accept the key as a query parameter, and Azure Functions also honors ?code= for host-level keys. This method is convenient but leaks the secret into URLs, which end up in logs and proxies. Prefer the header form whenever the API allows it.

Bearer Token and OAuth 2.0

Enterprise APIs typically require a short-lived access token rather than a static secret. The agent connection can hold the client credentials and fetch a token from your identity provider, or you can supply a token from your own flow. This is more setup but supports rotation and scoped permissions, which makes it the right choice for production systems shared across teams.

Managed Identity

When both the agent platform and the target service run on Azure, a managed identity can authenticate without any stored secret. The platform requests a token for its identity, and the API grants access through role assignments. This is the strongest option because there is no shared secret to steal or rotate, and access is revoked by removing the role.

For the CloudXeus course project, an API key in a header is the right level: it is simple, matches how Azure Functions keys work, and demonstrates the exact mechanics you will configure in the next chapter. Managed identity and OAuth are production-grade upgrades you reach for when the project grows.

Security Considerations

  • Use the least privilege the tool needs: read-only operations with a read-only key, write operations with a key that can only mutate what it must.
  • Rotate keys regularly and use the second key slot when rotating so the agent keeps working during the switch.
  • Keep the key out of the OpenAPI document, out of chat messages, and out of logs.
  • If an API is accidentally exposed, changing the key invalidates every stolen copy at once.

Never ask the model to fetch or reveal the key. The key is presented by the platform on the agent's behalf; if you ever see the key value in a conversation, treat it as a leak and rotate it immediately.

Summary

OpenAPI tool connections support several authentication methods, from none to fully managed identity. The API key in a header is the pragmatic choice for Azure Functions and the one you will configure for CloudXeus.
