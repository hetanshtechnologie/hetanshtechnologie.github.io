Agent Tracing - Concepts and Overview

An agent is a program that makes many small decisions in sequence — it calls a model, decides a tool is needed, runs the tool, feeds the result back, and repeats until it answers. When something goes wrong, a single log line cannot explain it; you need the whole story of that run. Tracing is how you capture that story. This chapter introduces the core concepts of tracing — traces, spans, and their attributes — and explains how they make agent behaviour inspectable, especially through Application Insights and OpenTelemetry-style instrumentation.

From Log Lines to Traces

A traditional log is a single event: request received, error 500, tool finished. For a linear service, stitching these events together in time is usually enough. An agent is different: it loops, it calls tools that take variable time, and it can spawn several parallel operations. You need to see the causal structure — which operation caused which, what each returned, and how long each took — not just a chronological list. That causal structure is a trace.

A trace represents one end-to-end unit of work, such as a single user question processed by the agent. Everything the agent does to answer that one question belongs to the same trace, even if it involves multiple model calls and several tools.

Spans: The Building Blocks of a Trace

A trace is made of spans. A span is a single operation inside the trace, with a start time, an end time, a name, and attributes describing what happened. Spans nest: one span can be the parent of several children. For a support agent, a typical trace might contain:

  • A root span representing the whole user turn.
  • Child spans for the first model call and for a retrieval tool.
  • A nested span for the tool's internal processing, and another for the second model call that writes the final answer.

Because spans are nested, a tool that hangs or a model call that returns garbage is easy to isolate: you look at the span where the anomaly appears and read its attributes.

What Attributes a Span Carries

Attributes are the key-value pairs that make a span useful. A well-instrumented span records at least:

  • Identity: trace ID, span ID, parent span ID, service name.
  • Timing: start time, duration, end status.
  • Context: the conversation or session ID, the application version, and any custom tags.
  • Payload: for model calls, the prompt, response, token counts, and finish reason; for tools, the arguments and return value.

This is the data that lets you replay a failure after the fact. Without attributes, a trace tells you what ran; with them, it tells you what was seen and decided.

How Tracing Reaches Application Insights

In the continuous evaluation labs, your agent reported to Application Insights. The standard path is OpenTelemetry: the agent's instrumentation library emits spans and metrics using the OpenTelemetry protocol, and an exporter forwards them to Application Insights, which stores them as trace, dependency, and request records. Foundry agents have this wiring built in, so enabling the connection was mostly configuration rather than hand-written code.

The important consequence is that trace data and evaluation data live side by side. You can query a conversation, jump to its trace, see the exact tool sequence, and correlate that with the evaluation score for the same conversation — a combination that turns a low score into a concrete diagnosis.

What to Look For in an Agent Trace

When you open a trace, keep a short checklist in mind:

  • Did the loop terminate? A trace with an unusually large number of model or tool spans suggests the agent never reached a final answer and kept iterating.
  • Did every tool return successfully? A tool span with an error status explains missing context.
  • Were there wasted calls? Repeated identical tool calls signal a prompt or routing problem.
  • Where did the time go? Latency is usually dominated by model calls; a slow tool is the exception worth investigating.
  • Was the answer grounded in what was retrieved? Compare the final model span's context with the response to spot hallucination.

Make traces linkable from user feedback. If a user marks an answer as poor, log the trace ID alongside the feedback. Later you can open the exact trace, see the full reasoning path, and fix the real cause instead of guessing.

Trace payloads can contain full prompts, retrieved documents, and user questions — all potentially sensitive. Set retention and access policies on the Application Insights workspace, redact secrets, and avoid logging raw credentials or PII in span attributes unless you have a compliance reason and appropriate protection.

Summary

Tracing captures the causal structure of a single agent run as a tree of nested spans, each carrying timing, identity, and payload attributes. OpenTelemetry instrumentation streams these spans to Application Insights, where they join evaluation data in one place. With traces you can answer the questions metrics cannot: which tools ran, what they returned, why the loop continued, and where the answer lost its grounding.
