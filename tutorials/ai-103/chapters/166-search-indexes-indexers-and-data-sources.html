Search Indexes, Indexers, and Data Sources

Azure AI Search is easy to use once you understand its three core moving parts. The data source tells the service where your content lives, the index defines what is stored and how it is searched, and the indexer moves content from the first to the second on a schedule. This chapter explains each component, how they connect, and the design decisions that determine search quality.

The Data Source

A data source is a connection definition. It names a location where documents are stored — typically an Azure Blob Storage container, but also databases, tables, and other supported sources — and the credentials the service uses to read it. Nothing is moved when you create a data source; it is simply a pointer plus connection information.

A typical data source definition includes:

  • The connection string or the storage account and access method (key, SAS token, or managed identity).
  • The container and an optional path or query that selects which files to read.
  • Optionally, a file-extension filter so only supported documents are picked up.

Prefer managed identity over shared keys where possible. It avoids storing secrets in connection strings and is the more secure pattern for production pipelines.

The Index

The index is the searchable store. It has two aspects: a schema, which defines the fields of each document, and the documents themselves, which populate that schema. When you design an index, you decide what each field holds and how the search engine should treat it.

Every field carries attributes that control its behavior:

AttributeEffect
searchableThe field can be matched by search queries.
filterableThe field can be used in filter expressions (for example, date ranges).
sortableThe field can order results.
facetableThe field can drive faceted navigation.
retrievableThe field is returned in query results (defaults to true).

For RAG, indexes commonly include at least: a document key, the chunk text, an embedding vector of that chunk, and metadata such as the source file name, page number, or title. The embedding vector is what powers vector search; the metadata is what powers filters and lets you cite sources in answers.

Keep searchable fields minimal. Every field marked searchable costs storage and indexing time. Only text fields that users might search should be searchable; numeric codes and metadata usually only need to be filterable and retrievable.

The Indexer

An indexer is the worker that reads from a data source and writes into an index. It is the only component that actively moves data. An indexer definition specifies:

  • Which data source to read.
  • Which index to write into.
  • How to map source content to index fields (the field mappings).
  • Optionally, a schedule so new documents are picked up automatically.
  • Optionally, a skillset that enriches documents with AI before they are stored.

Indexers make the pipeline self-maintaining. Upload a new document to blob storage, and the next scheduled run indexes it without any manual step.

How the Three Components Work Together

Think of the flow as an assembly line:

  1. A document lands in the data source (for example, a PDF in a blob container).
  2. The indexer runs, picks up the new document, and reads it.
  3. Optional skillsets enrich it — extracting text, creating chunks, generating embeddings.
  4. The indexer writes the resulting fields into the index.
  5. Query-time requests search the index and return the best matches.

You can also upload documents directly to an index through the REST API, without an indexer. Indexers exist for convenience and scale — use them when content arrives in bulk or changes over time, and reserve direct uploads for one-off or streaming scenarios.

Design Decisions That Matter

A few choices made while designing these components have outsized impact on RAG quality:

  • Chunking: how you split documents affects whether the right information is found. Too-large chunks dilute relevance; too-small chunks lose context.
  • Embedding field: storing a vector per chunk enables semantic search. The field must use the same model at query time as at index time.
  • Metadata: keeping the source path, title, and page in the index lets you cite answers and filter results.
  • Refresh strategy: a schedule determines how quickly new or changed documents become searchable.

Summary

Azure AI Search rests on three components: data sources point at your content, indexes define and store what is searchable, and indexers move content between the two. The index schema's field attributes decide how content can be searched, filtered, and returned, while the indexer's schedule keeps the data current.
