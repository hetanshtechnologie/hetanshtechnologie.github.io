Lab - Model Router in Microsoft Foundry

In this lab you will build a working model router. You will create a simple routing service in Python that examines each request, decides which of two deployments should answer it, forwards the call, and records which route was chosen. This mirrors what Foundry's router does under the hood and gives you a clear mental model of the concepts from the previous chapter. When you finish, you will have a small reusable router you can extend with semantic rules.

What You Need Before Starting

  • Python 3.9 or newer and VS Code.
  • Two chat model deployments in your Foundry project — for example gpt-4o-mini as the fast/cheap route and gpt-4o as the powerful route.
  • The endpoint and key for your Azure OpenAI resource.
  • The openai Python SDK installed, as in earlier labs.

If you only have one deployment, the lab still works — just configure the second route to point at the same deployment. The routing logic is what matters here.

Designing the Router

The router makes one decision per request: which deployment should answer this message? For this lab we use a simple rule — short, factual messages go to the small model; long or complex requests go to the powerful model. The router checks the message length and a small set of keywords to make the decision, then calls the chosen deployment and logs the outcome.

Setting Up the Project

Step 1 - Create the project folder

Create a folder named ai103-model-router and open it in VS Code. Create a Python file called router.py.

Step 2 - Set your credentials

In the integrated terminal, set the environment variables the script will read:

$env:AZURE_OPENAI_ENDPOINT = "https://YOUR-RESOURCE.openai.azure.com/"
$env:AZURE_OPENAI_KEY = "YOUR_KEY"

Step 3 - Write the router

Paste the following code into router.py. Replace YOUR_FAST_DEPLOYMENT and YOUR_POWERFUL_DEPLOYMENT with the names of your two deployments:

from openai import AzureOpenAI
import os

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

FAST = "YOUR_FAST_DEPLOYMENT"
POWERFUL = "YOUR_POWERFUL_DEPLOYMENT"

COMPLEX_KEYWORDS = ["refund", "contract", "cancel", "bug", "escalate"]


def choose_route(message):
    if len(message) > 200:
        return POWERFUL
    for word in COMPLEX_KEYWORDS:
        if word in message.lower():
            return POWERFUL
    return FAST


def ask(message):
    deployment = choose_route(message)
    print(f"[route] {deployment}")
    response = client.chat.completions.create(
        model=deployment,
        messages=[
            {"role": "system", "content": "You are a concise support assistant."},
            {"role": "user", "content": message},
        ],
    )
    return response.choices[0].message.content


if __name__ == "__main__":
    while True:
        msg = input("\nYour question (or 'quit'): ")
        if msg.lower() == "quit":
            break
        print(ask(msg))

Step 4 - Run and test the router

python router.py

Send a short question such as "What are your opening hours?" and confirm the fast route is chosen. Then send a long or keyword-bearing message such as "I need to cancel my contract and request a refund for the unused months" and confirm the powerful route handles it.

Recording Routing Decisions

A router that does not log its decisions is a router you cannot debug. Add structured logging of each decision so you can see the traffic mix later:

import json


def ask(message):
    deployment = choose_route(message)
    decision = {
        "message_length": len(message),
        "route": deployment,
        "keywords_hit": [w for w in COMPLEX_KEYWORDS if w in message.lower()],
    }
    print("[decision]", json.dumps(decision))
    response = client.chat.completions.create(
        model=deployment,
        messages=[
            {"role": "system", "content": "You are a concise support assistant."},
            {"role": "user", "content": message},
        ],
    )
    return response.choices[0].message.content

In a production version, write this decision record to your application telemetry — for example Application Insights or a log workspace — instead of the console. That way you can chart the share of requests each route handles and spot when the powerful model is being overused.

Adding a Capacity Fallback

The next improvement is a fallback: if the chosen deployment fails or is throttled, the router retries on the other deployment so the user still gets an answer. Wrap the call in a small retry loop:

def ask(message):
    deployment = choose_route(message)
    for attempt in (deployment, POWERFUL if deployment == FAST else FAST):
        try:
            response = client.chat.completions.create(
                model=attempt,
                messages=[
                    {"role": "system", "content": "You are a concise support assistant."},
                    {"role": "user", "content": message},
                ],
            )
            return response.choices[0].message.content
        except Exception as ex:
            print(f"[fallback] {attempt} failed: {ex}")
    return "I could not reach a model right now. Please try again."

Fallbacks can mask real problems. If throttling is caused by a quota issue, the fallback keeps the user happy but the underlying cost or capacity problem remains. Always alert on fallback frequency rather than treating it as normal operation.

Summary

You built a working model router that picks a fast or powerful deployment based on request length and keywords, logs every routing decision, and falls back when the primary route fails. You also saw how the decision log feeds monitoring and how fallbacks protect users while surfacing capacity problems. This is the same pattern Foundry's router productizes for you.
