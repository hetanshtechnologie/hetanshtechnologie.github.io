Azure Open AI and Azure AI Foundry

Two names appear constantly in this course: Azure OpenAI Service and Microsoft Foundry (also branded as Azure AI Foundry). They are related but not the same thing. This chapter explains what each is, how they fit together, and when you reach for which one.

Azure OpenAI Service

Azure OpenAI Service hosts OpenAI's models — the GPT families and others — as managed endpoints inside your Azure subscription. It is OpenAI's technology delivered with Azure's enterprise plumbing:

  • Same model families you already used on the OpenAI platform, accessed with nearly identical API conventions.
  • Regional hosting under your control, so data can stay where your compliance requires.
  • Enterprise identity and security through Microsoft Entra ID, private networking, and managed keys.
  • Content filtering configurations that you can tune per deployment.
  • Contractual commitments on availability and support that public platforms do not offer.

The core job of Azure OpenAI Service is simple to state: give applications a dependable, governed way to call generative models. You create an Azure OpenAI resource, deploy a model into it, and call the resulting endpoint with your keys or an identity token.

Microsoft Foundry

Microsoft Foundry is the broader platform that surrounds those models. Where Azure OpenAI Service is a model-hosting service, Foundry is a development environment for building, testing, evaluating, and operating AI applications end to end. Its major areas include:

  • Model catalog: browse OpenAI models, Microsoft models, and open models from many providers, and deploy any of them to an endpoint.
  • Playground: chat with deployed models interactively, adjust parameters, and compare behaviors without writing code.
  • Prompt flow: build multi-step application logic as flows that connect models, data, and tools.
  • Evaluations: run test datasets against your application and measure quality metrics.
  • Connections and data: attach data sources and services — including Azure OpenAI Service resources — to your project.
  • Deployment management: track every model deployment, its endpoint, quota, and cost.

Branding in this space evolves. "Azure AI Foundry" is the current name for the platform sometimes referred to as the AI Foundry portal, and it is the successor to earlier tooling such as Azure AI Studio. If you see an older term, it is the same family of tooling.

How They Relate

Think of Foundry as the workshop and Azure OpenAI as the machines inside it. Foundry manages and orchestrates; Azure OpenAI (and other services) executes. Concretely:

  • A Foundry project can connect to an Azure OpenAI resource — either one you created yourself or one you let Foundry create for you — and deploy models into it.
  • The model deployments you make from the Foundry portal live in that underlying resource, and you can see the same deployment in the Azure portal.
  • Your application code calls the deployment endpoint using the same chat-completions conventions you learned on the OpenAI platform.

So in the labs you will often do two things that look similar but are different layers: create a Foundry hub and project (your workspace), and deploy a model (a callable endpoint in an Azure OpenAI or Azure AI resource). Both are required.

Which One Do You Use When

  • If you only need to call a hosted GPT model from code with enterprise controls, Azure OpenAI Service is the direct path.
  • If you are exploring models, prototyping, evaluating quality, or building a multi-step application, start in Foundry — it wraps and manages the underlying model service.
  • For most of this course you will operate through Foundry and let it manage the underlying Azure OpenAI resource, so you get the platform benefits and the raw API access together.

Summary

Azure OpenAI Service hosts OpenAI's models with Azure's enterprise controls, while Microsoft Foundry is the platform that wraps those models with a catalog, playground, flow, and evaluation tooling. They work together: Foundry manages deployments that live in an underlying model resource, and your code calls those deployments with familiar chat-completion conventions. In the next chapters you will create the Foundry resources these workflows depend on.
