Calling an Azure MCP Server - Primer

Azure offers MCP servers that expose its AI services — language, speech, computer vision, and more — as standard MCP endpoints. This chapter is a primer: it shows what an Azure MCP server looks like, how a client connects, and the sequence of calls your code will make. The next chapters turn each of these steps into a hands-on lab.

What an Azure MCP Server Looks Like

An Azure MCP server is a small service — typically containerized and hosted in a platform like Azure Container Apps — that wraps one or more Azure AI services behind the MCP protocol. Instead of calling the language service REST API directly, your agent calls a tool exposed by the server, and the server makes the Azure call for you. The server owns the authentication to Azure, so your client does not need Azure keys at all.

Azure MCP serverExample tools it exposes
Azure Language serverTranslate text, detect language, analyze sentiment, extract entities
Azure Speech serverSpeech-to-text, text-to-speech, speech translation
Azure Vision serverImage analysis, OCR, captioning

Think of the server as an adapter between the MCP world and Azure's own APIs. Your agent speaks MCP; the server translates into Azure REST calls and translates the results back. This is the same "one server, many consumers" benefit from the previous chapter, applied to Azure services.

The Connection Sequence

Every client-server session follows the same outline:

  1. Connect: the client opens a transport to the server's endpoint (HTTP in the hosted case) and performs the MCP handshake — exchanging protocol version and capabilities.
  2. Initialize: the server announces what it supports. The client records the server's capabilities.
  3. Discover tools: the client requests tools/list and receives the server's tool catalog with schemas.
  4. Call tools: for each tool the model wants, the client sends tools/call with a name and arguments, and receives structured results.

The protocol layer is identical regardless of which Azure service sits behind the server. Only the tool names and arguments differ.

Authentication in Two Layers

Calling an Azure MCP server involves authentication at two distinct boundaries:

  • Client to server: the HTTP connection may require an API key or an Azure identity token so only authorized clients can reach the endpoint. This is configured when the server is deployed.
  • Server to Azure: the server authenticates to the Azure service it wraps, typically with a managed identity assigned to the server's hosting environment. Your code never sees those credentials.

Do not store Azure resource keys in your client. The whole point of the managed-identity pattern is that credentials live only on the server side. If your client needs a secret, it is the server's access key — keep it in a place your agent code controls, such as an environment variable or a secret store.

Discovering Tools from Python

The official MCP Python SDK makes the client side short and readable. Listing tools looks like this:

import asyncio

from mcp import ClientSession, StdioServerParameters
from mcp.client.sse import sse_client


async def list_tools(server_url: str):
    transport = sse_client(server_url)
    read, write = await transport.__aenter__()
    async with ClientSession(read, write) as session:
        await session.initialize()
        tools = await session.list_tools()
        for tool in tools.tools:
            print(tool.name, "-", tool.description)


asyncio.run(list_tools("http://YOUR_SERVER_ENDPOINT/sse"))

The ClientSession handles the handshake, initialize() negotiates capabilities, and list_tools() returns the catalog. Once you have the catalog, calling a tool is a single method:

result = await session.call_tool("translate_text", {"text": "Hello", "to": "es"})

Feeding Tools to a Model

An MCP connection only becomes an agent when the discovered tools are given to a model. The standard loop from earlier chapters applies: convert each tool's name, description, and input schema into a binding for your LLM, let the model decide, execute the call through MCP, and return the result. The MCP SDK even ships helpers to convert its tool objects into the schema shape that models expect, so the two worlds connect cleanly.

What Can Go Wrong

When a call fails, the usual suspects are:

  • Connection errors: the server is unreachable, the endpoint URL is wrong, or the server is still starting up.
  • Authentication failures: the server's access key is missing, wrong, or the identity has no permission to the underlying Azure service.
  • Schema mismatches: your call passes arguments that do not match the tool's input schema.
  • Azure-side errors: the underlying service is unavailable or out of quota; the server usually relays the error text in the tool result.

Start debugging with tools/list. If discovery works, transport and authentication are fine, and the problem is in the call. If discovery itself fails, the issue is connectivity or credentials — check the server endpoint and access key first.

Summary

An Azure MCP server wraps Azure AI services behind the standard MCP protocol, so an agent can translate text, analyze images, or synthesize speech with ordinary tool calls. The client connects, initializes, discovers tools, and calls them; authentication splits into a client-to-server key and a server-to-Azure managed identity.
