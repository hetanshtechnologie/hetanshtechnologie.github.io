Lab - Talking to our custom MCP server

Your custom MCP server exists and runs. In this final lab of the section you will connect to it, call its tools, and wire it into a LangChain agent — closing the loop you opened several chapters ago. You will connect over both stdio and HTTP, so you see both transports working with your own tools.

Prerequisites

  • The my_mcp_server.py file and environment from the previous lab.
  • mcp, langchain, and langchain-openai installed.
  • Your Foundry chat deployment details in a .env file for the agent step.
  • The server either running locally on localhost:8080 (SSE) or deployed to Container Apps.

If you are testing against the HTTP transport, make sure the server process is still running in its other terminal. If it crashed, restart it before continuing — the client cannot start it for you.

Step 1: Call the Server over stdio

Exercise 1: Connect and invoke a tool on a local process

Create stdio_client.py:

import asyncio

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client


async def main():
    server_params = StdioServerParameters(
        command="python",
        args=["my_mcp_server.py"],
    )

    read, write = await stdio_client(server_params)
    async with ClientSession(read, write) as session:
        await session.initialize()

        tools = await session.list_tools()
        print("Tools on the server:", [t.name for t in tools.tools])

        result = await session.call_tool("lookup_contact", {"name": "Sam"})
        print("lookup_contact:", result.content[0].text)

        result = await session.call_tool("evaluate_expression", {"expression": "(2 + 3) * 4"})
        print("evaluate_expression:", result.content[0].text)


asyncio.run(main())

Run it from the same folder as your server:

python stdio_client.py

The client launches your server as a subprocess, discovers both tools, calls them, and prints the results. You just exercised the full MCP protocol against code you wrote.

Notice the client and server are separate processes speaking the same protocol. That separation is the whole point of MCP — your server can be replaced, moved, or upgraded without the client changing a line.

Step 2: Call the Server over HTTP

Exercise 2: Reach the same tools over SSE

Create sse_client.py — the exact pattern you used with the Azure server, but pointed at your own endpoint:

import asyncio

from mcp import ClientSession
from mcp.client.sse import sse_client

SERVER_URL = "http://localhost:8080/sse"


async def main():
    read, write = await sse_client(SERVER_URL)
    async with ClientSession(read, write) as session:
        await session.initialize()
        result = await session.call_tool("lookup_contact", {"name": "Mira"})
        print("lookup_contact:", result.content[0].text)

        result = await session.call_tool("evaluate_expression", {"expression": "7 * 6"})
        print("evaluate_expression:", result.content[0].text)


asyncio.run(main())

Run it:

python sse_client.py

The same tools, same protocol — only the transport changed. If your server is deployed to Container Apps, substitute the container's URL plus /sse.

Comparing the two clients is instructive: the only differences are the connection setup. Everything after ClientSession — initialize, list tools, call tools — is identical. That transport independence is a direct benefit of the protocol's design.

Step 3: Wrap the Tools for an Agent

Now bridge your server into a LangChain agent, exactly as you did for the Azure server. The wrapper turns each MCP tool into a callable the model can invoke:

from langchain_core.tools import StructuredTool


def make_langchain_tool(session: ClientSession, mcp_tool):
    async def _run(**kwargs):
        result = await session.call_tool(mcp_tool.name, kwargs)
        return "\n".join(
            block.text for block in result.content if block.type == "text"
        )

    return StructuredTool(
        name=mcp_tool.name,
        description=mcp_tool.description,
        coroutine=_run,
    )

Step 4: Run the Agent

Exercise 3: Ask the model questions that need your server

Create agent_with_my_server.py:

import asyncio
import os

from dotenv import load_dotenv
from langchain.agents import AgentExecutor, create_tool_calling_agent
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import AzureChatOpenAI
from mcp import ClientSession
from mcp.client.sse import sse_client

load_dotenv()

SERVER_URL = "http://localhost:8080/sse"


async def run():
    read, write = await sse_client(SERVER_URL)
    async with ClientSession(read, write) as session:
        await session.initialize()
        tools = await session.list_tools()
        langchain_tools = [make_langchain_tool(session, t) for t in tools.tools]

        model = AzureChatOpenAI(
            azure_endpoint=os.getenv("AZURE_OPENAI_ENDPOINT"),
            api_key=os.getenv("AZURE_OPENAI_API_KEY"),
            api_version=os.getenv("AZURE_OPENAI_API_VERSION"),
            deployment_name=os.getenv("AZURE_OPENAI_DEPLOYMENT_NAME"),
            temperature=0,
        )

        prompt = ChatPromptTemplate.from_messages([
            ("system", "Use your tools when they help. You can look up contacts and evaluate arithmetic."),
            ("human", "{input}"),
            ("placeholder", "{agent_scratchpad}"),
        ])

        agent = create_tool_calling_agent(model.bind_tools(langchain_tools), langchain_tools, prompt)
        executor = AgentExecutor(agent=agent, tools=langchain_tools)

        for question in [
            "What is the email address for HetanshTechnologie?",
            "Compute the result of (8 + 2) * 3.",
            "What is 5 * 5?",
        ]:
            result = await executor.ainvoke({"input": question})
            print(f"\nQ: {question}\nA: {result['output']}")


asyncio.run(run())

Run it:

python agent_with_my_server.py
  1. The contact question should route through lookup_contact and return the email address from your in-memory directory.
  2. The expression question should route through evaluate_expression and return 30.
  3. The plain arithmetic question should be answered directly — the model recognizes no tool is needed.

Watch the sequence closely: the model emits a tool call, the agent executes it through your MCP server, the result comes back, and the model composes the final answer. Your own server now occupies the exact role the Azure server played two labs ago — proof that the whole pattern is transport- and implementation-agnostic.

Step 5: Deploy the Same Agent Against the Hosted Server

If you containerized and deployed your server in the previous lab, point SERVER_URL at the deployed FQDN and rerun the agent. Add an access key header if you configured one. Nothing else changes — the agent works identically against the local and hosted servers. This is the payoff of the architecture: the code you wrote for a local process scales to a cloud deployment without redesign.

When you are done, stop the local server and delete any container app you deployed. Both the running process and the cloud service consume resources — the former on your machine, the latter against your Azure subscription.

You also verified the identical code works against a hosted deployment.
