Knowledge source pre-requisites - Assigning permissions

The knowledge base pipeline crosses several Azure services, and each hop needs permission: the search indexer reads blobs, the embedding skill calls the embedding model, and the agent queries the index. The secure way to grant these is with managed identities and role assignments — no connection strings or keys embedded in code. This chapter creates those identities and grants exactly the roles each one needs.

Who Needs What

Three identities participate in the capstone. Each gets only the role its work requires, following the principle of least privilege:

IdentityNeeds access toRole
Search service (system-assigned identity)The blob container with course PDFsStorage Blob Data Reader
Search service identityThe embedding model deploymentCognitive Services OpenAI User
The agent's identityThe search indexSearch Index Data Reader

For local development, the agent's identity is usually you: the Azure CLI user running the Python scripts. The last step grants your signed-in user the read role on the index, which is the lab equivalent of assigning it to a production identity.

Step 1 - Enable the Search Service Identity

Give the search service a system-assigned managed identity, then capture its principal id — the Azure object that roles are assigned to:

az search service update `
  --name $searchName `
  --resource-group $rg `
  --identity-type SystemAssigned

$searchPrincipalId = az search service show `
  --name $searchName `
  --resource-group $rg `
  --query identity.principalId -o tsv

Write-Output "Search principal: $searchPrincipalId"

Step 2 - Let the Search Service Read the Blobs

Assign the Storage Blob Data Reader role at the storage account scope, so the indexer can read the course PDFs:

$subId = (az account show --query id -o tsv)

az role assignment create `
  --assignee $searchPrincipalId `
  --role "Storage Blob Data Reader" `
  --scope "/subscriptions/$subId/resourceGroups/$rg/providers/Microsoft.Storage/storageAccounts/$storageName"

Notice this role grants read only. The indexer never writes back to the source container, so data reader is the correct level. A data contributor role here would be excessive and is a common over-permissioning mistake.

Step 3 - Let the Embedding Skill Call the Model

Assign the Cognitive Services OpenAI User role on the Foundry AI resource that holds the embedding deployment. This lets the search service invoke the model without an API key in the skillset:

az role assignment create `
  --assignee $searchPrincipalId `
  --role "Cognitive Services OpenAI User" `
  --scope "/subscriptions/$subId/resourceGroups/$rg/providers/Microsoft.CognitiveServices/accounts/$aiResourceName"

Replace $aiResourceName with the name of your Foundry AI resource (the one from the model deployment chapter). With this in place, your skillset can switch from apiKey to a managed identity configuration.

The managed identity lives on the search service and is one configuration change away in the skillset: replace the apiKey field with the identity setup and the embedding skill authenticates without any secret. This is exactly how production enrichment pipelines are secured.

Step 4 - Let the Agent Read the Index

Grant read access to the search index. For the local labs, assign the role to your signed-in Azure CLI user:

$userObjectId = az ad signed-in-user show --query id -o tsv

az role assignment create `
  --assignee-object-id $userObjectId `
  --role "Search Index Data Reader" `
  --scope "/subscriptions/$subId/resourceGroups/$rg/providers/Microsoft.Search/searchServices/$searchName"

Search offers two index roles. Search Index Data Reader allows queries only; Search Index Data Contributor allows documents to be added and changed. Use the reader role for the agent and the contributor role only for code that loads documents, never for an interactive assistant.

Step 5 - Verify by Querying Without a Key

Role assignments can take a few minutes to propagate. Once they do, verify by authenticating with your identity rather than an API key. From Python, DefaultAzureCredential should now be enough to search the index:

from azure.identity import DefaultAzureCredential
from azure.search.documents import SearchClient

client = SearchClient(
    endpoint="https://YOUR_SEARCH_SERVICE.search.windows.net",
    index_name="docs-index-chunked",
    credential=DefaultAzureCredential(),
)

results = client.search(search_text="course", top=3)
for doc in results:
    print(doc["metadata_storage_name"])

If this returns documents, the permission chain works end to end with no key involved.

Troubleshooting

SymptomLikely causeFix
403 from DefaultAzureCredentialRole not propagated yet or missingWait a few minutes, then re-list the assignment.
Indexer cannot read blobsMissing Storage Blob Data ReaderConfirm the assignment at the storage account scope.
Embedding skill fails with auth errorOpenAI role missing or skillset still using a keyVerify the Cognitive Services OpenAI User assignment.
Role already existsAssignment created twiceAdd --skip-assignment or list and remove duplicates.

Summary

You enabled the search service's managed identity, granted it read access to the blob container and the embedding model, and gave your agent identity read access to the search index. The pipeline can now run without keys, and you verified it by querying the index with identity-based authentication.
