Introduction to LangGraph

LangChain's agent executor works well for simple tool loops, but many real applications need more control: branching, retries, cycles, checkpoints, and human approvals in the middle of a run. LangGraph is a framework, built on top of LangChain, that models agents as graphs. Instead of a hidden loop, you explicitly define nodes and edges — which makes complex behavior understandable, testable, and resumable. This chapter introduces the graph model and the vocabulary you need to build with it.

The Graph Mental Model

A LangGraph application is a directed graph. Work flows through nodes, and edges decide which node runs next. A node is any Python function that takes the current state and returns an update. An edge is a rule that decides the next node based on the state. The graph is compiled into a runnable object, and invoking it walks the state through the graph until a terminal condition is reached.

Compare this with the agent executor from the previous chapters. There, the loop was built in: call model, run tools, repeat. In LangGraph, you draw that loop. The framework does not assume a particular pattern — it gives you the machinery to express any pattern you can imagine.

State: The Heart of the Graph

Every node reads and updates a shared state. State is a typed object — typically a Pydantic model or a TypedDict — that travels through the graph and accumulates changes. For an agent, state usually holds the conversation messages, the list of tool calls so far, and the final answer.

from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    tool_calls: list

The Annotated[list, add_messages] annotation tells LangGraph how to merge updates from different nodes: new messages are appended rather than replacing the list. This reducer pattern is how LangGraph combines multiple state updates without losing information.

Nodes and Edges

A node is a plain function. It receives the current state and returns a dictionary of state updates:

def call_model(state: AgentState) -> dict:
    response = model.invoke(state["messages"])
    return {"messages": [response]}

def run_tools(state: AgentState) -> dict:
    outputs = []
    for call in state["messages"][-1].tool_calls:
        result = TOOL_EXECUTOR.invoke(call)
        outputs.append(result)
    return {"messages": outputs}

Edges connect nodes. A normal edge always goes from A to B. A conditional edge runs a routing function that looks at the state and returns the name of the next node:

def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    if last.tool_calls:
        return "tools"
    return "end"

Routing functions are what turn a linear chain into an agent. The model either requested tools — route to the tool node — or it produced a final answer — route to the end.

Building the Agent Graph

You assemble nodes and edges into a graph and compile it:

from langgraph.graph import StateGraph, START, END

graph = StateGraph(AgentState)
graph.add_node("model", call_model)
graph.add_node("tools", run_tools)
graph.add_edge(START, "model")
graph.add_conditional_edges("model", should_continue, {"tools": "tools", "end": END})
graph.add_edge("tools", "model")

agent = graph.compile()

Read the edges aloud and the agent's behavior is obvious: start at the model; if the model wants tools, run them, then go back to the model; if the model answers, stop. This explicit structure is why LangGraph applications are easier to reason about than loop-based agents.

Checkpoints: State with Memory

A unique capability of LangGraph is checkpointing. When you compile the graph with a checkpointer, every step's state is saved. That unlocks three powerful features:

  • Time travel: rerun a graph from any earlier step to inspect or branch from that point.
  • Persistence: pause a run, wait for input (such as a human approval), then resume.
  • Multi-turn memory: give each conversation a thread ID so a later turn can reload the full prior state.
from langgraph.checkpoint.memory import InMemorySaver

agent = graph.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "session-001"}}
result = agent.invoke({"messages": [{"role": "user", "content": "Hi"}]}, config)

The thread_id groups state across calls. Sending a second message with the same thread ID continues the same conversation, because the checkpointer restored the previous state before the run started.

Human-in-the-Loop

Because runs can be interrupted, LangGraph supports human approvals naturally. You mark an edge as interruptible; the graph stops before that node, exposes the pending update, and waits. A person reviews the tool call or the draft answer, approves or edits it, and the run continues. This is invaluable for workflows where a model should not act on its own — sending an email, charging a payment, or modifying a database.

The phrase graph can sound abstract, but you have already used the underlying ideas. The agent executor you built in the earlier lab is, functionally, a graph with two nodes and a conditional edge. LangGraph simply lets you open the hood.

When to Reach for LangGraph

Choose LangGraph when your workflow is more than a single loop:

  • Different user intents must take different paths (router-style behavior).
  • Human review is required at specific steps.
  • Conversations must resume reliably across sessions.
  • You need visibility into each stage and the ability to replay or fork a run.
  • Multiple agents cooperate, each owning a subgraph.

Summary

LangGraph models agent behavior as an explicit graph of nodes and edges operating on a shared state. Conditional edges create the agent loop, checkpoints add persistence and resumability, and interruptions enable human-in-the-loop workflows. It is a more expressive foundation than the fixed agent executor, at the cost of a little more design up front.
