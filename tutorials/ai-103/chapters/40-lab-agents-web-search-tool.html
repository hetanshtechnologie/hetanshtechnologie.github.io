Lab - Agents - Web Search tool

Your trip-planner agent knows a lot from its training data but nothing about what is current. If a customer asks whether a museum is open tomorrow, the agent has no honest way to answer. In this lab you will attach the Web Search tool to the agent, so it can look up fresh information instead of guessing — the first time your agent will actually do something beyond generating text.

Objectives

  • Attach a web search tool to your agent in the Foundry portal.
  • Test that the agent searches the web instead of answering from memory.
  • Repeat the same configuration in code using the Azure AI Projects SDK.

Step 1: Add Web Search in the portal

Start in the Foundry portal, where the tool is one checkbox away. Web Search runs on Bing grounding, and your Foundry project needs a connection to the Bing search service before the agent can use it.

Attach the tool in the portal

  1. Open your project in the Foundry portal and go to Agents.
  2. Open the trip-planner agent.
  3. Under Tools, enable Web Search. If prompted, select or create the Bing grounding connection.
  4. Save the agent. This creates a new version with the tool attached.

Step 2: Test that the agent really searches

The playground is the fastest way to verify the tool works. Ask a question whose answer changes regularly — something the model cannot possibly know from training data alone.

Probe the agent with a time-sensitive question

  1. Open the chat panel for the agent.
  2. Ask: What is today's weather forecast in Seattle?
  3. Watch the agent's answer. A correct tool-powered reply states the forecast and typically mentions it comes from a web source.
  4. Ask the same question a second time and confirm the answer stays current.

A good test question is one where the model would fail confidently without the tool. Weather, today's news, a sports score, or the current price of a product all work. If the agent answers with a plausible-sounding guess, the tool is not actually attached or the connection is misconfigured.

Step 3: Attach the tool from code

For code-managed agents, attach the tool through the SDK. The pattern is to fetch the Bing grounding connection from your project and wrap it in a tool definition, then pass that definition to the agent.

Create agent_with_search.py

import os
from dotenv import load_dotenv
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import BingGroundingTool

load_dotenv()

project_client = AIProjectClient.from_connection_string(
    credential=DefaultAzureCredential(),
    conn_str=os.getenv("PROJECT_CONNECTION_STRING"),
)

search_connection = project_client.connections.get(
    connection_name="YOUR_BING_CONNECTION_NAME"
)
search_tool = BingGroundingTool(connection_id=search_connection.id)

agent = project_client.agents.create_agent(
    model="YOUR_DEPLOYMENT_NAME",
    name="trip-planner-with-search",
    instructions=(
        "You are a travel planning assistant. Use web search whenever "
        "the customer asks about current facts such as opening hours, "
        "weather, prices, or events. Always prefer current information "
        "over memory for anything time-sensitive."
    ),
    tools=search_tool.definitions,
    temperature=0.5,
)

print(f"Agent created with web search: {agent.id}")

The Bing grounding connection is created once in your project and shared by all agents that need it. Look up its exact name in your project's connections page rather than guessing — connection names are case-sensitive identifiers that the SDK matches literally.

Step 4: Run the loop and observe a tool call

Extend the script (or reuse your invoke script) to send a time-sensitive question and print the run's steps. When the agent uses the tool, the run passes through requires_action while the search executes, and the final answer reflects the search results.

Invoke the agent and print the run steps

import time

thread = project_client.agents.create_thread()
project_client.agents.create_message(
    thread_id=thread.id,
    role="user",
    content="What events are happening in Paris this weekend?",
)

run = project_client.agents.create_run(
    thread_id=thread.id, agent_id=agent.id
)
while run.status in ("queued", "in_progress", "requires_action"):
    run = project_client.agents.get_run(
        thread_id=thread.id, run_id=run.id
    )
    time.sleep(1)

steps = project_client.agents.list_run_steps(
    thread_id=thread.id, run_id=run.id
)
for step in steps.data:
    print(step.type, getattr(step, "step_details", None))

In the output, one of the steps should be a tool_calls step with a search request. That is your proof that the model chose to search rather than guess.

Web Search consumes quota and can add latency to each answer. On an agent used by many customers, search costs add up quickly. Only attach the tool where current information genuinely matters, and review the telemetry to confirm searches happen for the right kinds of questions.

Summary

You gave your agent its first real capability by attaching Web Search, verified through time-sensitive questions that the model searches instead of fabricating, and reproduced the same configuration in code. The run's tool-call steps showed the agent deciding, on its own, to reach out to the web. Next you will build a custom function — a tool whose executor is code you write yourself.
