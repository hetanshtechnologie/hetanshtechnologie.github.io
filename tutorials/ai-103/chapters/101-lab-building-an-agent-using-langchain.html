Lab - Building an agent using LangChain

In this lab you will build a working agent in LangChain: a model that can call tools, observe the results, and answer accordingly. The agent you build will offer a currency-conversion helper and a weather placeholder, demonstrating the core tool-calling loop from the previous chapter. By the end you will have watched an agent decide to use a tool, and you will know how to extend the same pattern to your own functions.

What You Will Need

  • The Python environment you created in the getting-started lab, with langchain, langchain-openai, and python-dotenv installed.
  • Your Foundry chat deployment details stored in a .env file (endpoint, key, deployment name, API version).
  • langchain-community installed if you want to follow along with community tools, though this lab defines its own tools.

Reuse the same virtual environment from the previous lab. If you installed packages into a fresh environment, remember to install langchain and langchain-openai again before running this lab.

Step 1: Define Your Tools

Exercise 1: Create the tool functions

Create a file named tools.py with two tools the agent can use:

from langchain_core.tools import tool

@tool
def convert_currency(amount: float, from_currency: str, to_currency: str) -> str:
    """Convert an amount from one currency to another using a fixed sample rate."""
    rates = {"USD": 1.0, "EUR": 0.92, "GBP": 0.79, "JPY": 149.5}
    if from_currency not in rates or to_currency not in rates:
        return "Unsupported currency code."
    base = amount / rates[from_currency]
    converted = base * rates[to_currency]
    return f"{amount} {from_currency} = {converted:.2f} {to_currency}"

@tool
def get_weather(city: str) -> str:
    """Return a sample weather summary for a city."""
    return f"Sunny, 24 degrees Celsius in {city}. No precipitation expected."

Both functions use the @tool decorator, so LangChain automatically builds their descriptions and argument schemas for the model.

Notice that each function's docstring becomes the model's guide. A precise docstring that explains what the tool does and when to use it produces far better tool selection than a vague one. Write docstrings as if a stranger will read them — because the model will.

Step 2: Wire Up the Model and Agent

Exercise 2: Assemble the agent and executor

Create a file named agent.py in the same folder:

import os

from dotenv import load_dotenv
from langchain.agents import AgentExecutor, create_tool_calling_agent
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import AzureChatOpenAI

from tools import convert_currency, get_weather

load_dotenv()

model = AzureChatOpenAI(
    azure_endpoint=os.getenv("AZURE_OPENAI_ENDPOINT"),
    api_key=os.getenv("AZURE_OPENAI_API_KEY"),
    api_version=os.getenv("AZURE_OPENAI_API_VERSION"),
    deployment_name=os.getenv("AZURE_OPENAI_DEPLOYMENT_NAME"),
    temperature=0,
)

tools = [convert_currency, get_weather]
model_with_tools = model.bind_tools(tools)

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant. Use the provided tools when they help answer the question."),
    ("placeholder", "{chat_history}"),
    ("human", "{input}"),
    ("placeholder", "{agent_scratchpad}"),
])

agent = create_tool_calling_agent(model_with_tools, tools, prompt)
executor = AgentExecutor(
    agent=agent,
    tools=tools,
    max_iterations=5,
    verbose=True,
)

The temperature=0 setting makes the agent's decisions deterministic, which is helpful while you are learning. Production agents often use a small nonzero temperature to allow slightly more natural phrasing while still keeping tool selection reliable.

Step 3: Run the Agent

Exercise 3: Watch the agent decide

Add a small test section to the bottom of agent.py:

if __name__ == "__main__":
    questions = [
        "What is the weather like in Seattle?",
        "Convert 100 USD to EUR.",
        "Which is larger, 1200 or 900?",
    ]
    for question in questions:
        print("\n--- User:", question)
        result = executor.invoke({"input": question})
        print("Final answer:", result["output"])

Run the script from your activated environment:

python agent.py
  1. Watch the verbose output. For the weather and currency questions you should see the model emit a tool call, the executor run your Python function, and the model compose an answer from the returned text.
  2. For the pure arithmetic question, the model should answer directly without calling any tool. Noticing when not to use a tool is a sign the agent is working sensibly.
  3. Inspect the output — you should see the exact strings your tools returned, embedded in natural language answers.

If you see KeyError: 'agent_scratchpad' or a similar message, double-check that the prompt contains both placeholder messages. They are required — the executor injects the running tool-call trail there.

Step 4: Try a Multi-Step Request

Your tools are simple, but the agent can still chain them mentally. Ask it: "What is the weather in Chicago, and what is 50 USD in EUR?" The agent should call both tools — either in one turn or in sequence — and merge the results into a single answer. This demonstrates the loop from the previous chapter: each tool result becomes context the model can build on.

Because get_weather returns a fixed string, the agent's "weather report" is obviously fake. That is intentional for the lab — the point is the tool-calling mechanics, not meteorology. In a real system the function would call a live weather API and return real data.

Step 5: Extend with a Real API

To see how far the pattern goes, replace get_weather with a function that calls a public service such as the wttr.in weather service. A quick HTTP fetch inside the tool is all it takes:

import urllib.request

@tool
def get_weather(city: str) -> str:
    """Return a brief current-weather summary for a city using wttr.in."""
    url = f"https://wttr.in/{city}?format=%C+%t"
    with urllib.request.urlopen(url, timeout=10) as response:
        return response.read().decode("utf-8").strip()

Rerun the agent and ask about a city near you. The tool now returns real data, and the model wraps it in a natural answer. The agent structure did not change at all — you swapped one function for another and the whole loop kept working.

Summary

You built a complete LangChain agent with two custom tools, watched the model choose when to call them, verified that direct questions bypass the tools, exercised a multi-step request, and upgraded a placeholder tool to a live API call without changing the agent wiring. The same pattern — decorate a function with @tool, bind it to the model, create an executor — scales to arbitrarily many tools.
