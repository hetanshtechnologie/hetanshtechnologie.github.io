Azure Content Understanding - Custom Analyzer - Building the analyzer

With the invoice samples stored, you can now build the custom analyzer that extracts structured data from them. Azure Content Understanding lets you define a custom analyzer as a JSON schema of fields, configures OCR and layout options, and then runs that analyzer over documents through the portal or the REST API. This chapter walks through defining the invoice fields, registering the analyzer, and testing it against the stored samples.

The Parts of a Custom Analyzer

An analyzer definition has three parts that together describe what to look for and how to look:

  • Content type: what kind of input the analyzer expects — a document, an image, or an audio/video stream.
  • Configuration: processing options such as enabling OCR, choosing a language, and capturing layout.
  • Fields: the named pieces of information to extract, each with a type and a natural-language description.

Defining the Invoice Fields

For the CloudXeus invoice flow, the fields should capture what an accounts team actually needs. A solid starting set:

FieldTypeDescription
vendorstringCompany issuing the invoice
invoice_numberstringUnique invoice identifier
issue_datedateDate the invoice was issued
due_datedatePayment due date
tax_amountnumberTax charged on the invoice
total_amountnumberGrand total including tax

Write the field descriptions as precisely as you can. The extraction model reads those descriptions to decide what counts as a match, and vague descriptions are the most common source of wrong extractions.

Creating the Analyzer in the Portal

In the Content Understanding portal (or the Foundry project view for the resource):

  1. Open Analyzer templates and create a new analyzer named invoice-analyzer.
  2. Set the content type to document.
  3. Enable OCR and layout, and set the language to English.
  4. Add each field from the table above with its type and description.
  5. Save the analyzer, then run it against one of the stored invoices to confirm it returns sensible values.

Creating the Analyzer via the REST API

The same definition is portable as JSON, which is what you will ship in your automation. Save this as analyzer.json:

{
  "name": "invoice-analyzer",
  "contentType": "document",
  "description": "Extracts key fields from invoices",
  "config": {
    "ocr": true,
    "language": "en",
    "layout": true
  },
  "fields": {
    "vendor": { "type": "string", "method": "extract", "description": "Company issuing the invoice" },
    "invoice_number": { "type": "string", "method": "extract", "description": "Unique invoice identifier" },
    "issue_date": { "type": "date", "method": "extract", "description": "Date the invoice was issued" },
    "due_date": { "type": "date", "method": "extract", "description": "Payment due date" },
    "tax_amount": { "type": "number", "method": "extract", "description": "Tax charged on the invoice" },
    "total_amount": { "type": "number", "method": "extract", "description": "Grand total including tax" }
  }
}

Register it on your Content Understanding resource with a PUT request. In PowerShell:

$body = Get-Content -Raw analyzer.json
$headers = @{ "Content-Type" = "application/json"; "Ocp-Apim-Subscription-Key" = $env:CONTENT_UNDERSTANDING_KEY }
Invoke-RestMethod -Method Put `
  -Uri "$env:CONTENT_UNDERSTANDING_ENDPOINT/models/invoice-analyzer?api-version=2024-12-01-preview" `
  -Headers $headers -Body $body

Exercise 1: Register and test the analyzer

  1. Set the environment variables CONTENT_UNDERSTANDING_ENDPOINT and CONTENT_UNDERSTANDING_KEY to your resource's values.
  2. Save analyzer.json with the fields from the table above.
  3. Register the analyzer with the PUT call shown.
  4. Confirm the response contains the analyzer id and a status of READY.

Analyzing a Stored Invoice

With the analyzer registered, submit one of the stored samples and inspect the JSON result:

POST https://YOUR_ENDPOINT/models/invoice-analyzer:analyze?api-version=2024-12-01-preview

with the invoice file as the request body and the subscription key header set. The response nests the extracted data under the first document's fields object. Each field carries its value and a confidence score, for example:

"invoice_number": {
  "valueString": "INV-1042",
  "confidence": 0.98
},
"total_amount": {
  "valueNumber": 1249.75,
  "confidence": 0.95
}

Reviewing Extraction Quality

Run the analyzer over the whole stored set and look for patterns, not single failures:

  • Low confidence fields: describe the field more precisely or fix the source scan.
  • Consistent misreads: if totals are wrong only for scanned invoices, the problem is OCR, not the field definition.
  • Missing fields: if a vendor never prints a due date, accept that the field is legitimately absent — do not stretch descriptions to force a value.

Beware of a misleading pass: if the samples you test with are the same ones you inspected while designing the analyzer, you are testing your own assumptions. Reserve a handful of invoices you have never opened for a final validation run.

Summary

You defined an invoice analyzer with typed fields and precise descriptions, registered it through the portal and the REST API, ran it over stored invoices, and learned to review extraction quality by confidence and error pattern. The analyzer is now the extraction engine behind the CloudXeus invoice flow. The next chapters look at the sibling service in this space — Azure Document Intelligence — and how the two compare.
