Lab - Azure AI Search - Creating the indexer

The index exists and the data source points at your blob container, but nothing has moved between them. The indexer is the worker that reads documents from the data source, maps their content into the index fields, and writes the results. In this lab you create that indexer, run it, and confirm the documents land in the index.

What You Need Before Starting

  • The data source docs-datasource from the earlier data-source lab.
  • The index docs-index created in the previous lab.
  • The search service name, admin key, and resource group variables ($searchName, $adminKey, $rg).
  • At least one PDF uploaded to the docs blob container.

Step 1 - Understand What the Indexer Needs

An indexer definition has four key parts:

  • dataSourceName — which data source to read from.
  • targetIndexName — which index to write into.
  • fieldMappings — how source document fields become index fields.
  • schedule — optional, so the indexer re-runs automatically when documents change.

When the indexer reads a blob, it produces default fields such as metadata_storage_path, metadata_storage_name, and the raw file text in content. The field mappings tell Azure AI Search which source value belongs in each index field.

Step 2 - Write the Indexer Definition

Save the following as indexer.json. It maps the blob content to the index's content field and stores the source path in metadata_storage_path:

{
  "name": "docs-indexer",
  "dataSourceName": "docs-datasource",
  "targetIndexName": "docs-index",
  "fieldMappings": [
    {
      "sourceFieldName": "content",
      "targetFieldName": "content"
    },
    {
      "sourceFieldName": "metadata_storage_name",
      "targetFieldName": "title"
    },
    {
      "sourceFieldName": "metadata_storage_path",
      "targetFieldName": "metadata_storage_path"
    }
  ],
  "parameters": {
    "batchSize": 25,
    "maxFailedItems": 10,
    "maxFailedItemsPerBatch": 10,
    "configuration": {
      "parsingMode": "default"
    }
  },
  "schedule": {
    "interval": "PT6H"
  }
}

The content field produced by a blob indexer is the extracted text of the document. The default parsing mode works for plain text and simple PDFs. Advanced extraction — layout, tables, and OCR for scanned pages — is added in the skillset lab.

Step 3 - Create the Indexer

Create the indexer by sending the definition to the service. As with the index, the Azure CLI reads the whole JSON payload with --indexer-json:

az search indexer create `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey `
  --name docs-indexer `
  --indexer-json (Get-Content -Raw indexer.json)

Run the indexer immediately after creating it rather than waiting for the schedule. The scheduled run only picks up changes going forward; the first run should happen now so the initial documents are indexed without delay:

az search indexer run `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey `
  --name docs-indexer

Step 4 - Check the Indexer Status

Indexing is asynchronous, so you must poll for completion. Show the indexer status and its last run results:

az search indexer show `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey `
  --name docs-indexer

Look for the lastResult block. "status": "success" with a document count equal to the number of blobs you uploaded means the run worked. A status of transientFailure or inProgress needs another look after a few seconds.

Step 5 - Confirm Documents in the Index

The real proof is that the index now holds documents. Get the document count:

az rest --method get `
  --uri "https://$searchName.search.windows.net/indexes/docs-index/stats?api-version=2023-11-01" `
  --headers "api-key=$adminKey"

The response contains a documentCount value. If it matches your uploaded files, the pipeline works: blob in, document out.

If the document count stays at zero, the most common cause is a parsing failure on a scanned or image-only PDF. The default parser cannot extract text from scanned pages, so the file is skipped. Check lastResult.errors and lastResult.warnings in the indexer status to see exactly which files failed and why.

SymptomLikely causeFix
Invalid data sourceData source name typoList data sources and confirm the exact name matches.
Invalid target indexIndex name mismatchList indexes and compare with targetIndexName.

Summary

You created an indexer that reads from the blob data source, mapped its fields into the search index, ran it, and verified both the run status and the document count. The pipeline data source, index, and indexer is complete: content now flows automatically from blob storage into searchable documents. In the next lab you query that index.
