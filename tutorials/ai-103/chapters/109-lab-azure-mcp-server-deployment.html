Lab - Azure MCP Server deployment

In this lab you will deploy an Azure MCP server — the server that wraps Azure Language, Speech, and Vision services — to Azure Container Apps. The result is a hosted endpoint your agents can connect to from anywhere. This lab focuses on getting the server running and reachable; the next lab shows you how to talk to it.

Prerequisites

  • An Azure subscription with the ability to create resources.
  • The Azure CLI (az) installed and signed in. Verify with az account show.
  • Docker installed and running if you build images locally; alternatively, use the prebuilt container image supplied with the server project.
  • The azd tool (Azure Developer CLI) if you follow the simplified one-command deployment path.

Deploying a containerized server to Azure Container Apps incurs small costs while it runs. The per-second billing adds up slowly, but remember to delete the container app when you finish the labs, as shown in the cleanup step.

Step 1: Get the Server Project

Exercise 1: Clone the Azure MCP server repository

  1. Clone the Microsoft Azure MCP servers repository to your machine:
git clone https://github.com/Azure/azure-mcp-servers.git
cd azure-mcp-servers
  1. Confirm you are in the project folder and that the language/speech/vision server source is present. The repository contains several servers; this lab uses the language server subfolder.

If cloning is not an option on your machine, download the repository ZIP from the same URL and extract it. The deployment steps that follow do not care how you obtained the files.

Step 2: Deploy the Container

Exercise 2: Deploy with the Azure CLI

The fastest reliable path is to push a container image and run it in Container Apps. First, create a resource group and a Container Registry, then build and push the image:

az group create --name rg-ai103-mcp --location eastus

az acr create --resource-group rg-ai103-mcp \
  --name ai103mcpacr --sku Basic --admin-enabled true

az acr login --name ai103mcpacr

docker build -t ai103mcpacr.azurecr.io/azure-language-mcp:latest ./path/to/server
docker push ai103mcpacr.azurecr.io/azure-language-mcp:latest

Next, create a Container Apps environment and the app itself:

az containerapp env create \
  --name cae-ai103 --resource-group rg-ai103-mcp --location eastus

az containerapp create \
  --name mcp-language-server \
  --resource-group rg-ai103-mcp \
  --environment cae-ai103 \
  --image ai103mcpacr.azurecr.io/azure-language-mcp:latest \
  --ingress external \
  --target-port 80 \
  --min-replicas 1 --max-replicas 1 \
  --registry-server ai103mcpacr.azurecr.io \
  --registry-username ai103mcpacr \
  --registry-password YOUR_ACR_PASSWORD

Replace YOUR_ACR_PASSWORD with the registry password from az acr credential show. Container Apps builds and starts the container, which typically takes a few minutes.

Container Apps can also build directly from source with az containerapp up, which skips the manual registry steps entirely. The two-step path above is shown because it makes every stage visible — you will reuse the same image for redeployments.

Step 3: Configure the Server

Exercise 3: Set environment variables and an access key

  1. The server needs to know which Azure service to call and how to authenticate. Set an environment variable on the container app with the endpoint of your Azure AI Language resource:
az containerapp update \
  --name mcp-language-server \
  --resource-group rg-ai103-mcp \
  --set-env-vars \
    AZURE_AI_LANGUAGE_ENDPOINT=https://YOUR_LANGUAGE_ENDPOINT \
    MCP_ACCESS_KEY=YOUR_GENERATED_KEY
  1. Generate a strong random value for YOUR_GENERATED_KEY — this is the key your clients will present. A quick way on Windows is openssl rand -base64 32, or on Linux head -c 32 /dev/urandom | base64.
  2. Get the public URL of your server:
az containerapp show \
  --name mcp-language-server \
  --resource-group rg-ai103-mcp \
  --query "properties.configuration.ingress.fqdn" -o tsv

Write down the returned URL. Your MCP endpoint will be this URL with /sse appended — that is what clients connect to.

Never use a weak or reused value for MCP_ACCESS_KEY. Anyone with this key can call your server and, through it, your Azure services. Treat it as a credential: store it in a secret store in production and rotate it periodically.

Step 4: Verify the Server Is Alive

A simple health check confirms the container started before you build a client:

curl -s "http://YOUR_SERVER_FQDN/sse" -H "Authorization: Bearer YOUR_GENERATED_KEY" --max-time 10

An SSE endpoint holds the connection open, so do not expect a prompt to return — a response at all (or the connection staying open rather than instantly failing) means the server process is running. A connection refusal or an HTTP 401/403 points to a startup problem or a bad access key.

If the health check fails, look at the container's logs first: az containerapp logs show --name mcp-language-server --resource-group rg-ai103-mcp. Startup crashes usually leave an exception trace that names the missing variable or bad config.

Step 5: Clean Up

When you finish the MCP labs, remove the deployment to stop its running costs:

az group delete --name rg-ai103-mcp --yes --no-wait

This deletes the container app, the environment, and the registry in one operation.

Summary

You deployed an Azure MCP server to Azure Container Apps from source, configured its environment variables and access key, retrieved its public endpoint, and verified the process is running. You now hold two pieces of information that the next lab needs: the server URL and the access key. Next you will connect a real MCP client to this server and call its tools.
