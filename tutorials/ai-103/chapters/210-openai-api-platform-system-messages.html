OpenAI API Platform - System Messages

The single most powerful lever you have over a model is the system message. It is the persistent instruction that shapes the assistant's identity and behaviour for the whole conversation, and it is the difference between a model that answers vaguely and a model that behaves like a focused, consistent specialist. This chapter explains what system messages are, how to write them well, and how to use them in code.

What a System Message Is

Every chat conversation is a list of messages, and each message has a role. The system message is the one with role system. It sits at the top of the conversation and sets the rules for everything that follows — who the assistant is, what tone it uses, what it must do, and what it must refuse. Unlike user messages, which apply to a single turn, the system message applies to the entire conversation.

messages = [
    {"role": "system", "content": "You are a technical support assistant for a cloud hosting company. Answer in plain language, keep replies under three sentences, and offer a follow-up question at the end."},
    {"role": "user", "content": "My website went down. What should I check first?"}
]

A useful mental model: the system message is the job briefing, the user messages are the day-to-day requests.

What Makes a Good System Message

The best system messages are specific, concrete, and bounded. They cover the following:

  • Identity: who the assistant is and who it serves.
  • Tone and style: formal, friendly, technical, brief, and so on.
  • Rules: what to always do, what to never do, and how to handle unknown answers.
  • Format: plain text, bullet points, tables, or JSON.
  • Limits: length caps, topic boundaries, and fallback behaviour.

Compare these two:

{"role": "system", "content": "You are a helpful assistant."}

{"role": "system", "content": "You are an English-to-French translator for a legal firm. Translate only the user's text, do not add commentary, use formal language, and return 'UNABLE' if the text is not in English."}

The second system message produces predictable, on-task output; the first produces generic answers that may wander.

Write the system message as if you were briefing a new employee on their first day. The more precise the briefing — role, rules, format, limits — the more consistent the employee's work.

Using System Messages in Code

System messages are passed exactly like any other message in the chat completions call. The example below defines a tutor, asks it to explain in JSON, and prints the reply:

from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "You are a patient tutor. Explain concepts in two sentences, then answer in JSON with keys: summary and example."},
        {"role": "user", "content": "What is a context window?"}
    ],
    temperature=0.3
)

print(response.choices[0].message.content)

You have already used this exact pattern in the Microsoft Foundry labs earlier in the course. The OpenAI API platform and Azure OpenAI expose the same chat completions structure, so everything you learn about system messages here transfers directly to the enterprise platform.

Common Mistakes

  • Putting the question in the system message: keep the request in the user message and the rules in the system message.
  • Being vague: "be good" produces nothing actionable; "never mention competitors" is a concrete rule.
  • Overloading: a system message that is pages long dilutes every instruction. Keep the most important rules first and tight.
  • Contradicting yourself: the model follows instructions, but conflicting ones weaken all of them.

A system message is a guideline, not a guarantee of safety. Models can be tricked into ignoring instructions through prompt injection, and filtering is applied separately by the platform. Treat the system message as the first line of defence, not the only one.

Experimenting in the Playground

The playground makes system-message work iterative. Paste a system message, ask a few user questions, and watch how the assistant's style holds steady across turns. Then tighten or relax the wording and compare. This loop — draft, test, refine — is the same one you will apply in code, and it is far faster to do in the playground.

Summary

The system message is the persistent instruction that defines the assistant's identity, tone, rules, and format for an entire conversation. It differs from user messages, which apply to single turns, and a well-written system message makes model behaviour predictable and on-task.
