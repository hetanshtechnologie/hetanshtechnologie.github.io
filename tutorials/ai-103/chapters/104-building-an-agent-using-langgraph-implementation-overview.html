Building an agent using LangGraph - Implementation overview

The previous chapter introduced LangGraph's vocabulary: state, nodes, edges, checkpoints. This chapter walks through the full implementation of a real agent step by step, explaining each design decision. When you reach the lab, you will be assembling parts you have already seen here, rather than copying a mystery script.

Agent Blueprint

The agent you will implement follows a classic two-node cycle:

NodeResponsibility
agentCall the LLM with the conversation so far; produce either a final answer or tool calls
toolsExecute any requested tool calls and return the results to the state

A conditional edge leaves the agent node toward tools when the model requested tools, or toward END when it produced a final answer. A fixed edge returns from tools back to agent so the model can interpret the tool results.

Defining the State

State carries the conversation and the agent's working data through every step. The message field uses a reducer so tool results append to the history instead of replacing it:

from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

Keeping the state minimal has a practical benefit: the same object works with the model, the tools, and the graph — nothing needs translating at node boundaries.

You can add any fields your workflow needs — user id, order details, a retry counter, retrieved documents. Every node receives the whole state and returns an update dictionary. Only fields named in the update are changed.

The Agent Node

The agent node wraps a model that has tools bound to it. The model returns a message which may contain tool_calls; the node simply places that message into state:

from langchain_openai import AzureChatOpenAI
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode, tools_condition

model = AzureChatOpenAI(
    azure_endpoint="YOUR_ENDPOINT",
    api_key="YOUR_KEY",
    api_version="2024-06-01",
    deployment_name="ai103-chat-deploy",
)

def agent_node(state: AgentState) -> dict:
    response = model_with_tools.invoke(state["messages"])
    return {"messages": [response]}

Notice the node returns the full message object, tool calls included. The reducer appends it, and the routing step later reads it to decide the next move.

The Tools Node

LangGraph's prebuilt ToolNode executes any tool calls found in the latest message. Give it your list of tools and it handles dispatch, error capture, and result formatting:

from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """Return a sample weather summary for a city."""
    return f"Sunny, 24 degrees Celsius in {city}."

tools = [get_weather]
model_with_tools = model.bind_tools(tools)
tool_node = ToolNode(tools)

The ToolNode returns tool messages — structured results tied to each requested call. When the model next runs, it sees exactly which call produced which result.

Routing Between Nodes

LangGraph ships a ready-made condition, tools_condition, that implements the decision: if the latest message contains tool calls, route to tools; otherwise route to END. Wiring it is a single line:

graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)

graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", tools_condition)
graph.add_edge("tools", "agent")

app = graph.compile()

The tools_condition function knows both exit points by convention — tools for the tool node and END for termination — so you do not need to pass an explicit routing map.

If you want a customized decision — for example, logging every route change — write your own condition function. The signature is simple: receive state, inspect the last message, return a node name.

Why the Cycle Terminates

A graph with a cycle needs a stopping rule, or it could loop forever. The termination conditions here are the model's own behavior: a well-instructed model calls tools, reads results, and produces a final answer. Two safety nets exist:

  • Recursion limit: the compiler accepts recursion_limit — the maximum number of steps per run. Reaching it raises an error rather than burning tokens silently.
  • Model instruction: the system prompt tells the model to stop calling tools once it can answer. Good prompting is the first line of defense; the limit is the backstop.
app = graph.compile(recursion_limit=25)
result = app.invoke({"messages": [("user", "What is the weather in Paris?")]})
print(result["messages"][-1].content)

Adding a Checkpointer

Compiling with a checkpointer makes the graph resumable and gives each conversation durable memory. The in-memory saver is ideal for development; production systems swap in a durable store such as an SQLite or Redis-backed checkpointer:

from langgraph.checkpoint.memory import InMemorySaver

app = graph.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "thread-1"}}

app.invoke({"messages": [("user", "Remind me we are discussing Paris.")]}, config)
app.invoke({"messages": [("user", "What city were we discussing?")]}, config)

The second call returns the earlier context because both runs share thread-1. Without a checkpointer the second call would start from an empty state and the model would have no memory of the conversation.

Summary

You now understand every piece of the LangGraph agent: a message-based state with a reducer, an agent node that calls the bound model, a prebuilt tool node, a conditional edge that routes on tool-call presence, and a recursion limit that guarantees termination. Adding a checkpointer gives the agent durable conversation memory. In the next chapter you will implement this design end to end in a lab.
