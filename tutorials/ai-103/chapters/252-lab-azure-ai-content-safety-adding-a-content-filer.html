Lab - Azure AI Content Safety - Adding a content filer

In the previous chapter you learned what Azure AI Content Safety detects. This lab puts a filter to work: you will create a content filter configuration in Microsoft Foundry, attach it to a real chat deployment, and verify that it actually changes behavior by sending both safe and deliberately problematic prompts.

How Filters Attach to Deployments

A content filter configuration is a named set of thresholds, one per harm category, that applies to a model deployment. When a request or response crosses a threshold, the platform blocks or annotates it — you do not write any special handling code; the protection rides along with the deployment itself.

The workflow is:

  1. Create a filter configuration with your severity thresholds.
  2. Associate it with a deployment.
  3. Test with the playground and the API.

Not every model family supports attaching a custom filter, and some models ship with a built-in default filter. If the custom-filter option is unavailable for your model in the portal, use that model's default filter instead and read its documented thresholds — the testing steps below still apply.

Step 1: Create the Content Filter

Exercise 1: Define a filter with the CLI

The content filter is a resource in the Foundry resource group. Create it with the Azure CLI, giving the four harm categories and a threshold policy:

az resource create \
  --resource-group "YOUR_RESOURCE_GROUP" \
  --resource-type "Microsoft.MachineLearningServices/workspaces/contentfilters" \
  --name "strict-filter" \
  --location "YOUR_REGION" \
  --properties "{
    \"mode\": \"default\",
    \"thresholds\": {
      \"hate\": \"medium\",
      \"violence\": \"medium\",
      \"sexual\": \"medium\",
      \"selfHarm\": \"medium\"
    }
  }"

If the CLI resource type above is not recognized on your subscription, do not fight it — the portal path in Exercise 2 is fully supported and covers the same configuration.

Step 2: Create the Filter in the Portal

Exercise 2: Use the Foundry portal instead

For a reliable, UI-guided path, use the Foundry portal:

  1. Open your Foundry project and navigate to the Deployments area.
  2. Select the deployment you want to protect.
  3. Look for the Content filter (sometimes Filter configurations) section on the deployment details page.
  4. Click Create new and give it a name such as ai103-strict.
  5. For each category — hate, sexual, violence, self-harm — set the severity threshold you want to allow. Choosing medium allows only mild content; low is stricter and blocks more.
  6. Save the configuration. The deployment now uses these thresholds for every request and response.

Start with the same threshold on all four categories, then tighten per category based on your application. Most real apps tune violence and self-harm differently from sexual content — your product policy should drive those choices, not the other way around.

Step 3: Test the Filter with a Safe Prompt

Exercise 3: Confirm normal traffic still flows

Use the Foundry playground to chat with the deployment you just filtered:

  1. Open the Playground and select your deployment.
  2. Send an ordinary prompt, for example "Write a short welcome message for our website."
  3. Confirm you receive a normal response.

A well-configured filter is invisible to legitimate use. If normal prompts are being blocked, your thresholds are set too aggressively — raise them and retest.

Step 4: Test with a Prompt That Should Be Blocked

Now verify the filter actually does something. The goal is not to be offensive but to confirm the safety layer fires where your policy says it should. Choose a prompt that clearly crosses a threshold in a benign testing context, such as a request for violent content:

Exercise 4: Trigger the filter and read the response

  1. In the playground, send a prompt that explicitly requests harmful content in the category you set to a strict threshold.
  2. Observe the result. With a strict threshold you should see a refusal or a "content filtered" notice rather than generated content.
  3. If the request goes through anyway, lower the threshold for that category and repeat.

Use only clearly fictional or obviously harmful test inputs, and keep them confined to your own deployment. This lab is about verifying the filter fires — not about finding creative ways to defeat it. That distinction keeps your testing safe and professional.

Step 5: Verify from Code

Finally, confirm the filter is active through the API your application actually uses. The same chat call now carries the deployment's filter behavior automatically:

import os
from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

for prompt in ["Tell me a harmless joke about computers.", "YOUR_TEST_PROMPT_HERE"]:
    response = client.chat.completions.create(
        model="YOUR_FILTERED_DEPLOYMENT",
        messages=[{"role": "user", "content": prompt}],
    )
    choice = response.choices[0]
    print("Finish reason:", choice.finish_reason)
    print("Content:", choice.message.content or "(no content)")
    print("---")

The finish_reason value is the tell: a normal answer ends with stop, while a blocked response ends with content_filter.

Logging the finish_reason alongside each response gives you an audit trail of how often the filter fired and for which category of request. That data is exactly what a review meeting about your AI safety posture needs.

Summary

You created a content filter configuration, attached it to a deployment, and verified it from the portal and from code: safe prompts flow normally, filtered prompts stop with a content_filter finish reason, and per-category thresholds are tunable in one place. The filter is now a permanent guardrail on your deployment — and a reference point for the larger responsible-AI questions the rest of the course will keep returning to.
