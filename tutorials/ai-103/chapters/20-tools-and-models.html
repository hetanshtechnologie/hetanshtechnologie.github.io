Tools and Models

A model knows only what is in its training data and whatever you put in the conversation. It cannot check the weather, fetch a webpage, run code, or write to a database. Tools close that gap. This chapter explains what tools are, how a model decides to use them, and why they transform a model into something closer to an agent.

What a Tool Is

A tool is a piece of software you make available to the model through a description. The model does not run the tool itself. It declares that a tool should run and supplies the arguments; your application executes the tool and returns the result to the model. From the model's point of view a tool is like a function with a name, a description, and a typed argument list.

The Tool-Call Loop

Using a tool is a conversation, not a single request. The loop has five steps:

  1. You send the conversation, including the list of available tools.
  2. The model decides it needs a tool and returns a tool call with a function name and arguments, instead of a final answer.
  3. Your code executes the tool and collects the result.
  4. You send the result back to the model as a tool message.
  5. The model produces the final answer, now informed by the tool's output.

This loop can repeat several times in one user request if the model needs multiple tools.

Defining a Tool for the Model

Tools are described to the model with a JSON schema. The schema is a contract: it names the function, explains what it does, and lists its parameters with types and required flags.

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a city.",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "The city name."}
                },
                "required": ["city"],
            },
        },
    }
]

The description matters as much as the name. The model chooses tools by reading their descriptions, so a precise description of what a tool does — and when to use it — directly improves accuracy.

Built-in Tools vs Your Own Tools

Some platforms provide ready-made tools such as web search or file storage that are configured with a few lines. You can also define your own functions that wrap any Python code you like — a query against your database, a call to your company API, or a calculation. Built-in tools save time; custom tools connect the model to your systems.

Safety and Control

Giving a model tools means giving it the ability to act. That power needs guardrails:

  • Run tools in a sandbox with no access to production secrets.
  • Add confirmation steps for destructive actions such as deletions or purchases.
  • Validate tool arguments before executing them.
  • Limit tools to the minimum set the task requires.
  • Log every tool call for auditing.

A model can call a tool with plausible but wrong arguments, and it can misunderstand instructions that live in external data. Never let a model run destructive or billing-relevant actions without human approval.

Tools Are the Bridge to Agents

Once a model can call tools reliably, it stops being a pure text generator and becomes a problem solver: it can gather data, compute, and act in a loop until the task is done. That capability is the foundation of the agents you will build in the next section of this course.

Summary

Tools extend a model beyond text by giving it callable functions with schemas. The tool-call loop has the model request a tool, your code run it, and the result return to the model for a final answer. Tools come as ready-made built-ins or as your own functions, and they must always be wrapped in safety controls because they give the model real-world effects.
