Publishing, Routines, and Distributing Your Foundry Agent

A prompt agent that only exists in the portal playground is a prototype. Turning it into something applications can call requires publishing it — creating a stable, versioned endpoint — and then deciding how that endpoint is distributed and protected. This chapter covers publishing, the routine the agent runs on, and the options for sharing your agent with other applications and people.

Why Publishing Matters

Until an agent is published, it has no stable address. The playground is interactive by design: you type, the model answers, and nobody else is expected to connect. Publishing changes the contract. The agent receives an identity and a set of versions, and external callers can target a specific version with confidence that its behavior will not silently change underneath them.

Versions and Revisions

Agent configuration evolves. The instructions get tightened, a tool is added, the temperature changes. Publishing keeps that evolution safe by separating drafts from versions:

  • A draft is your current working copy. You can edit it freely without affecting anyone.
  • Publishing a draft creates a version — an immutable snapshot of instructions, model, and tool configuration.
  • Callers choose a version explicitly, or point at a default version that you control.

This is the same mental model as releasing a library. You can test a new version privately, then promote it to default when you are confident, and roll back to an older version if something goes wrong.

Because a version is immutable, the instruction prompt you ship with a version is the instruction prompt that version always runs with. Audit logs and traces reference the version, so you can always reconstruct exactly what behavior produced a given answer.

What a Routine Is

A routine is the execution plan the Agent Service uses when running your prompt agent. It describes how the service should process incoming messages: which model to call, in what order to consult tools, and how to assemble the final response. In practice the routine encapsulates the orchestration loop that the previous chapters described — message in, run, possible tool calls, final answer.

You rarely need to think about the routine while building a simple agent, because the default routine handles the common case well. Understanding it helps when behavior surprises you: if the agent seems to answer before using the tools you attached, the routine is the place to look at how tool invocation is scheduled.

Routine ElementWhat It Controls
Model selectionWhich deployment answers and how sampling parameters behave
Tool orderingWhether tools run before, during, or after model generation
Response assemblyHow final output text is built from model and tool results
Error handlingWhat happens when a tool fails or the model errors mid-run

Distributing Your Agent

Once published, an agent can be reached in several ways, and the right choice depends on who the consumer is:

  • Direct API calls: your own applications call the agent endpoint with an access token obtained through Microsoft Entra ID.
  • Shared chat experience: you can share a link that lets other users in your organization chat with the agent in a hosted UI.
  • Embedded in products: an application uses the endpoint and surfaces the agent inside its own interface, giving you full control of the experience.

Distribution and security go hand in hand. Every published agent endpoint requires an authenticated caller; the permissions are defined by Microsoft Entra ID, which the next chapters cover in detail.

Publish early and often. Each small change to instructions can be its own version, which gives you a reliable history of what was tried, what worked, and what broke. Teams that publish frequently find it far easier to answer the question "what was different when this agent started misbehaving?"

Planning Your Distribution Strategy

Before you publish, decide who may call the agent and how it will be governed:

  • Which applications or services are legitimate callers, and what Entra identities will they use?
  • Which versions should be available, and should any version be retired?
  • What level of logging and trace retention do you need for audit and debugging?
  • How will you announce behavior changes to consumers when a new default version is promoted?

Do not publish an agent as the default version and then immediately forget it. A published default is a commitment to every caller who did not pin a specific version. Treat version promotion with the same ceremony you would give a production release.

Summary

Publishing converts a prototype prompt agent into a versioned, callable service. Versions freeze behavior so callers can upgrade deliberately, routines define how the service executes each message, and distribution options range from direct API calls to shared chat links — all protected by Microsoft Entra ID.
