OpenAI - Tools - Web Search

The image generation tool showed you a tool that creates new content. The web search tool does the opposite: it fetches content from the outside world. Language models are trained on data that ends at a fixed point in time, so questions about current prices, breaking news, sports results, or live events are outside their knowledge. The web search tool bridges that gap by letting the model run a real search against the public web and answer using the pages it finds — with citations your application can surface to the user.

What the Web Search Tool Does

When you attach the web search tool to a request, the model can decide to run a search during its response. The model formulates a query, the search runs against current web content, and the results are folded into the context the model uses to compose its final answer. From your code's point of view it is one call: you ask, and the response already contains the grounded answer.

This removes the manual retrieval loop you would otherwise build yourself — detect that the question is time-sensitive, call a search provider, paste snippets into the prompt, and re-ask the model. The tool automates all of those steps inside the API.

Declaring the Tool

Add a web_search entry to the tools list. Beyond the usual name and description, the tool accepts options that control how broadly it searches and which region it targets.

from openai import OpenAI
import os

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

response = client.responses.create(
    model="gpt-5",
    input="What was the most recent major version release of Python?",
    tools=[
        {
            "type": "web_search",
            "name": "web_search",
            "description": "Searches the public web for current and factual information.",
            "search_context_size": "medium",
            "user_location": {
                "type": "approximate",
                "approximate": {"country": "US", "city": "Seattle", "region": "WA"},
            },
        }
    ],
)

Understanding the Options

  • search_context_size — how many results the search returns and feeds into the model. Small keeps the answer fast and cheap; high gives the model more material, which helps with complex questions at a higher cost.
  • user_location — an approximate location used to bias results. This matters for questions whose answer depends on where you are, such as "which movie is showing near me tonight" or "what is the weather right now".

Supply a location only when answers actually depend on geography. Biasing every query toward one region can reduce result quality for genuinely global questions.

What Comes Back in the Response

The response contains two kinds of evidence that the search ran:

  • A web search call item in the output list that records the query that was executed, so you can see exactly what the model searched for.
  • Annotations on the text answer that tie parts of the reply back to the web pages they came from, typically including titles and URLs.
for item in response.output:
    if item.type == "web_search_call":
        print("The model searched for:", item.query)

print(response.output_text)

Annotations are your best tool for accountability. When a user sees a claim sourced from the web, presenting the underlying links alongside the answer lets them verify it for themselves and builds trust in your application.

Retrieval with Citations

The key benefit of the web search tool is grounded output with traceable sources. A model answering from memory can sound confident and be wrong; a model answering from search results can point at the pages behind each claim. In applications where factual accuracy matters — news summaries, research assistants, or customer-facing answers about your own industry — being able to show the source is often a hard requirement.

You can feed the returned citations straight into your user interface. Each annotation maps a snippet of the answer to a source page, which lets you render references inline beneath the relevant sentence rather than dumping a generic list of links at the end.

Comparing the Built-in Tool to a Custom Search Function

AspectBuilt-in web search toolCustom search function tool
Setup effortDeclare the tool, doneWrite schema, implement the function, wire a provider key
Where the search runsManaged by the APIIn your own code, against your provider
CitationsReturned with the responseYou build and format them yourself
ControlOptions limited to context size and locationFull control of ranking, filtering, and budget

Use the built-in tool when you want grounded answers fast with minimal plumbing. Use a custom function when you need to search a private index, enforce strict filtering, or integrate a provider you already pay for.

Practical Considerations

  • Search results count as extra context, which increases latency and cost. Keep search_context_size as small as your question tolerates.
  • Web content is unvetted. The model can still be misled by a low-quality page, so verify critical facts in high-stakes applications.
  • Your own content filtering still applies. A search-driven answer should pass the same safety checks as any other response before it reaches a user.

Do not assume that a result with a citation is true — the citation proves where the information came from, not that the information is correct. For critical answers, your application should apply its own verification where feasible.

Summary

The web search tool lets a model answer questions that require current information by running a real web search inside the response. You declare the tool with a context size and an optional location, and the model decides when to search, returning both the answer and the citations behind it. For applications where accurate, traceable answers matter, this tool replaces a hand-built retrieval loop with a single API call.
