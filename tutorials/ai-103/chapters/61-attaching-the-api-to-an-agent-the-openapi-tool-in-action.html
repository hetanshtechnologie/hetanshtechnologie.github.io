Attaching the API to an Agent - The OpenAPI Tool in Action

An OpenAPI specification on its own does nothing. The payoff comes when you attach it to an agent: Foundry parses each operation into a tool, the model decides when to call it, and the platform executes the HTTP request. This chapter walks through attaching the CloudXeus orders spec to an agent in the Foundry portal and testing the integration end to end.

The Attachment Flow

Adding an OpenAPI tool to a Foundry agent follows a fixed sequence:

  1. Create a new agent or open the existing CloudXeus agent you built earlier in the course.
  2. Open the agent's Tools section and add a tool of type OpenAPI.
  3. Upload your validated .openapi.json file.
  4. Configure the server URL and the authentication method (the next chapter covers auth choices in depth).
  5. Save and test the tool from the chat playground.

If your spec contains a servers block with a URL, Foundry offers it as the default endpoint. You can override it during attachment, which is useful when the same spec serves multiple environments.

What Foundry Does with Your Spec

When the spec is attached, the platform converts it into tool definitions the model can see. Each path and method becomes one tool:

Operation in the specTool the model sees
get_orderget_order(order_id: string) -> Order
list_orderslist_orders(email: string) -> Order[]
cancel_ordercancel_order(order_id: string) -> Order

The model reads the summary and description fields to understand when each tool is appropriate. It never sees your connection credentials or the raw spec; it works only with the parsed tool signature.

Testing the Tool in the Chat Playground

Exercise — Watch the Agent Call the Orders API

  1. Open the agent's chat playground.
  2. Ask for order details in natural language:
What is the status of order ORD-1001?
  1. Watch the tool call: the model selects get_order, the platform sends the request to your function app, and the answer uses the returned JSON.
  2. Ask a question that spans the list operation:
Show me all orders for ada@example.com
  1. Confirm the agent uses list_orders and summarizes the matching orders.

The best test is an adversarial one: ask questions that are ambiguous, such as What do you know about ORD-9999? A good setup will surface the 404 response and answer honestly rather than inventing an order. If the agent hallucinates instead, tighten the operation descriptions so the model understands the lookup can fail.

What Happens When the Tool Fails

Failures surface in three common places:

  • Parsing errors: the spec has invalid JSON or duplicate operationIds; Foundry rejects the file at upload time.
  • Request errors: the API returns 404 or 409. The response body flows back to the model, which should report it gracefully.
  • Connection errors: the server URL is unreachable or the key is wrong. The platform logs the error so you can diagnose it.

Until you secure the API, every operation in the spec is callable by anyone who reaches your function app URL. Attaching the tool does not lock the API down — it adds a well-documented way in. The next two chapters fix that by choosing a proper authentication method and enforcing a function key.

Summary

Attaching an OpenAPI spec to a Foundry agent converts a REST API into callable tools. The agent reads the parsed operations, calls them during conversation, and grounds its answers in live order data. With the connection working, the next chapter examines the authentication methods available to OpenAPI tools.
