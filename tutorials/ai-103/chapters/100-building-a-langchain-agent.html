Building a LangChain agent

A LangChain agent is an application that lets a model decide, at runtime, what actions to take. Where a plain chain always follows the same fixed pipeline, an agent evaluates each incoming request and chooses whether to answer directly or to call a tool first — often in several steps. This chapter explains the pieces LangChain uses to build that decision loop and how they fit together.

What Makes a LangChain Agent

An agent in LangChain is built from a small set of components:

  • The model: the LLM that does the reasoning. It reads the user's request, decides whether a tool is needed, and eventually composes the final answer.
  • Tools: callable functions the model may invoke. A tool can be a Python function, an API wrapper, a database query, or any code you expose with a name and description.
  • The prompt: instructions that explain the agent's role, describe the tools available, and set the rules for producing tool calls.
  • The executor: the runtime loop that keeps calling the model and executing tools until the model produces a final answer.

The key idea is that the model decides. You do not hard-code the sequence of steps. Instead you provide the tools and let the model reason about which one fits the user's intent. This is what separates an agent from a scripted chain.

How Tool Calling Works

Modern chat models support a feature called tool calling (also called function calling). The model does not execute code — it requests a call by emitting a structured message that names a tool and supplies arguments. Your application inspects that request, runs the corresponding function, and sends the result back to the model as a tool-result message.

This round trip is what gives an agent its power. The model can see a tool's output, reconsider, and either call another tool or write the final answer. Each round trip is called a step, and an agent may take several steps for one user request.

# A tool exposed to the model
from langchain_core.tools import tool

@tool
def convert_celsius_to_fahrenheit(celsius: float) -> float:
    """Convert a temperature in Celsius to Fahrenheit."""
    return celsius * 9 / 5 + 32

Notice what the @tool decorator does. It converts an ordinary function into a tool that LangChain can describe to the model: the function name becomes the tool name, the docstring becomes the description, and the type hints define the expected arguments. The model reads exactly that metadata when it decides whether to call the tool.

Binding Tools to the Model

Before the model can request a tool call, it must know the tools exist. You attach them to the model with bind_tools:

from langchain_openai import AzureChatOpenAI

model = AzureChatOpenAI(
    azure_endpoint="YOUR_ENDPOINT",
    api_key="YOUR_KEY",
    api_version="2024-06-01",
    deployment_name="ai103-chat-deploy",
)

model_with_tools = model.bind_tools([convert_celsius_to_fahrenheit])

Calling the bound model returns either a final text answer or one or more tool_calls — structured requests naming a tool and its arguments. The presence of tool calls is your signal to execute the tools and feed the results back.

The Agent Loop

LangChain wraps the entire decision cycle in an AgentExecutor. The executor runs the model, checks whether tool calls were requested, executes them, appends the results to the conversation, and repeats — stopping when the model finally answers without requesting a tool.

from langchain_core.prompts import ChatPromptTemplate
from langchain.agents import AgentExecutor, create_tool_calling_agent

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant with access to tools."),
    ("placeholder", "{chat_history}"),
    ("human", "{input}"),
    ("placeholder", "{agent_scratchpad}"),
])

agent = create_tool_calling_agent(model_with_tools, [convert_celsius_to_fahrenheit], prompt)
executor = AgentExecutor(agent=agent, tools=[convert_celsius_to_fahrenheit], verbose=True)

result = executor.invoke({"input": "What is 25 degrees Celsius in Fahrenheit?"})
print(result["output"])

Two placeholders in the prompt are special. {agent_scratchpad} is where the executor stores the trail of tool calls and their results — the model reads it to decide the next step. {chat_history} holds the conversation so the agent can remember what was said earlier in the same session.

The verbose=True flag prints every model call and tool invocation as the agent runs. It is an excellent way to watch the decision loop in action while you are learning, and it is the first thing to enable when debugging a stubborn agent.

Why Multiple Steps Matter

A single tool call handles many questions, but real work often needs several. Consider a request like "Convert 68 degrees Fahrenheit to Celsius and double it." The agent may convert first, then multiply the result — two tool steps in sequence, with the second depending on the first. The executor's loop makes this possible because each tool result becomes part of the conversation the model sees next.

ScenarioStepsWhy the loop is needed
Direct answer1The model has no tool to call, or none is relevant
Single lookup2Call one tool, then answer from its output
Multi-step task3+Results from earlier calls feed into later ones
Wrong tool first3+The model corrects course after seeing an unexpected result

Handling Failure and Endless Loops

Agents are only as reliable as the reasoning behind them. Two failure modes deserve attention:

  • Tool errors: if a tool raises an exception, the executor can return the error to the model as a tool result. The model then explains the failure or tries a different approach, instead of crashing the whole request.
  • Runaway loops: a confused model might keep calling tools indefinitely. The AgentExecutor accepts max_iterations — the maximum number of steps before it forces a final answer. Setting a sensible limit is cheap insurance in production.
executor = AgentExecutor(
    agent=agent,
    tools=[convert_celsius_to_fahrenheit],
    max_iterations=4,
    handle_parsing_errors=True,
)

Without a step limit, a malfunctioning agent can burn tokens (and money) by looping. Always set max_iterations and think about what the agent should do when it cannot reach a good answer. A graceful fallback message is better than an endless tool-calling cycle.

Summary

A LangChain agent combines a model, tools, a prompt, and an executor. The model decides whether to call tools, the executor runs the loop, and the conversation accumulates tool results until the model produces a final answer. Tool calling is the mechanism, the agent scratchpad is the memory of the loop, and iteration limits keep the process safe.
