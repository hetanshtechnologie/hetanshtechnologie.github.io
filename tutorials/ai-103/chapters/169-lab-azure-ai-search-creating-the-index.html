Lab - Azure AI Search - Creating the index

Your search service now knows where documents live, but it still has no idea what to do with them. In this lab you define the index — the schema that describes every document field and how each one can be searched. This is the contract the indexer will fill in the next lab, so getting the field attributes right now saves you from rebuilding everything later.

What You Need Before Starting

  • The search service name and admin key from the data-source lab.
  • The data source docs-datasource created in the previous lab.
  • The Azure CLI signed in, with the azure-search extension installed, and your $rg, $searchName, and $adminKey variables still set.

Step 1 - Design the Schema

Before writing any JSON, decide what a single document should look like in the index. Each blob becomes one search document, and each field in the index maps to content from that blob. A minimal RAG-ready schema needs at least four things:

FieldTypePurpose
idEdm.StringThe document key. Every index requires exactly one key field.
titleEdm.StringA readable name, used in results and citations.
contentEdm.StringThe actual text of the document that search will match against.
metadata_storage_pathEdm.StringThe source blob's URI, useful for filters and provenance.

Field attributes decide behavior. The most important ones were introduced in the theory chapter: searchable allows text matching, filterable allows filter expressions, retrievable controls whether the field is returned, and sortable / facetable enable ordering and faceting.

Step 2 - Write the Index Definition

Save the following as index.json. It defines a key, searchable title and content, a filterable source path, and a vector field that a later enrichment lab will populate with embeddings:

{
  "name": "docs-index",
  "fields": [
    {
      "name": "id",
      "type": "Edm.String",
      "key": true,
      "searchable": false,
      "filterable": true,
      "retrievable": true
    },
    {
      "name": "title",
      "type": "Edm.String",
      "searchable": true,
      "retrievable": true
    },
    {
      "name": "content",
      "type": "Edm.String",
      "searchable": true,
      "retrievable": true
    },
    {
      "name": "metadata_storage_path",
      "type": "Edm.String",
      "searchable": false,
      "filterable": true,
      "retrievable": true
    },
    {
      "name": "embedding",
      "type": "Collection(Edm.Single)",
      "searchable": true,
      "retrievable": false,
      "dimensions": 1536,
      "vectorSearchConfiguration": "docs-vector-profile"
    }
  ],
  "vectorSearch": {
    "algorithmConfigurations": [
      {
        "name": "docs-hnsw",
        "kind": "hnsw",
        "hnswParameters": {
          "metric": "cosine",
          "m": 16,
          "efConstruction": 400,
          "efSearch": 500
        }
      }
    ],
    "profiles": [
      {
        "name": "docs-vector-profile",
        "algorithm": "docs-hnsw"
      }
    ]
  }
}

The vector field declares that a collection of 1536 floating-point numbers will be stored per document — the dimensionality of the embedding model used in this course. Query-time configuration syntax for vector search changes across API versions; the shape above matches the 2023-11-01 REST API and the az search index commands below. If your index later rejects the field, confirm the API version in your requests.

Step 3 - Create the Index

Create the index by sending the JSON file to the service. With the Azure CLI extension, use the --index-json option to pass the whole definition in one command:

az search index create `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey `
  --name docs-index `
  --index-json (Get-Content -Raw index.json)

A successful call echoes the index definition back, including the assigned @odata.etag. The index now exists on the service, ready to hold documents but still empty.

You can also create the index through the REST API directly, which is useful when you want to script from any language:

az rest --method put `
  --uri "https://$searchName.search.windows.net/indexes/docs-index?api-version=2023-11-01" `
  --headers "api-key=$adminKey" `
  --body (Get-Content -Raw index.json)

Step 4 - Verify the Index

List the indexes on the service to confirm docs-index is registered:

az search index list `
  --service-name $searchName `
  --resource-group $rg `
  --admin-key $adminKey -o table

You should see a single row for docs-index. Its document count is zero — populating it is the job of the indexer in the next lab.

Troubleshooting

SymptomLikely causeFix
Index name cannot be changedThe name field does not match --nameKeep both values identical and rerun.
Invalid field on embeddingVector config missing or wrong API versionEnsure vectorSearch is present and the version matches the field syntax.
Key field not foundNo field marked key: trueMark exactly one field as the key.
503 at creationService scaling or quota limitWait a minute and retry; check the service's replication count.

Summary

You designed a search schema, wrote it as an index definition with field attributes and a vector-search configuration, created the index on your service, and verified it with a listing command. The index is the empty container your documents will flow into. In the next lab you create the indexer that pulls content from the blob data source and writes it into docs-index.
