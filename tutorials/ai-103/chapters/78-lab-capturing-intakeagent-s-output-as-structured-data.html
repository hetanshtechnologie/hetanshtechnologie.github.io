Lab - Capturing IntakeAgent's Output as Structured Data

Right now IntakeAgent returns its intake record as free-flowing prose. That works for reading, but it is awkward for the next step of the workflow, which wants to branch on fields such as the account number or the priority. In this lab you will make IntakeAgent produce structured data instead: JSON that follows a fixed schema, so the rest of the pipeline can treat it as records rather than as text. You will configure structured output in the portal and then reproduce the same behavior from Python.

Objectives

  • Define a JSON schema for the intake record.
  • Configure IntakeAgent to respond only with structured output.
  • Update the workflow to consume the structured fields.
  • Call the same structured-output endpoint from Python.

Prerequisites

  • The intake-pipeline workflow and both CloudXeus agents from the previous labs.
  • Python 3.9 or newer with the openai package installed.

Step 1: Design the Intake Schema

A schema tells the model exactly which fields to produce, which types they have, and which are required. Design the intake record with fields that the workflow will later branch on and log:

{
  "type": "object",
  "properties": {
    "summary": { "type": "string", "description": "One sentence summarizing the request." },
    "product": { "type": "string", "description": "CloudXeus product mentioned, if any." },
    "is_urgent": { "type": "boolean", "description": "True if the customer signals urgency." },
    "account_id": { "type": "string", "description": "Account or order number, if provided." }
  },
  "required": ["summary", "is_urgent"]
}

Notice that product and account_id are not in the required list. When a customer does not mention them, the model should not invent values — making them optional lets the output stay honest. Anything the workflow absolutely needs should be required; everything else should not.

Step 2: Apply the Schema to IntakeAgent

Configure structured output in the agent

  1. Open IntakeAgent in the Foundry portal.
  2. In the agent's response configuration, enable structured output (sometimes labeled "output format" or "JSON response").
  3. Paste the schema from Step 1 as the response format, or build it with the schema editor.
  4. Save and publish a new version of the agent.
  5. Open the playground, resend the Meridian Retail message from the earlier lab, and confirm the reply is valid JSON matching the schema.

Structured output constrains the shape of the response, not its content accuracy. The model will still write a summary that might overstate the original message. Keep the instructions that forbid invented facts — the schema guarantees JSON, and only the prompt guarantees truthful JSON.

Step 3: Update the Workflow to Use the Fields

Back in the intake-pipeline workflow, IntakeAgent's output is now a JSON object instead of prose. Update the ResolverAgent node and the output node to use the individual fields.

Reference the structured fields

  1. Open the ResolverAgent node and change its user message to reference the summary field:
Original customer message:
$\{inputs.customer_message}

Intake summary:
$\{nodes.intake_agent.output.summary}
  1. In the Output node, add a new field is_urgent and bind it to $\{nodes.intake_agent.output.is_urgent}.
  2. Run the workflow again with the same test message and confirm is_urgent comes back as a true/false value rather than text.

Because the output is now structured, the next lab's condition node can branch directly on is_urgent. That is the whole payoff of this step: deterministic downstream logic built on top of generative output.

Step 4: Structured Output from Python

The same pattern works from Python, where you can go further and validate the response against a typed schema. The openai SDK supports a response_format parameter that requests strict JSON. Create structured_intake.py:

import os
from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

intake_schema = {
    "type": "object",
    "properties": {
        "summary": {"type": "string"},
        "product": {"type": "string"},
        "is_urgent": {"type": "boolean"},
        "account_id": {"type": "string"},
    },
    "required": ["summary", "is_urgent"],
    "additionalProperties": False,
}

message = (
    "Our virtual machine in eastus has been down for almost 2 hours "
    "and our billing dashboard depends on it. This is urgent, we are "
    "losing sales. Account AC-88231."
)

response = client.chat.completions.create(
    model="YOUR_DEPLOYMENT_NAME",
    messages=[
        {"role": "system", "content": "You are IntakeAgent. Summarize the "
         "customer request as JSON. Never invent fields."},
        {"role": "user", "content": message},
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "intake_record",
            "strict": True,
            "schema": intake_schema,
        },
    },
)

import json
record = json.loads(response.choices[0].message.content)
print("Summary  :", record["summary"])
print("Product  :", record.get("product", "not mentioned"))
print("Urgent   :", record["is_urgent"])
print("Account  :", record.get("account_id", "not mentioned"))

Run and validate the output

  1. Replace YOUR_DEPLOYMENT_NAME with your deployed model's name.
  2. Set your endpoint and key environment variables.
  3. Run the script and verify the printed fields match the message.
  4. Change the message so no account number is present, re-run, and confirm Account prints as "not mentioned" — proof the model respects the optional field.

Strict mode with additionalProperties: false tells the provider to guarantee the model only emits fields from your schema. If your SDK version rejects an unexpected key, check that you are using a model and API version that support structured output with strict JSON schemas.

Summary

You designed a JSON schema for the intake record, applied it to IntakeAgent so it returns clean structured output, updated the workflow to consume individual fields, and reproduced the same structured behavior from Python with validation. The pipeline now produces data the next steps can branch on — which is exactly what you will do when you add conditions to the workflow in the next lab.
