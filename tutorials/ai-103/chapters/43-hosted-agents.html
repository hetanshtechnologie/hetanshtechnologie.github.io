Hosted agents

In the previous chapter you built a conversational agent in code, wiring up function tool calling by hand. That gives you total control, but it also puts you in charge of the plumbing: the request loop, conversation state, tool dispatch, and error handling. Hosted agents take a different path. Instead of writing the orchestration loop yourself, you describe the agent — its instructions, model, and tools — and the platform runs it for you. Microsoft Foundry offers exactly this kind of managed agent service, and in this chapter you will learn what hosted agents are, how they are put together, and when they beat hand-built agents.

What Is a Hosted Agent

An agent, at its core, is a system that decides how to answer a user request and can take actions beyond generating text. Every agent combines four things:

  • A model that reasons about the request and chooses next steps.
  • Instructions that define the agent's role, tone, and boundaries.
  • Tools the agent can call, such as search, code execution, or your own APIs.
  • A runtime that drives the loop: send to model, detect a tool call, run the tool, feed the results back, and repeat until the model produces a final answer.

In a code-first agent you build the runtime yourself, as you did in the function tool calling lab. In a hosted agent the platform supplies the runtime. You provide the first three ingredients as configuration, and the service handles execution, retries, sessions, and state for you.

The Parts of a Hosted Agent

When you create a hosted agent in Foundry, you define roughly the following:

  • Identity and instructions: the system message that sets the agent's personality, scope, and guardrails.
  • Model deployment: the deployed chat model the agent will reason with.
  • Tools: an allow-list of capabilities. Common hosted tools include file search over uploaded documents, a sandboxed code interpreter, grounding through an Azure AI Search index, and calls to your own REST APIs.
  • Threads: persistent conversation history that the service stores for you, so multi-turn conversations stay coherent without you managing messages.
  • Settings: sampling parameters such as temperature, plus limits on steps and token usage.

The hosted runtime owns the conversation. When a user sends a follow-up question, the service retrieves the thread's history automatically, so your application code stays thin: create a thread, send a message, read the response.

The Microsoft Foundry Agent Service

Foundry organizes hosted agents around three concepts that mirror other Azure resources:

  • Agent hub: a container that groups agents and shared configuration, similar to how a workspace groups models and datasets.
  • Agent project: the scoped unit where you define agents, tools, and evaluations.
  • Agent deployment: a deployed, running instance of an agent that exposes a chat endpoint your application calls.

You can manage hosted agents through the Foundry portal or through the Agents SDK. A minimal SDK definition looks like this:

from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential

project = AIProjectClient.from_connection_string(
    conn_str="YOUR_PROJECT_CONNECTION_STRING",
    credential=DefaultAzureCredential(),
)

agent = project.agents.create_agent(
    model="YOUR_CHAT_MODEL_DEPLOYMENT",
    name="cloudxeus-support",
    instructions="You are a friendly support agent for CloudXeus. "
                 "Use your tools to find information before answering.",
    tools=[{"type": "file_search"}],
)
print("Agent created:", agent.id)

Hosted Agents vs Code-First Agents

AspectHosted AgentCode-First Agent
RuntimeManaged by the platformYou write and host it
Conversation stateThreads stored for youYou manage history
ToolsCurated set plus OpenAPI and MCPAnything you can run in code
ControlConfiguration levelFull code control
TelemetryBuilt inYou wire it yourself
Best forRapid, standard use casesComplex custom orchestration

Use a hosted agent when your requirements fit the built-in toolset and you want to move fast. Build your own when you need custom control flow, unusual runtimes, or deep integration with existing code.

A practical middle path is to start hosted and add a custom OpenAPI tool for the one capability you need. You keep the managed runtime while extending the agent with your own business logic. Later chapters show how OpenAPI tools plug into Foundry agents.

Hosted agents run in a shared managed environment. For workloads with strict compliance or data-residency requirements, check the data location and processing options for the agent service before you commit, and always treat the agent's tool access as attack surface.

Summary

A hosted agent is a model, a set of instructions, and a tool list driven by a platform-managed runtime. Microsoft Foundry packages these as agent hubs, projects, and deployments, and gives you both a portal and an SDK to create and manage them. Choose hosted agents for speed and simplicity, and reserve code-first agents for cases that genuinely need custom orchestration.
