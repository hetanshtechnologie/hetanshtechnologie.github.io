Deploying Models in Microsoft Foundry

Deploying a model is the step that turns a model card in the catalog into a live endpoint your application can call. It is the most important action you will repeat in this course, so this chapter explains the underlying concepts before the hands-on lab: what a deployment actually is, the choices you make while creating one, and how the resulting endpoint behaves.

What a Deployment Is

A deployment binds a specific model version to computing resources at an endpoint. When you deploy, Foundry provisions capacity, applies your configuration, and gives you a URL like https://YOUR_RESOURCE.cognitiveservices.azure.com/ plus a deployment name. Your application then sends requests to that endpoint, and the model answers.

The deployment name, not the model name, is what your code references. This indirection is deliberate: you can point a deployment at a new model version, or swap models, without changing your application's code — only the deployment's configuration changes.

There is a distinction between the model, which is the trained artifact you browse in the catalog, and the deployment, which is the running instance of that model. You can have several deployments of the same model with different settings, and you can delete a deployment without touching the model.

The Choices You Make When Deploying

Creating a deployment asks you for a handful of settings. Each one has real consequences, so it is worth understanding them before clicking:

  • Model and version: Which model family and which version you want. Newer versions are not always strictly better for your task, so version pins give you stability.
  • Deployment name: The identifier your code will call. Choose something short and stable.
  • Region: Where the compute runs. Keep it near your users and your data for latency and compliance.
  • Capacity and tier: How much throughput the endpoint can handle and how it is billed — pay-per-call tiers for variable traffic, provisioned capacity for steady, high volume.
  • Content filtering: The safety configuration that blocks harmful or filtered categories of content in requests and responses.

Billing and Quota

Deployments are where model costs are incurred. Understanding the two billing models saves you from surprising bills:

ModelHow you payBest for
Pay-as-you-goPer token or per requestVariable or low traffic, prototyping
Provisioned capacityFlat rate for reserved throughputSteady, high-volume production

Foundry also tracks quota — the amount of capacity you are allowed in each region. If a deployment fails with a quota error, the fix is usually either waiting for quota, requesting an increase, or moving to a region with available capacity.

A deployed model accrues cost even when nobody calls it in some configurations. Before you deploy in the labs, confirm the tier you are choosing, and delete deployments you are not actively using. A single forgotten paid deployment can quietly consume a free account's credit.

How Applications Talk to a Deployment

Your application talks to the deployment over HTTPS with an authentication header. Requests and responses are JSON, and the shape of that JSON follows the model's API convention. A chat completion request looks structurally like this:

{
  "model": "YOUR_DEPLOYMENT_NAME",
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "What is a token?"}
  ],
  "temperature": 0.7,
  "max_tokens": 200
}

And the response carries the generated text, usage counts, and metadata:

{
  "choices": [
    {
      "message": {"role": "assistant", "content": "A token is a chunk of text..."}
    }
  ],
  "usage": {"prompt_tokens": 18, "completion_tokens": 35}
}

The usage block in every response is free telemetry. Log it in your application and you get cost tracking per request without any extra tooling — a habit that will save you money and answer budget questions later.

Deployment Lifecycle

Deployments are not permanent by default. Understand the lifecycle so you can manage them confidently:

  1. Create: Provision the endpoint with your chosen settings.
  2. Test: Call it from the playground or from code with a small request.
  3. Monitor: Watch cost, latency, and errors on the monitoring dashboard.
  4. Update: Change settings or repoint the deployment at a new version.
  5. Delete: Remove the endpoint when you no longer need it, stopping its cost.

Every lab in this course will take you through most of this cycle, so the mechanics will become second nature quickly.

Deployment vs. Fine-Tuning

Deploying a model and fine-tuning a model are different operations and it is important not to confuse them. Deployment serves an existing model as-is. Fine-tuning trains an existing model on your data to change its behavior, and only after fine-tuning do you deploy the tuned version. Most applications never fine-tune at all; they deploy a foundation model and steer it with prompts and retrieval. Fine-tuning is a later chapter — for now, deploy first, and only consider fine-tuning if the foundation model's behavior cannot be fixed by better prompting.

Summary

A deployment is a running, billed instance of a model exposed at an endpoint with a name your code calls. When you deploy you choose the model version, deployment name, region, capacity, billing tier, and content filtering — and every choice has consequences for cost and behavior.
