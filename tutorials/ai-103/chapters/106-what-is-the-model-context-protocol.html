What is the Model Context Protocol

So far your agents have called tools defined in their own code. The Model Context Protocol, or MCP, takes a different approach: it is an open, standardized way for an AI application to discover and call tools, resources, and prompts provided by external servers. Instead of embedding a function in your agent, you connect to a server that advertises capabilities, and your agent calls whatever the server offers. This chapter explains what MCP is, who the participants are, and what a conversation over the protocol looks like.

The Three Roles

MCP defines a clear separation of roles:

  • MCP host: the application where the AI runs and where the user interacts — for example, an IDE, a chat client, or your own Python agent.
  • MCP client: the component inside the host that establishes connections to one or more servers on the host's behalf.
  • MCP server: a process that exposes capabilities — tools, resources, and prompts — over the protocol. A single server can serve many clients.

The distinction between host and client is subtle but important. Think of the host as the desktop app and the client as the connection code inside it. One host often manages several clients, each bound to a different server — your chat app might connect to a file server and a database server at the same time.

What a Server Exposes

An MCP server exposes three kinds of capability:

PrimitivePurposeExample
ToolsFunctions the model can invoke, with an input schemaQuery a database, send a message, translate text
ResourcesData the client can read and give the model as contextA project file, a log, a configuration document
PromptsReusable prompt templates the host can insertA "summarize this document" workflow template

Tools are the most common primitive in agent work — they give the model the power to do things. Resources feed the model with context. Prompts standardize recurring interactions.

How Discovery Works

The protocol's first phase is discovery. When a client connects, the server sends a description of its capabilities and announces which primitives it supports. The client can then request the list of tools. Each tool entry carries a name, a human-readable description, and a JSON Schema describing its arguments — the same metadata shape you have seen in LangChain's @tool decorators, but standardized across every server.

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "search_documents",
        "description": "Search documents for a keyword.",
        "inputSchema": {
          "type": "object",
          "properties": {
            "keyword": {"type": "string"}
          },
          "required": ["keyword"]
        }
      }
    ]
  }
}

The client passes this list to the model (for example, bound as tools). The model can then request a call exactly as it would call any other tool — the protocol is invisible to the model's reasoning.

How a Call Works

When the model decides a tool is needed, the client sends a call request over the established connection:

{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "search_documents",
    "arguments": {"keyword": "invoice"}
  }
}

The server executes the tool and returns a result structure — usually one or more content blocks plus an isError flag:

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {"type": "text", "text": "Found 3 matching documents."}
    ],
    "isError": false
  }
}

The client turns this into a tool message and sends it back to the model, which reads the outcome and continues its reasoning — exactly the loop you built by hand in the LangChain and LangGraph chapters.

Transports

MCP defines how messages travel between client and server. Two transports dominate:

  • Streamable HTTP (and the older HTTP with SSE): client and server communicate over HTTP endpoints. Servers can be hosted anywhere — including Azure Container Apps — and clients can reach them over the network. This is the transport used for Azure-hosted MCP servers.
  • Stdio: the client launches the server as a local subprocess and communicates over standard input and output. Simple and secure, but the server runs on the same machine as the client.

Transport matters for security and topology. A stdio server is invisible to the network — ideal for local, private tools. An HTTP server can be shared by many clients and deployed at scale, but it must be protected with authentication before untrusted callers reach it.

MCP in Context

MCP does not replace LangChain or LangGraph — it complements them. LangChain gives you the framework for building agents; MCP gives you a standard way to expose and consume tooling across organizational and network boundaries. You could attach an MCP connection as just another tool source inside a LangGraph agent, and nothing about the graph changes.

Summary

The Model Context Protocol is an open standard with three roles — host, client, and server — and three primitives: tools, resources, and prompts. Clients discover capabilities, models choose among them, and calls travel over HTTP or stdio transports using JSON-RPC messages. It is the industry's answer to the question of how AI applications connect to external systems in a reusable way. In the next chapter you will look at the design problems MCP was created to solve.
