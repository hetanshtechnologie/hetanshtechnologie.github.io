Microsoft Foundry Agent Service Overview

The script you wrote in the last lab runs on your own machine. That works for learning, but real applications need their agents hosted somewhere reliable — always available, secured with real identities, and reachable through a normal API call. Microsoft Foundry Agent Service is the managed layer that provides exactly that. In this chapter you will learn what the Agent Service is, the two broad types of agents it supports, and how a hosted agent fits into a production application.

What Is the Agent Service

The Agent Service is a cloud platform within Microsoft Foundry for building, hosting, and operating AI agents. Instead of managing infrastructure yourself, you describe your agent — the model it uses, the instructions it follows, and the tools it may call — and the service takes care of running it. The agent receives a stable endpoint, so any application can send it a message and receive an answer over HTTP.

The service sits on top of the same model deployments you have already used, but adds the orchestration layer that plain model calls lack: conversation memory across turns, the ability to call tools, and the bookkeeping of long-running executions. When you use the Agent Service you stop writing your own loop and start describing behavior.

Prompt Agents and App Agents

Foundry distinguishes two ways of building an agent, and the distinction matters for how you work:

AspectPrompt AgentApp Agent
DefinitionDeclared from a prompt, model, and toolsCustom application code wrapped in an agent interface
HostingManaged by the Agent ServiceRuns in your own compute (for example a container)
Custom logicLimited to what the model and tools can expressArbitrary code you write and deploy
Best forQuick, well-defined conversational assistantsAgents with bespoke business logic and workflows

Prompt agents are the faster path. You configure instructions and attach tools, and the service does the rest. App agents are the escape hatch: when your agent needs specialized computation, a custom user interface, or integration only your code can provide, you build it as an application and register it with the service so it still behaves like an agent to callers.

How a Prompt Agent Is Described

A prompt agent is configuration as much as it is code. Three ingredients define it:

  • The model: the deployment the agent uses for reasoning and generation.
  • The instructions: the system prompt that sets the agent's role, tone, and boundaries.
  • The tools: a list of capabilities such as web search, code execution, file search, or custom functions the agent is allowed to use.

When a user message arrives, the service loads this configuration, begins a run against the model, and manages the back-and-forth with any tools the model requests. Your application only ever sees the conversation — the mechanics are hidden behind the service boundary.

The instruction prompt is the single highest-leverage part of a prompt agent. A carefully written system prompt that states the agent's purpose, audience, tone, and constraints produces dramatically better behavior than a vague one — and requires no code changes to iterate on.

The Agent Lifecycle in the Service

Agents pass through several stages as they move from idea to production:

  • Create: define the agent in the Foundry portal or through code.
  • Test: chat with the agent in the playground and refine its behavior.
  • Publish: create a version and promote it so applications can target it.
  • Invoke: call the agent from your application using its endpoint.
  • Monitor: review traces, runs, and evaluations as usage grows.

Each stage is supported by the service, which means a team can iterate on an agent's prompt without redeploying any application code — the application simply targets a new version.

Why Teams Use the Agent Service

The managed agent platform changes how teams build AI features:

  • Speed: a working conversational agent can go from idea to a testable endpoint in minutes.
  • Consistency: the same agent endpoint is shared across chat, APIs, and automation.
  • Security: the service integrates with Microsoft Entra ID for authentication and authorization.
  • Governance: versions, tool usage, and token consumption are tracked in one place.
  • Focus: teams write prompts and tools instead of operating model infrastructure.

When Not to Use the Agent Service

The service is not the right fit for every scenario. If your agent needs heavy real-time computation, runs in a completely offline environment, or must embed directly into a single-user device application, a lighter approach may serve better. Likewise, if you need fine-grained control over the inference loop — every intermediate step, custom sampling, bespoke scheduling — you may prefer to build and run your own orchestration. The Agent Service optimizes for a managed, team-friendly workflow, and that trade-off is worth understanding before you commit.

Summary

Microsoft Foundry Agent Service turns agents into hosted services: you describe a model, instructions, and tools, and the service runs the conversation, manages memory, and exposes a stable endpoint. Prompt agents give you the fastest path; app agents give you full control.
