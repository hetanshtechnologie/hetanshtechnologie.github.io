Improving Response Completeness

A model can give a perfectly grammatical answer that still fails the user — because it answered only part of the question, skipped a required section, or stopped too early. This chapter looks at response completeness: what it means, why models are often incomplete, how to measure it, and which techniques reliably push the score up. In a grounded agent, completeness is rarely a model flaw; it is usually a sign that the prompt, the retrieved context, or the output contract is not demanding the full answer.

What Response Completeness Means

Completeness asks a simple question: did the answer cover everything the user asked for? A complete answer addresses every part of the request, includes the specific facts that were requested, and follows the agreed format without omitting required fields. An incomplete answer might be wrong only by omission — it is not contradictory, it just leaves gaps.

Completeness differs from accuracy. Accuracy is about being correct; completeness is about being exhaustive. Both matter. A support answer that is correct but silent on the customer's second question is incomplete, and the customer will have to ask again. In an LLM-as-a-judge evaluation, a separate completeness evaluator reads the request and the response and scores how fully the response satisfies the request.

DimensionQuestion it answers
AccuracyIs the content correct?
CompletenessDid it cover everything requested?
GroundednessIs it supported by the supplied context?
RelevanceDoes it address the user's actual question?

Why Responses Come Out Incomplete

Several common causes produce partial answers. Recognizing them tells you where to intervene:

  • Multi-part questions: the user asks three things at once and the model answers only the most salient one.
  • Missing context: retrieval returns chunks that cover the first topic but not the others, so the model has no material for the rest.
  • Token limits: max_tokens cuts the answer off mid-sentence, so the last sections never appear.
  • Vague instructions: the system prompt never demands a full answer, so the model stops after its first pass.
  • Format constraints: a required JSON schema has optional-looking fields the model skips.

Incomplete answers often show up in evaluations as a completeness score that is lower than accuracy. When accuracy is fine but completeness lags, the model has the right material and simply is not being pushed to use all of it.

Techniques That Improve Completeness

Treat completeness as a prompt and pipeline problem. The techniques below are ordered from cheapest to most involved:

TechniqueWhat you doWhen to use it
Require exhaustive coverageAdd instructions to cover every question part and list any unanswered partsAlways; it costs nothing
Expand retrieved contextRetrieve more chunks or use hybrid search so all topics are representedWhen answers miss topics entirely
Raise the output budgetIncrease max_tokens and watch finish_reasonWhen answers are truncated
Structured output contractDemand a JSON schema that lists every required fieldWhen downstream code needs all fields
Decompose the questionHave the model split the question into sub-questions and answer each oneWhen users ask multi-part questions

Making the Prompt Demand Completeness

The cheapest win is a system prompt that makes covering everything a hard rule. A small rewrite changes behaviour noticeably:

# Weak
You are a support assistant. Answer the user's question.

# Stronger
You are a support assistant.
- Identify every distinct question or request in the user's message.
- Answer each one explicitly, in the order it was asked.
- If a part cannot be answered, say so and explain why.
- Do not stop after the first question.

Detecting Truncation in Your Code

When the model stops because it ran out of output tokens, the API tells you. Checking finish_reason catches truncated answers before users do:

from openai import AzureOpenAI
import os

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

response = client.chat.completions.create(
    model="YOUR_DEPLOYMENT_NAME",
    max_tokens=500,
    messages=[
        {"role": "system", "content": "Cover every part of the user's question."},
        {"role": "user", "content": "List the pros and cons of migrating to the cloud and the main risks."},
    ],
)

if response.choices[0].finish_reason == "length":
    print("Answer truncated - increase max_tokens or shorten the request")
else:
    print(response.choices[0].message.content)

Log finish_reason along with every completion. A rising share of length results across your traffic is a strong early sign that your output budget is too small for the answers your prompts now demand.

Measuring Completeness with an Evaluator

Once the prompt techniques are in place, verify them with a completeness evaluator in Foundry. Feed it a set of sample questions and check the score distribution before and after your change. Improvement should be visible in the aggregate, not just in one cherry-picked example. Keep a small golden set of representative multi-part questions so the measurement is stable across runs.

Do not tune for completeness by making answers longer without reason. A bloated answer can satisfy an evaluator while hurting the user experience. Target the specific gaps your evaluation exposes, then re-run to confirm you fixed them without damaging other dimensions such as fluency and conciseness.

Summary

Response completeness measures whether an answer covers everything the user asked for. The usual culprits are vague prompts, thin retrieval, truncated output, and weak output contracts. You fix them with explicit coverage rules, richer context, bigger output budgets, structured output, and question decomposition — then verify the change with a completeness evaluator.
