Building an API-Powered Agent with OpenAPI Tools on Microsoft Foundry

A tool is any capability an agent can invoke. So far the tools you used were functions your own code executed. But most organizations already have functionality locked inside REST APIs. OpenAPI tools are the bridge: you describe an existing HTTP API with an OpenAPI specification, attach it to a Foundry agent, and the agent calls that API directly. This chapter explains the pattern and the CloudXeus scenario you will build: an orders API that a support agent can query.

Why Agents Should Call Your APIs

Retrieval answers questions about documents, but it cannot change state or read live systems. An orders API, an inventory system, or a ticketing service holds current data and performs actions. Exposing those as agent tools gives users answers grounded in reality:

  • Live order status instead of static FAQ text.
  • Actions such as placing or cancelling an order.
  • One interface that talks to many internal services.

The CloudXeus Scenario

CloudXeus is building a support agent that helps customers with their orders. Behind the scenes a small API, built on Azure Functions, exposes three operations:

  • Look up an order by its id.
  • List orders for a customer email.
  • Cancel an order (marked as an action with side effects).

In the upcoming labs you will build that API, describe it with OpenAPI, and attach it to a Foundry agent so the agent can fetch real order data during a conversation.

How an OpenAPI Tool Works in Foundry

Attaching an OpenAPI tool to a Foundry agent follows this flow:

  1. You provide an OpenAPI specification document that describes the API: its server URL, operations, parameters, and request or response schemas.
  2. Foundry parses each operation into a tool with a name derived from its operationId and a description derived from its summary and description fields.
  3. At runtime, when the model decides the tool is needed, the platform constructs and sends the HTTP request on your behalf.
  4. The API's response is returned to the model, which answers the user using the real data.

Authentication is handled through connection settings you configure on the agent, such as an API key header, and the model never sees your credentials.

Because the model reads the OpenAPI document to decide when to call a tool, the quality of your descriptions directly controls how well the agent uses the API. A vague summary means the model cannot tell when the operation is relevant.

Adding an OpenAPI Tool: The Steps

  1. Build and validate an OpenAPI specification for your API.
  2. Create an agent in Foundry (hosted or via the SDK).
  3. Add the OpenAPI specification as a tool, pointing at your API's endpoint and authentication.
  4. Test in the chat playground, sending requests that should trigger each operation.
  5. Monitor calls and tighten the descriptions and error responses as you find gaps.

OpenAPI Tools vs Other Tool Mechanisms

ApproachHow it connectsBest for
Function calling in codeYour application runs the functionLogic that lives in your process
OpenAPI toolAgent calls an existing HTTP APIReusing external or internal REST services
MCP serverAgent connects to a tool server over MCPRich, pluggable tool ecosystems

OpenAPI tools give an agent network access to your API. Every operation is a potential action, so apply the principle of least privilege: scope credentials, review what a malicious prompt could trigger, and prefer read-only operations unless the agent really needs to mutate data.

Summary

OpenAPI tools let Foundry agents call existing REST APIs by supplying a machine-readable description of them. The agent decides when to call, the platform executes the HTTP request, and the answer is grounded in live data.
