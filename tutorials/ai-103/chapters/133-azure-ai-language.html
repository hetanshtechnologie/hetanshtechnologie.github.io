Azure AI Language

In the previous chapters you performed text analysis by prompting a general-purpose model. Azure AI Language is the opposite approach: a dedicated cloud service whose models are purpose-built for specific language tasks, exposed through a stable REST API and SDKs. This chapter explains what Azure AI Language is, which capabilities it ships with, how it compares with LLM prompting, and how you authenticate to it from your applications.

What Azure AI Language Is

Azure AI Language is a family of prebuilt and customizable natural language services hosted by Azure. Instead of describing a task in a prompt and hoping the model follows, you call a dedicated endpoint for that task — detect the language, extract the entities, redact the PII — and the service returns a fixed, documented schema. The models behind these endpoints are trained specifically for their jobs, which makes them fast, predictable, and inexpensive at high volume.

You interact with the service through a REST API or through official SDKs for Python, .NET, JavaScript, and other languages. Everything in the labs of this section uses the Python SDK, which wraps the REST calls in convenient client objects.

Prebuilt Capabilities

The service groups a large set of features. The ones used in this section are:

CapabilityWhat it returnsTypical use
PII detection and redactionSpans and categories of personal information, plus redacted textScrubbing documents before storage or sharing
Language detectionDetected language code and confidence scoreRouting documents to the right pipeline
Prebuilt named entity recognition (NER)Entities, their types, and their offsets in the textExtracting people, places, organizations, dates, and amounts
Sentiment and opinion miningPer-document and per-sentence polarity scoresMeasuring customer satisfaction at scale
Key phrase extractionA ranked list of salient phrasesTagging and search indexing
Text summarizationExtractive or abstractive summariesCondensing long documents
Text translation (Azure Translator)Translated text and detected source languageBulk, multi-language translation

Prebuilt vs. Custom

Most features exist in two tiers. Prebuilt models ship trained by Microsoft and work out of the box — you send text and get a result with no training data required. Custom models let you train the service on your own labeled examples, which is useful when your domain uses unusual terminology or when you need entity types the prebuilt model does not know about, such as part numbers or internal team names.

A common workflow starts with the prebuilt model, measures its accuracy against a labeled sample of your data, and only invests in custom training where the prebuilt model falls short. This keeps cost low and time-to-value short.

Comparing with LLM Prompting

You have now seen both approaches, so it is worth naming exactly where the line falls:

ConsiderationAzure AI LanguageLLM prompting
Output contractFixed schema per featureYou define via prompt and JSON mode
CustomizationRequires custom trainingAny task describable in a prompt
ExplanationsNone — scores and spans onlyFree-text reasoning available
Unit of billingPer text record or characterPer token (input + output)
LatencyLow, single-passHigher, token generation
Best fitHigh-volume, well-specified tasksNovel tasks, judgment, tone, register

Neither approach dominates. PII redaction, language detection, and prebuilt NER are textbook Azure Language jobs; sentiment-with-explanation and audience-aware translation are textbook prompting jobs. The two work well together in one pipeline.

Authentication and Keys

The Azure AI Language resource lives in your Foundry resource group and exposes an endpoint plus two keys. Every request carries one of those keys in the Ocp-Apim-Subscription-Key header (the SDK does this for you), and the response comes back JSON. For production workloads, Azure also supports managed identity and Azure AD tokens so that no static key is stored in your code — the same pattern you saw with the MCP server. For the labs in this section, the two keys on the resource's Keys and Endpoint page are all you need.

Treat the keys like passwords. Never paste them into code you commit, keep them in environment variables or a key vault, and rotate them regularly. Because a key grants access to whatever data you send the service, a leaked key can also leak your documents.

Getting Started with the SDK

After installing the azure-ai-textanalytics package, a client is a few lines:

from azure.ai.textanalytics import TextAnalyticsClient
from azure.core.credentials import AzureKeyCredential

endpoint = "YOUR_LANGUAGE_ENDPOINT"
key = "YOUR_LANGUAGE_KEY"

client = TextAnalyticsClient(
    endpoint=endpoint,
    credential=AzureKeyCredential(key),
)

Each capability is a method on the client, and each takes a list of documents. The same client serves language detection, entity extraction, PII redaction, sentiment, and key phrases — which is why every lab in this section reuses this setup.

Summary

Azure AI Language provides prebuilt, purpose-trained text-analysis features behind a stable API, offering fixed schemas, low latency, and low per-call cost. It complements rather than replaces LLM prompting: the service excels at high-volume, well-specified tasks, while prompting handles novel or explanation-heavy work.
