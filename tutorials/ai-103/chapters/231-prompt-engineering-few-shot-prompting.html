Prompt Engineering - Few-shot Prompting

Few-shot prompting is the technique of including a handful of worked examples in the prompt before the real task. Instead of describing the desired behavior in words alone, you demonstrate it: show the model input-and-output pairs, then let it continue the pattern for the actual input. Where zero-shot prompting trusts the model's training, few-shot prompting shows the model the finish line.

The Anatomy of a Few-Shot Prompt

A few-shot prompt has three parts:

  1. Instructions — the task described briefly, if needed at all.
  2. Demonstrations — two to five pairs of example input and expected output.
  3. The real input — the actual item the model must handle, following the same format as the examples.

Why Examples Work Better Than Adjectives

Instructions describe a category; examples instantiate it. Telling the model "classify sentiment" leaves the category boundaries fuzzy. Showing it that "Fast delivery, great price." is positive and "It works, nothing special." is neutral pins down exactly where the line sits. This is especially valuable when:

  • The categories overlap or are counterintuitive.
  • The output format is unusual or must be exact.
  • The domain uses specific jargon.
  • The task is subtle enough that words fail.

Few-shot prompting does not retrain the model. The examples live inside the prompt and travel with every request. They cost tokens on every call, but they give you behavior control without any fine-tuning pipeline.

Choosing Good Examples

Example quality determines prompt quality. The best demonstrations share three traits:

  • Representative: they span the range of the task, including edge cases, rather than clustering around the easy middle.
  • Correct: an example with the wrong label teaches the model the wrong pattern.
  • Consistent format: every demonstration follows the exact output shape you want back.

How Many Examples?

There is no universal count, but the pattern is consistent:

ExamplesEffectWhen to use
0 (zero-shot)Fast, flexible, can driftCommon tasks, quick prototypes
1-3 (one/few-shot)Steadier format and labelsMost production classification and extraction
4-8 (few-shot)Best pattern fidelityComplex schemas, edge-case-heavy tasks
10+Prompt bloat, high token costRarely worth it — consider fine-tuning

Add examples until the failure mode you care about disappears, then stop. Every example is permanent token overhead on every call, so the smallest prompt that reliably works is the best prompt.

Common Few-Shot Pitfalls

  • Random examples: hand-pick examples that cover the failure cases you actually observed in zero-shot testing.
  • Wrong ordering: put the hardest or most diagnostic examples closest to the real input; the most recent demonstrations influence the answer most.
  • Format confusion: if instructions and demonstrations disagree, the demonstrations usually win. Keep them consistent.
  • Label leakage: with classification, never repeat the same label so many times that the model default to it.

Examples can also encode your own biases. If all your demonstrations are short and simple, the model may underperform on long, messy real-world inputs. Include at least one messy example so the model has seen an honest version of the task.

Summary

Few-shot prompting adds worked demonstrations to a prompt, giving the model exact examples of the input-output mapping you want. It outperforms zero-shot on tricky categories, strict schemas, and unusual domains, at the cost of tokens and maintenance effort. Well-chosen, correctly formatted examples teach the model far more than paragraphs of description.
