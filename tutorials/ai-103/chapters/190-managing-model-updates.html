Managing model updates

Cloud AI services do not stand still. New model versions ship, older API versions are retired, and the behavior of a prebuilt model can change subtly between releases. If your application treats the service as a black box that never changes, a quiet update can break extraction in production. This chapter is about managing that lifecycle deliberately: knowing when models change, versioning your custom work, and updating applications safely.

Why Model Versions Matter

A model version is a snapshot of a model's behavior — the training data, the schema, and the quirks. When Document Intelligence releases a new version of a prebuilt model, the field names or the confidence behavior can differ from what you coded against. Two practical consequences follow:

  • Your integration must be written against a pinned API version, not the latest, so it keeps working predictably.
  • You need a test set you can re-run whenever the version changes, to see exactly what shifted.

In this course the word model appears in two senses: the prebuilt models shipped by the service (invoice, receipt, layout) and your custom models trained on your own samples. Both can change, but the mechanics differ. Prebuilt versions change when the vendor ships one; custom versions change when you train again.

Prebuilt Model Lifecycle

Prebuilt models follow a lifecycle you should track:

  1. Preview: a new version is offered for evaluation. The API may change before release.
  2. General availability: the version becomes the recommended choice with a support commitment.
  3. Deprecation: older versions stop being improved and eventually stop being served on a schedule.

Stay on the current general availability version for production, and use preview versions only in sandboxes. Follow the service's release notes so a deprecation never surprises you.

Versioning Your Custom Models

When you retrain a custom model, the service keeps the new version alongside the old ones. This gives you a clean upgrade path:

  1. Train the new version on an updated or expanded set of labeled samples.
  2. Validate it against the fixed test set from the previous version and compare field accuracy.
  3. If results improve, point your application at the new model id.
  4. Keep the old version available until the new one has proven itself in production.

Treat the test set as a contract. It should cover the document variety you actually process — digital and scanned, single and multi-page. Every model change, whether a retrain or a new prebuilt version, is judged against that same set, which turns "the model got worse" into a measurable statement.

Updating Your Application Safely

A model update is a change to your system, and it deserves the same care as any code change:

  • Pin the API version in the client configuration so behavior does not drift between SDK releases.
  • Test before switching. Run the new model against your test set in a staging environment, not directly in production.
  • Compare outputs. Diff the extraction results from old and new versions on the same documents; the differences tell you what to verify by hand.
  • Roll back cleanly. Keep the previous model id or API version reachable so you can revert quickly if the new version misbehaves.
  • Update callers. If a field name or value type changed, update the code that consumes the result at the same time as the model.

Monitoring Deprecations

You should not learn about a deprecation by reading a failing request log. Add routine checks to your operations:

  • Watch the service's release notes and deprecation announcements on a regular cadence.
  • Track which API versions and model ids each of your deployments uses, in one inventory table.
  • Schedule a periodic validation run — even quarterly — that re-executes your test set against the versions you use.
  • Set a reminder before known retirement dates for the API versions your code depends on.

An expired API version usually returns errors that surface only under load or after business hours. Deprecation management is cheap compared to an unscheduled migration, so do not defer it.

Summary

Model updates are inevitable, and they are manageable. You pin API versions, track the prebuilt model lifecycle, version your custom models, validate every change against a fixed test set, and keep a clean rollback path. With that discipline in place, a new model version is a planned release rather than an incident.
