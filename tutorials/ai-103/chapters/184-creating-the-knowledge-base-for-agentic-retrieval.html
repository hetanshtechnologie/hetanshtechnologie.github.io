Creating the Knowledge Base for Agentic Retrieval

With the documents sitting in storage, the next task is to turn them into something an agent can search. That transformation happens in a knowledge base: the indexing service reads the source documents, splits them into manageable chunks, converts each chunk into an embedding vector using an embedding model, and stores the results in a vector index. This chapter creates that knowledge base for the CloudXeus documents and verifies that retrieval actually works before any agent is attached.

What a Knowledge Base Contains

A knowledge base is not a copy of the documents. It is a derived, searchable structure with three parts:

  • Chunks: the source text broken into passages small enough for a model to reason over.
  • Embeddings: the numeric vectors that capture the meaning of each chunk, produced by an embedding model.
  • Index: the organized collection of chunks and vectors that a query can search, along with metadata such as the original file name and location.

When a user asks the agent a question, retrieval converts the question into an embedding, finds the chunks whose vectors are most similar, and hands those passages to the model as context. The model then answers strictly from what was retrieved — this grounding is what keeps responses accurate and traceable.

How Indexing Works

Indexing runs as a pipeline with a few distinct stages:

  1. Connect to the source. The service reads the container you prepared in the previous chapter.
  2. Extract text. Each file is parsed into readable text, with OCR applied to scanned pages when supported.
  3. Chunk. The text is split on natural boundaries such as headings and paragraphs so each chunk stays coherent.
  4. Embed. Each chunk is passed through the embedding model to produce a vector.
  5. Write to the index. Chunks, vectors, and metadata are stored so they can be searched later.

Chunking is a quality lever you will tune more than once. Small chunks are precise but lose surrounding context; large chunks keep context but dilute relevance. Starting with modest chunks that follow document structure, then adjusting based on observed retrieval results, is the standard workflow.

Prerequisites for Indexing

Before you create the knowledge base, confirm the pieces from the preceding chapters are in place:

  • The embedding model deployment you created in the model-deployment chapter — its name is referenced by the index configuration.
  • The storage source from the previous chapter, reachable and readable.
  • The permissions assigned in the prerequisite chapter, so the indexing service can authenticate to storage.

Creating the Knowledge Base in the Foundry Portal

In Microsoft Foundry, knowledge bases live inside your project. To create one:

  1. Open your Foundry project and navigate to the Knowledge bases page.
  2. Click Create and give the knowledge base a name, for example cloudxeus-docs.
  3. Choose the index configuration: the index name, the vector index type, and the embedding deployment.
  4. Add the storage source by selecting the container cloudxeus-docs from your storage account.
  5. Confirm the connection details and click Create.

Creation registers the knowledge base and starts the indexing job. Most Foundry UIs let you watch progress from the same page.

Creating the Knowledge Base with the API

The same operation is available through a REST API, which is what your deployment automation will use. Register the knowledge base with a PUT request against your project's endpoint:

PUT https://YOUR_PROJECT_URI/knowledgebases/cloudxeus-docs?api-version=2025-05-01-preview

with a body that describes the index and the source:

{
  "index": {
    "indexName": "cloudxeus-docs-index",
    "indexKind": "vector",
    "embedding": {
      "deploymentName": "text-embedding-ada-002",
      "dimensions": 1536
    },
    "instructions": "Split documents on headings and paragraphs, keeping passages short."
  },
  "sources": [
    {
      "uri": "https://cloudxeusdocsstore.blob.core.windows.net/cloudxeus-docs",
      "connectionString": "DefaultEndpointsProtocol=https;AccountName=cloudxeusdocsstore;AccountKey=YOUR_KEY;EndpointSuffix=core.windows.net",
      "documentId": "/sources/cloudxeus-docs"
    }
  ]
}

The connection string contains the storage account key. Prefer a managed identity when the service supports it, and never commit a connection string to source control. If you must use a key, rotate it regularly and store it in a secret store.

Running and Monitoring the Indexing Job

After registration, an indexing job begins automatically. As it runs, check these signals:

  • Status: the job moves through queued, running, and completed states.
  • Document count: the number of files successfully processed versus the number attempted.
  • Failures: files that could not be parsed, usually due to an unsupported format or an unreadable scan. Fix the file and re-run the job.

Index in a small batch first — a handful of documents — before pointing the job at the whole container. This gives you fast feedback on chunking and extraction quality without burning time on a large run that needs changes.

Verifying Retrieval

A knowledge base that never returns the right passages is worse than no knowledge base. Verify it before wiring in an agent. In the Foundry portal, open the knowledge base and run a test question such as "What is the return policy?". Look at the chunks that come back: do they actually answer the question, and are they drawn from the right documents? If retrieval misses, adjust chunk size or the embedding model and re-run indexing.

Summary

You registered a knowledge base over the CloudXeus storage source, configured its index and embedding model, ran the indexing job, and checked that retrieval returns relevant chunks. The knowledge base is now ready for agents. In the next chapter you will look at the hard cases — scanned PDFs and tables that span multiple pages — and how to parse them so they index well.
