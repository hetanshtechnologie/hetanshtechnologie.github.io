Prompt Engineering - Basic Prompt fundamentals

Prompt engineering is the craft of writing inputs that make large language models produce useful, predictable output. The model already contains the knowledge; your job is to point it in the right direction. A well-built prompt can turn a vague, generic answer into a focused, well-structured response — and the difference is entirely in how the request is written, not in the model itself.

What a Prompt Is Made Of

At its most basic, a prompt is just the text you send to the model. But most effective prompts are built from a few reusable ingredients:

  • Instruction: the task, stated directly — "summarize", "translate", "classify", "write".
  • Context: background information the model needs to answer well.
  • Input data: the actual content to work on — a document, an email, a product review.
  • Output format: how the answer should be shaped — bullet list, JSON, table, one sentence.
  • Constraints: limits such as length, tone, audience, or forbidden content.

You do not always need all five. A prompt like "What is 2+2?" works with just an instruction. The ingredients matter when the task is complex, ambiguous, or produces inconsistent results — that is when you add context, format, and constraints.

Clarity Beats Cleverness

The single most common prompt mistake is vagueness. Compare these two prompts for the same task:

Tell me about Python.
Explain Python's list comprehension feature to a beginner who
already knows basic for loops. Give two examples and end with
a one-line summary.

The first prompt hands the model a wide-open choice: it might write a history of the language, a tutorial on syntax, or a comparison with other languages. The second prompt fixes the topic, the audience, the structure, and the ending. Models perform best when the boundaries of the task are clear.

Before you send a prompt, ask yourself: could a human follow this instruction and produce the exact output I want? If the answer is no, the prompt needs more specificity.

Giving the Model a Role

Assigning a role frames the model's behavior for the entire response. A role statement is usually one sentence at the start of the prompt, for example:

  • "You are a senior SQL expert who writes efficient, well-commented queries."
  • "You are a patient tutor for high-school physics students."
  • "You are a copy editor who tightens prose without changing meaning."

Roles work because they activate relevant patterns in the model. A prompt that begins with "you are a strict copy editor" is far more likely to produce edited text with tracked changes and comments than the identical request without the role.

Specifying the Output Format

Applications rarely want free-form prose. Telling the model the exact shape of the answer makes it both easier to read and easier to parse in code:

RequestWeak outputStructured output
Summarize this emailThree loose paragraphsSubject + 3 bullet points + action items
Classify a review"I think it's positive..."{"sentiment": "positive"}
Extract detailsSentences with the facts buried insideA table or JSON object with named fields

When you need JSON, say so explicitly and show the schema. A prompt that ends with "respond only with a JSON object with fields name, price, and available" reliably produces parseable output — no scraping required.

Providing Examples and Constraints

Two more ingredients do most of the heavy lifting in real prompts:

  • Examples show the model exactly what you mean. One or two worked examples often clarify a task better than a paragraph of instructions. This technique is called few-shot prompting and gets its own chapter later.
  • Constraints set the guardrails: "maximum 100 words", "do not mention prices", "answer in Spanish", "if you are unsure, say 'I don't know'". Constraints convert an open-ended task into a bounded one.

A prompt is a statement of intent, not a contract. Even a perfectly written prompt can produce a wrong answer. Treat prompt quality as the first line of defense, and validate the output in code — check for required fields, truncation, or clearly off-topic text.

A Practical Prompt Template

Combining the ingredients, a reliable working prompt looks like this:

Role:     You are an experienced data analyst.
Task:     Summarize the sales report below.
Format:   Respond with a bullet list of the top 3 findings,
          then one sentence on risks.
Constraint: Use plain language, no jargon, under 150 words.
---
{sales report text}

You can reuse this same skeleton across summarization, extraction, classification, and content tasks. The variable part is the task, the format, and the input — the discipline of filling in each field is the discipline of prompt engineering.

Iteration Is Part of the Process

Rarely is the first prompt the best prompt. The normal workflow is: draft, test, observe the failure mode, adjust, retest. Common failure modes and their fixes:

  • Too generic → add role and format.
  • Wrong structure → add a worked example.
  • Too long → add a length constraint.
  • Fabricates facts → instruct the model to state uncertainty and ground its answer in provided context.
  • Inconsistent across runs → lower temperature or tighten the prompt.

Keep a small prompt notebook: record the prompt, the output, and what you changed between versions. Pattern recognition across dozens of iterations is how prompt intuition is built.

Summary

A good prompt combines a clear instruction, relevant context, the input data, a specified output format, and explicit constraints. Roles, examples, and bounded tasks produce dramatically better results than bare questions, and iteration turns good prompts into reliable ones.
