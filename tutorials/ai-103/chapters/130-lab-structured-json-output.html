Lab - Structured JSON Output

In the previous lab the model answered with free-form text that varied from run to run. In this lab you will force the same analysis into strict JSON using the chat API's JSON mode, then parse the result into Python objects. When you finish, entity and topic extraction will return a predictable schema that your application code can consume without string parsing.

Prerequisites

  • The naive_prompt.py file and environment from the previous lab.
  • The json module (part of the standard library) and openai installed.

Step 1: Turn On JSON Mode

Exercise 1: Request valid JSON

Create json_output.py:

import json
import os

from dotenv import load_dotenv
from openai import AzureOpenAI

load_dotenv()

client = AzureOpenAI(
    azure_endpoint=os.getenv("AZURE_OPENAI_ENDPOINT"),
    api_key=os.getenv("AZURE_OPENAI_KEY"),
    api_version="2024-06-01",
)

DEPLOYMENT = "YOUR_DEPLOYMENT_NAME"

document = (
    "Acme Robotics shipped its new inspection drone to Frankfurt on "
    "March 12. CEO Dana Whitfield announced the launch at the plant "
    "near Berlin, with a retail price of 2,400 euros."
)

response = client.chat.completions.create(
    model=DEPLOYMENT,
    response_format={"type": "json_object"},
    messages=[
        {
            "role": "system",
            "content": (
                "You are a text analysis assistant. Always respond with "
                "valid JSON, no prose around it."
            ),
        },
        {
            "role": "user",
            "content": (
                "Extract the entities from this text. Return a JSON object "
                "with an 'entities' key holding a list of objects with "
                "'name' and 'type' fields.\n\n" + document
            ),
        },
    ],
)

content = response.choices[0].message.content
print(content)
data = json.loads(content)
print(type(data))
print(data["entities"])
  1. Run the script. The printed message should be a JSON object with an entities list.
  2. The final lines call json.loads and confirm the result is a real Python dict — proof your code can walk it like any other data.

JSON mode guarantees syntactically valid JSON, but it does not guarantee your schema. The model decides the exact key names and structure, so the instruction that specifies the schema is just as important as the JSON mode flag. If you need a hard contract, describe the schema in detail in the prompt.

Step 2: Add Topics to the Same Object

Exercise 2: Combine entities and topics in one response

Extend the script with a second analysis pass that returns both entities and topics in a single object:

response2 = client.chat.completions.create(
    model=DEPLOYMENT,
    response_format={"type": "json_object"},
    messages=[
        {
            "role": "system",
            "content": (
                "You analyze product reviews. Respond only in JSON."
            ),
        },
        {
            "role": "user",
            "content": (
                "Analyze this review and return a JSON object with two "
                "keys: 'entities' (list of {name, type}) and 'topics' "
                "(list of short strings).\n\n"
                "The camera arrived late and the autofocus hunts in low "
                "light, but Acme support replaced the lens unit quickly."
            ),
        },
    ],
)

data2 = json.loads(response2.choices[0].message.content)
print(json.dumps(data2, indent=2))
  1. Run the script and inspect the pretty-printed JSON.
  2. Check that both keys exist and that entities holds objects while topics holds plain strings.
  3. Add a malformed instruction — for example, ask for the schema with inconsistent field names in the system and user messages — and see how the model reconciles or ignores the conflict. This demonstrates why the schema instruction must live in one authoritative place.

Combining entities and topics in a single call saves tokens and latency versus two separate calls. The pattern generalizes: any analysis you can describe can be bundled into one JSON response.

Step 3: Write a Small Schema Validator

A parseable format is only half the battle — the fields must actually be present. A tiny validator turns schema drift into a clear error instead of a silent KeyError:

def require(data: dict, key: str, kind: type) -> list:
    value = data.get(key)
    if not isinstance(value, list) or not all(isinstance(i, kind) for i in value):
        raise ValueError(f"Field '{key}' must be a list of {kind.__name__}.")
    return value

entities = require(data2, "entities", dict)
topics = require(data2, "topics", str)
print(f"Parsed {len(entities)} entities and {len(topics)} topics.")
  1. Append the validator to json_output.py and run it.
  2. Temporarily change one key name in the prompt (for example, topic instead of topics) and rerun. The validator should raise a descriptive error instead of crashing with an obscure KeyError.

In production, prefer a library such as Pydantic for validation. The hand-rolled validator above is intentionally small so you can see the principle: treat model output as untrusted data and check it before use.

Summary

You switched a chat model into JSON mode, asked it to return entities and topics under a fixed schema, parsed the output with json.loads, and validated the structure before use. Structured output turns a chat model from a text generator into a reliable data-transformation component. In the next lab you will apply the same prompting approach to sentiment and tone.
