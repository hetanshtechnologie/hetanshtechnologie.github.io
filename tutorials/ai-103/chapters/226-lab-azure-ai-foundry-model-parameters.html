Lab - Azure AI Foundry - Model parameters

Model parameters are the dials you turn to control how a language model generates text. They do not change what the model knows; they change how it samples from its probability distribution when it produces each token. In this lab you will adjust the most important parameters — temperature, top-p, max tokens, and stop sequences — in the playground and observe exactly what each one does to the output.

What You Will Need

  • The playground open with your deployed chat model selected.
  • A simple, repeatable prompt you will reuse across every test below.
  • A few minutes of patience: parameter effects are easiest to see when you change one dial at a time.

How Sampling Parameters Work

When a model generates text, it assigns a probability to every possible next token and then picks one. The picking strategy is what you control:

ParameterWhat it controlsLow valueHigh value
temperatureCreativity of the token selectionDeterministic, repetitiveVaried, sometimes random
top_pHow many top candidates are consideredNarrow, safe choicesWide, more variety
max_tokensHard cap on response lengthShort answersLonger answers
stopStrings that end generation earlyNoneList of end markers

The recommended guidance is to adjust either temperature or top-p, not both at the same time. Changing both at once muddies which dial caused the difference you are seeing.

Step 1: Test Temperature

Exercise 1: Watch temperature change creativity

  1. Use the prompt "List three creative names for a coffee shop that serves books."
  2. Set temperature to 0 and send the prompt three times. The answers should be nearly identical.
  3. Set temperature to 1 and send the same prompt three times. The lists will now differ between runs.
  4. Record which setting produces the most useful output for your use case.
# Minimal JSON request for a temperature test
{
  "messages": [
    {"role": "system", "content": "You are a creative naming assistant."},
    {"role": "user", "content": "List three creative names for a coffee shop that serves books."}
  ],
  "temperature": 0.0,
  "max_tokens": 100
}

Use a low temperature for tasks where accuracy matters: classification, extraction, translation, and structured data. Use a higher temperature for brainstorming, marketing copy, and creative writing where variety is the point.

Step 2: Test Top-p

Top-p keeps the set of candidate tokens whose combined probability reaches a given threshold, then picks from that set. A low top-p makes the model conservative; a high top-p lets it roam:

  1. Reset temperature to a neutral 0.7.
  2. Set top_p to 0.1 and ask "Suggest one tagline for a travel app."
  3. Set top_p to 1 and ask the same question. Compare how conventional the two results are.

Step 3: Test Max Tokens

Max tokens caps how much the model can produce in one response. It is both a cost control and a reliability control:

  1. Ask "Write a short story about a robot who learns to paint."
  2. Set max_tokens to 40 and send. The story cuts off mid-sentence.
  3. Raise max_tokens to 500 and send again. The model now completes the story.

When the model hits the token cap, the API marks the response as truncated. In production code you must check this and tell the user the answer was cut off. Otherwise users silently receive incomplete answers and blame the model for something the settings caused.

Step 4: Test Stop Sequences

A stop sequence tells the model to stop generating the moment a specific string appears. It is ideal for forcing a clear boundary between sections:

  1. Ask "Write two sentences about the sun. Then stop."
  2. Add Then as a stop sequence and resend. Generation halts as soon as the model begins that word.
  3. Remove the stop sequence and resend to see the difference.
# JSON with a stop sequence
{
  "messages": [
    {"role": "user", "content": "Write two sentences about the sun. Then stop."}
  ],
  "max_tokens": 200,
  "stop": ["\n\n"]
}

Choosing Parameters for Your Application

There is no universally correct setting — parameters are chosen per task. A good default starting point for most apps is temperature 0.3 to 0.7, top_p 0.9, a generous max_tokens, and no stop sequence. Then you adjust based on what you observe, changing one dial at a time and keeping a log of what worked.

Summary

You tested temperature, top-p, max tokens, and stop sequences against a live deployment and saw each one shift the output. You now know the practical trade-offs: low values for accuracy, higher values for creativity, token caps for cost, and stop sequences for structure. Next you will add a system prompt to steer the model's behavior from the very first message.
