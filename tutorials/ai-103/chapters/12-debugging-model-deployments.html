Debugging model deployments

Sooner or later, every developer stares at a model endpoint that is not behaving. This chapter gives you a systematic way to debug model deployments: how to read the failure, where to look for the cause, and how to fix the common problems. Most issues fall into a small number of recognizable categories, so a little structure saves a lot of guessing.

The Most Common Failure Modes

Almost every deployment problem belongs to one of these families. When something breaks, start by classifying it:

SymptomLikely causeQuick check
401 / 403Wrong or expired key, or missing permissionsCompare your key with the one in the portal
404Wrong URL, deployment name, or API versionCopy the exact endpoint from the deployment page
429Rate limit or quota exhaustedCheck the monitoring dashboard for usage
Timeout / slowLong prompts, high max_tokens, or low capacityReduce the request size or raise capacity
Empty or odd responsePrompt or settings issue, content filterTest the same prompt in the playground
Deployment stuck provisioningRegional availability or quota problemCheck the deployment status and region

Work Through HTTP Status Codes First

The HTTP status code is the first diagnostic signal. Do not skip it:

  • 4xx errors mean your request is the problem — a bad key, a wrong URL, a malformed body. The fix is in your code or configuration.
  • 5xx errors mean the service or endpoint has a problem. Retry with backoff, check service status, and verify the deployment is in a Ready state.

Read the entire error message, not just the status code. The JSON body returned by the endpoint usually names the exact problem — an invalid deployment name, an unsupported parameter, or a quota limit. Paste that body into a search engine and you will often find the fix directly.

Verify the Obvious Things in Order

When a request fails, walk this checklist before changing anything clever:

  1. Deployment name: Is it spelled exactly as shown on the deployment page? Names are case-sensitive.
  2. Endpoint URL: Does it match the value shown in the portal, including the https:// prefix?
  3. API version: Is the version string valid and supported? The portal shows a working example you can copy.
  4. Key: Is the key current, correct, and not accidentally truncated when copied?
  5. Request body: Is the JSON valid, with the right field names for the model's API?
  6. Deployment status: Is the deployment actually in a Ready state?

In practice, the vast majority of 4xx errors are a mistyped deployment name or a stale key.

Debugging with curl

Your code adds layers — SDKs, config files, environment variables — that can hide the real problem. Strip them away and hit the endpoint directly with curl. If the raw request works, the bug is in your code; if it fails, the bug is in your configuration. Start from the working example the portal provides:

curl.exe https://YOUR_ENDPOINT/openai/deployments/YOUR_DEPLOYMENT_NAME/chat/completions?api-version=2024-06-01 `
  -H "api-key: YOUR_KEY" `
  -H "Content-Type: application/json" `
  -d '{"messages":[{"role":"user","content":"Hello"}]}'

The portal's deployment page usually offers a "Show code" or "Sample code" view that contains a complete, working request. Use it as your ground truth: if the sample works and your application does not, compare them line by line — the difference is your bug.

Debugging Response Quality

Sometimes the endpoint works but the answer is wrong, empty, or unexpected. That is a quality problem, not a connection problem, and it has a different checklist:

  • Empty content with a content-filter reason: The request or response tripped a safety filter. Rephrase the prompt, or check the filter severity in the response metadata.
  • Short or cut-off answers: Raise max_tokens or ask the model to be more detailed in the prompt.
  • Repetitive output: Adjust sampling settings such as temperature and penalties.
  • Inconsistent format: Add explicit output-format instructions or use structured-output features.
  • Wrong facts: The model is hallucinating; ground it with retrieved data or add sources to the prompt.

Do not chase quality problems with deployment changes. Retrying, changing capacity, or redeploying will not fix a hallucination or a bad tone. Quality fixes belong in the prompt, the settings, or the data pipeline — not in the deployment configuration.

Deployment Not Appearing or Not Ready

If a new deployment never reaches Ready status, the usual culprits are regional model availability, exhausted quota, or a provisioning delay. Check the deployment's error message, confirm the model is offered in the chosen region, and either request a quota increase or redeploy in a different region. If the deployment shows in Foundry but not in the Azure portal, refresh both — they occasionally lag each other by a minute.

Systematic Logging as a Debugging Tool

The best debugging tool is a good log. Make your application log the essentials for every request — the deployment used, the response status, the finish reason, and the token usage. When a problem appears later in production, these logs tell you exactly what happened instead of forcing a reconstruction:

print(f"deployment={deployment} status={status} "
      f"finish={finish_reason} tokens={usage}")

Summary

Debugging a model deployment starts with classifying the failure, then working through the obvious checks — deployment name, endpoint, API version, key, body, and status. Connection problems are fixed in configuration; quality problems are fixed in prompts, settings, and data. The playground, curl, and good logging are the tools that make the diagnosis fast.
