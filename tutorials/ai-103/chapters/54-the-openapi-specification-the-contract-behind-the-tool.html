The OpenAPI Specification - The Contract Behind the Tool

Before a machine can call an API reliably, it needs to know exactly what the API accepts and returns. The OpenAPI Specification is the de facto standard for that description: a JSON or YAML document that defines the endpoints, the inputs, the outputs, and the errors of an HTTP API. In this chapter you learn the parts of an OpenAPI document and write a small one for the CloudXeus orders service.

What an API Contract Buys You

  • Clients, including agents, can discover operations without reading source code.
  • Tools can generate code, tests, and documentation from one file.
  • Foundry can convert operations into callable agent tools automatically.
  • Changes become reviewable diffs instead of undocumented rewrites.

The Shape of an OpenAPI Document

Every OpenAPI document is organized around four top-level sections:

  • info: the title, version, and description of the API.
  • servers: the base URLs the API is hosted at.
  • paths: the actual operations, grouped by URL path.
  • components: reusable schemas and other building blocks.

Optionally, a security section declares how callers authenticate.

Operations

A path such as /orders/{order_id} can have several operations, one per HTTP method. Each operation declares:

  • operationId: a unique name that tools use to refer to the operation.
  • summary and description: human- and model-readable guidance on when to use it.
  • parameters: path, query, and header inputs.
  • requestBody: the JSON payload for write operations.
  • responses: the possible status codes and their shapes.

Write the summary and description for the model, not only for humans. In an agent setting these strings are the model's manual for when to pick each operation, so be concrete: Get the full status of one CloudXeus order by its id beats Get order.

Components and Schemas

Repeated shapes are defined once in components/schemas and referenced with $ref. This keeps the document tidy and makes request and response bodies precise:

"components": {
  "schemas": {
    "Order": {
      "type": "object",
      "properties": {
        "id": {"type": "string"},
        "customer_email": {"type": "string"},
        "status": {"type": "string", "enum": ["placed", "shipped", "cancelled"]},
        "total": {"type": "number"}
      },
      "required": ["id", "customer_email", "status"]
    }
  }
}

A Complete Example

Putting it together, a minimal CloudXeus orders API spec has two operations: list orders for a customer, and get one order by id.

{
  "openapi": "3.0.1",
  "info": {"title": "CloudXeus Orders API", "version": "1.0.0"},
  "servers": [{"url": "https://YOUR_FUNCTION_APP.azurewebsites.net/api"}],
  "paths": {
    "/orders": {
      "get": {
        "operationId": "list_orders",
        "summary": "List orders for a customer",
        "parameters": [
          {"name": "email", "in": "query", "required": true,
           "schema": {"type": "string"}}
        ],
        "responses": {
          "200": {
            "description": "The customer's orders",
            "content": {
              "application/json": {
                "schema": {
                  "type": "array",
                  "items": {"$ref": "#/components/schemas/Order"}
                }
              }
            }
          }
        }
      }
    },
    "/orders/{order_id}": {
      "get": {
        "operationId": "get_order",
        "summary": "Get one CloudXeus order by its id",
        "parameters": [
          {"name": "order_id", "in": "path", "required": true,
           "schema": {"type": "string"}}
        ],
        "responses": {
          "200": {
            "description": "The order",
            "content": {
              "application/json": {
                "schema": {"$ref": "#/components/schemas/Order"}
              }
            }
          },
          "404": {"description": "Order not found"}
        }
      }
    }
  },
  "components": {
    "schemas": {
      "Order": {
        "type": "object",
        "properties": {
          "id": {"type": "string"},
          "customer_email": {"type": "string"},
          "status": {"type": "string"},
          "total": {"type": "number"}
        }
      }
    }
  }
}

The operationId becomes the tool name when Foundry imports this spec, so choose short, unique, snake_case names. Duplicate operationIds are invalid and will fail to import.

Validating and Maintaining the Spec

  • Validate your file against the OpenAPI schema with a tool such as the Swagger editor before importing it.
  • Keep descriptions in sync with the real API; an outdated spec produces confident but wrong tool calls.
  • Version the API and its spec together so agents always bind to a consistent contract.

Summary

The OpenAPI Specification is the contract that turns an HTTP API into something agents can use. You now know its four main sections, how operations are described, and how components keep schemas reusable.
