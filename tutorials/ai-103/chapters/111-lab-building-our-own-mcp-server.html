Lab - Building our own MCP Server

You have called someone else's MCP server. Now you will build your own. This lab walks you through creating a small MCP server in Python that exposes a couple of genuinely useful tools — a contact lookup and a simple calculator — using the official MCP SDK. When you finish, you will own the whole stack: your tools, your schemas, your endpoint.

Prerequisites

  • Your Python virtual environment from the earlier labs.
  • The MCP SDK and its server extras installed:
pip install "mcp[server]"

The server extras pull in everything needed to run both transports. If the [server] extra fails to resolve on your platform, install mcp alone — it includes the core primitives you need for this lab.

Step 1: Design Your Server

Your server will expose two tools:

ToolPurposeArguments
lookup_contactReturn an email address for a name from a small in-memory directoryname (string)
evaluate_expressionEvaluate a simple arithmetic expression safelyexpression (string)

Both are intentionally simple so the focus stays on MCP mechanics rather than domain logic. In a real deployment these would call a database and a proper computation engine.

Step 2: Write the Server

Exercise 1: Create the MCP server

Create my_mcp_server.py:

import ast
import operator

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("ai103-contact-server")

CONTACTS = {
    "sam": "sam@example.com",
    "HetanshTechnologie": "HetanshTechnologie@example.com",
    "mira": "mira@example.com",
}


@mcp.tool()
def lookup_contact(name: str) -> str:
    """Return the email address for a person by name."""
    key = name.strip().lower()
    if key not in CONTACTS:
        return f"No contact found for {name}."
    return f"{name} <{CONTACTS[key]}>"


SAFE_OPERATORS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.Pow: operator.pow,
    ast.USub: operator.neg,
}


def _safe_eval(node):
    if isinstance(node, ast.Constant):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in SAFE_OPERATORS:
        left = _safe_eval(node.left)
        right = _safe_eval(node.right)
        return SAFE_OPERATORS[type(node.op)](left, right)
    if isinstance(node, ast.UnaryOp) and type(node.op) in SAFE_OPERATORS:
        return SAFE_OPERATORS[type(node.op)](_safe_eval(node.operand))
    raise ValueError("Unsupported expression.")


@mcp.tool()
def evaluate_expression(expression: str) -> float:
    """Evaluate a simple arithmetic expression such as '2 + 3 * 4'."""
    tree = ast.parse(expression, mode="eval")
    return _safe_eval(tree.body)


if __name__ == "__main__":
    mcp.run(transport="stdio")

The FastMCP class generates the tool schemas from your functions' type hints and docstrings automatically — the same decoration pattern you used with LangChain, but for the MCP protocol.

Never evaluate arbitrary input with Python's eval. The example above walks an AST and only allows a fixed set of operators, which is why it is safe. This matters especially for servers that face the network: a tool that runs eval on user input is an invitation to arbitrary code execution.

Step 3: Run the Server Locally

Exercise 2: Start the server over stdio

  1. Run the server from the activated environment:
python my_mcp_server.py
  1. The server prints nothing and waits — stdio servers only respond to messages on standard input. Leave the process running and open a second terminal for the next step.
  2. Confirm it stays up with no errors. If you see a traceback, fix the import before continuing.

A quiet terminal is a healthy sign for a stdio server. It means the process launched and is blocked waiting for protocol messages. Any startup exception would print immediately.

Step 4: Add an HTTP Transport

A stdio server only works on one machine. To reach it from other hosts — or from a container in Azure — add the HTTP (SSE) transport. This makes the server a network endpoint your agents can call remotely:

if __name__ == "__main__":
    mcp.run(transport="sse", host="0.0.0.0", port=8080)

Restart the server and you now have an endpoint at http://localhost:8080/sse. This is the same shape as the Azure-hosted server you called in the previous lab — the difference is that this one is yours.

Binding to 0.0.0.0 exposes the server on all network interfaces, including your LAN. Only do this when you understand who can reach it. For a public deployment, put authentication in front of the endpoint and prefer HTTPS.

Step 5: Containerize for Azure

To deploy this server the way you deployed the Azure MCP server, package it as a container. Create a Dockerfile in the project folder:

FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY my_mcp_server.py .

EXPOSE 8080
CMD ["python", "my_mcp_server.py"]

Create requirements.txt alongside it:

mcp[server]

Build and push the image to a registry, then deploy it with the same az containerapp create steps you used in the Azure MCP deployment lab — pointing the image at your own container this time.

Deployment is a review, not a new skill. The container app, environment, ingress, and FQDN steps are identical to the earlier lab; only the image name and the tools inside change.

Summary

You built an MCP server with the Python SDK that exposes two original tools with automatically generated schemas, ran it over stdio, added an SSE transport for remote access, and containerized it for Azure Container Apps. Your server is now a genuine participant in the MCP ecosystem. In the next lab you will connect a client to it and put the tools to work.
