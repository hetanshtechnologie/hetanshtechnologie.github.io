Understanding State Conversations, Session Context, and Memory

Ask a model a question and it answers. Ask a follow-up that depends on the first answer and the model seems to remember — but only because your code sent the earlier turns back to it. This chapter untangles the vocabulary people use when they talk about agent memory: state, conversations, sessions, context, and memory. Getting these straight is the difference between an agent that seems to remember and one that actually does.

Models Are Stateless

Every call to a chat model is independent. The model has no knowledge that a previous request from the same client ever happened. What looks like memory is really input: whatever conversation history your code includes in the request. If you send only the latest user message, the model answers with no idea what came before.

This is the single most important idea in the section. Statelessness is not a bug you must fight; it is a design that keeps the model simple and makes memory a problem your application can control explicitly.

State: What the Agent Knows at a Moment

State is the complete set of information an agent has access to at any point in a run: the system instructions, the conversation history, any variables set during the session, and the results of tool calls. State is a snapshot. Two identical requests with different state produce different behavior, and the same state applied to two requests makes behavior reproducible.

Conversation History

In practical API terms, the conversation is the list of messages you send: system, user, assistant, and tool entries in order. The model reads this list and continues from it.

  • History grows with every turn.
  • You control what is in it: you can trim it, summarize it, or keep only recent turns.
  • What you include is what the model sees; nothing more.

Conversation history is therefore your first and simplest memory mechanism, bounded by the context window.

Session Context

A session is a container for one logical interaction with a user — one chat thread, one customer support case, one window of a web app. Session context is the working data tied to that container: the user id, the topic being discussed, the current order id, and the accumulated conversation.

ConceptScopeLives where
Conversation historyOne chat threadIn the request messages you send
Session contextOne user interactionIn memory, a cache, or a store keyed by session id
Persistent memoryAcross sessionsIn a durable database

Context Window: The Room You Have

The context window is the token budget for everything in a single request: system prompt, conversation history, tool definitions, tool results, and the answer being generated. Context window and memory are different things:

  • The context window is a limit you can run out of.
  • Memory is anything you keep outside the window and bring back when needed.

Good agent design treats the context window as scarce space. You do not stuff all of history into it; you curate what is relevant to the current turn.

Working Memory vs Long-Term Memory

It helps to borrow the two-layered model humans use:

TypeWhat it holdsExample
Working memoryWhat is active right now, in the context windowThe current order id during a support conversation
Long-term memoryWhat persists across sessionsThe customer's shipping preference, saved from last week

Working memory is cheap but volatile: it exists only while the conversation is alive. Long-term memory is durable but must be explicitly stored, retrieved, and scoped.

Memory vs Context

The pair is easy to confuse, so pin it down:

  • Context is what the model sees at generation time — always a subset of what exists.
  • Memory is what the system retains — the superset that can be recalled into context.

Every turn your code moves selected memory into context. Choosing what to move, and when to stop moving it, is the craft of agent memory.

When you design an agent, ask three questions about every piece of information: Does this turn need it? Will later turns in this session need it? Will a future session need it? The answers tell you whether the information belongs in the context window, in session state, or in persistent storage.

Where State Lives

State can live at several layers, and each layer has different durability:

LayerDurabilityTypical use
In-memory in your processLives until the process stopsSession scratchpad, current tool state
CacheLives minutes to hoursSession context across serverless instances
DatabaseLives indefinitelyLong-term memory, user preferences, audit

Serverless platforms make this concrete: a function instance can disappear at any time, so anything you truly want to keep must live outside the process.

Never store secrets or personal data in memory you cannot scope. If two users share a session store, one user's orders can leak into the other's context. Memory must always be scoped to its owner, whether that is a user, a tenant, or a session id.

Summary

Model calls are stateless, so memory is built by your code: conversation history rides in the request, session context binds working data to one interaction, and persistent memory survives across sessions. The context window caps what the model sees at any moment, which is why memory must be curated rather than dumped.
