Lab - Function Tool Calling - Defining the application

In the previous lab the agent stopped mid-run at requires_action with a function call it could not execute itself. This lab is the missing half: an application that implements the functions, dispatches the model's calls, submits the results back, and lets the run continue to a final answer. When you finish, you will have a complete agent application — model planning, your code acting.

Objectives

  • Implement the two functions the agent declares.
  • Dispatch a model's tool calls to the right function.
  • Submit tool outputs, resume the run, and read the final answer.

The Tool-Call Cycle

The full cycle has five stages, and each is visible in the code below:

  1. Start a run; the model emits a tool call and the run enters requires_action.
  2. Read the requested function names and arguments from the run.
  3. Execute the matching local functions.
  4. Submit the outputs back to the run.
  5. Poll until the run completes and the agent writes its final answer.

Step 1: Implement the functions

Write the two functions as plain Python. In a real system these would call a weather API and a booking service; here they return simple, clearly fake estimates so you can see the flow end to end.

Add the function implementations

def get_weather(city: str) -> dict:
    return {
        "city": city,
        "conditions": "sunny with light clouds",
        "high_c": 24,
        "low_c": 17,
        "rain_chance_pct": 10,
    }

def get_hotel_rate(city: str, nights: int) -> dict:
    base = 140 if city.lower() == "paris" else 95
    return {
        "city": city,
        "nights": nights,
        "nightly_rate_usd": base,
        "total_estimate_usd": base * nights,
    }

Return JSON-serializable values — dicts, lists, strings, numbers. The tool output is text that gets fed back to the model, so keep it structured and complete rather than pretty-printed prose.

Step 2: Dispatch tool calls to functions

The model's call gives you a function name and arguments. Write a dispatcher that maps names to implementations, catches unknown names, and returns results in the form the run expects.

Create the dispatcher

FUNCTION_IMPL = {
    "get_weather": get_weather,
    "get_hotel_rate": get_hotel_rate,
}

def dispatch_tool_call(name: str, arguments: dict):
    implementation = FUNCTION_IMPL.get(name)
    if implementation is None:
        return {"error": f"Unknown function: {name}"}
    return implementation(**arguments)

Step 3: Build the complete client

Now assemble everything into one script. The run loop watches for requires_action, executes every requested call, submits the outputs, and then keeps polling. The loop is short because the agent in this lab needs only one round of tool calls before it can answer.

Create run_agent_with_tools.py

import json
import os
import time
from dotenv import load_dotenv
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

load_dotenv()

project_client = AIProjectClient.from_connection_string(
    credential=DefaultAzureCredential(),
    conn_str=os.getenv("PROJECT_CONNECTION_STRING"),
)

agent = next(
    a for a in project_client.agents.list_agents().data
    if a.name == "trip-planner-functions"
)

thread = project_client.agents.create_thread()
project_client.agents.create_message(
    thread_id=thread.id,
    role="user",
    content="We want 3 nights in Paris. What should we pack and roughly "
            "what will the hotel cost?",
)

run = project_client.agents.create_run(
    thread_id=thread.id, agent_id=agent.id
)

while run.status in ("queued", "in_progress", "requires_action"):
    if run.status == "requires_action":
        tool_calls = (
            run.required_action.submit_tool_outputs.tool_calls
        )
        outputs = []
        for call in tool_calls:
            arguments = json.loads(call.function.arguments)
            result = dispatch_tool_call(call.function.name, arguments)
            outputs.append(
                {
                    "tool_call_id": call.id,
                    "output": json.dumps(result),
                }
            )
        run = project_client.agents.submit_tool_outputs(
            thread_id=thread.id,
            run_id=run.id,
            tool_outputs=outputs,
        )
    run = project_client.agents.get_run(
        thread_id=thread.id, run_id=run.id
    )
    time.sleep(1)

messages = project_client.agents.list_messages(thread_id=thread.id)
for item in reversed(messages.data):
    if item.role == "assistant" and item.content:
        for part in item.content:
            if hasattr(part, "text"):
                print(part.text.value)

The submit_tool_outputs call is what changes requires_action back into in_progress. Until the outputs are submitted, the run cannot continue — this is the moment your application actually performs the work the model requested.

Step 4: Run and inspect

Execute the script and watch for two things in the output:

  • The run loop goes through requires_action once or twice, proving the tool cycle executed.
  • The final answer includes both the weather-based packing advice and a hotel cost estimate grounded in your function's numbers.
python run_agent_with_tools.py

Challenge: force two calls

  1. Change the user message to ask only about the hotel rate.
  2. Confirm the agent calls get_hotel_rate and nothing else.
  3. Add a third function to the schema and implementation, such as get_flight_time, and watch the agent decide when to use it.

Your functions here are safe simulations, but real function tools can mutate real systems — send emails, place orders, or update records. Before exposing any function to a model, ask: what is the worst reasonable call the model could make, and is that call reversible?

Summary

You completed the full function-calling contract: the agent declares functions and plans calls, and your application executes them and returns results. The dispatcher pattern — mapping names to implementations, running them, and submitting outputs — is the exact skeleton you will reuse for real integrations with booking systems, databases, and internal APIs. Your agent now acts, not just talks.
