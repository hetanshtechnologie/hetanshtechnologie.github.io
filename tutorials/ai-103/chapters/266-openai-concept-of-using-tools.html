OpenAI - Concept of using Tools

A language model on its own can only produce text — it cannot check a database, call an API, or look anything up. Tools (also called function calling) fix this by letting the model request that your application perform an action. This chapter explains the concept: what tools are, how the model requests them, and how the call-and-response loop works.

The Core Idea

Tools extend a model's reach. You define functions that the model is allowed to call, describe them in a machine-readable form, and hand those descriptions to the model. When the model decides it needs data or an action to answer the user, it does not fake the result. Instead it emits a request: "call function get_weather with arguments {location: Seattle, date: tomorrow}".

Your application then:

  1. Receives the tool call.
  2. Executes the real function.
  3. Sends the result back to the model.
  4. Lets the model compose the final answer using the real data.

This is why tool use powers assistants that can book flights, query databases, and control devices — the model reasons, your code acts.

Describing a Tool to the Model

The model never sees your Python function. It sees a JSON description with a name, a description, and a parameter schema. That schema is what the model uses to fill in valid arguments:

tools = [
    {
        "type": "function",
        "name": "get_weather",
        "description": "Get the current or forecast weather for a city.",
        "parameters": {
            "type": "object",
            "properties": {
                "location": {"type": "string"},
                "date": {"type": "string"}
            },
            "required": ["location"]
        }
    }
]

The description matters: it is the model's only guide to when and how to call the tool, so write it like documentation.

The model does not execute anything. It only produces a structured request. This is a deliberate safety boundary — your code stays in control of what actually runs, which lets you add permission checks, logging, and rate limiting around every tool.

The Call Loop in Practice

A complete tool interaction has three or more round trips. In the Responses API the loop looks like this in outline:

from openai import OpenAI

client = OpenAI(api_key="YOUR_API_KEY")

def get_weather(location: str, date: str) -> str:
    # Real code: query a weather service here.
    return f"sunny, 22C in {location} on {date}"

response = client.responses.create(
    model="gpt-4o-mini",
    input="Is it nice in Seattle tomorrow?",
    tools=tools,
)

# The model either answers directly or asks us to call a tool.
print([item.type for item in response.output])

If the model produced a function_call item, you extract its arguments, run your real function, and send the result back in the next request as tool output. The model then finishes with a natural-language answer.

Multiple and Chained Calls

One turn can require several tools. The model might check weather and then fetch flight prices, producing two tool calls. Applications loop: while the response still contains pending function calls, keep executing and feeding results back. This chain is how agents solve multi-step problems, and it is the subject of the next chapters.

Keep tool descriptions precise and parameters minimal. A tool with too many optional parameters invites the model to guess values it does not have. Where possible, make parameters required or give them clear default behavior.

Choosing Between Tools and Prompting

SituationBetter choice
The answer needs live data (stock price, DB row)Tool call
The answer needs a calculation or actionTool call
The answer is derivable from knowledge alonePlain generation
You want the model to merely format known factsStructured output

Use tools when the model must access something outside its training data or cause a real effect.

Summary

Tools let models request real-world actions through structured calls. You learned how tools are described with a name, description, and parameter schema, how the model emits function-call requests, and how your code executes them and feeds results back. This call-and-response loop is the engine behind every agent you will build in later chapters.
