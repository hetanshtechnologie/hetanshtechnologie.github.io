Lab - Listing Tools on the Azure Language MCP Server

Every MCP session begins the same way: connect, initialize, and ask the server what it can do. The tools/list call is that question, and the answer — the tool catalog with descriptions and input schemas — is the contract your agent builds on. In this lab you will fetch that catalog from the Azure Language MCP server, inspect the schema of each tool, and practice reading a schema the way a model would.

Prerequisites

  • A deployed Azure Language MCP server with its URL and access key.
  • Your Python environment with the MCP SDK installed:
pip install mcp httpx

Step 1: Fetch the Tool Catalog

Exercise 1: List tools and their descriptions

Create mcp_list_tools.py:

import asyncio

from mcp import ClientSession
from mcp.client.sse import sse_client

SERVER_URL = "http://YOUR_SERVER_FQDN/sse"
ACCESS_KEY = "YOUR_GENERATED_KEY"


async def main():
    read, write = await sse_client(SERVER_URL, headers={
        "Authorization": f"Bearer {ACCESS_KEY}",
    })
    async with ClientSession(read, write) as session:
        await session.initialize()
        tools = await session.list_tools()
        print(f"Connected. {len(tools.tools)} tool(s) exposed:\n")
        for tool in tools.tools:
            print(f"- {tool.name}")
            print(f"  {tool.description}\n")


asyncio.run(main())
  1. Run the script. You should see the server's language tools — translation, language detection, sentiment, entity extraction, and PII redaction, depending on the server version.
  2. Count the tools and compare with the expected catalog from the lecture chapter. Any difference is a version difference, not a problem.

Discovery failure means transport or authentication trouble: the server is unreachable, the endpoint path is wrong, or the access key is missing or invalid. Success at this step proves the connection layer is sound and moves the problem to the call layer.

Step 2: Print the Input Schemas

Exercise 2: Read each tool's argument contract

Extend the script to print the full JSON schema of every tool:

import json

        for tool in tools.tools:
            print(f"=== {tool.name} ===")
            print(json.dumps(tool.inputSchema, indent=2))
            print()
  1. Run the script and study the schema of translate_text. It should declare text and to as required string properties, with an optional from property.
  2. Compare that with the schema for detect_language or analyze_sentiment, which should require only text.
  3. Note any required arrays, descriptions, and defaults — these are the details a model uses to build a correct call.

The schema is the source of truth for tool calling. When a model or a human passes the wrong argument name or type, the failure usually traces back to the schema — which is why printing it is the first debugging move.

Step 3: Build a Helper That Finds a Tool by Name

Exercise 3: Look up a tool before calling it

Add a lookup helper that returns a tool and its required fields:

def find_tool(tools, name: str):
    for tool in tools.tools:
        if tool.name == name:
            return tool
    return None


        translate = find_tool(tools, "translate_text")
        if translate is None:
            print("translate_text not found. Available tools:")
            for tool in tools.tools:
                print(" -", tool.name)
        else:
            required = translate.inputSchema.get("required", [])
            props = list(translate.inputSchema.get("properties", {}).keys())
            print("translate_text requires:", required)
            print("declared properties:", props)
  1. Run the script. The helper should report the required fields of translate_text.
  2. Change the requested name to translate and rerun. The helper should fall back to printing the full catalog, mirroring the diagnostic path you would follow in a real agent.

Step 4: Simulate What a Model Sees

A model does not read the catalog like a human — it receives the tool names, descriptions, and schemas as its tool definitions, then predicts which tool and arguments fit the user's request. To simulate that, print a compact, model-style summary of the catalog:

def summarize(tools) -> str:
    lines = []
    for tool in tools.tools:
        props = ", ".join(tool.inputSchema.get("properties", {}).keys())
        lines.append(f"{tool.name}: {tool.description} | args: {props}")
    return "\n".join(lines)


        print("Model-facing summary:")
        print(summarize(tools))
  1. Run the script and read the summary. Decide which tool you would choose to translate a sentence, detect a language, or score sentiment.
  2. Now use that same mental decision as the expected behavior of an agent: the description and args are precisely the signal the model uses, so vague descriptions here directly degrade agent performance.

If you ever find an agent calling the wrong tool, the fix is usually in the catalog, not in the agent: make descriptions unambiguous and distinct, and name arguments consistently with the tool's purpose.

Summary

You connected to the Azure Language MCP server, fetched its tool catalog with tools/list, printed and interpreted the input schemas, built a lookup helper, and reproduced the model's view of the catalog. Discovery is the layer where transport and authentication problems surface first, so this lab doubles as the diagnostic foundation for every MCP integration that follows.
