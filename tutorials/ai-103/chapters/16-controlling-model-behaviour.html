Controlling Model Behaviour

In the previous lab you made a raw API call and got a plain answer. That is only the beginning. A deployed model is not a single fixed behaviour; it is a general-purpose engine that can behave like a customer agent, a translator, a JSON generator, or a strict factual assistant depending on how you configure each request. This chapter explains the levers that control model behaviour: the system prompt, sampling parameters, output formatting, and few-shot examples.

Behaviour Is Configured, Not Hard-Coded

Once a model is trained, its weights are frozen. When you change its behaviour, you are not retraining it. Instead you are changing the context and settings of each inference call. This is a crucial idea: all of the steering happens at request time through the parameters you pass to the API. That is what makes one deployment reusable for many different jobs.

The System Prompt: Setting the Role and the Rules

The most powerful behavioural control is the system prompt. It is a message with role: "system" that describes who the model is, what rules it must follow, and how it should respond. It stays in effect for the whole conversation, unlike a user message which applies to a single turn.

A good system prompt covers:

  • Identity: who the assistant is and who it serves.
  • Tone and style: formal, friendly, technical, brief, and so on.
  • Rules: what to do and what to refuse.
  • Format: plain text, bullet points, tables, JSON.
  • Limits: length, topics, fallback behaviour when information is missing.

Compare these two system prompts:

{"role": "system", "content": "You are a helpful assistant."}

{"role": "system", "content": "You are a support agent for a software company. Answer in two sentences or fewer, use plain language, and if you do not know the answer, say you will escalate the question."}

Write the system prompt as if you were briefing a new employee. The clearer and more specific the briefing, the more consistent the responses.

Sampling Parameters: Creativity vs Determinism

Every time the model produces a token, it assigns probabilities to a set of candidate tokens and picks one. Sampling parameters control how that pick is made.

ParameterWhat it controlsLower valueHigher value
temperatureHow much the model favours likely over unlikely tokens.More focused, predictableMore varied, creative
top_pThe cumulative probability mass considered when picking.Narrow, conservativeBroad, exploratory
max_tokensHard limit on the length of the generated answer.Shorter answersLonger answers
frequency_penaltyDiscourages repeating tokens that already appeared.More repetitionLess repetition
presence_penaltyEncourages talking about new topics.Stays on topicShifts topics more
seedSets a starting state to make sampling more reproducible.Same seed tends to give similar output

temperature and top_p both influence randomness and interact with each other. It is best practice to adjust one at a time and leave the other at its default instead of pushing both aggressively.

In practice, code and factual tasks work well with temperature near zero, while brainstorming, naming, and creative writing benefit from values around 0.7 or higher.

Requesting Structured Output

Raw prose is hard to parse in an application. Many workloads need JSON. You can instruct the model to emit JSON and, on recent models, you can enforce it with the response_format parameter:

response = client.chat.completions.create(
    model="YOUR_DEPLOYMENT_NAME",
    response_format={"type": "json_object"},
    messages=[
        {"role": "system", "content": "Return a JSON object with keys: name and summary."},
        {"role": "user", "content": "Summarise the book Moby Dick."},
    ],
)

When you enforce a JSON format, also describe the schema in the prompt. The model then knows exactly which keys to produce, and your code can parse the result with json.loads without error handling gymnastics.

Few-Shot Examples

Sometimes rules are easier to show than to describe. Few-shot prompting adds one or more example input-output pairs to the conversation so the model can imitate the pattern. This is especially effective for classification, extraction, and reformatting tasks.

messages = [
    {"role": "system", "content": "Classify each email as urgent or normal."},
    {"role": "user", "content": "Server is down, please help now."},
    {"role": "assistant", "content": "urgent"},
    {"role": "user", "content": "Reminder: review next week's report."},
    {"role": "assistant", "content": "normal"},
    {"role": "user", "content": "The invoice from last month is missing."},
]

Content Filtering: The Platform Guardrail

On top of your configuration, the platform applies its own content safety checks. Inputs and outputs pass through content filters that block harmful categories such as hate, violence, sexual content, and self-harm. You cannot switch these filters off; they are a baseline, and applications that need stricter policy add their own guardrail layer.

A Practical Configuration Recipe

Combine the levers in this order for predictable behaviour:

  1. Write a precise system prompt with role, tone, rules, and format.
  2. Set sampling parameters for the task, usually a low temperature for factual work.
  3. Use structured output when your code must parse the answer.
  4. Add few-shot examples for tasks with a strong format or style component.
  5. Validate the output in your own code; never trust the model blindly.

Summary

Model behaviour is controlled at request time through the system prompt, sampling parameters, output formatting, and examples. The system prompt sets the role and rules, sampling parameters tune determinism and creativity, structured output makes answers parseable, and few-shot examples demonstrate desired patterns.
