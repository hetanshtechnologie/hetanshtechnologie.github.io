Our First AI Agent - Review

You have now built, registered, and invoked your first AI agent. Before moving on to identity and tools, it is worth pausing to review what you actually built and why each piece exists. This chapter consolidates the previous eight chapters into a single mental model you can carry through the rest of the course.

The One-Page Architecture

Strip away the SDK calls and your agent reduces to five parts:

PieceRoleWhere It Lives
ModelDoes the reasoning and generates textA deployment in your Foundry project
InstructionsSet role, tone, and behavioral rulesThe agent definition (portal or code)
AgentBinds model + instructions into one objectRegistered in the Foundry project
ThreadHolds the conversation historyCreated per conversation
RunExecutes the agent against a threadTracked on the thread

The agent is static configuration; the thread and run are per-conversation state. Every conversation you started in the labs was a fresh thread, and each answer came from a new run.

The Conversation Flow, Step by Step

Follow one message through the system:

  1. Your application posts a user message into a thread.
  2. A run is created against the thread, using the agent's configuration.
  3. The service feeds the thread to the model, which produces text — or, with tools, a request to call one.
  4. Your code polls the run until it reaches a terminal status.
  5. The completed thread is read back to retrieve the final answer.

This is the same loop whether the agent is a prompt agent in Foundry, a script using the OpenAI SDK, or a full application agent. Only the mechanics differ.

What You Learned to Do

  • Build an agent script with the OpenAI SDK, including credential handling and the poll loop.
  • Create a prompt agent in the Foundry portal and tune its instructions in the playground.
  • Register an agent from code with the Azure AI Projects SDK.
  • Make registration idempotent so rerunning a script never duplicates agents.
  • Invoke the registered agent from a client program and read its answers.

Decisions Worth Remembering

Along the way you made choices that matter in production, not just in a lab:

  • Credentials: keys and connection strings live in .env files, and the goal is to move to Microsoft Entra ID identities as soon as you can.
  • Idempotent registration: create-or-reuse logic makes deployment reproducible and safe.
  • Name lookup: finding an agent by name keeps scripts portable across projects.
  • Instructions as the source of truth: the prompt is the behavior, and iterating on it is the main tuning loop.

If you only remember one diagram from this section, remember the five pieces in the table above. Tools, identity, and advanced services all plug into that model without changing it — tools extend what a run can do, identity controls who may start a run, and services like RAG feed better context into the thread.

What Comes Next

Your agent is currently a closed box that only you can call — and only because your personal login happens to work. The next chapters open that box in two ways:

  • Microsoft Entra ID explains who is allowed to call your agent and how permissions are granted — the identity layer every real deployment needs.
  • Agent tools let your agent do things beyond generating text, starting with web search and then custom functions you define yourself.

Summary

Your first agent is a small but complete system: configuration bound to a model, conversations in threads, execution through runs, and registration made safe to repeat. You built it three ways — SDK script, portal, and code registration — and invoked it like a production client would. That foundation is now ready for identity, tools, and everything that follows.
