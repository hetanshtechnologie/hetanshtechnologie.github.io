Model Router in Microsoft Foundry

Most applications do not need a single model for everything. A trivial question and a complex reasoning task place very different demands on the model, and paying top-tier prices for every request is wasteful. The model router in Microsoft Foundry solves this by sending each request to the most appropriate model among a group, based on rules you define. This chapter explains what model routing is, why it matters, and the routing strategies you can configure.

What Model Routing Is

Model routing is the practice of directing each incoming request to one model from a set, instead of pinning the application to a single deployment. The router is the decision layer: it reads the request, applies your routing logic, and forwards the request to the chosen model with the chosen configuration. The application keeps talking to one stable endpoint while the router handles the distribution behind it.

Routing is different from load balancing. A load balancer spreads identical traffic across identical servers; a model router sends different traffic to different models based on the request's characteristics, so each model is used where it fits best.

Routing also gives you one place to swap models. When a new model version improves quality or a cheaper model arrives, you change the router rules and the whole application benefits — no client-side changes needed.

Why Route at All

Three pressures push most production applications toward routing:

  • Cost: simple requests can be handled by small, inexpensive models. Routing sends the expensive frontier model only where it is actually needed.
  • Latency: small models answer faster. For quick lookups and formatting tasks, routing avoids the extra wait of a heavyweight model.
  • Capability: some tasks genuinely require reasoning, vision, or a large context window. Routing guarantees those tasks land on a model that can do them.

Routing Strategies

Foundry's model router lets you mix several strategies. The right choice depends on what signals your traffic carries:

  • Priority-based routing: try models in order — for example, use a preferred primary model, and if it is unavailable or at capacity, fall back to the next. This is the foundation of high availability.
  • Semantic routing: use an embedding or classification step to understand the request's intent, then pick the model by category — a pricing question goes to the small model, a refund dispute goes to the reasoning model.
  • Rule-based routing: route by request attributes such as prompt length, expected complexity keywords, or the client or user tier — premium users get the frontier model, everyone else gets the fast one.
  • Threshold and capacity fallback: when the primary model is throttled or out of quota, route to a secondary model so the request still completes.

Start with priority-based routing plus a capacity fallback. It is simple, improves reliability immediately, and teaches you your traffic mix before you invest in semantic routing.

Routing Configuration

In Foundry, routing is configured at the deployment or endpoint level. The configuration has three parts:

  1. The route set: the ordered list of models and their deployments.
  2. The routing strategy: how a request is matched to a model — by priority, by semantic category, by rules, or a combination.
  3. Fallback behaviour: what happens when the chosen model fails, throttles, or rejects the request.

For a rules-based setup, a routing decision might be expressed like this:

routes:
  - name: "primary"
    model: "gpt-4o-mini"
    conditions:
      - field: "request"
        match: "simple"
  - name: "fallback"
    model: "gpt-4o"
    conditions:
      - field: "priority"
        match: "premium"

Routing introduces a new failure surface. If the router's rules are wrong, requests can be sent to a model that cannot handle them — a vision request landing on a text-only model, for example. Test each route with the full range of real request shapes before promoting it to production.

Observability of Routing Decisions

Every routing decision should be visible in telemetry: which request went to which model, why that route was chosen, and whether a fallback fired. Without this, a degraded experience is hard to trace. Log the route name, the chosen model, and the trigger — primary, semantic match, or fallback — with each completion, and alert when fallbacks become frequent, since that usually signals a capacity or correctness problem in the primary route.

Summary

The model router sends each request to the best-fitting model among a configured set, balancing cost, latency, and capability. Foundry supports priority-based, semantic, rule-based, and capacity-fallback strategies, all defined in one routing configuration the application sees as a single endpoint.
