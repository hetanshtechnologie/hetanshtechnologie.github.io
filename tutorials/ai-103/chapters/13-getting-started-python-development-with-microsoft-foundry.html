Getting Started Python Development with Microsoft Foundry

Everything you have done in the portal — deploying models, testing prompts, inspecting endpoints — becomes far more powerful when you drive it from Python. This chapter lays the groundwork for all the coding that follows: how Python projects talk to Foundry, how to structure a project, and how to make your first authenticated call to a deployed model.

How Python Talks to Foundry

Your Python application calls a deployed model over HTTPS using its endpoint and key. There are two popular ways to make that call:

  • The Azure AI Inference SDK: A Python library that provides a consistent client for chat, embeddings, and other model types across Foundry deployments.
  • Direct REST requests: Plain HTTP calls using a library such as requests or the standard urllib, with no SDK dependency.

Both approaches work, and both authenticate the same way: the endpoint URL plus an API key in the request header. The SDK just wraps that HTTP call in convenient Python objects.

The names of SDK packages change over time as the platform evolves. When you install, prefer the packages the current Foundry documentation points to — this course shows the general pattern, and the pattern (a client pointed at your endpoint, authenticated with your key) is stable even when a package name changes.

Project Structure

Keep your work organized from the start. A minimal, clean structure for this course looks like this:

ai103-labs/
|-- .env                # secrets live here, never committed
|-- requirements.txt    # package list
|-- src/
|   |-- config.py       # loads endpoint and key from the environment
|   `-- chat.py         # your first model-calling script
`-- README.md

Never hardcode an endpoint key in a Python file. Keys pasted into source code end up in version control, and versions of source code leak. Load them from environment variables or a local .env file that your version control ignores.

Configuration First

Write a small configuration module that reads your endpoint and key once, so every script in your project shares the same connection values. A typical implementation loads values from a .env file:

# src/config.py
import os
from pathlib import Path

def load_env(path=".env"):
    """Load KEY=VALUE lines from a .env file into the environment."""
    p = Path(path)
    if not p.exists():
        return
    for line in p.read_text().splitlines():
        line = line.strip()
        if line and not line.startswith("#") and "=" in line:
            key, _, value = line.partition("=")
            os.environ.setdefault(key.strip(), value.strip())

load_env()

ENDPOINT = os.getenv("AZURE_FOUNDRY_ENDPOINT")
KEY = os.getenv("AZURE_FOUNDRY_KEY")
DEPLOYMENT = os.getenv("AZURE_FOUNDRY_DEPLOYMENT")

And the matching .env file, which you fill with real values from your Foundry deployment page:

# .env  (never commit this file)
AZURE_FOUNDRY_ENDPOINT=https://YOUR_RESOURCE.cognitiveservices.azure.com/
AZURE_FOUNDRY_KEY=YOUR_KEY
AZURE_FOUNDRY_DEPLOYMENT=YOUR_DEPLOYMENT_NAME

Your First Chat Call

The simplest useful script sends one chat message and prints the model's reply. Written with plain requests, it makes every step visible:

# src/chat.py
import json
import requests
from config import ENDPOINT, KEY, DEPLOYMENT

url = (
    f"{ENDPOINT.rstrip('/')}/openai/deployments/{DEPLOYMENT}"
    "/chat/completions?api-version=2024-06-01"
)

payload = {
    "messages": [
        {"role": "system", "content": "You are a concise assistant."},
        {"role": "user", "content": "What is retrieval augmented generation?"},
    ],
    "max_tokens": 200,
}

resp = requests.post(url, headers={"api-key": KEY}, json=payload)
resp.raise_for_status()

data = resp.json()
print(data["choices"][0]["message"]["content"])
print("Tokens used:", data["usage"])

Always call raise_for_status() (or the SDK equivalent) after the request. It turns a silent failure into a clear exception, which is exactly what you want while debugging. Handle HTTP 4xx and 5xx errors explicitly, because a model endpoint is a network call like any other.

Turning the Call into a Reusable Function

Production code does not sprinkle raw requests everywhere. Wrap the call in a function your application can reuse, with sensible defaults and clear parameters:

# src/client.py
import requests
from config import ENDPOINT, KEY, DEPLOYMENT

def chat(messages, temperature=0.7, max_tokens=200):
    url = (
        f"{ENDPOINT.rstrip('/')}/openai/deployments/{DEPLOYMENT}"
        "/chat/completions?api-version=2024-06-01"
    )
    payload = {
        "messages": messages,
        "temperature": temperature,
        "max_tokens": max_tokens,
    }
    resp = requests.post(url, headers={"api-key": KEY}, json=payload, timeout=60)
    resp.raise_for_status()
    data = resp.json()
    return {
        "content": data["choices"][0]["message"]["content"],
        "usage": data.get("usage"),
        "finish_reason": data["choices"][0].get("finish_reason"),
    }

Common First-Call Mistakes

These are the mistakes beginners hit most often, so you can skip them:

  • Wrong deployment name: The model field in the request must be your deployment name, not the model card name.
  • Missing /openai/deployments/ path segment: The URL shape matters; copy it from the deployment page rather than reconstructing it from memory.
  • Stale API version: Use the version string the portal shows in its sample request.
  • Key with a stray newline: When copying keys from the portal into a .env file, trailing whitespace breaks authentication silently. Strip values in your loader.
  • Not reading the error body: The endpoint explains its own failures — always print the full error text.

Timeouts are the invisible killer of model calls. Chat models can take tens of seconds on long requests, so set an explicit timeout of 60 seconds or more rather than relying on a default that may fire too early. Also remember that model responses are non-deterministic — a retry can return a slightly different answer, so design your tests to tolerate variation.
