Monitoring AI Workloads - Foundry Observability and Search Health

A deployed model that nobody watches is a black box until the day it silently degrades. Monitoring turns generative workloads into something you can inspect: how many calls are flowing, how fast they respond, whether they fail, and — with the right tooling — whether the answers are still any good. In this chapter you will learn how Foundry surfaces telemetry for AI workloads, how Application Insights stores and queries it, and how to keep an eye on the search services that power RAG and memory.

What Observability Means for AI

Observability is the ability to answer questions about a running system from data it produces, rather than from guesswork. For AI workloads the questions include:

  • How many requests reached the deployment, and how many failed?
  • How long did each call take, and how many tokens did it consume?
  • What did the model receive and produce for a particular run?
  • Did the workflow branch the way the design intended?
  • Is response quality drifting over time?

The first three are classic application monitoring. The last one is unique to AI — a model can keep succeeding technically while its answers become less useful. Monitoring quality is the subject of the next two chapters; this chapter covers the telemetry plumbing that makes all of it possible.

Foundry's Built-In Monitoring Views

Foundry provides monitoring surfaces directly in the portal for the resources it manages:

  • Deployment metrics: Token usage, call counts, and error rates for each model deployment, broken down over time.
  • Run history for workflows: Per-node status, duration, and inputs/outputs for every workflow run.
  • Agent traces: The sequence of model calls, tool invocations, and memory lookups an agent made while answering.

These views answer operational questions quickly — did last night's batch run, how many tokens did it burn, did the urgent branch fire correctly. What they do not do is keep a long history or answer arbitrary questions; that is where Application Insights comes in.

Think of the portal views as the dashboard on the machine and Application Insights as the flight recorder. Dashboards are for glancing; the flight recorder is for digging into a specific event weeks after it happened.

Application Insights for AI Telemetry

Application Insights is Azure's telemetry service, and it stores your AI workload's events as logs and traces you can query with Kusto Query Language (KQL). Once connected, Foundry writes rich detail into it:

  • Chat completion invocations with their prompts and responses.
  • Agent step executions and tool calls.
  • Evaluation results, when continuous evaluation is enabled.
  • Custom properties you attach, such as user IDs or scenario tags.

With data in Application Insights you can build dashboards, set alerts (for example, "error rate above 5%"), and write one-off queries to investigate incidents.

Monitoring Azure AI Search Health

RAG pipelines and memory stores depend on Azure AI Search, and a healthy search service is a silent partner in every good answer. Watch these aspects:

  • Query latency: Slow queries make agents feel sluggish and can cascade into timeouts.
  • Indexing and query load: High volume may require scaling the replica or partition count.
  • Storage usage: Indexes that grow without bound eventually hit storage limits and stop accepting documents.
  • Error rates: Sudden error spikes usually indicate throttling or a broken indexer.

If an agent starts returning empty or off-topic answers while the model itself looks healthy, check the search service before the model — a broken index produces confident nonsense, which looks exactly like a model problem but is not.

Adopt a quick triage order when AI output goes wrong: check the trace (did the model get the right context?), then the search service (did the index return sensible hits?), then the model quality itself (is the prompt still fit for the data?). Most "the model is dumb now" incidents are actually the first two.

Connecting Telemetry and Alerts

The monitoring loop only works if it ends in action. Close the loop by:

  • Defining alert thresholds on the metrics that matter to you — error rate, latency, token consumption.
  • Sending alerts to a channel your team actually watches.
  • Adding custom dimensions to your traces so you can slice by customer, region, or feature.
  • Reviewing quality metrics over time, not just on demand.

Telemetry contains sensitive data. Prompts, responses, and retrieved documents routinely include personal information, so protect the Application Insights resource with the same access controls you give the model deployment itself. Who can read your traces can read your users' messages.

Summary

Monitoring AI workloads combines operational telemetry — calls, tokens, latency, errors — with AI-specific signals like traces, workflow runs, and search health. Foundry's built-in views handle day-to-day checks, while Application Insights provides the durable, queryable record behind them. Watch your search service as closely as your models, because RAG and memory answers depend on it. The next two chapters introduce the instruments that measure the one thing telemetry cannot: the quality of the answers themselves.
