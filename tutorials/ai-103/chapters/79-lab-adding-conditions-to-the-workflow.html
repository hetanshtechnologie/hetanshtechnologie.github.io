Lab - Adding conditions to the workflow

Your intake pipeline now produces structured data — including an is_urgent flag. In this lab you will make the workflow act on that data by adding a condition node that routes each ticket down one of two paths: urgent tickets get a faster, more direct reply and an alert; normal tickets follow the standard path. This is where the pipeline stops being a straight line and becomes a real decision-making process.

Objectives

  • Add a condition node to the intake workflow.
  • Branch on the structured is_urgent field.
  • Create distinct output paths for urgent and standard tickets.
  • Run the workflow with both urgent and non-urgent inputs to verify the branches.

Prerequisites

  • The intake-pipeline workflow with structured output from the previous lab.
  • IntakeAgent and ResolverAgent versions that produce the is_urgent field.

Step 1: Add the Condition Node

Insert a branching point

  1. Open the intake-pipeline workflow.
  2. Drag a Condition node onto the canvas, between IntakeAgent and ResolverAgent.
  3. Draw an edge from the IntakeAgent node into the Condition node.
  4. Open the Condition node's settings and configure a test against the structured field:
Condition: $\{nodes.intake_agent.output.is_urgent} == true

A condition node has two exits: the true path, taken when the test evaluates to true, and the false path, taken otherwise. Data that arrives at the condition is passed along whatever path is chosen, so both branches can access IntakeAgent's summary.

Step 2: Build the Two Branches

Give each branch its own version of the reply. Urgent tickets need a prompt that produces a more direct, acknowledgment-heavy reply; standard tickets keep the existing ResolverAgent prompt.

Create the urgent path

  1. Drag a second Agent node onto the canvas and name it UrgentResolver.
  2. Select ResolverAgent's published version for it.
  3. Add a note in its prompt that this reply is for an urgent, high-priority ticket:
Original customer message:
$\{inputs.customer_message}

Intake summary:
$\{nodes.intake_agent.output.summary}

The ticket is marked URGENT. Acknowledge the impact, state that
it is being escalated to the on-call team, and keep the reply
shorter than usual.
  1. Draw an edge from the Condition node's true exit to the UrgentResolver node.

Wire the standard path

  1. Draw an edge from the Condition node's false exit to the existing ResolverAgent node.
  2. Leave the ResolverAgent node's prompt unchanged so standard tickets keep the standard reply.

It is easy to connect a node to the wrong condition exit. Check the arrow labels on the canvas: the true branch must go to the urgent handler and the false branch to the standard handler. A single swapped edge silently routes every urgent ticket through the slow path.

Step 3: Update the Output Node

The workflow now has two possible sources for the draft reply, so the output node must pick up whichever one ran.

Expose both outcomes

  1. Open the Output node.
  2. Add an output field draft_reply and bind it to the standard ResolverAgent's output.
  3. Add an output field urgent_reply and bind it to UrgentResolver's output.
  4. Draw edges from both agent nodes into the Output node.
  5. Save the workflow. The run will produce whichever reply field corresponds to the branch that executed.

Step 4: Test Both Branches

Verify routing with two runs

  1. Run the workflow with the urgent message from earlier labs (the down virtual machine). Confirm is_urgent is true and urgent_reply is populated.
  2. Run the workflow again with a non-urgent message:
Our blob storage account shows a 403 error since this morning.
Not urgent, but we do need help by end of day. Account BA-44590.
  1. Confirm is_urgent is false and draft_reply (the standard path) is populated.
  2. Compare the two replies and confirm the urgent one acknowledges escalation while the standard one does not.

Conditions can test more than booleans. You can compare strings, check that a field is missing, or combine several tests with and / or. A useful follow-up: add a second condition that routes tickets without an account_id into a branch that asks the customer for their account number.

Step 5: Review Run History

Open the workflow's run history. Each run should show the condition node in the executed path, along with which agent produced the reply. This audit trail is one of the main reasons to build pipelines as workflows: you can prove which branch handled each ticket and why.

Summary

You added a condition node that branches the intake pipeline on the structured is_urgent field, built separate urgent and standard reply paths, and verified both branches with realistic runs. The workflow now makes decisions, not just calls.
