Introduction to Workflows

So far your agents have done one thing at a time: receive a message, think, and reply. Many real applications need more structure than that. A support ticket must be captured, triaged, enriched with customer data, routed to the right team, and logged to a database — several steps that must happen in a defined order, with decisions along the way. This is orchestration, and in Microsoft Foundry you build it with workflows. In this chapter you will learn what a workflow is, what its building blocks are, and when a workflow is the right tool compared to a single agent.

What Is a Workflow

A workflow is a graph of connected steps that executes a business process. Each step — called a node — does one unit of work: accept input, call an agent, run a model, evaluate a condition, transform data, call an external service, or emit output. Nodes are connected with edges, and data flows along those edges from one node to the next.

The key idea is that a workflow is deterministic structure around generative behavior. The path data takes is defined up front, while the content produced at each step is handled by models and agents. This gives you the reliability of a defined process and the intelligence of AI where it is needed.

Think of a workflow as a flowchart. You decide the boxes and the arrows in advance; the boxes filled with AI decide what words to generate when they run. The control flow is yours; the creativity is delegated to the models.

The Building Blocks: Nodes

Foundry workflows provide a small set of node types that cover most orchestration needs:

Node typeWhat it does
InputDefines the entry point — the data a caller provides when the workflow starts
Agent / LLMRuns an agent or a plain model call to produce text, decisions, or structured data
ConditionBranches the flow based on a test — for example, "is the priority high?"
Code / TransformRuns custom logic to shape, filter, or combine data between steps
HTTPCalls an external API, such as a CRM or a ticketing system
OutputDefines what the workflow returns to its caller

You connect these nodes visually in the Foundry portal. Each connection carries the previous node's output forward, and the next node can reference those values in its own configuration.

Why Workflows Beat Single Agents for Many Tasks

A single agent can be instructed to "do the whole process," but that has real drawbacks:

  • Unpredictability: The agent might skip a step or do steps out of order.
  • No observability: You cannot see which step failed or how long each step took.
  • No reuse: A support agent, a triage agent, and a logging agent all live inside one big prompt.
  • Mixed concerns: Deterministic work like "write a row to the database" is better done with code than with a language model.

A workflow fixes all of these. The order of steps is enforced, each node logs its own run, agents are reused across workflows, and deterministic work is done by code or HTTP nodes while models handle only the language-heavy parts.

When to Use a Workflow

Workflows shine when your process has clear structure:

  • A defined sequence: capture, validate, process, respond.
  • Branching: different actions depending on the input.
  • Multiple systems: the process touches databases, APIs, and email in a fixed order.
  • A need for auditability: you must prove which step did what.

They are a poor fit when the task is genuinely open-ended — a free-form chat assistant that should "figure it out" is better as a plain agent. A rule of thumb: if you can draw the process as a flowchart, it belongs in a workflow; if you cannot, keep it in an agent.

Start by drawing the flowchart on paper or a whiteboard before you open the portal. Decide where the AI steps are, where the deterministic steps are, and where the decision points are. The diagram you draw becomes your workflow almost node for node.

Workflows and Agents Together

Workflows and agents are complementary, not competing. An agent is a smart component; a workflow is the process that uses it. A typical pattern in this course's labs will be: an IntakeAgent reads a customer request and extracts facts from it, the workflow validates the extracted facts, routes the ticket based on a condition, and passes everything to a second agent that drafts the reply. Each agent stays small and focused while the workflow keeps the process honest.

Summary

A workflow is a graph of nodes — input, agent, condition, code, HTTP, and output — connected into a deterministic process around generative steps. Workflows give you predictable ordering, per-step observability, and reusable components where single agents give you flexibility but little structure.
