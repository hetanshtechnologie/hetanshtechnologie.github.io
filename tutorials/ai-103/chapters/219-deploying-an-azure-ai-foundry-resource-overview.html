Deploying an Azure AI Foundry resource - Overview

Before you can use Foundry, you need the Azure resources it runs on. This overview chapter explains the pieces you are about to create — the hub, the project, and the supporting services — plus the decisions around regions and capacity that determine whether your setup costs anything. The lab in the next chapter turns this into clicks.

The Building Blocks: Hubs and Projects

Foundry organizes everything into two levels of container. Understanding them up front makes every later step clearer:

  • A hub (the resource you create in Azure) is the top-level container. It holds the shared configuration — network settings, encryption, and the connected Azure resources such as the model service. It is the billable unit: creating the hub also provisions the connected services behind the scenes.
  • Projects live inside a hub and are the working spaces where you actually build. Each project tracks its own deployments, playground chats, evaluations, and connections to data. A single hub can contain many projects, letting one organization share infrastructure while keeping work separated.

For this course you need exactly one hub and one project. The hub ties everything together; the project is where you will deploy models and run the playground in the labs that follow.

The Supporting Resources

Creating a Foundry hub does not create a single resource — it creates the hub plus the services it needs to operate. When you run the lab, watch the deployment list and you will typically see several resources appear together:

  • The hub itself (an Azure AI resource).
  • An AI model service (an Azure OpenAI-style resource) that hosts your model deployments.
  • A storage account for project data, traces, and intermediate files.
  • A key vault for storing connection secrets such as API keys.
  • Possibly a container registry and AI search resource, depending on which options you enable.

This bundle is why Foundry recommends creating the hub with a single click rather than assembling services manually — the wizard wires them together with the correct permissions automatically.

Choosing a Region

The region you choose for the hub matters more than you might expect:

  • Model availability: not every model is available in every region. If a model refuses to deploy later, a different region is the usual fix.
  • Latency and compliance: resources close to your users respond faster, and some data must stay in a specific geography.
  • Consistency: your hub, project, and model deployments work best in the same region. Mixing regions is possible but adds friction.

For the course, pick a region that is close to you and that lists the models you will deploy (chat models such as GPT families are broadly available). If you are unsure, choose your nearest major region and adjust only if a deployment fails.

Capacity and Quota

Model deployments consume capacity — measured in tokens per minute for standard deployments. Your subscription has a quota: a ceiling on how much capacity you can use in a region. Two practical consequences follow:

  • Small test deployments need very little capacity, so quota is rarely a problem for this course.
  • If a deployment reports a quota error, the fix is usually to lower the requested tokens-per-minute value or to request a quota increase for that region — not to change your code.

Pricing Tiers

The Foundry hub itself has a basic tier designed for exactly this kind of learning and development work — it is free for standard-scope usage under the free-account allowances. The model deployments you add later are a separate charge consideration:

  • Free tiers exist for some models in some regions; they are rate-limited but perfect for labs.
  • Standard (pay-as-you-go) deployment bills per token used. A few dozen test requests cost fractions of a cent.
  • Provisioned throughput reserves capacity for a fixed monthly price — only for production-scale needs, never for this course.

The supporting resources — storage, key vault, registry — also incur small charges in some configurations. Under the free account's allowances and the basic hub tier, a typical course setup stays at zero cost. The discipline is to delete the hub (and its whole resource group) when you are done, which deletes everything with it.

What You Will Create in the Lab

Here is the end state of the next lab in plain terms:

  1. A resource group that holds everything for this course.
  2. An Azure AI hub in that group, with its supporting services created automatically.
  3. A project inside the hub, ready for model deployments and playground sessions.

Summary

A Foundry deployment is a hub plus supporting services, organized into projects. Choose a region for model availability and latency, keep deployments small to stay inside quota, and rely on free and basic tiers to keep the course at zero cost.
