Lab - Building the CloudXeus Orders API with Azure Functions

With the Core Tools installed and verified, you are ready to build the real CloudXeus orders API. In this lab you scaffold a Python function app, add an HTTP-triggered function, and implement three operations that a support agent will later call: fetch one order by id, list orders for a customer email, and cancel an order. The functions run in memory for now; publishing to Azure comes in the next lab.

The Three Operations

The CloudXeus support agent needs these capabilities from the API:

OperationHTTP method and pathWhat it does
Get an orderGET /api/orders/{order_id}Returns a single order by its id, or a 404 if missing
List ordersGET /api/orders?email=...Returns every order belonging to one customer
Cancel an orderPOST /api/orders/{order_id}/cancelChanges an order's status to cancelled

Keeping the paths flat and the operationIds obvious will make the OpenAPI specification in a later chapter almost write itself.

Scaffold the Project

Create a folder for the API and initialize a Python function app with the v2 programming model:

mkdir cloudxeus-orders-api
cd cloudxeus-orders-api
func init --worker-runtime python --model v2

This produces a project with a function_app.py file, a local.settings.json for local configuration, and a requirements.txt.

If you worked through the earlier Core Tools lab, the hello function may still be in function_app.py. Remove it and its imports so only the orders code below remains.

Write the Orders Function

Replace the contents of function_app.py with the code below. The data lives in an in-memory dictionary so the API works without a database; in production you would back these operations with a database or another durable store.

import json

import azure.functions as func

app = func.FunctionApp()

ORDERS = {
    "ORD-1001": {
        "id": "ORD-1001",
        "customer_email": "ada@example.com",
        "status": "shipped",
        "total": 49.98,
    },
    "ORD-1002": {
        "id": "ORD-1002",
        "customer_email": "grace@example.com",
        "status": "placed",
        "total": 15.00,
    },
    "ORD-1003": {
        "id": "ORD-1003",
        "customer_email": "ada@example.com",
        "status": "placed",
        "total": 89.50,
    },
}


@app.route(route="orders/{order_id}", methods=["GET"],
           auth_level=func.AuthLevel.ANONYMOUS)
def get_order(req: func.HttpRequest) -> func.HttpResponse:
    order_id = req.route_params.get("order_id")
    order = ORDERS.get(order_id)
    if order is None:
        body = json.dumps({"error": "Order not found"})
        return func.HttpResponse(body, status_code=404,
                                 mimetype="application/json")
    return func.HttpResponse(json.dumps(order), mimetype="application/json")


@app.route(route="orders", methods=["GET"],
           auth_level=func.AuthLevel.ANONYMOUS)
def list_orders(req: func.HttpRequest) -> func.HttpResponse:
    email = req.params.get("email")
    matches = [o for o in ORDERS.values()
               if o["customer_email"] == email]
    return func.HttpResponse(json.dumps(matches), mimetype="application/json")


@app.route(route="orders/{order_id}/cancel", methods=["POST"],
           auth_level=func.AuthLevel.ANONYMOUS)
def cancel_order(req: func.HttpRequest) -> func.HttpResponse:
    order_id = req.route_params.get("order_id")
    order = ORDERS.get(order_id)
    if order is None:
        body = json.dumps({"error": "Order not found"})
        return func.HttpResponse(body, status_code=404,
                                 mimetype="application/json")
    if order["status"] == "cancelled":
        body = json.dumps({"error": "Order already cancelled"})
        return func.HttpResponse(body, status_code=409,
                                 mimetype="application/json")
    order["status"] = "cancelled"
    return func.HttpResponse(json.dumps(order), mimetype="application/json")

Each endpoint is declared with the @app.route decorator. The route pattern, the HTTP methods, and the auth level are all set in one place, which is the v2 programming model's main benefit over the older per-function function.json files.

Run and Test Locally

Exercise — Start the Host and Exercise Every Endpoint

  1. Start the local host from the project folder:
func start
  1. In a second terminal, fetch one order:
curl "http://localhost:7071/api/orders/ORD-1001"
  1. List orders for a customer:
curl "http://localhost:7071/api/orders?email=ada@example.com"
  1. Cancel an order and confirm the status flips to cancelled:
curl -X POST "http://localhost:7071/api/orders/ORD-1002/cancel"
  1. Check the failure paths too: a missing order id should return 404, and cancelling an already-cancelled order should return 409.

Because the data is in memory, restarting the host resets every change, including cancelled orders. That is fine for a lab; the moment the API is published, each instance gets its own fresh dictionary. A real deployment would store orders in a database such as Azure Cosmos DB or SQL.

Summary

You have a working, locally tested CloudXeus orders API with three HTTP endpoints, all built with the Python v2 programming model. The next chapter walks through what each piece of the code does before you publish the API to Azure.
