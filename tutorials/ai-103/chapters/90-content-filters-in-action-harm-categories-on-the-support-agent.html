Content Filters in Action - Harm Categories on the Support Agent

In this chapter you will see what content filtering actually looks like on the support agent you have been building. Content filters classify text along several harm categories, assign each piece a severity level, and let you decide where to draw the block line. We will examine the harm categories, walk through what a filtered response looks like in code, and discuss how to tune the thresholds for a real application rather than leaving them at their defaults.

The Harm Categories

Azure's content filters screen text against a set of harm categories. Each category targets a different family of harmful content:

CategoryWhat it flags
Hate and fairnessAttacks or discrimination against groups based on protected attributes
SexualSexual content, explicit or suggestive language, and sexual exploitation
ViolenceDescriptions or promotion of violence, injury, and weapons
Self-harmContent that encourages, describes, or plans self-injury

Each category is scored by the safety model and reported on a severity scale, typically from 0 (safe) to 6 (extreme), with a configurable threshold for each category. You decide what happens above the threshold: block, flag for review, or log without interrupting the user.

Severity is not the same as certainty. The filter reports how severe the detected content is, not merely whether it is present. This lets you allow mild or contextual content while blocking genuinely harmful output.

What a Filtered Request Looks Like

When a content filter blocks a request, the API response tells you so. For a model deployment with filters enabled, a blocked input produces a response whose finish reason or error content indicates the filter fired:

{
  "error": {
    "code": "content_filter",
    "message": "The response was filtered due to the prompt triggering"
             "Azure OpenAI's content management policy."
  }
}

For an application that calls the safety service directly, you get a structured verdict for each category instead:

{
  "categoriesAnalysis": [
    {
      "category": "Hate",
      "severity": 2,
      "severityLevel": "Low"
    },
    {
      "category": "SelfHarm",
      "severity": 0,
      "severityLevel": "Safe"
    }
  ],
  "action": "Accept",
  "blocklistsMatch": []
}

Handle the content-filter error explicitly in your code. A filter block is a normal, expected outcome for a safety-aware application — not a crash. Map it to a friendly user message and log the category so you can review false positives.

Seeing the Filters on the Support Agent

The support agent sits behind filters configured at the deployment level, so every request and every answer passes through them without the agent code being aware. To exercise them in the playground or your test harness, try prompts such as an insulting request, a request that asks the agent to produce self-harm content, or an aggressive demand that tries to coerce the agent. Each will return the content-filter block instead of a normal answer.

Test the filter from Python

Send a deliberately harmful test message to your deployed model and inspect how the client reports the block:

from openai import AzureOpenAI
import os

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

try:
    response = client.chat.completions.create(
        model="YOUR_DEPLOYMENT_NAME",
        messages=[
            {"role": "user", "content": "YOUR_TEST_HARMFUL_MESSAGE"},
        ],
    )
    print(response.choices[0].message.content)
except Exception as ex:
    print("Request blocked by content filters:")
    print(ex)

Replace YOUR_TEST_HARMFUL_MESSAGE with a clear test phrase — for example a request to write threatening text. Do not use real user data for this kind of test.

Tuning the Thresholds

The default thresholds are a starting point, not a final configuration. Tuning is an iterative process:

  1. Run a sample of real traffic through the filter and collect every block.
  2. Review the blocked examples by hand and separate true positives from false positives.
  3. Adjust the severity threshold per category until legitimate traffic passes while harmful traffic is blocked.
  4. Repeat after product changes — new features and new user communities change what your traffic looks like.

Do not disable a category because you saw a false positive. Lower that category's threshold or refine your blocklist instead. A disabled filter is a permanent hole that a single harmful request can exploit.

Beyond Text: Blocklists and Custom Rules

Content filters handle broad harm categories; blocklists handle your specific vocabulary. If your product has a company-policy term list — competitor names in promotions, profanity in a family product, internal names in a public bot — you can define blocklists that match exact words or phrases and block on them independently of the severity model. Combining categories, blocklists, and custom thresholds gives you a layered policy that matches your business instead of a generic default.

Summary

Content filters classify traffic along harm categories — hate, sexual, violence, and self-harm — and score each on a severity scale with configurable thresholds. Blocked requests return a content-filter error your code should handle gracefully, and the safety service can return structured per-category verdicts for programmatic decisions. On the support agent you can test the filters directly, tune thresholds on real traffic, and extend the policy with custom blocklists.
