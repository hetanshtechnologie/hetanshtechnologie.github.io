Azure Content Understanding - Custom Analyzer - Invoice storage

Before you build a custom analyzer that understands invoices, you need a library of invoices for it to learn from and to be tested against. This chapter sets up that library: a storage container holding a varied collection of invoice samples, organized so the analyzer build and later evaluation runs are repeatable. The quality of your custom analyzer will track the quality of this dataset, so the choices here matter more than they look.

Why Sample Storage Matters

A custom analyzer is configured with field definitions, but the reality of invoices varies enormously — one vendor prints the total top-right, another embeds it in a table, and a third ships a scanned two-pager. You cannot tune for that variety without representative samples. The stored set of invoices serves three purposes:

  • Design reference: you inspect samples to decide which fields to define and how to describe them.
  • Testing: you run the analyzer over samples you have not used during configuration to measure accuracy.
  • Regression detection: you re-run the same set after every configuration change to confirm nothing broke.

What Invoices to Collect

Curate for variety, not just volume. A good invoice library includes:

  • Multiple vendors with different layouts and logos.
  • Different formats: digital PDFs and scanned pages.
  • One-page and multi-page invoices, including multi-page tables.
  • Different currencies and tax styles so amounts and tax fields are exercised.
  • Edge cases: handwritten notes, rotated pages, damaged scans, and missing fields.

If you do not have real invoices, generate a small set of synthetic ones with a script — varying vendor names, totals, and layouts. Synthetic data is fine for learning the workflow, but for a production analyzer you must validate against genuine documents and comply with any data-use rules your organization applies.

Creating the Storage Account and Container

The invoice samples live in their own container so the analyzer pipeline can be pointed at exactly this data. Create it with the Azure CLI:

az storage account create \
    --name cloudxeusinvoicestore \
    --resource-group cloudxeus-docs-rg \
    --location eastus \
    --sku Standard_LRS \
    --kind StorageV2

az storage container create \
    --name invoice-samples \
    --account-name cloudxeusinvoicestore \
    --auth-mode login

Exercise 1: Create the invoice sample container

  1. Create the storage account cloudxeusinvoicestore in the resource group cloudxeus-docs-rg using the commands above.
  2. Create the container invoice-samples inside it.
  3. Verify the container exists: az storage container show --name invoice-samples --account-name cloudxeusinvoicestore --auth-mode login.
  4. Record the storage account name and container name for the exercises in the next chapters.

Uploading the Invoice Samples

Collect your invoices in a local folder and upload the whole folder in one pass:

az storage blob upload-batch \
    --account-name cloudxeusinvoicestore \
    --auth-mode login \
    --destination invoice-samples \
    --source ./invoices

Then confirm every file arrived:

az storage blob list \
    --account-name cloudxeusinvoicestore \
    --auth-mode login \
    --container-name invoice-samples \
    --output table

Invoices contain sensitive information such as customer names, addresses, and payment details. Only upload data you are authorized to process, and remember that Content Understanding analyses route through the cloud — keep the samples within the scope of your data-protection agreements.

Organizing for Reuse

Structure the container so you can point different test runs at different slices. A practical layout is:

invoice-samples/
  digital/
    vendor-a/
    vendor-b/
  scanned/
  multipage/
  edge-cases/

This arrangement lets you evaluate the analyzer separately on easy and hard documents, which is exactly what you will do when you review extraction quality. If you plan to compare configurations, keep the file names stable between runs so results line up file by file.

Summary

You created a dedicated storage container for invoice samples, curated a varied set of documents, uploaded them, and organized the collection by format and difficulty. This library is now the fixed reference for building and testing the custom analyzer. In the next chapter you will define the analyzer and connect it to these stored invoices.
