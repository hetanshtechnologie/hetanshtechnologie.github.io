Quick note on monitoring the model usage

This is a short, practical chapter. Now that your applications are calling real deployments, you should know where to look when questions arise about cost, throughput, or failures. Model usage is not a mystery that requires guesswork — Microsoft Foundry and Azure collect the relevant metrics for you, and knowing where to find them saves you from painful surprises in your bill.

Why Monitor at All

Every call to a deployed model consumes tokens, and tokens are what you pay for. Usage therefore has two sides: the cost of running your application and the health of the deployment. Monitoring gives you three concrete benefits:

  • Cost awareness: You can see how many tokens a feature consumes and spot unexpected spikes before the invoice arrives.
  • Capacity management: You can watch rate limits and latency and decide when to raise the deployment's token rate limit or add a second deployment.
  • Failure detection: You can catch throttling, quota exhaustion, and error spikes while they are still small.

What the Metrics Tell You

For each deployment, Foundry tracks a handful of high-value metrics. The ones you will rely on most are:

MetricWhat it measuresWhy it matters
Tokens per minuteHow many prompt and completion tokens the deployment processed per minuteDirectly drives cost; used for budgeting
RequestsNumber of calls receivedShows traffic volume and demand patterns
LatencyTime to complete a requestReveals slowness and degradation
Throttling eventsRequests rejected because limits were exceededSignals you need a higher quota or better batching
Error rateFailed calls as a share of total callsCatches misconfiguration and outages

Token usage reported by the service and token usage reported inside the API response should agree closely. If you want per-request accounting — for example, to bill an internal team per feature — read response.usage from the API response, as you did in the previous lab, and log it yourself. The platform metrics give you the aggregate view; your own logs give you the per-request detail.

Where to Look

There are three places to check, depending on what you need:

  • The Foundry deployments page: Each deployment shows a small built-in metrics panel with recent usage and latency. This is the fastest place to get a rough picture.
  • Azure Monitor: The same metrics are available in the Azure portal under the resource, where you can build charts, set alerts, and combine them with other telemetry.
  • Cost Management: For a billing-oriented view, the Cost Analysis blade shows spending grouped by service, region, or resource. This is where an unusually large bill becomes visible first.

Set a simple alert on the token metric before you forget. An alert that fires when a deployment's tokens per minute stays unusually high for an hour is cheap to configure and can flag a runaway loop in your application long before the bill does.

A Minimal Monitoring Habit

You do not need a full observability platform to start. A useful baseline routine is:

  1. Check each deployment's metrics once a week.
  2. Note the total tokens consumed and the peak latency.
  3. Log the per-request usage and id from the API responses so you can trace any future issue back to a specific call.

That is enough to notice problems early, and it scales naturally into the Application Insights and tracing work covered elsewhere in this course.

Summary

Monitoring model usage is mostly a matter of knowing where the numbers live. Track tokens, requests, latency, throttling, and errors; look at the Foundry deployments page for a quick view, Azure Monitor for charts and alerts, and Cost Management for billing. Pair that with per-request usage logged from the API response, and you will always have an answer when someone asks what your AI feature is costing.
