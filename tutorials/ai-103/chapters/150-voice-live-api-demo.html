Voice Live API - Demo

This chapter walks through a Voice Live API session from connection to conversation. There is no exercise box here — instead you will follow a narrated demo, tracing exactly which messages cross the connection at each moment of a short voice call. By the end you should be able to picture the session flow well enough to design your own.

The Demo Scenario

Our demo is a booking assistant. The user speaks: "Do you have a table for two this evening?" The session must hear the sentence, understand the request, form an answer, and speak it back — all inside a single live connection, with no visible gap between the user stopping and the assistant starting.

Step 1 — Opening the Session

The demo starts with a connection request. The client sends a session configuration that states the parameters of the conversation:

{
  "session_id": "booking-demo-01",
  "audio_in": "wav-pcm-16khz-mono",
  "audio_out": "wav-pcm-16khz-mono",
  "recognition": { "language": "en-US" },
  "synthesis": { "voice": "en-US-AriaNeural" },
  "model": { "model_name": "the-deployed-conversation-model" }
}

The service accepts, and from this point the channel is open. The configuration object is worth studying: it declares the audio formats, the recognition language, the voice that will speak back, and the model that will think — all decided before the first word.

Step 2 — The User Speaks

The user begins to talk. The client sends the audio in small chunks as they are captured. The service replies with recognition events that trail the audio by only a fraction of a second:

{ "event": "recognition_started", "session_id": "booking-demo-01" }
{ "event": "transcript_partial", "text": "Do you have a" }
{ "event": "transcript_partial", "text": "Do you have a table for two" }
{ "event": "transcript_partial", "text": "Do you have a table for two this evening" }
{ "event": "transcript_final", "text": "Do you have a table for two this evening?" }

Notice the three partial transcripts. Each replaces the previous one as more audio is heard, and the final event settles the sentence. A UI could show these partials live, exactly like the caption behavior you built in the realtime recognition lab.

Step 3 — The Model Responds

Once the final transcript is committed, the conversation model inside the session produces a response. The service emits the assistant's reply as text, along with the signals that orchestrate the audio:

{ "event": "assistant_message", "role": "assistant",
  "content": "Yes, we have a table for two available at 7 this evening." }
{ "event": "synthesis_started" }

This is the seam between understanding and speaking. The transcript became an assistant message, and the service is now committed to turning that message into audio.

Step 4 — The Assistant Speaks

Synthesis begins, and audio chunks stream back to the client:

{ "event": "audio_chunk", "data": "<base64 audio bytes, part 1>" }
{ "event": "audio_chunk", "data": "<base64 audio bytes, part 2>" }
{ "event": "audio_chunk", "data": "<base64 audio bytes, part 3>" }
{ "event": "synthesis_done", "session_id": "booking-demo-01" }

The client plays each chunk as it arrives. Playback starts while the assistant is still "finishing its sentence," which is what makes the exchange feel natural instead of canned.

Step 5 — Handling an Interruption

Partway through the reply, the user interrupts: "Actually, make it eight." The service detects speech while it is still synthesizing and reacts:

{ "event": "synthesis_interrupted" }
{ "event": "recognition_started", "session_id": "booking-demo-01" }
{ "event": "transcript_final", "text": "Actually, make it eight." }

Two things happen in sequence: the audio synthesis is cut off, and the session pivots back to listening. The conversation continues from the new input — the user never had to wait for the assistant to finish before being heard. This interruption dance is the defining behavior of a live voice session and the reason it feels like talking to a person.

Step 6 — Closing the Session

When the conversation is over, the client sends a closing signal and the service confirms:

{ "event": "session_ended", "session_id": "booking-demo-01" }

The channel closes, and billing for the session stops. In a production app this is where you would save the transcript, attach the session to a CRM record, and free any resources the session held.

Key Takeaways from the Demo

  • Everything happens over one connection: audio in, recognition events, model messages, and audio out.
  • Partials, assistant messages, and synthesis signals are all separate events you can react to independently.
  • Interruption is not an error — it is a designed transition from synthesis back to recognition.
  • Configuration upfront (voices, languages, formats) means the live phase is pure streaming.

When you prototype your own live voice session, log every event with a timestamp from the start. The event ordering you observe is the blueprint for your application logic, and it will save you from guessing which signal means what.

Summary

The Voice Live API demo showed the full lifecycle of a realtime voice conversation: a configured session opens, user audio streams in as recognition events, the model replies, synthesized audio streams out, and interruptions pivot the session back to listening.
