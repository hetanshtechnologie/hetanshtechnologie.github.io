Locking Down the CloudXeus API with a Function Key

Right now the orders API is anonymous: anyone with the URL can read and cancel orders. This chapter closes that gap. You will require a function key on every endpoint, fetch the key, confirm the API rejects anonymous requests, and point the Foundry agent connection at the key so only the agent can call the service.

Why a Function Key

Azure Functions gives every function app a set of keys. When a route is configured with auth_level=FUNCTION, the runtime demands a valid key on every request and rejects calls without one. This is a shared-secret model: fast to set up, easy to understand, and entirely appropriate for a course project or an internal service behind an agent.

Step 1 — Require the Key in Code

Change the auth level on all three routes in function_app.py. For example, the first route becomes:

@app.route(route="orders/{order_id}", methods=["GET"],
           auth_level=func.AuthLevel.FUNCTION)
def get_order(req: func.HttpRequest) -> func.HttpResponse:

Apply the same FUNCTION level to list_orders and cancel_order.

You can also raise the bar for the whole app by configuring the function_authentication settings at the app level. Per-route FUNCTION auth is enough here and keeps the change local to your code.

Step 2 — Republish the App

Deploy the updated code to Azure so the runtime enforces the new auth level:

func azure functionapp publish func-cloudxeus-orders-001

Step 3 — Fetch a Function Key

List the keys for the function app and copy the default host key:

az functionapp keys list --name func-cloudxeus-orders-001 `
  --resource-group rg-cloudxeus-orders

Note the value of the default key; you will use it in the next step.

The key printed by the CLI is a live secret. Do not paste it into code, chat messages, or the OpenAPI document. It belongs in the agent's connection settings and in your secret storage.

Step 4 — Confirm Anonymous Calls Fail

Exercise — Prove the Lock Works Before Opening the Door

  1. Call the API without a key. You should receive 401 Unauthorized:
curl "https://func-cloudxeus-orders-001.azurewebsites.net/api/orders/ORD-1001"
  1. Call again with the key in the x-functions-key header. You should get the order JSON:
curl "https://func-cloudxeus-orders-001.azurewebsites.net/api/orders/ORD-1001" `
  -H "x-functions-key: YOUR_FUNCTION_KEY"

Step 5 — Point the Agent Connection at the Key

Back in the Foundry portal, edit the agent's OpenAPI tool connection and select the API key (header) authentication method:

  • Header name: x-functions-key
  • Header value: your function key

Save the connection. Every request the agent makes to the orders API now carries the key automatically, and the model never sees it.

Test the End-to-End Flow

Return to the chat playground and repeat the earlier tests:

  • Ask for the status of ORD-1001; the agent calls the API with the key and answers correctly.
  • Ask to cancel an order; the mutation works only because the connection is authenticated.
  • Confirm that attempting to reach the API directly, without the key, still returns 401.

You now have a closed loop: the API refuses anonymous callers, the agent presents a valid key, and the credential stays hidden inside the platform connection. This is the minimum viable security posture for a real tool-backed agent.

Summary

The orders API is locked down with a function key: routes require authentication, anonymous calls fail with 401, and the Foundry agent connection supplies the key on every request.
