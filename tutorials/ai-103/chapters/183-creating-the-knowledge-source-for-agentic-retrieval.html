Creating the Knowledge Source for Agentic Retrieval

Before an agent can answer questions from company documents, those documents need to live somewhere the retrieval pipeline can reach. That somewhere is the knowledge source: the raw, unmodified files — policy PDFs, product manuals, invoice samples — that will later be split into chunks, embedded into vectors, and indexed into a searchable knowledge base. This chapter prepares that source for the CloudXeus project. By the end you will have a storage account with an organized container of documents, ready for the knowledge base you build in the next chapter.

What a Knowledge Source Is

Think of a knowledge source as the shelf of ingredients and a knowledge base as the prepared meal. The source holds original files in their native form. The knowledge base is the structure built from them: text fragments, their embedding vectors, and the index that makes retrieval fast. The two layers stay separate because documents change. When a new version of a manual arrives, you replace the file in the source and re-run indexing, and the agent starts retrieving the new content without any manual rework.

Keeping the source untouched also protects its role as the ground truth. Because the knowledge base is derived from these files, you can always trace a retrieved answer back to the original document — provided the source preserves the original, unmodified bytes.

Choosing the Storage Layer

Azure Blob Storage is the natural home for a knowledge source. It stores files cheaply, scales to large volumes of documents, and integrates directly with the indexing services that build knowledge bases. Blobs are organized inside containers, and containers can hold folders that mirror the way your documents are organized on disk.

Storage optionGood forNotes
Azure Blob StorageDocuments and files feeding an indexThe standard choice for knowledge sources
Azure FilesShared SMB-style drivesLess common for retrieval pipelines
Azure Data Lake StorageVery large analytical datasetsUseful when the source is huge or analytics-driven
SharePoint / OneDriveOffice content already in Microsoft 365Convenient, but adds connector and permission complexity

Creating the Storage Account and Container

You can create the storage account in the Azure portal or with the Azure CLI. The CLI keeps the setup repeatable, which matters when you need to recreate environments for testing. From a terminal, run the following (line-continuation backslashes work in bash; use backticks in PowerShell):

az group create --name cloudxeus-docs-rg --location eastus

az storage account create \
    --name cloudxeusdocsstore \
    --resource-group cloudxeus-docs-rg \
    --location eastus \
    --sku Standard_LRS \
    --kind StorageV2

az storage container create \
    --name cloudxeus-docs \
    --account-name cloudxeusdocsstore \
    --auth-mode login

The portal route is equally simple: create a storage account of type StorageV2, then add a container to it. Either way, make a note of the storage account name and the container name — you will supply both when you connect the knowledge base.

Uploading and Organizing Documents

Most indexing pipelines accept the common office formats. The exact set your knowledge base supports depends on its parser, but this table is a good approximation:

FormatNotes
PDFDigital PDFs extract directly; scanned PDFs require OCR
DOCXWord documents convert to text and structure
TXT / MDSimple and reliable to index
HTMLWeb pages flattened to text
CSV / TSVDelimited tabular data
PPTX / XLSXSlide and spreadsheet content

Keep related documents together in folders. Under cloudxeus-docs you might create policies/, product-manuals/, and invoices/. Folder names often become part of the document metadata the agent can use, and separate folders make it easy to refresh one subject area without re-indexing everything.

Upload a whole folder from your machine with a single command:

az storage blob upload-batch \
    --account-name cloudxeusdocsstore \
    --auth-mode login \
    --destination cloudxeus-docs \
    --source ./local-documents

Keep a local copy of every file you upload. When you need to update the source, it is far easier to refresh from a canonical folder than to reconstruct the contents from scratch.

Preparing Documents for Retrieval Quality

The quality of the knowledge base depends on the quality of its source. A few habits make retrieval dramatically better:

  • Use the current version. The index is rebuilt from whatever is actually in the container.
  • Prefer digital text. Digitally born PDFs and DOCX files extract cleanly; scanned pages introduce OCR errors into numbers and names.
  • Keep files focused. A single coherent document chunks better than a grab-bag of unrelated content.
  • Mind file sizes. Very large files may be split into many chunks; check the limits of your indexing service.
  • Remove superseded versions so retrieval does not surface stale information.

Permissions and Access

The knowledge base you create next must be allowed to read this container. If you followed the previous chapter, the required role assignments are already in place — typically the indexing service is granted a role such as Storage Blob Data Reader through a managed identity, or it connects using a connection string stored in its configuration. Verify the connection before building the index: from the storage account's Access Control page, confirm that the identity used by the indexing service appears with read permission on the container.

Summary

You created a Blob Storage account and a container to act as the knowledge source, uploaded and organized the CloudXeus documents, and confirmed that the permissions from the previous chapter let the indexing service read them. The source is now a clean, versioned shelf of original files. In the next chapter you will build the knowledge base on top of it and run the indexing job that turns these documents into retrievable vectors.
