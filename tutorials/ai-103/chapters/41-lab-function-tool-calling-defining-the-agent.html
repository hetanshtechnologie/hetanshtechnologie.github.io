Lab - Function Tool Calling - Defining the agent

Web Search was a managed capability: the platform executed it for you. Function tool calling is the other side of the tool story — you define a function, describe it to the model, and write the code that actually runs it. This lab covers the first half of that contract: defining the functions and building an agent that knows they exist. The next lab covers the application side that executes the calls.

Objectives

  • Write JSON schema definitions for two custom functions.
  • Attach those functions to an agent so the model can request them.
  • Verify the agent's definition contains the functions and triggers a tool call on the right question.

The Functions You Will Build

Your travel agent needs live data it cannot invent. Define two functions that a real backend could implement:

  • get_weather — returns a short forecast for a city.
  • get_hotel_rate — returns a nightly rate estimate for a city and a number of nights.

The model will never run these functions. It will emit a call with arguments, and your application — the topic of the next lab — will run them. Your job here is to make sure the model knows exactly how to ask.

Step 1: Write the function schemas

Each function needs a name, a description, and a JSON schema for its parameters. The description is what the model reads to decide when to call it, so be explicit about when each function applies.

Define the functions

weather_schema = {
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": (
            "Returns the current weather forecast for a city. Use this "
            "whenever the customer asks about weather, temperature, "
            "rain, or conditions at a destination."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "The city name, for example Paris.",
                }
            },
            "required": ["city"],
        },
    },
}

hotel_schema = {
    "type": "function",
    "function": {
        "name": "get_hotel_rate",
        "description": (
            "Returns an estimated nightly hotel rate for a city. Use "
            "this when the customer asks about hotel prices or "
            "accommodation costs."
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "The city name."},
                "nights": {
                    "type": "integer",
                    "description": "Number of nights to stay.",
                },
            },
            "required": ["city", "nights"],
        },
    },
}

Keep parameter names short and meaningful, and mark required explicitly. The model fills in what the schema declares, so the schema is your contract — both for the model's calls and for the application code that will execute them.

Step 2: Attach the functions to the agent

Pass the function schemas as the agent's tools when you create it. The exact class names differ slightly between SDK versions, so the important thing is the shape: a tool list where each entry declares one function with its schema.

Create the agent with function tools

import os
from dotenv import load_dotenv
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient

load_dotenv()

project_client = AIProjectClient.from_connection_string(
    credential=DefaultAzureCredential(),
    conn_str=os.getenv("PROJECT_CONNECTION_STRING"),
)

agent = project_client.agents.create_agent(
    model="YOUR_DEPLOYMENT_NAME",
    name="trip-planner-functions",
    instructions=(
        "You are a travel planning assistant. When the customer asks "
        "about weather, call get_weather. When they ask about hotel "
        "rates, call get_hotel_rate. Combine the answers into a short, "
        "friendly itinerary suggestion."
    ),
    tools=[weather_schema, hotel_schema],
    temperature=0.5,
)

print(f"Agent created: {agent.id}")

The model only sees the descriptions you wrote. It does not know, or care, what your functions do internally — it trusts the description to tell it when to call and what arguments to send. That separation of concerns is the whole design: the model plans, your code executes.

Step 3: Verify the agent triggers a tool call

Create a thread, ask a question that clearly needs one of the functions, and inspect the run. The run should pause at requires_action with the model's proposed function call instead of completing with an answer.

Probe the agent for a tool call

import time

thread = project_client.agents.create_thread()
project_client.agents.create_message(
    thread_id=thread.id,
    role="user",
    content="Should I bring an umbrella if I travel to Amsterdam tomorrow?",
)

run = project_client.agents.create_run(
    thread_id=thread.id, agent_id=agent.id
)

while run.status in ("queued", "in_progress"):
    run = project_client.agents.get_run(
        thread_id=thread.id, run_id=run.id
    )
    time.sleep(1)

print("Run status:", run.status)
if run.status == "requires_action":
    print("The agent wants to call a function.")
    print(run.required_action.submit_tool_outputs)

The run stopping at requires_action is expected and correct — it is not a failure. It means the run is waiting for your application to execute the requested functions. A run left in this state will time out, which is exactly what happens if you connect this agent to a client that does not know how to handle tool calls.

If the model answers the weather question directly instead of calling the function, refine the descriptions. A description that names the trigger ("whenever the customer asks about weather") usually fixes it faster than editing the general instructions.

Summary

You defined two custom functions with JSON schemas, attached them to an agent, and confirmed the agent requests a function call when the question calls for it. The agent now has a plan it cannot execute by itself — it needs an application that implements get_weather and get_hotel_rate. That is precisely what the next lab builds.
