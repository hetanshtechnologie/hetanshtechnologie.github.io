Review of conversations and memory

This chapter pulls together everything you have learned about conversations, state, and memory into one review. It is a checkpoint, not a lab: the goal is to consolidate the ideas so that the rest of the course can build on solid ground. Each section below recaps a core concept, states the key distinction you must remember, and points at the lab that demonstrated it.

State: What an Agent Carries Between Turns

State is the collection of information an agent holds between one turn and the next. Without state, every request is independent and the agent cannot hold a coherent conversation. State comes in three layers:

  • Session context: Which conversation is this, who is talking, and what the current goal is.
  • Conversation history: The transcript of messages exchanged so far.
  • Persistent memory: Facts and knowledge that survive beyond the session in an external store.

The important distinction: conversation history lives in the message list and dies with the session; persistent memory lives in a store and survives it.

The Memory Lifecycle: Capture to Forget

Every memory passes through five stages, and each stage is a place where the system can go wrong:

StageWhat happensCommon failure
CaptureThe agent extracts a fact worth keepingThe fact is never noticed or extracted
StoreThe fact is written to durable storageWrite fails or is skipped by policy
RetrieveRelevant memories are pulled back on later turnsWrong or stale memory is returned
UpdateChanged facts are refreshedOld and new values coexist
ForgetOutdated or disallowed memories are removedStale data persists forever

Types of Memory: Short-Term vs Long-Term

Short-term memory is the working context inside the model call — the system prompt, retrieved context, and message history. It always consumes tokens and disappears when the call ends. Long-term memory is durable, stored externally, and loaded only when retrieved. A good mental model: short-term memory is the desk, long-term memory is the filing cabinet.

Because both kinds of memory ultimately reach the model as text, they compete for the same token budget. The more history you include and the more memories you retrieve, the less room remains for the answer — which is why retrieval precision and history summarization are practical skills, not optional extras.

Memory Scope: Who Gets to See What

Scope is the access boundary of a memory. The four levels you covered were:

  • Conversation scope — visible only within one thread.
  • User scope — follows a user across conversations.
  • Agent scope — owned by a single agent.
  • Project or organization scope — shared knowledge across many agents.

The failure mode to remember: if you retrieve by agent or project but forget to filter by user, memories leak between users. The user boundary must always be respected in the query.

What the Labs Proved

The two labs in this section demonstrated the concepts end to end:

  • Agents and conversations: An agent "remembers" within a session only because the transcript is re-read every turn. Starting a new session wipes everything. From Python, you own the history yourself — whatever you put in the message list is all the model sees.
  • Memory stores and the memory search tool: Connecting the agent to an Azure AI Search-backed memory store lets facts persist across sessions. The agent uses the memory search tool to look up relevant memories, and you can inspect the stored documents in the search explorer.

Key Takeaways

  • Models are stateless; agents feel stateful because the application supplies context.
  • Conversation history is cheap to keep but dies with the session.
  • Persistent memory requires an external store and a retrieval mechanism.
  • Every memory must carry a scope, and retrieval must enforce it.
  • All memory consumes context, so quality of retrieval matters more than quantity.

Before moving on, run one mental check: could you explain to a colleague the difference between session state, conversation history, and persistent memory? If yes, you are ready for the next section. If not, re-read the first chapters of this section before continuing.

Summary

Conversations are powered by state, which splits into session context, history, and persistent memory. Memory follows a five-stage lifecycle and comes in short-term and long-term forms, always scoped to a conversation, user, agent, or project.
