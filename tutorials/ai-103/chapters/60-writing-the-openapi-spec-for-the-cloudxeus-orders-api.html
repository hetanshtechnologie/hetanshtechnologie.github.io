Writing the OpenAPI Spec for the CloudXeus Orders API

The CloudXeus orders API now runs in Azure, but an agent still has no idea what it does. The OpenAPI specification is the bridge: a machine-readable document that lists every operation, its inputs, and its outputs. In this chapter you write the complete specification for the three orders operations, mirroring the code you deployed.

Recap: The Four Sections You Need

As covered earlier, an OpenAPI document is built from the same building blocks:

  • info — title and version of the API.
  • servers — the base URL that hosts the operations.
  • paths — one block per endpoint, with one entry per HTTP method.
  • components — reusable schemas referenced from paths.

The Server URL

The servers block points at the deployed function app. Every path in the document is resolved against this URL, so the /api prefix must be included:

"servers": [
  {
    "url": "https://func-cloudxeus-orders-001.azurewebsites.net/api"
  }
]

Replace the host with your own function app name. If you later publish a second environment, such as staging, you add another server entry and the agent connection can pick which one to use.

Describing the Three Operations

Each operation needs an operationId, a summary, and precise parameter and response definitions. The operationId becomes the tool name in Foundry, so keep them unique and descriptive. The summary is what the model reads when deciding whether to call the tool, so describe the outcome, not the mechanics.

{
  "openapi": "3.0.1",
  "info": {"title": "CloudXeus Orders API", "version": "1.0.0"},
  "servers": [{"url": "https://YOUR_FUNCTION_APP.azurewebsites.net/api"}],
  "paths": {
    "/orders/{order_id}": {
      "get": {
        "operationId": "get_order",
        "summary": "Fetch a single CloudXeus order by its order id",
        "description": "Returns the status, customer email, and total for one order.",
        "parameters": [
          {
            "name": "order_id",
            "in": "path",
            "required": true,
            "schema": {"type": "string"}
          }
        ],
        "responses": {
          "200": {
            "description": "The requested order",
            "content": {
              "application/json": {
                "schema": {"$ref": "#/components/schemas/Order"}
              }
            }
          },
          "404": {"description": "Order not found"}
        }
      }
    },
    "/orders": {
      "get": {
        "operationId": "list_orders",
        "summary": "List every order belonging to a customer email",
        "parameters": [
          {
            "name": "email",
            "in": "query",
            "required": true,
            "schema": {"type": "string"}
          }
        ],
        "responses": {
          "200": {
            "description": "The customer's orders",
            "content": {
              "application/json": {
                "schema": {
                  "type": "array",
                  "items": {"$ref": "#/components/schemas/Order"}
                }
              }
            }
          }
        }
      }
    },
    "/orders/{order_id}/cancel": {
      "post": {
        "operationId": "cancel_order",
        "summary": "Cancel a CloudXeus order by its order id",
        "description": "Changes the order status to cancelled. Returns 409 if already cancelled.",
        "parameters": [
          {
            "name": "order_id",
            "in": "path",
            "required": true,
            "schema": {"type": "string"}
          }
        ],
        "responses": {
          "200": {
            "description": "The cancelled order",
            "content": {
              "application/json": {
                "schema": {"$ref": "#/components/schemas/Order"}
              }
            }
          },
          "404": {"description": "Order not found"},
          "409": {"description": "Order is already cancelled"}
        }
      }
    }
  },
  "components": {
    "schemas": {
      "Order": {
        "type": "object",
        "properties": {
          "id": {"type": "string"},
          "customer_email": {"type": "string"},
          "status": {"type": "string",
                      "enum": ["placed", "shipped", "cancelled"]},
          "total": {"type": "number"}
        },
        "required": ["id", "customer_email", "status", "total"]
      }
    }
  }
}

Reading the Spec Back Against the Code

Every endpoint in the function code has a counterpart in the spec:

FunctionSpec entryDetail to check
get_orderGET /orders/{order_id}Path parameter marked required, 404 documented
list_ordersGET /ordersQuery parameter email required
cancel_orderPOST /orders/{order_id}/cancel409 documented for the duplicate-cancel case

The spec and the code must agree in every detail. If the spec claims a parameter is optional but the code requires it, the agent will build malformed requests and the tool will fail at runtime. Keep the enum of status values in sync with what the code can actually return.

Validating the Document

Before you hand the spec to an agent, validate it:

  • Paste the JSON into the online Swagger Editor and confirm it parses with no errors.
  • Confirm every operationId is unique.
  • Confirm every $ref points at a schema that exists in components.

Save the finished document as cloudxeus-orders-api.openapi.json; you will upload it when you attach the tool to the agent.

Summary

The OpenAPI document turns the deployed API into a tool contract: it names the operations, declares their inputs, and describes their responses, all in a file an agent can read. With the spec written and validated, the next chapter attaches it to a Foundry agent and watches the tool in action.
