Agent Tools in Microsoft Foundry

Your agent can already hold a conversation, but it cannot do anything. It cannot look up current information, run calculations, read a file, or reach into another system. Tools are the mechanism that changes this: they are capabilities you attach to an agent, and they let the model act on the world instead of only predicting words about it. This chapter introduces the tool model in Microsoft Foundry and the tools you will use in the coming labs.

What a Tool Is

A tool is a named capability with an interface the model can invoke. Concretely, a tool has:

  • A name the model can reference, such as web_search or get_weather.
  • A description that tells the model when and why to use it.
  • An input contract describing the arguments the call expects.
  • An executor that runs the call and returns a result the model can read.

The model does not run the tool. It requests the tool by emitting a structured call, the platform or your application executes it, and the result is fed back into the conversation. That division is what makes tools safe: the model can suggest a call, but the execution happens in code you control.

How the Agent Decides to Use a Tool

Tool use is driven by the model during a run. When a message arrives, the model sees the tools attached to the agent — their names, descriptions, and input schemas — alongside the conversation. If the request needs information or action the model cannot produce from its own knowledge, it emits a tool call instead of a plain answer. The run then enters requires_action, and the platform or application executes the call.

Three factors shape how well this works:

  • Descriptions: a clear description tells the model exactly when a tool applies.
  • Prompt guidance: instructions can nudge the agent toward or away from specific tools.
  • Schema quality: well-defined parameters make the model's calls reliable and easy to execute.

Tool calling is the same mechanism whether the tool is built in or your own function. The model only knows the description you give it. That is why tool descriptions are worth writing carefully — the quality of the agent's decisions tracks the quality of the descriptions it was given.

Built-In Tools in Microsoft Foundry

Foundry agents can use a set of built-in tools without you writing any executor code. Each one is a managed capability:

Built-In Tools vs. Custom Functions

The key difference is who executes the call:

  • Built-in tools are executed by the platform. You attach them, and Foundry handles the search, the sandbox, or the file access. The cost is that you share a managed environment with defined boundaries.
  • Function calling delegates execution to your application. The model emits a structured request, and your code performs the real action — reading a database, calling a legacy API, or updating a ticket. This is the most flexible and the most work.

Both approaches produce the same conversation flow, and a single agent can mix them. You might attach Web Search for current facts and function calling for live data from your own systems.

Attaching and Managing Tools

Tools are configured as part of the agent definition, whether you edit in the portal or register through code. Managing tools well involves a few habits:

  • Start narrow. Attach only the tools the agent genuinely needs; every extra tool is a chance to be called in the wrong situation.
  • Describe precisely. Write each tool description from the model's perspective: when should this tool be used, and what should it return?
  • Version with the agent. A tool list change is a behavior change, so it belongs in the same versioned definition as the instructions.
  • Audit usage. Trace data shows which tools were called, how often, and whether the calls were appropriate.

When an agent misuses a tool — calling it too often, or failing to call it when it should — fix the description before touching code. A description that names concrete trigger conditions ("use this only when the user asks for live prices") changes behavior more reliably than tweaking the prompt in general.

Tools expand what an agent can do, and therefore what can go wrong. Web Search can return unreliable pages, Code Interpreter runs real code, and a custom function may have real side effects. Attach each tool only after you understand what its execution costs — in money, in risk, and in trust.

Summary

Tools give agents the ability to act: they are named capabilities with descriptions and input contracts, requested by the model and executed by the platform or your code. Built-in tools like Web Search and Code Interpreter cover common needs without custom code, while function calling connects the agent to your own systems. Well-chosen tools, precise descriptions, and careful versioning turn a chatbot into a genuinely useful agent.
