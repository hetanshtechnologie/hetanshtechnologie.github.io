Introduction to Guardrails in Microsoft Foundry

A generative model will happily follow instructions — including harmful ones — unless something stops it. Model-level safety training reduces the chance of bad behaviour, but it is not a guarantee, and it cannot react to the specifics of your application, your users, or your documents. That is the job of guardrails: explicit, configurable checks that run around the model to detect and block harmful or inappropriate content. This chapter introduces the guardrails available in Microsoft Foundry and how they fit into an agent architecture.

What Guardrails Are

Guardrails are control layers that inspect traffic before it reaches the model, after the model responds, or both. Think of them as a security checkpoint: inputs are screened for attacks before they enter, outputs are screened for policy violations before they leave, and suspicious traffic is flagged or blocked outright. Unlike prompt instructions, which the model can ignore, guardrails are deterministic services that return hard verdicts your code can act on.

The guardrails in Microsoft Foundry build on Azure AI Content Safety and related safety services. The main building blocks are:

GuardrailWhat it protects against
Content filtersHate, sexual, violence, self-harm, and related harmful content at configurable severity
Prompt shieldsJailbreak attempts and indirect prompt injection
Groundedness detectionHallucinated or unsupported content in responses
Protected material detectionReproduction of copyrighted text and known code

Where Guardrails Sit in the Architecture

An agent can have guardrails at several points. A typical production layout looks like this:

  1. Input gate: the user's message is scanned before it reaches any model call — catching injection attempts and harmful requests early.
  2. Per-call screening: prompts, including retrieved context and tool results, are screened before each model invocation.
  3. Output gate: the generated answer is screened before it is returned to the user — catching content the model produced despite its training.

Even with a platform-level content filter enabled on a deployment, it is good practice to add explicit guardrail calls in your application. The platform filter is a baseline; your guardrails enforce your own policy with your own thresholds and logging.

Built-In and Customizable

Foundry lets you use guardrails two ways:

  • Built-in defaults: enable the platform content filters on your deployment and get immediate protection with no code. These can be configured per harm category and severity.
  • Programmatic guardrails: call the safety services from your application code with your own thresholds, so you can block, flag, or rewrite content based on your business rules and log every decision.

You can also attach guardrail definitions to a model deployment so that every request that uses it is screened automatically, which is convenient when several applications share one deployment.

Configuring Guardrails in Foundry

In the Foundry portal, guardrails are typically configured from the model deployment settings or from a dedicated safety/guardrails page. The configuration choices you will meet are:

  • Which harm categories to screen and at which severity threshold each should block.
  • Whether to enable jailbreak detection and how to respond to it.
  • Where to send safety events — for example, to a Log Analytics workspace or Application Insights for review.
  • Whether violations should block the request or simply be logged alongside the response.

Choosing to block versus flag is a product decision, not just a technical one. Blocking stops the whole request, which can frustrate legitimate users if thresholds are too aggressive. Start conservative, measure false positives on real traffic, and tighten in stages.

Guardrails Are Not a Replacement for Prompt Design

Good guardrails work alongside good prompts; they do not replace them. The system prompt should still instruct the model about scope, refusal behaviour, and tone, while the guardrail enforces the boundary mechanically. The prompt handles the model's judgement; the guardrail handles the cases where judgement fails — and it does so with a deterministic, auditable decision.

Design guardrail responses with the user in mind. A blocked request should return a neutral, helpful message such as "I'm sorry, I can't help with that" rather than an error page, and the block should be logged so you can review why it fired.

Summary

Guardrails are deterministic safety layers that screen inputs and outputs around a generative model. Foundry provides content filters, prompt shields, groundedness detection, and protected-material detection, and lets you enable them on deployments or call them from code. They complement prompt design by enforcing boundaries mechanically and logging every decision. The next chapters look at two guardrails in detail — content filters in action, and prompt shields.
