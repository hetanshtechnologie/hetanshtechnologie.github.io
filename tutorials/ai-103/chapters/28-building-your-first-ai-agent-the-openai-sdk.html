Building Your First AI Agent - The OpenAI SDK

In this chapter you will see how the pieces come together in code. The OpenAI SDK, which you have used since your first API call, also provides an agent framework. Because your Foundry deployment speaks the same API, you can point the SDK's agents at your deployment and start orchestrating immediately.

The SDK as an Agent Framework

The OpenAI Python SDK ships with an Agents module on top of the chat completions API. Its job is to make the tool-call loop you built by hand into a managed runtime. You define an agent, attach instructions and tools, and let the runtime handle the planning, calling, and looping for you.

There are three core ideas:

  • Agent: the decision-maker — a model plus instructions, tools, and settings.
  • Tool: a callable your agent can invoke, defined as a function.
  • Runner: the loop that takes your input, runs the agent, and returns the result.

Frameworks change quickly. The concepts — agent, tool, runner — appear in every SDK generation, but method names may differ between versions. Read the version notes in the documentation that matches the package you install.

Your First Agent

Here is the smallest useful agent. It holds a conversation and answers from the model's knowledge:

from openai import AzureOpenAI
from agents import Agent, Runner
import os

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

agent = Agent(
    name="Helper",
    instructions="You are a friendly assistant. Answer clearly and briefly.",
    model="YOUR_DEPLOYMENT_NAME",
)

result = Runner.run_sync(agent, "Explain a database index in one paragraph.")
print(result.final_output)

Notice how the instructions field plays the role of the system prompt, and model is your deployment name. Everything you learned about behaviour control carries over unchanged.

Adding a Tool to the Agent

The real power appears when the agent can act. Any plain Python function can become a tool. The SDK inspects its name, docstring, and type hints to build the schema automatically:

import math

def square_root(number: float) -> str:
    """Compute the square root of a number."""
    return f"The square root of {number} is {math.sqrt(number):.4f}"

agent = Agent(
    name="Calculator",
    instructions="Use the square_root tool for root calculations.",
    model="YOUR_DEPLOYMENT_NAME",
    tools=[square_root],
)

result = Runner.run_sync(agent, "What is the square root of 729?")
print(result.final_output)

During the run, the agent reads the question, decides it needs the tool, calls square_root(729), receives the result, and writes its final answer — the loop you coded by hand in the previous labs, now managed for you.

How This Maps to Foundry

Nothing about the agent is stored in the cloud. The agent exists only in your Python process; the model still lives in your Foundry deployment. You get all of the agent orchestration locally while the heavy lifting — inference, content filtering, quota — stays in Azure. Your endpoint and key do the same job they always did.

SDK agent conceptWhat it maps to
modelYour deployment name in Foundry
AzureOpenAI clientYour endpoint, key, and API version
toolsThe same function schemas you wrote by hand
RunnerThe tool-call loop, automated

Running and Testing the Agent

A few practical habits pay off when you test:

  • Start with a goal that is small enough to verify by reading the output.
  • Give the agent a tool that obviously helps, so you can see the loop fire.
  • Print the result's tool-call history to confirm which tools ran and with which arguments.
  • Test refusal and error paths, not just the happy path.

An agent that can call tools can also misuse them. Even in experiments, do not attach tools that can delete data or spend money unless you are ready for the agent to call them.

Summary

The OpenAI SDK provides an agent framework on top of the chat completions API you already know. An agent combines instructions and tools, a runner drives the loop, and your Foundry deployment remains the model underneath. With one agent and one tool working, you have the nucleus of every larger system you will build in this course.
