Lab - Azure AI Language resource

You tried language detection in the browser in the previous chapter, possibly creating a resource along the way. Now you will create the Azure AI Language resource deliberately, both in the Azure portal and with the Azure CLI, and collect the endpoint and keys that every remaining lab in this section needs. Think of the resource as the billing and security boundary for the service: it owns your keys, tracks your usage, and defines which region your data is processed in.

Prerequisites

  • An Azure subscription. If you do not have one, create a free account before starting.
  • Access to the Azure portal at portal.azure.com.
  • Optionally, the Azure CLI installed locally for the command-line path.

Creating the Resource in the Portal

Step 1 — Start the create flow

  1. Sign in to the Azure portal at portal.azure.com.
  2. Select Create a resource from the top-left corner.
  3. Search for Language service and choose Language service from the results.
  4. Select Create to open the creation blade.

Step 2 — Fill in the basics

  1. Subscription: choose the subscription that will own the resource.
  2. Resource group: pick an existing group or select Create new and name it, for example rg-ai103.
  3. Region: choose a region close to your users, such as East US or West Europe. Data stays in the region you choose.
  4. Name: enter a globally unique name such as lang-ai103-demo.
  5. Pricing tier: select the free tier F0 if it is available in your region; otherwise use the standard tier.
  6. Leave the Custom question answering and Custom text classification / custom NER toggles as they are — the prebuilt features do not need them.

Step 3 — Create and verify

  1. Select Review + create, then Create.
  2. Wait for the deployment to complete, then select Go to resource.
  3. On the resource overview page, open Keys and Endpoint from the left menu and confirm the endpoint URL and two keys are visible.

The Language service is a single-service Cognitive Services resource. You can also create a multi-service AI Services resource that shares one endpoint and one key across Language, Translator, Speech, and other Azure AI services. Single-service resources are easier to reason about for these labs, so use one here.

Creating the Resource with the Azure CLI

If you prefer automation, create the same resource from a terminal. Run the commands from a shell where you are already signed in with az login.

# Sign in (opens a browser window for authentication)
az login

# Create a resource group in East US
az group create --name rg-ai103 --location eastus

# Create the Language service resource
az cognitiveservices account create \
  --name lang-ai103-demo \
  --resource-group rg-ai103 \
  --kind TextAnalytics \
  --sku F0 \
  --location eastus

After creation, fetch the endpoint and keys:

# Show the endpoint
az cognitiveservices account show \
  --name lang-ai103-demo \
  --resource-group rg-ai103 \
  --query properties.endpoint

# Show the two access keys
az cognitiveservices account keys list \
  --name lang-ai103-demo \
  --resource-group rg-ai103

The output contains everything your code needs. Note the --kind TextAnalytics value — that is the Azure kind identifier for the Language service.

The free tier is limited to a few thousand text records per month and a low requests-per-second rate. If you start seeing 429 errors during the labs, you have hit the free quota — wait and retry rather than assuming your code is broken.

Collecting the Connection Values

No matter how the resource was created, you need two values for every remaining lab:

  • Endpoint: the HTTPS URL from Keys and Endpoint, for example https://lang-ai103-demo.cognitiveservices.azure.com/.
  • Key 1 or Key 2: either access key. Both grant the same access; rotate between them when you rotate credentials.

In the code samples that follow you will see placeholders such as YOUR_ENDPOINT and YOUR_KEY. Substitute your real values, or better, load them from environment variables so they never sit in source files.

For production, Azure supports managed identity and Azure AD tokens so your applications never hold a static key at all. The key-based path in these labs is for learning; the same endpoint accepts token-based authentication when you are ready.
