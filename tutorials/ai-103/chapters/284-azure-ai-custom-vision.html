Azure AI Custom Vision

Azure AI Custom Vision is a service for building image classifiers and object detectors without writing machine learning code. The prebuilt services you have used so far — Computer Vision and Face — recognise the world they were trained on. Custom Vision lets you teach a model to recognise things the prebuilt models have never seen: your own product defects, a specific animal breed, a particular document layout, or the visual signs of a machine fault. You supply the example images, tag them, and the service handles the training and produces a model you can call through an API.

When Custom Vision Fits — and When It Does Not

The decision between a prebuilt service and Custom Vision comes down to a simple question: does the general-purpose model already cover my domain?

  • Use Computer Vision when you need generic capabilities such as reading text, tagging common objects, or describing scenes — it already knows millions of common concepts.
  • Use Custom Vision when your images contain a narrow or proprietary set of categories, or when the general model's predictions are not accurate enough on your data.
  • Consider the newer Image Analysis custom model feature as an alternative for modern custom classification and object detection workloads, since it is built on top of the current vision platform.

Custom Vision is a supervised learning workflow: the model learns exclusively from the examples you provide. The quality of the resulting model is capped by the quality and representativeness of your training set. More images, more variety, and cleaner labelling produce a better model — there is no shortcut around good data.

Project Types and Domains

Work in Custom Vision is organised into projects. Each project is defined by two choices:

  • Project type: Image classification (one label per image) or object detection (multiple labelled objects with bounding boxes in each image).
  • Domain: a hint about what kind of images you will train on. General, food, landmarks, retail, and compact domains trade off speed, accuracy, and exportability. The compact domains allow exporting the finished model to run offline, while the general domains generally train stronger models.

The Training Lifecycle

Every Custom Vision workflow follows the same loop, whether you click through the portal or drive it with the SDK:

  1. Collect a set of representative images for each category.
  2. Tag each image with its label — and for detection, draw the bounding box around each object.
  3. Train the model. The service splits your data automatically, using most of it to learn and the rest to measure performance.
  4. Evaluate the reported precision, recall, and other metrics. If they are weak, add images or fix the labelling and train again.
  5. Publish the best iteration to a prediction endpoint, where your application calls it.

Treat training as an iterative process, not a single event. The first iteration is almost never the final one. Inspect the misclassified images from each iteration — they show you exactly what kind of example the model is missing.

Training and Prediction Resources

Custom Vision uses two separate Azure resources. The training resource covers creating projects and running training jobs; the prediction resource serves inference requests once you publish an iteration. Keeping them separate lets you scale prediction independently and control who can create projects versus who can simply call the endpoint.

  • CustomVision.Training — used by the training portal and the training SDK. This is where projects, images, and trained iterations live.
  • CustomVision.Prediction — receives classification and detection requests for published iterations and returns results.

Both are billed separately, and prediction charges apply per inference call rather than per project.

What the Service Returns

A classification prediction is a list of the project's tags, each with a confidence score. Your code picks the tag with the highest score, or applies a threshold to decide that the image matches nothing confidently. Detection predictions extend this with a bounding box for every object found:

[
  { "tagName": "defective", "probability": 0.91, "boundingBox": null },
  { "tagName": "ok", "probability": 0.06, "boundingBox": null }
]

For object detection, each entry carries a boundingBox with left, top, width, and height expressed as fractions of the image dimensions.

Limits to Keep in Mind

  • The maximum image size for a single call is 4 MB for a URL upload and 6 MB for binary uploads, depending on the endpoint.
  • Image files should be under 6 MB and re-encoded if they are too large; very wide or tall images may need resizing first.
  • Training iterations have a maximum number of images per project that depends on the resource tier — plan your dataset size up front.
  • Compact-domain models can be exported (TensorFlow, CoreML, ONNX, Docker), whereas general-domain models only run in the cloud.

Summary

Custom Vision answers the question that prebuilt vision services cannot: how do I recognise my categories in my images? It is a supervised workflow organised into classification and detection projects, trained from labelled examples, and measured by precision and recall. Training and prediction run on separate Azure resources, and once an iteration is published your application can call it like any other vision API.
