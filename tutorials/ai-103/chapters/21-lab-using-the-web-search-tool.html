Lab - Using the Web Search Tool

In this lab you will connect a web search tool to a deployed model using the function-calling loop. The model will decide when current information is needed, call the search tool, and use the returned results to answer the question. The pattern you build here is the same one used for any tool: database queries, APIs, or internal systems.

What You Need

  • Your endpoint and key environment variables.
  • A deployed chat model, for example gpt-4o-mini.
  • The openai SDK installed, as in the earlier labs.

Design the Tool Schema

Create web_search_tool.py in a new folder ai103-lab21. The tool is declared with a schema so the model knows it exists and how to call it:

from openai import AzureOpenAI
import json
import os

client = AzureOpenAI(
    azure_endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
    api_key=os.environ["AZURE_OPENAI_KEY"],
    api_version="2025-01-01-preview",
)

tools = [
    {
        "type": "function",
        "function": {
            "name": "web_search",
            "description": "Search the public web and return a short summary of results.",
            "parameters": {
                "type": "object",
                "properties": {
                    "query": {"type": "string", "description": "The search query to run."}
                },
                "required": ["query"],
            },
        },
    }
]

Implement the Tool

Next, write the Python function the model can trigger. In this lab the function returns placeholder text; in a real project it would call a search provider's API.

A real implementation would send the query to a search API, parse the returned snippets, and return just the top few titles and summaries. That keeps the model's context window small and the answer fast.

Run the Tool-Call Loop

Add the loop that lets the model call the tool and then answer using the result:

messages = [
    {"role": "system", "content": "Use the web_search tool whenever the question asks about current information."},
    {"role": "user", "content": "What was the result of the most recent general election in your country?"},
]

response = client.chat.completions.create(
    model="YOUR_DEPLOYMENT_NAME",
    messages=messages,
    tools=tools,
)

message = response.choices[0].message
messages.append(message)

if message.tool_calls:
    for call in message.tool_calls:
        print("Tool requested:", call.function.name, call.function.arguments)
        arguments = json.loads(call.function.arguments)
        result = web_search(arguments["query"])
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": result,
        })

final_response = client.chat.completions.create(
    model="YOUR_DEPLOYMENT_NAME",
    messages=messages,
    tools=tools,
)
print(final_response.choices[0].message.content)

Run and Observe

Step 1 - Run the script

python web_search_tool.py

Step 2 - Watch the two-stage output

First you will see a line printed by your code: Tool requested: web_search {"query": "..."}. That is the model deciding it needs fresh data. Then the final answer appears, written using the placeholder search result. If the model decides it already knows the answer, it will skip the tool and answer directly.

Step 3 - Experiment

Change the system prompt to force tool use for every question, and try a question the model certainly knows, such as "What is the capital of France?". Watch how a stronger prompt makes the model reach for the tool even when it does not need it.

Connecting a Real Search Provider

To turn the placeholder into real results, replace the body of web_search with a call to a search API. Azure provides search and grounding services that can be wired into agents; the general pattern is the same:

  1. Send the query to the provider's API with your provider key.
  2. Parse the response into a compact list of titles and snippets.
  3. Return that list as the tool result string.

Store provider keys in environment variables, never in the script. A leaked search key can be used to spend money or access private data.

Common Issues

  • The model never calls the tool: strengthen the system prompt or make the question obviously time-sensitive.
  • tool_call_id mismatch: copy the exact id from the tool call into the tool message.
  • Malformed arguments: the model sometimes returns arguments as a string; always run json.loads and validate before use.
  • Loop never ends: add a safety counter that stops after a few iterations.

Summary

You have implemented the full tool-call loop: a schema that advertises the tool, a Python function that plays its part, and a two-stage exchange where the model requests the tool and then answers using its output. This exact pattern powers web search and extends unchanged to any other function you want to hand the model.
