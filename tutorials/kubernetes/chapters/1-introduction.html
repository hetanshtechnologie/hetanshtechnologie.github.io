Introduction: What is Kubernetes and Why Use It?

Kubernetes (often shortened to k8s — there are 8 letters between the "K" and the "s") is an open-source system for automating the deployment, scaling, and management of containerized applications. It was born inside Google, where it grew out of an internal system called Borg (Google has been running containers at massive scale for almost two decades). In 2015 Google donated the project to the Cloud Native Computing Foundation (CNCF), and today Kubernetes is the most widely adopted container-orchestration platform in the world.

If you have ever deployed a website to a single server, then shipped an update, watched the server crash, and tried to restart it at 2 am while users complained — Kubernetes was built to solve exactly that class of problems, but at the scale of hundreds or thousands of servers.

Why do we even need Kubernetes?

First you need containers. A container packages your application together with everything it needs to run: the code, the runtime, system libraries, configuration, everything. Because of that packaging, the app behaves identically on your laptop, in a test server, and in production.

Containers solve "it works on my machine" — but they create a new problem. When you have dozens of containers on different machines, you now have to answer questions like:

  • Which machine should each container run on?
  • What happens when a machine dies and its containers disappear?
  • How do I roll out a new version to 50 containers without downtime?
  • How do I give more replicas when traffic spikes, and fewer when it drops?
  • How do my containers find each other, when IP addresses change constantly?
  • How do I store login credentials, database passwords, and app settings safely?

That is container orchestration, and Kubernetes is a tool for automating every one of those tasks. You tell Kubernetes what you want ("run 3 copies of the web app that listen on port 80"), and Kubernetes figures out how to make it true — and keeps making it true forever.

Declarative by design: you describe the desired state of your system in a YAML file, and Kubernetes constantly works to make the actual state match the desired state. This one idea — "declare the end state, not the steps" — is the most important mental model in Kubernetes.

What Kubernetes actually does

  • Deployment: installs your container images onto the right machines and keeps them running.
  • Scaling: increases or decreases the number of copies of your app, manually or automatically.
  • Self-healing: restarts failed containers, replaces dead nodes, and reschedules work automatically.
  • Service discovery & load balancing: gives every group of pods a stable name and address and spreads traffic among them.
  • Rolling updates & rollbacks: ships new versions gradually and can instantly go back to the last good one.
  • Configuration & secrets: stores app settings and passwords separately from your code and injects them into pods.
  • Storage: attaches disk volumes that survive even if the pod does not.

The three big benefits

1. Scalability

A single server can only handle so much traffic, and you can only make one server "bigger" up to a point. Kubernetes is built for horizontal scaling: you add more copies of your app across more machines, and a Service spreads the load between them. Scaling up can be a one-second command (kubectl scale) or fully automatic (HorizontalPodAutoscaler reacts to CPU or memory usage).

2. Self-healing

Machines crash. Containers crash. Processes hang. Kubernetes treats these as normal events and cleans up after them automatically: if a pod dies, a controller creates a replacement; if a node goes offline, the workload is rescheduled elsewhere; if an app stops responding, its health check fails and the pod is restarted. You no longer get woken up to "restart the server."

3. Portability

Because the desired state is just YAML files, the exact same definitions run on your laptop (Minikube), on a bare-metal server, on-premises with Rancher or OpenShift, and on every major cloud (Amazon EKS, Google GKE, Azure AKS, and many more). You are not locked into a single vendor's proprietary deployment format.

One cluster, two kinds of machines

Before running commands, it helps to see the big picture. A Kubernetes deployment is called a cluster, and it is made of two halves:

ComponentWhat it isExamples
Control Plane (the "brain")Makes all decisions: scheduling, health checking, scaling. Holds the desired state.API Server, etcd, Scheduler, Controller Manager
Worker Nodes (the "muscle")Machines that actually run your applications inside pods.kubelet, kube-proxy, container runtime, pods

You, the administrator, almost never touch the nodes directly. You talk to the API Server using a command-line tool called kubectl (pronounced "kube control"), and the control plane does the rest. Nodes are deliberately interchangeable — if one dies, its workloads move to another with no human involvement.

Important: do not confuse "master/worker" terminology you may see in older tutorials with today's reality. The control plane and worker nodes are split out of security: the control plane is heavily protected, and worker nodes are ordinary machines your applications run on.

Should you always use Kubernetes?

Kubernetes is powerful but it is not magic, and it is not always the right tool. A good rule of thumb:

Good fit for KubernetesProbably overkill for
  • Many services that need to share infrastructure
  • Load that varies and needs automatic scaling
  • Teams that deploy many times a day
  • High-availability requirements (no single point of failure)
  • Moving between clouds or keeping on-prem + cloud in sync
  • One small website or a hobby project
  • A team of one with no time for operational tooling
  • Single-server systems that fit on a VM today
  • Workloads that a serverless platform already handles

Even when you do adopt it, most teams start with a managed Kubernetes offering on their cloud (EKS, GKE, AKS) so someone else runs the control plane for them — the principles you are about to learn are exactly the same on all of them.
