Advanced Topics: Updates, Storage, Ingress, and Observability

You already know enough Kubernetes to run a real service. This chapter adds the production skills: shipping changes without downtime, surviving pod restarts with persistent storage, routing hostnames to your apps, and knowing what is happening in your cluster.

1. Rolling updates and rollbacks

When you change the image (or any pod template field) of a Deployment, Kubernetes does a rolling update: it starts new pods while the old ones are still serving, waits for the new ones to become healthy, then removes the old ones. Zero downtime, by default. (Strategy recreate exists, but it kills everything first — for most apps, rolling wins.)

Demo (re-apply your nginx Deployment from Chapter 4 first, then):

# bump the image and record WHY this change happened
kubectl set image deployment/nginx-deployment nginx=nginx:1.26
kubectl rollout status deployment/nginx-deployment     # watch it complete
kubectl rollout history deployment/nginx-deployment    # every version + change-cause

Now imagine the new image is broken. Roll back in one command — no manual undo:

kubectl rollout undo deployment/nginx-deployment
kubectl rollout status deployment/nginx-deployment

How Kubernetes controls the update

SettingMeaningSane default / example
maxSurgeHow many extra pods (beyond desired) may exist during update25%
maxUnavailableHow many old pods may be down at once25%
minReadySecondsHow long a pod must be healthy before it counts as ready5 for slow-starting apps
progressDeadlineSecondsGive up & mark rollout "failed" if stuck600
Why look at this at all: the default strategy is great, but for a new release that crashes on startup, Kotlin-style "the rollout waits forever" happens when maxUnavailable is small. Add a readiness probe (Section 4) so Kubernetes knows a pod is actually serving before counting it as done.

2. Persistent Volumes and Persistent Volume Claims

Pods are disposable, so their storage must not be tied to the pod's life. Kubernetes separates two concerns:

  • PersistentVolume (PV) — the storage itself (a disk, an NFS share, a cloud volume). Cluster-level resource.
  • PersistentVolumeClaim (PVC) — a request: "give me 1 Gi of fast storage, read-write." Treated like a disk you mount into pods.

In most modern clusters you skip creating PVs yourself and use a StorageClass that provisions storage on demand (dynamic provisioning). On Minikube this works out of the box:

kubectl get storageclass            # "standard" = dynamically provisions local volumes

Create a PVC and use it in a pod:

# pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
# pod-with-storage.yaml
apiVersion: v1
kind: Pod
metadata:
  name: storage-test
spec:
  containers:
  - name: writer
    image: busybox
    command: ["sh", "-c", "echo 'survives restart' > /data/hello.txt; sleep 3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data-pvc
kubectl apply -f pvc.yaml -f pod-with-storage.yaml
kubectl exec storage-test -- cat /data/hello.txt    # file exists
kubectl delete pod storage-test
kubectl apply -f pod-with-storage.yaml               # new pod, same PVC
kubectl exec storage-test -- cat /data/hello.txt    # file STILL exists

Access modes you will meet

ModeMeaningTypical use
ReadWriteOnce (RWO)One node can mount, read & writeDatabases, caches
ReadOnlyMany (ROX)Many nodes, read-onlyShared config, read replicas
ReadWriteMany (RWX)Many nodes, read & writeShared file stores (NFS), CI caches

3. Ingress controllers (hostname routing)

A LoadBalancer gives every service its own IP — expensive and clunky when you have many services. Ingress is a single entrance that routes by hostname and path: api.myapp.com → service A, www.myapp.com → service B, with TLS handled once.

Terminology (a common beginner trap): the Ingress object is just rules. The Ingress controller (NGINX Ingress, Traefik, HAProxy, cloud ones) is the actual proxy that implements them. Most clusters need you to install a controller.

On Minikube it is one command:

minikube addons enable ingress
minikube addons list | findstr ingress     # after: "ingress: enabled"

Create two small deployments and services (reuse the nginx image, name them app-a and app-b, following the Service pattern from Chapter 4), then route hostnames:

# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: a.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: app-a-service
            port: { number: 80 }
  - host: b.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: app-b-service
            port: { number: 80 }
kubectl apply -f ingress.yaml
# give the fake hostnames a local address (find your minikube IP)
kubectl get ingress
minikube ip
# Windows: add "<minikube-ip>  a.example.com  b.example.com" to C:\Windows\System32\drivers\etc\hosts
# Linux/macOS: add the same line to /etc/hosts
curl http://a.example.com     # Nginx welcome (from service A)
curl http://b.example.com     # Nginx welcome (from service B)
Diagnosing a latency/hang on curl: the Ingress controller may need a moment to load after minikube addons enable ingress. Give it 30–60 seconds (kubectl get pods -n ingress-nginx to confirm it's Running) before testing.

4. Monitoring and logging basics

Logs

Applications should write to stdout/stderr — kubelet captures container output and makes it searchable:

kubectl logs <pod-name>            # current logs
kubectl logs <pod-name> -f         # follow (like tail -f)
kubectl logs <pod-name> --previous # logs of the pod's previous crashed container (gold for debugging crashes!)
kubectl logs -l app=nginx --all-pods=true     # logs from pods matching a label

Metrics

Historical CPU/memory needs the metrics-server. Minikube ships it:

minikube addons enable metrics-server
sleep 30   # wait for it to collect
kubectl top nodes
kubectl top pods

That is the foundation. Full observability stacks are Prometheus (metrics collection + alerts) and Grafana (dashboards); log pipelines are usually Fluentd/Fluent Bit —> Elasticsearch or Loki. All are ecosystem projects, run on the same Kubernetes you now know, and are worth exploring after this course.

Health checks: liveness and readiness probes

        # the nginx container:
        readinessProbe:
          httpGet: { path: /, port: 80 }     # "start sending traffic only when this passes"
        livenessProbe:
          httpGet: { path: /, port: 80 }     # "if this fails, restart the container"
        startupProbe:                        # optional: give slow apps time to boot
          httpGet: { path: /, port: 80 }
          failureThreshold: 30
          periodSeconds: 10
readiness vs liveness: readiness = "do not route traffic to me yet" (used by Services, safe). liveness = "restart me, I am stuck" (dangerous if misconfigured — a wrong liveness probe can crash-loop a healthy app). When in doubt, start with a readiness probe only.
✏️ Exercise: Apply the three probes above to the nginx Deployment and run kubectl get deploy — readiness is the reason a rollout "pauses." Now: (a) write kubectl rollout undo after a bad set image; (b) mount a PVC into nginx and confirm data survives a pod delete. You have now done the full production loop.
