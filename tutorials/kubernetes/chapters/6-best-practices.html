Best Practices: Resources, Namespaces, and Security Basics

Tutorial clusters forgivingly swallow sloppy YAML. Production clusters do not: they get noisy neighbors, overloaded nodes, and — if left open — attackers. This chapter teaches the discipline that separates a hobby demo from a deployable system, plus the security fundamentals (RBAC and Network Policies) that real platforms require.

1. Resource requests and limits

A container should always declare what it needs and what it may not exceed. Two settings, confusingly similar at first glance:

requestslimits
MeaningReserve this much; the scheduler guarantees itCap usage at this; the runtime enforces it
PurposeFair scheduling, prevents overcommit of nodesStops one app from starving the node
Verdict if never setPods may never be scheduled correctlyA runaway pod can kill neighbor nodes
        resources:
          requests:
            cpu: "250m"          # 0.25 CPU core
            memory: "256Mi"
          limits:
            cpu: "1"             # at most 1 full core
            memory: "512Mi"

CPU is measured in cores or milli-units: 0.5 = 500m. Memory uses Mi/Gi (mebibytes — 1024-based) in requests because that is how the kernel counts it. When memory hits the limit, the pod is killed (OOMKilled) — this is the classic "my pod keeps restarting" mystery. When CPU hits its limit, the app is only throttled, not killed.

Rule of thumb for beginners: always set requests and limits for CPU and memory on every container. Start with requests based on observation (kubectl top pod over a week) and limits at ~2× the request. For the HPA to work, requests must be present.

2. Namespaces: folders for your cluster

A Namespace partitions the cluster into logical groups. Three namespaces always exist: default, kube-system (where the control plane runs), and kube-public. You will use them to separate environments (dev, staging, prod) or teams.

kubectl create namespace dev
kubectl get pods -n dev                       # operate inside the namespace
kubectl apply -f nginx.yaml -n dev            # create objects there
kubectl config set-context --current --namespace=dev   # make -n default for this session
kubectl get namespaces

Why bother? Isolation (dev can't accidentally see prod secrets), policy enforcement (quotas), and cleanup (kubectl delete namespace dev deletes everything in it). Pair namespaces with a ResourceQuota to cap total CPU/memory a team may use:

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi

3. Labels, selectors, and annotations

  • Labels are key-value pairs that identity — Services, ReplicaSets, and monitoring all choose objects via label selectors (app: nginx, tier: frontend, version: v2).
  • Annotations are key-value metadata that tools read but selectors ignore (deprecated flags, tool info, timestamps).

Conventions: use a consistent label set (e.g. app, tier, environment) and never change a Deployment's selector after creation — only the pod template labels are safe to edit. Changing the selector orphan-s both old and new pods.

4. Security basics: RBAC

Kubernetes is no different than any system: default it to deny, then grant least privilege. RBAC (Role-Based Access Control) is the mechanism, built on four concepts:

ObjectDefinesExample
ServiceAccountAn identity your pod runs as (not a human!)myapp-sa
Role / ClusterRoleA set of allowed actions on resources"get, list pods" (namespaced) vs "get nodes" (cluster-wide)
RoleBinding / ClusterRoleBindingAttaches a Role to a ServiceAccount/user"bind myapp-sa to pod-reader"
# role.yaml — never let an app do more than its job
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: ServiceAccount
  name: myapp-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
The biggest beginner leak: admins copy the long-lived admin ServiceAccount credentials out of clusters. Never; and pass a pod's identity via serviceAccountName: in the pod spec, with bound tokens where possible. Audit with kubectl auth can-i --list.

5. Network Policies: your private firewall inside the cluster

By default, all pods can talk to all pods. NetworkPolicy is the micro-firewall: allow only the traffic your app truly needs. It works only if your cluster has a CNI that enforces it (Calico, Cilium, Antrea — Minikube's default generally permits policies with the right add-on, usually via Cilium).

# only the web frontend may reach the database
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-only
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: database        # this policy applies to database pods
  policyTypes: ["Ingress"]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend    # only pods tagged app:frontend may connect
    ports:
    - port: 5432

Follow the default-deny pattern: apply an empty podSelector: {} policy that blocks everything for a namespace, then add explicit allow policies. Everything not allowed is denied.

6. More habits that save you in production

  • Pin image versions (nginx:1.25, not latest) and prefer digest pinning for critical images.
  • Run as non-root and read-only root filesystem in the pod security context (securityContext: { runAsNonRoot: true, readOnlyRootFilesystem: true }).
  • Health checks on everything — readiness + liveness probes (Chapter 5) prevent both downtime and crash-loops.
  • Always courtesy-delete (kubectl delete -f file.yaml) instead of leaving test workload running.
  • Keep YAML in Git — every cluster object should be a reviewed file, not a shell history. Tools like kubectl diff and GitOps (Argo CD/Flux, Chapter 7) come from this habit.
  • Tie the HPA to the right metric: autoscale on real business metrics if possible (requests/second), not only CPU.
✏️ Exercise: Create a dev namespace with a ResourceQuota of 2 CPU / 2 Gi. Deploy nginx there with resources requests: 250m/128Mi, limits: 500m/256Mi. Then (a) apply the allow-web-only NetworkPolicy against your database-style pod, (b) verify with kubectl top that your limits are being respected. You have now built a small but genuinely production-minded cluster.
