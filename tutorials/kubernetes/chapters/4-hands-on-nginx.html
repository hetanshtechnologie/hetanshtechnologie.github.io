Hands-On: Deploying Nginx

This is the chapter everything so far has been building toward. On your running local cluster you will: deploy a real application, watch it heal itself, scale it up and down, expose it to your browser, and inject configuration and secrets into it. Five skills, ~30 minutes, zero cloud costs.

1. Write your first Deployment

Create a file called nginx.yaml with this content (spaces for indentation, never tabs):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80

Deploy it and watch the results:

kubectl apply -f nginx.yaml
kubectl get deployments
kubectl get pods -o wide

You should see a Deployment named nginx-deployment with 3/3 ready, and three pods each with their own IP. Behind the scenes the Deployment created a ReplicaSet, which created the three pods.

2. Watch self-healing work

Now deliberately kill a pod — Kubernetes should not care at all:

kubectl delete pod <one-of-the-pod-names>
kubectl get pods

The ReplicaSet immediately creates a brand-new replacement pod. The desired state (3 replicas) was declared, so Kubernetes simply refuses to accept anything else. This is self-healing in its purest form.

Peek at the machinery: kubectl get replicasets shows the ReplicaSet the Deployment created (name like nginx-deployment-<hash>). kubectl describe deployment nginx-deployment shows events such as "Created pod" and "Scaled up replica set".

3. Scale the Deployment

Horizontal scaling is a single command:

kubectl scale deployment nginx-deployment --replicas=5
kubectl get pods
kubectl get deployment nginx-deployment -o wide

You now have five Nginx pods. Scale back down whenever you like with --replicas=3. Kubernetes balances pods across the available space on your node automatically.

4. Expose the app with a Service

Pods have IPs that change and are only reachable inside the cluster. Add a Service to nginx.yaml: append a second YAML document (separated by ---) that routes to pods labeled app: nginx:

---
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: NodePort          # starts as NodePort for local testing
  selector:
    app: nginx
  ports:
  - port: 80              # port on the Service
    targetPort: 80        # port on the pod container
    nodePort: 30080       # fixed external port (30000-32767 allowed)
kubectl apply -f nginx.yaml
kubectl get svc nginx-service

Reach it from your browser

Minikube makes this trivial — it opens the URL for you:

minikube service nginx-service

You should see the Nginx welcome page. What actually happened: traffic hit <node-ip>:30080 → kube-proxy → one of the Nginx pods, balanced automatically. Press curl on it a few times or load it in two browsers — all five pods answer the same content.

Scale does not mean data must differ: hitting the NodePort repeatedly shows Nginx's default page from whichever pod answered. That is load balancing, not session affinity — good enough for stateless web apps. (If you need a name behind one IP inside the cluster, a ClusterIP Service with port/targetPort is all you need.)

5. NodePort vs LoadBalancer

On single-node local clusters both behave similarly, but in the real world they differ:

NodePortLoadBalancer
Exposed asA high port on every node (30000–32767)A real cloud load balancer with a public IP
Provider neededNoneCloud controller (EKS/GKE/AKS/DigitalOcean…)
Minikube / kindWorks directlyMinikube needs minikube tunnel; kind needs MetalLB
Use in productionRarely — usually by Ingress/InfraYes, for public services; often behind an Ingress

Try a LoadBalancer on Minikube (leave this terminal open in the background):

minikube tunnel

In a second terminal, change the Service type and re-apply:

kubectl patch svc nginx-service -p '{"spec":{"type":"LoadBalancer"}}'
kubectl get svc nginx-service   # wait for EXTERNAL-IP, then open it in a browser

On a cloud cluster the exact same YAML makes your cloud provider spin up a real load balancer and assign a public IP.

6. ConfigMaps: configuration without rebuilds

Create a ConfigMap three different ways and note how they differ:

kubectl create configmap app-config --from-literal=log_level=debug
kubectl create configmap app-config-file --from-env-file=settings.env   # settings.env = KEY=VALUE lines
kubectl create configmap from-yaml-file --from-file=./app.conf          # file becomes a mounted file

Now wire the log_level value into the Nginx pods as an environment variable by adding to the container in nginx.yaml:

        env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: log_level
kubectl apply -f nginx.yaml
kubectl exec deploy/nginx-deployment -- sh -c 'echo "LOG_LEVEL=$LOG_LEVEL"'

Changing the ConfigMap does not require rebuilding the image — a rolling restart makes the new value available.

7. Secrets: passwords the safe-ish way

kubectl create secret generic app-secret \
  --from-literal=db_password='SuperS3cret!'
kubectl get secret app-secret -o yaml          # value shown as base64

Use it two ways inside the pod:

        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: db_password
        volumeMounts:
        - name: secret-vol
          mountPath: /etc/app-secret
          readOnly: true
      volumes:
      - name: secret-vol
        secret:
          secretName: app-secret
kubectl apply -f nginx.yaml
kubectl exec deploy/nginx-deployment -- sh -c 'echo $DB_PASSWORD; ls /etc/app-secret; cat /etc/app-secret/db_password'
Beginner security note: that base64 is not encryption. Anyone with cluster access can decode it. For real deployments encrypt Secrets at rest, scope access with RBAC (Chapter 6), and consider an external vault.

8. Inspect and clean up

kubectl logs deploy/nginx-deployment       # logs from the first pod
kubectl logs -l app=nginx --tail=20        # logs from all matching pods
kubectl top pod                            # CPU/memory (needs metrics-server, see ch. 5)
kubectl delete -f nginx.yaml               # removes Service + Deployment
✏️ Exercise: Recreate the Deployment (re-apply nginx.yaml), scale it to 5, open minikube service nginx-service, then in a loop run kubectl get pods while deleting a pod — watch the replacement appear within a second. Finally, change image: nginx:1.25 to nginx:1.26 and kubectl apply; the Deployment rolls out the new image without downtime (we go deep on this in Chapter 5).
