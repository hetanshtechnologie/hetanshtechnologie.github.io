Core Concepts

This chapter teaches you the ten objects you will use every single day in Kubernetes. The best way to read it is with a picture in your head: a Deployment creates Pods on Nodes, a Service gives those Pods a stable name, and ConfigMaps/Secrets supply them settings and passwords. Everything else in Kubernetes is a variation on these ideas.

Pods, Nodes, and Clusters

Pods

A Pod is the smallest thing you can deploy in Kubernetes: one or more containers that share a network and storage and are always scheduled together. Yes, a Pod can hold more than one container — that pattern (called a sidecar) is used for helper tasks like logging or metrics collectors — but in the beginning, think of a Pod as "one running instance of your application."

  • Each Pod gets its own IP address inside the cluster.
  • Pods are ephemeral — they die, get replaced, get rescheduled. Never point anything directly at a pod's IP for long.
  • You almost never create a Pod by itself. You create a workload (like a Deployment) and it makes the Pods for you.

Nodes

A Node is a machine — physical or virtual — that belongs to your cluster. Every worker node runs three things:

ProcessJob
kubeletThe "node agent". Talks to the control plane, starts and stops containers, reports health.
kube-proxyNetworking rules that make Services work — forwards traffic to the right pods.
Container runtimeActually runs the containers (containerd, CRI-O, or Docker when used as the runtime).

Clusters

A Cluster is the whole system: one or more control-plane nodes plus many worker nodes, all managed as a single unit. On your laptop, a Minikube "cluster" is usually just one machine that plays both roles. In production it is many machines spread across multiple server racks or clouds.

Memory trick: Cluster ⇒ Nodes ⇒ Pods ⇒ Containers. Each level is a group of the one below it.

Deployments, ReplicaSets, and Services

Deployments

A Deployment is the object you will write 90% of the time. You tell it: "here is my image, here is the desired number of replicas, here is how to update me." The Deployment then makes sure that desired state stays true — forever. It is the object that gives you rolling updates, rollbacks, and self-healing with almost no work.

ReplicaSets

A ReplicaSet is a lower-level controller that simply guarantees "exactly N pod copies exist at all times." If a pod dies, the ReplicaSet creates a replacement. You will rarely write a ReplicaSet yourself — a Deployment creates and manages a ReplicaSet for you.

Services

Pods are born and die constantly, so their IPs change constantly. A Service is a stable name + IP that sits in front of a group of pods and balances traffic across them. It picks the pods using label selectors — "give me all pods tagged app: nginx."

Service typeWho can reach itWhen to use
ClusterIP (default)Only inside the clusterService-to-service communication (your backend talking to your database)
NodePortFrom outside, via a high port on any nodeQuick testing / exposing one service
LoadBalancerFrom outside, via a cloud load balancer IPThe normal way to expose apps on a cloud cluster (EKS, GKE, AKS)
Ingress (not a Service type, but…)From outside, via hostnames/paths like app.example.comHTTP routing with TLS for many services (Chapter 5)
Handy mental model: Deployment = "how many copies and which version". Service = "how they are found". A Service does not launch anything — it only routes traffic to pods that already match its selector.

ConfigMaps and Secrets

ConfigMaps

A ConfigMap stores non-secret configuration: database names, feature flags, URLs, environment variables. It keeps configuration out of your container image, so you can change settings without rebuilding and redeploying the image. You can mount it as environment variables or as files inside the pod.

Secrets

A Secret is the same idea for sensitive data: passwords, API tokens, private SSH keys. A few honest caveats for beginners:

  • The values are only base64-encoded in YAML — that is not encryption, just encoding. Anyone with access to the Secret object can decode it.
  • Kubernetes stores Secrets in etcd. Enable encryption at rest in a real cluster.
  • Whichever way you use Secrets (env vars or files), the data is visible inside the pod to whoever can enter the pod.
  • Prefer mounted files over environment variables when pods restart often; prefer external secret stores (Vault, cloud KMS) as you grow.

Below is what a real Deployment that uses all three ideas looks like. You will meet this YAML again in Chapter 4 — read it now at a relaxed pace and see how the pieces fit (metadata identifies the object, spec declares the desired state):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  labels: { app: my-app }
spec:
  replicas: 3
  selector:
    matchLabels: { app: my-app }        # the Deployment "owns" pods with this label
  template:
    metadata:
      labels: { app: my-app }           # pods get this label for the Service to find
    spec:
      containers:
      - name: app
        image: nginx:1.25
        ports: [{ containerPort: 80 }]
        env:
        - name: LOG_LEVEL
          valueFrom: { configMapKeyRef: { name: app-config, key: log_level } }
        envFrom:
        - configMapRef: { name: app-config }   # all keys become env vars
        volumeMounts:
        - { name: app-secret-vol, mountPath: /etc/app-secret }
      volumes:
      - name: app-secret-vol
        secret: { secretName: app-secret }      # a mounted Secret
---
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector: { app: my-app }              # routes to pods carrying this label
  ports:
  - { port: 80, targetPort: 80 }
YAML gotcha for beginners: it is the tabs vs spaces trap. Kubernetes YAML uses spaces only — never tabs. Indentation is the entire structure of the file. If a file refuses to apply, look at indentation first.

What about namespaces, labels…?

You will meet namespaces (folders for a cluster), labels (key-value tags that Services and controllers use to select things), and annotations (non-selecting metadata) properly in Chapter 6 (Best Practices). For now, absorb this chapter's ten objects: Pod, Node, Cluster, Deployment, ReplicaSet, Service, ClusterIP/NodePort/LoadBalancer, ConfigMap, Secret.
