Best Practices, Pitfalls & Real-World Use Cases

Best practices

1. Keep nodes small and single-purpose

A node should do one thing: "extract fields", "validate", "generate draft", "run tool". Small nodes are easy to unit test and rerun. If a node has three if branches switching between LLM and logic paths, split it.

2. Design the state schema up front

State is your contract between nodes. Keep it explicit and typed, and only store what other nodes actually need. For fields that grow, use reducers:

from typing import Annotated, TypedDict
from operator import add
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]   # append, never overwrite
    scores: Annotated[list[float], add]       # accumulate numbers

3. Guard every loop

LLM routing is probabilistic — always bound recursion and iteration counts:

result = app.invoke(
    {"messages": [HumanMessage("...")]},
    config={"recursion_limit": 25},   # hard cap on graph steps
)

For loops you write yourself (like the research node in Chapter 4), add a for _ in range(MAX_STEPS) guard and break once the answer is final.

4. Use checkpointing for memory and human-in-the-loop

A checkpointer persists state after every super-step. Give it a thread_id and multi-turn conversations "remember" prior turns; you can also extract state mid-run for human approval before continuing. This is one of LangGraph's killer features.

from langgraph.checkpoint.memory import InMemorySaver

app = graph.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "user-42"}}
app.invoke({"messages": [HumanMessage("Hi, I'm Aisha")]}, config=config)
app.invoke({"messages": [HumanMessage("What's my name?")]}, config=config)  # remembers
In-memory state is lost on restart. For persistence across processes use langgraph-checkpoint-postgres (or SQLite). To fetch/set state for approvals: app.get_state(config) and app.update_state(config, values).

5. Stream for good UX

For chat products, don't wait for the whole graph. Stream tokens or node updates:

for chunk in app.stream({"messages": [msg]}, config, stream_mode="messages"):
    print(chunk[0].content, end="")   # token-by-token

6. Prefer deterministic routing over LLM routing

Use rules, validators, and regex where possible; reserve the LLM for judgment calls. Deterministic routers are free, fast, and auditable. Example: route to "human" only if an API error occurred or a required field is empty.

7. Test with real traces and an eval set

Use LangSmith to trace runs, then build a small dataset of inputs with expected outcomes and run evaluation after every change to your prompts or graph structure. Agent changes are easy to overfit — evals keep you honest.

8. Choose models per node and control cost

Use a cheap, fast model for routing and extraction; use a stronger model only for the node where quality matters (e.g., final summary). Cache identical tool results.

Common pitfalls

PitfallSymptomFix
Overwriting instead of appendingChat history shrinks to one message per runAdd add_messages reducer to messages
Missing END edgeGraph fails to compile with "orphaned" nodesEvery node reaches END via an edge or conditional path
No recursion guardCost explosion or timeout on a tricky promptSet recursion_limit; add step counters in hand-rolled loops
Mutating state in placeUnexpected values when nodes rerun (retries)Nodes must return partial updates; don't mutate the input dict
Unhandled tool errorsRun dies on a 404 or malformed JSONWrap tool bodies in try/except and return an error ToolMessage so the LLM can recover
Context window overflowErrors after long conversationsTrim/condense history (trim_messages) or summarize older turns into a running summary
Leaking secrets to the modelAPI keys appear in prompts or tracesNever put credentials in state/messages; redact tool inputs
Naive parallelismDuplicate work or race conditionsUse explicit fan-out with Send only when workers are independent

Real-world use cases

  • Support ticket triage — classify intent, search the wiki, draft a reply; escalate to a human with full context when confidence is low.
  • RAG researcher + reviewer — a researcher agent gathers sources and a reviewer agent checks citations and flags hallucination risks before an answer ships.
  • Code review / code-fix agents — run static analysis, propose diffs, apply tests, and loop until the test suite passes (bounded by recursion limit).
  • Finance document workflows — extract fields from invoices, validate them against rules, and pause for human approval before payment — checkpointing makes each stage resumable.
  • Content production pipelines — outline generation → research → drafting → fact-check → formatting as a multi-agent graph.
  • Multi-step automation — booking, forms, and browser automation where an agent decides actions, a tools agent executes, and a validator confirms completion.

Companies such as GitHub (Copilot pull-request agents), LinkedIn (feed summarization), and numerous enterprises use LangGraph in production for exactly these patterns.
