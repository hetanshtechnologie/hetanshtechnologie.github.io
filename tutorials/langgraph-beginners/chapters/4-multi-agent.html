Multi-Agent Workflow: Research + Summarizer

Single agents are great for one task. But real applications decompose work: a research agent gathers raw material; a summarizer agent condenses it; a formatter agent publishes it. In LangGraph you compose agents as nodes in one graph, and they communicate by reading and updating the shared state.

Key idea: agents don't call each other directly. Agent 1 writes results into state; agent 2 reads them on the next edge. This decoupling makes each agent independently testable and swappable.

Running example: explain a technical topic

We reuse one chat model, but give each node a different system prompt so each behaves like a specialist "agent". The state carries three fields: topic (input), research_notes (written by agent 1), and final_summary (written by agent 2).

from typing import TypedDict
from langchain_core.messages import SystemMessage, HumanMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END
from dotenv import load_dotenv
load_dotenv()

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

class WorkflowState(TypedDict):
    topic: str
    research_notes: str
    final_summary: str

# --- Agent 1: Research ---
def research_node(state: WorkflowState):
    system = SystemMessage(
        "You are a research agent. Collect detailed factual notes about the topic: "
        "key concepts, how it works, and a concrete example. Do not summarize yet."
    )
    user = HumanMessage(f"Topic: {state['topic']}")
    notes = model.invoke([system, user]).content
    return {"research_notes": notes}          # <-- communicate via state

# --- Agent 2: Summarizer ---
def summarize_node(state: WorkflowState):
    system = SystemMessage(
        "You are a summarization agent. From the research notes, write a concise, "
        "beginner-friendly summary of at most 150 words."
    )
    user = HumanMessage(f"Research notes:\n{state['research_notes']}")
    summary = model.invoke([system, user]).content
    return {"final_summary": summary}

# --- Wire the pipeline ---
graph = StateGraph(WorkflowState)
graph.add_node("research", research_node)
graph.add_node("summarize", summarize_node)
graph.add_edge(START, "research")
graph.add_edge("research", "summarize")      # agent 1 hands off to agent 2
graph.add_edge("summarize", END)

app = graph.compile()

result = app.invoke({"topic": "Retrieval-Augmented Generation (RAG)"})
print(result["final_summary"])

Notice the execution order: research fills research_notes, then summarize reads it via state["research_notes"] and writes final_summary. Two LLM calls, one graph, clean handoff.

Upgrade 1: give the research agent tools (a loop inside a node)

A node can be as smart as you like. Instead of one plain LLM call, make research a tool-calling loop over an internal knowledge base — the same pattern as Chapter 3, but contained inside a single node of the outer graph.

from langchain_core.tools import tool
from langchain_core.messages import ToolMessage

@tool
def fetch_fact(concept: str) -> str:
    """Fetch background facts about a concept from our internal knowledge base."""
    kb = {
        "rag": "RAG retrieves relevant documents, embeds them, and augments the prompt "
               "with them before generation to reduce hallucination.",
        "embedding": "An embedding maps text to a dense vector; similar texts are near "
                     "each other in vector space.",
        "vector": "A vector database stores embeddings and returns nearest neighbors.",
    }
    return kb.get(concept.lower(), f"No entry found for '{concept}'.")

model_with_tools = ChatOpenAI(model="gpt-4o-mini", temperature=0).bind_tools([fetch_fact])

def research_agent_node(state: WorkflowState):
    messages = [
        SystemMessage("Research agent. Use fetch_fact to gather facts you need, "
                      "then produce detailed notes."),
        HumanMessage(f"Topic: {state['topic']}"),
    ]
    for _ in range(5):                       # guard against infinite loops
        ai_msg = model_with_tools.invoke(messages)
        messages.append(ai_msg)
        if not ai_msg.tool_calls:
            break
        for tc in ai_msg.tool_calls:
            result = fetch_fact.invoke(tc["args"])
            messages.append(ToolMessage(content=result, tool_call_id=tc["id"]))
    return {"research_notes": messages[-1].content}

graph = StateGraph(WorkflowState)
graph.add_node("research", research_agent_node)
graph.add_node("summarize", summarize_node)
graph.add_edge(START, "research")
graph.add_edge("research", "summarize")
graph.add_edge("summarize", END)
app = graph.compile()

Now agent 1 reasons, calls fetch_fact, observes results, and loops until confident — then hands its notes to agent 2. In production, replace fetch_fact with Tavily/SerpAPI web search, a SQL query, or a vector-store lookup.

Upgrade 2: a supervisor for dynamic routing

When the flow depends on the content, add a third node that decides the next step via a conditional edge. This is the classic supervisor pattern.

def needs_more_research(state: WorkflowState) -> str:
    # Rich enough? Deterministic check on the notes.
    if state["research_notes"] and len(state["research_notes"]) > 200:
        return "summarize"
    return "research"     # go back and gather more

graph = StateGraph(WorkflowState)
graph.add_node("research", research_node)
graph.add_node("summarize", summarize_node)
graph.add_edge(START, "research")
graph.add_conditional_edges("research", needs_more_research,
                            {"research": "research", "summarize": "summarize"})
graph.add_edge("summarize", END)
app = graph.compile()
Supervisor variants: the routing function can be deterministic (token counts, validation rules) or an LLM (a small classifier). Hand-rolled routing is cheaper, faster, and fully auditable — prefer it when a rule works.

How the agents "talk" to each other

MechanismDescriptionWhen to use
Shared stateAgent A writes state["research_notes"]; agent B reads it later.Pipeline workflows; structured handoff (most common).
Messages listAgents append AIMessages/ToolMessages to messages with add_messages.Conversational agents that must see full history.
Supervisor routingA router node chooses the next agent based on content.Dynamic, multi-skill routing (support vs. billing vs. sales).
Parallel fan-outSeveral worker nodes run concurrently for the same input (e.g. one per region).Speed-ups: same task split across workers.

Why this scales

  • Each agent node is a plain function — test it in isolation with a fixture state.
  • Swap LLM providers per node: use a cheap model for research, a stronger one for final summary.
  • Add checkpointing (Chapter 5) so the pipeline can stop, resume, and be human-reviewed between agents.
