1. What Modules Are and Why to Use Them

Every Terraform configuration you write is already a module — the root module. A child module is a separate directory of Terraform files that is invoked by another configuration.

┌──────────────────────────────────────────────────────┐
│                   Root Module                        │
│  main.tf  variables.tf  outputs.tf                  │
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐   │
│  │ module   │  │ module   │  │ module           │   │
│  │ "vnet"   │  │ "aks"    │  │ "monitoring"     │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────────────┘   │
└───────┼──────────────┼─────────────┼────────────────┘
        │              │             │
   ┌────▼─────┐  ┌─────▼────┐  ┌────▼────────┐
   │ VNet     │  │ AKS      │  │ Monitoring   │
   │ Module   │  │ Module   │  │ Module       │
   │ (local)  │  │ (Reg.)   │  │ (Git)        │
   └──────────┘  └──────────┘  └──────────────┘

Key benefits of modules:

  • Reusability — Write once, use in many environments.
  • Encapsulation — Hide implementation details behind clean interfaces.
  • Consistency — Enforce standards (naming, tags, security) centrally.
  • Testability — Isolate and test infrastructure components independently.
  • Maintainability — Fix a bug once, propagate everywhere.

2. Module Structure

A well-structured module mirrors the root module convention:

modules/
  azure-vnet/
    main.tf            # Core resource definitions
    variables.tf       # Input variable declarations
    outputs.tf         # Output value declarations
    versions.tf        # Required providers and version constraints
    README.md          # Usage documentation
    examples/          # Minimal working examples
      complete/
        main.tf
    tests/             # Automated tests
      vnet_test.go

variables.tf — Declaring Inputs

variable "resource_group_name" {
  description = "Name of the resource group"
  type        = string

  validation {
    condition     = length(var.resource_group_name) > 0 && length(var.resource_group_name) <= 90
    error_message = "Resource group name must be 1-90 characters."
  }
}

variable "address_space" {
  description = "Address space for the virtual network"
  type        = list(string)
  default     = ["10.0.0.0/16"]
}

variable "subnets" {
  description = "Map of subnet configurations"
  type = map(object({
    address_prefixes  = list(string)
    service_endpoints = optional(list(string), [])
    delegation = optional(object({
      name    = string
      service = string
    }))
  }))
}

variable "tags" {
  description = "Tags to apply to all resources"
  type        = map(string)
  default     = {}
}

main.tf — Core Resources

resource "azurerm_resource_group" "this" {
  name     = var.resource_group_name
  location = var.location
  tags     = var.tags
}

resource "azurerm_virtual_network" "this" {
  name                = "${var.resource_group_name}-vnet"
  location            = azurerm_resource_group.this.location
  resource_group_name = azurerm_resource_group.this.name
  address_space       = var.address_space
  tags                = var.tags
}

resource "azurerm_subnet" "this" {
  for_each = var.subnets

  name                 = each.key
  resource_group_name  = azurerm_resource_group.this.name
  virtual_network_name = azurerm_virtual_network.this.name
  address_prefixes     = each.value.address_prefixes
  service_endpoints    = each.value.service_endpoints

  dynamic "delegation" {
    for_each = each.value.delegation != null ? [each.value.delegation] : []
    content {
      name = delegation.value.name
      service_delegation {
        name = delegation.value.service
      }
    }
  }
}

outputs.tf — Exporting Values

output "vnet_id" {
  description = "Resource ID of the virtual network"
  value       = azurerm_virtual_network.this.id
}

output "vnet_name" {
  description = "Name of the virtual network"
  value       = azurerm_virtual_network.this.name
}

output "subnet_ids" {
  description = "Map of subnet name to resource ID"
  value       = { for k, v in azurerm_subnet.this : k => v.id }
}

3. Creating a Custom Module — Azure VNet Example

Let's build a production-ready VNet module from scratch. The module will support subnets, peering, NSGs, and flow logs.

Full Module Layout

modules/
  azure-vnet/
    main.tf
    variables.tf
    outputs.tf
    versions.tf
    nsg.tf
    flow-log.tf
    peering.tf
    README.md

versions.tf

terraform {
  required_version = ">= 1.5"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.80"
    }
  }
}

nsg.tf — Network Security Group

resource "azurerm_network_security_group" "this" {
  count = var.create_nsg ? 1 : 0

  name                = "${azurerm_virtual_network.this.name}-nsg"
  location            = azurerm_resource_group.this.location
  resource_group_name = azurerm_resource_group.this.name
  tags                = var.tags
}

resource "azurerm_network_security_rule" "rules" {
  for_each = var.create_nsg ? { for r in var.nsg_rules : r.name => r } : {}

  name                        = each.value.name
  priority                    = each.value.priority
  direction                   = each.value.direction
  access                      = each.value.access
  protocol                    = each.value.protocol
  source_port_range           = each.value.source_port_range
  destination_port_range      = each.value.destination_port_range
  source_address_prefix       = each.value.source_address_prefix
  destination_address_prefix  = each.value.destination_address_prefix
  resource_group_name         = azurerm_resource_group.this.name
  network_security_group_name = azurerm_network_security_group.this[0].name
}

flow-log.tf — Network Flow Logs

resource "azurerm_network_watcher_flow_log" "this" {
  count = var.enable_flow_logs ? 1 : 0

  name                      = "${azurerm_virtual_network.this.name}-flowlog"
  network_watcher_name      = var.network_watcher_name
  resource_group_name       = var.network_watcher_resource_group
  network_security_group_id = azurerm_network_security_group.this[0].id
  storage_account_id        = var.flow_log_storage_account_id
  enabled                   = true
  version                   = 2

  retention_policy {
    enabled = true
    days    = var.flow_log_retention_days
  }

  traffic_analytics {
    enabled               = true
    workspace_id          = var.log_analytics_workspace_id
    workspace_region      = var.location
    workspace_resource_id = var.log_analytics_resource_id
    interval_in_minutes   = 10
  }
}

peering.tf — VNet Peering

resource "azurerm_virtual_network_peering" "this" {
  for_each = var.peerings

  name                      = each.key
  resource_group_name       = azurerm_resource_group.this.name
  virtual_network_name      = azurerm_virtual_network.this.name
  remote_virtual_network_id = each.value.remote_vnet_id
  allow_forwarded_traffic   = each.value.allow_forwarded_traffic
  allow_gateway_transit     = each.value.allow_gateway_transit
  use_remote_gateways       = each.value.use_remote_gateways
}

Calling the Module

module "hub_vnet" {
  source = "../../modules/azure-vnet"

  resource_group_name = "rg-network-hub"
  location            = "eastus"
  address_space       = ["10.0.0.0/16"]

  subnets = {
    "firewall" = {
      address_prefixes  = ["10.0.1.0/24"]
      service_endpoints = []
    }
    "management" = {
      address_prefixes  = ["10.0.2.0/24"]
      service_endpoints = ["Microsoft.KeyVault"]
    }
  }

  create_nsg = true
  nsg_rules = [
    {
      name                       = "AllowHTTPS"
      priority                   = 100
      direction                  = "Inbound"
      access                     = "Allow"
      protocol                   = "Tcp"
      source_port_range          = "*"
      destination_port_range     = "443"
      source_address_prefix      = "*"
      destination_address_prefix = "*"
    }
  ]

  tags = {
    environment = "production"
    cost-center = "networking"
  }
}

4. Calling Modules

Modules are invoked with the module block. The block name is a local identifier unique in the current configuration.

Basic Call with Source

module "vnet" {
  source = "./modules/azure-vnet"

  resource_group_name = "rg-app-prod"
  subnets             = local.subnet_config
}

Using for_each

Create multiple instances from a map — ideal for multi-region or multi-environment deployments:

variable "environments" {
  type = map(object({
    location    = string
    address_space = list(string)
  }))
  default = {
    dev = {
      location      = "eastus"
      address_space = ["10.1.0.0/16"]
    }
    staging = {
      location      = "westus2"
      address_space = ["10.2.0.0/16"]
    }
    prod = {
      location      = "eastus"
      address_space = ["10.0.0.0/16"]
    }
  }
}

module "vnet" {
  source   = "./modules/azure-vnet"
  for_each = var.environments

  resource_group_name = "rg-network-${each.key}"
  location            = each.value.location
  address_space       = each.value.address_space
}

Using count

Conditionally create module instances:

module "logging" {
  source   = "./modules/logging"
  count    = var.enable_central_logging ? 1 : 0

  log_analytics_sku  = "PerGB2018"
  retention_in_days  = 90
}

Passing Outputs Between Modules

module "vnet" {
  source = "./modules/azure-vnet"
  # ...
}

module "aks" {
  source = "./modules/azure-aks"

  subnet_id = module.vnet.subnet_ids["aks"]
  vnet_id   = module.vnet.vnet_id
}
Tip: Always reference module outputs with the full path (module.vnet.subnet_ids) — never reference resources inside the module directly.

5. Module Sources

Terraform supports several source types for loading modules:

┌─────────────────┬──────────────────────────────────────────────┐
│ Source Type      │ Example                                      │
├─────────────────┼──────────────────────────────────────────────┤
│ Local path       │ source = "./modules/azure-vnet"              │
│ Terraform Reg.   │ source = "Azure/aks/azurerm"                 │
│ GitHub           │ source = "github.com/org/repo//modules/vnet" │
│ Git              │ source = "git::https://...//modules/vnet"    │
│ HTTP URL         │ source = "https://example.com/module.zip"    │
│ S3 Bucket        │ source = "s3::bucket-name/module.zip"        │
│ GCS Bucket       │ source = "gcs::bucket-name/module.zip"       │
└─────────────────┴──────────────────────────────────────────────┘

Local Path

module "vnet" {
  source = "./modules/azure-vnet"
  # ...
}

GitHub Source

module "vnet" {
  source = "github.com/contoso/terraform-modules//azure-vnet?ref=v2.1.0"
  # ...
}

Git Source with Subdirectories

module "vnet" {
  source = "git::https://github.com/contoso/terraform-modules.git?ref=v2.1.0//modules/azure-vnet"
  # ...
}

HTTP Source

module "vnet" {
  source = "https://releases.contoso.com/modules/azure-vnet/2.1.0.zip"
  # ...
}

6. Terraform Registry

The Terraform Registry is the public catalog of community and official modules.

Public Registry

module "aks" {
  source  = "Azure/aks/azurerm"
  version = "~> 8.0"
  # ...
}

Private Registry (Terraform Cloud / Enterprise)

module "vnet" {
  source  = "app.terraform.io/my-org/vnet/azure"
  version = "~> 2.0"
  # ...
}

Registering Your Own Module

  1. Create a Git repository with the module source.
  2. Tag releases with semantic versions (e.g., v1.0.0).
  3. On Terraform Cloud, connect the workspace and add to the module registry.
  4. For public publishing, submit to the HashiCorp Terraform Registry via GitHub.
Tip: Official modules from the hashicorp or cloud-provider namespaces are reviewed for quality and security. Prefer them over unknown third-party modules.

7. Module Versioning Best Practices

Use Semantic Versioning for all modules:

┌────────────┬────────────────────────────────────────────────┐
│ Version    │ What it means                                  │
├────────────┼────────────────────────────────────────────────┤
│ v1.0 → 1.1 │ New feature, backward-compatible              │
│ v1.1 → 2.0 │ Breaking change (renamed variables, removed   │
│             │ outputs, changed resource types)              │
│ v1.1 → 1.2 │ Bug fix, security patch                       │
└────────────┴────────────────────────────────────────────────┘

Version Constraints

module "vnet" {
  source  = "./modules/azure-vnet"
  version = "~> 2.1"     # Allows 2.1.0 through 2.x.x, but not 3.0
}

module "aks" {
  source  = "Azure/aks/azurerm"
  version = ">= 8.0, < 9.0"   # Range constraint
}

module "firewall" {
  source  = "Azure/firewall/azurerm"
  version = "~> 5.0"    # Patch-level constraint
}

Best Practices

  • Never update module versions in production without running terraform plan first.
  • Pin to a minimum version with ~> to receive compatible updates.
  • Test new versions in a dev/staging environment before promoting.
  • Maintain a CHANGELOG.md in every module repository.
  • Use terraform init -upgrade to update lock files deliberately.

8. Module Composition Patterns

Modules can be composed in different topologies depending on your architecture.

Pattern 1: Flat Composition

All modules called from the root, no inter-module nesting:

root/
  main.tf calls → module.vnet
                 module.aks
                 module.database

Pattern 2: Layered / Nested Composition

A higher-level module composes other modules:

root/main.tf → module.environment
                 ├── module.vnet
                 ├── module.aks
                 └── module.monitoring

# modules/environment/main.tf
module "vnet" {
  source = "../azure-vnet"
  # ...
}

module "aks" {
  source = "../azure-aks"
  subnet_id = module.vnet.subnet_ids["aks"]
}

module "monitoring" {
  source = "../azure-monitoring"
  vnet_id = module.vnet.vnet_id
}

Pattern 3: Stack-Based Composition

Separate root modules per concern (network, compute, data):

terraform/
  stack-network/
    main.tf → module.vnet
  stack-compute/
    main.tf → module.aks, module.vmss
  stack-data/
    main.tf → module.cosmosdb, module.redis
  stack-bootstrap/
    main.tf → module.resource_groups, module.locks

Pattern 4: Environment Modules

Different root configurations per environment, calling shared modules:

envs/
  dev/main.tf       → module "base" { source = "../../modules/base-stack" ... }
  staging/main.tf   → module "base" { source = "../../modules/base-stack" ... }
  prod/main.tf      → module "base" { source = "../../modules/base-stack" ... }

9. Testing Modules

Testing modules ensures correctness before they're consumed by other configurations.

Using terraform validate and plan

cd modules/azure-vnet
terraform init
terraform validate
terraform plan -var-file="examples/complete/terraform.tfvars"

Using Terratest (Go-based Integration Tests)

package test

import (
    "testing"
    "github.com/gruntwork-io/terratest/modules/terraform"
    "github.com/stretchr/testify/assert"
)

func TestAzureVNetModule(t *testing.T) {
    t.Parallel()

    terraformOptions := terraform.WithDefaultRetryableErrors(t, &terraform.Options{
        TerraformDir: "../examples/complete",
        Vars: map[string]interface{}{
            "resource_group_name": "rg-test-vnet",
            "address_space":       []string{"10.99.0.0/16"},
        },
    })

    defer terraform.Destroy(t, terraformOptions)
    terraform.InitAndApply(t, terraformOptions)

    vnetId := terraform.Output(t, terraformOptions, "vnet_id")
    assert.Contains(t, vnetId, "rg-test-vnet")

    subnetIds := terraform.OutputMap(t, terraformOptions, "subnet_ids")
    assert.Contains(t, subnetIds, "firewall")
    assert.Contains(t, subnetIds, "management")
}

Using Terraform Test (Native)

Since Terraform 1.6, native testing is built in:

# tests/vnet.tftest.hcl
variables {
  resource_group_name = "rg-test"
  address_space       = ["10.0.0.0/16"]
  subnets = {
    "web" = {
      address_prefixes  = ["10.0.1.0/24"]
      service_endpoints = []
    }
  }
}

run "vnet_created" {
  command = apply

  assert {
    condition     = module.vnet.vnet_name != ""
    error_message = "VNet name should not be empty"
  }

  assert {
    condition     = contains(keys(module.vnet.subnet_ids), "web")
    error_message = "Web subnet should exist"
  }
}

# Run native tests
terraform test
Tip: Always include an examples/ directory in your module. It serves as both documentation and a smoke-test target.

10. Summary & Checklist

Key Takeaways

  • A module is any directory containing .tf files with inputs, resources, and outputs.
  • Use modules to enforce consistency, enable reuse, and simplify complex configurations.
  • Pin module versions and use semantic versioning.
  • Prefer Terraform Registry modules when available; create private modules for internal patterns.
  • Test modules with examples, native tests, or Terratest before publishing.

Common Mistakes to Avoid

  • Hardcoding values inside modules instead of accepting inputs.
  • Referencing module resources directly from the root module (always use outputs).
  • Not pinning module versions — a breaking change can break all consumers.
  • Overly large modules that do too many things (single responsibility).
  • Ignoring terraform fmt and terraform validate in CI.
