1. Why CI/CD for Terraform

Running terraform apply from your laptop works for experiments. The moment infrastructure supports production workloads — databases serving traffic, DNS records pointed at your clusters, TLS certificates encrypting customer data — manual, developer-machine-driven workflows become a serious liability. CI/CD pipelines for Terraform address five core problems:

ProblemWithout CI/CDWith CI/CD
ConsistencyEach developer uses a different Terraform version, different env vars, different OS.Locked tool versions and a reproducible runner environment.
Auditability"Who applied this?" — nobody knows. Maybe it was a late-night Slack request.Every apply is tied to a PR, a commit SHA, and an identity.
Review gatesOne person pushes production changes with no second set of eyes.PRs require approvals; plan output is visible before merge.
SecurityCredentials stored in ~/.aws/credentials or env vars on dev laptops.Short-lived tokens via OIDC federation; no long-lived secrets in repos.
Speed & collaborationTerraform locks block the whole team; one person at a time.Remote state + locking + pipeline concurrency controls.
Key principle: The pipeline, not a human, is the entity that touches production infrastructure. Humans propose changes; the pipeline applies them.

The general flow

 Developer                CI/CD Pipeline              Cloud Provider
 ─────────                ──────────────              ──────────────
 git push / PR
    │
    ├──── Trigger ──────────►  terraform fmt -check
    │                          terraform validate
    │                          terraform init
    │                          terraform plan -out=tfplan
    │                          security scan
    │                          policy check
    │
    │                     ◄─── Post plan output to PR
    │
    │  Code review + approval
    │
    ├── Merge to main ────►  terraform apply tfplan
    │                          (apply the EXACT plan)
    │
    │                     ◄─── State updated, resources created
    │
    ├── Scheduled cron ───►  terraform plan (drift check)
    │                          alert if unexpected changes

2. Plan/Apply Separation

This is the single most important concept in Terraform CI/CD. Without it, every other piece of the pipeline is theatre.

Why separate plan and apply?

If you run terraform apply -auto-approve in a pipeline, the plan and apply happen atomically. There is no opportunity for a human to review what will happen before it does happen. This is dangerous because:

  • Terraform's HCL is declarative but sometimes non-obvious — a for_each over a data source could delete resources you did not expect.
  • A provider bug or upstream API change could cause Terraform to propose destructive actions.
  • Malicious or accidental changes to code could destroy production databases.

The -out flag

The -out flag serializes the plan to a binary file. That file contains the exact actions Terraform will take. When you later run terraform apply tfplan, Terraform executes only those serialized actions — it does not re-plan. If anything in the configuration or state has changed since the plan was created, Terraform rejects the file.

# Step 1: Create a saved plan
terraform plan -out=tfplan

# Step 2: Apply the EXACT saved plan
terraform apply tfplan
Never run terraform apply -auto-approve in a CI pipeline that handles production infrastructure. Always save the plan, present it for review, and then apply the exact plan file.

What happens if state changed between plan and apply?

$ terraform apply tfplan
Error: Saved plan is stale

The given plan file was created by a different Terraform core
version or the state has changed since it was created. The plan
file cannot be applied.

This safety net ensures the apply matches the reviewed plan exactly.

Plan output format options

FormatFlagUse case
Human-readable (default)stdoutPR comments, terminal output
Binary plan file-out=tfplanExact replay during apply
JSON plan-jsonMachine parsing, policy checks, custom tooling
Exercise: Run terraform plan -out=tfplan, then run terraform show -json tfplan to see the JSON representation. Try modifying a resource in your config, then running terraform apply tfplan — notice Terraform refuses the stale plan.

3. GitHub Actions

GitHub Actions is the most common CI/CD platform for open-source and private Terraform repositories. Below is a complete, production-ready workflow.

Complete Workflow

# .github/workflows/terraform.yml
name: Terraform

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  id-token: write   # Required for OIDC
  contents: read
  pull-requests: write

env:
  ARM_USE_OIDC: "true"
  ARM_TENANT_ID: ${{ secrets.AZURE_TENANT_ID }}
  ARM_SUBSCRIPTION_ID: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
  ARM_CLIENT_ID: ${{ secrets.AZURE_CLIENT_ID }}
  TF_VERSION: "1.9.8"

jobs:
  terraform:
    name: Terraform ${{ github.event_name }}
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - name: Terraform Format Check
        run: terraform fmt -check -recursive
        working-directory: infra/

      - name: Terraform Init
        run: terraform init -backend-config="resource_group_name=${{ secrets.STATE_RG }}" -backend-config="storage_account_name=${{ secrets.STATE_SA }}"
        working-directory: infra/

      - name: Terraform Validate
        run: terraform validate -no-color
        working-directory: infra/

      # --- PR path: plan only ---
      - name: Terraform Plan
        if: github.event_name == 'pull_request'
        id: plan
        run: |
          terraform plan -no-color -out=tfplan 2>&1 | tee plan.txt
          echo "plan_exit_code=$?" >> "$GITHUB_OUTPUT"
        working-directory: infra/
        continue-on-error: true

      - name: Comment Plan on PR
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('infra/plan.txt', 'utf8');
            const truncated = plan.length > 60000
              ? plan.substring(0, 60000) + '\n\n... (truncated)'
              : plan;
            const body = `### Terraform Plan
            \`\`\`\n${truncated}\n\`\`\`
            *Triggered by @${context.actor} on \`${context.sha.substring(0, 7)}\`*`;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: body
            });

      - name: Fail if Plan Failed
        if: github.event_name == 'pull_request' && steps.plan.outputs.plan_exit_code != '0'
        run: exit 1

      # --- Push to main: apply ---
      - name: Terraform Apply
        if: github.event_name == 'push'
        run: terraform apply -auto-approve -input=false tfplan
        working-directory: infra/

OIDC Authentication to Azure

The workflow above uses OpenID Connect (OIDC) federation instead of long-lived service principal secrets. Setup steps:

  1. Create an Azure AD App Registration and Service Principal.
  2. Add a federated credential in Azure: subject = repo:OWNER/REPO:ref:refs/heads/main.
  3. Grant the Service Principal the necessary roles on your subscription (e.g., Contributor).
  4. Store AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID, and AZURE_CLIENT_ID as GitHub Actions secrets.
# Create the federated credential via Azure CLI
az ad app federated-credential create \
  --name "github-terraform-main" \
  --id "<app-registration-id>" \
  --parameters '{
    "name": "github-terraform-main",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:myorg/myrepo:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'
Why OIDC? OIDC tokens are short-lived (typically 10 minutes), scoped to the repository and branch, and require no secrets to be stored in GitHub. This is significantly more secure than storing a ARM_CLIENT_SECRET in your repository secrets.

Reusable Terraform Module Workflow

For repositories with multiple Terraform directories, use a matrix strategy:

jobs:
  terraform:
    strategy:
      matrix:
        directory: [infra/networking, infra/compute, infra/database]
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
        working-directory: ${{ matrix.directory }}
      - run: terraform plan -out=tfplan
        working-directory: ${{ matrix.directory }}

4. Azure DevOps

Azure DevOps Pipelines is a natural fit for teams already invested in the Microsoft ecosystem. It supports YAML pipelines, approval gates, and service connections with managed identities.

Complete Azure DevOps Pipeline

# azure-pipelines.yml
trigger:
  branches:
    include:
      - main
      - 'feature/*'

pr:
  branches:
    include:
      - main

variables:
  - name: terraformVersion
    value: '1.9.8'
  - name: tfWorkingDirectory
    value: 'infra'
  - name: serviceConnection
    value: 'azure-terraform-sc'  # Service connection name

stages:
  # ── STAGE 1: Validate ──────────────────────────────────
  - stage: Validate
    displayName: 'Validate Terraform'
    jobs:
      - job: validate
        displayName: 'Fmt, Init, Validate'
        pool:
          vmImage: 'ubuntu-latest'
        steps:
          - task: TerraformInstaller@1
            displayName: 'Install Terraform'
            inputs:
              terraformVersion: $(terraformVersion)

          - task: TerraformTaskV4@4
            displayName: 'Terraform Init'
            inputs:
              provider: 'azurerm'
              command: 'init'
              workingDirectory: $(tfWorkingDirectory)
              backendServiceArm: $(serviceConnection)
              backendAzureRmResourceGroupName: 'tfstate-rg'
              backendAzureRmStorageAccountName: 'tfstatestore'
              backendAzureRmContainerName: 'tfstate'
              backendAzureRmKey: 'pipeline.tfstate'

          - bash: |
              terraform fmt -check -recursive
            displayName: 'Terraform Format Check'
            workingDirectory: $(tfWorkingDirectory)

          - task: TerraformTaskV4@4
            displayName: 'Terraform Validate'
            inputs:
              provider: 'azurerm'
              command: 'validate'
              workingDirectory: $(tfWorkingDirectory)
              environmentServiceNameAzureRM: $(serviceConnection)

  # ── STAGE 2: Plan ──────────────────────────────────────
  - stage: Plan
    displayName: 'Terraform Plan'
    dependsOn: Validate
    jobs:
      - job: plan
        displayName: 'Generate Plan'
        pool:
          vmImage: 'ubuntu-latest'
        steps:
          - task: TerraformInstaller@1
            displayName: 'Install Terraform'
            inputs:
              terraformVersion: $(terraformVersion)

          - task: TerraformTaskV4@4
            displayName: 'Terraform Init'
            inputs:
              provider: 'azurerm'
              command: 'init'
              workingDirectory: $(tfWorkingDirectory)
              backendServiceArm: $(serviceConnection)
              backendAzureRmResourceGroupName: 'tfstate-rg'
              backendAzureRmStorageAccountName: 'tfstatestore'
              backendAzureRmContainerName: 'tfstate'
              backendAzureRmKey: 'pipeline.tfstate'

          - task: TerraformTaskV4@4
            displayName: 'Terraform Plan'
            inputs:
              provider: 'azurerm'
              command: 'plan'
              workingDirectory: $(tfWorkingDirectory)
              environmentServiceNameAzureRM: $(serviceConnection)
              commandOptions: '-out=tfplan'

          - publish: $(tfWorkingDirectory)/tfplan
            artifact: 'tfplan'
            displayName: 'Publish Plan Artifact'

  # ── STAGE 3: Apply ─────────────────────────────────────
  - stage: Apply
    displayName: 'Terraform Apply'
    dependsOn: Plan
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: apply
        displayName: 'Apply Plan'
        pool:
          vmImage: 'ubuntu-latest'
        environment: 'production'   # ← Has approval gates configured
        strategy:
          runOnce:
            deploy:
              steps:
                - task: TerraformInstaller@1
                  displayName: 'Install Terraform'
                  inputs:
                    terraformVersion: $(terraformVersion)

                - task: TerraformTaskV4@4
                  displayName: 'Terraform Init'
                  inputs:
                    provider: 'azurerm'
                    command: 'init'
                    workingDirectory: $(tfWorkingDirectory)
                    backendServiceArm: $(serviceConnection)
                    backendAzureRmResourceGroupName: 'tfstate-rg'
                    backendAzureRmStorageAccountName: 'tfstatestore'
                    backendAzureRmContainerName: 'tfstate'
                    backendAzureRmKey: 'pipeline.tfstate'

                - download: current
                  artifact: 'tfplan'

                - task: TerraformTaskV4@4
                  displayName: 'Terraform Apply'
                  inputs:
                    provider: 'azurerm'
                    command: 'apply'
                    workingDirectory: $(tfWorkingDirectory)
                    environmentServiceNameAzureRM: $(serviceConnection)
                    commandOptions: '-auto-approve $(Pipeline.Workspace)/tfplan/tfplan'

Approval Gates

Azure DevOps environments let you configure approval checks before a deployment proceeds:

  1. Go to Pipelines → Environments → production → Approvals and checks.
  2. Add an Approvals check and select the approvers.
  3. Optionally add a Branch policy check to restrict which branches can deploy.
Note: The deployment job type is critical here. Regular jobs do not support Azure DevOps environments and their approval gates.

5. GitLab CI

GitLab CI/CD is popular for teams hosting on GitLab. Terraform Cloud can be used as the backend, or you can use a standard remote backend like Azure Blob Storage.

Complete .gitlab-ci.yml

# .gitlab-ci.yml
stages:
  - validate
  - plan
  - apply

variables:
  TF_ROOT: infra
  TF_STATE_NAME: default
  TF_VERSION: "1.9.8"

# ── Template for Terraform commands ───────────────────────
.terraform-base:
  image:
    name: hashicorp/terraform:${TF_VERSION}
    entrypoint: [""]
  before_script:
    - cd ${TF_ROOT}
    - terraform init
      -backend-config="resource_group_name=${STATE_RG}"
      -backend-config="storage_account_name=${STATE_SA}"

# ── Stage 1: Validate ────────────────────────────────────
fmt-check:
  extends: .terraform-base
  stage: validate
  script:
    - terraform fmt -check -recursive -diff
  allow_failure: false

validate:
  extends: .terraform-base
  stage: validate
  script:
    - terraform validate -no-color
  allow_failure: false

# ── Stage 2: Plan ────────────────────────────────────────
plan:
  extends: .terraform-base
  stage: plan
  script:
    - terraform plan -out=tfplan -no-color
    - terraform show -no-color -json tfplan > tfplan.json
  artifacts:
    paths:
      - ${TF_ROOT}/tfplan
      - ${TF_ROOT}/tfplan.json
    expire_in: 1 day
  rules:
    - if: $CI_MERGE_REQUEST_IID
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

# ── Stage 3: Apply ───────────────────────────────────────
apply:
  extends: .terraform-base
  stage: apply
  script:
    - terraform apply -auto-approve -input=false tfplan
  dependencies:
    - plan
  artifacts:
    paths:
      - ${TF_ROOT}/tfplan
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual    # ← Requires manual trigger in GitLab UI
  environment:
    name: production

GitLab-Specific Features

FeatureDescription
when: manualRequires a human to click "Play" in the GitLab UI before apply runs.
environmentTracks deployments per environment; shows history in the Operations dashboard.
ArtifactsThe tfplan file is passed between stages via GitLab's artifact mechanism.
Merge Request PipelinesPlans run automatically on MRs; apply only runs on the default branch.
Protected branchesCombine with branch protection rules to require approval before merging.
Tip: For a more integrated experience, consider GitLab's built-in Terraform state management. Set the TF_STATE_NAME variable and use the GitLab-managed Terraform state backend.

6. Atlantis

Atlantis is a Terraform-specific pull request automation tool. Unlike GitHub Actions or GitLab CI, Atlantis runs as a self-hosted server that listens for webhook events and comments on PRs with plan/apply output. It is popular in organizations that want a centralised, auditable Terraform workflow without writing custom CI/CD YAML.

How Atlantis Works

 Developer                 Atlantis Server              Cloud Provider
 ─────────                 ───────────────              ──────────────
 git push / PR
    │
    ├──── Webhook ──────────►  Detects terraform files
    │                          Runs: terraform plan
    │                          Comments plan on PR
    │
    │                     ◄─── "Plan: +3 ~1 -0"
    │
    │  Reviewer comments
    │  "atlantis apply"
    │
    ├── Webhook ───────────►  Runs: terraform apply
    │                          Comments result on PR
    │
    │                     ◄─── "Apply: +3 ~1 -0 complete"

Repo-Level Configuration

# atlantis.yaml (in repo root)
version: 3
automerge: false
parallel_plan: true
parallel_apply: false

projects:
  - name: networking
    dir: infra/networking
    workspace: default
    autoplan:
      when_modified: ["*.tf", "*.tfvars", "modules/**/*.tf"]
      enabled: true
    apply_requirements: [approved, mergeable]
    workflow: custom

  - name: compute
    dir: infra/compute
    workspace: default
    autoplan:
      when_modified: ["*.tf", "*.tfvars"]
      enabled: true
    apply_requirements: [approved]

workflows:
  custom:
    plan:
      steps:
        - init:
            extra_args: ["-backend-config=backend.hcl"]
        - run: terraform fmt -check
        - plan:
            extra_args: ["-out=$PLANFILE", "-var-file=terraform.tfvars"]
    apply:
      steps:
        - apply:
            extra_args: ["$PLANFILE"]

Atlantis vs CI/CD Pipeline Comparison

AspectAtlantisGitHub Actions / GitLab CI
InfrastructureSelf-hosted server (K8s, ECS, or VM)Managed by GitHub / GitLab
PR integrationNative — comments on PR automaticallyCustom — you write comment logic
Plan storageManaged internally (S3, GCS, etc.)Pipeline artifacts
Multi-repoSingle server handles all reposEach repo has its own workflow
LockingBuilt-in workspace locking per directoryBackend-level state locking
Custom workflowsatlantis.yaml per repoYAML pipeline files
Maintenance burdenMust maintain server, updates, permissionsLow — managed service
Note: Atlantis requires SSH keys or personal access tokens to push plan output back to PRs. Ensure your server has appropriate network access to your Git provider.

7. Security Scanning

Security scanning tools analyze Terraform configurations for misconfigurations, compliance violations, and known vulnerabilities before they reach production. Integrating these into CI/CD catches issues at the earliest possible point.

Tools Overview

ToolMaintainerPolicy LanguageStrengths
tfsecAqua Security (now Checkmarx)Rego-like rulesFast, focused on cloud provider misconfigs, native GitHub SARIF output
checkovBridgecrewPython (custom checks)Broad coverage (Terraform, CloudFormation, K8s), built-in policy library
terrascanTenableOPA/RegoDeep policy enforcement, supports 18+ IaC frameworks, Kubernetes admission control

GitHub Actions Integration

# Add these steps to your Terraform workflow

- name: tfsec Security Scan
  uses: aquasecurity/tfsec-action@v1.0.3
  with:
    working_directory: infra/
    soft_fail: false  # Set to true to warn without failing
    format: sarif      # Output format for GitHub code scanning

- name: Upload tfsec SARIF
  if: always()
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: tfsec-results.sarif

- name: Checkov Scan
  uses: bridgecrewio/checkov-action@v12
  with:
    directory: infra/
    framework: terraform
    output_format: cli,sarif
    output_file_path: checkov-results.sarif
    soft_fail: false

- name: Terrascan Scan
  uses: tenable/terrascan-action@main
  with:
    iac_type: terraform
    iac_dir: infra/
    policy_type: all
    sarif_output: terrascan-results.sarif
    fail_on: high

Sample Findings

# tfsec output example
[WARNING] azure-storage/no-public-access: Storage account should not
allow public blob access — infra/storage.tf:12
  Detected: allow_blob_public_access = true

[ERROR] azure-keyvault/no-soft-delete: Key Vault should have soft delete

Suppressing false positives

# Inline annotation (tfsec)
resource "azurerm_storage_account" "logs" {
  #tfsec:ignore:azure-storage/no-public-access  # Logs bucket intentionally public
  allow_blob_public_access = true
}

# Config file (.tfsec.yml at repo root)
---
exclude:
  - azure-keyvault/no-soft-delete    # Managed via Azure Policy
  - azure-network/enable-nsg-flow-log # Planned for Q3

8. Policy as Code

Security scanning catches misconfigurations. Policy as code goes further — it enforces organizational standards: naming conventions, tag requirements, allowed instance sizes, encryption mandates, and more. Policies are written in code, versioned alongside infrastructure, and enforced automatically.

OPA / Rego for Terraform

Open Policy Agent (OPA) with Rego is the de facto standard for Terraform policy enforcement. The conftest tool evaluates Terraform plan JSON against Rego policies.

Example Rego Policy

# policy/enforce_tags.rego
package terraform.enforce_tags

required_tags := {"environment", "owner", "cost-center"}

deny[msg] {
    resource := input.planned_values.root_module.resources[_]
    resource.type == "azurerm_resource_group"

    tags := object.get(resource.values, "tags", {})
    missing := required_tags - object.keys(tags)
    count(missing) > 0

    msg := sprintf(
        "Resource group '%s' is missing required tags: %v",
        [resource.address, missing]
    )
}

deny[msg] {
    resource := input.planned_values.root_module.resources[_]
    resource.type == "azurerm_linux_virtual_machine"

    size := resource.values.vm_size
    allowed := {"Standard_B2s", "Standard_B2ms", "Standard_D2s_v3"}
    not allowed[size]

    msg := sprintf(
        "VM '%s' uses disallowed size '%s'. Allowed: %v",
        [resource.address, size, allowed]
    )
}

Running conftest in CI

# Generate plan JSON
terraform plan -out=tfplan
terraform show -json tfplan > plan.json

# Run policy checks
conftest test plan.json --policy policy/

# Output on failure:
# FAIL - policy/enforce_tags.rego - terraform.enforce_tags
#   Resource group 'rg-prod' is missing required tags: {"cost-center"}
# FAIL - policy/enforce_tags.rego - terraform.enforce_tags
#   VM 'vm-web-01' uses disallowed size 'Standard_G2'. Allowed: {...}

Sentinel (HashiCorp Cloud Platform)

Sentinel is HashiCorp's built-in policy-as-code framework for Terraform Cloud / Enterprise. Policies are written in Sentinel (a Python-like language) and enforced at the policy set level.

# sentinel/policy-set/sentinel.hcl
schema_version = 1

import "tfplan/v2"

# Require all resources to have a "team" tag
tag_check = rule {
    all tfplan.resource_changes as _, rc {
        rc.mode is "managed" implies
        rc.change.after.tags contains "team"
    }
}

# Enforce encryption on storage accounts
storage_encrypted = rule {
    all tfplan.resource_changes as _, rc {
        rc.type is "azurerm_storage_account" implies
        rc.change.after.enable_https_traffic_only is true
    }
}

main = rule {
    tag_check and storage_encrypted
}
FeatureOPA / Rego + conftestSentinel
Runs whereAny CI/CD pipelineTerraform Cloud / Enterprise only
LanguageRego (declarative)Sentinel (Python-like)
Enforcement levelsPass/fail in pipelineadvisory, soft-mandatory, hard-mandatory
TestableYes (conftest --test)Yes (sentinel test)
CostFree / open sourceRequires HCP or TFE license
Start simple: Begin with 3-5 critical policies (required tags, encryption, no public access) and expand over time. Overly aggressive policy enforcement on day one slows adoption.

9. Drift Detection

Infrastructure drift occurs when the actual state of cloud resources diverges from what Terraform expects. Common causes:

  • Manual changes made in the cloud console ("click-ops")
  • Auto-scaling events that create resources Terraform does not manage
  • Provider-side updates that modify resource attributes
  • External tools (Azure Policy, AWS Config) that mutate resources

Scheduled Drift Detection Pipeline

# .github/workflows/drift-detection.yml
name: Drift Detection

on:
  schedule:
    - cron: '0 6 * * 1-5'  # Weekdays at 06:00 UTC
  workflow_dispatch:         # Allow manual trigger

permissions:
  id-token: write
  contents: read
  issues: write

jobs:
  detect-drift:
    name: Check for Drift
    runs-on: ubuntu-latest
    strategy:
      matrix:
        directory: [infra/networking, infra/compute, infra/database]
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.9.8"

      - name: Terraform Init
        run: terraform init
        working-directory: ${{ matrix.directory }}

      - name: Terraform Plan (drift check)
        id: plan
        run: |
          terraform plan -detailed-exitcode -no-color > plan-output.txt
          echo "exit_code=$?" >> "$GITHUB_OUTPUT"
        working-directory: ${{ matrix.directory }}
        continue-on-error: true

      - name: Create Issue on Drift
        if: steps.plan.outputs.exit_code == '2'
        uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync(
              `${process.env.WORKING_DIR}/plan-output.txt`, 'utf8'
            );
            const truncated = plan.length > 60000
              ? plan.substring(0, 60000) + '\n...truncated'
              : plan;
            await github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `⚠️ Drift detected in ${{ matrix.directory }}`,
              body: `## Infrastructure Drift Detected\n\n` +
                `**Directory:** \`${{ matrix.directory }}\`\n` +
                `**Workflow run:** ${context.serverUrl}/${context.repo.owner}/` +
                `${context.repo.repo}/actions/runs/${context.runId}\n\n` +
                `### Plan Output\n\`\`\`\n${truncated}\n\`\`\`\n\n` +
                `Review and remediate by applying the plan or reverting ` +
                `the manual change.`,
              labels: ['drift', 'infrastructure']
            });

      - name: Fail if Drift Found
        if: steps.plan.outputs.exit_code == '2'
        run: |
          echo "::error::Drift detected! Review the plan output."
          exit 1

Understanding exit codes

Exit CodeMeaningAction
0No changesEverything matches — no action needed.
1ErrorPlan failed (state lock, auth error, etc.). Investigate.
2Changes presentDrift detected — create an issue, alert the team.

Drift detection strategies

 Strategy                 Frequency        Best For
 ─────────                ─────────        ────────
 Scheduled pipeline       Daily/weekly     Small to mid-size estates
 Terraform Cloud          Built-in         Teams already on HCP/TFE
 Azure Policy + Change    Continuous       Enforcing compliance at
   Tracking                               scale
 Event-driven             On resource      Real-time alerting on
                          change           critical resources
Note: Not all drift is bad. Some provider attributes are computed and will always show differences in plan output. Use -refresh-only flag (Terraform ≥ 1.15) to check drift without proposing changes, or use ignore_changes lifecycle blocks for attributes that legitimately change outside Terraform.

10. Summary & Checklist

 Terraform CI/CD Maturity Model

 Level 0: Manual
   terraform apply from laptop
   ✗ No version control on runs
   ✗ No review process

 Level 1: Basic Pipeline
   terraform fmt + validate + plan in CI
   ✓ All changes go through PRs
   ✗ Apply still manual or unreviewed

 Level 2: Plan/Apply Separation
   Saved plans reviewed before apply
   ✓ OIDC auth, no long-lived secrets
   ✓ Plan output visible on PRs

 Level 3: Security & Policy
   tfsec / checkov / OPA in pipeline
   ✓ Automated security gates
   ✓ Policy as code enforced

 Level 4: Full Governance
   Drift detection, approval gates, audit trail
   ✓ Compliance reporting
   ✓ Continuous monitoring

Key Takeaways

  • Always separate plan and apply — save the plan with -out=tfplan, review it, then apply the exact file.
  • Use OIDC federation instead of long-lived secrets for cloud provider authentication.
  • Pin Terraform versions — specify exact versions in your pipeline and required_version constraints.
  • Run terraform fmt -check before validate to enforce consistent formatting.
  • Integrate security scanning (tfsec, checkov, terrascan) as mandatory pipeline steps — not optional.
  • Implement policy as code starting with 3-5 critical rules; expand over time.
  • Detect drift with scheduled pipeline runs; alert on divergence between expected and actual state.
  • Use approval gates — require manual approval before production applies, even on the main branch.
  • Version your state — store state in a remote backend with versioning enabled; never rely on local state.
  • Audit everything — every apply must be traceable to a PR, a commit, and an identity.
  • Test policies separately — use conftest test or sentinel test to validate policy logic before enforcing.
  • Start simple, iterate — begin with fmt/validate/plan; add security, policies, and drift detection as your team matures.
