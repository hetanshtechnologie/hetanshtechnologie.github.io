1. What Are Providers?

Providers are plugins that Terraform uses to interact with cloud platforms, SaaS providers, and other APIs. Each provider exposes resources (things you create), data sources (things you query), and configuration blocks (authentication, endpoints).

┌──────────────────────────────────────────────────────────┐
│                   Terraform Core                          │
│                                                           │
│   HCL Config ──► Plan ──► Apply                           │
│       │              ▲         │                          │
│       │              │         ▼                          │
│       ▼              │   ┌─────────────┐                  │
│ ┌───────────┐        │   │ Provider A  │ ──► Azure        │
│ │ Provider  │ ◄──────┘   │ (azurerm)   │                  │
│ │ Registry  │            ├─────────────┤                  │
│ │           │            │ Provider B  │ ──► AWS          │
│ │ terraform │            │ (aws)       │                  │
│ │   .io     │            ├─────────────┤                  │
│ └───────────┘            │ Provider C  │ ──► GCP          │
│                          │ (google)    │                  │
│                          └─────────────┘                  │
└──────────────────────────────────────────────────────────┘
ProviderRegistry AddressWhat It Manages

Key concept: When you run terraform init, Terraform downloads the provider plugins declared in your configuration and locks their versions in .terraform.lock.hcl.

2. Provider Configuration

Provider blocks configure authentication, regions, and other settings. Every provider block uses the source address and a pinned version.

2.1 Azure (azurerm)

terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}

provider "azurerm" {
  features {}

  # Authenticate via:
  # 1. az login (CLI), or
  # 2. ARM_CLIENT_ID / ARM_CLIENT_SECRET / ARM_TENANT_ID / ARM_SUBSCRIPTION_ID
}

# Optional: scope resources to a subscription
provider "azurerm" {
  alias           = "management"
  subscription_id = "00000000-0000-0000-0000-000000000000"
  features {}
}

2.2 AWS

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"

  default_tags {
    tags = {
      Environment = "production"
      ManagedBy   = "terraform"
    }
  }

  # Authenticate via:
  # 1. AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY env vars, or
  # 2. ~/.aws/credentials profile, or
  # 3. IAM role (EC2 / ECS task)
}

2.3 Google Cloud Platform

terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }
}

provider "google" {
  project = "my-gcp-project-id"
  region  = "us-central1"
  zone    = "us-central1-a"

  # Authenticate via:
  # 1. gcloud auth application-default login, or
  # GOOGLE_CREDENTIALS / GOOGLE_APPLICATION_CREDENTIALS env var
}

2.4 Version Pinning Strategies

ConstraintMeaningExample Range
= 3.1.0Exact version3.1.0
~> 3.1.0Minor & patch only3.1.x
~> 3.0Patch only3.x.x
>= 3.0, < 4.0Range3.0.0 – 3.999.999
Best practice: Use the ~> (pessimistic constraint) operator. It allows patches and minor updates but prevents major version bumps that may contain breaking changes.

3. Provider Aliases & Multi-Region

Aliases let you declare multiple instances of the same provider — useful for deploying to different regions, subscriptions, or accounts.

3.1 Azure Multi-Region Example

provider "azurerm" {
  alias           = "primary"
  subscription_id = "aaaa-1111"
  features {}
}

provider "azurerm" {
  alias           = "secondary"
  subscription_id = "bbbb-2222"
  features {}
}

resource "azurerm_resource_group" "primary" {
  provider = azurerm.primary
  name     = "rg-primary"
  location = "East US"
}

resource "azurerm_resource_group" "secondary" {
  provider = azurerm.secondary
  name     = "rg-secondary"
  location = "West US 2"
}

3.2 AWS Multi-Region Example

provider "aws" {
  alias  = "us_east"
  region = "us-east-1"
}

provider "aws" {
  alias  = "eu_west"
  region = "eu-west-1"
}

resource "aws_s3_bucket" "replica" {
  provider = aws.eu_west
  bucket   = "my-replicated-bucket-eu"
}
Important: When a provider has an alias, every resource that uses it must specify the provider argument. Omitting it will cause an error at plan time.

4. Resource Basics

Resources are the most important building blocks. Each resource block declares the resource type and a local name — together they form the resource address.

resource "<TYPE>" "<LOCAL_NAME>" {
  # configuration arguments
}
# Example:
resource "azurerm_resource_group" "main" {
  name     = "rg-demo"
  location = "East US"
}

4.1 Azure Full Stack Example

Let's build a complete VM deployment with networking:

# ─── Resource Group ──────────────────────────────
resource "azurerm_resource_group" "main" {
  name     = "rg-terraform-demo"
  location = "East US"
}

# ─── Virtual Network ─────────────────────────────
resource "azurerm_virtual_network" "main" {
  name                = "vnet-main"
  address_space       = ["10.0.0.0/16"]
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name
}

# ─── Subnet ──────────────────────────────────────
resource "azurerm_subnet" "frontend" {
  name                 = "snet-frontend"
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.main.name
  address_prefixes     = ["10.0.1.0/24"]
}

# ─── Network Security Group ──────────────────────
resource "azurerm_network_security_group" "web" {
  name                = "nsg-web"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name

  security_rule {
    name                       = "Allow-SSH"
    priority                   = 100
    direction                  = "Inbound"
    access                     = "Allow"
    protocol                   = "Tcp"
    source_port_range          = "*"
    destination_port_range     = "22"
    source_address_prefix      = "203.0.113.0/24"
    destination_address_prefix = "*"
  }

  security_rule {
    name                       = "Allow-HTTP"
    priority                   = 110
    direction                  = "Inbound"
    access                     = "Allow"
    protocol                   = "Tcp"
    source_port_range          = "*"
    destination_port_range     = "80"
    source_address_prefix      = "*"
    destination_address_prefix = "*"
  }

  tags = {
    environment = "demo"
  }
}

# ─── Public IP ───────────────────────────────────
resource "azurerm_public_ip" "main" {
  name                = "pip-web"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name
  allocation_method   = "Static"
  sku                 = "Standard"
}

# ─── Network Interface ──────────────────────────
resource "azurerm_network_interface" "main" {
  name                = "nic-web"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name

  ip_configuration {
    name                          = "internal"
    subnet_id                     = azurerm_subnet.frontend.id
    private_ip_address_allocation = "Dynamic"
    public_ip_address_id          = azurerm_public_ip.main.id
  }
}

# ─── Associate NSG with NIC ──────────────────────
resource "azurerm_network_interface_security_group_association" "web" {
  network_interface_id      = azurerm_network_interface.main.id
  network_security_group_id = azurerm_network_security_group.web.id
}

# ─── Linux Virtual Machine ───────────────────────
resource "azurerm_linux_virtual_machine" "web" {
  name                = "vm-web-01"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  size                = "Standard_B2s"
  admin_username      = "azureuser"

  network_interface_ids = [
    azurerm_network_interface.main.id,
  ]

  admin_ssh_key {
    username   = "azureuser"
    public_key = file("~/.ssh/id_rsa.pub")
  }

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "Standard_LRS"
  }

  source_image_reference {
    publisher = "Canonical"
    offer     = "0001-com-ubuntu-server-jammy"
    sku       = "22_04-lts"
    version   = "latest"
  }

  tags = {
    environment = "demo"
  }
}

5. Implicit vs Explicit Dependencies

5.1 Implicit Dependencies

Terraform automatically infers dependencies when one resource references another's attribute. This is the most common and preferred pattern.

# azurerm_subnet.frontend is referenced via virtual_network_name,
# so Terraform knows to create the VNet BEFORE the subnet — implicit dependency.
resource "azurerm_subnet" "frontend" {
  name                 = "snet-frontend"
  virtual_network_name = azurerm_virtual_network.main.name  # ← implicit dep
  resource_group_name  = azurerm_resource_group.main.name
  address_prefixes     = ["10.0.1.0/24"]
}
Implicit dependency graph:

azurerm_resource_group.main
    │
    ├──► azurerm_virtual_network.main
    │         │
    │         └──► azurerm_subnet.frontend
    │                   │
    │                   └──► azurerm_network_interface.main
    │                              │
    │                              └──► azurerm_linux_virtual_machine.web
    │
    └──► azurerm_network_security_group.web
              │
              └──► azurerm_network_interface_security_group_association.web

5.2 Explicit Dependencies with depends_on

Use depends_on when a dependency exists but isn't expressed through attribute references — for example, a policy that must be applied before a resource is created.

resource "azurerm_linux_virtual_machine" "web" {
  name                = "vm-web-01"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  size                = "Standard_B2s"
  admin_username      = "azureuser"

  network_interface_ids = [azurerm_network_interface.main.id]

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "Standard_LRS"
  }

  source_image_reference {
    publisher = "Canonical"
    offer     = "0001-com-ubuntu-server-jammy"
    sku       = "22_04-lts"
    version   = "latest"
  }

  # Explicit: wait for NSG rules to propagate before creating VM
  depends_on = [
    azurerm_network_security_group.web,
  ]
}
Use sparingly: Overusing depends_on hides the true dependency graph and makes plans slower. If an implicit reference exists, prefer that. Only use depends_on for non-obvious ordering.

6. Resource Meta-Arguments

Meta-arguments are available on every resource type and control behavior like repetition, lifecycle, and timeouts.

6.1 count

Creates multiple instances of a resource. The count is an integer expression.

variable "instance_count" {
  type    = number
  default = 3
}

resource "azurerm_linux_virtual_machine" "web" {
  count               = var.instance_count
  name                = "vm-web-${count.index + 1}"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  size                = "Standard_B2s"
  admin_username      = "azureuser"

  network_interface_ids = [
    azurerm_network_interface.main[count.index].id,
  ]

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "Standard_LRS"
  }

  source_image_reference {
    publisher = "Canonical"
    offer     = "0001-com-ubuntu-server-jammy"
    sku       = "22_04-lts"
    version   = "latest"
  }
}

# Access all instances
output "vm_ids" {
  value = azurerm_linux_virtual_machine.web[*].id
}
Limitation: With count, removing an item from the middle of the list causes all subsequent items to be destroyed and recreated. Prefer for_each for stable naming.

6.2 for_each

Creates resources from a map or set. Each instance gets a unique key, making insertion/deletion safe.

variable "vms" {
  default = {
    web   = { size = "Standard_B2s", zone = "1" }
    api   = { size = "Standard_B2ms", zone = "2" }
    worker = { size = "Standard_B1ms", zone = "1" }
  }
}

resource "azurerm_linux_virtual_machine" "app" {
  for_each            = var.vms
  name                = "vm-${each.key}"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  size                = each.value.size
  admin_username      = "azureuser"
  zone                = each.value.zone

  network_interface_ids = [
    azurerm_network_interface.app[each.key].id,
  ]

  os_disk {
    caching              = "ReadWrite"
    storage_account_type = "Standard_LRS"
  }

  source_image_reference {
    publisher = "Canonical"
    offer     = "0001-com-ubuntu-server-jammy"
    sku       = "22_04-lts"
    version   = "latest"
  }
}

6.3 lifecycle

The lifecycle block overrides default behaviors for creation, update, and destruction.

prevent_destroy

resource "azurerm_storage_account" "critical" {
  name                     = "stcritdata2026"
  resource_group_name      = azurerm_resource_group.main.name
  location                 = azurerm_resource_group.main.location
  account_tier             = "Standard"
  account_replication_type = "GRS"

  lifecycle {
    prevent_destroy = true   # terraform destroy will FAIL if this resource exists
  }
}

create_before_destroy

resource "azurerm_linux_virtual_machine" "web" {
  name                = "vm-web-01"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  size                = "Standard_B2s"
  admin_username      = "azureuser"

  lifecycle {
    create_before_destroy = true  # Build new VM before destroying old one
  }

  # ... rest of config
}

ignore_changes

resource "azurerm_linux_virtual_machine" "web" {
  # ...

  # External tools may modify the tags; don't drift on every plan
  lifecycle {
    ignore_changes = [
      tags["LastModifiedBy"],
      tags["AppliedPatch"],
    ]
  }
}

replace_triggered_by

resource "azurerm_linux_virtual_machine" "web" {
  # ...

  # Force recreation when the subnet changes
  lifecycle {
    replace_triggered_by = [
      azurerm_subnet.frontend,
    ]
  }
}

precondition & postcondition

resource "azurerm_linux_virtual_machine" "web" {
  # ...

  lifecycle {
    precondition {
      condition     = var.vm_size != "Standard_B1s"
      error_message = "VM size B1s is too small for production workloads."
    }

    postcondition {
      condition     = self.power_state == "running"
      error_message = "VM failed to reach running state."
    }
  }
}
Pro tip: Combine precondition with variables and data sources to enforce organizational policies — for example, verifying that the chosen region supports the required VM SKU.

6.4 timeouts

Override Terraform's default operation timeouts (varies by resource provider).

resource "azurerm_linux_virtual_machine" "web" {
  # ...

  timeouts {
    create = "30m"
    update = "20m"
    delete = "15m"
  }
}

7. Resource Addressing

Resource addresses uniquely identify every resource and attribute in a Terraform configuration.

Full addressing syntax:

module.<name>.resource.<type>.<name>
  └─ optional   └─ required  └─ required

Examples:
  azurerm_resource_group.main                        # resource type + name
  azurerm_linux_virtual_machine.web[0]               # count index
  azurerm_linux_virtual_machine.app["api"]           # for_each key
  module.network.azurerm_virtual_network.main        # module-scoped
  azurerm_linux_virtual_machine.web.private_ip       # attribute access

7.1 Targeting from the CLI

# Plan changes to a specific resource
terraform plan -target=azurerm_linux_virtual_machine.web

# Target an entire module
terraform plan -target=module.network

# Target with for_each
terraform plan -target='azurerm_linux_virtual_machine.app["api"]'

# Destroy a specific resource (careful!)
terraform destroy -target=azurerm_linux_virtual_machine.web[1]
Avoid in automation: Using -target in CI/CD pipelines can mask drift and missing dependencies. Use it only for debugging.

7.2 Moving Resources

Rename a resource without destroying and recreating it:

# In the config, write a move block (Terraform 1.1+)
moved {
  from = azurerm_linux_virtual_machine.web
  to   = azurerm_linux_virtual_machine.app_server
}

# Or move from count to for_each:
moved {
  from = azurerm_linux_virtual_machine.web[0]
  to   = azurerm_linux_virtual_machine.web["primary"]
}

8. Data Sources

Data sources query existing infrastructure that Terraform does not manage. They use the data block instead of resource.

# ─── Query the current Azure subscription ────────
data "azurerm_client_config" "current" {}

# ─── Look up an existing VNet ────────────────────
data "azurerm_virtual_network" "shared" {
  name                = "vnet-shared-hub"
  resource_group_name = "rg-networking"
}

# ─── Get the latest Ubuntu image ─────────────────
data "azurerm_platform_image" "ubuntu" {
  location  = "East US"
  publisher = "Canonical"
  offer     = "0001-com-ubuntu-server-jammy"
  sku       = "22_04-lts"
}

# ─── AWS: Look up latest Amazon Linux AMI ────────
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]
  }
}

# ─── GCP: Look up the default compute service account ──
data "google_compute_default_service_account" "default" {
  project = "my-gcp-project-id"
}

# ─── Use data source values in a resource ────────
resource "azurerm_linux_virtual_machine" "web" {
  # ...
  size = data.azurerm_platform_image.ubuntu.id != "" ? "Standard_B2s" : "Standard_B1ms"
}
Data source vs resource: A data block only reads — it will never create, modify, or destroy infrastructure. If the queried resource doesn't exist, the plan fails.

8.1 Using data with for_each

variable "subnets_to_lookup" {
  default = {
    frontend = { name = "snet-frontend", vnet = "vnet-main" }
    backend  = { name = "snet-backend", vnet = "vnet-main" }
  }
}

data "azurerm_subnet" "existing" {
  for_each             = var.subnets_to_lookup
  name                 = each.value.name
  virtual_network_name = each.value.vnet
  resource_group_name  = "rg-networking"
}

output "subnet_ids" {
  value = { for k, v in data.azurerm_subnet.existing : k => v.id }
}

9. Sensitive Resources

Terraform provides built-in support for hiding sensitive values in state and output.

9.1 The sensitive Argument

# Marks an output as sensitive — hidden in CLI output, stored in state
output "admin_password" {
  value     = azurerm_linux_virtual_machine.web.admin_password
  sensitive = true  # Value won't appear in terraform output without -json
}

9.2 Sensitive Variables

variable "db_password" {
  type      = string
  sensitive = true   # Won't be shown in plans or output
}

resource "azurerm_postgresql_flexible_server" "main" {
  # ...
  administrator_password = var.db_password
}

9.3 Marking a Resource Attribute as Sensitive

resource "random_password" "db" {
  length           = 16
  special          = true
  override_special = "!@#$%&"
}

locals {
  db_password = random_password.db.result
}

resource "azurerm_key_vault_secret" "db_password" {
  name         = "db-password"
  value        = local.db_password
  key_vault_id = azurerm_key_vault.main.id

  # Attributes marked sensitive won't be shown in plan output
  lifecycle {
    ignore_changes = [value]
  }
}
State file is still sensitive: Even with sensitive = true, values are stored in plaintext in the Terraform state file. Use remote state backends with encryption (e.g., Azure Storage, S3 with SSE, GCS with CMEK) and restrict access with IAM.

10. Summary & Checklist

Key Takeaways

  • Providers are plugins that bridge Terraform and cloud APIs. Pin versions and authenticate via environment variables or identity.
  • Resources declare desired infrastructure state. Reference other resources by name for automatic dependency ordering.
  • Provider aliases enable multi-region or multi-subscription deployments in a single configuration.
  • count and for_each replicate resources — for_each is preferred for stable addressing.
  • lifecycle controls destruction behavior, drift handling, and pre/postconditions.
  • Data sources query existing infrastructure without managing it.
  • Sensitive values must be marked and protected in both state and CI/CD pipelines.

Chapter 3 Checklist

  1. Declared required_providers with version constraints for every provider.
  2. Configured provider authentication via environment variables (not hardcoded secrets).
  3. Used ~> version constraint to allow safe upgrades.
  4. Used provider aliases only where multi-region/subscription is needed.
  5. Defined all resources with explicit names (no reliance on defaults).
  6. Let implicit dependencies (attribute references) handle ordering.
  7. Used depends_on only when no implicit reference is possible.
  8. Used for_each over count for multi-instance resources.
  9. Added lifecycle { prevent_destroy = true } on critical-state resources.
  10. Used lifecycle { ignore_changes } for attributes modified outside Terraform.
  11. Leveraged data sources to reference existing infrastructure.
  12. Marked sensitive variables and outputs with sensitive = true.
  13. Verified terraform plan shows expected changes before apply.
