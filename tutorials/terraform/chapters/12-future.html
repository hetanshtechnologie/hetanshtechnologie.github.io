1. Terraform v1.x Roadmap & Recent Features

Terraform has steadily evolved since v1.0. HashiCorp continues to invest in the core language while adding features that reduce friction in daily workflows.

Moved Blocks

Moved blocks let you rename or reorganize resources without destroying and recreating them. This solves one of the longest-standing pain points in Terraform.

# Before: resource was at module level
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
}

# After moving into a module — no destroy/recreate needed
moved {
  from = aws_instance.web
  to   = module.compute.aws_instance.web
}

# Rename a resource
moved {
  from = aws_instance.legacy
  to   = aws_instance.application
}

Import Blocks

Declarative import replaces the imperative terraform import command. You can now bring existing resources under Terraform management via configuration alone.

import {
  to = aws_s3_bucket.data
  id = "my-existing-data-bucket"
}

resource "aws_s3_bucket" "data" {
  bucket = "my-existing-data-bucket"

  lifecycle {
    prevent_destroy = true
  }
}

Test Framework

The native terraform test command allows you to write acceptance tests directly alongside your configuration.

# tests/networking.tftest.hcl

variables {
  vpc_cidr = "10.0.0.0/16"
}

run "creates_vpc_with_correct_cidr" {
  command = apply

  assert {
    condition     = module.vpc.vpc_cidr_block == var.vpc_cidr
    error_message = "VPC CIDR block mismatch"
  }
}

run "subnets_are_distributed_across_azs" {
  command = apply

  assert {
    condition     = length(module.vpc.azs) >= 2
    error_message = "VPC must span at least 2 availability zones"
  }
}

Provider-Defined Functions

Providers can now expose custom functions directly in HCL — no more locals blocks full of workaround expressions.

output "encoded" {
  # ipcidr() is provided by the hashicorp/aws provider
  value = provider::aws::ipcidr("10.0.0.0/16", 4, 8)
}

output "parsed" {
  # provider::aws::arn_parse() extracts components from an ARN
  value = provider::aws::arn_parse(data.aws_caller_identity.current.arn)
}

2. Licensing Changes — The BSL Controversy

In August 2023, HashiCorp moved Terraform (and all other products) from the Mozilla Public License (MPL 2.0) to the Business Source License (BSL). This sparked significant debate across the community.

┌──────────────────────────────────────────────────────────────────┐
│                     LICENSING TIMELINE                           │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  2014         2016         2020         Aug 2023     2024+      │
│   │            │            │              │            │         │
│   ▼            ▼            ▼              ▼            ▼         │
│ ┌──────┐   ┌──────┐   ┌──────┐       ┌─────────┐  ┌─────────┐  │
│ │ MPL  │──▶│ MPL  │──▶│ MPL  │──────▶│  BSL    │  │ BSL +   │  │
│ │      │   │ 2.0  │   │ 2.0  │       │ 1.1     │  │ OFL*    │  │
│ └──────┘   └──────┘   └──────┘       └─────────┘  └─────────┘  │
│                                                                  │
│  * OFL = Open Function License (HashiCorp's conversion clause)  │
│    BSL converts to MPL 4 years after release                     │
└──────────────────────────────────────────────────────────────────┘

What the BSL Means in Practice

  • Free for personal/educational use — no changes for most learners.
  • Free for service providers if you do NOT offer a competing managed product.
  • Restricted if you build a commercial Terraform Cloud alternative using Terraform source code.
  • BSL releases automatically convert to MPL 4 years after publication.

Community Reaction

The move prompted the founding of the OpenTofu project under the Linux Foundation (see next section). Key concerns included:

  • Forking restrictions make it harder for third parties to contribute.
  • Managed service providers offering Terraform-as-a-service face new legal obligations.
  • The precedent may influence other IaC tools to follow suit.

3. OpenTofu — The Open-Source Fork

OpenTofu is a community-driven, open-source fork of Terraform maintained under the Linux Foundation. It preserves the MPL 2.0 license and aims to be a drop-in replacement for Terraform.

Key Differences

AspectTerraform (HashiCorp)OpenTofu (Linux Foundation)
LicenseBSL 1.1MPL 2.0
GovernanceHashiCorp / IBMLinux Foundation / CNCF
State EncryptionRoadmap itemImplemented (AES-256-GCM)
Provider CompatNative100% compatible with TF providers
Managed OfferingTerraform CloudMultiple community/commercial options

Migration Path

Migrating from Terraform to OpenTofu is typically a one-command process:

# 1. Backup your state
cp terraform.tfstate terraform.tfstate.backup

# 2. Install OpenTofu
brew install opentofu        # macOS
# or: sudo apt install tofu  # Debian/Ubuntu
# or: winget install opentofu # Windows

# 3. Replace terraform commands with tofu
tofu init
tofu plan
tofu apply

OpenTofu reads existing Terraform state files, .tf files, and provider configurations without modification.

State Encryption Example

OpenTofu supports encrypting state at rest — a feature not yet available in Terraform:

encryption {
  key_provider "pbkdf2" "state_key" {
    passphrase = var.state_encryption_passphrase
  }

  method "aes_gcm" "state_method" {
    keys = key_provider.pbkdf2.state_key
  }

  state {
    method = method.aes_gcm.state_method
  }

  plan {
    method = method.aes_gcm.state_method
  }
}

4. Pulumi — Code-First IaC

Pulumi takes a fundamentally different approach: instead of a DSL (HCL), you write infrastructure as code using general-purpose programming languages.

Side-by-Side: S3 Bucket Comparison

Terraform (HCL):

resource "aws_s3_bucket" "data" {
  bucket = "my-app-data-${var.environment}"

  tags = {
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}

resource "aws_s3_bucket_versioning" "data" {
  bucket = aws_s3_bucket.data.id

  versioning_configuration {
    status = "Enabled"
  }
}

Pulumi (TypeScript):

import * as aws from "@pulumi/aws";

const dataBucket = new aws.s3.Bucket("data", {
  bucket: `my-app-data-${environment}`,
  tags: {
    Environment: environment,
    ManagedBy: "Pulumi",
  },
});

new aws.s3.BucketVersioning("data-versioning", {
  bucket: dataBucket.id,
  versioningConfiguration: {
    status: "Enabled",
  },
});

Pulumi (Python):

import pulumi
import pulumi_aws as aws

data_bucket = aws.s3.Bucket("data",
    bucket=f"my-app-data-{environment}",
    tags={
        "Environment": environment,
        "ManagedBy": "Pulumi",
    })

aws.s3.BucketVersioning("data-versioning",
    bucket=data_bucket.id,
    versioning_configuration={
        "status": "Enabled",
    })

Pulumi Advantages

  • Full programming constructs: loops, conditionals, functions, classes.
  • Built-in StackReference for cross-stack outputs (simpler than Terraform remote state).
  • ComponentResource for reusable abstractions with real OOP patterns.
  • Pulumi AI — generate infrastructure from natural language.

Pulumi Challenges

  • Smaller community and fewer learning resources than Terraform.
  • Debugging can be harder when errors originate in generated provider code.
  • Team adoption may require language-specific tooling (package managers, IDE support).

5. Crossplane — Kubernetes-Native Infrastructure

Crossplane extends Kubernetes to manage external infrastructure. Instead of a separate CLI tool, you define infrastructure using Kubernetes YAML manifests.

Core Concepts

Crossplane ConceptTerraform EquivalentDescription
ProviderProviderConnects to cloud APIs (AWS, Azure, GCP)
Managed ResourceResourceIndividual infrastructure object
Composite Resource (XR)ModuleReusable, opinionated building blocks
ClaimModule invocationEnd-user request for infrastructure
CompositionModule internalsTemplate that defines how XRs are realized

Example: S3 Bucket via Crossplane

apiVersion: s3.aws.upbound.io/v1beta1
kind: Bucket
metadata:
  name: my-app-data
  labels:
    environment: production
spec:
  forProvider:
    region: us-east-1
    versioning:
      - enabled: true
    serverSideEncryptionConfiguration:
      - applyServerSideEncryptionByDefault:
          - sseAlgorithm: aws:kms
    tags:
      - key: ManagedBy
        value: Crossplane
  providerConfigRef:
    name: aws-provider

Crossplane Advantages

  • Declarative drift reconciliation — Kubernetes controller continuously converges desired state.
  • Uses GitOps workflows (Argo CD, Flux) for infrastructure changes.
  • Composable abstractions via Composite Resources — platform teams can expose simplified interfaces.
  • Multi-cloud from a single control plane.

Crossplane Challenges

  • Requires a running Kubernetes cluster — operational overhead.
  • Steeper learning curve for teams unfamiliar with Kubernetes.
  • Crossplane provider coverage may lag behind Terraform providers.
  • Debugging issues requires Kubernetes knowledge (kubectl, CRD inspection).

      bucketName: `my-app-data-${this.node.tryGetContext('env')}`,
      versioned: true,
      encryption: s3.BucketEncryption.KMS,
      removalPolicy: cdk.RemovalPolicy.RETAIN,
    });
  }
}

When Cloud-Specific Tools Make Sense

  • You are 100% committed to a single cloud provider.
  • You need the fastest possible feature parity (new AWS services appear in CloudFormation/CDK before Terraform).
  • Your team is already deeply invested in a cloud provider's ecosystem.
  • Compliance requirements mandate using vendor-supported tooling.

Terraform → Ansible Handoff

# terraform/main.tf — provision infrastructure

resource "aws_instance" "app" {
  count         = 3
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.medium"

  tags = {
    Name = "app-server-${count.index}"
  }

  connection {
    type        = "ssh"
    host        = self.private_ip
    user        = "ubuntu"
    private_key = var.ssh_private_key
  }

  provisioner "local-exec" {
    command = <<-EOT
      ansible-playbook \
        -i '${self.private_ip},' \
        -e 'instance_id=${self.id}' \
        -e 'env=${var.environment}' \
        ../ansible/site.yml
    EOT
  }
}

output "app_ips" {
  value = aws_instance.app[*].private_ip
}

Drift Remediation with AI

When monitoring detects that a resource has drifted from its declared state, AI tools can:

  1. Detect the drift via API comparison.
  2. Generate a remediation plan (terraform plan-style diff).
  3. Suggest whether to accept the drift or revert to declared state.
  4. Auto-apply if within policy guardrails.

Limitations & Considerations

  • AI-generated Terraform must be reviewed by humans — LLMs can hallucinate resource attributes.
  • Security-sensitive configurations should never be auto-applied without review.
  • AI suggestions are only as good as the provider documentation and training data.
  • Complex multi-module architectures still require human design decisions.

The Ten Commandments of Terraform

  1. Never store state locally in production. Use remote backends with locking.
  2. Never hardcode secrets in .tf files. Use Vault, SSM, or sensitive variables.
  3. Always run terraform plan before apply. Review every change.
  4. Always version-pin providers and modules to avoid breaking changes.
  5. Always use modules for anything repeated more than twice.
  6. Always use moved blocks instead of destroy/recreate when restructuring.
  7. Always enable state encryption when using OpenTofu or Terraform Cloud.
  8. Always implement testing — even a few smoke tests catch major regressions.
  9. Always use CI/CD pipelines for plan and apply in shared workspaces.
  10. Always document your modules — future you will thank present you.

Final Thoughts

Infrastructure as Code is no longer optional — it is a fundamental discipline for any team operating in the cloud. Terraform has been the de facto standard for years, and whether you stick with it, move to OpenTofu, or adopt an alternative like Pulumi or Crossplane, the principles remain the same: declare your desired state, version it, test it, and apply it safely.

The tools will keep evolving. AI will make IaC more accessible. New providers will cover emerging services. But the core skill — understanding how to design, build, and operate cloud infrastructure reliably — will remain valuable for years to come.
