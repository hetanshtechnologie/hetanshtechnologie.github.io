Chapter 5: State Management & Remote Backends

State is the heart of Terraform. Every resource you create, every attribute you reference, every dependency between objects — all of it lives in a single JSON file called the state file. Understanding state is not optional; it is the difference between a smooth workflow and hours of debugging. In this chapter you will learn what state contains, why local state is risky, how to use remote backends, and the best practices that keep teams productive.

5.1   What Is Terraform State?

When Terraform runs plan or apply, it compares two things:

  1. Your configuration — the HCL files you write.
  2. The current state — a JSON record of every resource Terraform currently manages.

Terraform uses the state to build a resource graph, determine the correct order of operations, and know which real-world objects map to which blocks in your code. Without state, Terraform would have no way to know that azurerm_linux_web_app.myapp corresponds to a specific App Service instance in Azure.

┌──────────────────┐       ┌────────────────┐       ┌──────────────────┐
│  HCL Config      │       │  State File    │       │  Real Infrastructure │
│  *.tf            │──────▶│  terraform.tf  │──────▶│  Azure / AWS / GCP   │
│                  │       │  .state        │       │                       │
└──────────────────┘       └────────────────┘       └──────────────────────┘
        ▲                          │                         │
        │          Terraform       │         Provider        │
        └────  plan / apply  ◀─────┘       read / write  ◀──┘

Key points about state:

  • State maps configuration blocks to real infrastructure IDs (e.g., /subscriptions/…/resourceGroups/myRG).
  • It stores metadata: dependency order, provider version used at creation time, and resource attributes returned by the API.
  • Terraform never automatically deletes resources — if you remove a block from your config, the state still holds the resource until you run apply.

5.2   State File Structure

The state file is plain JSON. Here is a simplified excerpt from a typical terraform.tfstate:

{
  "version": 4,
  "terraform_version": "1.7.0",
  "serial": 42,
  "lineage": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "outputs": {
    "resource_group_name": {
      "value": "rg-demo",
      "type": "string"
    }
  },
  "resources": [
    {
      "mode": "managed",
      "type": "azurerm_resource_group",
      "name": "main",
      "each": "single",
      "provider": "provider[\"registry.terraform.io/hashicorp/azurerm\"]",
      "instances": [
        {
          "schema_version": 0,
          "attributes": {
            "id": "/subscriptions/xxx/resourceGroups/rg-demo",
            "name": "rg-demo",
            "location": "eastus",
            "tags": { "env": "dev" }
          }
        }
      ]
    }
  ]
}
FieldPurpose
versionState file format version (currently 4)
serialIncrements on every change; used for locking
lineageUnique ID generated when state is created; used to detect corruption
outputsValues exported by output blocks
resourcesEvery managed resource, its attributes, and dependencies

You should never edit the state file by hand. Use terraform state commands instead.

5.3   Local State (The Default)

By default, Terraform writes the state file to your working directory as terraform.tfstate. This is convenient for learning but dangerous for any shared project.

Why local state is risky

RiskConsequence
Not in version controlColleagues cannot see current infrastructure
Only one person holds the stateConcurrent runs overwrite each other silently
No lockingTwo apply commands at the same time can corrupt state
Not encryptedSecrets (passwords, connection strings) may appear in plain text
Deleted with the repoFull loss of infrastructure record

A .gitignore should always exclude local state:

# .gitignore
terraform.tfstate
terraform.tfstate.*
.terraform/
.terraform.lock.hcl

5.4   Remote Backends

Remote backends store state in a durable, shared location with optional locking. Terraform supports several backends natively. The three most popular for cloud teams are Azure Blob Storage, AWS S3, and Google Cloud Storage.

5.4.1   Azure Blob Storage (azurerm)

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-terraform-state"
    storage_account_name = "stterraformstate"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
    use_azuread_auth     = true
  }
}

Prerequisites:

  • A Resource Group, Storage Account, and Blob Container must exist before running terraform init.
  • use_azuread_auth = true uses Azure AD tokens instead of access keys — recommended for production.
  • The key is the blob name; use different keys for different environments (e.g., dev.tfstate, prod.tfstate).

The Terraform resources to create the state container:

resource "azurerm_resource_group" "state" {
  name     = "rg-terraform-state"
  location = "eastus"
}

resource "azurerm_storage_account" "state" {
  name                     = "stterraformstate"
  resource_group_name      = azurerm_resource_group.state.name
  location                 = azurerm_resource_group.state.location
  account_tier             = "Standard"
  account_replication_type = "ZRS"

  min_tls_version = "TLS1_2"

  blob_properties {
    versioning_enabled = true
    delete_retention_policy {
      days = 90
    }
  }
}

resource "azurerm_storage_container" "state" {
  name                  = "tfstate"
  storage_account_name  = azurerm_storage_account.state.name
  container_access_type = "private"
}

5.4.2   AWS S3 (s3)

terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "network/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

Key points:

  • dynamodb_table enables state locking. Create the DynamoDB table with a partition key of LockID.
  • encrypt = true enables server-side encryption with AES-256.
  • Consider enabling versioning and force_destroy = false on the bucket for safety.

5.4.3   Google Cloud Storage (gcs)

terraform {
  backend "gcs" {
    bucket = "mycompany-terraform-state"
    prefix = "network"
  }
}

GCS backends support locking by default when you have the cloud-platform scope. Use a dedicated bucket for state, never share it with application data.

5.4.4   Terraform Cloud / HCP Terraform

terraform {
  cloud {
    organization = "mycompany"
    workspaces {
      name = "network-prod"
    }
  }
}

Terraform Cloud provides a managed backend with state storage, locking, audit logs, and policy enforcement — ideal for teams that want a fully managed solution.

5.5   Backend Configuration & Locking

When you first configure a remote backend, you must migrate the local state:

# Step 1: Add backend block to your configuration
# Step 2: Run init — Terraform will prompt you
terraform init

# Output:
# Backend configuration has changed!
# Do you want to copy existing state to the new backend?
#   Pre-existing state:  0 resources
#   New backend:         0 resources
# Enter a value: yes

Once migrated, the local terraform.tfstate file is no longer used. All operations target the remote store.

How locking works

When you run terraform apply:

  1. Terraform acquires a lock on the state file.
  2. If another user holds the lock, Terraform waits (or fails with Error: state locked).
  3. After a successful apply, the lock is released and the state is written.

If a run crashes mid-apply, the lock may be stuck. You can force-unlock:

# Only use this if you are sure no other run is active!
terraform force-unlock LOCK_ID

Overriding backend configuration at runtime

You can supply backend values on the command line without editing the HCL — useful in CI/CD pipelines:

terraform init \
  -backend-config="resource_group_name=rg-terraform-state" \
  -backend-config="storage_account_name=stterraformstate" \
  -backend-config="container_name=tfstate" \
  -backend-config="key=staging.terraform.tfstate"

This pattern lets you reuse a single backend block across dev, staging, and prod by varying key and credentials.

5.6   State Operations

Terraform provides a rich set of sub-commands to manipulate state without editing the JSON. Master these to recover from misconfigurations and manage infrastructure changes safely.

5.6.1   terraform state list

Lists every resource tracked in state:

$ terraform state list
azurerm_resource_group.main
azurerm_linux_web_app.myapp
azurerm_service_plan.plan
azurerm_app_service_plan.staging

5.6.2   terraform state show

Displays all attributes for a specific resource:

$ terraform state show azurerm_linux_web_app.myapp

# azurerm_linux_web_app.myapp:
resource "azurerm_linux_web_app" "myapp" {
    id                = "/subscriptions/.../webApps/myapp"
    name              = "myapp"
    location          = "eastus"
    https_only        = true
    site_config {}
}

5.6.3   terraform state mv

Renames or moves a resource in state. Essential when refactoring code (e.g., moving a resource into a module):

# Rename a resource
terraform state mv azurerm_resource_group.old_name azurerm_resource_group.new_name

# Move into a module
terraform state mv azurerm_linux_web_app.myapp module.web.azurerm_linux_web_app.myapp

# Move between state files (import from another)
terraform state mv -state=old.tfstate -state-out=new.tfstate \
  azurerm_linux_web_app.myapp azurerm_linux_web_app.myapp

5.6.4   terraform state rm

Removes a resource from state without deleting it. Use when you want to stop managing a resource via Terraform:

# Stop managing a resource but leave it running
terraform state rm azurerm_linux_web_app.legacy

# Remove an entire module from state
terraform state rm module.legacy_web

5.6.5   terraform import

Brings an existing resource under Terraform management. You write the HCL block first, then import the real object:

# 1. Add the resource block to your config
resource "azurerm_linux_web_app" "imported" {
  name                = "existing-app"
  resource_group_name = azurerm_resource_group.main.name
  location            = azurerm_resource_group.main.location
  service_plan_id     = azurerm_service_plan.plan.id
  site_config {}
}

# 2. Import it
terraform import azurerm_linux_web_app.imported \
  /subscriptions/xxx/resourceGroups/rg-demo/providers/Microsoft.Web/sites/existing-app

# 3. Run plan — Terraform will show any drift
terraform plan
Tip: As of Terraform 1.5+, you can use import blocks directly in HCL, eliminating the need for the separate command: 
import {
  to = azurerm_linux_web_app.imported
  id = "/subscriptions/xxx/resourceGroups/rg-demo/providers/Microsoft.Web/sites/existing-app"
}

5.6.6   terraform state pull and terraform state push

For advanced scenarios you can download or upload the raw state JSON:

# Download state as JSON
terraform state pull > state-backup.json

# Upload a modified state (use with extreme caution)
terraform state push state-backup.json

5.7   State File Encryption & Security

State files often contain sensitive values — database passwords, API keys, TLS certificates, and connection strings. Securing them is critical.

Encryption at rest

BackendHow to encrypt
Azure BlobEnabled by default with Microsoft-managed keys; use CMK for stricter control
AWS S3encrypt = true in the backend config; consider SSE-KMS with a dedicated key
GCSEnabled by default; configure encryption_service_account for CMEK

Encryption in transit

All remote backends communicate over HTTPS/TLS. Ensure your CI/CD runners are on trusted networks.

Access control

# Example: Azure RBAC for state storage — only Terraform service principal can read/write
resource "azurerm_role_assignment" "tf_contributor" {
  scope                = azurerm_storage_account.state.id
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = data.azuread_service_principal.tf_sp.id
}

Best practices for state security:

  • Use least-privilege — only the CI/CD identity and a small set of admins should access state.
  • Enable Azure Storage analytics / CloudTrail / GCP Cloud Audit to log every state access.
  • Mark the state container as private — no anonymous access.
  • Use the sensitive attribute on outputs to prevent accidental display, but remember it is only a display guard — the raw value is still in state.
  • Consider using external secrets (Azure Key Vault, AWS Secrets Manager, GCP Secret Manager) for passwords instead of writing them to Terraform at all.

5.8   Drift Detection

Configuration drift occurs when someone manually changes infrastructure outside Terraform (via a portal, CLI, or another tool). Drift detection finds these changes so you can decide whether to update state or revert the manual change.

Detecting drift

# Plain plan shows drift as additions, deletions, and in-place changes
terraform plan

# Output excerpt:
# azurerm_linux_web_app.myapp has changed
#   ~ site_config {
#       - ftps_state = "Disabled"
#       + ftps_state = "FtpsOnly"
#     }

# JSON output for programmatic analysis
terraform plan -out=plan.json -detailed-exitcode
echo $?  # 0 = no change, 1 = error, 2 = changes present

Automated drift detection

Schedule a pipeline job that runs terraform plan on a regular cadence and alerts the team when drift is detected:

# Azure DevOps / GitHub Actions pattern
steps:
  - name: Terraform Plan
    run: terraform plan -detailed-exitcode -no-color
    continue-on-error: true
    id: plan

  - name: Alert on drift
    if: steps.plan.outcome == 'failure'
    run: |
      echo "::warning::Infrastructure drift detected! Review the plan output."

Remediating drift

  1. Revert the manual change — let Terraform reapply the desired state.
  2. Accept the change — update your HCL to match the new reality and run apply.
  3. Ignore specific attributes — use lifecycle { ignore_changes = [...] } for fields that are intentionally managed outside Terraform.
resource "azurerm_linux_web_app" "myapp" {
  # ...
  lifecycle {
    ignore_changes = [
      app_settings["WEBSITE_RUN_FROM_PACKAGE"],
    ]
  }
}

5.9   Best Practices for Team State Management

When multiple engineers share a Terraform codebase, state management becomes a discipline. Follow these rules to avoid pain.

#PracticeWhy It Matters
1Always use a remote backendEliminates single-person state, enables locking
2Separate state per environmentA dev apply must never touch prod resources
3Separate state per team/componentReduces blast radius and lock contention
4Never use force-unlock casuallyForcing a unlock while someone else is applying can corrupt state
5Enable versioning on state storageAllows rollback if state is accidentally corrupted
6Restrict access with IAM/RBACOnly CI/CD and authorized admins should read/write state
7Audit state accessKnow who touched state and when
8Use terraform state mv for refactorsMaintains resource identity across code reorganization
9Never terraform state rm without planningRemoving from state silently orphans the real resource
10Back up state before bulk operationsterraform state pull to a file; you can always push back

State file organization patterns

Pattern A: One state per environment
├── environments/
│   ├── dev/         → state key: dev.terraform.tfstate
│   ├── staging/     → state key: staging.terraform.tfstate
│   └── prod/        → state key: prod.terraform.tfstate

Pattern B: Component-based state (larger teams)
├── components/
│   ├── networking/  → state key: networking.terraform.tfstate
│   ├── database/    → state key: database.terraform.tfstate
│   └── app/         → state key: app.terraform.tfstate

Pattern C: Workspace-based (Terraform Cloud)
├── Workspace per environment, managed via VCS integration
└── Policies enforce naming and placement

Working with multiple state files

When components have separate state files, reference outputs from one workspace in another using terraform_remote_state or data "terraform_remote_state":

data "terraform_remote_state" "networking" {
  backend = "azurerm"
  config = {
    resource_group_name  = "rg-terraform-state"
    storage_account_name = "stterraformstate"
    container_name       = "tfstate"
    key                  = "networking.terraform.tfstate"
  }
}

# Use outputs from the networking state
resource "azurerm_linux_web_app" "myapp" {
  # ...
  virtual_network_subnet_id = data.terraform_remote_state.networking.outputs.subnet_id
}

5.10   Summary & Checklist

State is the bridge between your HCL code and real-world infrastructure. Treat it with the same care you give to production databases.

What you learned

  • State tracks the mapping between configuration and real resources.
  • Local state is fine for prototyping but dangerous for teams.
  • Remote backends (Azure, AWS, GCS, Terraform Cloud) provide durability, locking, and encryption.
  • terraform state sub-commands let you list, show, move, remove, import, pull, and push state safely.
  • Encryption at rest and in transit is essential because state contains secrets.
  • Drift detection catches manual changes and keeps your infrastructure predictable.
