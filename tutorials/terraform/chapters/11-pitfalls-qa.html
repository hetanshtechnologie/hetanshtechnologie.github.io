Chapter 11: Common Pitfalls, Troubleshooting & Q&A

Even experienced engineers trip over the same Terraform landmines. This chapter catalogues the top 15 mistakes, teaches you how to diagnose and fix the most common error messages, and prepares you for interview questions with 15+ Q&A pairs.

Mistake 1: State File in Version Control

Committing terraform.tfstate to Git exposes secrets (database passwords, API keys) stored by providers and creates merge conflicts when multiple engineers apply concurrently.

# NEVER do this
git add terraform.tfstate        # secrets in plain text
git add terraform.tfstate.backup # same problem
Fix: Add the state file to .gitignore and configure a remote backend immediately.
# .gitignore
.terraform/
*.tfstate
*.tfstate.backup
*.tfplan
.terraform.lock.hcl

Mistake 2: No Remote Backend

Local state means only one person can work at a time, and the state file lives on a single machine. A laptop failure means total state loss.

terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
Warning: You must run terraform init -migrate-state to move existing local state to the remote backend. This is a one-time operation per workspace.

Mistake 3: Hardcoded Secrets

Embedding secrets directly in .tf files is a critical security violation. They appear in plan output, state, and version history.

# BAD
resource "aws_db_instance" "main" {
  password = "SuperSecret123!"   # visible in plan output
}
# GOOD — use a sensitive variable + secrets manager
variable "db_password" {
  type      = string
  sensitive = true  # redacted from plan output
}

resource "aws_db_instance" "main" {
  password = var.db_password
}

# Reference from a secrets manager at apply time
data "aws_secretsmanager_secret_version" "db" {
  secret_id = "prod/database/password"
}

Mistake 4: Not Using Variables

Without variables every environment requires editing source files directly, eliminating any chance of reuse.

# BAD
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  tags = { Name = "web-prod" }
}

# GOOD — variables.tf
variable "environment" {
  type = string
}

variable "instance_type" {
  type    = string
  default = "t3.micro"
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = var.instance_type
  tags = { Name = "web-${var.environment}" }
}

Mistake 5: Missing Provider Version Pinning

Without version constraints a terraform init may pull a major version with breaking changes, causing failures in CI at the worst possible time.

terraform {
  required_version = ">= 1.5.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"  # accepts 5.x, rejects 6.0
    }
    random = {
      source  = "hashicorp/random"
      version = "3.6.2"   # exact pin
    }
  }
}
Tip: Run terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 to lock transitive dependencies across platforms.

Mistake 6: Resource Drift Not Detected

If someone manually changes a resource in the console (adds a tag, resizes an instance), Terraform won't know until you run plan. Without periodic drift detection, your state and reality silently diverge.

# CI pipeline drift check (runs every night)
terraform plan -detailed-exitcode -out=drift.tfplan

# Exit codes:
#   0 = no changes
#   1 = error
#   2 = changes detected (drift!)
Warning: -detailed-exitcode returns 2 when drift is found. Use this in CI to create an alert ticket automatically.

Mistake 7: Using Latest AMI/Image Without Pinning

Using latest for container images or a dynamic AMI lookup without pinning means every apply may deploy different software versions.

# BAD — non-reproducible
resource "aws_instance" "web" {
  ami = "ami-latest"  # doesn't exist, but conceptually wrong
}

# GOOD — pin a specific AMI or use data source with explicit filters
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-2023.6.*"]   # pin to a known release
  }
}

# Then use the result
resource "aws_instance" "web" {
  ami = data.aws_ami.amazon_linux.id
}

Mistake 8: Not Using Modules

Copy-pasting resource blocks across projects leads to inconsistent configurations and makes updates a nightmare.

# modules/vpc/main.tf
variable "cidr_block" { type = string }
variable "azs"        { type = list(string) }

resource "aws_vpc" "this" {
  cidr_block = var.cidr_block
}

resource "aws_subnet" "public" {
  for_each          = toset(var.azs)
  vpc_id            = aws_vpc.this.id
  cidr_block        = cidrsubnet(var.cidr_block, 4, index(var.azs, each.value))
  availability_zone = each.value
}

output "vpc_id"    { value = aws_vpc.this.id }
output "subnet_ids" { value = [for s in aws_subnet.public : s.id] }

# modules/vpc/versions.tf
terraform {
  required_version = ">= 1.5"
  required_providers {
    aws = { source = "hashicorp/aws"; version = "~> 5.0" }
  }
}
# Root main.tf — use the module
module "vpc" {
  source     = "./modules/vpc"
  cidr_block = "10.0.0.0/16"
  azs        = ["us-east-1a", "us-east-1b", "us-east-1c"]
}

resource "aws_instance" "web" {
  subnet_id = module.vpc.subnet_ids[0]
}

Mistake 9: Ignoring terraform plan Output

The terraform plan output is your last line of defence. Skipping it means you might accidentally destroy a production database.

# Always review the summary at the bottom of plan output:
# Plan: 3 to add, 1 to change, 2 to destroy.
#
# Pay special attention to "destroy" lines — they mean data loss.
Warning: In CI, always gate apply behind a manual approval step that requires reviewing the plan diff. Never auto-apply to production.

Mistake 10: Not Using .gitignore

Without .gitignore, the .terraform/ directory (potentially hundreds of MB of provider binaries) and state files get committed.

# Recommended .gitignore for Terraform projects
.terraform/
.terraform.lock.hcl
*.tfstate
*.tfstate.backup
*.tfplan
crash.log
override.tf
override.tf.json
*_override.tf
*_override.tf.json
.terraformrc
terraform.rc

Mistake 11: Using count When for_each Is Better

count assigns resources by numeric index. Removing an item shifts all higher indices, causing resources to be destroyed and recreated.

# BAD — removing item at index 1 shifts index 2 → 1
variable "environments" {
  default = ["dev", "staging", "prod"]
}

resource "aws_s3_bucket" "env" {
  count  = length(var.environments)
  bucket = "myapp-${var.environments[count.index]}"
}

# GOOD — for_each keyed by name, no shifting
resource "aws_s3_bucket" "env" {
  for_each = toset(var.environments)
  bucket   = "myapp-${each.value}"
}
Rule of thumb: If you need to delete items from a list without destroying others, use for_each with a set or map.

Mistake 12: Not Handling State Locking

Without state locking, two concurrent terraform apply commands can corrupt the state file, leading to orphaned resources and expensive debugging sessions.

# S3 backend with DynamoDB locking
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/main.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"  # creates the lock entry
    encrypt        = true
  }
}
Tip: If you get stuck, terraform force-unlock <LOCK_ID> manually releases the lock. Only do this when you are certain no other process is running.

Mistake 13: Destroying Everything with terraform destroy

terraform destroy removes every resource in the state — including databases with production data. Use targeted removal instead.

# SAFE — destroy only a specific resource
terraform destroy -target=aws_instance.legacy_server

# BETTER — remove from config, then plan
# 1. Delete the resource block from main.tf
# 2. Run terraform plan (shows what will be destroyed)
# 3. Approve and apply
Warning: Always use -target or remove individual resources from your code. Running destroy on a shared workspace is catastrophic.

Mistake 14: Not Using Sensitive Variables

Without sensitive = true, passwords and API keys appear in terraform plan output and CI logs.

variable "api_key" {
  type      = string
  sensitive = true   # plan output will show (sensitive value)
}

# Also mark outputs as sensitive
output "db_password" {
  value     = random_password.db.result
  sensitive = true
}

Mistake 15: Circular Module Dependencies

When Module A depends on Module B and Module B depends on Module A, Terraform cannot resolve the dependency graph.

# BAD — circular
module "vpc" {
  source      = "./modules/vpc"
  db_endpoint = module.database.endpoint  # module database also uses vpc_id
}

module "database" {
  source  = "./modules/database"
  vpc_id  = module.vpc.vpc_id  # circular!
}

# GOOD — extract shared data to root, inject into modules
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

module "database" {
  source = "./modules/database"
  vpc_id = aws_vpc.main.id    # passed in, not looked up
}

module "vpc" {
  source      = "./modules/vpc"
  db_endpoint = module.database.endpoint  # database already has vpc_id
}
Tip: Keep data flowing in one direction. Pass dependencies down, never up. If you need a bidirectional relationship, flatten it into the root module.

11.2 — Troubleshooting Guide

Below are the most common error messages you will encounter and step-by-step fixes for each.

Error: "Provider produced inconsistent result"

This occurs when the provider returns a different value for an attribute than what was planned. It usually means a provider bug or a race condition.

# Full error:
# Error: Provider produced inconsistent result after apply
# After applying the action, the provider returned an unknown value
# for attribute "arn".

# COMMON CAUSES:
# 1. Provider version bug — upgrade the provider
# 2. AWS eventual consistency — add a retry
# 3. Race condition with async resource creation

# FIX 1: Upgrade provider
terraform init -upgrade

# FIX 2: Add lifecycle rule to retry
resource "aws_instance" "web" {
  # ...
  lifecycle {
    create_before_destroy = true
  }
}

# FIX 3: For data sources, add a depends_on or time_sleep
resource "time_sleep" "wait" {
  depends_on      = [aws_iam_role.example]
  create_duration = "10s"
}

Error: "Backend initialization required"

You see this when the backend configuration has changed since the last init.

# Error: Backend initialization required
# The currently selected backend requires a reinitialization.

# FIX:
terraform init -migrate-state

# If you changed from local to remote:
terraform init -migrate-state

# If the backend type changed entirely:
terraform state pull > backup.tfstate    # backup first!
terraform init -migrate-state
Warning: Always back up your state file before migrating backends. A failed migration can leave you without any state.

Error: "Resource already managed"

This error appears when you import a resource that Terraform is already tracking, or when you add a resource that was created outside Terraform.

# Error: resource already managed by Terraform
# aws_s3_bucket.existing is already managed by Terraform

# FIX: Remove the resource from state first, then import
terraform state rm aws_s3_bucket.existing
terraform import aws_s3_bucket.existing my-existing-bucket-name

# OR: If the resource was created manually and you want Terraform
# to manage it, use import directly
terraform import aws_s3_bucket.existing my-existing-bucket-name

Error: "Cycle in resource dependencies"

A circular dependency exists between two or more resources.

# Error: Cycle: aws_security_group.web, aws_security_group.db

# DIAGNOSE — see the cycle details:
terraform graph 2>/dev/null | dot -Tpng > graph.png

# FIX: Break the cycle by extracting shared resources
# or using separate security group rules

# BAD — circular
resource "aws_security_group" "web" {
  ingress {
    security_groups = [aws_security_group.db.id]
  }
}
resource "aws_security_group" "db" {
  ingress {
    security_groups = [aws_security_group.web.id]
  }
}

# GOOD — use separate rule resources
resource "aws_security_group" "web" {
  # no ingress referencing db
}

resource "aws_security_group" "db" {
  # no ingress referencing web
}

resource "aws_security_group_rule" "web_to_db" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  security_group_id        = aws_security_group.db.id
  source_security_group_id = aws_security_group.web.id
}

resource "aws_security_group_rule" "db_from_web" {
  type                     = "ingress"
  from_port                = 80
  to_port                  = 80
  protocol                 = "tcp"
  security_group_id        = aws_security_group.web.id
  source_security_group_id = aws_security_group.db.id
}

Error: "Invalid for_each argument"

The value passed to for_each is known only at apply time (it depends on another resource).

# Error: Invalid for_each argument
# The given "for_each" argument value is unsuitable: must be known
# before apply time.

# COMMON CAUSES:
# 1. Using a data source output that isn't known at plan time
# 2. Using a resource attribute that isn't known until apply

# FIX 1: Use a known-at-plan-time value
variable "environments" {
  default = ["dev", "staging", "prod"]
}

resource "aws_s3_bucket" "env" {
  for_each = toset(var.environments)  # known at plan time ✓
  bucket   = "myapp-${each.value}"
}

# FIX 2: If using a data source, use -target or depends_on
data "aws_ami" "latest" {
  most_recent = true
  owners      = ["amazon"]
}

# If data source isn't available at plan time, try:
# terraform apply -target=data.aws_ami.latest
# Then run terraform apply again

Error: "Error acquiring the state lock"

Another Terraform process is currently modifying state, or a previous run crashed without releasing the lock.

# Error: Error acquiring the state lock
# Error message: ConditionalCheckFailedException: The conditional
# request failed

# FIX 1: Check if another process is running
# Look for running terraform processes in your terminal / CI

# FIX 2: Force-unlock (only if you're certain no other process is running)
terraform force-unlock LOCK_ID

# To find the LOCK_ID, look at the error message — it contains the ID

# FIX 3: For S3 backend, check DynamoDB
aws dynamodb scan \
  --table-name terraform-locks \
  --filter-expression "LockID = :id" \
  --expression-attribute-values '{":id":{"S":"my-terraform-state/prod/main.tfstate"}}'
Warning: Only force-unlock if you are 100% certain no other Terraform process is running. Force-unlocking while another process is active can corrupt your state.

How to Debug with TF_LOG

Terraform's built-in logging reveals exactly what the provider is doing, including raw API calls.

# Basic logging levels (most to least verbose):
# TRACE, DEBUG, INFO, WARN, ERROR

# Enable logging to a file
export TF_LOG=DEBUG
export TF_LOG_PATH="./terraform-debug.log"
terraform plan

# Or enable for a single run
TF_LOG=TRACE terraform apply

# Log to stderr (default)
export TF_LOG=DEBUG
terraform plan 2> debug.log

# Provider-specific debug
export TF_LOG=TRACE
export TF_LOG_PATH="./debug.log"
terraform plan
LevelUse WhenVolume
TRACEDeep provider debugging; seeing raw HTTP callsVery high
DEBUGUnderstanding plan/apply flow; provider behaviourHigh
INFOGeneral operational informationModerate
WARNPotential issues that don't block executionLow
ERRORFailures requiring attentionMinimal
Tip: For most debugging, TF_LOG=DEBUG gives the best balance of detail and readability. Use TRACE only when you need to see raw API payloads.

terraform console for Debugging Expressions

terraform console opens an interactive REPL for evaluating Terraform expressions against your current state.

# Start the console
terraform console

# List all resources in state
> ls

# Check a specific attribute
> aws_instance.web.public_ip

# Evaluate a complex expression
> [for s in module.vpc.subnet_ids : upper(s)]

# Test a function
> cidrsubnet("10.0.0.0/16", 4, 1)

# Check a local value
> local.common_tags

# Exit
> exit
Tip: terraform console is invaluable for testing expressions before putting them in your configuration. It prevents syntax errors and logic bugs.

11.3 — Interview-Style Q&A

These 15+ questions and answers cover the most frequently asked Terraform topics in interviews and team discussions.

Q1: What is the Terraform state file and why is it important?

Answer: The state file (terraform.tfstate) is a JSON mapping of your configuration to real infrastructure. It tracks resource IDs, attribute values, dependencies, and metadata. Terraform uses it to determine what to create, update, or destroy on the next apply. Losing the state file means Terraform loses track of all managed resources, requiring manual import.

Q2: How do you handle Terraform state in a team environment?

Answer: Use a remote backend (S3 + DynamoDB, GCS + Cloud Storage, or Azure Blob + native locking) so the state is shared, versioned, and locked during operations. Every team member runs against the same state, and the lock prevents concurrent corruption.

Q3: Explain the difference between count and for_each.

Answer: count creates resources by numeric index — removing an item shifts all higher indices, causing unnecessary destroys and recreates. for_each creates resources by a map or set key, so removing an item only destroys that specific resource without affecting others. Prefer for_each for any list that might change.

Q4: What are Terraform workspaces and when should you use them?

Answer: Workspaces let you manage multiple state files for the same configuration. Use them for dev/staging/prod environments with identical infrastructure but different variable values. For larger differences, separate directories or Terragrunt are preferred because workspaces share the same configuration and can lead to accidental cross-environment changes.

Q5: How do you handle secrets in Terraform?

Answer: Never hardcode secrets in .tf files. Use a secrets manager (Vault, AWS Secrets Manager, Azure Key Vault) as a data source, mark variables as sensitive = true, and avoid logging plan output. For CI/CD, inject secrets via environment variables and ensure plan output is never saved to unencrypted logs.

# Vault approach
data "vault_generic_secret" "db" {
  path = "secret/data/prod/database"
}

resource "aws_db_instance" "main" {
  password = data.vault_generic_secret.db.data["password"]
}

Q6: What is Terraform drift and how do you detect it?

Answer: Drift is when real infrastructure diverges from the Terraform configuration (e.g., someone manually changes an instance size). Detect it by running terraform plan regularly. Use -detailed-exitcode in CI to get a non-zero exit code when drift is found, and set up alerts.

Q7: How do modules work and why should you use them?

Answer: Modules are containers of Terraform configuration that encapsulate resources, variables, and outputs. They promote reuse (write once, use everywhere), enforce consistency, and simplify large configurations by breaking them into composable units. Published modules can be shared across teams via a module registry.

Q8: Explain terraform import and when you would use it.

Answer: terraform import brings existing infrastructure under Terraform management. Use it when you create resources manually or via another tool and want Terraform to track them. After import, you must write the corresponding .tf resource block to match the imported resource's configuration.

# Import an existing S3 bucket
terraform import aws_s3_bucket.my_bucket my-existing-bucket

# Then write the matching config
resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-existing-bucket"
}

Q9: What is terraform plan and why is it important?

Answer: terraform plan shows exactly what Terraform will do without making any changes — resources to create, modify, or destroy. It's your safety net: always review the plan output before apply, especially the "destroy" count. In CI/CD, gate apply behind a manual review of the plan diff.

Q10: How do you handle provider version upgrades safely?

Answer: Pin provider versions with ~> constraints, run terraform init -upgrade in a test environment first, review the changelog, run a full plan in staging, and only then upgrade production. Use the .terraform.lock.hcl file to lock dependencies across environments.

Q11: What is the difference between terraform apply and terraform destroy?

Answer: terraform apply creates, updates, or deletes resources to match the configuration. terraform destroy removes ALL resources managed by the state file, regardless of the current configuration. Never run destroy on a shared workspace without explicit approval.

Q12: How do you structure Terraform for a multi-environment setup?

Answer: Use separate directories per environment (envs/dev/, envs/prod/) with shared modules. Each directory has its own backend.tf pointing to a separate state file. Use Terragrunt or a CI/CD pipeline to manage the directory hierarchy. Avoid workspaces for large differences.

# Directory structure
terraform/
├── modules/
│   ├── vpc/
│   ├── database/
│   └── compute/
├── envs/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── backend.tf
│   │   └── variables.tf
│   └── prod/
│       ├── main.tf
│       ├── backend.tf
│       └── variables.tf

Q13: What are Terraform data sources?

Answer: Data sources (data "..." "") query existing infrastructure or external data without creating anything. They're used to look up AMIs, VPC IDs, account details, or external API responses. Data sources are read-only and evaluated during plan.

Q14: How do you handle Terraform in CI/CD pipelines?

Answer: Automate fmt -check, validate, init, and plan in a pipeline. Gate apply behind manual approval. Store the plan output as a build artifact and apply that exact artifact to avoid drift between plan and apply. Use a remote backend with locking for team safety.

# Example CI/CD pipeline stages
# Stage 1: Validate
terraform fmt -check -recursive
terraform validate

# Stage 2: Plan
terraform plan -out=plan.tfplan -detailed-exitcode

# Stage 3: Apply (manual gate)
terraform apply plan.tfplan

Q15: What are provisioners and why are they discouraged?

Answer: Provisioners (local-exec, remote-exec, file) run commands on resources after creation. They're discouraged because they create untracked state, have no rollback on failure, and break the declarative model. Use them only as a last resort (e.g., bootstrapping a VM when no better option exists).

Q16: How do you handle resource imports and state manipulation safely?

Answer: Back up state first (terraform state pull > backup.tfstate), then use terraform state mv or terraform state rm to adjust state. For imports, write the matching .tf block first, then run terraform import. Always validate with terraform plan after manipulation to confirm no unintended changes.

Q17: What is the purpose of lifecycle blocks?

Answer: lifecycle controls resource behaviour:

  • create_before_destroy: Create a replacement before destroying the old one (zero-downtime).
  • prevent_destroy: Block accidental destroy (safety for databases).
  • ignore_changes: Ignore specific attributes that change outside Terraform.
  • replace_triggered_by: Force recreation when another resource changes.
resource "aws_db_instance" "main" {
  # ...
  lifecycle {
    prevent_destroy = true  # never destroy this database
    ignore_changes  = [tags] # ignore tag drift
  }
}
