Chapter 7: Workspaces & Environment Separation

Running a single Terraform configuration against a single environment is a learning exercise. Real projects need multiple environments—development, staging, production, and more—each with its own state, its own variable values, and ideally its own blast radius. This chapter covers every major strategy for environment separation, from Terraform's built-in workspaces to the directory-based and backend-based patterns used in production.

7.1 Why Environment Separation Matters

If you point one set of state files at your production database while a developer runs terraform apply from a feature branch, you are one accidental merge away from an outage. Separation exists for three reasons:

  1. Safety. Each environment has its own state, so a broken apply in dev cannot corrupt prod.
  2. Configuration drift. Dev and prod may legitimately differ (instance sizes, replica counts, feature flags). Isolating configs lets each environment evolve independently.
  3. Access control. Developers may be allowed to destroy dev infrastructure but must never touch prod without approval.

Without separation, a single terraform destroy or mis-scoped apply can take down production. The strategies below exist to prevent exactly that.

7.2 Terraform Workspaces

Workspaces are Terraform's built-in mechanism for managing multiple states from the same configuration. Every Terraform root module starts in the default workspace, but you can create more.

How Workspaces Work

Workspaces are essentially named state files. The same main.tf, variables.tf, and outputs.tf are shared, but each workspace maintains its own state. When you switch workspaces, Terraform swaps the state file behind the scenes.

  terraform/
  ├── main.tf          ← shared across all workspaces
  ├── variables.tf     ← shared across all workspaces
  └── terraform.tfstate.d/
      ├── default/     ← default workspace state
      │   └── terraform.tfstate
      ├── dev/         ← dev workspace state
      │   └── terraform.tfstate
      └── prod/        ← prod workspace state
          └── terraform.tfstate

CLI Commands

CommandDescription
terraform workspace listList all workspaces; current one marked with *
terraform workspace new devCreate a new workspace named dev and switch to it
terraform workspace select devSwitch to an existing workspace
terraform workspace delete devDelete a workspace (must not be current)
terraform workspace showPrint the current workspace name

Using Workspaces in Config

You can reference the current workspace inside configuration using the terraform.workspace built-in:

locals {
  env = terraform.workspace

  instance_type = terraform.workspace == "prod" ? "m5.xlarge" : "t3.medium"

  tags = {
    Environment = terraform.workspace
    ManagedBy   = "terraform"
    Project     = "myapp"
  }
}

resource "aws_instance" "app" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = local.instance_type
  tags          = local.tags
}

This works, but it quickly becomes unwieldy. Every environment-specific value ends up in if/else conditionals scattered throughout your code.

Workspace Limitations

LimitationWhy It Matters
Shared configurationAll workspaces run the exact same code; you cannot have a prod-only resource.
Conditional logic sprawlDifferences between environments require terraform.workspace == "..." conditionals everywhere.
No access isolationAnyone who can run Terraform can switch to any workspace (including prod).
Local state by defaultWorkspaces only isolate state when using the local backend; remote backends add complexity.
Hard to reviewA plan in the prod workspace looks identical to one in dev—easy to misread.

Because of these limitations, workspaces are best reserved for ephemeral or personal environments (e.g., feature-branch previews). For anything long-lived, use directory-based or backend-based separation.

7.3 Directory-Based Separation (Recommended)

The industry-standard approach is to give each environment its own directory (or its own set of variable files) so that each environment has an independent configuration and state.

7.4 Variable Files Per Environment

If your environments differ only in values (not in which resources exist), you can use a single root module with variable files per environment.

terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── dev.tfvars
├── staging.tfvars
└── prod.tfvars

dev.tfvars

aws_region      = "us-east-1"
vpc_cidr        = "10.0.0.0/16"
azs             = ["us-east-1a", "us-east-1b"]

task_cpu        = 256
task_memory     = 512
desired_count   = 1

db_instance_class = "db.t3.micro"
db_multi_az       = false
db_backup_retention = 1

enable_nat_gateway = false

prod.tfvars

aws_region      = "us-east-1"
vpc_cidr        = "10.100.0.0/16"
azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]

task_cpu        = 1024
task_memory     = 2048
desired_count   = 3

db_instance_class = "db.r6g.xlarge"
db_multi_az       = true
db_backup_retention = 30

enable_nat_gateway = true

Plan and Apply with Variable Files

# Initialize
terraform init

# Plan for dev
terraform plan -var-file="dev.tfvars" -out=dev.tfplan

# Apply for dev
terraform apply dev.tfplan

# Plan for prod
terraform plan -var-file="prod.tfvars" -out=prod.tfplan

# Apply for prod
terraform apply prod.tfplan
Important: With variable files you share one state file across environments unless you also use separate backends. Combine this pattern with backend-per-environment (Section 7.5) for full isolation.

Environment-Scoped Variable Defaults

For cleaner defaults, set environment-aware values inside the configuration itself:

variable "env" {
  description = "Environment name"
  type        = string
}

variable "db_instance_class" {
  description = "RDS instance class"
  type        = string
  default     = null
}

locals {
  env_defaults = {
    dev = {
      db_instance_class  = "db.t3.micro"
      db_multi_az        = false
      db_backup_retention = 1
    }
    staging = {
      db_instance_class  = "db.t3.medium"
      db_multi_az        = false
      db_backup_retention = 7
    }
    prod = {
      db_instance_class  = "db.r6g.xlarge"
      db_multi_az        = true
      db_backup_retention = 30
    }
  }

  env_config = lookup(local.env_defaults, var.env, {})
}

resource "aws_db_instance" "main" {
  instance_class    = coalesce(var.db_instance_class, local.env_config.db_instance_class)
  multi_az          = local.env_config.db_multi_az
  backup_retention_period = local.env_config.db_backup_retention
}

7.5 Backend-Per-Environment Pattern

Backend configuration in Terraform cannot use variables. This means you cannot write a single backend "s3" { key = var.env }. The workaround is to use partial configuration and initialize per environment.

Partial Backend Configuration

envs/dev/backend.hcl

bucket         = "myapp-terraform-state"
key            = "dev/terraform.tfstate"
region         = "us-east-1"
dynamodb_table = "terraform-locks"
encrypt        = true

envs/prod/backend.hcl

bucket         = "myapp-terraform-state"
key            = "prod/terraform.tfstate"
region         = "us-east-1"
dynamodb_table = "terraform-locks"
encrypt        = true

Initialize with Backend Config

# Dev
terraform init -backend-config="envs/dev/backend.hcl"

# Staging
terraform init -backend-config="envs/staging/backend.hcl"

# Prod
terraform init -backend-config="envs/prod/backend.hcl"

Each environment's state lives under a different key in the same S3 bucket, giving you full isolation with a single bucket.

  S3 Bucket: myapp-terraform-state
  ┌──────────────────────────────────────┐
  │  dev/terraform.tfstate               │ ← dev state
  │  staging/terraform.tfstate           │ ← staging state
  │  prod/terraform.tfstate              │ ← prod state
  └──────────────────────────────────────┘
  DynamoDB Table: terraform-locks
  ┌──────────────────────────────────────┐
  │  dev/terraform.tfstate    → Lock-ID  │
  │  staging/terraform.tfstate → Lock-ID │
  │  prod/terraform.tfstate   → Lock-ID  │
  └──────────────────────────────────────┘

Using Different S3 Buckets or Accounts

For organizations that need cross-account isolation (e.g., production state in a separate AWS account), each environment's backend.hcl can point to a different bucket and role ARN:

# envs/prod/backend.hcl
bucket         = "prod-terraform-state-account-123456789012"
key            = "infra/terraform.tfstate"
region         = "us-east-1"
dynamodb_table = "prod-terraform-locks"
encrypt        = true
role_arn       = "arn:aws:iam::123456789012:role/TerraformStateAccess"

Changes should flow in one direction: dev → staging → prod. A promotion workflow codifies that flow.

name: "Terraform"

on:
  push:
    branches: [main]
    paths: ["terraform/**"]
  pull_request:
    branches: [main]
    paths: ["terraform/**"]

env:
  TF_VERSION: "1.6.0"
  AWS_REGION: "us-east-1"

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - name: Terraform Format
        run: terraform fmt -check -recursive
        working-directory: terraform
      - name: Terraform Validate
        run: terraform validate
        working-directory: terraform

  plan-dev:
    needs: validate
    runs-on: ubuntu-latest
    environment: dev
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.DEV_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
      - name: Terraform Init
        run: terraform init -backend-config="envs/dev/backend.hcl"
        working-directory: terraform
      - name: Terraform Plan
        run: terraform plan -var-file="envs/dev/variables.tfvars" -out=dev.tfplan
        working-directory: terraform
      - name: Terraform Apply
        if: github.ref == 'refs/heads/main'
        run: terraform apply -auto-approve dev.tfplan
        working-directory: terraform

  plan-prod:
    needs: plan-dev
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.PROD_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
      - name: Terraform Init
        run: terraform init -backend-config="envs/prod/backend.hcl"
        working-directory: terraform
      - name: Terraform Plan
        run: terraform plan -var-file="envs/prod/variables.tfvars" -out=prod.tfplan
        working-directory: terraform
      - name: Terraform Apply
        if: github.ref == 'refs/heads/main'
        run: terraform apply -auto-approve prod.tfplan
        working-directory: terraform

Makefile for Local Workflow

.PHONY: init plan apply destroy

# Initialize for a specific environment
init:
	terraform init -backend-config=envs/$(ENV)/backend.hcl

# Plan for a specific environment
plan:
	terraform plan -var-file=envs/$(ENV)/variables.tfvars -out=$(ENV).tfplan

	terraform destroy -var-file=envs/$(ENV)/variables.tfvars

#   make plan ENV=dev
#   make apply ENV=dev

7.7 Drift Detection Across Environments

Drift occurs when real infrastructure diverges from what Terraform recorded in state. Drift detection means periodically running terraform plan to find and reconcile these differences.

Why Drift Happens

  • Someone manually changes a security group rule in the AWS console.
  • An autoscaling group adds an instance that Terraform doesn't track.
  • A backup or snapshot is created outside of Terraform.
  • Cloud provider makes automatic changes (e.g., instance replacement after health check failure).

Drift Detection with terraform plan

# Run plan for each environment and check the exit code
terraform init -backend-config="envs/dev/backend.hcl"
terraform plan -var-file="envs/dev/variables.tfvars" -detailed-exitcode

# Exit codes:
#   0 = no changes
#   1 = error
#   2 = changes detected (drift found)

Automated Drift Detection Schedule

# .github/workflows/drift-detection.yml
name: "Drift Detection"

on:
  schedule:
    - cron: "0 8 * * 1"  # Every Monday at 8:00 UTC

jobs:
  detect-drift:
    strategy:
      matrix:
        env: [dev, staging, prod]
    runs-on: ubuntu-latest
    environment: ${{ matrix.env }}
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.6.0"
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1
      - name: Terraform Init
        run: terraform init -backend-config="envs/${{ matrix.env }}/backend.hcl"
        working-directory: terraform
      - name: Check for Drift
        id: drift
        run: |
          terraform plan -var-file="envs/${{ matrix.env }}/variables.tfvars" -detailed-exitcode -no-color | tee drift-output.txt
          echo "exit_code=${PIPESTATUS[0]}" >> "$GITHUB_OUTPUT"
        working-directory: terraform
        continue-on-error: true
      - name: Create Issue if Drift Detected
        if: steps.drift.outputs.exit_code == '2'
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Drift detected in ${{ matrix.env }} environment`,
              body: 'Terraform detected changes outside of Terraform management.\n\n```\n' + require('fs').readFileSync('terraform/drift-output.txt', 'utf8') + '\n```',
              labels: ['drift', '${{ matrix.env }}']
            })

7.8 Best Practices for Managing Multiple Environments

1. Use Modules as the Single Source of Truth

All environments should consume the same modules. Differences live in variable values, not in duplicated code.

# Good: same module, different variables
module "ecs" {
  source = "../../modules/ecs"
  # ... variables differ per environment
}

# Bad: duplicated module code in each env directory
module "ecs" {
  source = "./modules/ecs"  # copy-pasted, drifts over time
}

2. Enforce State Locking

Always use a remote backend with locking (DynamoDB for S3, native lock for Terraform Cloud). This prevents concurrent applies from corrupting state.

3. Separate AWS Accounts for Production

The strongest isolation is separate AWS accounts per environment. This provides:

  • Independent billing
  • Independent IAM policies
  • Blast radius limited to a single account
  • Network-level isolation (no accidental cross-VPC communication)
  ┌─────────────────────────────────────────────────┐
  │              AWS Organizations                   │
  │                                                  │
  │  ┌──────────────┐  ┌──────────────┐            │
  │  │  Dev Account  │  │ Stage Account │            │
  │  │  111111111111 │  │  222222222222 │            │
  │  └──────────────┘  └──────────────┘            │
  │                                                  │
  │  ┌──────────────┐  ┌──────────────┐            │
  │  │ Prod Account │  │  Shared acct  │            │
  │  │  333333333333 │  │  444444444444 │            │
  │  └──────────────┘  │ (DNS, IAM)   │            │
  │                     └──────────────┘            │
  └─────────────────────────────────────────────────┘

4. Tag Everything Consistently

locals {
  common_tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
    Project     = var.project_name
    CostCenter  = var.cost_center
    Team        = var.team
  }
}

resource "aws_instance" "app" {
  tags = merge(local.common_tags, {
    Name = "${var.environment}-app-${var.instance_number}"
  })
}

5. Use Sentinel or OPA for Policy Enforcement

In larger organizations, use policy-as-code to enforce constraints across all environments:

# Sentinel policy: enforce instance size limits
import "tfplan/v2" as tfplan

instance_size_by_env = {
  "dev":    ["t3.micro", "t3.small"],
  "staging": ["t3.medium", "t3.large"],
  "prod":   ["m5.large", "m5.xlarge", "m5.2xlarge"],
}

main = rule {
  all tfplan.resource_changes as _, rc {
    rc.type == "aws_instance" implies
      rc.change.after.instance_type in
        instance_size_by_env[rc.change.tags.Environment]
  }
}

6. Maintain a Runbook

Document the promotion workflow, approval requirements, and rollback procedures for each environment:

stagingTech lead sign-offBusiness hours30 minutes

7. Version-Pin Everything

terraform {
  required_version = "= 1.6.2"  # Pin exact version, not just ">= 1.5"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"  # Allow patch updates, block minors
    }
  }
}

8. Remote State Data Sources for Cross-Environment Reads

Sometimes a staging deployment needs to reference dev resources (or prod needs to reference shared DNS). Use terraform_remote_state or data "terraform_remote_state":

data "terraform_remote_state" "shared" {
  backend = "s3"
  config = {
    bucket = "myapp-terraform-state"
    key    = "shared/terraform.tfstate"
    region = "us-east-1"
  }
}

# Reference shared DNS zone
resource "aws_route53_record" "api" {
  zone_id = data.terraform_remote_state.shared.outputs.dns_zone_id
  name    = "api.${var.environment}.example.com"
  type    = "CNAME"
  ttl     = 300
  records = [module.ecs.alb_dns_name]
}

7.9 Summary & Checklist

This chapter covered the major strategies for environment separation in Terraform:

StrategyProsConsBest For
Workspaces Simple, built-in, no code duplication Shared code, no access control, conditional logic sprawl Ephemeral/preview environments
Variable files Single codebase, clean separation of values Shared state unless combined with backend separation Small projects with few differences between envs
Directory-based Full isolation, self-documenting, supports per-env configs Code duplication at root module level Production workloads, enterprise teams
Backend-per-env State isolation, same code, scalable Manual init per environment Most production setups

Chapter Checklist

  • ☐ Decide on a separation strategy (workspaces vs. directories vs. variable files)
  • ☐ Configure remote state with backend-per-environment
  • ☐ Create environment-specific variable files for all environments
  • ☐ Extract shared infrastructure into reusable modules
  • ☐ Set up state locking (DynamoDB or Terraform Cloud)
  • ☐ Define a promotion workflow (dev → staging → prod) with approval gates
  • ☐ Implement drift detection on a schedule
  • ☐ Tag all resources consistently across environments
  • ☐ Separate AWS accounts for production workloads
  • ☐ Enforce policy-as-code (Sentinel/OPA) for guardrails
  • ☐ Document the runbook: promotion, approval, and rollback procedures
  • ☐ Pin Terraform and provider versions to prevent surprises
