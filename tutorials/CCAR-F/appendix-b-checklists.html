Appendix B — Design Checklists

These checklists are stage gates, not bureaucracy. An unchecked item is a known risk that should be recorded and owned. Use them in design review, before enabling a new tool, and before shipping a change to a system that acts on behalf of users.

Checklist 1 — Architecture selection

  • The goal can be stated in one sentence with a measurable success condition.
  • The path has been classified as fixed, branching, or emergent.
  • A deterministic workflow was considered first and rejected with a written reason if an agent was chosen.
  • Each model-controlled decision has a named owner and a logged reason.
  • Stop conditions and step budgets are explicit and testable.
  • Repeated-call detection exists and terminates with an honest failure.
  • Authority boundaries are documented per actor, including what each actor must not do.
  • Irreversible actions have a human gate enforced in code.
  • Cost per successful outcome is estimated, not just cost per call.
  • The system can be replayed from a saved trace for debugging.

Checklist 2 — Decomposition and planning

  • Subtasks are defined by outcomes, not activities.
  • Each subtask has acceptance criteria that can be tested without reading the model's mind.
  • Dependencies between subtasks are explicit; parallel work has no hidden ordering.
  • Assumptions are listed with a test for each one.
  • Replanning triggers are defined before execution begins.
  • Fan-in defines how partial failure is reported and how completeness is tracked.
  • Compensation is specified for stages that cannot be rolled back.
  • No subtask depends on knowledge that only appears in a later subtask.

Checklist 3 — Multi-agent orchestration

  • A single agent was shown to be insufficient, with the reason recorded.
  • Each agent has a distinct purpose and authority scope.
  • Handoff payloads are typed, with required fields and validation at the boundary.
  • Payloads carry decisions and open questions, not raw conversation dumps.
  • Message schemas have versions and backward-compatibility rules.
  • Durable state records step, inputs, decisions, and pending approvals.
  • Loops between agents are bounded and detectable.
  • Aggregation logic states how disagreement is surfaced.
  • Cost per run is monitored by agent, not only in aggregate.

Checklist 4 — Reliability and oversight

  • Tool, reasoning, and environment failures are distinguished in the error taxonomy.
  • Each error class has a detection signal and a containment action.
  • Retries are safe: idempotency or keys are in place for mutating calls.
  • Fallback chains are ordered, bounded, and observable.
  • No high-stakes path relies solely on a prompt-level rule.
  • Programmatic validation gates sit immediately before consequential actions.
  • Hooks can deny an action before it executes, not only log it afterwards.
  • Interruption points survive restarts and record who approved what.
  • A kill switch exists and has been tested.
  • Each alert has a runbook with first checks, owner, and rollback path.

Checklist 5 — Tool design

  • Names are specific, consistent, and mutually distinguishable.
  • Descriptions state purpose, when to use, when not to use, and limits.
  • Input schemas use required fields, enums, and constraints rather than free text.
  • Unknown fields are rejected; inputs are validated with a real schema library.
  • Identity and tenant come from trusted session context, never from model text.
  • Mutating tools are idempotent and use a two-phase confirm/execute pattern.
  • Errors are structured with a code, a retryable flag, and a corrective hint.
  • Partial success is reported explicitly with a completeness indicator.
  • Outputs are compact projections with artefact references where needed.
  • Each tool is exposed only to agents that need it.
  • Call logs include name, arguments, decision, latency, and result status.

Checklist 6 — MCP integration

  • The right primitive is used: tool for actions, resource for data, prompt for reusable context.
  • Resource URIs are stable, documented, and versioned.
  • Capabilities are discovered at runtime rather than hard-coded.
  • Transport matches deployment: local standard I/O or remote HTTP with sessions.
  • Authentication and authorisation are enforced at the server boundary.
  • Roots and client-declared boundaries are respected.
  • Long-running operations report progress with tokens and status.
  • Third-party servers are reviewed like code dependencies, including update policy.
  • Schema and protocol versions are recorded in traces.
  • Built-in versus custom boundaries are documented with a reason.

Checklist 7 — Claude Code configuration

  • Shared conventions live in the root instruction file; local rules live in subdirectory files.
  • Load order and precedence have been verified with a test file in each scoped path.
  • Generated files, secrets, and large artefacts are excluded from context.
  • Path-scoped rules replace vague global statements.
  • Instructions are short, imperative, and testable rather than aspirational.
  • Reusable workflows are packaged as named commands or skills with input contracts.
  • Subagents are scoped narrowly and given only the tools they need.
  • Hooks log, lint, and deny appropriate actions at defined lifecycle points.
  • Plan mode is used for changes with wide blast radius.
  • Permission levels match team policy and are reviewed when the policy changes.
  • CI integration has explicit failure conditions and preserves useful logs.

Checklist 8 — Prompt and output quality

  • Instructions separate stable rules from variable input.
  • Ambiguous terms are replaced with definitions or examples.
  • Constraints are stated as testable conditions, not adjectives.
  • Structured prompts use consistent tags for repeated sections.
  • Examples vary in surface detail and include boundary cases.
  • Extended thinking is used only where multi-step reasoning justifies its cost.
  • Sampling settings are chosen for the task and changed one at a time.
  • A no-answer or abstain path exists where evidence may be missing.
  • Structured output uses a schema; semantic correctness gets separate validation.
  • An eval set with property assertions runs on every prompt change.

Checklist 9 — Context and provenance

  • Context is budgeted by component: instructions, history, evidence, tools, output.
  • Stable prefixes are kept stable so caching can help.
  • Large tool outputs are filtered, referenced, or summarised deliberately.
  • Verified facts are carried in a durable fact block rather than left to summarisation.
  • Scratchpads are bounded and contain invariants plus open questions.
  • Compaction preserves decisions, constraints, and commitments.
  • Escalation triggers are defined and logged.
  • Confidence scores are calibrated against a validation set before use.
  • Rare severe cases are oversampled in review and evaluation.
  • Every claim in a synthesis maps to supplied evidence; conflicts are annotated.
Exercise B.1 — Gate review. Apply Checklists 1, 4, and 5 to a current project. Mark each item done, partial, or missing. Choose the five missing items with highest risk and assign an owner.
Exercise B.2 — Pre-mortem. Imagine your system failed in production last night. Using the checklists, list the six items whose absence best explains the failure.
