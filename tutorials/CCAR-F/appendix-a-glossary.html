Appendix A — Glossary

These definitions are written for practitioners. Where a term has both a precise technical meaning and a loose industry usage, both are given. Terms are grouped by the part of the system in which they usually appear, though many cross boundaries.

Architecture and control

Agent
A loop that observes, decides, acts, and observes again. In engineering terms: a model plus instructions, tools, state, and explicit stopping rules.

Agentic system
The whole application around an agent — tools, memory, policies, runtime, evaluation, and user interface. Buying an agent does not give you an agentic system.

Workflow
A path prescribed by the developer. Transitions are code, not model decisions. Preferred when steps are stable or audits demand repeatability.

Autonomy spectrum
The range from fixed script to fully model-directed behaviour. Most useful systems sit in the middle: bounded autonomy over a small set of decisions.

Stop condition
The predicate that ends a loop because the goal is met. Distinct from a budget, which ends a loop because resources are exhausted.

Step budget
A hard maximum on iterations or tool calls. Prevents runaway loops and makes cost predictable.

Loop detection
Recognising repeated call signatures or unchanged state and terminating with an honest failure rather than continuing indefinitely.

Escalation
Transferring a decision to a higher-authority actor — another agent, a policy layer, or a human — when uncertainty or risk exceeds a threshold.

Graceful degradation
Continuing to deliver reduced but correct service when a component fails, instead of failing entirely or pretending nothing happened.

Idempotency
The property that repeating the same request produces the same effect. Essential for safe retries of mutating tools.

Planning and decomposition

Decomposition
Breaking a goal into subtasks with defined outcomes, owners, and acceptance criteria. Splitting by activity instead of outcome is a common error.

Hierarchical plan
A goal with nested subgoals. Useful when a parent must coordinate several independent children.

Sequential pipeline
Stages ordered by dependency. Simple to reason about; a failure can block everything downstream.

Fan-out / fan-in
Distributing work to several workers, then combining results. Requires explicit completeness tracking.

Adaptive planning
Revising the plan when observations invalidate assumptions. Needs recorded reasons so reviewers can reconstruct the change.

Assumption register
A list of beliefs the plan depends on, with how to test each one. Prevents hidden assumptions from becoming silent failures.

Orchestration and state

Orchestrator
The component that directs work, delegates, and aggregates. It should not also perform every subtask.

Subagent
A separately scoped actor with a narrow instruction set and limited tools. Useful for isolation, not automatically for speed.

Topology
The shape of connections between agents: star, chain, tree, blackboard, or debate. Shape determines failure propagation.

Handoff
Transfer of control from one actor to another, carrying a payload that explains what happened and what remains.

Handoff payload
A typed structure with required fields such as goal, completed steps, decisions, open questions, and evidence references.

In-context state
Information currently present in the context window. Fast to use, lost on reset, limited in size.

External memory
State stored outside the context — a database, checkpoint, or file. Durable and inspectable, but must be explicitly loaded and saved.

Durable state
Persisted state sufficient to resume after a restart: current step, inputs, decisions, and pending approvals.

Checkpoint
A saved snapshot of state at a step boundary. Enables replay, resume, and debugging.

Reliability and safety

Tool error
A failure in the tool or its dependencies — timeout, bad response, permission denial.

Reasoning error
A wrong decision by the model: incorrect tool choice, bad argument, flawed inference.

Environment error
A failure outside the model and tool — network partition, queue backlog, upstream schema change.

Retry
Re-running a failed operation. Safe only when the operation is idempotent or properly keyed.

Fallback chain
An ordered list of alternatives tried when the primary approach fails. Each step should be observable.

Programmatic validation
Checks in code — schemas, rules, policies — that do not depend on model cooperation.

Hook
A lifecycle callback that runs at a defined point, able to log, transform, or deny an action before or after it occurs.

Interruption point
A place in control flow where execution pauses for human review. Must survive restarts if the task is long.

Silent failure
Degradation that produces plausible output without an error signal. Usually detected by users before dashboards.

Least privilege
Granting only the permissions needed for a specific job, limiting blast radius if an agent is manipulated.

Tools and protocols

Tool contract
The name, description, input schema, output shape, error shape, and limits that define a tool's boundary.

Strict tool use
Rejecting inputs that do not conform to the declared schema instead of coercing or guessing.

Enum
A closed list of allowed values. Converts ambiguous free text into testable options.

Tool scoping
Exposing only the tools an agent needs. Reduces selection ambiguity and limits authority.

Tool search
A discovery step for very large catalogs, where listing every tool in context is impractical.

MCP
Model Context Protocol: a standard contract for AI applications to discover and use tools, resources, and prompts exposed by servers.

MCP resource
A data capability addressed by a URI. Read-oriented, distinct from an action-oriented tool.

MCP prompt
A reusable template with arguments, exposed by a server for clients to discover and invoke.

STDIO transport
Local process communication over standard input and output. Simple, low overhead, suited to local servers.

Streamable HTTP transport
Network transport for remote servers, supporting sessions and concurrent clients.

Root
A boundary declared by a client telling a server which parts of a workspace it may access.

Development environment

CLAUDE.md
An instruction file read by a coding assistant at startup. Versions at different levels form a hierarchy.

Load order
The sequence in which instruction files are read, determining which rules take precedence.

Path-scoped rule
An instruction that applies only to files matching a path pattern.

Slash command
A named, invokable workflow distributed with a project or team.

Skill
A reusable package of instructions and resources that an assistant can apply when it matches a task.

Plan mode
A workflow where the assistant proposes steps for approval before editing files.

Agent SDK
A programmatic interface for embedding an agent loop in application code with session control.

Prompting, output, and evaluation

System prompt
Stable instructions that frame a model's behaviour across a session, separated from variable user input.

Few-shot examples
Sample input–output pairs that anchor a format or judgement rule.

Chain-of-thought
Prompting for visible intermediate steps. Useful for multi-step tasks; not a guarantee of correctness.

Extended thinking
Additional model-side reasoning budget traded against latency and cost.

Temperature
Sampling parameter controlling randomness. Low for extraction, higher for generation.

Top-p / top-k
Sampling controls that restrict the token distribution. Interact with temperature, so change one at a time.

Structured output
Constraining a response to a schema so code can consume it as typed data.

Validation gate
A check that output must pass before it proceeds to the next stage.

LLM judge
A model used to score outputs against a rubric. Needs calibration and atomic questions.

Eval case
An input plus expected properties, not necessarily an exact expected string.

Stratified sampling
Sampling proportionally or deliberately across known slices so rare important cases are represented.

Context and provenance

Context window
The maximum tokens a model can consider in one call, including instructions, history, evidence, and output.

Context economics
The trade-off between cost, latency, and quality as context grows. More context is not free and not always better.

Context bloat
Unnecessary tokens from large tool outputs or repeated history that crowd out relevant evidence.

Fact block
A small, durable set of verified facts carried forward explicitly instead of being left to summarisation.

Compaction
Reducing a long context or session memory while preserving invariants and commitments.

Scratchpad
A bounded working-memory slot for current state and open questions.

Per-field confidence
Uncertainty reported for each value rather than one score for the whole answer.

Calibration
Adjusting confidence thresholds so stated confidence matches observed accuracy on a validation set.

Claim-to-source mapping
An explicit link from each claim in an answer to the evidence supporting it.

Conflict annotation
Surfacing disagreement between sources instead of silently choosing one.
