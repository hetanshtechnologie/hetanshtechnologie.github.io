22. Tool Scoping and Large Catalogs

Giving an agent every tool it might ever need feels generous, but it makes both the agent and the system worse. A smaller tool set is easier to reason about, cheaper to present, safer to expose, and more reliable to route. This chapter covers least-privilege scoping, how catalogs break down as they grow, and the discovery patterns that let a system have hundreds of tools without showing all of them to every agent.

Least Privilege as a Default

Least privilege is usually discussed as a security rule, but for agents it is also an accuracy rule. Every irrelevant tool is a candidate the model must reject. Remove the candidates that can never be right for this task and you remove a class of wrong answers before they start.

Apply the principle at three levels. At the environment level, an agent gets credentials only for the systems it is allowed to touch. At the tool level, the catalog exposes only operations permitted for the current role. At the task level, phase-based scopes can further narrow the set: a planning phase gets read-only tools, an execution phase gets the write tools needed for the approved plan.

Start with an empty tool set and add tools when a logged task requires them. The reverse — start with everything and remove tools after an incident — leaves a long tail of forgotten capabilities.

Scoping Tools per Agent

In a multi-agent design, scoping is what gives each role its identity. An orchestrator may need planning and coordination tools but no domain writes. A research worker may need search and read tools; a drafting worker may need templates and a revision store; only a publishing agent should see the publish operation. These boundaries are more reliable than instructions telling an agent not to use a tool it can see.

agents:
  planner:
    tools: ["list_tasks", "estimate_cost", "ask_human"]
  researcher:
    tools: ["search_docs", "get_record", "scratchpad_write"]
  publisher:
    tools: ["get_draft", "validate_draft", "publish"]
    requires_approval: ["publish"]
  defaults:
    deny_unlisted: true

Handoffs need care. When a subagent sends a result to the orchestrator, the receiving agent should not inherit the sender's tools; it should receive only the data it is allowed to act on. If a write capability must move between roles, do it with an explicit capability token that names the operation, target, and expiry. Silent inheritance is how a read-only planner acquires write access.

Dynamic scoping within one agent is useful too. A support agent in discovery mode sees lookup tools; after the issue is identified, the relevant remediation tools are added for that turn. This narrows decisions at each step while keeping the overall system capable. The scope change should be recorded in the trace so that post-incident review can reconstruct what the agent could see.

How Catalogs Degrade Selection

Catalog growth creates four problems. First, attention dilution: with fifty plausible tools, distinguishing the right one requires much finer judgement than with five. Second, description collision: large catalogs accumulated over time tend to contain near-duplicates — two search tools, three variants of "get user" — that confuse routing. Third, context cost: a catalog of 120 tools with roughly 60 tokens of name, description, and schema each consumes about 7,200 tokens before the user's request is even considered. Fourth, drift: nobody remembers why each tool exists, so stale entries survive indefinitely.

These effects interact. A large catalog raises cost, which encourages trimming descriptions, which reduces routing signal, which increases misselection. The result is a system that is expensive and unreliable at the same time. There is a practical ceiling: beyond roughly twenty to thirty simultaneously visible tools, most agents benefit from discovery-based patterns rather than a flat list.

Adding a tool is a permanent cost unless someone removes it. Treat a new tool as a change to the routing surface, not as an isolated feature addition.

Search Patterns for Large Catalogs

The standard solution is two-stage discovery. In stage one, the agent sees a small set of core tools, including a find_tool operation backed by an index of the full catalog. The agent describes what it needs; the index returns the top few matching tools with their descriptions and schemas. In stage two, the agent calls one of the discovered tools using its now-complete contract.

def discover(need, top_k=3, min_score=0.55):
    hits = index.search(need, fields=["name", "description",
                                      "tags", "example_intent"])
    chosen = [h for h in hits if h.score >= min_score][:top_k]
    if not chosen:
        return {"tools": [], "hint": "no_match_ask_user"}
    return {"tools": chosen, "hint": "inspect_then_call"}

Several details make this work. The index should be built from the same descriptions the model sees, so there is no gap between what search matches and what the agent reads. Keep a handful of universal tools always available — asking the user, checkpointing, and the discovery tool itself — so the agent is never stranded. Cache discovery results within a session: if a tool was found three steps ago, its description is already in context and need not be returned again.

Set an explicit relevance threshold. A search that always returns three tools will occasionally return three wrong tools, and the agent may act on the least-bad one. Returning nothing with a no_match hint is safer; the agent can rephrase the need or ask a person. For high-risk domains, require the discovered tool to be confirmed by a policy gate before execution.

Layered and Namespace Designs

An alternative to retrieval is hierarchy. Tools are grouped into namespaces such as billing.*, docs.*, and repo.*. The agent first selects a namespace, then sees only that namespace's tools. This mirrors how people navigate large APIs and produces predictable, explainable routing. The cost is an extra decision step and the need to maintain sensible categories.

Hybrid designs are common: a small core catalog plus namespace-level browsing plus search for everything else. Namespaces help humans reason about ownership and permissions; search helps agents find unfamiliar capabilities. Whichever design you choose, document the discovery path — a tool that cannot be found is functionally absent, no matter how well implemented.

Measuring Scoping Quality

Track four numbers. Selection accuracy is the fraction of decisions where the chosen tool was the intended one. Unused tool rate is the share of exposed tools never called in a representative sample; persistently unused tools are candidates for removal. Denial rate counts calls blocked by policy gates, which reveals whether agents are reaching for capabilities they should not have. Context overhead measures tokens spent on tool definitions per successful task.

Review the catalog monthly: add nothing without a logged need, merge near-duplicates, and archive tools with no calls for thirty days. Re-run a fixed benchmark suite after each change so that a scope reduction does not silently break a rare but important workflow.

Summary

  • Scope tools by environment, role, and task phase; unlisted capabilities should be denied by default.
  • Per-agent tool sets create real role boundaries; handoffs carry data, not inherited capabilities.
  • Large catalogs dilute attention, collide in description, cost context tokens, and drift over time.
  • Two-stage discovery with a small core set, a searchable index, thresholds, and caching scales better than a flat list.
  • Measure selection accuracy, unused tools, denial rate, and context overhead, and review the catalog regularly.
