18. Enforcement Layers, Hooks, and Human Oversight

"Never do X" written in a prompt is a preference, not a prohibition. It may be honoured on ninety-nine runs and ignored on the hundredth, and the hundredth may be the one that matters. This chapter is about turning preferences into guarantees: where to place deterministic checks, how to attach them to an agent's lifecycle, when to stop and ask a person, and what the extra machinery costs.

Why Instructions Wear Out on Risky Paths

A prompt is one input among many competing for the model's attention. As a conversation lengthens, early instructions sit farther from the current decision; a long tool transcript can crowd out the safety rule stated at the top. Even without crowding, the model is asked to balance objectives — be helpful, be fast, complete the task — and a rule expressed in natural language has no absolute priority over them.

The failure rate is low per step but compounds. If a constraint is violated with probability 0.01 on any given action, a forty-step run has roughly a one-in-three chance of seeing at least one violation. That is acceptable for a formatting preference and unacceptable for a destructive operation. Risky paths require enforcement whose probability of failure is closer to zero and does not degrade with conversation length.

There is also an asymmetry of cost. A missed formatting rule costs a rewrite; an unauthorised deletion costs recovery time, trust, and possibly data. Engineering effort should follow that asymmetry rather than be spread evenly across all rules. Classify each rule by the consequence of breaking it, then decide which enforcement layer it belongs in.

Do not treat a system prompt, a role description, or a repeated warning as a control. They shape behaviour; they do not constrain it. If the rule must never be broken, something outside the model must check it.

Programmatic Validation as a Gate

The strongest enforcement layer is ordinary software: a function that inspects a proposed action and returns allow or deny. It does not matter whether the proposal came from a careful model or a confused one; the check applies equally. Three kinds of validation are worth separating.

  • Structural validation confirms the call matches its declared shape: required fields present, types correct, enums within the allowed set, strings within length limits.
  • Policy validation applies business rules: the target account belongs to the current tenant, the amount is under the caller's approval limit, the path stays inside the working directory.
  • Outcome validation inspects the result before it is trusted: the returned row count matches the request, the diff touches only expected files, the computed total reconciles with the source.
def gate(action, ctx):
    if not schema_ok(action, ctx.tool_schema):
        return Decision(False, "schema_mismatch")
    if action.tool == "refund":
        if action.args["amount_usd"] > ctx.approval_limit:
            return Decision(False, "limit_exceeded", needs_human=True)
        if action.args["account_id"] not in ctx.tenant_accounts:
            return Decision(False, "cross_tenant", fatal=True)
    if action.tool == "write_file" and ".." in action.args["path"]:
        return Decision(False, "path_traversal", fatal=True)
    return Decision(True, "ok")

Place the gate before execution, not after it. Post-hoc detection of a destructive action is an incident report, not a control. Where a check cannot be done beforehand — for example, verifying that a database update affected exactly one row — make the tool itself return the affected count and validate that count in the same turn.

A deny decision should be a useful observation, not a dead end. Return a short machine-readable reason such as limit_exceeded plus the remediation path. The agent can then ask for approval instead of retrying the same forbidden call.

Lifecycle Hooks and Where They Fire

Hooks are registration points that run code at defined moments in an agent's lifecycle. They are the mechanism that makes enforcement automatic rather than dependent on the agent remembering to invoke it. The exact names vary between runtimes, but four positions appear almost everywhere.

PositionFires whenTypical use
Before tool callAfter the model proposes a call, before executionSchema and policy gates, audit logging, permission check
After tool callOnce the tool returnsOutcome validation, result redaction, metric capture
On step boundaryBetween reasoning iterationsBudget checks, progress detection, context trimming
On stop or errorRun terminates or throwsCheckpoint write, notification, cleanup, final audit entry

A hook configuration usually pairs an event with a matcher and a command. The matcher narrows which events trigger the hook; the command does the work. A practical set might validate every shell invocation, append every write to an audit log, and block any command containing a destructive pattern unless an approval token is present.

hooks:
  PreToolUse:
    - matcher: "shell|write_file"
      command: "python policy_gate.py --stdin"
      timeout_ms: 2000
      on_deny: "block_and_explain"
  PostToolUse:
    - matcher: "shell"
      command: "python redact_outputs.py --stdin"
  Stop:
    - command: "python checkpoint.py --write-final"

Keep hooks small and deterministic. A hook that calls a slow model to judge a command adds latency to every step and reintroduces the uncertainty the gate was meant to remove. If a hook must make a nuanced decision, have it produce evidence for a human reviewer rather than deciding on its own.

Interruption Points in a Workflow

Even with perfect gates, some decisions should not be made by a machine at all. An interruption point is a planned pause where the run stops, persists its state, and waits for external input. Unlike an error-triggered stop, it is expected: the design assumes the pause will happen on the normal path.

Good interruption points sit at boundaries of irreversibility or high cost. Before sending a message to a customer, before committing a transaction, before publishing generated content, and after a cumulative spend threshold are all sensible places. The pause should carry a resume token so that work already completed is not repeated when the run continues.

Interruption also solves a subtler problem: the agent's own confidence is not a reliable signal for escalation. A model can be confidently wrong. External triggers — amount, recipient, data sensitivity, operation type — are observable and auditable, so they make better interruption criteria than asking the agent "are you sure?".

Review Workflows and Approval Queues

Human oversight only works if the reviewer receives enough context to decide quickly. An approval request should bundle the proposed action, the policy rule that triggered review, the evidence the agent gathered, the predicted consequence, and the cost of rejecting. A reviewer seeing only "agent requests permission to run a command" will either click through reflexively or block everything.

Use risk tiers to keep queues manageable. Tier one actions — reads, drafts, calculations — proceed automatically with logging. Tier two actions — writes to shared resources, moderate spend — require a single approval. Tier three actions — irreversible writes, external communications, large transfers — require two approvers and a recorded reason. Sampling can cover tier one: review a random five percent to detect policy drift without slowing the pipeline.

Every decision, including approvals, belongs in an append-only audit log with a timestamp, actor, action hash, and outcome. Besides satisfying compliance needs, this log is the raw material for improving the system: it shows which rules fire often, which reviewers override the agent, and where automation is safe to expand.

The Cost of Multi-Agent Systems

Oversight has a price, and multi-agent designs multiply it. If one agent uses 8,000 tokens per task, four cooperating agents may consume 40,000 or more because each needs its own context, handoff summaries, and recovery attempts. Coordination adds another tax: messages must be serialised, interpreted, and reconciled, and every handoff is a chance to lose a constraint.

SituationPreferWhy
One clear objective, short trajectorySingle agentLower token and failure cost
Independent subtasks, parallelisableFan-out workersLatency gain offsets overhead
Conflicting incentives, e.g. draft vs auditSeparate rolesIsolation prevents self-approval
Deeply uncertain taskHuman plus agentJudgement cheaper than more automation

Failure modes also compound: a misrouted message in a four-agent chain can propagate through three subsequent decisions before anyone notices. The remedy is the same as for tool errors — validate every handoff against a schema and keep an outer watchdog that can stop the whole run. Add agents only when the benefit (parallelism, isolation, specialised context) exceeds this overhead.

Summary

  • Prompt rules are preferences with nonzero violation rates; risky paths need deterministic enforcement outside the model.
  • Use pre-execution gates for structural, policy, and outcome checks, returning machine-readable deny reasons.
  • Attach checks to lifecycle positions — before tools, after tools, at step boundaries, and on stop or error.
  • Plan interruption points at irreversible or expensive boundaries, with resume tokens and evidence-rich review requests.
  • Oversight must be priced: add agents only when isolation or parallelism outweighs token, coordination, and failure costs.
