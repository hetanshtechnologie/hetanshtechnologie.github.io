23. MCP Fundamentals and Primitives

Every application that wants to give a model access to external capabilities faces the same plumbing problem: how to describe an action, pass arguments, return results, and discover what is available. Without a shared convention, each application builds a private adapter for each integration. A standard protocol replaces that tangle with one connector shape. This chapter introduces that shape and the three primitives it exposes.

Why a Standard Protocol Exists

Consider ten agent applications and twenty useful systems. Without a common protocol, you may need two hundred adapters. With a common protocol, each application implements one client and each system implements one server — thirty pieces of work instead of two hundred. The benefit is not just fewer lines of code; it is a stable boundary that both sides can evolve independently.

The protocol defines messages and lifecycle, not product behaviour. It says how a server advertises a tool and how a client invokes it; it does not say which tool the model should pick or whether the call is wise. That separation is deliberate: the same server can be used by a coding assistant, a support bot, or a batch pipeline, each with different policies.

A protocol is a vocabulary, not an architecture. It makes integrations portable; it does not make them safe, cheap, or well designed. Those remain your responsibilities.

The Client–Server Model

In this model, the host is the application the user interacts with — an IDE, a chat client, or your own service. The host contains a client that manages a connection to a server, a separate process or service that exposes capabilities. One host may run several clients, each connected to a different server, and each server may offer tools, resources, and prompts.

The server is deliberately not the model. It does not decide when a capability should be used and usually does not see the conversation. It answers three kinds of questions: what do you offer, may I read this data, and please run this operation with these arguments. The host decides what to include in the model's context and enforces its own policies before a call is made.

A connection follows a predictable sequence. The client establishes a transport, sends an initialization message with its supported version and capabilities, and receives the server's capabilities in return. It then lists the available primitives, maintains them for the session, and invokes them as needed. Either side may send notifications when its offerings change, so a long-running host can refresh its view without reconnecting.

1. transport opened (stdio process or HTTP session)
2. client -> server: initialize {protocol_version, client_caps}
3. server -> client: initialize_result {server_caps}
4. client -> server: tools/list, resources/list, prompts/list
5. host exposes approved items to the model
6. client -> server: tools/call {name, arguments}
7. server -> client: result {content, isError, ...}

Servers can run locally as child processes — useful for filesystem or repository access — or remotely over HTTP — useful for shared enterprise services. The primitive model is the same in both cases, which is why the same server code can often be reused across deployments with only a transport change.

Tools, Resources, and Prompts

Three primitives cover most integration needs, and the distinction between them is about who decides to use them.

  • Tools are model-controlled operations. The model proposes a call with arguments; the host may approve it; the server executes it. Use tools for actions and computations: querying an API, creating a record, running a calculation.
  • Resources are application-controlled data. They have identifiers (typically URIs) and are read into context by the host or user, often because a person attached them or a rule selected them. Use resources for documents, schemas, logs, and reference data that should be inspectable rather than executed.
  • Prompts are user-controlled templates. A person or host selects a prompt by name, supplies parameters, and receives a ready-made message or sequence of messages. Use prompts for repeatable workflows such as "review this pull request" or "summarise this meeting".

Choosing the right primitive has practical consequences. Exposing a static policy document as a tool invites the model to fetch it at arbitrary moments; exposing it as a resource lets the host include it when relevant. Putting a write operation in a resource is impossible by design — resources are read-oriented. If you find yourself describing a resource as "run this with parameters", you probably want a tool.

Discovery and Capability Exchange

Discovery is what makes a connection useful without hardcoding. During initialization, each side declares what it supports — for example, whether the server offers prompts or sends list-change notifications. The client then asks for lists of tools, resources, and prompts. Each item carries a name, a description, and enough metadata for the host to decide whether to expose it.

Capability negotiation protects both sides. A client that does not understand a feature can still interoperate with a server that offers it, because the feature is declared rather than assumed. Version negotiation serves the same purpose across protocol revisions. Well-behaved clients cache discovery results and refresh them on notification, avoiding a full list call before every action.

server = Server("catalog", version="1.0")
return {
  "capabilities": {
    "tools": {"listChanged": True},
    "resources": {"subscribe": False},
    "prompts": {"listChanged": False}
  },
  "instructions": "Read catalog://schema before writing records."
}

Descriptions produced during discovery are part of the routing surface, exactly as in any other tool system. A server with thirty poorly described tools will be misrouted just as surely as an in-process catalog with the same problem. Keep descriptions short, specific, and stable, and change them with the same care you would change an API.

Use the server's instruction field for facts the client cannot infer — required setup steps, authority limits, or which resource defines the data schema. Do not use it to tell the model which tool to prefer; that is the host's policy.

What the Protocol Does Not Decide

It is easier to design systems when you know which questions the standard will not answer. It does not decide authorization: the host must determine whether a user may invoke a tool, and the server must still validate its own authority. It does not decide trust: a third-party server is untrusted input, and its descriptions and results should be treated as data, not instructions.

It does not decide model behaviour — tool selection, retry policy, and context budgeting live in the host. It does not define a universal error taxonomy beyond basic success or failure signalling, so each tool should carry its own structured error payload. It does not prescribe deployment, observability, or cost controls. Finally, it does not guarantee that a capability is safe: a tool can be perfectly described and still be a bad idea to expose.

Thinking in Primitives

When mapping a requirement, ask who should initiate. If the model should decide to act, build a tool. If the host or user should decide to include information, publish a resource. If a person should start a repeatable workflow, define a prompt. A read-only database query can be a tool when the model decides what to search for, or a resource when the host always attaches the same report. The same underlying operation can appear in both forms — the difference is control, not capability.

Summary

  • A standard protocol turns an N-by-M adapter problem into one client and one server per side.
  • The host contains the client; the server exposes capabilities and does not see or control the conversation.
  • Tools are model-initiated actions, resources are host-initiated data, and prompts are user-initiated templates.
  • Initialization exchanges versions and capabilities, followed by listing and refreshable discovery.
  • Authorization, trust, selection, error policy, and deployment remain application responsibilities.
