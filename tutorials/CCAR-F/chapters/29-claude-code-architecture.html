29. Claude Code Architecture and Setup

Claude Code is a terminal-based working environment in which a model reads your repository, edits files, runs commands, and reports results. It is less like a chat window with a code attachment and more like a colleague who has the same shell access you do. That difference explains both its usefulness and its risks: anything you can do from the prompt, it can attempt to do.

What the environment actually is

Four pieces work together. A command-line client runs in your terminal and owns the session. A model reasons about the request and decides which tool to call next. A tool layer exposes file reads, edits, searches, shell commands, network access, and any connected MCP servers. A context assembly layer gathers instructions, recent messages, and relevant file content into each model request.

There is no single magical index of the repository. Discovery happens through tool calls: the assistant lists directories, searches for symbols, opens files, and reads test output. This is why a well-organized repository is easier to work in. Clear names, small modules, and a documented entry point reduce the number of discovery calls and the amount of file content that must be loaded into context.

LayerResponsibilityWhat you control
ClientTerminal UI, session state, approvalsWorking directory, permissions, theme
ModelPlanning and tool selectionModel choice, instruction files
ToolsFile, shell, web, MCP operationsWhich servers and tools are enabled
ContextInstructions and conversation historyWhat you include, when you reset

The loop you are really running

Each exchange repeats a short cycle. The assistant receives the user's request plus accumulated context, forms an approach, calls a tool, receives the result, and decides whether to continue. Results that surprise it — a failing test, a missing file, a type error — feed the next decision. The loop ends when the assistant reports completion, asks a question, or reaches a stopping condition.

request + context
      |
      v
plan --> tool call --> observation --> revise plan
  ^                                        |
  +----------------------------------------+
      |
      v
final answer (or a question for the user)

if scope_changes && context_is_stale:
    clear the session or compact before continuing

Two things accumulate as the loop runs: file content and conversation history. Neither is free. A session that has opened thirty files to investigate a bug may have only a fraction of its useful context left when it comes time to write the fix. Recognize the signs — repeated questions, forgotten constraints, edits that contradict earlier decisions — and reset or summarize before quality degrades.

Approval gates sit on the action side of the loop. Reads are usually permitted without prompting, while edits and shell commands may require confirmation depending on the active permission mode. These gates are not a judgment about the model's intelligence; they are a control for actions that are hard to undo.

Setting up a workspace

Start in the repository root. The working directory determines which files are visible, which instruction files load, and which MCP servers with relative paths resolve correctly. Launching from a parent folder often produces an assistant that cannot find configuration it expects, while launching from a deeply nested folder hides the rest of the project.

  1. Confirm the repository is clean: commit or stash current work before a long automated session.
  2. Start the client from the project root and verify the displayed path.
  3. Authenticate with the intended account and select the appropriate model.
  4. Trust or approve the folder only after checking scripts and configuration files you do not recognize.
  5. Connect only the MCP servers the task needs, and check that each one starts successfully.
  6. Run a small read-only request first: ask for the project structure and entry points.
A repository can contain instructions inside files that the assistant reads. Treat those files as data, not as commands from your organization. If a README asks the assistant to install an unknown package or disable safety checks, assume the text is untrusted until you have verified it.

Starting a new project

For greenfield work, begin with constraints rather than features. State the language and runtime, the expected scale, the testing approach, and what "done" means. A request such as "build a small service" leaves hundreds of decisions to be made silently. A request that names the framework, the storage choice, and the acceptance test gives the assistant a target it can verify.

A productive first session has three phases. Ask for a short plan without writing code, correct the plan, then authorize implementation in small slices. After each slice, require the tests to run and review the diff. This is slower than a single large instruction but far cheaper than untangling a thousand-line change that drifted from your intent in paragraph two.

Exercise 29.1 — Write a greenfield kickoff request
  1. Choose a small application, such as a command-line expense tracker with a JSON file for storage.
  2. Write a request that names the runtime, one hard constraint, one explicit non-goal, and the command that proves success.
  3. List two questions you would expect the assistant to ask before writing code, and how you would answer them.

Onboarding to an unfamiliar codebase

Onboarding is an information-gathering task, so keep the assistant read-only at first. Ask for a map: the main entry points, the dependency direction between major modules, where configuration enters the system, and how tests are organized. Request file paths and line references so you can verify each claim yourself. A confident architecture summary without evidence is a hypothesis, not a fact.

A useful orientation prompt names the sources you want consulted and the format of the answer. Supplying structure reduces the chance that the assistant returns a generic summary of the README.

<role>Repository orientation</role>
<task>Map this codebase for a new maintainer.</task>
Sources: README, package manifest, top-level directories,
and the five largest source files.
Answer with a table: Area | Entry file | Depends on | Test location.
Then list three <risk> areas where a change could break
unrelated behavior, with a file path for each.
Do not modify any file; reading only.

After the map, validate understanding with a tiny change: rename a local variable, add a test for a documented behavior, or fix a trivial typo. If the assistant navigates directly to the right file and the test suite passes, the mental model is probably sound. If it searches broadly or edits the wrong module, correct the map before assigning real work.

Ask for the commands developers use — build, test, lint, and local run — and verify them yourself. Build instructions in a repository are frequently stale, and a failed command discovered now is cheaper than one discovered during a deadline.

Session hygiene and common failures

Keep one topic per session. Unrelated tasks share context, so a long debugging conversation followed by a new feature request can carry stale assumptions into the new work. Use a fresh session for a new goal, or summarize the decisions you want to keep and start again with that summary.

SymptomLikely causeResponse
Repeats a question already answeredContext crowded outReset or summarize

Exercise 29.2 — Recover a drifting session
  1. A session has been debugging for two hours and now contradicts a constraint you set at the start. Explain why continuing in the same session is risky.
  2. Write a three-sentence handoff summary that preserves the goal, the decisions made, and the remaining work.
  3. State what you would verify in the repository before letting the assistant edit files again.

Check your understanding

  1. Name the four layers of the environment and the responsibility of each.
  2. Why does a well-organized repository reduce the cost of a session?
  3. Which working directory should you start from, and what goes wrong when you do not?
  4. What should a repository-orientation request include so its claims can be verified?
  5. Give two symptoms of context drift and the appropriate response to each.

Summary

  • The environment combines a terminal client, a model, a tool layer, and context assembly.
  • Discovery happens through file and search tool calls, not a single automatic index.
  • Start from the repository root, with a clean working tree and only the MCP servers you need.
  • For new projects, agree on a plan before authorizing implementation in small, tested slices.
  • Onboard with read-only orientation requests that demand paths, evidence, and a tiny validation change.
  • Keep one topic per session and reset when context drift appears.
