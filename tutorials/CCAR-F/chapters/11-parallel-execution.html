11. Fan-Out, Fan-In, and Synchronization

Fan-out/fan-in is the most tempting pattern in agent design: split work among many workers, then gather the answers. Used well, it turns forty minutes into three; used carelessly, it yields contradictory results, duplicate writes, and a collector that starts too early. This chapter covers the plumbing that makes parallel execution predictable — partitioning, aggregation, race control, partial-failure policy, and the synchronization barrier between the two halves.

Anatomy of a fan-out/fan-in run

Three roles are involved. The dispatcher partitions the input into disjoint slices and creates one task per slice. Workers execute the same instruction against their own slice and return a structured result. The collector waits at a barrier, validates what arrived, and reduces the results into a single answer. Keeping these roles distinct matters: a worker that decides when aggregation begins, or a collector that silently repairs a worker's malformed output, makes the system impossible to reason about.

Partitioning should be deterministic. If there are 97 documents and a target slice size of 10, compute ceil(97 / 10) = 10 shards, nine of 10 items and one of 7. Use a stable key — document ID, line range, or a hash bucket — so a retry asks for the same slice rather than a different one. Random partitioning breaks idempotency: a retried worker may receive different items and write under a different result key, leaving duplicates behind. Pass a slice descriptor with every task: shard_index, item_ids, attempt, and input_digest.

RoleResponsibilityMust not do
DispatcherPartition, assign IDs, enforce worker capInterpret worker results
WorkerProcess one slice, emit typed result and errorsWrite directly to the final artifact
CollectorValidate, deduplicate, reduce, report gapsStart before the barrier releases

Aggregation: four ways to reduce results

The collector's reduction strategy must match the question. Four common strategies cover most cases:

  • Concatenate — appropriate when the answer is a list, such as all flagged lines. Preserve shard order for reproducibility.
  • Vote — appropriate for classification, where each shard returns a label. Require a quorum such as at least 3 of 5 workers agreeing, and record the margin.
  • Weighted reduce — appropriate when workers report conflicting values with confidence scores. Weight by confidence but cap the weight of any single shard, for example at 25%.
  • Structured merge — appropriate when each shard owns different fields of a shared record. Merge by key and reject collisions instead of choosing a winner arbitrarily.

Every strategy needs a tie-break rule decided in advance. If two shards claim the same record with different values and neither has higher confidence, the collector should emit a conflict item into the output rather than pick one. Silent winner selection is how a clean-looking report ends up contradicting its own sources. Aggregation should also produce a coverage summary — items submitted, items accepted, items rejected, items missing — so the caller can tell the difference between "all clear" and "nothing was checked."

Report both the answer and its provenance. A result such as { "flagged": 14, "shards": 10, "coverage": "97/97", "conflicts": 2 } is far more useful than a bare 14. It lets a reviewer decide whether to trust the number without rerunning the whole job.

Race conditions and shared state

Race conditions appear when workers touch a shared resource: a results file, a database table, a rate-limited API, or a common scratchpad. The safest design is to give workers no shared writable state. Each writes to its own key, such as result:{run_id}:shard:{index}:attempt:{n}, and only the collector assembles the final object. When shared writes are unavoidable, use three defences:

  1. Idempotency keys. Derive the key from the item and its digest, for example ticket:4471:sha256:9ab2. A repeated write updates the same record rather than creating a second one.
  2. Compare-and-swap. Include a version number; a write succeeds only if the stored version still matches the version the worker read. Otherwise the worker rereads and retries.
  3. Ownership scopes. Assign each shard a distinct namespace or partition, so shard:03 physically cannot write shard:07's keys.

Rate limits are a different kind of contention. Ten workers calling one external API simultaneously can turn a service's 60-request-per-minute limit into a burst of failures. Use a token bucket or a semaphore in the dispatcher, and record throttling as a distinct error class — a 429 response is retryable with backoff, while a 400 response is not. Parallelism should not be used to discover an API's limits at the worst possible moment.

Partial failure: decide the policy before you run

At moderate scale, partial failure is the norm rather than the exception. With 12 workers at 90% individual success, the probability that every worker succeeds is about 0.28. A design that assumes universal success will fail most runs. Choose one of three policies explicitly:

PolicyRuleUse whenRisk
All must passAny shard failure fails the runCompliance, exact billing, legal reviewHigh retry cost, low completion rate
QuorumAt least N of M shards, and minimum coverageClassification, voting, survey workMay hide systematic bias in missing shards
Best effortAccept successes, list gaps, mark partialExploratory analysis, draftsIncomplete results mistaken for complete ones

Give each worker a retry budget — commonly two additional attempts with exponential backoff and jitter for transient faults — and classify failures before retrying. Retry a timeout or a throttling response; do not retry a malformed input or a permissions error, because repeating the same cause wastes budget. A results envelope should record attempts, last_error_class, and terminal_reason, so the collector can distinguish "gave up" from "still running."

run:
  shards: 12
  retry_budget: 2
  backoff_ms: [500, 1500]
  on_failure:
    transient: retry_with_jitter
    validation: quarantine_and_report
    auth: abort_run
  barrier:
    quorum_shards: 11
    min_coverage: 0.95
    timeout_seconds: 180
  guard: if ( ok_shards >= 11 && coverage >= 0.95 ) -> aggregate()
         else -> mark_partial( include_gap_list: true )

Synchronization barriers and stragglers

A barrier is the rule that decides when fan-in may begin. The naive rule — wait for every worker forever — fails when one worker is stuck on a slow tool call. A practical barrier closes on the earliest of three conditions: all shards complete, a quorum plus minimum coverage is reached, or a timeout expires. Each condition must be recorded in the run log, because the meaning of the aggregated answer depends on which one fired.

Stragglers are workers that finish after the barrier closes. Decide their fate up front. Options are: discard them and note their IDs; admit them into a second, additive merge if the output supports it; or hold the final artifact as provisional until a deadline. Discarding is simplest but must be honest — the coverage figure should exclude straggler items rather than claim they were checked. Cancellation of stuck workers matters too: a worker that continues writing after the run ends can corrupt a later run that reuses the same keys. Propagate a cancellation token and verify that workers acknowledge it.

Barrier anti-pattern: premature aggregation. If the collector starts when the first shard finishes, the result depends on scheduling order, not on data. This produces different answers on identical inputs — the hardest kind of bug to reproduce. Always make the barrier explicit and observable.

Sizing the run: latency, cost, and coordination

Parallelism changes the cost shape. For N items, shard size S, and W workers, W = ceil(N / S). Wall time is approximately the longest worker plus aggregation, while token cost is the sum of all workers plus the merge. If 240 items take 5 seconds each to process and a merge takes 12 seconds, then with 24 shards of 10 items the ideal wall time is about 50 + 12 = 62 seconds, compared with 1,200 seconds for a single sequential pass. The same run at 2,000 tokens per shard and 8,000 for the merge costs 56,000 tokens. Doubling the worker count halves the ideal latency but doubles worker tokens and increases the chance of at least one failure.

Coordination overhead also grows. With 24 shards, a dispatcher sending a task, a worker acknowledging, a worker returning, and a collector acknowledging produces roughly 96 messages. At 100 tokens per message that is 9,600 tokens of envelope traffic, plus queueing delay. This is why very fine sharding eventually becomes slower: a shard of one item spends more time on messaging than on work. A useful lower bound is about 20 to 50 items per shard for cheap operations, or one substantial document per shard for expensive ones.

Summary

  • Keep dispatcher, worker, and collector roles separate and give each shard a deterministic identity.
  • Match the reduction strategy to the question, and always emit coverage and provenance with the answer.
  • Prefer private worker keys; when shared writes are unavoidable, use idempotency keys and version checks.
  • Declare all-must-pass, quorum, or best-effort policy before execution, with bounded retries by error class.
  • Close barriers explicitly on completion, quorum, or timeout, and account for stragglers honestly.
  • Size shards so that useful work dominates messaging overhead.
