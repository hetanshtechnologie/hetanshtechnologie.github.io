34. Slash Commands and Skills

What a custom command actually is

A slash command is a stored prompt template that a person invokes by name. Unlike free-form typing, it is reproducible: the same command expands to the same instructions in the same order every time. Commands are ordinary markdown files, not programs. When you type /review, the environment inserts the file's content into the conversation as a user turn. Nothing executes at expansion time unless the prompt asks the model to execute something.

That distinction matters for safety and for testing. A command is data that shapes attention; it is not a hidden script. Use commands for work with a stable shape: reviewing a staged diff, producing a release note, scaffolding a test file, translating a ticket into a plan, or running a prescribed investigation. Avoid them for one-off questions where typing naturally is faster.

A practical heuristic: if you have written the same 200-word instruction more than three times, write a command. If a teammate cannot predict the result from the command name alone, rename it.

Anatomy of a command file

Project commands live under .claude/commands/ and are committed with the repository; personal commands live in the user-level configuration directory. A file's name becomes the command name, and subdirectories form namespaces. Frontmatter at the top declares metadata; everything below it is the prompt body.

---
description: Review the staged diff for correctness and risk
argument-hint: [focus-area]
allowed-tools: Bash(git diff --cached), Read, Grep
---

Review the currently staged changes. Focus on $ARGUMENTS if provided.

Steps:
1. Read the diff with git diff --cached.
2. For each changed file, list one concrete risk with a file:line reference.
3. Check the convention in @CONTRIBUTING.md before commenting on style.
4. End with a verdict: APPROVE, REQUEST_CHANGES, or NEEDS_CONTEXT.

Do not modify files. Do not run tests unless I ask explicitly.
Verify with `npm run lint && npm test` only when I say "verify".
Keep the response under 400 words and use a markdown table.

The description is shown in command listings, so write it as an action phrase, not a noun. argument-hint documents what follows the command name. allowed-tools is a whitelist for that invocation; treat it as a boundary, not a suggestion. A review command that grants write access can quietly become an editing command, which defeats the purpose of a separate review step.

Notice how the body ends with explicit output constraints: length, structure, and a closed set of verdict values. Without those lines, the model produces a useful but variable essay each time. Variability is acceptable in conversation and harmful in a repeatable procedure.

Arguments, file references, and tool permissions

$ARGUMENTS substitutes the entire text after the command name. Positional placeholders such as $1 and $2 let you structure input: /migrate users status draft can map to a table name and a target value. Always tell the model what to do when an argument is missing — either ask for it or use a documented default. Silent substitution of an empty string is a common source of confusing output.

A reference written as @path/to/file injects that file's content at expansion time. This is excellent for small, stable policy documents and poor for large generated files. Every injected file consumes context on every invocation, so a 900-line style guide attached to a frequently used command is a recurring tax. Prefer a short pointer that tells the model to read the file only if the task requires it.

Failure mode: a command that says "check everything and fix what you find." It combines a broad scope with write permission and no stopping condition. Split it into a read-only diagnostic command and a separate, explicitly invoked fix command. Narrow tools and a clear terminal condition are more reliable than a polite request to be careful.

Permission boundaries should match the job. A command that only summarizes code needs read and search tools. A command that applies a codemod needs write access but should still avoid shell access unless the codemod is invoked through a fixed script. Grant the minimum capability and make the command fail visibly when it cannot complete, rather than silently degrading to a weaker behaviour.

Distributing commands across a team

Project-scoped commands are ordinary repository files, so the normal review process applies. Require a second reviewer for changes to commands that can modify files or run shell commands. Keep the repository copy authoritative; a personal command with the same name creates confusing divergence between teammates. If both scopes are present, document which one should win and verify it once rather than debating it repeatedly.

Namespaces reduce collisions. A command stored as .claude/commands/team/release.md reads as /team/release and signals ownership. Use verbs in names: /team/audit-schema is clearer than /team/schema. Keep descriptions under roughly a dozen words, and make them distinguish similar commands — "review a staged diff for risk" and "review an OpenAPI contract for breaking changes" are two different tools that a generic "review code" description would blur together.

Version commands alongside the code they operate on. When a build script changes its flags, the command that invokes it must change in the same pull request. A stale command is worse than no command because it produces confident, obsolete instructions.

Deciding between a command and a skill

Commands and skills differ mainly in who decides to use them. A command is user-invoked: a person types the name. A skill is model-invoked: the model reads its description and chooses to load it when the task appears relevant. That single difference drives most design decisions.

QuestionCommandSkill
TriggerPerson types /nameModel matches the description
Best forFixed procedure with a known startCapability that composes across tasks
DiscoveryListed by name in helpFound by semantic relevance
Context costPaid only when invokedPaid when selected; body can be loaded in stages
Failure signatureNever invoked, or invoked with wrong inputNever selected, or selected too often
A useful test: ask who should be surprised. With a command, the user should be surprised if the procedure does not run. With a skill, the user should be surprised if the model fails to notice that the skill is relevant. If neither sentence feels true, the behaviour probably belongs in an instruction file instead.

Choose a command when the workflow has a clear boundary — a release, an audit, a handoff. Choose a skill when the capability may be needed incidentally inside many different workflows, such as interpreting a particular file format or applying an organisation-specific analysis method. You can combine them: a command may state that a certain skill should be used, but keep the decision explicit rather than hoping both mechanisms trigger correctly.

Authoring and testing a reusable skill

A skill is typically a directory containing a SKILL.md file plus optional reference documents and deterministic scripts. The frontmatter carries a name and a description. The description is routing logic: it must name both the capability and the situations that should trigger it.

---
name: api-contract-review
description: Review an OpenAPI contract for breaking changes. Use when a task
  mentions an API spec, OpenAPI, Swagger, endpoint compatibility, or
  versioning a public interface.
---

# API contract review

1. Locate the specification (default: docs/openapi.yaml).
2. Compare it with the last released copy in docs/releases/.
3. Classify each change as compatible, additive, or breaking.
4. Require a migration note for every breaking change.

Rules:
- A renamed required field is breaking even when its type is unchanged.
- Adding an optional response field is additive.
- Never approve a breaking change without a version bump.

Reference: @references/compatibility-matrix.md
Checker: python scripts/check_contract.py --strict && echo PASS

Keep the main skill file short enough to read in one pass; detailed tables, examples, and edge cases belong in referenced files that are loaded only when needed. This is progressive disclosure: the model sees the existence of knowledge without paying for all of it up front. Scripts should do deterministic work that language models are unreliable at — comparing two schemas, computing a checksum, enumerating missing fields — and return compact, structured results.

Test a skill with three prompts. The first is a clear match that should select it. The second is a near miss that shares vocabulary but should not select it. The third is an unrelated task that should ignore it. If the clear match fails, sharpen the trigger words in the description. If the near miss selects the skill, narrow the description and add an explicit "do not use when" line. A vague description such as "helps with APIs" is the most common authoring error.

Summary

  • Commands are versioned prompt templates invoked by a person; skills are capabilities selected by the model.
  • Frontmatter controls discovery, arguments, and tool boundaries; the body controls the procedure and output.
  • Inject small stable documents, not large generated ones, and always define missing-argument behaviour.
  • Use namespaces, verb-based names, and review for commands that can modify state.
  • Write skill descriptions as routing rules, keep the main file short, and test match, near-miss, and non-match prompts.
