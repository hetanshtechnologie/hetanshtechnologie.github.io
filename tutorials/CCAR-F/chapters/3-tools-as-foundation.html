3. Tools as the Basis of Agency

A language model on its own transforms text into text. It can reason, summarise, and propose, but it cannot inspect a live database, send a message, or change a file. Agency begins at the moment you give it something it can call. Tools are not an accessory to an agent; they are the mechanism that turns deliberation into effect. The design of those tools — their names, descriptions, schemas, and permissions — determines what the system can do far more than the wording of its prompt.

Why access to actions creates agency

Consider two systems with an identical model and system prompt. The first can only answer from its weights and the current conversation. The second can call get_order_status, search_knowledge_base, and issue_refund. The first is an advisor; the second can pursue a goal in the world. Nothing about the model changed. The difference is that the second system has an action space, and an action space plus a loop is what we mean by an agent.

This is why tool design precedes loop design in this book. A loop with no actions merely rewrites its own thoughts; a loop with poorly specified actions makes confident mistakes at machine speed. Before you decide how many iterations to allow, you must know what an iteration can do. Tool access defines the boundary of possible behaviour, so it is the first safety decision you make.

The practical consequence is that capability should be added incrementally. Start with read-only tools that let the system observe the environment. Verify that its reasoning is sound with those tools. Only then add narrow write tools, one at a time, with explicit authority checks. A team that begins with full write access learns about failures from production incidents; a team that begins with reads learns from traces.

Terminology used here. A "tool" is a callable operation exposed to the model with a declared interface. A "tool call" is one invocation of it. The "action space" is the set of tools available in a given step. These terms are used consistently throughout the book regardless of the transport or framework involved.

Anatomy of a tool contract

A tool contract has four parts: a name, a description, an input schema, and a result shape. The model sees all four when it decides whether and how to call the tool. The name should be short, verb-first, and unique within the catalog. The description states what the tool does and — importantly — when it should and should not be used. The schema declares parameter types, required fields, enums, and constraints. The result shape tells the model what it will get back, including how failures appear.

{
  "name": "search_orders",
  "description": "Find orders by customer email or order id. Use for lookup only. Do not use to modify or cancel orders.",
  "input_schema": {
    "type": "object",
    "properties": {
      "customer_email": { "type": "string", "format": "email" },
      "order_id": { "type": "string", "pattern": "^ORD-[0-9]{6}$" },
      "status": { "type": "string", "enum": ["pending", "shipped", "delivered", "returned"] },
      "limit": { "type": "integer", "minimum": 1, "maximum": 50, "default": 10 }
    },
    "required": ["customer_email"],
    "additionalProperties": false
  },
  "returns": { "orders": ["Order"], "truncated": "boolean" }
}

Notice the details that make the contract usable. The pattern on order_id prevents a malformed identifier from reaching the service. The enum on status turns a free-text guess into a validated choice. The bounded limit stops a runaway query. Setting additionalProperties to false rejects invented parameters. Each of these is small on its own; together they remove a large class of tool-call errors before any business logic runs.

The result shape matters just as much. If a failed lookup returns an empty string, the model cannot distinguish "no orders" from "service unavailable." If it returns a structured object such as {"status":"error","retryable":true,"reason":"timeout"}, the loop can decide whether to retry, ask the user, or stop. Error contracts are part of the interface, not an afterthought.

Descriptions are routing instructions

Models select tools largely from the text they read. A description that says "search" competes with every other search tool; a description that says "look up historical invoice documents in the finance archive, excluding draft invoices" is far easier to route correctly. This is not prompt magic — it is disambiguation. If two tools overlap in purpose, the model must guess, and guessing produces wrong calls.

A useful pattern is to write each description with three clauses: the operation, the appropriate situation, and an explicit exclusion. Compare "manages users" with "creates a new internal user account. Use only after identity verification is complete. Never use to change permissions — call update_role instead." The second version gives the model a decision rule and removes a dangerous overlap.

Read actions versus write actions

The most consequential property of a tool is whether it changes state. Read actions — searches, lookups, computations — are generally safe to repeat and safe to delegate. Write actions — sending email, changing records, spending money, deleting files — are not. They may be irreversible, externally visible, and subject to policy. Treating both categories the same is a common and expensive mistake.

PropertyRead toolWrite tool
RepeatabilityIdempotent in practiceMay duplicate effects
ReversibilityNot applicableOften requires manual compensation
Retry policyRetry freely with backoffRetry only with an idempotency key
Approval needRareRequired above a threshold
Default scopeBroad, filtered by queryNarrow, filtered by resource

Idempotency is the key engineering lever on the write path. If a refund tool accepts a client-generated key and the server records it, a retried call with the same key produces one refund rather than three. Without that key, a timeout after the server committed the change leaves the model unsure whether to retry — and a retry can double the effect. Design write tools so the model can supply a stable key derived from the task, such as refund-ORD-104827-1.

Failure mode: a write tool that reports a timeout even after the change was applied. The model sees failure and retries; the system performs the action twice. Solve this in the tool implementation with an idempotency key and a truthful result, not by instructing the model "be careful not to call twice."

Authority boundaries and least privilege

Authority boundaries live outside the model. The model can request an action; a policy layer decides whether the request is permitted. This separation matters because a prompt can be manipulated by untrusted content — a document the system reads might contain instructions that try to redirect it. If the tool layer enforces scope, the worst such manipulation can achieve is a denied call.

Make boundaries concrete. A support agent may read any ticket but may issue refunds only up to 50 currency units, only for orders in its assigned region, and only when a verification flag is present. Encode these as parameters checked by the tool, not as sentences in the prompt. A check such as amount <= 50 && region == agent.region && verified == true is deterministic and auditable; "only refund small amounts when appropriate" is neither.

  1. Define the resource a tool may touch — a table, a directory, a set of endpoints.
  2. Define the operation allowed on it — read, create, update, delete.
  3. Define quantitative limits — amount, row count, file size, call rate.
  4. Define who grants exceptions and how the grant is recorded.
  5. Log every denied call with the reason and the originating task identifier.

A useful pattern is separate credentials for separate tools. The read tool uses a token with select-only permissions; the write tool uses a different token with narrowly scoped update rights. If one credential leaks or one tool is exploited, the blast radius is contained. This is defence in depth applied to agency: even a confused or coerced model cannot exceed the operating-system-level grant.

Summary

  • Tool access is what turns a text transformer into an agent; the action space defines possible behaviour.
  • A tool contract combines a name, a description, an input schema, and a result shape that includes failure information.
  • Descriptions act as routing instructions; disambiguate by stating operation, situation, and exclusion.
  • Read tools can be retried freely; write tools need idempotency keys, narrow scope, and often approval.
  • Authority boundaries belong in a policy layer with separate credentials, not in natural-language instructions.
  • Add capability incrementally: reads first, then narrow writes, verifying with traces at each stage.
