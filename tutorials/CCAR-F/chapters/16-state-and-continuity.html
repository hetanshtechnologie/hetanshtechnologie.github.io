16. State, Memory, and Session Continuity

An agent that remembers nothing must rediscover everything; one that remembers too much rereads history and acts on obsolete facts. State management decides what the system knows, where it lives, how long it stays valid, and how it survives a crash. Chapter 15 covered messages; this chapter covers the durable substrate beneath them: a message is an event, state is the accumulated result of events the system chose to keep.

In-context state versus external state

In-context state is what the model sees now: instructions, conversation, tool results, injected notes. External state lives in files, databases, caches, or artifact stores. In-context data is immediately available but expensive, volatile, and capped by the window; external data is durable and cheap per byte but needs an explicit read and can be stale.

PropertyIn-contextExternal
AvailabilityImmediate, no tool callRequires lookup and parsing
DurabilityLost when the call or session endsSurvives process restarts
Practical sizeThousands of tokens, competing with reasoningMegabytes to terabytes
Cost of accessPaid on every turn that includes itPaid only when read
SharingNot shareable between agentsShareable with locking or versioning
Failure riskSilent omission after compactionMissing key, stale version, corrupt write

Keep the current objective, active constraints, recent decisions, and artifact identities in context; keep full documents and transcripts externally. In a 200,000-token window, reserving 8,000 to 16,000 tokens for a compact state block is a reasonable start. Loading 150,000 tokens of history "just in case" raises cost every turn and hides relevant details.

Four key spaces, not one bag of memory

Separate remembered data into four namespaces with different lifetimes and owners:

  • Run state — ephemeral facts for one execution: plan version, current stage, retry counters, checkpoints. Lifetime: one run. Owner: orchestrator.
  • Session memory — user preferences, confirmed facts, and decisions that should persist across runs in the same conversation. Lifetime: one session, with expiry. Owner: session manager.
  • Artifact store — immutable outputs such as drafts, extracted tables, and evidence files, addressed by content hash. Lifetime: project or retention policy. Owner: the system.
  • Knowledge and configuration — instructions, schemas, reference documents. Lifetime: until explicitly changed. Owner: maintainers.

Use explicit, versioned keys such as run:8f3c:stage:2:checkpoint. A key should say what it holds and who owns it; naming state data invites unrelated overwrites. Store a schema_version too: a checkpoint from plan version 3 must not be replayed by version 4 without migration, since field meanings may have changed.

Content addressing. Name artifacts by a hash of their bytes, for example sha256:9c41...:v1. Two agents that produce identical content get the same key, which makes deduplication free and makes "did this result change?" answerable by comparing strings instead of rereading documents.

Persistence and write discipline

State is useful only if a write is complete or absent — never half-finished. Use atomic checkpoints: write to a temporary key, then swap the pointer. For files, write a temporary file and rename it; for object stores, write a versioned object and update an index. Include a checksum and timestamp so readers can detect corruption or staleness.

The order of writes matters around side effects. Before an irreversible external action — sending a message, paying an invoice, deleting a record — write an intent containing the action, its target, and a unique idempotency key. After the action succeeds, write the completion record with the external transaction ID. If the process dies between the two writes, recovery sees an intent without a completion and can query the external system using the idempotency key instead of blindly repeating the action. This pattern is small, but it removes the most dangerous ambiguity in agent recovery: "did I already do it?"

checkpoint:
  run_id: run-8f3c
  stage: verify
  schema_version: 2
  input_digest: sha256:4a10bd9e
  status: intent | complete | failed
  side_effect: { type: publish, key: pub-771, external_id: null }
  guard: if ( status == "intent" && external_id == null ) -> query_before_retry
  freshness: if ( age_seconds > 3600 ) -> revalidate_source

Escape weathering as a design requirement too. Not every fact deserves forever: customer preferences might live for 90 days, extracted source facts until the source version changes, and derived summaries until their inputs are replaced. Give each namespace a default time-to-live and a way to mark a fact as confirmed by a user, which typically extends its lifetime. Without expiry, a system gradually becomes confident in contradictions.

Crash recovery: replay, repair, or resume

Imagine a six-step run that crashes immediately after step 3 writes its artifact but before it marks step 3 complete. Recovery has three options, in increasing order of sophistication:

  1. Restart from step 1. Safe but wasteful, and unsafe if step 1 has side effects.
  2. Resume from the last completed checkpoint, step 2, repeating step 3. Requires step 3 to be idempotent.
  3. Repair by inspecting the partial artifact from step 3, confirming it against the intent record, and marking it complete if valid.

Most production systems implement option 2 and add option 3 for expensive or externally visible steps. To make resume correct, every step must be idempotent: the same input digest and the same step name must produce the same key and the same effect. Retry counters belong in run state, with a cap — commonly 3 attempts for transient failures and 0 for validation failures, since repeating a malformed input will not repair it. A recovery routine should also log why it chose a path: "resumed at step 3 because checkpoint complete and digest matched" is far easier to audit than a silent jump.

Do not replay on stale inputs. A checkpoint is only valid for the input digest and configuration version it recorded. If the source document changed while the process was down, replaying step 3 against the old digest produces a result that no longer matches reality. Revalidate the digest before resuming; if it differs, invalidate downstream checkpoints and restart from the affected stage.

Session identity and continuity across interactions

Three identifiers prevent most continuity bugs. A run ID identifies one execution attempt. A session ID identifies a conversation or user engagement across many runs. A thread or task ID identifies a line of work inside a session, which may span several runs and be resumed after a pause. Persist all three in the state block, and include them in tool calls and logs. When a user asks "continue where you left off," the system needs to resolve the session to the right thread, then the thread to the latest run, then the run to its last valid checkpoint. Without explicit IDs, the system guesses from recent text — and guesses become particularly unreliable after context compaction.

Continuity also has a social dimension. A session that stores personal data needs a retention policy, an access boundary, and a way for a user to inspect or delete remembered facts. Treat memory writes as privileged operations: record what was stored, why, and on whose authority. When resuming after a long gap, present a short digest of remembered facts ("I still have the target schema and your preference for metric units") and let the user correct it. That single step catches a surprising number of stale assumptions before they turn into bad work.

Security and cost trade-offs

Every remembered byte is a potential liability and a potential expense. Credentials should never enter session memory or artifacts; keep them in a secret store and pass short-lived handles. Logs should record state keys and digests, not full values, unless the values are explicitly non-sensitive. On the cost side, load state in tiers: a compact always-present block, a second tier fetched when a task touches a specific namespace, and a third tier of raw artifacts fetched by identifier. A useful budget test is to ask what happens if the second tier is unavailable: a well-designed agent degrades to asking for clarification rather than inventing missing facts.

Exam mindset. When a question describes lost context after a restart, the correct answer is usually external durable state plus an explicit resume protocol — not a longer prompt. When it describes a duplicated side effect, look for a missing idempotency key or a missing intent record, not a retry-count problem.

Summary

  • Keep current goals and artifact identities in context; keep full data and history externally.
  • Separate run state, session memory, artifacts, and configuration into distinct versioned namespaces.
  • Write checkpoints atomically, and record intent before side effects with an idempotency key.
  • Validate digests and versions before resume; invalidate downstream checkpoints when inputs change.
  • Use run, session, and thread IDs to make "continue where you left off" deterministic.
  • Apply retention, access control, and tiered loading to keep memory useful and inexpensive.
