45. Escalation and Error Propagation

Every agent will eventually meet a situation it cannot resolve: a tool is down, the request is ambiguous, or confidence is too low to act safely. What happens next is a design decision, not an accident. Escalation decides who takes over; error propagation decides what information travels with the failure. Get these wrong and you get the most expensive kind of bug — one that produces a confident, plausible, wrong answer instead of an error.

Escalation triggers

Escalation should be triggered by explicit conditions, not by a vague feeling that the model is struggling. Define triggers across four categories:

  • Capacity triggers. Turn count, tool-call count, or retry budget exhausted. These are deterministic and easy to test.
  • Confidence triggers. The top answer's score falls below a threshold, or the gap between the top two candidates is smaller than a margin such as 0.08.
  • Authority triggers. The requested action exceeds the agent's permission — refunds above a limit, deletion of records, or commitments to a customer.
  • Ambiguity triggers. Required slots remain unfilled, or two interpretations of the request lead to materially different actions.

Assign each trigger an action: retry, ask the user, route to another agent, or hand to a human. A trigger with no assigned action is a TODO that will surface as a production incident. For example, "refund above 200 units" might route to a human with a pre-filled payload, while "search returned no results" might simply ask the user to rephrase. Both are escalations; they differ in destination and urgency.

Prefer a small number of well-named triggers over a long list of special cases. Six triggers you can explain and test beat twenty conditions buried in a prompt that nobody can audit.

Handoff payloads

When control moves to a human or another agent, the receiving party needs enough context to continue without re-asking everything. A handoff payload is a structured bundle containing the original goal, the facts established so far, the actions already attempted, the reason for escalation, and the specific decision required.

{
  "handoff_id": "H-9031",
  "reason": "AUTHORITY_LIMIT",
  "goal": "issue a refund for order ORD-77150",
  "established_facts": {
    "order_id": "ORD-77150",
    "amount_units": 260,
    "policy_cap_units": 200
  },
  "attempts": [
    {"tool": "orders.lookup", "result": "ok"},
    {"tool": "refunds.create", "result": "blocked_by_cap"}
  ],
  "question": "Approve a 260-unit exception refund?",
  "suggested_action": "approve_once",
  "guard": "amount_units > policy_cap_units && approval == null"
}

Three qualities make a payload useful. It is self-contained — the receiver need not open the original transcript to understand the case. It is ordered — attempts appear in sequence so the receiver sees what has already failed. And it is actionable — it ends with a concrete question and, where appropriate, a suggested action. A payload that says "needs review" without a question forces the receiver to reconstruct the problem and defeats the purpose of escalation.

Include the guard that fired. The guard string in the example makes the reason auditable: it shows the exact comparison that blocked the action. When a reviewer disputes an escalation, the guard tells you whether the rule or the data was wrong.

Local versus upstream error handling

Errors can be handled where they occur or passed up the call stack. The right choice depends on whether the local component has enough information to recover.

SituationHandle locallyPropagate upstreamRationale
Tool returns a transient 429 rate limitYes — backoff and retry onceOnly after retries failLocal layer knows the retry budget
Tool returns a schema violationYes — retry with corrected argumentsIf repeated twiceArgument shape is local knowledge
Required user slot is missingRarelyYes — ask the userOnly the conversation layer can ask
Action exceeds authorityNoYes — escalate immediatelyLocal layer cannot grant permission
Two tools disagree about a valueNoYes — carry both with sourcesResolution needs cross-tool context

A useful heuristic: handle locally what the component can verify and fix; propagate what requires a decision the component is not entitled to make. Swallowing an error at the wrong layer is how silent bugs are born. If a tool wrapper catches an authentication failure and returns an empty list, the model sees "no results" and confidently tells the user the record does not exist. The truth — that the system could not check — never propagates.

Never convert a failure into an empty success. An empty list, a null value, or a default score that is indistinguishable from a real result destroys the receiver's ability to detect the error. Carry an explicit status field such as ok | empty | error through every layer.

Propagation contracts

A propagation contract defines how errors and partial results move between components. It specifies the status vocabulary, which fields must be preserved, what may be transformed, and which layer owns the final user-facing message. Without a contract, each layer reinvents the error format and information is lost at every seam.

  1. Define a status enum. Use ok, partial, empty, error, and blocked. Each has a defined meaning and a defined next step.
  2. Preserve identity. Request ids, source ids, and timestamps survive every hop. Never replace them with a friendly phrase.
  3. Accumulate, do not overwrite. If three sub-tasks fail, the parent result should list all three, not just the last one.
  4. Separate internal detail from user text. The internal error carries codes and stack context; the user message is derived from it at the boundary, with technical detail removed.
  5. Log at the point of detection. The first component that notices an anomaly records it, so the trail begins at the truth.

Test propagation with fault injection: make one tool return a rate limit, another return malformed JSON, and a third return a slow timeout. Assert that the final output carries all three statuses with their identifiers. A system that passes this test can be debugged; one that collapses everything into "something went wrong" cannot.

Ambiguity and silent bugs

The most dangerous failures are not loud errors but ambiguities that the model resolves on its own. A user asks to "send it to the usual address." If two addresses are on file with equal recency, the model may pick one arbitrarily. The action succeeds, the tool returns ok, and nobody detects a problem until a package arrives in the wrong place.

Silent bugs share a signature: the system had insufficient information, but produced a confident result anyway. Detect them by monitoring for conditions that should force a question. If the same entity appears with two conflicting values, if a pronoun has more than one plausible referent, or if a required field was inferred rather than stated, require disambiguation before acting.

Add a cheap consistency probe for high-stakes actions. Before executing, ask a second pass: "List the assumptions this action depends on." If any assumption is not backed by a fact block entry or a tool result, treat it as unresolved. This costs one extra short call but catches the classic case where the model silently filled a gap with a plausible guess.

Disambiguation patterns

When ambiguity is detected, how you ask matters as much as asking at all. Four patterns work well:

  1. Offered choices. "I have two addresses: home and office. Which one?" Fast for the user, easy to validate.
  2. Contrastive restatement. "Do you mean the invoice from March, or the one we just discussed?" Useful when the candidates differ on one dimension.
  3. Assumption plus confirmation. "I'll use the office address unless you say otherwise — confirm?" Efficient, but only acceptable for reversible actions.
  4. Constrained repair. "The date must be a weekday in November; please give one." Best when the earlier value violated a rule.

Match the pattern to reversibility. For irreversible or high-cost actions, never proceed on an assumption; require an explicit answer. For low-cost reversible actions, an assumption with a visible confirmation keeps the dialogue moving. Record which pattern was used so you can measure whether users actually answer the question — a disambiguation that users ignore is a design failure.

Exercise 45.1 — Build a trigger table. For a travel-booking agent, define six escalation triggers covering capacity, confidence, authority, and ambiguity. For each, specify the exact numeric or logical condition, the destination (retry, user, another agent, human), and the one field that must appear in the handoff payload. Identify which two triggers could produce silent bugs if ignored.
Exercise 45.2 — Test a propagation contract. Design a fault-injection test with three failing tools: one rate limit, one malformed response, and one timeout. Write the expected final result including status vocabulary and preserved identifiers. Then show a wrong implementation that converts one failure into an empty success and explain how your test catches it.

Escalation rates are not a sign of weakness; they are a measurement instrument. A sudden rise in authority escalations may mean a policy changed without updating the agent. A rise in ambiguity escalations may mean a new user segment uses different vocabulary. A drop in escalations can be worse than a rise if it coincides with more complaints — that combination often means the model has started guessing instead of asking. Track escalation counts by trigger, review the payloads weekly, and treat each one as free feedback about where the design needs sharpening.

Summary

  • Trigger escalation with explicit numeric, confidence, authority, and ambiguity conditions.
  • Send self-contained, ordered, actionable handoff payloads that include the fired guard.
  • Handle errors locally only when the component can verify and fix them; otherwise propagate.
  • Enforce a propagation contract with a status vocabulary, preserved identifiers, and accumulated failures.
  • Counter silent bugs with consistency probes and match disambiguation patterns to action reversibility.
