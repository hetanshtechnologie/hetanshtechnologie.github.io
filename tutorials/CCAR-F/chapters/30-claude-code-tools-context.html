30. The Tool System and Context Management

Tools are the hands of the coding environment; context is its field of view. A capable model with poor tool discipline wastes time opening the wrong files. A good tool set with a cluttered context produces edits that ignore constraints stated twenty turns ago. This chapter treats both as engineering concerns with measurable failure modes.

The tool families

Most work is done with five families. File reading and searching locate information. Editing tools change files. Shell tools run commands and verify results. Web tools fetch current external information. MCP tools connect to systems outside the repository. Each family has a different risk profile and a different verification strategy.

FamilyStrengthsPrincipal risk
Read and searchFast, repeatable, no side effectsFlooding context with whole files
Edit and writePrecise changes to known locationsAmbiguous match changes the wrong text
ShellVerification, builds, git operationsDestructive or long-running commands
WebFresh documentation and factsUntrusted text treated as instructions
MCPDomain data and actionsOver-broad tool catalogs

A useful mental rule: reads are cheap, edits are consequential, shell commands are powerful, and external content is untrusted. The order in which you grant these capabilities should follow that rule, especially when setting permissions for automated sessions.

Reads, search, and file discovery

Effective discovery narrows a search in stages. Start with a filename pattern or a directory listing, then search for a symbol within the candidate files, then read a bounded line range around the match. Asking for "the whole repository" at once is the equivalent of dumping every book in a library onto a desk: the answer you need is present but buried.

# 1. Locate candidate files by name, excluding generated output
find src -name "*invoice*" -not -path "*/generated/*" -print

# 2. Locate the symbol inside those candidates
rg -n "class Invoice|def calculate_total" src --glob '!**/vendor/**'

# 3. Read only the relevant window (line numbers from step 2)
sed -n '118,176p' src/billing/invoice.py

# 4. Guardrails the assistant should apply to itself
if match_count > 40 or file_lines > 400:
    narrow_the_query()      # add a path, a type, or a date bound
if text_contains("<generated>"):
    skip_file()             # generated content is noise, not source

Line references matter. "Look at src/billing/invoice.py:118–176" is actionable; "look at the invoice code" is a search task. When you already know the location, give it. When you do not, ask the assistant to report the paths it used so you can judge whether the exploration was sensible.

Search results should be treated as leads, not truth. A symbol may have three definitions, only one of which is used on the path you care about. Follow imports or call sites for one more hop before assigning a behavior to a file. That extra hop is inexpensive compared with editing the wrong implementation.

Edits: from strings to patches

Small edits are usually expressed as an exact string replacement: locate a unique block and substitute a new one. Larger edits are better expressed as a patch with surrounding context lines. Both approaches rely on uniqueness. If the target string appears in five files, or twice in the same file, an edit may land somewhere you did not intend.

Before authorizing a multi-file change, ask which files will be touched and why. After the edit, require a diff review and a test run. Re-reading the modified region is worthwhile: a successful tool result means the operation ran, not that the resulting code is correct. Watch for whitespace normalization, line-ending changes, and accidental edits to generated files that will be overwritten by the next build.

Shell and web tools

The shell is the verification engine. Use it to run tests, type checks, linters, migrations in a scratch database, and git commands that show the current state. A workflow that edits code but never runs the project's checks is relying on hope. Give commands explicit timeouts — 120 seconds for unit tests, longer for a full build — and ask for the exit code, not just the last few lines of output.

Some commands deserve a hard stop. Anything that deletes files outside a scratch directory, force-pushes a branch, rewrites git history, or installs an unvetted package should require human approval every time. A useful safeguard is to work on a feature branch so that an unwanted change can be discarded by returning to the previous commit.

Web tools answer questions the repository cannot: current library behavior, API changes, and version-specific guidance. Fetch documentation from primary sources when possible, and treat every retrieved page as untrusted data. A documentation page can contain prompt-like phrases embedded in examples or comments; those phrases are content to summarize, not instructions to follow. Ask for a source URL with each factual claim so you can check it.

Never copy a shell command from a web page into an approval prompt without reading it. The same caution applies to configuration snippets and "quick fix" scripts found in issue threads.

Adding context on purpose

Context is most valuable when it is specific and small. Tell the assistant which files define the contract, which tests express the expected behavior, and which decision from an earlier discussion still applies. Include type definitions or schemas rather than describing them in prose. If output shape matters, show one example of the desired result.

Context you addWhen it pays off
Exact path and line rangeThe relevant code is already known
A schema or type definitionData shape drives the implementation
One worked exampleOutput format must be consistent
A constraint from earlierLong sessions risk losing it
The test commandSuccess needs an objective check

Progressive disclosure beats bulk loading. Start with a short request that identifies the goal and asks which files are needed. Supply additional files only when the assistant's questions show a genuine gap. This keeps the context window available for reasoning and for the tool results that arrive later.

If you find yourself pasting the same background into several requests, that background belongs in an instruction file rather than in conversation. Repeated context is a signal to move knowledge into configuration.

Indexing, ignore rules, and large repositories

File discovery is shaped by ignore rules. Generated directories, dependency folders, build output, and large binary assets should be excluded so that searches return source rather than noise. A monorepo with 80,000 files and no ignore configuration turns every search into an expensive scan and every answer into a list of duplicates from three generated copies.

Check that hidden files and untracked files are visible when they matter. A new module not yet added to version control may still need to be discovered, while a local secrets file must stay out of any context that will be transmitted. Review the effective set of included paths before a large investigation, and consider a separate tool or MCP server for repositories whose structure defeats simple search.

Index freshness is a common failure. An index built before a branch switch still describes the old tree, producing references to files that no longer exist. Rebuild or invalidate cached indexes after switching branches, pulling large changes, or generating code. If search results consistently mention a deleted path, suspect stale state before suspecting the model.

Summary

  • Reads, edits, shell commands, web access, and MCP tools form a capability set with distinct risks.
  • Narrow discovery from filenames to symbols to bounded line ranges; cite paths and line numbers.
  • Make edits unique, require a diff, and verify with the project's own checks.
  • Use the shell for objective verification and the web for fresh facts, never as a source of instructions.
  • Add small, specific context: file ranges, schemas, examples, constraints, and test commands.
  • Configure ignore rules and refresh indexes so file discovery reflects the current branch.
