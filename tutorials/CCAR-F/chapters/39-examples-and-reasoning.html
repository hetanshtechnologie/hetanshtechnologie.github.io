39. Examples and Visible Reasoning

Why examples change behaviour

A rule describes a category; an example shows a member of it. When you write "classify severity as low, medium, or high," the model must infer the boundary between adjacent labels from the words alone. When you follow the rule with three classified cases, the boundaries become observable. Examples also anchor format: a single well-formed output row does more to shape punctuation, field order, and level of detail than a paragraph describing them.

This is why few-shot prompting remains useful even in systems that follow instructions well. It is not a trick to make the model smarter. It is a way of transferring tacit knowledge that is hard to state: what counts as a "material" risk, how terse a summary should be, whether an escalation includes a suggested fix. Those judgements are easier to demonstrate than to define.

Examples are not free. Each one consumes context and attention, and a poorly chosen example can be more damaging than none. A single atypical case can teach the model that the exception is the norm. Treat examples as part of the specification and subject them to the same review as rules.

Designing a few-shot set

Start with three to five examples for a classification or extraction task. Fewer than three leaves boundary behaviour underspecified; more than five often adds little and crowds out the actual input. Use real cases from the task, not idealised ones. If production inputs contain truncated logs and mixed languages, at least one example should contain them.

Cover four kinds of case: a clear positive, a clear negative, a boundary case near the decision threshold, and a case where the correct answer is "unknown" or "escalate." Balance labels so the model does not infer a prior from the example set. If four of five examples are labelled high severity, a borderline case will drift toward high even when the rule says otherwise.

Order matters at the margins. In many tasks the most recent examples carry more influence, so place the most instructive boundary case last. Keep the structure identical across examples — same field names, same ordering, same phrasing — so the only thing that varies is the answer. Varying the format while teaching a classification task forces the model to learn two things at once.

Example 1
input:  checkout returns 502 for 3 of 1200 requests
output: {"severity": "medium", "evidence": "error rate < 1%"}

Example 2
input:  all checkout requests fail after deploy 4b2
output: {"severity": "high", "evidence": "complete failure"}

Example 3
input:  one customer reports slow checkout; no metrics attached
output: {"severity": "unknown", "evidence": "no aggregate data"}

Rule: mark severity high only when failure is complete or
      p95 latency > 2000ms && affected_users > 100.

Notice that the rule comes after the examples and resolves the boundary cases. That ordering is a deliberate choice: examples show the shape of the answer, while the rule provides the general principle that covers unseen inputs. If examples and rules disagree, the model receives conflicting evidence. Check them together after any edit.

Quick evaluation: hold out five real cases that are not in the example set. Run the prompt ten times on each. If accuracy varies by more than about twenty percent across runs, the boundary is probably defined by an example rather than by the rule — clarify the rule before adding more examples.

Chain-of-thought prompting

Asking a model to work through a problem in steps before answering can improve tasks that require several dependent decisions: diagnosing a failure from multiple signals, calculating a result from several fields, or checking a design against a list of constraints. The benefit is that intermediate conclusions become part of the context for the next step, reducing the chance that the model jumps to an answer before considering a necessary condition.

The technique is most valuable when the task has a verifiable answer and a short final output. It is less useful for simple classification, where the extra text adds cost without changing the decision. It is also a poor substitute for tools. For arithmetic over large numbers, a calculator call is more reliable than a long verbal derivation.

Be careful when requesting visible reasoning. A request to "show your full chain of thought" may produce a plausible narrative that does not reflect the model's actual computation, and it can leak lengthy internal detail into logs or user-facing output. Ask instead for a brief, structured rationale: the checks performed, the evidence used, and the decisive factor. That gives a reviewer something to audit without turning every response into an essay.

Respond in two parts.
1. CHECKS: a list of at most four checks you performed, each with
   the evidence value used (for example, p95=2400ms).
2. VERDICT: one of PASS, FAIL, or ESCALATE, followed by one sentence.

Do not include private deliberation or speculative narrative.
If a required value is missing, write ESCALATE and name the value.

Extended thinking and when it pays

Some interfaces offer an extended thinking mode: the model is given a larger budget of internal computation before it responds. This differs from asking for visible steps. The additional work happens in the model's reasoning process, and the answer can remain short. It is useful for problems where the model must hold several constraints in mind simultaneously — for example, choosing a deployment plan that satisfies cost, residency, and latency rules at once.

The budget is a resource with diminishing returns. Raise it when errors show that the model stopped before checking a later constraint, or when a task genuinely requires multi-step search. Leave it low for extraction, rewriting, and classification, where extra deliberation mainly increases latency and cost. A practical method is to run twenty representative tasks at two budget levels and compare accuracy against the extra time and token cost. Keep the lower setting unless the improvement is large enough to matter for the use case.

Extended thinking does not repair missing context. If the relevant file was never provided, more deliberation produces a more elaborate guess. It also does not guarantee correctness: a model can reason at length from a wrong premise. Pair it with evidence requirements and deterministic verification, especially when the output drives an automated action.

Failure modes are predictable. Overfitting to examples produces a model that handles the demonstrated cases beautifully and fails on everything slightly different. Verbose reasoning produces walls of text that reviewers stop reading. An oversized thinking budget makes an interactive assistant feel sluggish. All three are configuration mistakes, and all three are fixed by measuring rather than by intuition.

Testing examples and reasoning prompts

Build a small evaluation set before tuning. Twenty inputs is enough to reveal gross problems: five clear cases, five boundary cases, five messy real-world cases, and five adversarial or missing-data cases. Record expected properties, not just exact strings — the correct severity and the presence of an evidence reference, for example. Run the prompt five times on each input and record the pass rate and the variance.

Change one variable at a time. Adding an example, reordering examples, and increasing the thinking budget are three separate experiments. If you change all three between measurements, you will not know which one helped. Keep the winning configuration under version control with the evaluation results attached, so a later model upgrade can be judged against a real baseline.

Summary

  • Examples transfer tacit knowledge about boundaries, tone, and format more reliably than abstract rules alone.
  • Use three to five varied, real cases with balanced labels and a boundary case; keep their structure identical.
  • Prefer brief structured rationales over long visible reasoning, and prefer tools for exact computation.
  • Extended thinking helps with interacting constraints but costs latency and cannot repair missing context.
  • Evaluate on a held-out set, change one variable at a time, and version the winning configuration.
