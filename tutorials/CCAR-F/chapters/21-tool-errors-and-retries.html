21. Tool Errors, Retries, and Partial Success

When a tool fails, the agent does not just receive bad news — it receives the raw material for its next decision. A vague error forces the model to guess; a precise error lets it repair, retry, or stop cleanly. This chapter treats errors as part of the tool's interface, designs payloads an agent can act on, and addresses the awkward middle ground where a tool succeeds for some items and fails for others.

What Makes an Error Payload Useful

A human-facing error message is written for reading; an agent-facing error payload is written for branching. The payload should be a structured object with a stable code, a classification, a human-readable explanation, and a remediation hint. It should also carry a correlation identifier so that a log entry can be found later.

{
  "ok": false,
  "code": "RATE_LIMITED",
  "retryable": true,
  "fatal": false,
  "message": "Quota of 100 requests per minute exceeded.",
  "retry_after_ms": 1200,
  "remediation": "wait_and_retry_once",
  "correlation_id": "req_01HQ8K3P"
}

Compare this with the string "Error: something went wrong". The structured version tells the agent exactly what the outer policy should do. The string invites three bad behaviours: immediate retry, abandonment, or a fabricated explanation in the final answer. Every field has a job — retryable drives the loop, fatal tells the agent to stop the run, retry_after_ms supplies the backoff, and remediation names the next action.

Keep the code set small and documented. Ten stable codes with clear meanings beat forty codes invented per handler. Reserve a generic UNKNOWN code for genuine surprises, and log the underlying exception separately so that the agent is not exposed to implementation details or secrets.

Never put stack traces, credentials, or raw SQL in an agent-facing error. Return a safe summary plus a correlation ID; keep the detail in the server log where a human can find it.

Retryable Versus Fatal

The first classification decision is whether repeating the same call could ever succeed. Transient conditions — rate limits, brief network failures, temporary lock contention, cold-start timeouts — are retryable with backoff. Deterministic conditions — invalid arguments, missing permissions, unknown identifiers, unsupported operations — are not. Between them sit repairable errors: the call was rejected for a reason the agent can fix, such as a missing required field or a stale ID.

A circuit breaker prevents a retryable storm. After five failures from one upstream in a short window, the tool should report UPSTREAM_UNAVAILABLE with retryable: false rather than letting every agent in the system hammer the service. The agent then uses a fallback path or escalates. This is a case where the tool's classification changes with system state, and that is correct — the question is not "is this error type usually transient" but "is repeating this specific call likely to work now".

Idempotency and Safe Repeats

Retries are only safe when repeating an operation has the same effect as performing it once. Reads are naturally idempotent. Writes are not: a refund request retried after a lost response can refund twice. The standard remedy is an idempotency key — a unique token supplied by the caller and stored by the server. If the same key appears again within the deduplication window, the server returns the original result instead of executing the operation.

def create_payment(args, idem_key, seen):
    if args["amount_usd"] <= 0:
        return {"ok": False, "code": "INVALID_ARGUMENT"}
    if idem_key in seen:
        return seen[idem_key]           # replay original result
    result = payment_api.charge(
        account=args["account_id"],
        amount=args["amount_usd"],
        token=idem_key)
    seen[idem_key] = result             # keep for 24 hours
    return result

The key should be generated before the first attempt and held constant across retries; generating a fresh key per attempt defeats the mechanism. Derive it from a deterministic tuple — task ID, step number, and target — so that a restarted agent can reconstruct the same value. Store results for at least as long as the maximum plausible retry window; twenty-four hours is a common choice.

Where idempotency keys are unavailable, prefer naturally idempotent write shapes: set a value to a target state rather than incrementing it, use put with a version token instead of blind append, and include an expected-version field so a stale retry is rejected. Document the tool's repeat semantics in its description; the agent cannot infer them from the schema alone.

Partial Results and Progressive Output

Batch tools often finish some items and fail others. Reporting the whole call as a failure throws away useful work; reporting it as a success hides gaps. Use a partial-success envelope that carries completed items, failed items with individual codes, and a status field.

{
  "ok": "partial",
  "completed": [{"id": "A1", "score": 0.82}],
  "failed": [{"id": "A2", "code": "NOT_FOUND",
              "retryable": false}],
  "counts": {"total": 8, "succeeded": 7, "failed": 1},
  "next": "retry_only_failed_items"
}

The next field is important: it states the recommended action, so the agent does not re-run the entire batch and duplicate the seven successful items. This connects back to idempotency — a retry of only the failed subset must be safe. For progressive output, where results stream in over time, emit a sequence of envelopes with an is_final flag and a monotonically increasing sequence number. The agent can then reason with early results without mistaking them for the complete answer.

Do not average away failures. If seven of eight records were scored, the result is "seven scores plus one missing record", not "eight scores at 87.5 percent confidence". Preserve the missing item as a first-class fact.

Error Contracts the Model Can Use

An error contract is the set of codes, fields, and meanings shared across all tools in a system. Consistency matters more than any individual code: if one tool signals rate limiting with 429 in text, another with busy, and a third with an empty result, the agent must learn three dialects. Standardise on one envelope and list the common codes in each tool's description where relevant.

The contract should also say what the agent is expected to do. A short table in the tool documentation — code, class, recommended action — turns error handling into a lookup rather than an inference. Include the contract in tests: every simulated error must produce a payload with the required fields, and every code must appear in the documented set. When a new code is added, update the documentation and the tests in the same change.

Testing the Error Path

Error handling is usually the least tested part of a tool. Build a fault-injection harness that can make each dependency fail in a specified way: return a 429, delay for two seconds, drop the connection mid-response, return a malformed body, or succeed for half a batch. Run the same scenario against the agent and check three things — that it classifies the error correctly, that the number of retries respects the policy, and that the final answer reflects the degradation.

Track metrics that expose bad handling: retries per successful call, fraction of errors classified as fatal, and rate of answers that claim success after a tool reported failure. A rising retries-per-success ratio usually means the agent is treating deterministic errors as transient. A falling fatal rate may mean the policy has become too permissive about retries.

Summary

  • Design errors as structured payloads with stable codes, classification, remediation, and a correlation ID.
  • Retry only when repeating the specific call can work; use repair steps for fixable errors and stop for fatal ones.
  • Protect writes with idempotency keys or naturally idempotent shapes, and record results for the full retry window.
  • Report partial success explicitly, keep failed items visible, and direct retries to the unfinished subset.
  • Standardise an error contract across tools and test it with injected failures and safety metrics.
