15. Agent Messages and Handoff Protocols

Multi-agent systems fail at their seams. A worker finishes a perfect analysis, writes the result as a friendly paragraph, and the next agent interprets a key phrase differently. An orchestrator assumes a result is final while the worker considered it provisional. A retried message arrives twice and triggers two publications. These are protocol problems, not reasoning problems. This chapter defines message envelopes, handoff payloads, validation rules, and delivery safeguards that make the seams boring — which is exactly what you want from them.

Why typed messages beat natural-language notes

Natural language is excellent for explaining and terrible for coordinating. It omits metadata, tolerates ambiguity, and changes shape under pressure. A typed message separates control information — who sent it, for which run, in response to what, with which schema version — from the body that carries the actual content. The receiving component can route, deduplicate, and validate the control fields without asking a model to interpret them.

Consistency also enables automation. If every result has status and confidence fields, a collector can implement a quorum rule in code. If those concepts exist only as words inside prose, the collector needs another model call to extract them, which adds cost and another chance of error. A good rule is: anything that changes a control decision must be a field, not a phrase.

The message envelope

A practical envelope carries eleven fields. Some are technical identifiers; others are semantic labels that help the receiver decide what to do.

  • message_id — globally unique, used for deduplication.
  • run_id and task_id — the execution and the specific assignment.
  • from and to — logical roles or agent instances.
  • type — such as task, result, error, ack, nack, or escalation.
  • reply_to — the message being answered, forming a trace.
  • sequence — a monotonically increasing number per sender, for ordering.
  • created_at and expires_at — freshness and time-to-live.
  • schema_version — how to parse the body.
  • body — the typed payload.
  • refs — artifact identifiers with digests, not inlined blobs.
  • status — provisional, final, or partial.
message:
  message_id: msg-7f21a
  run_id: run-8f3c
  task_id: audit-auth-03
  from: worker:audit-03
  to: orchestrator
  type: result
  reply_to: msg-7f019
  sequence: 4
  created_at: 2026-04-12T09:31:22Z
  expires_at: 2026-04-12T10:31:22Z
  schema_version: 2
  status: final
  body: { findings: 3, highest_severity: "high", confidence: 0.82 }
  refs: [ "sha256:4a10bd9e:findings.json" ]
  guard: if ( sequence <= last_seen && expires_at > now ) -> drop_duplicate()

A body should be small. Ten workers returning 1,500-token bodies produce 15,000 tokens in the collector's context; putting full reports in messages rather than artifact references makes that number grow without bound. The envelope plus a reference lets the collector decide which reports deserve a full read. Keep messages under roughly 1,000 tokens unless the task genuinely requires an inlined payload, and store larger material behind a digest-addressed reference.

Handoff payloads: what the next agent actually needs

A handoff is a message whose purpose is continuity: agent B must continue work that agent A began. A useful handoff has six parts. Goal restates the objective in B's own scope. Completed work lists what is done with artifact references. Decisions records choices made and their reasons. Open risks names what is unresolved, including assumptions from the register. Next action states a single recommended step and its acceptance criterion. Context digest summarises the background B would otherwise reconstruct — relevant constraints, known failures, and the current plan version.

handoff:
  from: researcher
  to: writer
  goal: "Draft the migration section using verified figures only."
  completed: [ { artifact: "sha256:9c41:figures.json", status: final } ]
  decisions: [ "Exclude Q1 data: source version mismatch (A-07)." ]
  open_risks: [ "Approval token for pricing table not yet issued." ]
  next_action: { step: "draft_section", acceptance: "5 claims, each with an artifact ref" }
  context_digest: "plan v4; currency set = EUR, USD, GBP; reviewer dislikes absolute claims"
Write handoffs for a reader with amnesia. Assume the next agent has never seen the conversation. If a fact is needed to make the next decision, include it or reference it. Phrases like "as discussed" and "the usual approach" are defects in a handoff, not shorthand.

Handoffs should also state what B must not redo. A writer that re-verifies every figure because the handoff did not mark them final wastes budget and may introduce new errors. Marking completed work with a status and a digest makes "do not redo" explicit and checkable. Equally, mark anything partial so B knows where verification stopped.

Continuity without shipping the whole history

Continuity does not require copying the entire transcript. In fact, copying it usually degrades performance: the relevant material is buried among obsolete attempts and abandoned plans. Use progressive disclosure instead. The handoff includes a compact digest plus references; the receiving agent can fetch a specific artifact if the digest is insufficient. Each reference should include a digest so the receiver can confirm it is reading the version the sender saw.

Keep a decision log as a first-class artifact. It records choices with IDs, reasons, and the alternatives rejected. When a later agent asks "why did we exclude that source?", the answer comes from the log rather than from speculation. A decision log also prevents contradiction: two workers can check whether a decision already exists before proposing its opposite. In long runs, the log doubles as the basis for a final summary, because it contains the reasoning that a result list omits.

Stale context is worse than missing context. A missing fact produces an explicit question; a stale fact produces a confident wrong action. Attach an as_of timestamp to each external fact and revalidate facts whose source has a newer digest before using them for irreversible steps.

Validation at the boundary

Every message crossing an agent boundary should pass through a validator before it is acted upon. Validation has four layers. Envelope validation checks required fields, identifier formats, and expiry. Schema validation checks the body against the declared schema version — required keys, types, ranges, and enumeration values. Reference validation checks that cited artifacts exist and their digests match. Policy validation checks that the requested action is within the receiver's authority, such as a publish request carrying an approval token.

The validator's response is explicit: accept with ack, reject with nack naming the failed rule, or quarantine with needs_review when the message is suspicious but might be legitimate. A nack should include the message ID, the failing field, the expected form, and whether a retry is meaningful. Sending a malformed result back for repair is useful; sending an authorization failure back for repair is not. Define size limits as well — a message over 1,000 tokens or an artifact list over 20 references should be rejected rather than silently truncated, because truncation can remove the very field that made the message valid.

Delivery failure modes and safeguards

Four delivery problems recur in distributed agent systems. Lost messages are handled with acknowledgements and a retry timer: if no ack arrives within a deadline, resend with the same message_id. Duplicate delivery is handled by recording seen IDs and by making side effects idempotent; the receiver must not publish twice just because a retry occurred. Out-of-order arrival is handled with sender sequence numbers — a receiver buffers or rejects a message whose sequence is lower than the last one processed, unless the message type explicitly allows reordering. Stale messages are handled with expires_at and with a run-generation check: a result from run generation 2 must not be accepted by generation 3.

receive:
  steps:
    - check seen(message_id): if true -> ack_without_processing
    - check expires_at > now: if false -> reject_stale
    - check sequence > last_sequence: if false -> buffer_or_reject
    - validate_envelope -> validate_schema -> validate_refs -> validate_policy
    - process_once -> record_last_sequence -> emit_ack
  on_validation_failure: nack( include_rule: true, retryable: by_class )

Note the ordering: deduplication happens before processing, so a duplicate is acknowledged without re-executing its effects. Sequence checks happen before validation, so an old message cannot roll back the receiver's state. These small ordering decisions are where protocol design earns its keep. Log every transition with message ID and rule name; when a run goes wrong, a message trace is usually faster to read than any model's account of what it believed it did.

Summary

  • Typed envelopes separate routing metadata from content and enable code-level control.
  • Keep message bodies compact and place large material behind digest-addressed references.
  • Handoffs must state goal, completed work, decisions, risks, next action, and context digest.
  • Validate envelope, schema, references, and policy at every agent boundary.
  • Use IDs, sequence numbers, expiry, and run generations against loss, duplication, reordering, and staleness.
  • Log message transitions so a failed run can be reconstructed from a trace.
