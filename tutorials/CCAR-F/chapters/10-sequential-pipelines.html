10. Sequential Pipelines

A sequential pipeline is the agentic equivalent of an assembly line: each stage accepts a specific input, performs one job, and emits an output the next stage can trust. The hard part is not the stage prompts but the boundaries between them — what happens when a stage produces a plausible but wrong result, and how the run recovers when the failure appears three stages later. This chapter treats a pipeline as contracts, gates, checkpoints, and compensation rules, not a list of prompts.

Order is a design constraint, not a convenience

Stages must be ordered when a real dependency exists: a customer record has to be resolved before an entitlement can be checked, a number has to be extracted before it can be verified, a draft has to be approved before it can be sent. If no such dependency exists, sequencing the work is a choice with a cost. A chain of six stages each taking 8 seconds runs in at least 48 seconds of model time; the same six operations with no dependencies could run in roughly 8 seconds across six workers. Sequence also forces all intermediate context through a single line, which means an early misunderstanding is carried forward and amplified.

Sequence becomes the right answer when the work is cumulative — each stage adds a property that later stages need — or when the environment requires a particular order, such as a human approval before publication. A useful discipline is to write the dependency explicitly beside each stage: "stage 4 needs verified_amounts from stage 3; it does not need the raw document." If you cannot state the dependency in one line, the stage boundary is probably in the wrong place.

Stage contracts: input, output, and gate

Every stage should have three declared parts. The input contract names the fields the stage requires and their types. The output contract names what it promises to produce. The gate is a deterministic check that runs on the output before the next stage begins. A gate is not a prompt asking the model to "be careful"; it is code that rejects a value with a clear error when a required field is missing, a count is wrong, or a reference cannot be resolved.

stage:
  name: verify_amounts
  input:  { extracted: array<Field>, currency: string }
  output: { verified: array<VerifiedField>, conflicts: array }
  gate:
    - each verified.amount is numeric
    - each verified has source_line > 0
    - conflicts == [] OR escalate( "unresolved_amount" )
  on_reject: retry_stage( max: 2 ) else route( "human_review" )
  checkpoint_key: run:{run_id}:stage:verify:{input_digest}

Notice that the gate has an explicit escape route. A pipeline that only knows how to retry will loop forever on a structurally valid but semantically impossible input — for example, a currency code the system does not support. Routing to human review after two bounded retries is cheaper and safer than a fifteenth attempt with a slightly different temperature. The rejection payload should contain the stage name, the failed rule, the offending value, and the attempt number, so the repair step has something concrete to work with.

Keep stage outputs small and complete. A stage that emits a 12,000-token narrative forces the next stage to rediscover the three fields it actually needs. Prefer a compact structured result plus references to full artifacts. A useful limit is roughly 500 to 2,000 tokens of structured output per stage, with larger material stored behind an identifier.

Error propagation and blast radius

Errors in a chain are not independent. A wrong extraction in stage 1 becomes a wrong verification in stage 2, a confident but flawed draft in stage 3, and a published error in stage 4. This is the pipeline's blast radius: once a value is downstream, later stages usually lack the original evidence needed to challenge it. The probability of a clean run also falls quickly. With five stages at 0.98 reliability each, the chance of no failure is about 0.904; with eight stages at 0.97 it is roughly 0.784. Longer chains need more gates, not more hope.

Three techniques reduce propagation. Reference forwarding attaches the source location to every derived value, so a later stage can inspect the origin without rereading everything. Cross-checks recompute one invariant independently — totals must sum, counts must match, citations must point to real lines — and treat a mismatch as a stage failure rather than a warning. Confidence tagging marks each field as confirmed, inferred, or unknown, allowing a final gate to block publication when critical fields are merely inferred. Never let a summary erase these tags; a confident-sounding summary is how uncertainty disappears.

Failure mode — silent defaulting. A stage that replaces a missing value with 0 or "N/A" can pass every structural gate. The next stage then reasons from a fabricated fact. Require an explicit sentinel such as unavailable and a rule stating which downstream decisions are allowed when that sentinel appears.

Compensation: undoing work after a later failure

Some stage effects cannot simply be rolled back. If stage 5 reserves inventory and stage 7 fails validation, the reservation still exists. Compensation is the practice of executing a deliberate inverse action for each completed stage that had an external effect. Think of it as a list of undo operations accumulated as the pipeline advances: publish → retract draft, reserve → release reservation, notify → send correction. On failure, the compensations run in reverse order, and each one gets its own retry budget.

  1. Record the compensation action when the forward action succeeds, not when the failure occurs.
  2. Store the external identifier returned by the forward action; a compensation without it cannot target the right object.
  3. Run compensations in last-in-first-out order, so dependencies are unwound safely.
  4. Make each compensation idempotent and record its own completion; a retry after a partial compensation must be harmless.
  5. If a compensation fails permanently, escalate with the list of uncompensated effects — never declare the run clean.

Not every stage needs compensation. Pure transformations that only write to the pipeline's own storage can be discarded by invalidating their checkpoint. The test is simple: did the outside world observe it? If yes, you need an inverse action and a record of it.

Checkpoints and resumability

A checkpoint is the validated state of the pipeline at a stage boundary. Store at least the run ID, stage name, input digest, output artifact reference, gate result, and a list of side effects with their IDs. Keying the checkpoint by input digest prevents a stale result from being reused after upstream data changes. On restart, the runner compares the current input digest with the checkpoint's digest; a match allows resume, a mismatch invalidates that checkpoint and everything after it.

Decide what "resume" means for each stage. For a pure stage, resume means skip it and load its output. For a stage with side effects, resume means verify the external effect first — using an idempotency key — then skip or repair. Keep a small ledger of transitions: stage:started, stage:gated, stage:side_effect, stage:compensated. This ledger turns a post-mortem question from "what happened?" into a query. It also makes retries observable: a stage that has failed four times should be visible before it consumes a fifth attempt.

Two clocks matter. Stage latency determines runtime; checkpoint frequency determines how much work a crash costs. If a stage takes 30 seconds, checkpointing after every stage is cheap. If a single stage streams for 20 minutes, checkpoint its partial output every minute or two so a crash does not erase the entire effort.

When to break the chain

Pipelines are not sacred. Split a stage when it mixes two different failure policies — a permissive generation step and a strict validation step should not share a retry budget. Merge stages when the handoff loses more information than the separation preserves; passing a simplified summary into the next stage often destroys details the next stage needs. Parallelise inside a stage when it processes a collection, keeping the overall chain intact while reducing the slowest stage's duration from, say, 60 seconds to 8 seconds across eight shards.

A practical review check is to list the pipeline's stages with three numbers each: expected tokens, expected latency, and probability of needing repair. Stages with high token cost and high repair probability are candidates for earlier gates. Stages with low value and high latency are candidates for removal. A seven-stage pipeline where stage 3 adds 1,200 tokens of prose that nobody reads is not rigour; it is latency with a prompt attached.

Summary

  • Use a pipeline when dependencies are real and cumulative; otherwise consider parallel work.
  • Define an input contract, an output contract, and a deterministic gate for every stage.
  • Bound retries and route persistent failures to review rather than looping indefinitely.
  • Reduce blast radius with source references, invariants, and explicit uncertainty tags.
  • Record compensations at the moment of side effect, then unwind them in reverse order on failure.
  • Checkpoint by input digest so recovery can resume safely and detect stale results.
