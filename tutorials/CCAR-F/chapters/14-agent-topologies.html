14. Topologies and Agent Selection

A topology is the pattern of communication among agents, a separate decision from plan shape: a hierarchical plan can run on a star, and a parallel plan through a shared workspace. Topology decides who talks to whom, how much context is copied, where bottlenecks form, and which failures are survivable. This chapter compares star, chain, tree, blackboard, and debate, then gives selection criteria.

Star: one hub, many spokes

In a star, a central agent communicates with all workers, and workers do not communicate with one another. It is the direct implementation of the orchestrator-and-subagents pattern from the previous chapter. With n workers, a simple exchange costs about 2n messages: one task out and one result back per worker. The hub holds the global view, assigns scope, and validates results, which makes conflict resolution straightforward.

The hub is also the bottleneck. Every result passes through its context, so ten workers returning 2,000 tokens each place 20,000 tokens of material in the hub before synthesis. Beyond roughly eight to twelve workers, the hub's context becomes the limiting resource and its judgement degrades: it starts skim-reading results. Mitigations include asking workers for shorter structured returns, staging results in groups of four or five, or moving to a tree. A hub failure is total — no worker has the authority to continue — so the hub's decisions and checkpoints should be persisted frequently.

Chain: a relay of specialists

A chain passes work from one agent to the next: researcher to analyst to writer to reviewer. With n agents there are only n − 1 handoffs, making it the cheapest topology in message count and the easiest to audit — each link has one sender and one receiver. It maps naturally onto pipelines with real stage ordering, and it gives each agent a small, stable context.

The chain's weakness is cumulative distortion. Each agent receives a representation created by the previous one, not the original evidence. If the analyst compresses twelve findings into three sentences, the writer can only work with three sentences. A chain of five agents can drift substantially from the source while every individual handoff looks reasonable. Defences include passing immutable artifact references alongside summaries, requiring each agent to cite the original source, and allowing later agents to query earlier stages rather than accepting their prose. Chains also serialise latency: the total time is the sum of all links, so they are a poor choice when work can proceed in parallel.

Chain versus pipeline. A pipeline is a plan with ordered stages; a chain is a communication topology that can implement one. You can run a five-stage pipeline on a star (the hub performs each stage) or on a chain (one agent per stage). Choose the topology by asking who needs to see what, not by counting stages.

Tree: hierarchy with local aggregation

A tree introduces intermediate coordinators. A root delegates to three branch leads, each of which manages five workers. Instead of 15 results arriving at the root, three summaries arrive; the root resolves only cross-branch conflicts. Message count is approximately 2(n − 1) for a tree with n agents — slightly more than a star — but the context per node is much smaller. Depth adds latency because a result must travel upward one level at a time.

Trees are the right shape when the problem decomposes into genuinely different domains: separate regional markets, separate subsystems of a codebase, separate sections of a large document. They are wasteful when the branches are doing identical work — that is a fan-out pattern with an unnecessary middle management layer. The classic tree failure is summary loss at branch boundaries. Give each branch a fixed return shape and keep evidence references reachable from the root, so a suspicious summary can be expanded on demand instead of triggering a full re-run.

Blackboard: a shared workspace

In a blackboard topology, agents read from and write to a shared artifact — a problem board, a shared document, a structured knowledge base. There is no central router; agents pick up the next item that matches their role and post findings for others to use. This is a good fit for open-ended investigation where agents cannot predict in advance which discovery will matter: a security review, a root-cause analysis, a design exploration.

The cost is coordination discipline. Without conventions, agents overwrite one another, duplicate work, or read partially written entries. A workable blackboard needs three mechanisms: typed entries with owners and timestamps, a reservation or claim protocol so only one agent works an item, and an append-only log so history is not lost. Versioning is essential because an agent may act on information that was true when it read it but was later revised. A shared store is also a single point of failure and a security boundary — every agent that can read the board sees everything on it, which may conflict with data-scope requirements.

Blackboard failure mode: anchoring. When all agents see the same early hypothesis, they tend to reinforce it rather than challenge it. Periodically seed independent checks that do not read the board until they have produced a candidate answer, or reserve a dedicated sceptic role.

Debate: structured disagreement

A debate topology has competing agents advance different answers and a judge compare them. A minimal form uses two proposers with different mandates and one evaluator; a stronger form adds a critic who attacks both proposals before the judge rules. This is the most expensive of the five shapes — with n participants the message count can exceed 4n because arguments, rebuttals, and judgements circulate repeatedly — but it is valuable when the cost of a wrong decision is high and the evidence genuinely supports multiple interpretations.

Debate only works if the roles are different in substance. Two agents given the same prompt and the same data usually produce the same answer, so the "debate" becomes a duplicate vote. Give one agent a conservative mandate, another a coverage-oriented mandate, and a third the task of finding disconfirming evidence. Require the judge to cite which argument survived and why, and record the losing arguments rather than discarding them — they are useful if the decision is revisited. Debate is a poor fit for routine extraction, high-volume classification, or any task where latency is the primary constraint.

Selection criteria and anti-patterns

Choose a topology from four questions. Dependency: does work arrive in a fixed order (chain), in independent slices (star or tree), or unpredictably (blackboard)? Context: does every agent need the same large body of material (blackboard) or only its own slice (star/tree)? Risk: is a wrong answer cheap to correct, or does it warrant adversarial checking (debate)? Scale: how many agents are needed before the hub's context or the queue becomes the bottleneck (tree)? Budget and latency then act as tie-breakers.

select_topology:
  if ( fixed_order && slices < 6 )        -> chain
  else if ( independent && workers <= 10 ) -> star
  else if ( independent && domains_differ ) -> tree
  else if ( emergent_dependencies )         -> blackboard
  else if ( high_impact && ambiguous )  -> debate
  else                                      -> single_agent
  hard_limits: max_agents = 20, max_hops = 4, max_context_per_agent = 16k

Anti-patterns are worth naming. A star with twenty workers is usually a tree waiting to be designed. A chain with ten links is usually a pipeline that needs checkpoints or a star inside one stage. A blackboard without an append-only log is a shared file that will be overwritten. A debate over a factual extraction task is theatre. And any topology whose message count exceeds the value of the work it coordinates is an expensive way to look sophisticated. The best multi-agent design is often no multi-agent design: a single agent with good tools and a clear contract beats a five-agent topology with vague handoffs.

For each scenario, choose a topology and justify it with one dependency observation and one risk observation.

  1. A help-desk draft must be classified, enriched with account data, written, and legally checked before sending.

Summary

  • Star centralises control but concentrates context and failure in the hub.
  • Chain is cheap and ordered but suffers cumulative distortion and serial latency.
  • Tree scales heterogeneous work by aggregating locally before reaching the root.
  • Blackboard supports emergent dependencies but needs claims, versions, and an append-only log.
  • Debate is worth its cost only for high-impact decisions with genuinely different mandates.
  • Select topology from dependency, context, risk, and scale — then check the message bill.
