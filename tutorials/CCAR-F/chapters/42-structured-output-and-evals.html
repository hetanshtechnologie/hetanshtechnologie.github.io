42. Structured Output and Evaluation

Prose is a poor interface between a model and a program. If downstream code must parse a paragraph to find an invoice total, the system will eventually break on a polite sentence like "I'd say it's around forty dollars." Structured output turns model responses into typed data, and evaluation turns "seems good" into a measured claim. This chapter covers both: how to obtain reliable structured data and how to know whether the whole system is working.

Why structure is an architectural concern

A free-text response has unbounded shape; a program expects a bounded one. The gap between them is where silent bugs live. Consider an extraction pipeline that reads contracts. If the model returns "date": "next Tuesday" instead of an ISO date, a naive parser may store the literal string and a later comparison will quietly fail. Structure is not cosmetic — it is the contract that lets components trust one another.

Three approaches exist, in increasing order of strictness: ask for JSON in the prompt (soft), enable a JSON mode that guarantees syntactically valid JSON (medium), and supply a schema that constrains the output to exact types and allowed values (strict). Choose based on what breaks if the format is wrong. A chat UI can recover from soft JSON; a payment processor cannot.

Even with a strict schema, validate in your application. A schema guarantees shape, not truth. A field can be perfectly typed and completely wrong, so pair structural validation with semantic checks such as "total equals the sum of line items."

JSON mode and schema-constrained extraction

JSON mode ensures the response parses as JSON. It does not ensure the keys you want are present. Schema-constrained extraction goes further: you provide a definition with required fields, types, enums, and nested objects, and the decoder is nudged or forced to conform. The practical difference shows up in failure rates. In a small invoice test set of 200 documents, a soft prompt might yield 8 percent malformed outputs, JSON mode might cut that to 1 percent, and a strict schema with a retry gate often reaches near zero malformed outputs after one retry.

Write schemas that express real constraints. Prefer enum over free strings for categorical values, use integer in the smallest unit (cents) to avoid floating-point drift, and mark fields required only when their absence should fail the task. Over-constraining produces brittle extraction when a document legitimately omits a value; under-constraining pushes ambiguity into your code.

{
  "type": "object",
  "required": ["vendor", "total_cents", "currency", "line_items"],
  "properties": {
    "vendor": {"type": "string", "minLength": 1},
    "total_cents": {"type": "integer", "minimum": 0},
    "currency": {"type": "string", "enum": ["USD", "EUR", "GBP"]},
    "line_items": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["description", "amount_cents"],
        "properties": {
          "description": {"type": "string"},
          "amount_cents": {"type": "integer", "minimum": 0}
        }
      }
    }
  },
  "additionalProperties": false
}

The additionalProperties: false flag is worth emphasizing. Without it, models sometimes invent helpful-looking extras such as a confidence note or a guessed tax field. Those extras then flow into storage and pollute downstream reports. Closed schemas keep the data surface small and predictable.

Tool-based extraction as an alternative

Instead of asking for a final JSON answer, you can define an extraction tool whose parameter list is the target schema, then let the model call it. This looks like a tool call but functions as structured output. The advantage is that the call site is explicit in the transcript: you can see which document produced which record, and you can attach the call to a specific turn. It also composes well with agentic flows where several extractors run in sequence.

The trade-off is verbosity and cost: each tool call carries schema overhead in the prompt. For a single extraction on a short input, direct schema output is simpler. For a pipeline with five linked extractors, the tool form gives you a clean audit trail.

Validation loops and retry gates

A validation loop is a deterministic check wrapped around the model call. It has three possible outcomes: accept, retry with feedback, or reject. Retries must be bounded and must change something — repeating the identical prompt after a malformed response usually reproduces the same error.

  1. Parse and schema-check. If invalid, record the exact validation error path, such as line_items[2].amount_cents: expected integer.
  2. Add semantic checks. Compare totals, check that dates fall in a plausible range, and verify enums against a lookup table.
  3. Retry with the error text. Feed the failure back as a short correction instruction, at most two times, with a lower temperature on each retry.
  4. Gate the result. If checks still fail, route to a human queue or a fallback parser instead of passing bad data downstream.
attempt = 0
while attempt < 3:
    raw = model.generate(prompt + corrections, temperature=0.2 - 0.05*attempt)
    ok, errors = validate_against_schema(raw)
    if ok && semantic_checks_pass(raw):
        return raw
    corrections.append("Fix these fields: " + errors)
    attempt += 1
return route_to_review_queue(raw)

Notice the guard uses both escaped comparison and logical operators. The important design point is that the loop cannot run forever: attempt < 3 and the explicit review fallback make the behaviour testable. A retry without a gate is just an expensive way to produce the same error three times.

Do not let retries mask systemic problems. If more than a few percent of outputs need a retry, the schema, the examples, or the source document quality is wrong. Track retry rate as a first-class metric, not a hidden detail.

Multi-pass review and evaluation workflow

Some tasks benefit from a second pass: extract, then review. The reviewer receives the structured record plus the source, and answers a narrow question — "does each field have support in the source?" This catches plausible hallucinations that schema validation cannot. Keep the reviewer's output structured too, for example a list of field-level objections, so its result can be acted on automatically.

Evaluation makes improvement measurable. A practical workflow has five steps:

  1. Build a dataset. Sample 100 to 300 real cases, including edge cases and known failures. Label the expected output or the expected rubric score.
  2. Define a rubric. Score dimensions such as correctness, completeness, and format compliance on a 0–3 scale with written anchors for each level.
  3. Choose a grader. Use exact match for deterministic fields, a programmatic check for arithmetic, and model grading for subjective dimensions. Calibrate the model grader against human labels on a small set first.
  4. Run in batch. Execute the full dataset asynchronously, store every input/output pair, and compare against a baseline version.
  5. Triage regressions. Group failures by cause — schema, retrieval, reasoning, or grader error — before changing the prompt.

Model grading is useful but biased. Graders tend to favour verbose, confident answers and may penalise correct terse ones. Mitigate this by hiding which system produced an answer (blind comparison), randomising presentation order, and measuring agreement with human raters. If agreement is below roughly 80 percent, fix the rubric before trusting the score.

Closing the loop

Structured output and evaluation are two halves of one idea: make the model's contribution legible to the rest of the system, and make the system's quality legible to you. Schemas, validation loops, and tool-based extraction handle the first half. Datasets, rubrics, batch runs, and calibrated graders handle the second. When a regression appears, the combination lets you answer not just "something changed" but "field X failed on documents of type Y after we altered the enum." That specificity is what separates a prototype from a maintainable system.

Summary

  • Treat output format as a contract; choose soft prompts, JSON mode, schemas, or tool calls by the cost of a format error.
  • Express real constraints with enums, integers, required fields, and closed schemas.
  • Wrap model calls in bounded validation loops with semantic checks and an explicit review fallback.
  • Use multi-pass review to catch plausible but unsupported values that schemas cannot detect.
  • Evaluate with a labelled dataset, a written rubric, calibrated graders, batch runs, and cause-based triage.
