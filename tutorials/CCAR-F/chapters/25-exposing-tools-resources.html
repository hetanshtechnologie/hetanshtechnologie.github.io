25. Exposing Tools and Resources

A tool is a promise, and a resource is a place. When a server exposes a tool, it promises that a valid argument object will perform a defined unit of work and return a defined shape. When it exposes a resource, it offers addressable content that a client can fetch and cache. Models reason about tools; clients reason about resources. A well-designed surface makes that split obvious to both.

Two primitives, two contracts

The two primitives are deliberately asymmetric. A tool invocation is a request message with a payload and a response message with a result or an error. A resource read is a lookup by identifier, usually followed by content bytes plus metadata. This asymmetry is useful: it lets a client prefetch context without side effects, while keeping mutations behind an explicit call that can be approved, logged, and retried.

PropertyToolResource
Primary question"What should happen?""What is at this address?"
Invoked byThe model, through a call messageThe client, through a read request
Typical payloadJSON argument objectURI string, optional range or cursor
CacheableOnly when marked read-onlyYes, keyed by URI plus version
Side effectsPossible and often the pointShould be none
Failure surfaceTool error result with retry guidanceNot found, forbidden, unavailable

Both primitives are contracts enforced at the server boundary. Validate before business logic runs: a malformed request that reaches your handler may be partially executed. Parse, validate, then dispatch. Adding a field to the schema is a public API change even when the field is optional.

Writing a tool contract the model can route

A tool declaration has three fields that do most of the routing work: a name, a description, and an input schema. Keep the name short, stable, and verb-led, such as search_invoice. Use lowercase with underscores and avoid abbreviations that only your team understands. A name containing a version number is a decision you will later have to honor.

The description is a routing instruction for a model, not documentation for humans. Put the discriminating sentence first: what the tool does and when to choose it. Add one sentence about when not to choose it, especially when a sibling overlaps. "Gets a customer record by exact identifier; use search_customer for partial names" beats "Customer tool." Aim for 40 to 120 words.

The input schema is a JSON Schema object. Constrain everything: enum for fixed choices, minimum and maximum for numbers, maxLength for strings, and additionalProperties: false so typos fail fast. Mark only genuinely required fields as required, and give every optional field a documented default. An implicit default is guessed differently by different models.

{
  "name": "reserve_slot",
  "description": "Reserves a 30-minute appointment slot. Use only
  after availability has been checked with list_slots. Does not
  send a confirmation email; that is a separate step.",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["calendar_id", "start_utc"],
    "properties": {
      "calendar_id": {"type": "string", "pattern": "^cal_[a-z0-9]{8}$"},
      "start_utc":   {"type": "string", "format": "date-time"},
      "duration_min": {"type": "integer", "enum": [15, 30, 45], "default": 30},
      "note": {"type": "string", "maxLength": 280}
    }
  }
}

# Server-side guard: validate, then dispatch
if payload.duration_min < 15 or payload.duration_min > 45:
    raise InvalidArgument("duration_min must be one of 15, 30, 45")
if payload.note and "&" in payload.note:
    payload.note = escape_ampersands(payload.note)

Four failure modes recur. Two nearly identical descriptions make the model flip between tools. An unbounded text field invites a 10,000-character argument. A schema with twenty optional parameters hides the three that matter. A result whose shape changes by success condition forces the caller to guess. Fix these in the declaration, not in prompt text.

Keeping reads and actions apart

A read boundary is a promise that nothing changes. list_slots may query a database, but it must not create a reservation or send a notification. When reads and actions are blended, clients cache the uncacheable, retries duplicate side effects, and permission prompts lose meaning because every call might mutate something.

SignalRead operationAction operation
Verbget, list, search, describecreate, update, delete, send
IdempotenceNaturally repeatableNeeds an idempotency key
ApprovalRarely requiredCommonly required
Retry policySafe automatic retryRetry only with the same key
ResultContent plus metadataStatus plus affected identifier

For expensive or irreversible actions, split preview from commit. preview_change computes the diff and returns a token that expires in five minutes; apply_change accepts that token plus an idempotency key. Only the commit changes state. If you cannot split the operation, add a dry_run flag that defaults to true and document that it performs checks but no writes.

Never let resource listing mutate state. A client may enumerate resources repeatedly for indexing or display. If reading a URI generates a report, consumes a queue item, or rotates a secret, the "read" is actually an action and must be moved behind an explicitly invoked tool.

Resource URI design

A resource URI is a stable handle, not a command. Use the structure scheme://authority/path?query#fragment and treat the scheme as a namespace you control. Files can appear as file:///srv/reports/q3.csv, domain objects as issue://ENG-142, and parameterized views as metrics://cpu?window=5m&step=30s.

Six rules keep URIs usable. Keep identifiers stable when storage moves. Never embed secrets or session tokens. Percent-encode spaces and reserved characters consistently. Use path segments for hierarchy and query parameters for filters. Use a fragment for a subsection, such as repo://main/README.md#install. Publish templates with named variables, for example repo://{branch}/{path}, so clients can build valid URIs without string concatenation.

Three errors cause most integration pain. Identity churn occurs when a URI includes a timestamp, so the same document appears new on every read. Ambiguous authority occurs when two backends both use db:// with different meanings. Unbounded results occur when a URI expands to a million rows; set a default page size and return a cursor.

A URI may be opaque to the client. If your storage layer is likely to change, expose an identifier such as doc://8f14e45f and keep the mapping server-side. Hierarchical URIs are easier to browse, but they couple clients to your directory layout.

Metadata that earns its space

Metadata communicates intent that an identifier cannot. For resources, useful fields include a title, a short description, a MIME type, a byte size, a last-modified timestamp, and annotations for audience and priority. A 4 KB text/markdown resource can render inline; a 2 GB video/mp4 should be offered as a download link.

For tools, hints such as read-only, destructive, idempotent, and open-world tell a client how much caution to apply. A destructive hint should trigger confirmation; a read-only hint may allow automatic retries. Change notifications let a server announce a new document instead of making the client poll every ten seconds.

Hints are signals, not enforcement. A tool marked read-only still needs server-side checks that reject writes. If metadata contradicts behavior, clients will learn to distrust every other declaration you publish.

Versioning a public surface

Clients discover declarations at runtime, so a breaking change can fail a session that started minutes earlier. Additive changes are usually safe: a new tool, an optional argument with a default, a new resource scheme. Breaking changes include renaming a tool, narrowing a type, removing an enum member, or making an optional field required.

ChangeCompatible?Safe technique
Add optional argumentYesDefault in schema and handler
Widen a string to add a formatYesKeep old format accepted
Remove an enum valueNoDeprecate, then ship as v2
Rename a toolNoRegister both names for two releases
Change resource schemeNoAlias old URIs to new ones

Run two versions side by side for two releases, return a deprecation notice in response metadata, and remove the old declaration only when telemetry shows no traffic. Negotiate capability at session start. Keep validation strict: reject unknown fields with additionalProperties: false, and relax to accept-and-ignore only when older clients send fields your handler no longer recognizes.

Summary

  • Tools are verbs that perform work; resources are nouns that can be fetched and cached.
  • A tool's name, description, and constrained input schema form the contract the model routes on.
  • Keep reads free of side effects; put mutations behind explicit tools with confirmations and idempotency keys.
  • Resource URIs should be stable, encoded, and parameterized through query strings or published templates.
  • Metadata informs client behavior but must never replace server-side enforcement.
  • Classify changes as additive or breaking, and dual-register declarations across a deprecation window.
