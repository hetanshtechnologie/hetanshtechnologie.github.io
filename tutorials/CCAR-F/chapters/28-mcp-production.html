28. MCP in Production

A server that works for one developer on a laptop is not yet a production service. Production adds several tenants, a security boundary, an upgrade path, and people who need to understand failures at 3 a.m. This chapter covers the capabilities and constraints that appear at that point: model calls initiated by the server, notifications and roots, authentication, versioning, and the choice between built-in and custom tools.

What changes when a server goes live

The biggest change is that the server is no longer the only actor. A client may connect from a laptop, a CI runner, or a hosted agent, and each of those callers carries a different identity and a different budget. State that was harmless in a single-user demo — a global cache, a mutable working directory, a single API key — becomes a cross-tenant leak when shared.

Design for isolation from the start. Put tenant identifiers in an authenticated context rather than in tool arguments, because an argument is model-controlled. Give each request a correlation identifier and carry it through logs, downstream calls, and error responses. Define what happens when a dependency is unavailable: return a structured error with a retry hint rather than hanging until the client's timeout fires.

Server-initiated model calls

Normally the model calls tools. Occasionally the server needs the model: to summarize a large document before returning it, to choose between two interpretations of an ambiguous record, or to draft text that the server will then validate. The server can send a sampling request to the client, asking it to run a completion on the server's behalf.

The request carries messages, a system prompt, a token ceiling, and optional model preferences. It cannot invoke tools, which keeps this channel from becoming an unbounded recursive loop. The client may approve, modify, or reject the request; it may also apply its own token budget. A correct server therefore treats rejection as a normal outcome with a deterministic fallback.

{
  "method": "sampling/createMessage",
  "params": {
    "messages": [{"role": "user", "content": {
      "type": "text", "text": "Condense this change log to five bullets."}}],
    "systemPrompt": "You write terse engineering summaries.",
    "maxTokens": 300,
    "modelPreferences": {"costPriority": 0.7, "speedPriority": 0.4}
  }
}

# Server-side ceiling: never let a caller exceed the approved budget
if requested_tokens < 1 or requested_tokens > 300:
    requested_tokens = 300
if client_rejected and fallback_text is None:
    return deterministic_truncate(change_log, max_chars=1200)

Use sampling sparingly. Every model call adds latency, cost, and nondeterminism to a path that may be on the critical route of an agent loop. If a regular expression or a sorting function gives the same answer, use that instead. Good uses include language generation and judgment calls that cannot be expressed as a rule; poor uses include parsing structured data or deciding whether a number is in range.

A sampling request is not a privileged channel. The client may show it to the user, edit the messages, or refuse it. Do not put secrets, hidden instructions, or decisions that must be authoritative into a sampling request.

Notifications, roots, and progress

Three mechanisms let a server communicate outside the request–response path. Log notifications carry a level such as debug, info, warning, or error plus a logger name; they are for operators, not for end users. Progress notifications are tied to a token supplied by the caller in the original request: each update includes the token, a current value, an optional total, and a short message. Roots tell the server which directories a client has made available.

MechanismDirectionTypical use
Log notificationServer → clientDiagnostic events, dependency failures
Progress notificationServer → clientLong index build, bulk export
Roots listClient → serverAllowed filesystem starting points
Roots changedClient → serverUser opened a second project

Roots are a boundary, not a hint. If a client advertises file:///home/me/project/, the server resolves every relative path against that root and rejects paths that escape it with .. segments or symlinks. Re-read the root list when a change notification arrives; a stale root either blocks legitimate work or grants access to a directory the user has since removed.

Progress tokens should be opaque strings with a short lifetime. Emit updates at a fixed cadence, for example every 250 milliseconds, and always send a final update that marks completion. A job that stops sending progress without a terminal message looks hung to a client even if it finished successfully.

Authentication and least privilege

Remote servers should authenticate every request. A bearer token in the Authorization header is common, validated for signature, expiry, issuer, and audience. Do not accept an identity from a query parameter or a tool argument: both appear in logs and can be altered by the caller. Map scopes to capabilities at the gateway and again inside the server, so a mistake in one layer does not grant access.

Least privilege applies per tool, not per server. A principal with records:read may call search_record but must receive a denial from delete_record. Return a clear authorization error rather than an empty result, because an empty result invites the model to broaden its query. Keep the audit record short and consistent: timestamp, principal, tool name, a hash of the arguments, decision, duration, and result size. Redact fields known to contain personal data.

ControlFailure without it
Short-lived tokens (15–60 min)A leaked credential works for months
Per-tool scopesRead-only users can mutate data
Root containmentPath traversal reaches unrelated files
Audit logNo way to reconstruct an incident
Treat the model's tool arguments as hostile input that happens to be well formed. Validate types, ranges, and tenant ownership in the handler even when the schema already passed.

Versioning across a fleet

In production, clients and servers upgrade at different times. The initialize exchange carries a protocol version and capability flags; both sides should fall back to a mutually supported level or fail with a clear message. Never silently ignore an unknown field that changes behavior. Declare optional features behind capability flags so an older client never calls a method its server does not understand.

Roll out changes in stages. Deploy to a small canary group, watch error rates and tool latency for an hour, then widen the rollout. Keep the previous server version available for one release cycle so a client can be rolled back quickly. When you must remove a tool, first return a structured deprecation warning in the response metadata for two releases; only then drop the declaration.

Built-in tools versus custom tools

Clients supply general-purpose tools such as reading a local file, editing text, running a shell command, and searching the web. Your server supplies domain tools. The two sets should complement each other. Duplicating a built-in capability invites inconsistent behavior: two file readers with different path rules, or two search tools with different result shapes.

QuestionPrefer built-inPrefer custom
OperationGeneric file or shell workDomain action with business rules
AuthorityUser's local environmentShared service and its permissions
DeterminismSimple, well-understood behaviorValidation, policy, and audit required
Context costRarely used in a sessionCalled often with compact results

A useful pattern is to wrap rather than replace. A custom publish_release tool can call the client's file reader to gather artifacts, apply the organization's checks, and then commit through an authenticated service. The model sees one clear action; the server keeps the policy. Avoid exposing all twenty internal tools when three well-chosen ones cover the workflow, and measure how often each tool is called before adding more.

Summary

  • Production adds tenant isolation, authentication, observability, and controlled upgrades to a working server.
  • Sampling lets a server request a model completion, but the client may refuse and the server needs a deterministic fallback.
  • Log, progress, and roots notifications extend the protocol beyond request–response; roots must be enforced against path traversal.
  • Authenticate every remote request, scope permissions per tool, and keep a compact audit trail.
  • Negotiate versions at initialize time, canary releases, and deprecate declarations before removal.
  • Prefer built-in tools for generic operations and custom tools for domain actions that need policy and audit.
