40. Steering Output and Sampling Controls

Steering before sampling

Most output problems are instruction problems, not parameter problems. If a response contains the wrong fields, wanders into unrelated topics, or ignores a required caveat, changing a sampling setting is unlikely to help. Start by specifying the target: length, structure, vocabulary, ordering, and how to handle missing information. Sampling controls then shape the variation that remains.

Effective output guidance is concrete. "Be brief" is weak; "at most 180 words, no preamble, three bullets followed by one risk line" is strong. "Use JSON" is incomplete; name the fields, their types, the allowed values, and what to emit when a value is unknown. The same principle applies to style: if the audience is a support agent, say what a support agent needs — a short explanation, a recommended action, and an escalation trigger — rather than asking for a "friendly tone."

Also define refusal and escalation behaviour. A model facing an incomplete request will otherwise fill the gap with a guess. A line such as "if the log file is absent, respond with exactly NEEDS_INPUT: log_file and stop" turns an ambiguous failure into a detectable state. This is more valuable in automation than a polite apology, because downstream code can branch on it.

Temperature

Temperature controls how strongly the model favours its highest-probability continuations. Lower values concentrate choices on the most likely tokens; higher values flatten the distribution and allow less common choices. Names and exact ranges vary across APIs, but a common scale runs from 0 to around 1 or 2 in some systems. Treat the numbers as relative within one API, not as universal constants.

For extraction, classification, and code generation against a specification, low values such as 0 to 0.2 are usually appropriate. You want the model to follow the pattern, not improvise. For drafting, naming, or exploring alternatives, moderate values around 0.5 to 0.8 can produce more varied output. Very high settings tend to produce incoherent text on longer tasks rather than useful creativity.

A temperature of zero is often described as deterministic. In practice it means greedy selection: at each step the most likely token is chosen. Because context changes with every token, and because upstream systems may differ slightly between runs, identical requests can still produce different outputs. Use zero to reduce variance, not to eliminate it. Where exact reproducibility matters, cache the result and reuse it instead of regenerating.

Exam mindset: if a question contrasts a vague instruction with a parameter tweak, the instruction is usually the better first fix. Parameters shape a distribution; they cannot supply missing requirements.

Top-p and top-k

Top-p, also called nucleus sampling, keeps only the smallest set of tokens whose combined probability reaches a threshold, then samples from that set. A value of 0.9 means the model considers the likely core of the distribution and discards the long tail. Top-k keeps a fixed number of candidates, for example the forty most likely tokens, regardless of their probabilities. Both reduce randomness, but they do so differently: top-p adapts to how peaked the distribution is, while top-k does not.

Most systems let you set temperature and top-p together, and some also expose top-k. Avoid changing all three at once. Choose one primary control, leave the others at their defaults, and measure. If you reduce temperature and top-p simultaneously and quality drops, you will not know which change caused it. A common starting point for factual work is low temperature with top-p near 0.9; for open-ended drafting, a moderate temperature with the same top-p is a reasonable baseline.

Determinism and reproducibility

Teams often ask for "deterministic" model output. It helps to separate three claims. Repeatability means repeated calls under the same conditions usually agree. Reproducibility means you can reconstruct a past result by recording the inputs and settings. Exact equality means byte-for-byte identity, which is the strongest and least realistic claim. Sampling controls mainly help with the first; engineering practice delivers the second.

To achieve practical reproducibility, record the model identifier and version, the full prompt, the parameter values, the tool results that entered context, and any seed the API supports. Pin dependencies and model versions in configuration. Store the rendered prompt rather than only its template, so later template edits do not change what a historical run actually received. When a result matters — an approval decision, a generated report attached to a release — persist the output itself.

Some APIs offer a seed parameter. Where supported, a fixed seed can make a sequence of random choices more stable, but it does not override changes in the model or in upstream context. Do not rely on a seed as a correctness control. Use validation instead: parse the output, check required fields, and retry a bounded number of times if it fails.

task: support-summary
model: pinned-model-version
temperature: 0.2
top_p: 0.9
max_output_tokens: 400
seed: 20261121
stop_sequences: ["\n\nEND"]
retry:
  on: invalid_schema_or_error
  max_attempts: 2
verifier: python tools/validate_summary.py && echo ACCEPT
fallback: if confidence < 0.7 then emit NEEDS_INPUT

The configuration shows the layering. Output guidance lives in the prompt; sampling controls limit variation; a verifier decides whether the response is usable; a retry policy handles transient failures; and a fallback handles uncertainty. No single setting is expected to do all of that work.

Interactions and failure modes

Settings interact with prompts and with each other. A high temperature combined with a weak output specification produces drift. A low temperature combined with contradictory rules produces the same wrong answer every time, which can be harder to notice than varied mistakes. A very low token limit can truncate a JSON object, turning a correct answer into invalid output. A tight top-p can prevent the model from choosing the one uncommon word that your domain requires.

  • Repetition: temperature too low on a long generative task; raise it slightly or diversify the prompt.
  • Inconsistent format: specification too vague; add a template before adjusting sampling.
  • Truncated answers: token limit too low or no stop condition; raise the limit and define an ending marker.
  • Odd vocabulary: top-p or top-k too restrictive; widen the candidate set.
  • False confidence: no escalation rule; add an explicit unknown state and validate it.

Another interaction is with evaluation. If you compare two prompts while sampling randomly, differences of a few percentage points may be noise. Use enough trials to see a stable pattern, lower variance for the comparison, or both. Conversely, if a prompt must work across many kinds of input, testing only at temperature zero can hide brittleness that appears under normal settings.

Choosing settings by task

Classify the task first, then choose the starting configuration. Extraction, routing, and schema filling want low variance and strong output structure. Summarisation wants moderate structure with enough freedom to phrase things naturally. Brainstorming wants wider exploration, usually with human selection afterward. Code changes want low variance and, more importantly, mechanical verification with tests and linters.

Write the choice down in a configuration file next to the prompt, with a one-sentence reason. "Temperature 0.2 because the output feeds a parser; top-p left at default" will still make sense six months later. A bare number in a dashboard will not. Revisit the setting when the failure pattern changes, not on a schedule.

Summary

  • Specify length, structure, fields, and fallback behaviour in the prompt before tuning sampling.
  • Temperature changes sharpness; top-p trims a probability tail; top-k caps candidate count.
  • Use low variance for extraction and code, moderate variance for drafting and exploration.
  • Repeatability, reproducibility, and exact equality are different goals requiring different measures.
  • Combine settings with validation, bounded retries, pinned versions, and recorded configurations.
