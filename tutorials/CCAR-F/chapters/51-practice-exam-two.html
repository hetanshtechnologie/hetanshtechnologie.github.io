51. Practice Exam Two and Final Review

Before you begin

This second paper is original to this book and shifts weight toward tools, protocol details, context management, and operational judgement. Take it under the same conditions as the first: forty minutes, no notes, no looking ahead. If you have not yet worked through Chapter 50, do that first — the review method described there applies here too.

Where the first paper asked "which architecture?", this one often asks "which boundary?" and "what survives?". Those questions reflect how production systems fail: not because a model cannot reason, but because state is lost, a boundary is vague, or a control is invisible.

Time split. Aim for about ninety seconds per question. Mark uncertain items and move on. A second pass with a clear head recovers more marks than fighting one hard item.

Questions

1. A tool returns a large nested object, but the agent only needs three fields. What should the tool contract do?

  1. Return the whole object so nothing is lost.
  2. Return a compact projection of the required fields plus an artefact ID for the full record.
  3. Return a natural-language paragraph with no structure.
  4. Return an error unless the caller asks for exactly one field.

2. A tool modifies a record. It is called twice after a timeout and creates two records. Which design change is the root fix?

  1. Increase the timeout.
  2. Add an idempotency key so repeated calls produce one effect.
  3. Ask the model to call the tool only once.
  4. Return a friendlier error message on the second call.

3. Which situation most strongly justifies a multi-agent design over a single agent with tools?

  1. The task has one clear goal and five known tools.
  2. Distinct subgoals need different authority boundaries and can be validated independently.
  3. The team wants the answer to sound more authoritative.
  4. The prompt is longer than one page.

4. An orchestrator must choose the next agent. The choice is obvious from two fields in the request. What is the best implementation?

  1. A model call that reasons about the best next agent every time.
  2. A deterministic rule on those fields, with a logged reason.
  3. A vote among all agents.
  4. A random selection to avoid bias.

5. Where should tenant identity come from in a tool call?

  1. From a field the model fills in based on the conversation.
  2. From trusted session context injected by the harness, never from model-generated text.
  3. From the tool description.
  4. From the user's writing style.

6. A CLAUDE.md file at the repository root says "use tabs". A subdirectory file says "use two spaces". What normally happens?

  1. The first file loaded always wins.
  2. The more specific, closer file takes precedence for that path.
  3. Both rules are ignored.
  4. The rules are merged into a four-space rule.

7. A hook should block a command that touches production credentials. Where should this check live?

  1. In a paragraph of the system prompt.
  2. In a lifecycle hook or policy layer that can deny the action before it runs.
  3. In the model's temperature setting.
  4. In the README.

8. Which use of extended thinking is most defensible?

  1. Every request, to maximise quality.
  2. Only when the task has genuine multi-step dependencies and the extra latency and cost are acceptable.
  3. Only when the output must be short.
  4. When the model seems unsure, regardless of task type.

9. Few-shot examples are helping, but the model copies superficial phrasing from them. What should change?

  1. Add more examples with identical wording.
  2. Vary surface details while holding the underlying decision pattern constant, and label why each example is correct.
  3. Remove all labels from the examples.
  4. Increase temperature to encourage originality.

10. A scratchpad grows until it dominates the context. Which hygiene rule is most important?

  1. Never remove anything, to preserve history.
  2. Keep only current invariants and open questions, with explicit size limits and periodic compaction.
  3. Store everything as prose paragraphs.
  4. Write the scratchpad in a different language.

11. Why delegate discovery work to a subagent rather than doing it in the main conversation?

  1. Subagents always produce better prose.
  2. Search noise stays out of the main context, and the parent receives a compact, structured result.
  3. It removes the need for tools.
  4. It guarantees lower latency.

12. A validation set shows that a confidence score is consistently overconfident. What should happen?

  1. Ignore it; confidence is subjective.
  2. Calibrate thresholds against observed outcomes before using them to route reviews.
  3. Raise the threshold to 100 percent.
  4. Remove the validation set.

13. Random sampling of eval cases keeps missing a rare but severe failure. What sampling approach helps?

  1. Stratified sampling that oversamples the rare slice.
  2. Larger random samples only.
  3. Sampling only easy cases.
  4. Removing the rare slice from the dataset.

14. A server-side compaction step rewrites session memory. Which property should be preserved above all?

  1. Original wording.
  2. Conversation length.
  3. Task invariants, decisions, constraints, and open commitments.
  4. The number of tool calls.

15. An MCP server needs to report long-running progress to clients. Which capability fits?

  1. Progress notifications with a token and status updates.
  2. Sending a new tool definition for each update.
  3. Silently finishing faster.
  4. Closing and reopening the connection per step.

16. A custom tool can be called by any agent in a large system. Which change best follows least privilege?

  1. Publish one general tool with a flag for every action.
  2. Split into narrow tools and expose only the set each agent needs.
  3. Give all agents the same credentials for simplicity.
  4. Remove descriptions so the model cannot find the tool.

17. A model produces valid JSON but sometimes places a date in the wrong field. Which safeguard is most specific?

  1. Ask for "more accurate output" in the prompt.
  2. Add field-level type and format validation with a repair or retry step.
  3. Switch to plain text.
  4. Increase the schema's depth.

18. A team wants every prompt change to be checked against a stable set of cases before release. What is the minimum useful setup?

  1. A large unlabelled document pile.
  2. A small labelled eval set with assertions on properties, run automatically on each change.
  3. A longer system prompt.
  4. User surveys after release only.

19. An error occurs three levels up the call stack from where it happened. What is the strongest propagation contract?

  1. Each layer converts the failure into a typed error with cause, context, and a recommended handling class.
  2. Each layer hides the error to keep output clean.
  3. Each layer retries unconditionally.
  4. Each layer writes a generic "something went wrong" message.

20. A final answer contains eight claims but only six sources were supplied. What should the evaluation flag?

  1. Answer length.
  2. Unsupported claims without a claim-to-source mapping.
  3. The model's persona.
  4. The number of bullet points.

Answer key with reasoning

1 — B

Tool outputs are context. Returning a compact projection with an artefact ID keeps the window useful while preserving a path to full detail. Whole-object returns cause bloat; unstructured prose cannot be validated.

2 — B

A duplicate side effect is an idempotency problem. Timeouts and friendlier errors treat symptoms. An idempotency key makes repeated calls safe by construction.

3 — B

Multi-agent designs earn their cost when subgoals have genuinely different authority boundaries or can be validated independently. One goal with known tools belongs to a single agent; prose length and prestige are not criteria.

4 — B

Obvious choices should be deterministic and logged. A model call adds latency and variance; voting and randomness add noise. Reserve model-based choice for genuine ambiguity.

5 — B

Identity is a security property. It must come from trusted session context, not from generated text that untrusted input could influence. Descriptions and writing style carry no authority.

6 — B

Closer, more specific instruction files override general ones for their path. This is why hierarchies exist: shared defaults plus local exceptions. Neither blanket precedence nor averaging applies.

7 — B

A denial must be enforced before the action runs. Hooks and policy layers can do that; prompts, temperature settings, and documentation cannot.

8 — B

Extended thinking trades latency and cost for reasoning depth. Use it where multi-step dependencies justify that trade. Uniform use wastes budget, and uncertainty alone is not a task property.

9 — B

Examples teach the pattern, not the wording. Varying surface features while keeping the decision rule constant, and explaining the label, reduces superficial copying.

10 — B

A scratchpad is a working set, not an archive. Keep invariants and open questions, impose size limits, and compact deliberately.Keeping everything defeats the purpose.

11 — B

Discovery produces noise. Isolating it in a subagent protects the parent's context, and a structured return makes the result usable. It does not remove tools or guarantee speed.

12 — B

Confidence is only useful if calibrated. Compare scores with outcomes on a validation set and set thresholds accordingly. Ignoring or exaggerating the problem breaks review routing.

13 — A

Random sampling represents the majority and misses thin slices. Stratifying and oversampling the rare, severe slice ensures it appears in the eval set.

14 — C

Compaction is lossy. Preserve the facts that determine correctness: invariants, decisions, constraints, and commitments. Wording, length, and call counts are not semantic content.

15 — A

Progress notifications are designed for long-running work. Redefining tools, hiding duration, or churning connections do not report status and may break clients.

16 — B

Narrow tools and per-agent exposure reduce both ambiguity and blast radius. A flag-heavy mega-tool and shared credentials widen access; hiding descriptions does not restrict it.

17 — B

Shape validation is not semantic validation. Field-level type and format checks with a repair or retry path target the actual failure. Depth and tone do not help.

18 — B

A small labelled set with property assertions gives fast, repeatable signal on every change. Unlabelled piles and post-release surveys cannot gate a release.

19 — A

Typed errors that retain cause and context let callers decide whether to retry, abort, or escalate. Hiding, blindly retrying, or flattening errors destroys the information needed for recovery.

20 — B

Provenance requires a mapping from every claim to supplied evidence. Two claims without sources are unsupported regardless of how fluent the answer reads.

Final review: the twenty decisions worth memorising

Use this list as a last-pass checklist. Each line compresses a principle developed earlier in the book.

  1. Fixed path plus audit requirement → deterministic workflow, not an agent.
  2. Agent loop → always has a stop condition, a step budget, and loop detection.
  3. Repeated tool signature → halt and report; do not hope for a different sample.
  4. Irreversible action → programmatic gate plus recorded approval.
  5. Tool description → precise purpose, boundaries, and non-use cases.
  6. Tool schema → required fields, enums, constraints, strict validation.
  7. Mutating tool → idempotency key and two-phase confirm/execute.
  8. Tool output → compact projection plus artefact reference.
  9. Multi-agent → only when authority boundaries or independent validation justify it.
  10. Handoff → typed payload with required fields, validated at the boundary.
  11. Long-running task → durable state with step, inputs, and pending approvals.
  12. Fan-out → retry transient failures, report partial results honestly.
  13. Prompt → constraints, examples near the boundary, and an abstain path.
  14. Structured output → schema checks shape; independent validation checks truth.
  15. Eval → measure retrieval, generation, and provenance separately.
  16. Context → filter, reference, then summarise; never summarise blindly.
  17. Scratchpad → invariants and open questions, with hard size limits.
  18. Delegation → keep search noise out of the parent context.
  19. Confidence → calibrate before using it to route work.
  20. Synthesis → annotate conflicts and map every claim to a source.
Exercise 51.1 — Two-minute recall. Cover the list and write as many of the twenty decisions as you can in two minutes. Repeat tomorrow. Aim for fifteen before the exam.
Exercise 51.2 — Build a one-page system. On a blank page, sketch a system with one workflow, one agent loop, one tool with strict validation, one human gate, one handoff payload, and one eval assertion. Label the boundary each control belongs to.

Check your understanding

  1. Why is an idempotency key a root fix rather than a workaround?
  2. What information does a typed handoff payload guarantee that a prose summary does not?
  3. Why should obvious routing decisions be deterministic?
  4. What does calibration allow you to do with a confidence score?
  5. Why must a final synthesis annotate source disagreement?

Summary

  • Twenty original scenario questions oriented toward tools, context, and operations.
  • Reasoned answers explain which boundary and which control the question tests.
  • A final twenty-decision checklist compresses the entire book into revision prompts.
  • Use both papers to find reasons for mistakes, not just scores.
  • Finish with recall practice and a one-page system sketch rather than more reading.
