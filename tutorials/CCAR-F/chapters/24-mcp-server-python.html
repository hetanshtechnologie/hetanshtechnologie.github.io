24. Building an MCP Server in Python

The fastest way to understand a protocol is to implement a small server. In this chapter we build one that exposes a single useful tool — looking up a term in a local glossary — and then extend it with a resource. The goal is not a production service but a working mental model: how handlers are registered, what the process does when launched, how to talk to it from a client, and which mistakes surface immediately.

A Minimal Server End to End

A server has three jobs: declare what it offers, execute requests for those offerings, and move messages over a transport. The framework supplies the message framing and version handling; you supply the declarations and handlers. Here is a complete first version using an in-memory glossary:

import asyncio
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import TextContent, Tool

GLOSSARY = {
    "idempotent": "Repeating an operation has the same effect as doing it once.",
    "context": "The information available to a model while it decides.",
}

app = Server("glossary-server")


async def list_tools():
    return [
        Tool(
            name="define_term",
            description=("Return the definition of one glossary term. "
                         "Use for exact term lookup; does not search prose."),
            inputSchema={
                "type": "object",
                "properties": {
                    "term": {"type": "string", "minLength": 1,
                             "maxLength": 80}
                },
                "required": ["term"],
                "additionalProperties": False,
            },
        )
    ]


async def call_tool(name, arguments):
    if name != "define_term":
        raise ValueError("unknown tool: " + name)
    term = arguments["term"].strip().lower()
    if len(term) > 80:
        return [TextContent(type="text",
                            text="INVALID_ARGUMENT: term too long")]
    if term not in GLOSSARY:
        return [TextContent(type="text",
                            text="NOT_FOUND: " + arguments["term"])]
    return [TextContent(type="text", text=GLOSSARY[term])]


async def main():
    async with stdio_server() as (reader, writer):
        await app.run(reader, writer, app.create_initialization_options())


if __name__ == "__main__":
    asyncio.run(main())

The important structural point is that declaration and execution are separate functions. list_tools returns metadata; call_tool receives a name plus arguments. The framework calls the first during discovery and the second during invocation. Notice also that the "not found" case returns a text item rather than raising: it is a normal outcome with a stable prefix, not a crash.

Registering Handlers

Most frameworks let you register handlers either by decorating functions or by passing them to a server object. Both styles do the same thing — they put your function in a dispatch table keyed by operation. Explicit registration is easier to inspect in a small server; decorators scale better when a module contributes many handlers.

@app.list_tools()
async def handle_list():
    return await list_tools()


@app.call_tool()
async def handle_call(name, arguments):
    result = await call_tool(name, arguments)
    return result


def dispatch(name):
    if name == "define_term":
        return define_term
    if name == "search_terms":
        return search_terms
    raise KeyError("unregistered tool: " + name)

Three rules keep handlers maintainable. Validate arguments inside the handler even though a schema exists — the schema is a contract for callers, not a substitute for defensive code. Return content objects in the shape the framework expects, with explicit content types. And keep each handler short: delegate to ordinary functions that you can unit-test without a protocol session.

Descriptions belong with declarations, not buried in handler code. If a tool's description and its implementation disagree, the model will be routed according to the description and then surprised by the result. Treat that pair as one artefact and review them together.

Use a dictionary of handlers instead of a long chain of if statements once you pass five tools. A lookup table makes it obvious which names are legal and simplifies testing.

Running the Server Locally

A local server is launched as a child process by the host. Communication happens over standard input and output, which means those streams are reserved for protocol messages. Any diagnostic text must go to standard error or a file; a stray print() on stdout corrupts the message stream and usually looks like a mysterious parse failure.

{
  "mcpServers": {
    "glossary": {
      "command": "python",
      "args": ["-m", "glossary_server"],
      "env": {"GLOSSARY_DATA": "./data/terms.json"}
    }
  }
}

Start the process once with a simple client before connecting it to a full application. Confirm that initialization succeeds, that the tool list contains exactly what you expect, and that one call returns the right text. Configuration such as file paths and timeouts should arrive through environment variables, not hardcoded constants, so the same server can run in a developer's workspace and in a test harness.

Never log request bodies containing user data to stdout. Use structured logging to stderr with a request ID, and keep sensitive values out of both logs and error strings.

Testing With a Client

A client test exercises the whole path: spawn the process, initialize a session, list tools, invoke one, and close cleanly. This catches registration mistakes, schema errors, and transport issues that unit tests of the handler cannot see.

async def smoke_test(session):
    tools = await session.list_tools()
    names = [t.name for t in tools.tools]
    assert names == ["define_term"], names

    result = await session.call_tool(
        "define_term", {"term": "Idempotent"})
    text = result.content[0].text
    assert "same effect" in text, text

    missing = await session.call_tool(
        "define_term", {"term": "not-a-term"})
    assert missing.content[0].text.startswith("NOT_FOUND")

Add three layers of tests. Unit tests call your handler functions directly with valid, invalid, and edge-case arguments. Contract tests assert that the advertised schema matches what the handler actually accepts — a schema that omits a required field is a common bug. Session tests run the smoke test above against a real spawned process. Keep the session test fast enough to run on every change; if it takes more than a few seconds, developers will stop running it.

Common Mistakes

Most first servers fail in predictable ways. The table below maps symptoms to causes so that debugging starts in the right place.

SymptomLikely causeFix
Parse error during startupLogging written to stdoutSend diagnostics to stderr
Tool never appears in the listHandler not registeredCheck decorator or dispatch table
Call rejected before handler runsArguments violate the declared schemaMatch schema to handler expectations
Model chooses the wrong toolVague or overlapping descriptionAdd object, scope, and negative clause
Hang on larger requestsBlocking call inside async handlerRun blocking work in a thread or task
Errors vanish into a stack traceException escapes the handlerReturn a structured failure payload

Two subtler issues appear later. Global mutable state — a cache or counter kept in the server process — makes results depend on call order and breaks under concurrent clients. And unbounded operations, such as reading an entire directory tree, can exhaust memory before any timeout fires. Bound every operation with a limit and return a clear "result truncated" signal when the limit is reached.

Hardening the First Version

Once the smoke test passes, add four things before sharing the server. Wrap external calls in timeouts and return a typed error payload with a code, retryability, and remediation hint. Validate and normalise inputs inside handlers: trim strings, enforce maximum lengths, and reject unexpected keys. Emit structured logs with a request ID, tool name, duration, and outcome category. Finally, version the tool names or descriptions when behaviour changes, so a host that cached an older list can detect the mismatch.

These steps are small but they change the character of the server. Instead of a demo that works when everything goes right, you get a component that fails informatively — which is what a model-facing tool needs, because the model's next decision depends on the quality of the failure.

Summary

  • A server declares capabilities, executes calls, and delegates message framing to the framework.
  • Handlers should validate arguments, return typed content, and delegate real work to testable functions.
  • Local stdio servers reserve stdout for protocol traffic; use stderr for logs and environment variables for config.
  • Layer unit, contract, and session tests to catch schema, registration, and transport faults.
  • Harden with timeouts, structured errors, bounded operations, request IDs, and version awareness.
