35. Subagents, Hooks, and Plan Mode

Why delegate to a subagent

A subagent is a separate model invocation with its own instruction set, tool set, and context window. The parent gives it a task and receives a result; the noisy intermediate work stays in the child's context. This is useful for two reasons. First, it protects the parent's context from hundreds of lines of search output. Second, it creates a natural authority boundary: a child granted only read tools cannot accidentally edit a file while investigating.

Delegation is not free. Starting a subagent costs tokens, time, and a handoff that can lose nuance. Delegate when a task is self-contained and its output can be described in a sentence or two: locating every caller of a deprecated function, assessing whether a schema migration is reversible, checking a dependency's licence, or reviewing a diff for a specific risk. Do not delegate "help with the feature" — the child lacks the conversation history and will either guess or ask the parent to repeat everything.

A useful test is the stranger test. If you would need to brief a competent stranger with twenty minutes of background before they could start, write that background into the task brief or keep the work local. Subagents excel as focused specialists, not as mind readers.

Configuring a subagent

Subagents are usually defined as markdown files with frontmatter in a dedicated directory. The fields describe identity, trigger, capability, and model choice.

---
name: migration-reviewer
description: Assess database migrations for reversibility and data loss.
  Use when a task adds, edits, or reviews a migration file, or asks
  whether a schema change can be rolled back safely.
tools: Read, Grep, Glob, Bash(git diff)
model: a-fast-model
---

You review migrations. You never apply them.

For each migration, report:
1. Whether a down path exists and what it restores.
2. Any destructive operation and the rows it can affect.
3. Whether a backfill can be batched safely.
4. One concrete failure scenario with the relevant file:line.

Return a short markdown table. End with SAFE, CONDITIONAL, or UNSAFE.
If you cannot find the schema baseline, say so instead of guessing.

The description is a routing instruction. It should say when to delegate, not merely what the agent is. A description of "database helper" will be ignored or overused; "use when a migration file is added or a rollback question is asked" gives the parent a clear decision rule. The tools list is the real safety boundary — a reviewer without write tools cannot drift into fixing the problem it was asked to assess.

Model choice is a cost and latency lever. Narrow, high-volume investigations can run on a faster model; tasks requiring subtle judgement may justify a stronger one. Choose the cheapest model that passes a small evaluation set of representative tasks, and revisit that choice when the task distribution changes.

Designing the handoff contract

The brief you give a subagent should contain four things: the goal, the evidence available, the output shape, and the stopping condition. "Investigate the login timeout" is a goal with no evidence or shape. A better brief names the log directory, the two relevant services, a ranked list of hypotheses with file and line references, and a limit such as "stop after fifteen minutes and report what you have."

Require evidence in the result. A subagent that reports "the cache is probably stale" is less useful than one that reports "the cache key at cache.py:88 omits the tenant identifier; three call sites pass different tenants." Evidence makes the parent's job verification rather than interpretive guessing. Ask for a confidence label and a list of open questions.

Context isolation is a feature. A subagent that has not read the entire conversation may miss a constraint, but it also cannot be anchored by an early wrong assumption. Include durable constraints in the brief — language, style rules, forbidden files — and let the child start clean.

Some teams use a hierarchical pattern: a coordinator splits work among three specialists and merges their results. This works when the merge is mechanical, such as combining three independent audits into one checklist. It fails when the pieces must continuously reinterpret one another's output. If the subagents need to argue about a shared design, keep the decision in the parent context instead.

Hooks as deterministic enforcement

Hooks are commands that run at defined points in the session lifecycle. They are ordinary programs, so they do exactly what they are written to do. That makes them stronger than an instruction: a prompt can persuade, but a hook can refuse. Common events include PreToolUse and PostToolUse, UserPromptSubmit, Stop, SessionStart, PreCompact, Notification, and SubagentStop.

A hook configuration names an event, a matcher such as a tool name, and a command. The command receives a JSON object on standard input containing fields like the session identifier, working directory, tool name, and tool input. Exit status carries the decision: zero allows the operation, while a non-zero status blocks it and feeds the reason back to the model. Some events also accept structured JSON output with fields such as decision or permissionDecision, allowing allow, deny, or ask.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python .claude/hooks/guard.py >> .claude/logs/guard.log 2>&1"
          }
        ]
      }
    ],
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          { "type": "command", "command": "python .claude/hooks/final_check.py" }
        ]
      }
    ]
  }
}

Use PreToolUse to prevent an action: block shell commands containing a dangerous flag, deny writes to generated directories, or require confirmation before a network call. Use PostToolUse to react: run a formatter after an edit, append an audit record, or notify another system. Use Stop as a final gate that checks whether the session's completion criteria were met before it ends.

Failure mode: a hook that blocks without explaining why. The model sees a rejection with no actionable reason and may retry the same operation several times. Always return a specific message — "writes to dist/ are generated; edit src/ instead" — and log rejections so a human can see whether the rule is too strict.

Keep hooks fast and side-effect-aware. A hook that takes twenty seconds turns every tool call into a pause. A hook that writes secrets into a shared log creates a new security problem. Test the command directly with representative stdin JSON before wiring it into the configuration, and version it with the repository so its behaviour is reviewable.

Plan mode and deliberate iteration

Plan mode separates investigation from modification. In the planning phase the session reads files, searches, and asks questions, but does not change the repository. The output is a proposed sequence of actions. A human reviews that proposal, requests changes, and only then grants permission to execute. This is the right default for multi-file changes, ambiguous requirements, schema edits, and anything with a costly rollback.

A good plan is specific enough to be wrong. It names the files to be touched, the commands to be run, the expected tests, the main risk, and the rollback path. "Refactor the service layer" cannot be meaningfully approved. "Split services/billing.py into pricing and invoicing modules, update the three imports in api/routes.py, add unit tests for the tax rounding branch, and keep the old module as a re-export for one release" can be.

Iteration is where plan mode earns its keep. When the reviewer says "do not change the public interface," the plan is revised before any code is written, at a fraction of the cost of rewriting an implementation. Use a short loop: present plan, collect objections, revise, present again. Limit it to two or three rounds; if agreement never converges, the requirement is unresolved and needs a human decision rather than another draft.

Skip plan mode for small, well-understood edits where the cost exceeds the benefit. A one-line typo fix does not need a document. The decision is proportional: the more files, the more irreversible the operation, and the more ambiguous the request, the stronger the case for planning first.

Putting the three together

These mechanisms compose naturally. A plan-mode session can delegate codebase surveys to read-only subagents, then use a hook to guarantee that no writes occur before approval. During execution, hooks enforce the boundaries the plan assumed — for example, blocking edits to generated files. After execution, a subagent can audit the diff against the approved plan and report deviations.

Summary

  • Subagents trade handoff overhead for isolated context and narrow tool authority.
  • Routing descriptions, minimal tools, and evidence-based output contracts make delegation reliable.
  • Hooks enforce deterministic rules at lifecycle events; always return a specific rejection reason.
  • Plan mode delays modification until a human has reviewed a concrete, testable proposal.
  • The three mechanisms compose: delegate research, enforce boundaries, and approve before execution.
