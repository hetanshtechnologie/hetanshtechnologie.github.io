31. Permission Modes

Permission modes answer a narrow question: which actions may the assistant take without asking? They are not a measure of trust in the model, and they are not a substitute for review. They are a control surface for irreversibility. A useful policy lets cheap, reversible work flow freely while placing a deliberate pause in front of actions that are expensive, hard to undo, or visible outside your machine.

Why approval levels exist

Consider two actions: opening a file and force-pushing a branch. Both are tool calls. The first has no lasting effect; the second can erase commits for everyone on the team. Treating them identically is the core mistake in permission design. Approval levels express the difference in a form the client can enforce before the call runs.

The second reason is human attention. If every file edit produces a dialog, people start approving without reading, and the control becomes decoration. A good policy is selective enough that each prompt still deserves attention. Aim for a handful of meaningful approvals per session rather than dozens of reflexive ones.

FactorLow concernHigh concern
ReversibilityEasy to undo locallyPermanent or shared effect
Blast radiusOne file in the workspaceRepository, cloud, or other people
ObservabilityVisible in the diffHidden in logs or external state
CostNear zeroBilled API or compute usage

A ladder of approval levels

Most environments offer a small set of levels that can be arranged from cautious to permissive. Think of them as a ladder, and choose the lowest rung that still lets the work progress.

  1. Plan only. The assistant investigates and proposes steps but changes nothing. Best for unfamiliar codebases or high-stakes refactors.
  2. Review each action. Reading is free; edits and commands pause for approval. This is the sensible default for interactive work.
  3. Accept edits in scope. File changes inside the project proceed automatically; shell commands and external calls still require a decision.
  4. Broad automation. Most actions run without prompting, inside a sandbox with restricted network and credential access.
  5. Unrestricted. No approvals and no sandbox. Appropriate only in a disposable environment with nothing valuable to lose.

Level three is often the sweet spot for an experienced developer. Edits are visible in version control and can be reverted, so automatic acceptance saves time. Commands that compile, install, or transmit remain gated. Level four belongs in a container that can be thrown away; without that boundary, a single mistaken command can affect the host.

A permission mode controls the assistant's tools, not your operating system. File ownership, database grants, and cloud IAM still apply. Keep those underlying controls narrow so that a permissive mode cannot become a full compromise.

Risk profile of common actions

Classify actions by consequence rather than by syntax. rm -rf ./build and rm -rf ~ look similar but differ enormously in scope. Likewise, a database query and a migration both involve SQL, but only one changes production state.

ActionSuggested handlingReason
Read a source fileAllowNo side effects
Edit a tracked source fileAllow in scoped modeRevertible through git
Run unit tests or lintAllowLocal and bounded
Install an unfamiliar packageAsk every timeExecutes third-party code
Delete outside the workspaceDenyBeyond review via diff
Push, deploy, or migrateAsk every timeShared and hard to reverse

Pay special attention to commands that download and execute code in one step, to scripts that read environment variables, and to anything that writes outside the project directory. A request to "clean up temporary files" is a classic route to a destructive command because the scope sounds harmless while the actual path is not.

Team policy and guardrails

Personal preference and organizational policy are different things. A developer may choose to accept edits automatically; the organization must still be able to forbid certain commands. Encode the non-negotiable rules centrally, in settings that apply to every session, and keep them short enough to understand. Deny rules should win over allow rules, and an unmatched action should default to asking rather than running.

{
  "permissions": {
    "allow": [
      "Read(src/**)",
      "Edit(src/**)",
      "Bash(npm test)",
      "Bash(npm run lint)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)",
      "Bash(curl * | sh)",
      "Edit(.env*)"
    ],
    "ask": ["WebFetch", "mcp__deploy__*"]
  }
}

# Effective decision, expressed as a rule order
if matches(action, deny_rules):
    decision = "block"                 # deny always wins
elif matches(action, ask_rules) or not matches(action, allow_rules):
    decision = "prompt"
elif risk_score(action) >= 8:
    decision = "prompt"
else:
    decision = "run"
Write rules with explicit paths and named commands. A wildcard that allows every shell command also allows every command you meant to deny, and a broad edit rule can overwrite your own policy files.

Guardrails work best in layers. Permission rules decide what may run. A sandbox limits what a permitted process can reach, such as denying network access or hiding home-directory credentials. Hooks can add checks at lifecycle points, for example scanning a command before execution. Version control provides the last layer: a clean branch and a reviewed diff make recovery possible when the earlier layers fail.

Automation and CI trade-offs

Automated sessions cannot answer a prompt, so a configuration that works interactively may hang in a pipeline. The usual response is to pre-approve a narrow set of commands and run the job in a disposable container with a short-lived token. The container is the important part: automation with broad permissions and no isolation concentrates risk in a place where nobody is watching in real time.

Prefer deterministic automation. Give the job a specific prompt, a fixed working directory, a pinned dependency set, and a machine-checkable success condition. Log every tool call with its arguments and decision so a failed run can be reconstructed. If the agent needs an action outside the allowlist, fail the job with a clear message instead of silently skipping the step.

Failure modes and recovery

Over-restrictive policies produce approval fatigue: people click through prompts without reading them, which is functionally equivalent to no policy. If that happens, remove prompts for reversible local actions and keep them for genuinely consequential ones. Under-restrictive policies produce incidents: an unreviewed command deletes a directory, pushes a commit, or exposes a token. When that happens, treat the policy as defective, not the operator as careless.

Inconsistent policies across a team are a quieter problem. If one developer runs unrestricted and another reviews every edit, code review becomes the only shared control. Align the defaults, document the exceptions, and review the rule set whenever a new tool or MCP server is introduced. After any incident, add the smallest rule that would have prevented it and test that the rule does not block ordinary work.

Summary

  • Permission modes govern actions, not intelligence; classify work by irreversibility and scope.
  • The approval ladder ranges from plan-only to unrestricted, with scoped edit acceptance as a practical middle.
  • Reads and local checks can run freely; installs, deletions, pushes, and migrations deserve prompts or denials.
  • Central policy should override local preference, with deny rules winning and unknown actions asking.
  • Automation needs narrow allowlists, disposable environments, and short-lived credentials.
  • Watch for approval fatigue and incidents; both are signals to redesign the policy.
