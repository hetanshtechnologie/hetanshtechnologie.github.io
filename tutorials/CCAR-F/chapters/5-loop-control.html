5. Stopping, Iterating, and Escalating

A loop without a stopping rule is a defect waiting for an input. The same property that lets an agent adapt — choosing its own next step — also lets it repeat a failed step forever, burn a budget on a question it cannot answer, or declare success prematurely. Control is not an optional safety accessory; it is part of the system's definition. This chapter turns "the loop should stop sensibly" into concrete budgets, conditions, detectors, and handoffs.

Why an unbounded loop is a defect

Three things go wrong when autonomy is unbounded. Cost grows without a ceiling: ten iterations at 2,000 tokens each is 20,000 tokens for one task. Latency becomes unpredictable: a request that usually finishes in four steps sometimes takes twenty. And failure becomes ambiguous: if the system never stops, you cannot tell whether it is still working or stuck. A bounded loop converts these into measurable quantities.

Bounds also change behaviour for the better. When a system knows it has eight steps, it tends to use them deliberately; when it believes it has unlimited steps, it explores redundantly. This is why a step budget is not merely a kill switch — it is a resource-allocation decision that shapes the policy. Set it too low and legitimate work is cut off; set it too high and you pay for indecision.

Where budgets belong. A budget enforced only by telling the model "stop after eight steps" is a suggestion, not a control. The runtime must count iterations and tokens and refuse further tool calls when a limit is reached. Keep the instruction for the model's planning and the counter for enforcement.

Step budgets, token budgets, and time limits

Use at least two independent budgets. A step budget limits the number of decide–act iterations; a token budget limits total context consumed; a wall-clock limit protects latency. They fail differently. A loop can take five steps but 30,000 tokens because one tool returned a huge document; it can also take twenty cheap steps in two seconds. Any single budget leaves a gap.

BudgetTypical starting valueWhat it catchesWhat it misses
Steps6–12 per taskRepeated actions, indecisionHuge single results
Tokens12k–30k per taskContext bloat, long documentsMany cheap steps
Wall clock2–30 secondsLatency budget breachesCost overruns
Write actions0–3 per taskUncontrolled side effectsRead-only waste

Set the values from the requirement, not from habit. If a service must answer within three seconds at the 95th percentile and each model step averages 400 milliseconds, a twelve-step budget already consumes 4.8 seconds before tool time; the budget must be six steps or fewer. If the task is an overnight analysis with a two-minute allowance, twelve steps is generous but reasonable.

Reserve part of the budget for recovery. A common pattern is to cap normal work at eight steps and keep two additional steps exclusively for correcting a detected failure. Without that reserve, the system exhausts its budget on the mistake and has no room to fix it.

Stop conditions: success, exhaustion, and defeat

Distinguish three reasons to stop. Success means the verification condition is met and the goal is satisfied. Exhaustion means the available sources or tools have been tried without finding an answer. Defeat means a constraint was violated — a policy denial, an unrecoverable tool error, or a budget hitting zero. Each deserves a different response.

A success condition should be checkable from state, not inferred from tone. "The refund was issued and the confirmation id is recorded" is checkable. "The assistant believes the issue is resolved" is not. Where a check cannot be automated, require a human confirmation before labelling the task complete. This matters especially for write workflows: a tool returning 200 is evidence of an attempt, not proof that the business outcome occurred.

Exhaustion is underused. Agencies often keep searching when every named source has returned nothing, because nothing told them the search space was finite. Give the loop an explicit list of sources and mark them as visited. When all are visited and the goal is unmet, stop and report what was checked. This produces a useful answer instead of a silent timeout.

Detecting loops and stalled progress

A loop is not merely long; it is unproductive repetition. Detection compares the current state to earlier states. Hash the tuple of (tool_name, normalised_arguments, result_digest) after each action. If the same hash appears three times, the system is almost certainly cycling. Normalise arguments so that a timestamp or a reordered key does not hide an identical call.

Progress detection is subtler. Define a progress signal — a new fact added to state, a changed status field, a reduced open-question count. If four consecutive iterations add no new fact, the loop is stalled even if the tool calls differ. Stalled loops often arise from a mismatched tool: the model keeps querying a search endpoint that cannot answer a question requiring arithmetic.

Once a cycle is detected, do not simply increment a counter and continue. Break the pattern deliberately: switch tool, ask the user for clarification, or escalate. Repeating the same action with a slightly different prompt is the classic failure of naive retry logic. The control layer should force a change of strategy, not just a change of wording.

loop_control:
  max_steps: 8
  reserve_steps: 2
  max_tokens: 24000
  max_wall_clock_ms: 15000
  max_write_actions: 2
  cycle_detection:
    window: 12
    identical_call_threshold: 3
    progress_fields: [new_facts, open_questions, status]
    stall_after_no_progress: 4
  on_cycle: force_strategy_change
  on_stall: escalate("no_progress")
Failure mode: a detector that counts only identical tool names. A loop that calls search_docs(q1), search_docs(q2), search_docs(q3) with synonyms looks varied but makes no progress. Include result digests and a progress signal, not just call identity.

Escalation paths and handoff payloads

Escalation is a controlled transfer of responsibility, not an admission of defeat. There are three common destinations: back to the user for clarification, to a human operator for a decision, and to a different automated component with different capabilities. Each needs a payload that carries enough context to continue without repeating work.

A handoff payload should contain the original goal, the constraint that triggered escalation, the actions already taken, the key observations, the current best hypothesis, and the specific question the recipient must answer. Omitting the last item is the most common mistake — a human receives a transcript and has to infer what is being asked. State the ask explicitly: "Approve a refund of 120 units for ORD-104827; policy limit is 50; evidence attached."

  1. Detect the trigger: budget, policy denial, repeated cycle, or low confidence.
  2. Freeze state so the run cannot continue in parallel with the handoff.
  3. Build the payload with goal, actions, evidence, and a single explicit question.
  4. Route by trigger type — clarification to user, authority to operator, capability to specialist.
  5. Record the handoff identifier in the trace so the eventual resolution can be linked back.

Escalation thresholds should reflect cost asymmetry. If a wrong answer costs little and a human interruption costs a lot, tolerate more uncertainty before escalating. If a wrong write action is expensive or regulated, escalate early. A refund agent might escalate at any amount above 50 units even when it is 95 percent confident, because the downside of an error is larger than the delay of a question.

Summary

  • Unbounded loops fail on cost, latency, and diagnosability; bounds make behaviour measurable.
  • Use step, token, wall-clock, and write-action budgets, with a reserve for recovery.
  • Success must be verifiable from state; exhaustion follows a finite source list; defeat follows a constraint breach.
  • Detect cycles with normalised call hashes and stalls with a progress signal, then force a strategy change.
  • Escalation routes to a user, an operator, or a specialist depending on the trigger type.
  • A good handoff carries the goal, actions, evidence, and one explicit question for the recipient.
