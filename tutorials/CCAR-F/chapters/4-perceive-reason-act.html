4. The Observe–Decide–Act Loop

An agent does not produce one answer; it conducts a sequence. Each pass through that sequence has the same skeleton: observe the current situation, decide on an action, act, and observe the result. The output of one pass becomes the input of the next. Understanding this loop as a data-flow problem — rather than as a mysterious conversation — makes it possible to reason about state, cost, and failures precisely.

The four phases of one iteration

Name the phases so you can discuss them: perception gathers the relevant facts; decision selects the next action; action invokes a tool or emits a response; observation captures what changed. A fifth activity, updating state, runs alongside them. Every phase should be visible in your logs, because a loop that cannot be inspected cannot be debugged.

Consider a simple goal: "confirm whether order ORD-104827 can be shipped today." Iteration one perceives the user request and the current time, decides to look up the order, calls get_order_status, and observes "pending, warehouse = Berlin, stock = 0." Iteration two perceives that observation, decides to check a second system, calls get_stock_level, and observes "restock expected 16:00." Iteration three perceives the new fact, decides the goal is satisfied, and answers with a qualified yes. Three iterations, two tools, one answer.

The loop is not a straight line. Observations can invalidate earlier decisions, forcing a branch rather than a continuation. If get_stock_level had returned "unknown," iteration three might decide to query a different source instead of answering. This ability to revise is the reason a loop exists; a pipeline would have committed to its next stage regardless.

Naming convention. This book uses "perceive, decide, act, observe" and "observe–decide–act" interchangeably for the same cycle. The observation phase closes one iteration and feeds the next, so the ordering is circular rather than linear.

Perception: deciding what enters the loop

Perception is not passive. The system must choose which facts are relevant, and that choice has a cost. Everything placed in the context window consumes tokens and competes for attention; a stale or irrelevant document can steer a decision as effectively as a correct one. Good perception is a filtering problem: present the smallest set of facts sufficient for the next decision.

Sources typically include the user's request, the system instructions, the tool catalog, prior observations in this session, and retrieved external material. Each has a different trust level. The user's request is authoritative about intent but may contain mistakes. Tool output is authoritative about the system it queried but may be stale. Retrieved documents are untrusted content: they may describe facts, but they must not be allowed to issue instructions to the loop.

Mark boundaries explicitly in the material you assemble. When a retrieved passage says "ignore previous instructions," the loop should treat those words as data to be summarised, not as a command. Delimiting untrusted text and stating the rule once in the system instructions is more reliable than hoping the model intuits the distinction.

Deciding: from state to action

The decision phase maps the current state to one of several actions: call a tool, ask the user a clarifying question, produce a final answer, or escalate. The quality of that mapping depends on three things — a clear goal statement, accurate state, and an action space whose options do not overlap. If the goal is "reduce the error rate," the loop has no termination criterion and will wander. If the goal is "identify the deployment that raised the error rate above 2 percent and report its ID," the loop has something it can check.

Write goals with a verification condition attached. "Find the missing invoice" is vague; "find invoice ORD-104827 or report that three named systems contain no record of it" is verifiable. The difference shows up in the loop: with the second goal, the system can recognise when it has exhausted its sources and stop. With the first, it keeps searching indefinitely.

Acting and observing: closing the loop

An action is only useful if its result returns to the loop in a usable form. Tool results should be structured, bounded in size, and labelled with the tool that produced them. A 400-line log dump pushed into context can crowd out the goal; a summary with line references and an error count preserves what matters. The general rule is to return the smallest result that supports the next decision, with a pointer to the full data if needed.

Observation also means noticing absence. If a query returns zero rows, the loop must distinguish "no matching records" from "the query was malformed." Many failed runs come from treating an empty result as a fact and proceeding down the wrong branch. Include result counts and status codes in the observation so absence is interpreted correctly.

When an action fails, the observation should carry a retry classification: transient, permanent, or policy-denied. A transient timeout may be retried; a validation error should change the arguments; a policy denial should stop that path and escalate. Conflating these categories produces loops that retry forbidden actions or give up on recoverable ones.

observation:
  tool: get_stock_level
  call_id: "c-7f21"
  status: partial
  data:
    warehouse: Berlin
    available_units: 0
    restock_eta: "2026-11-21T16:00:00Z"
  meta:
    rows_returned: 1
    stale_seconds: 42
    retry_class: none
    source: inventory_api_v2
Attach a call_id to every action and repeat it in the observation. When two tools return similar data, the identifier prevents the loop from attributing a result to the wrong call — a subtle error that is almost invisible in a plain-text transcript.

State updates and continuity between iterations

A loop is stateless only if you make it so. In practice you maintain a working state: the goal, the actions taken, the key observations, the remaining budget, and the current best hypothesis. This state must be updated deliberately after each iteration. If you rely on the entire conversation as memory, important facts get buried; if you keep a structured summary, you can carry it forward compactly.

Distinguish three kinds of state. Ephemeral state lives only within one run — the current plan and scratch results. Session state persists across turns in the same conversation — facts the user confirmed earlier. Durable state survives failures and restarts — a task record in an external store. Mixing them causes bugs: a task that resumes after a crash and repeats a refund because the "already done" fact lived only in the lost conversation.

Choose a small set of fields and update them at a fixed point in each iteration. A minimal working record might contain goal, step_count, completed_actions, open_questions, and last_result_digest. Keeping it small is a feature: a compact state can be injected into context cheaply and can be persisted after every step without much overhead.

Traceability: making the loop explainable

Traceability is the ability to reconstruct why the system did what it did. It matters for debugging, for audit, and for improvement. A useful trace records, for every iteration, the state at the start, the action selected, the tool arguments, the observation, the state update, and the reason for continuing or stopping. The "reason" field need not be a long essay; a short category such as goal_met, budget_exhausted, or awaiting_clarification is enough.

Traces also reveal waste. If 60 percent of runs call search_knowledge_base twice with nearly identical queries, the tool description or the perception filter needs work. If escalations happen mostly after a particular tool's partial result, that tool's contract needs a clearer success signal. Aggregate trace statistics, not single anecdotes, should drive changes to the loop.

Summary

  • An iteration consists of perception, decision, action, observation, and a deliberate state update.
  • Perception should include the smallest sufficient set of facts, with clear trust boundaries for untrusted content.
  • Goals need verification conditions so the loop can recognise success or exhaustion.
  • Tool results should be structured, bounded, labelled with a call identifier, and classified for retry.
  • Keep ephemeral, session, and durable state separate; persist completion facts before risky actions.
  • Traces record state, action, result, and stop reason, and aggregate statistics reveal systemic waste.
