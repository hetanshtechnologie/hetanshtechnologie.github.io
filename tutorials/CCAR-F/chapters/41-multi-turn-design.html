41. Multi-Turn Interactions and State

A single prompt is a transaction. A conversation is a process. The moment an assistant must remember what was said three turns ago, honour a decision made five turns ago, or notice that the user has quietly changed the goal, you are no longer writing a prompt — you are designing a turn-taking system with state. This chapter treats the turn as the smallest unit of design and shows how context, state, and repair interact over a long exchange.

Turns as the unit of design

Most failure reports say "the model gave a wrong answer," but the defect is usually in how the turn was framed. A turn has four parts: the user's contribution, the context the model can see, the action the model takes, and the state that survives when the turn ends. Design all four, not just the first two.

Begin by classifying turns. In a support assistant, a typical session contains a goal turn (state the problem), zero or more clarification turns (fill missing slots), one or more action turns (call a tool, fetch data), and a close turn (confirm resolution). Each class deserves a different system instruction and a different stopping rule. A clarification turn should end with exactly one focused question; an action turn should end only after the tool result has been observed and interpreted.

A useful discipline is the "one job per turn" rule. Ask the model to advance exactly one piece of the task per response. When a turn tries to clarify, decide, act, and summarise simultaneously, the output becomes hard to validate and harder to repair. In practice, splitting a three-job turn into two or three turns raises latency slightly but sharply reduces the rate of silent errors.

Name your turn types in code, not just in prose. An enum such as GOAL | CLARIFY | ACT | CONFIRM | REPAIR lets you attach the right tools, temperature, and stopping rule to each turn instead of relying on the model to infer the mode.

How context accumulates across turns

Every turn adds tokens. If the assistant echoes a long tool result back on each reply, the transcript grows quadratically: turn one carries 2,000 tokens, turn two carries 4,000, turn ten carries 20,000, and the cost of each subsequent reply climbs with it. Accumulation is not free, and it is not neutral — distant instructions compete with recent ones for influence.

Three patterns keep accumulation controlled:

  • Append only the deltas. Store the user message, the assistant's message, and a compact record of any tool call. Do not reinsert full tool payloads into the conversational transcript when a short citation would do.
  • Pin the contract, rotate the evidence. Keep the system instruction and the task goal fixed at the front. Let the middle of the context hold the current evidence, replacing stale evidence as the conversation moves on.
  • Anchor with a recap. After every three to five substantive turns, insert a short "current understanding" block that restates the goal, the confirmed facts, and the open questions. This gives later turns a reliable summary even if earlier detail fades.

Consider a flight-rebooking dialogue. The original goal — "move my Tuesday flight to Wednesday" — is stated in turn one. By turn eight the transcript is full of seat maps and fare rules. Without a pinned goal, the model may happily start optimising a seat it was never asked about. The recap block is the cheap insurance that keeps the objective in view.

A recap block is a convenience, not an authority. If the recap contradicts the user's latest message, the latest user message wins. Always timestamp or version recaps and re-derive them from the source turns when a conflict is detected.

Turn management policies

Turn management decides when to ask, when to act, and when to stop. Three policies cover most systems.

Fixed script (state machine)Regulated flows, forms, KYCFeels rigid; user cannot skip aheadAllow "out of order" slots to be captured and parked

Hybrid (-scripted skeleton, model-filled slots)Most production assistantsBoundary confusion between stagesPublish the active stage to the model each turn

Regardless of policy, set numeric bounds. A common configuration is a maximum of 12 user turns, a maximum of 3 clarification questions before escalation, and a maximum of 5 tool calls per action turn. When a bound is hit, the assistant should not silently keep going; it should hand off or state what is blocking completion. Bounds convert an infinite vague problem into a finite, testable one.

Also budget the kinds of turns. If clarification turns exceed roughly 25 percent of a session, the intake prompt is probably missing fields that could be collected in one structured form. If action turns dominate but resolution stays low, the tools are likely failing and the model is retrying rather than reporting.

Carrying state across turns

State is the data that must survive the boundary between turns. Distinguish three kinds:

  1. Conversation state — the goal, the slot values collected so far, and the open questions.
  2. World state — facts about the external system, such as the current booking reference or the balance after a transaction.
  3. Control state — counters, retry budgets, and the active turn type.

Keep state outside the model. The transcript is a view of state, not the state itself. Maintain a structured record in your application, inject the relevant slice into the prompt at each turn, and update it from a validated model response rather than from free text. This makes state inspectable, diffable, and recoverable after a crash.

A compact state record might look like this. Notice that each field has an owner and a confidence, so the system knows which values are user-provided and which were inferred.

{
  "session_id": "S-4821",
  "turn_index": 6,
  "active_stage": "ACT",
  "goal": "rebook Tuesday flight to Wednesday",
  "slots": {
    "passenger": {"value": "A. Rao", "source": "user", "confidence": 1.0},
    "date": {"value": "2026-11-25", "source": "user", "confidence": 0.95},
    "fare_class": {"value": null, "source": "inferred", "confidence": 0.4}
  },
  "control": {"clarifications_asked": 1, "tool_calls": 3, "retries_left": 2},
  "guard": "retries_left > 0 && turn_index <= 12"
}

The guard string is not executable by the model; it is evaluated by your application before a tool call is permitted. Keeping guards in code is the difference between "the model was told to stop" and "the model was made to stop."

Repairing a derailed conversation

Conversations drift. The user answers a question from two turns late, the model misreads a negation, or a tool returns stale data that the model treats as current. Repair is the explicit act of bringing the dialogue back to a known-good state.

Use a three-step repair pattern. First, detect: compare the latest user message against the active slot set and flag contradictions, or trigger when a confidence drops below a threshold. Second, acknowledge: name the mismatch plainly — "I had noted the 25th, but you just said the 26th; which is correct?" Third, rewrite: update the state record, invalidate any dependent facts, and restate the plan.

Invalidation matters more than it seems. If the travel date changes, every derived fact — available flights, quoted fare, seat hold — becomes stale. A repair that updates the date but keeps the old fare quote is worse than no repair, because it looks coherent. Propagate the change through the dependency graph, or mark downstream slots as unknown and re-collect them.

Exercise 41.1 — Design a turn ledger. Take a workflow you know (for example, resetting a password or filing an expense). List the turn types it contains, assign a maximum count to each, and write the state record fields with an owner and confidence for every slot. Then state two guards your application would enforce in code rather than in the prompt.
Exercise 41.2 — Repair a derailed dialogue. Write a six-turn dialogue in which a user changes a key requirement in turn four and the assistant has already acted on the old value in turn three. Mark the exact turn where drift begins, list every state field that must be invalidated, and draft the acknowledgement and rewrite messages. Explain how you would test that no stale value survives.

A worked policy in one paragraph

Put together, a robust multi-turn assistant pins a fixed contract, tags each turn with a type, injects a structured state slice, enforces numeric bounds in code, recaps every few turns, and treats repair as a first-class turn type. When you can describe all of that in a paragraph, you can also turn it into a test suite: assert the state after each turn, assert the guard fires at the bound, and assert that a deliberate contradiction produces a repair rather than a confident wrong answer. Multi-turn design is therefore less about clever phrasing and more about making the invisible state visible and enforceable.

Summary

  • Design the turn, not just the prompt: user input, visible context, action, and surviving state.
  • Append deltas, pin the contract, rotate evidence, and recap every three to five turns.
  • Choose a turn-management policy — fixed, model-led, or hybrid — and enforce numeric bounds in code.
  • Keep a structured state record outside the model with owners and confidence for each slot.
  • Repair drift by detecting, acknowledging, and rewriting state, including all dependent facts.
