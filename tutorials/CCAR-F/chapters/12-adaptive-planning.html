12. Adaptive Planning and Ambiguity

Every plan is written against assumptions, and the real world rarely reads them. A tool returns a different schema, a source is missing, or an early result contradicts the premise of step five. An adaptive plan treats change as input: it notices a mismatch, decides whether it matters, revises only the affected portion, and keeps correct work. This chapter covers the triggers, registers, questions, and guardrails that make that behaviour deliberate.

Triggers: when the plan is no longer valid

Replanning without a trigger is thrashing; failing to replan after a material change is stubbornness. Define triggers as observable conditions with thresholds, not as vague impressions that "things are going badly." Most useful triggers fall into five classes:

Trigger classObservable conditionExample thresholdDefault response
New evidenceSource fact contradicts a recorded assumptionAny contradiction in a critical fieldInvalidate affected steps
Tool failureConsecutive failures of the same call3 attempts in one stageSubstitute route or escalate
Specification gapRequired field absent from the briefAny field marked unknownAsk or choose a reversible default
User correctionExplicit rejection of an intermediate resultOne correction with a stated reasonPatch plan, keep stable prefix
Budget or timeConsumed tokens or elapsed time80% of budget with 50% of work leftReduce scope, report shortfall

Each trigger carries a severity: a missing optional field is a note; a missing required field is a blocker; a slow tool becomes a route-change trigger only when it breaches a deadline. Severity decides whether to pause, patch, or continue with a recorded deviation. Written rules turn "the agent got confused" into a traceable decision.

The replanning loop

Adaptation is a six-step loop: detect a trigger; scope which steps depended on the invalid premise; decide to continue, patch, substitute, or abort; preserve the stable prefix of valid steps; publish a new plan version with a change note; continue from the first affected step, reusing checkpoints whose digests still match.

replan:
  trigger: tool_failure | new_evidence | spec_gap | user_correction | budget
  impact: steps [3,4,5] because assumption A-02 changed
  decision: patch
  stable_prefix: [1,2]
  new_plan_version: v4
  change_note: "Currency set changed from 2 to 3; stage 3 must remap units."
  budget: replans_left = 1, tokens_reserved = 12000
  guard: if ( replans_left < 1 && severity == "blocker" ) -> ask_user()

Preserving the stable prefix is the most important and most often skipped step. A naive replanner rewrites the entire plan from scratch, which invalidates checkpoints, repeats expensive tool calls, and can quietly alter decisions the user already approved. A good patch has three properties: it changes the smallest set of steps, it names the assumption that changed, and it keeps a diff. With a diff, a reviewer can answer "why is step 4 different?" without reconstructing the whole session.

Bound the number of replans. Give a run a replan allowance — commonly two or three for a medium task — and reserve a slice of the token budget for it. When the allowance is exhausted, the agent must either complete with documented deviations or ask a human. Unlimited adaptation is a way of postponing the moment when the task should be declared impossible.

Assumption registers

An assumption register is a small table of things the plan believes but has not verified. It is the antidote to hidden premises. Each row has an ID, a statement, a confidence level, the source of the belief, a test that would verify it, and an expiry condition. When a trigger fires, the agent can look up which assumptions were affected instead of guessing.

IDAssumptionConfidenceSourceVerification test
A-01Input CSV uses UTF-8 encodingHighFile metadataRead first 4 KB without errors
A-02All amounts are in one currencyMediumSample of 20 rowsDistinct currency codes = 1
A-03The approval API is reachableLowDocumentation onlyHealth probe before stage 6

Confidence is not decoration. Low-confidence assumptions deserve an early, cheap test — a health probe, a header check, a sample of 20 rows — before expensive work depends on them. This is the principle of front-loading uncertainty: spend a little effort early to avoid a large rewrite late. High-confidence assumptions still belong in the register, because when they fail the failure is usually surprising and needs a recorded reason.

Expired assumptions should be re-verified rather than silently trusted. A fact sampled from a file at the start of a long run can be invalid if the file was updated during the run. Attach a digest or timestamp to the evidence source and invalidate any assumption whose source changed. If verification is impossible — for example, an external service is down — demote the assumption to unverified and let downstream gates require a human check before irreversible actions.

Clarification questions: asking well and asking once

A vague brief creates a decision: proceed with a default or ask. Ask when the answer changes the structure of the work, when a wrong guess is expensive or irreversible, or when two reasonable interpretations would produce incompatible outputs. Proceed when the difference is cosmetic, when a reversible default exists, or when the user is unavailable and a documented assumption can carry the run. A useful test is the rework test: if a wrong guess would force more than about 20% of completed work to be redone, ask now.

Questions should be concrete and cheap to answer. Instead of "What format should the report use?", offer two named options with a recommendation: "Should the report be a one-page executive brief (default) or a detailed 10-page analysis? I recommend the brief for this audience unless you need the evidence tables." Good questions carry three things: a short context, a small set of mutually exclusive options, and a default that lets the user reply with a single word. Batch related questions into one message — three questions asked together cost one interruption; three interruptions cost three.

Avoid hypothetical questions. Asking about a situation that has not occurred ("What would you do if the API were down?") shifts the burden back to the user. Ask about the live decision instead ("The API is down; should I use the cached export or stop?"). The second question has a real answer and an actionable consequence.

When no answer is available, proceed with a conservative default and label it. Mark the affected output with assumption: A-04 and include the assumption in the final report, so a reader can see which parts were decided on their behalf. Never convert an unanswered question into an unmarked fact; that is the point where an adaptable system becomes an unreliable one.

Incomplete specifications and safe defaults

Incomplete specs are normal at the start of a project. The architect's job is to make incompleteness explicit and to choose defaults whose failure is cheap. Three rules help. First, use an explicit sentinel such as unknown or not_supplied rather than an empty string or zero, so downstream components can detect missing information. Second, reorder work so reversible actions come first: draft before publish, simulate before execute, validate before send. Third, defer any step whose default could cause an external side effect. If the shipping address is missing, prepare the label but do not print it.

Represent unknowns in the output schema itself. A field defined as amount: number | "unknown" forces every consumer to handle the unknown case. A field defined simply as number invites the model to invent a plausible value, and invented values are indistinguishable from real ones once they are in a report. For each unknown, record who could resolve it, by when, and what happens if nobody does — usually omit_from_output, escalate, or use_default.

Preventing replan thrash

An agent that replans after every new observation can become stuck in a loop: plan, discover, replan, discover a consequence of the replan, replan again. Three controls keep adaptation stable. A change threshold requires the new evidence to alter a critical field or a dependency before the plan changes; cosmetic differences are recorded, not acted upon. A cooldown prevents a second replan within a short window unless the trigger is a blocker. A stable prefix locks completed steps with valid digests so a replan cannot touch them.

Track plan versions with a one-line reason each. If successive versions differ only because a field was misread, improve the reading step instead of patching downstream. Sometimes the right move is to stop adapting, report the ambiguity, and ask for a specification.

Exercise 12.1 — Build an assumption register

A planning task must book travel and submit an expense report. The brief says "book the usual option" and "submit after approval." List four assumptions with confidence levels, verification tests, and default actions if the assumption fails. Mark which should be checked before any booking occurs.

Hint: front-load the checks whose failure would make a booking expensive to reverse.

Exercise 12.2 — Patch, do not restart

A six-step report plan has completed steps 1 and 2. During step 3, a new source appears that changes a key figure used in steps 3 and 5; step 4 depends only on step 2. Write the replan decision: affected steps, stable prefix, new step order, and the change note. Then state one condition under which you would ask the user instead of patching.

Hint: keep steps whose inputs are unchanged, order the rest around the new figure, and escalate if an approved number changes.

Summary

  • Replanning should be triggered by observable conditions with declared severity and thresholds.
  • A replanning loop detects, scopes, decides, preserves, publishes a diff, and resumes.
  • Assumption registers turn hidden premises into testable items with confidence and expiry.
  • Ask concrete, batched questions with options and a default when a wrong guess is costly.
  • Represent unknowns explicitly and defer irreversible actions until they are resolved.
  • Bound adaptation with replan allowances, change thresholds, and cooldowns.
