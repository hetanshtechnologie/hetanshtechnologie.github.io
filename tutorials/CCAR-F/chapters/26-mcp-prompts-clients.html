26. MCP Prompts and Clients

Tools let a model act. Resources give it something to read. Prompts are the third primitive: a reusable, parameterized message sequence that a server publishes and a client can insert into a conversation. They are the right home for instructions that a team wants to own centrally — a revision checklist, an incident triage form, a standard way to summarize a document — without asking every user to remember the exact wording.

Why put prompts on the server

A prompt stored in a client's settings is a local convenience. A prompt stored on a server is a governed artifact. It can be updated once for every user, tested against a fixed set of inputs, and versioned alongside the tools it references. When the schema of a tool changes, the prompt that teaches a model to use that tool can ship in the same release.

The division of labor is worth stating plainly. A tool executes. A resource provides content. A prompt supplies a starting point for a conversation: a list of messages with roles and text, possibly with resource references attached. A prompt does not run code and does not guarantee a particular model output. It is a template the client chooses to use, usually after a user selects it by name.

Prompts are user-invoked by default. A client typically lists available prompts for a user to pick from, gathers the required arguments, and then inserts the resulting messages. Do not design a prompt as if it were an invisible system instruction that always applies; use server-side instructions or a project instruction file for that.

Designing a prompt template

A declaration has a name, a description, and an argument list. A prompts/get request supplies the name plus concrete argument values and returns messages. Each message has a role — usually user or assistant — and content that may be plain text, an image, or an embedded resource.

{
  "name": "review_release_notes",
  "description": "Produces a release-note review with a risk section.
  Use before publishing notes that mention an API change.",
  "arguments": [
    {"name": "version", "description": "Release tag, e.g. 2.4.0", "required": true},
    {"name": "audience", "description": "internal or external", "required": false}
  ]
}

// Client request
{"method": "prompts/get", "params": {
  "name": "review_release_notes",
  "arguments": {"version": "2.4.0", "audience": "external"}
}}

// Server response (abridged)
{"messages": [
  {"role": "user", "content": {"type": "text",
   "text": "Review the notes for version 2.4.0. Flag any claim
   that a field was added when it was actually renamed."}},
  {"role": "user", "content": {"type": "resource",
   "uri": "doc://releases/2.4.0/notes", "mimeType": "text/markdown"}}
]}

# Before rendering, the server validates argument values
if len(version) < 5 or len(version) > 24:
    raise InvalidParams("version must be 5-24 characters")
if audience != "internal" && audience != "external":
    raise InvalidParams("audience must be internal or external")

Keep returned text short. A prompt that embeds 4,000 words of boilerplate consumes context before the model sees the user's data. Prefer a resource reference: the message says read this document, and the client decides whether to inline it. Only the client knows the remaining context budget.

Write the description as a selection rule, not a label: "Reviews release notes for API claims; use when a version touches public interfaces." Avoid promising an outcome the server cannot control.

Arguments, defaults, and validation

Arguments are declared as strings in most implementations, even when they represent numbers or dates. The server therefore owns type coercion and validation. An argument named limit that arrives as "50" must be parsed, bounds-checked, and rejected with a clear message if it is outside the allowed range.

Argument kindRuleFailure mode if omitted
Required identifierMatch a documented patternPrompt silently targets the wrong record
Enum-like choiceValidate against a fixed setFree text changes the prompt's behavior
Numeric limitParse, then bound to 1–100Oversized context or empty result
Optional labelSubstitute a default explicitlyDifferent clients render different blanks

Every argument value should be treated as untrusted text. A user may paste a value containing instruction-like sentences, delimiters, or newlines. Place values inside clear delimiters in the rendered message, escape delimiter characters, and never concatenate an argument directly into a system-level instruction. Validate length as well as type: an audience value of 20,000 characters is almost always a mistake or an attempt to smuggle extra directions.

How clients discover what is available

Discovery starts with an initialization exchange. The client announces its protocol version and capabilities; the server replies with its own capabilities. A server that supports prompts advertises that fact, and the client then calls prompts/list. Lists may be paginated: a response can include a nextCursor, and the client must keep requesting pages until none remains. Treating the first page as the whole catalog is a common bug that makes prompts appear to vanish.

Clients should cache declarations for the life of a session but refresh them after a change notification. Capabilities are negotiated once; renegotiating mid-session is not part of the normal flow. If a client requests a method the server did not advertise, the expected result is a method-not-found error, not a silent empty list. A practical client keeps three separate caches — tools, resources, and prompts — because they change at different rates.

Name collisions are inevitable when several servers are connected. A tool or prompt called search on two servers is ambiguous from the user's perspective. Prefix declarations with the server alias during registration, keep the original name in the request sent to that server, and display both in any selection UI. The mapping belongs in the client, not in the server's public name.

Connecting to servers

Local servers are usually launched as child processes with a command, arguments, and environment variables. Remote servers are addressed by URL with headers for authentication. Both forms end up as connection entries that the client reads at startup.

{
  "mcpServers": {
    "docs-local": {
      "command": "python",
      "args": ["-m", "docs_server", "--root", "/srv/handbook"],
      "env": {"DOCS_INDEX": "production", "LOG_LEVEL": "warn"}
    },
    "tickets-remote": {
      "url": "https://mcp.example.internal/tickets",
      "headers": {"Authorization": "Bearer ${TICKETS_TOKEN}"},
      "timeoutMs": 30000
    }
  }
}

Keep credentials out of configuration files committed to a repository. Reference environment variables or a secret store, and rotate tokens without editing the file. Set an explicit connection timeout — 30 seconds is a reasonable default for a remote server — and fail fast at startup if a required variable is missing. A server that starts with an empty token and reports "no results" is far harder to diagnose than one that refuses to start.

Connection lifecycle deserves a little discipline. Start the process, wait for readiness, exchange initialization, load declarations, and only then expose the server's capabilities to the user. On shutdown, close the transport and reap the child process. A leaked child process holds file descriptors and ports, so repeated restarts of a client can exhaust resources by the end of a day.

Error handling across the boundary

Two error channels coexist and should not be confused. Protocol-level failures arrive as JSON-RPC error objects with numeric codes: -32602 for invalid parameters, -32601 for an unknown method, -32603 for an internal error. Business-level failures from a tool are normally returned inside the result as a tool error, because the request itself was well formed and the model needs to see the failure text.

SituationChannelClient response
Missing required argument-32602 invalid paramsAsk the user for that value
Server process exitedTransport errorReport offline; do not retry blindly
Tool found no matching recordTool error in resultLet the model explain or broaden the query
Request exceeded deadlineTransport timeoutRetry once if the call is read-only

Retry policy follows the same read-versus-action boundary used for tool design. Retry a read after a timeout or a transient transport error, with a small backoff and a cap of two attempts. Never automatically retry a mutation unless it carries an idempotency key, because the first attempt may have succeeded and the acknowledgement was lost. Surface the raw error code in logs but translate it into plain language for the user: "the ticket server is unavailable" is more useful than a stack trace.

A tool error should not be escalated to a protocol error simply to make it look important. Doing so hides the failure from the model, which then cannot adapt its next step. Keep the error in the channel the receiving layer can act on.

Summary

  • Prompts are server-owned, parameterized message templates that users choose to insert into a conversation.
  • A declaration lists the name, description, and arguments; prompts/get returns the rendered messages.
  • Servers must coerce and validate arguments because most arrive as strings.
  • Discovery is capability-based and paginated; keep separate caches for tools, resources, and prompts.
  • Launch local servers as managed child processes and address remote servers by URL with secret-backed headers.
  • Protocol errors and tool errors are different channels; only idempotent reads are safe to retry automatically.
