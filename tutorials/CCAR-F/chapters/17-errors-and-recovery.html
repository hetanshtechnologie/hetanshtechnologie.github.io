17. Error Classes, Detection, and Recovery

An agent that never fails is an agent that never does anything interesting. Every useful action crosses a boundary — a network, a database, a file system, a permission check — where the world can say no. The design question is not whether failures will happen, but whether the system notices them quickly and responds in a way that preserves trust. This chapter builds a vocabulary for failures and a process for recovery.

Three Sources of Failure

It helps to sort failures by who is responsible, because the appropriate response differs for each class. The first class is a tool error: the action itself was well formed, but the thing that executed it rejected or could not complete it. An API returns a rate-limit code, a query times out, a file is locked, or an authenticated session has expired. The request was reasonable; the environment refused it.

The second class is a reasoning error. Here the machinery worked exactly as specified — the tool ran, the arguments validated, a result came back — but the choice was wrong. The agent queried yesterday's partition when today's was needed, called the read-only lookup when a write was required, or declared the task complete after inspecting only one of three required sources. These are not crashes. They are correct executions of an incorrect plan.

The third class is an environment error — a failure of the execution context rather than of any action. The process runs out of memory, the context window fills before the answer is assembled, a mount disappears, or a service silently returns stale data. These are the most dangerous errors because they look like step-level success while corrupting the outcome.

ClassTypical signalFirst responseBad response
ToolHTTP 429/5xx, timeout, exception payloadClassify, then retry or switch providerReplay identical request forever
ReasoningWrong tool, wrong arguments, unsupported claimRe-plan with the new observationRetry the same call with the same arguments
EnvironmentOOM, context exhaustion, missing mountShed load, trim context, checkpoint, escalateAssume a clean result because no tool failed

The most common recovery mistake is applying the tool-error playbook to a reasoning error: resend the same call, get the same unhelpful answer, burn budget. A wrong question retried ten times is still the wrong question.

Naming matters less than attribution. You do not need to agree on a taxonomy with your team. You do need the agent to answer, after each anomaly, "was the fault in the action, in the plan, or in the stage?" Recovery starts with an honest attribution.

Signals That Reveal a Failure

Explicit signals are the easy ones: non-success status codes, exception objects, validation errors, and timeouts. A well-behaved tool returns these in a structured form so that the calling agent can inspect a field such as retryable instead of parsing prose. But many failures are silent, and detecting them requires watching the shape of the trajectory rather than a single step.

  • Repetition. The same tool called three times with identical arguments usually means the agent did not incorporate the result, or the result was ambiguous.
  • No progress. Ten steps pass, the scratchpad grows, but no new fact enters the working set. Measure progress by newly established facts, not by token count.
  • Budget drift. A step that normally consumes two calls consumes twenty; cost spikes often precede visible failure.
  • Claim/evidence mismatch. The summary asserts a number that never appeared in any tool output — a reasoning failure with a confident surface.
  • Context pressure. As the window fills, earlier constraints are displaced and the agent violates rules it obeyed at step one.

Practical systems combine in-step checks with an outer watchdog. The in-step check validates each observation before admitting it to memory. The watchdog watches aggregate properties — elapsed time, cumulative spend, steps since the last verified fact — and can stop a spiralling run even when no step reported an error.

Absence of an error is not evidence of success. A tool that returns an empty list is not the same as a tool that found nothing; it may be a tool that queried the wrong tenant. Require tools to distinguish "no matching records" from "query not executed" in their payloads.

The Retry-or-Abort Decision

Once an anomaly is detected, the first branch is whether to try again. Use three questions: is the cause transient, is the action safe to repeat, and is there enough budget left for another attempt? Only when all three answers are yes does a retry make sense.

SituationRetry?Reason
HTTP 429 rate limit, read-only callYes, with backoffTransient, side-effect free
HTTP 400 invalid argumentNo, repair arguments firstDeterministic; identical retry cannot help
HTTP 401 expired credentialNo, refresh then retryState must change before repetition works
Payment submitted, response lostNo blind retryNon-idempotent; use an idempotency key
Wrong tool selectedNo, re-planReasoning error, not execution error
Context window exhaustedNo, compact or restartRetrying reproduces the overflow

When you do retry, use bounded exponential backoff with jitter: increase the delay after each failure, add randomness to avoid synchronising parallel workers, and cap attempts at three. Log each retry with its attempt number and classification. An unbounded retry loop is not resilience; it is an expensive way to prove the service is down.

Write the retry rule in the tool contract, not in the prompt. If the tool returns {retryable: true, retry_after_ms: 800}, the agent can follow a deterministic policy instead of improvising one from the prose of an error message.

Fallback Chains

When the primary path cannot deliver, a fallback chain offers the next-best option. The chain should be ordered by fidelity, not by convenience: try the closest substitute first, then progressively cheaper or less complete sources, and end with an explicit request for human input. A chain for a market-data question might be: live quote service, then delayed quote service, then the last cached snapshot with its timestamp, then a qualitative answer that names the data gap.

def answer_with_fallback(query, budget_ms=2500):
    chain = [
        ("live_quotes", lambda: call_live(query)),
        ("delayed_quotes", lambda: call_delayed(query)),
        ("cached_snapshot", lambda: read_cache(query, max_age_s=900)),
    ]
    for name, attempt in chain:
        if budget_ms <= 0:
            break
        result = attempt()
        if result is not None and result.freshness_ok:
            return {"value": result.value, "source": name,
                    "confidence": result.confidence}
        budget_ms -= result.elapsed_ms
    return {"value": None, "source": "none",
            "needs_human": True, "reason": "all sources unavailable"}

Three details make this work. Every rung reports source and freshness so downstream code applies the right trust level. The chain has a shared time budget, or a slow failing source consumes everything before the cache is tried. Exhausting the chain is a legitimate outcome, not an exception to swallow: the caller must receive a clearly labelled "I could not determine this" result.

Graceful Degradation

Graceful degradation reduces the scope or precision of an answer instead of failing entirely. A documentation assistant whose search backend is down can still answer from its local index, provided it says the sources are partial. A code-review agent that cannot run tests can still report structural issues, provided it does not claim the change is verified.

The rule is that degraded output must be marked as degraded. An unlabelled partial answer is worse than no answer, because it invites the reader to act on false confidence. Attach a status field — complete, partial, or blocked — to the result envelope, and require downstream consumers to branch on it. In a multi-agent pipeline, that field travels with the handoff; a subagent must not strip the uncertainty marker when it writes its summary.

Degradation is a product decision as much as a technical one. Decide in advance which capabilities are essential and which are optional. If a feature cannot be safely offered without a given service, it should fail closed; if it can, it should fail open with a visible caveat.

Designing a Recovery Policy

A recovery policy answers the questions above before runtime. Keeping it outside the prompt makes it testable and reviewable:

retry:
  max_attempts: 3
  backoff_ms: [200, 400, 800]
  jitter: 0.25
  only_if: [retryable_flag, idempotent, budget_remaining]
escalate_after: 3_failed_steps_or_8000ms
fallbacks:
  - live_service
  - delayed_service
  - cached_900s
degraded_output_status: partial
human_review_if: [confidence < 0.6, any_write_attempt_failed]

Summary

  • Classify anomalies by source — tool, reasoning, or environment — before choosing a response; the same symptom can require opposite remedies.
  • Detect silent failures through trajectory signals such as repetition, stalled progress, budget drift, and claim/evidence mismatch.
  • Retry only transient, idempotent actions within a remaining budget, using bounded backoff with jitter and a recorded classification.
  • Order fallback chains by fidelity, give them a shared budget, and treat exhaustion as an explicit outcome.
  • Degrade gracefully only with visible labels; unmarked partial answers destroy downstream trust.
