44. Memory, Facts, and Trim Strategies

When context runs short, the tempting fix is "summarise the conversation." Summaries are convenient and lossy in exactly the ways that hurt: they keep the gist and drop the identifier. This chapter explains why that happens, how to separate durable facts from disposable narrative, and how to choose among the three practical trim operations — filter, summarise, and reference.

Why summaries lose facts

A summary is a generative compression, not a lossless encoding. The model decides what is salient, and salience correlates with narrative importance rather than with machine relevance. In a long ticket, the fact that the customer was polite across six messages feels salient; the order number buried in message two does not. The summary keeps the tone and loses the identifier.

Three specific failure patterns recur:

  • Identifier drift. Codes, amounts, dates, and proper names are the first details to be approximated or omitted. INV-2026-00417 becomes "the April invoice."
  • Confidence flattening. A user-stated fact and a model guess both become "the customer said...", erasing their different reliability.
  • Decision amnesia. The summary describes what was discussed but not what was decided, so later turns reopen settled questions.

The deeper issue is that a summary removes the evidence needed to verify itself. Once the raw turns are gone, no downstream component can check whether the summary is accurate. Treat summaries as a convenience for orientation, never as the sole record of truth.

Never let a summary be the only place a critical value exists. If a value will be used by a tool, a validator, or an audit log, store it as a structured field before any trimming occurs.

Persistent fact blocks

The antidote is to extract facts into a dedicated, structured block that is preserved verbatim across trims. A fact block is a list of atomic records, each with a key, a value, a source, a timestamp, and a confidence. Atomic means one fact per record — do not bundle a name, date, and amount into a single sentence.

At the start of each new context assembly, inject the fact block in full, then append the recent transcript. Because the block is small and stable, it survives summarisation of the surrounding conversation. A typical block for a support session might hold eight to fifteen records and cost only a few hundred tokens.

{
  "facts": [
    {"key": "order_id", "value": "ORD-77150", "source": "user",
     "turn": 2, "confidence": 1.0, "pinned": true},
    {"key": "delivery_date", "value": "2026-11-24", "source": "tool:orders",
     "turn": 5, "confidence": 0.99, "pinned": true},
    {"key": "refund_eligible", "value": "true", "source": "tool:policy",
     "turn": 6, "confidence": 0.9, "pinned": false},
    {"key": "preferred_channel", "value": "email", "source": "inferred",
     "turn": 4, "confidence": 0.55, "pinned": false}
  ],
  "guard": "confidence > 0.5 && turn < 20"
}

The pinned flag distinguishes facts that must never be trimmed from those that may be dropped under pressure. In the example, an identifier and a tool-confirmed date are pinned; an inferred channel preference is not. When a conflict arises, higher confidence and more recent turn win, but a pinned user-stated value overrides an inferred one regardless of recency.

A memory tool

Structured facts work best when the model can read and write them explicitly. Give the assistant a small memory tool with four operations — set, get, delete, and list — and require every persistent value to pass through it. The tool enforces the schema, so the model cannot write a free-form note where a typed value belongs.

OperationArgumentsGuardTypical failure
setkey, value, source, confidencekey in allowlist; value type checkedModel writes a guess as user-stated
getkeyreturns version and timestampStale read after a correction
deletekey, reasonpinned keys require approvalOrphaned dependent facts
listoptional prefixreturns at most 20 recordsBloat if used without a limit

The list limit matters more than it appears. An unrestricted list call can dump the entire memory into the context and undo your budgeting work. Return the highest-value records first, ordered by pinned status and confidence, and cap the response. Likewise, every set should invalidate dependent facts: changing a delivery date invalidates a previously computed "days until delivery."

Log memory writes as events, not overwrites. Keeping the last five values of a key lets you detect oscillation — a user correcting the same field three times often signals a misunderstanding, not three updates.

Tool-output bloat

Retrieval and tool calls are the main source of context growth. A single search tool that returns twenty full documents can add 40,000 tokens, most of which will never influence the answer. Worse, bulky outputs bury the few lines that do matter.

Fix this at the tool boundary, not in the prompt. Design tools to return compact, structured results with three zones: a status line, a small set of top results with identifiers, and an optional pointer to full content. For example, a search tool might return the five best passages at 300 tokens each plus a result-set id, rather than twenty documents at 2,000 tokens each. If the model needs more, it calls a fetch(result_id, offset) tool deliberately.

  1. Return the minimum fields needed for the current decision.
  2. Include stable identifiers so content can be re-fetched or cited later.
  3. Truncate long fields at the tool layer and report the original length.
  4. Escalate the truncation to the user only if the missing part could change the answer.

This pattern — a small default with an explicit expansion path — keeps average context low without sacrificing access. It also produces cleaner provenance, because every expanded item has an identifier that can be traced back to a source.

Filter, summarise, or reference

When trimming is unavoidable, you have three moves. The choice depends on whether the information might be needed again and whether exact wording matters.

StrategyWhat it doesUse whenRisk
FilterDrops whole items by ruleLow-value, replaceable content such as raw logsMay discard a rare critical item
SummariseCompresses content into proseNarrative context where gist sufficesLoses identifiers and confidence
ReferenceReplaces content with a pointerBulky but retrievable materialBroken pointer means silent loss

Prefer filtering first, because it is deterministic and auditable: "keep only the last eight turns" is a rule you can test. Use summarisation for narrative that no one will need verbatim, after extracting its facts into the fact block. Use references for anything large that lives elsewhere — a document id, a result-set handle, a URL — and make the pointer resolvable with a tool the model can actually call.

A robust trim pipeline applies them in that order: extract facts, filter obvious noise, summarise the remainder that is safe to compress, and replace everything still too large with a reference. Each stage logs what it removed, so a quality regression can be traced to a specific trim decision.

Treating memory as a product surface

Memory is not a hidden implementation detail; it shapes what the assistant can promise. If facts are pinned and sourced, the system can say "I have your order number and confirmed date." If content has been trimmed to references, it can say "I can pull the full contract again." If neither is true, honesty requires saying "I no longer have that detail." Designing the memory layer first, and the prompt second, lets you make those claims accurately — and gives the model a stable foundation that survives the inevitable pressure on context.

Summary

  • Summaries preserve narrative gist but lose identifiers, confidence, and decisions.
  • Extract atomic facts into a structured block with source, confidence, and pinned status.
  • Expose memory through a guarded tool with set, get, delete, and bounded list operations.
  • Compact tool outputs at the source and provide an explicit expansion path with stable ids.
  • Trim deterministically: extract facts, filter noise, summarise safe narrative, reference the rest.
