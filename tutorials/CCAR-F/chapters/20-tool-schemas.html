20. Input Schemas and Strict Validation

A tool description tells the model what a tool is for; its input schema tells the model what a valid request looks like. The schema is also the contract enforced at the boundary: anything that reaches the implementation has passed a structural check, which turns a large class of runtime surprises into predictable rejections. Good schemas are small, closed, and specific. This chapter covers how to design them and how strict validation changes the model's behaviour.

A Schema Is a Contract

Most tool interfaces accept a JSON object described with JSON Schema. The model reads that description and produces arguments; the runtime validates those arguments before calling the implementation. This split matters: the model is a probabilistic generator, but the validator is deterministic. A schema is the place where you convert "the model will probably send something sensible" into "only sensible values get through".

{
  "type": "object",
  "properties": {
    "customer_id": {"type": "string", "pattern": "^cus_[0-9]{8}$"},
    "days": {"type": "integer", "minimum": 1, "maximum": 90,
             "default": 30},
    "status": {"type": "string",
               "enum": ["open", "paid", "overdue"]}
  },
  "required": ["customer_id"],
  "additionalProperties": false
}

Every field in this example carries information. The pattern rejects guessed identifiers that do not match the real ID format. The range on days prevents an unbounded scan. The enum prevents the model from inventing a status like "maybe-paid". Setting additionalProperties to false prevents hallucinated fields from slipping through. The schema is doing design work, not merely documenting the API.

Design the schema before writing the handler. If you cannot express the valid call precisely in the schema, the tool's purpose is probably too broad — split it into two narrower tools.

Required, Optional, and Defaults

The required list is a statement of what the model must supply. Keep it short. Every required field is another chance for the model to fabricate a value or omit the field and trigger a repair cycle. Ask yourself for each field: can the implementation derive this from context, a stored setting, or a safe default? If yes, make it optional.

Optional fields are not free, either. A default such as 30 days silently changes the meaning of a request when the user said "recent" without a number. Defaults should be conservative and visible: prefer a smaller window over a larger one, and include the applied default in the tool's result so the agent can report it. A missing field, an explicit null, and an empty string are different states; collapse them only when the distinction genuinely does not matter.

A common anti-pattern is a schema with fifteen required fields, ten of which are internal flags the model cannot possibly know. Move those into server-side configuration. Another is a single "options" object with no constraints, which hides the actual contract from both the model and the validator.

Enums and Closed Vocabularies

Free-text string fields are the largest source of invalid tool arguments. An enum converts an open-ended guess into a choice from a small set. Use enums for statuses, sort orders, formats, regions, and operation modes — anywhere the implementation branches on a known value.

Enum values should be short, stable machine tokens; human explanation belongs in the field description. A value such as last_30_days is better than recent, whose meaning drifts. If the user's vocabulary differs from the tool's — they say "urgent" while the enum says high — state the mapping in the tool description so the model can translate.

Closed vocabularies do create a maintenance obligation. Adding a value changes the contract, so clients and tests must be updated together. That is a healthy constraint: it forces an explicit decision about whether a new category is real. If the set is genuinely open, provide a documented escape hatch such as an other enum value plus a separate notes field, rather than allowing arbitrary strings.

Do not use an enum to express a permission boundary. A model can select any value in the enum; authorization must be checked server-side. Enums prevent typos, not misuse.

Constraints That Prevent Bad Calls

Beyond types and enums, JSON Schema offers constraints that encode operational limits. Each one prevents a specific failure mode before the handler runs.

Use constraints that a human could justify in one sentence. A pattern that encodes a 40-character internal format may be accurate but opaque; if the model cannot satisfy it from available information, validation failures will rise. Prefer a simple pattern plus a clear description over an exotic regular expression.

Strict Mode and Additional Properties

Strict validation means the runtime rejects anything that does not exactly match the declared shape: unknown fields, missing required fields, wrong types, and values outside constraints. In some APIs, strict mode also requires every property to appear in the required list, with optionality expressed by allowing null as a type. That convention makes the model choose explicitly for every field rather than silently omitting one.

The practical benefit is a sharp drop in "almost valid" calls that fail deep inside a handler. The cost is more visible failures when the schema and the user's request are misaligned. That is a good trade: a rejection at the boundary produces a clear error the agent can repair, while a subtle mismatch inside the handler produces wrong data.

def validate_strict(args, schema):
    errors = []
    for key in args:
        if key not in schema["properties"]:
            errors.append("unknown_field:" + key)
    for key in schema.get("required", []):
        if key not in args:
            errors.append("missing_required:" + key)
    if len(errors) > 0:
        return None, errors
    return args, []

When a strict call is rejected, return the list of offending field names to the model together with the expected shape. Generic messages such as "invalid arguments" force the model to guess; specific messages such as "missing_required: customer_id; unknown_field: cust_id" make repair deterministic.

Examples as Anchors

Schemas describe what is allowed; examples show what is typical. A single valid argument object in the tool description can reduce errors more than another paragraph of prose, especially for nested structures and enum translations. Include one example for a common case and, when a field is tricky, one for the edge case.

Keep examples consistent with the schema — validators and tests should check them. A stale example is worse than none, because the model will imitate it confidently. Avoid examples that embed placeholder values which look real; use obvious dummy values such as cus_00000001 so accidental leakage is visible in logs.

Summary

  • A schema converts probable model behaviour into a deterministic boundary check before the handler runs.
  • Keep required fields few, defaults conservative and visible, and distinguish absent from explicit null when it matters.
  • Use enums and closed vocabularies for branch points; enforce permissions server-side, not through enum values.
  • Ranges, lengths, patterns, item counts, and closed objects each prevent a concrete class of bad calls.
  • Strict validation plus specific error messages and fresh examples produces reliable, repairable tool calls.
