43. The Context Window

The context window is the total amount of text a model can consider in one call. It is simultaneously a memory limit, a budget line, a latency knob, and a quality risk. Architects who treat it as "a big number that is always enough" discover the truth during an incident: the retrieved documents, the system prompt, the tool schemas, and the chat history all compete for the same finite space. This chapter makes that competition explicit and gives you a budgeting method.

Tokens, limits, and what actually counts

Models measure context in tokens, not characters. In English, a token is often a word or part of a word; a useful planning approximation is that 100 tokens are roughly 75 words, or that one token averages about four characters. Code, identifiers, and non-Latin scripts can be far denser. Never size a prompt by character count alone.

A modern long-context model may advertise a window in the hundreds of thousands of tokens. That number is a hard ceiling, not a recommended operating point. Several things consume it in every request:

  • The system instruction and any persistent rules — often 300 to 2,000 tokens.
  • Tool definitions. Fifteen tools with detailed schemas can cost 3,000 tokens before any user input arrives.
  • Conversation history, which grows each turn.
  • Retrieved documents, which are usually the largest and most variable block.
  • Reserved output space. If you ask for a 2,000-token answer, that space must remain available.

Compute the usable input as window - reserved_output - fixed_overhead. On a 200,000-token window with 4,000 reserved for output and 5,000 of fixed overhead, you have about 191,000 tokens for history and evidence. That sounds generous until a retrieval step returns fifty full documents at 6,000 tokens each — 300,000 tokens, well beyond the ceiling. The failure is not a model defect; it is an unbudgeted retrieval call.

Count tokens with the tokenizer that matches your model, in CI, on representative inputs. A rough multiplier is fine for early design but not for a production guard. Assert that the final assembled prompt is below the budget before it is sent.

Cost, speed, and quality trade-offs

Long context is not free even when it fits. Three costs rise together with prompt length.

DimensionAs context growsWhy it matters
Input costIncreases roughly linearly with tokensA 50,000-token prompt billed repeatedly can dominate the budget
Latency to first tokenUsually increases, often superlinearlyUser-facing agents feel sluggish past a few thousand tokens
ReliabilityCan decrease after a pointRelevant detail may be overlooked amid distractors

Consider a retrieval assistant processing 10,000 queries a day. Shortening the average prompt from 12,000 to 4,000 tokens removes 8,000 tokens per query, or 80 million tokens a day. Even at a modest per-token price, that is a material line item. The same change typically reduces time to first token as well, so the user experience improves alongside the invoice.

Quality is subtler. Adding more relevant evidence helps up to a point; adding irrelevant evidence can hurt. The practical rule is to maximise signal density rather than total context. Five precise passages beat thirty loosely related ones. When in doubt, retrieve more candidates and then rerank down to a small set before assembly.

Attention dilution and position effects

A long prompt does not give every token equal influence. Two well-documented effects matter in practice. First, information at the very beginning and very end of a context tends to be recalled more reliably than information buried in the middle — sometimes called a lost-in-the-middle pattern. Second, as distractors accumulate, the model's effective attention to any single fact is diluted.

You can observe this without special tooling. Place a unique fact — say a confirmation code HT-7742 — in a document set of twenty, then vary its position: first, middle, last. Ask a question that requires the code. Repeat thirty times per position with a fresh surrounding text. A drop in accuracy for the middle position is the dilution effect made visible on your own data.

Design around it rather than fighting it:

  1. Put the task instruction and the acceptance criteria at the front.
  2. Put the single most important evidence passage near the end, immediately before the question.
  3. Include a short explicit index or recap of the evidence in the middle so key facts are repeated, not merely present once.
  4. Remove near-duplicate passages; repetition of similar text is a major source of dilution.
Do not assume a bigger window fixes reasoning. If an answer requires joining three facts, a window that contains all three but buries one in 100,000 tokens of noise can still fail. Retrieval precision and positioning beat raw capacity.

Budgeting a context window

Treat the window like memory in an embedded system: allocate fixed regions, cap the variable ones, and assert the total. A workable budget for a support agent might look like this.

WINDOW            = 128000   # model context limit
RESERVED_OUTPUT   =  4096    # room for the answer
FIXED_OVERHEAD    =  6000    # system + tool schemas
SAFETY_MARGIN     =  2048    # tokenizer drift
USABLE            = WINDOW - RESERVED_OUTPUT - FIXED_OVERHEAD - SAFETY_MARGIN
# USABLE = 115856 tokens for history + retrieved evidence

HISTORY_CAP       = 24000    # last 8 turns, summarised beyond that
EVIDENCE_CAP      = 88000    # at most 12 reranked passages, 7000 each
ASSERT (history + evidence) <= USABLE && passages <= 12

The assertion is the point. If it fails, the application must act — drop the oldest history, rerank more aggressively, or refuse and ask a narrower question. Silently truncating in the middle of a JSON tool schema is a classic cause of baffling production errors.

Set per-source caps too. A single retrieved document should rarely be allowed to consume more than a fixed share, say 10 percent of the evidence budget. Otherwise one verbose file crowds out all other evidence and the answer silently degrades to a single-source summary. Log the final composition of every prompt — counts by source, tokens per region — so you can diagnose quality regressions by what was in the window.

A decision table for context pressure

When the budget is tight, choose a response deliberately. The right move depends on which region is oversized and whether the missing information is essential.

SymptomLikely causeFirst actionLast resort
History alone exceeds capToo many turns retained verbatimSummarise turns older than the last eightStart a new session with a state handoff
Evidence exceeds capRetrieval returned too many documentsRerank and keep top passagesAsk the user to narrow the query

Making the budget a system property

Context budgeting belongs in infrastructure, not in individual prompts. Build a single assembly function that receives history, evidence, tool definitions, and reserved output, then enforces caps and logs the composition. Every caller uses it. When a new tool is added, the fixed overhead rises and the assembly function automatically reduces the evidence cap — with an alert if the reduction crosses a threshold. This centralisation is what turns context from a vague constraint into an engineering resource you can measure, forecast, and defend in a design review.

Summary

  • Context is measured in tokens and shared by instructions, tools, history, evidence, and reserved output.
  • Longer prompts cost more, increase latency, and can reduce reliability through dilution.
  • Middle-position facts are recalled less reliably; place key evidence at the edges and deduplicate.
  • Budget explicitly: reserve output, cap fixed overhead, and assert the assembled size before sending.
  • Handle context pressure with per-region strategies — summarise history, rerank evidence, load tools selectively.
