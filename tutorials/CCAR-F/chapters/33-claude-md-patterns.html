33. Scoped Instructions and Team Patterns

Why one global file stops scaling

A single CLAUDE.md at the repository root is an excellent starting point. It gives every session the same basics: how to run tests, which branch conventions apply, where the domain vocabulary lives. It begins to fail when the repository contains several subsystems with genuinely different rules. A monorepo may hold a Python data pipeline, a TypeScript web client, and a set of infrastructure definitions. Telling the model "always use pytest" is wrong for the client, and "never edit generated files" may be correct in one directory and irrelevant in another.

The failure is not loud. The model reads the global file, applies a rule from the wrong subsystem, and produces a plausible change that fails review. Because the file is always present, its instructions receive the same weight as a rule that actually belongs to the directory being edited. Scope is a way of restoring signal: the closer a rule is to the code it governs, the more likely it is to be applied at the right time and ignored everywhere else.

There are two mechanisms to combine. The first is a subdirectory instruction file, loaded when the session works inside that subtree. The second is a path-scoped rule, a standalone instruction with a glob pattern that decides when it applies. They solve different problems: directory files describe a place, while path rules describe a pattern that can occur in several places.

Subdirectory instruction files and load order

Place a file named CLAUDE.md inside a subdirectory to add guidance for that subtree. If the repository root has one and services/payments/ has another, a session editing services/payments/client.py sees both. The root file is the base layer; the nested file is an overlay. Both are in context, so a nested file should add local knowledge rather than repeat the entire root document.

Order matters when the two disagree. Treat the most specific file as the tie-breaker: a nested rule overrides a general one only inside its own subtree. Do not rely on the model to reconcile a direct contradiction. If the root says "use tabs" and a subdirectory says "use two spaces," you have created a test of interpretation rather than a rule. Write the nested file as an explicit exception — "In this directory only, use two spaces because the generated protobuf wrappers require it" — so the model can see that both statements are true.

Keep nested files short. A useful target is 20 to 60 lines. Anything longer is usually a sign that the content belongs in a repository document that the instruction file points to. The instruction file should answer three questions: what is unusual here, what must never be changed, and which command proves a change is correct.

Path-scoped rules with glob patterns

A path-scoped rule lives in a separate file and declares the paths where it applies. In the working layout used by this book, rules are kept under .claude/rules/ with YAML-style frontmatter at the top. A minimal example looks like this:

---
description: Apply strict validation to public API handlers
paths:
  - "src/api/**/*.ts"
  - "src/**/routes/*.ts"
---

# Public API handlers

Every handler must validate the request body before use.
Use the schema objects in src/schemas/; do not hand-roll checks.
Return a 400 response with an `errors` array for invalid input.
Never log raw request bodies — they may contain credentials.
Match <path> values relative to the repository root, not the shell cwd.

The glob patterns are evaluated against file paths the session touches. A rule marked src/api/**/*.ts is intended for TypeScript handlers under that tree, not for test fixtures or documentation. Wildcards are generous by default: ** crosses directory boundaries, while * normally stays within one segment. Write the narrowest pattern that covers the real cases, then add a second pattern if a separate directory needs the same rule.

Scope is a routing decision. A path-scoped rule that matches nothing is dead weight in the repository but harmless in context. A rule that matches too much is worse: it competes with correct local instructions on every unrelated file. Review glob patterns the way you would review a CI filter.

Exclusions and negative scope

Most rule systems let you describe what is out of scope as well as what is in scope. Use exclusions for generated code, vendored dependencies, snapshots, and historical directories. A typical mistake is to write a rule for src/**/*.py and then discover that it fires inside src/legacy/ where the code is frozen. An exclusion such as !src/legacy/** makes the intent explicit and survives later refactors better than an informal warning in prose.

Be careful with overlapping positive and negative patterns. When two rules both match a file and give conflicting guidance, the result depends on load order and specificity, which is exactly the kind of hidden behaviour you want to avoid. Prefer a single rule with a precise pattern over two broad rules that cancel each other out. If you need a true exception, state it in the same file:

---
paths:
  - "services/**/*.py"
  - "!services/legacy_v1/**"
---

Use structured logging from platform.log for all new service code.
The legacy_v1 tree is excluded because it targets Python 3.8 and
uses the older logging adapter; do not modernise it in feature PRs.
Failure mode: "the model ignored my rule." Before blaming the model, check whether the file was loaded at all. Verify the current working directory, confirm the pattern matches the exact path string, and look for a contradictory instruction in a higher-priority file. Three configuration faults explain most apparent disobedience.

Team patterns that survive review

Instructions are source code for behaviour, so give them the same lifecycle. Store shared rules in version control, require review for changes, and keep them small enough that a diff is meaningful. A practical ownership model has three layers:

  • Repository baseline — root file with build commands, branch policy, and vocabulary. Owned by the platform team.
  • Domain overlays — subdirectory files for each service or package. Owned by the team that merges into that subtree.
  • Cross-cutting rules — path-scoped files for concerns such as SQL safety, secret handling, or accessibility. Owned by whoever enforces the concern organisation-wide.

A useful convention is to include a "why" sentence in every non-obvious rule. "Do not use SELECT * in repository queries" is a constraint; adding "because the reporting tables contain a column with personal data that must be explicitly projected" turns it into knowledge the model can generalise from. When the model meets a similar table not covered by the rule, the reason helps it make the right call.

Another effective pattern is a pointer rather than a copy. If the organisation already maintains a style guide, the instruction file should name the document and the relevant section, not paste 400 lines into context. The model can read the referenced file on demand when it needs the detail. This is cheaper in tokens and avoids two sources of truth drifting apart.

Onboarding test: ask a new teammate to find the answer to "how do I add a migration?" using only the instruction files. If they cannot, the model probably cannot either. Treat that as a documentation bug, not a prompting problem.

Measuring whether scope works

Treat instruction scope as something you can test. Pick five representative tasks: one in each subsystem, one cross-cutting change, and one task that should trigger a safety rule. Run them with the rule set enabled and record whether the expected rule appeared in the model's reasoning and whether the resulting diff obeyed it. A score of four out of five usually reveals one pattern that is too broad or one exception that was never written down.

Also watch for context cost. Ten short rules that fire on every task can consume more attention than one long document that is read once. Consolidate rules that always apply together, and split only when the trigger conditions genuinely differ. The goal is not the maximum number of rules; it is the smallest set that reliably changes behaviour where it should.

Summary

  • Use root instructions for universal facts and subdirectory files for local exceptions.
  • Path-scoped rules route guidance by glob pattern; narrow patterns beat broad ones with disclaimers.
  • Exclusions protect generated, vendored, and frozen code from well-intentioned rules.
  • Treat instruction files as reviewed source code with clear ownership and a stated reason.
  • Verify scope with representative tasks and watch the token cost of always-on rules.
