19. How Models Select Tools

Before an agent can use a tool, it must decide that this tool, right now, is the right one. That decision is made from a compact description of the tool's purpose and parameters, not from reading its implementation. Tool selection is therefore a design problem in documentation: the words you publish about a tool are the routing instructions the model follows. This chapter explains what the model sees, what it weighs, and how to diagnose routes that go wrong.

Descriptions Are Routing Instructions

At decision time the model typically sees a tool's name, a short description, and a parameter schema. It does not see your intent, your architecture diagram, or the comment in the source file that explains the tool's real purpose. If the description says "handles data", the model has almost no information; if it says "reads the current subscription balance for one account; does not modify billing", the model has a precise route.

A good description answers four questions in two or three sentences: what operation is performed, on what object, under what conditions it is appropriate, and what it explicitly does not do. The negative clause is disproportionately valuable because it separates neighbouring tools. Compare a weak pair — search described as "search the system" and lookup described as "look things up" — with a strong pair: find_customer_orders described as "list order IDs for a customer in the last 90 days; use for discovery, not for full order details", and get_order_detail described as "return line items and payment status for one known order ID; requires an ID from find_customer_orders".

The second pair encodes a workflow. It tells the model that one tool produces the input the other consumes, and that using the detail tool with a guessed ID is inappropriate. Descriptions can therefore express preconditions and sequencing, not just capability. Keep them short enough to be read at a glance, but specific enough to rule out the wrong choice.

Write descriptions as if they were routing rules for a new colleague: verb, object, scope, and boundary. Avoid "utility", "helper", "various", and "general-purpose" — these words carry no routing signal.

Signals the Model Weighs

Tool selection is not a lookup of keywords; it is a judgement over several signals. Understanding the signals lets you strengthen the useful ones and remove misleading ones.

  • Name semantics. A name like archive_thread suggests a write even before the description is read. Names that sound similar invite confusion.
  • Description overlap with the request. Words shared between the user's task and the tool description raise the chance of selection, but superficial overlap can mislead — "invoice" appears in both billing and document tools.
  • Parameter affordance. If the user supplied a customer ID and one tool has a customer_id parameter while another needs a free-text query, the structured tool becomes more attractive.
  • Stated outcome. Descriptions that name the returned artefact — IDs, counts, a boolean, a summary — help the model match the tool to its next step.
  • Contextual precedent. Tools used successfully earlier in the same conversation, or shown in an example, gain and keep attention.
  • Catalog order and grouping. Order is a weak but real signal; when two tools are nearly indistinguishable, the earlier one often wins.

No single signal dominates. A poorly named tool can still be chosen on the strength of its description, and a well-described tool can be ignored when the required argument is missing from the conversation. This is why selection failures are rarely fixed by changing one word; they usually require aligning name, description, schema, and available context.

Where Ambiguity Creeps In

Ambiguity is not a property of language alone; it is a property of the catalog. The most common source is overlapping capability. Two tools that both "search customers" — one against the CRM and one against the data warehouse — force the model to guess which source the user meant. Unless the descriptions state freshness, authority, and cost, the choice is arbitrary.

A second source is generic naming. Tools called get_data, run, or process give the model nothing to discriminate on. A third is hidden preconditions: a tool requires an ID obtained from another tool, but its description does not say so, so the model calls it with a fabricated value. A fourth is multi-intent requests. "Find the failing orders and email the supplier" contains a discovery step and a communication step; a model that jumps straight to the communication action has skipped a necessary stage.

Finally, catalogs drift. A tool is deprecated, its scope narrows after a policy change, or a new tool is added with 90 percent overlapping purpose. The old description remains, so the model keeps routing to behaviour that no longer matches. Selection quality decays silently unless catalogs are reviewed on a schedule.

If two tools can satisfy the same request and nothing in their descriptions distinguishes them, the model will choose inconsistently. Inconsistency in logs is a catalog design defect, not a model defect.

Selection Heuristics

Given a choice, a reliable agent tends to follow a small set of heuristics. Encoding these in descriptions and instructions makes behaviour predictable.

HeuristicHow to express it
Specific before general"Use only for exact order IDs; for partial names use find_customer_orders"
Read before write"Requires an ID returned by a read tool; never guess identifiers"
Local before remote"Reads the checked-out repository; no network access"
Cheap before expensive"Cached values up to 5 minutes old; use before the live API"
Ask when truly tied"If both billing and shipping records match, ask which the user means"

These heuristics mirror good engineering instincts: gather evidence before acting, prefer reversible operations, and avoid unnecessary cost. When the model has no such guidance, it may choose the shortest path to a plausible answer rather than the safest path to a correct one.

Controlling Selection

There are four levers for controlling which tools get used, in increasing order of force. The first is description engineering — the cheapest lever and the first thing to try. The second is scoping: expose only the tools relevant to the current agent or task, so ambiguous neighbours are never candidates. The third is structured routing: a planner step that emits an explicit tool name, validated by a schema before execution. The fourth is API-level constraints, such as a parameter that restricts the candidate set to a single tool for a turn.

route = {"tool": "get_order_detail", "reason": "known_order_id",
         "preconditions_met": True}
if not route["preconditions_met"] or budget_ms < 100:
    ask_user("Which source should I use?")
else:
    execute(route["tool"], arguments)

Each lever has a cost. Aggressive scoping can remove a tool the agent unexpectedly needs. A separate planner adds a call and a failure mode. API-level constraints reduce flexibility and can trap the agent if the correct tool was excluded. Use the lightest lever that fixes the observed problem, and document why a stronger one was or was not adopted.

Never rely on a single instruction such as "always prefer tool A" to resolve a structural overlap. Either the descriptions distinguish the tools or they do not; an extra sentence in a system prompt is not a durable fix.

Analyzing Selection Failures

Treat selection as a measurable behaviour. Log, for each decision, the user request, the candidate tool names and descriptions visible at that moment, the tool chosen, the arguments, and whether the step advanced the task. Over a few hundred runs, patterns appear: a pair of tools confused more than ten percent of the time, a tool never selected despite being correct, or a particular phrasing that reliably triggers the wrong route.

Build a simple confusion table from those logs: rows are intended tools, columns are selected tools, cells are counts. Off-diagonal entries with high counts identify description pairs to rewrite or scopes to separate. After changing a description, replay the same set of requests and compare the table. This turns tool selection from guesswork into an engineering loop with a baseline and a result.

Summary

  • Tool descriptions are routing instructions; write verb, object, scope, precondition, and explicit boundaries.
  • Selection combines name semantics, description overlap, parameter affordance, returned artefacts, precedent, and ordering.
  • Ambiguity usually comes from catalog structure — overlapping tools, generic names, hidden preconditions, and drift.
  • Prefer specific over general, read over write, local over remote, and cheap over expensive; encode these in descriptions.
  • Use the lightest control that works, and track selection quality with a confusion table over logged decisions.
