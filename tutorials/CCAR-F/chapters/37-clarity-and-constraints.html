37. Clarity, Specificity, and Constraints

The measurable cost of ambiguity

Ambiguity is often treated as a stylistic flaw. It is better understood as a source of rework. Consider the instruction "summarize the report briefly." Four decisions are unspecified: which parts of the report matter, how brief is brief, what format the summary should take, and who the reader is. A model must guess all four. If one guess is wrong, a human revises the request; the second attempt may fix the length but change the format, producing another round trip.

You can measure this yourself with a small experiment. Take twelve real tasks from your backlog and write each one twice: once as you would normally phrase it, and once with a goal, inputs, constraints, output format, and a completion check. Run three trials of each version. Count how many revisions are needed before the output is usable. Teams commonly find that the specified version reduces three to five revision rounds to one or two, and — more importantly — makes failures consistent enough to diagnose.

Unspecified elementTypical guessLikely correction
AudienceGeneric technical reader"This is for executives; drop the implementation detail."
LengthA few paragraphs"Make it five lines."
FormatProse"Use a table with three columns."
ScopeWhole document"Only the sections after the findings heading."

Notice that none of these corrections requires more intelligence from the model. They require information that was already in the requester's head but never crossed the boundary into the prompt. Clarity is an act of transfer, not an act of persuasion.

Decomposing an instruction

A reliable prompt has six parts, not six paragraphs. They can be written as sections, bullets, or tagged blocks; the structure matters more than the notation. The parts are the goal, the context, the inputs, the constraints, the output specification, and the completion check.

  • Goal — one sentence describing the change in the world. "Produce a migration plan" is a goal; "think about migrations" is not.
  • Context — facts the model cannot infer: the reader, the deadline, the system's history, the reason this matters now.
  • Inputs — exactly which files, data, or prior messages are in scope, and which are explicitly out of scope.
  • Constraints — rules that must hold, separated into hard requirements and preferences.
  • Output specification — structure, length, field names, ordering, and vocabulary.
  • Completion check — an observable condition or command that decides whether the task is done.

Here is the same request written at two levels of specificity. The second version is longer by about sixty words and saves several rounds of correction:

WEAK: Make the nightly report better.

SPECIFIED:
Goal: Turn the nightly report into a decision-ready summary.
Input: rows from reports/nightly.csv. Ignore rows where status == "skipped".
Constraint: Do not modify the CSV. Keep the existing column order.
Output: a markdown table with exactly four columns:
        region | count | p95_ms | trend
Done: a reader can name the worst region in under 10 seconds, and
      `python tools/check_report.py && echo PASS` succeeds.

Rule for flags: mark trend as UP when p95_ms > 500 and the
previous value was lower; otherwise mark it FLAT or DOWN.
Never emit a value of <unknown>; write "no data" instead.

The escaped characters in that example reflect a practical concern: when a prompt contains shell operators or literal angle brackets, it must survive being stored in HTML, JSON, or a configuration file. Losing an && or a > silently changes the meaning of the completion check. Validate rendered prompts the same way you would validate any other configuration text.

Designing constraints that hold

Not all constraints are equal. A hard constraint is a condition that makes the result unacceptable if violated: "no new runtime dependencies," "do not touch generated files," "all amounts in cents." A preference is a direction that may be traded against a stronger goal: "prefer the existing helper," "keep functions short." Label them differently. When everything is phrased as "must," the model cannot tell which rules it may compromise when two of them collide.

Constraint formExampleStrengthFailure mode
Hard prohibitionNever write to dist/Strong, narrowBlocks legitimate work if over-broad
Allowed setUse only cents or millisStrong, testableNeeds maintenance as options grow
Positive instructionRead the schema before writing SQLModerateHard to verify automatically
PreferencePrefer existing utilitiesWeak by designTreated as mandatory by mistake
Source of truthFollow docs/money.mdStrong if document is currentStale referenced document

Prefer definitions over denials where possible. "Write amounts as integers in cents" gives the model a constructive rule; "do not use floating point for money" leaves the alternative unspecified. Keep the prohibition as well if the risk is high, but lead with the replacement behaviour. Between five and nine constraints is a useful working range for a single task; beyond that, group them by phase or move stable rules into instruction files.

State the priority explicitly when conflicts are foreseeable. A line such as "if a test would require changing a generated file, stop and report instead" resolves a collision before it happens. Without it, the model faces a genuine dilemma: satisfy the test or respect the boundary. Either choice can look like a mistake to the reviewer.

Copy the rule, not just the link. A source-of-truth reference is efficient only when the referenced document is authoritative and available. If a policy lives in a private wiki the model cannot read, include the few sentences that govern this task directly in the prompt.

Making completion measurable

"Done" should be observable by someone who did not write the prompt. Compare the two versions below:

  • Weak: "The code should be clean and the tests should look reasonable."
  • Strong: "All files pass ruff check; pytest -q reports zero failures; no diff touches src/generated/; the response lists changed files and the command output for each check."

The strong version does not require a human to interpret taste. It also separates product correctness from presentation: a task may produce correct code with a poor report, and those deserve different feedback. Where no command can verify the result, use a structural test instead — "each finding includes a file path, a line number, and one sentence of evidence" — which a reviewer can check in seconds.

Be careful with criteria that invite gaming. A rule such as "the response must be under 200 words" can be satisfied by deleting necessary caveats. Pair limits with content requirements: "under 200 words, and every risk must retain its evidence reference." Similarly, "all tests pass" is weak if the agent may skip or rewrite tests; add "without modifying files under tests/ unless the request explicitly allows it."

A diagnostic loop for failed outputs

When an output is wrong, resist rewriting the whole prompt. Identify which layer failed and repair only that layer. This keeps prompts stable and makes improvements cumulative.

SymptomMost likely layerRepair
Correct analysis, wrong shapeOutput specificationAdd field names and an example row
Confident but wrong factsInputs or contextProvide the source file or restrict the scope
Rule violatedConstraint designMake it hard, positive, and visible near the goal
Stopped too earlyCompletion checkName the artifact and the verifying command
Wandering into unrelated workScopeAdd an explicit out-of-scope list

Run two or three trials after each repair. A single success proves very little with a stochastic system; a single failure after four previous successes tells you more. Keep a short changelog of prompt revisions and their observed effect, especially for prompts used in automation. That record becomes the baseline for deciding whether a model upgrade or a prompt change is the right response to a regression.

Check your understanding

  1. Why is ambiguity best described as a source of rework rather than a style issue?
  2. Name the six parts of a well-decomposed instruction.
  3. Why should hard constraints and preferences be labelled differently?
  4. What is wrong with a completion check based only on word count or "clean code"?
  5. How would you repair a failure where the analysis is correct but the format is wrong?

Summary

  • Unspecified audience, scope, length, and format force the model to guess and the human to correct.
  • Write goals, context, inputs, constraints, output specifications, and completion checks explicitly.
  • Use hard constraints sparingly, define positive alternatives, and resolve foreseeable collisions.
  • Make "done" observable through commands or structural checks that do not depend on taste.
  • Diagnose failed outputs by layer and repair the smallest cause, then verify across several trials.
