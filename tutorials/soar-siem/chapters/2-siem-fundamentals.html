2. SIEM Fundamentals

Chapter 2

What is a SIEM?

SIEM stands for Security Information and Event Management. It combines two older disciplines into one platform:

  • SIM (Security Information Management): long-term storage, analysis, and reporting of security data — the "information" half.
  • SEM (Security Event Management): real-time monitoring, correlation, and alerting on security events — the "event" half.

A SIEM centralizes logs and telemetry from across the environment into one place, normalizes them into a common format, correlates them to spot suspicious activity, alerts analysts when something looks wrong, and provides search, dashboards, and reporting for investigation and compliance.

Core Components of a SIEM

Every SIEM, from open source to enterprise, shares the same conceptual pipeline:

ComponentFunction
Collector / ForwarderGathers logs and events from source systems (servers, firewalls, cloud, endpoints) and sends them to the SIEM
Ingestion / PipelineReceives data, parses raw formats, validates, and routes records to storage
Parser / NormalizerTranslates many different log formats into a single normalized schema so events can be compared
Storage / IndexPersists normalized events in a fast-searchable format (inverted index, data lake, or both)
Correlation EngineApplies rules to detect combinations and sequences of events that indicate an attack
Alerting EngineGenerates alerts when correlation rules fire; routes them to queues, email, or SOAR
Search & DashboardsLets analysts query the data and build visualizations for monitoring and investigation
ReportingProduces compliance and management reports (e.g., PCI DSS, ISO 27001, internal metrics)
Key Idea: A SIEM is fundamentally a centralized log analytics platform built for security. The value comes not from storing logs, but from normalizing them into a common schema so a single correlation rule can see an attack that spans many different systems.

The Evolution of SIEM

SIEM technology has evolved significantly since its origins in the late 1990s and early 2000s:

  • 2000s: First-generation SIEMs (e.g., ArcSight, QRadar) focused on log aggregation and compliance reporting. Rules were static and required heavy tuning.
  • 2010s: Big-data SIEMs brought scale (Elasticsearch-based), and SaaS offerings (Splunk Cloud, LogRhythm) reduced operational burden. Alert fatigue became a recognized problem.
  • 2020s: Cloud-native SIEMs (Microsoft Sentinel, Google Chronicle) arrived with on-demand scale, built-in UEBA, threat-intel integration, and deep automation hooks into SOAR and XDR. Detection-as-code and AI-assisted analysis became mainstream.

How a SIEM Detects Threats

SIEMs detect threats through several complementary mechanisms. Mature teams use all of them:

  • Signature / rule-based detection: Explicit rules ("if event type X and attribute Y then alert") written by detection engineers. Fast, precise, but only catches known patterns.
  • Correlation across sources: Rules that combine events from multiple systems ("failed login on VPN followed by successful login from a different country"). This is the unique value of a SIEM.
  • Anomaly / UEBA: Baseline "normal" user and entity behavior; alert on statistically significant deviations. Catches insider threats and compromised accounts.
  • Threat intelligence matching: Compare IOCs (IPs, domains, hashes) from external feeds against observed events.
  • ML / AI-assisted: Models that group similar alerts, rank risks, or detect novel patterns. Always paired with human validation.

What a SIEM Cannot Do Alone

Setting realistic expectations is critical for SOC design. A SIEM alone:

  • Cannot respond — it detects and alerts, but acting (blocking, quarantining, isolating) requires other tools such as SOAR, EDR, and firewalls.
  • Cannot see what it is not fed — if a system does not send logs, the SIEM is blind to it.
  • Cannot eliminate false positives — tuning and detection engineering are continuous work.
  • Cannot protect data it never receives or that is collected without context (e.g., no user/asset mapping).
Real-World Context: Gartner has tracked SIEM for decades and uses the term "SIEM" broadly enough that modern cloud-native products and XDR platforms blur the line. When evaluating, focus on the capabilities that matter to your SOC: data ingestion breadth, query speed, correlation quality, automation hooks, and total cost of ownership.

When Does an Organization Need a SIEM?

  • You have multiple log sources and cannot manually triage them.
  • You need to meet compliance requirements that mandate log monitoring (PCI DSS, HIPAA, SOC 2, ISO 27001).
  • You need evidence and timelines for incident investigations.
  • You want to detect attacks that span multiple systems.
  • You are building a SOC and need a central detection platform.
