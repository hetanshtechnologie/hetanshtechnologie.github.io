10. Integrating SIEM & SOAR

Chapter 10

The SIEM + SOAR Partnership

SIEM and SOAR are designed to work as a team. The SIEM is the eyes: it sees everything, normalizes it, and detects anomalies. The SOAR is the hands: it takes action, orchestrates other tools, and manages the response. The integration between them is where most of the operational value lives.

The Flow: SIEM collects → SIEM detects → SOAR orchestrates → SOAR responds → results feed back to SIEM for validation and tuning. This creates a closed loop: detection informs action, and action informs detection.

Data Flow: SIEM to SOAR

  1. Alert generation: a correlation rule fires in the SIEM.
  2. Alert delivery: the SIEM pushes the alert to the SOAR via API, webhook, or connector (or the SOAR polls the SIEM).
  3. Alert normalization: the SOAR maps SIEM alert fields to its own incident/artifact schema.
  4. Playbook execution: the appropriate playbook(s) trigger on the alert type.
  5. Action execution: the playbook calls EDR, firewall, intel, ITSM, email tools.
  6. Results feed-back: outcomes (verdicts, actions taken, timestamps) are written back to the SIEM or recorded in the case.

Bidirectional Integration

Mature integrations are bidirectional. Not only does the SIEM push alerts, the SOAR can:

  • Query the SIEM during playbooks to gather supporting evidence (raw logs, historical activity).
  • Write back annotations — verdicts, notes, and closure reasons that improve SIEM analytics.
  • Suppress or update alerts once automation has resolved them, preventing analyst double-work.
  • Sync severity between case and alert to keep both systems consistent.

Designing the Alert Schema

The interface between SIEM and SOAR is only as good as its schema. Agree on a minimum set of fields every alert must carry:

  • alert_id, rule name, rule id, severity, status
  • time generated (UTC)
  • affected entities: user(s), host(s), source/destination IP, file hashes
  • description and raw event reference (URL or query back-link)
  • tenant/scope (for multi-tenant SOCs)

Consistent fields let playbooks treat alerts uniformly. Inconsistent schemas force per-alert playbooks and become unmaintainable.

Avoiding the "Automation Stack Overflow"

Integration misconfigurations cause real failures:

  • Runaway loops: SOAR writes to SIEM → SIEM re-fires the rule → SOAR runs again → infinite loop. Add loop detection and idempotency keys.
  • Loss of audit trail: if actions happen in SOAR but the SIEM timeline doesn't reflect them, investigations become confusing. Write actions back.
  • Duplicate handling: if both SIEM and SOAR open cases, analysts see double work. Define a single source of truth (usually the SOAR case, with the SIEM alert linked).
  • Alert floods: a bad rule in the SIEM floods the SOAR, which faithfully automates the flood. Put rate limits and throttles at the ingestion layer.

Measuring the Integration: MTTA and MTTR

SIEM-to-SOAR automation is the main lever on the SOC's most-reported metrics:

Metric Hygiene: Define MTTA/MTTR consistently before measuring. Decide whether MTTR means "time to containment", "time to resolution", or "time to case closure" — and state it. Use automation dashboards to segment automated vs human-handled incidents; they behave very differently.

Reference Architecture: A Typical Integrated SOC Stack

  • Visibility: SIEM (primary) + EDR telemetry + cloud audit logs.
  • Action: SOAR orchestrating EDR, firewall, email gateway, identity provider, ITSM.
  • Context: threat-intel feeds (STIX/TAXII), asset inventory/CMDB, vulnerability data.
  • Case flow: SIEM alert → SOAR incident → analyst queue → ITSM ticket (for cross-team work) → closure → metrics.

Common Mistakes in SIEM/SOAR Integration

  • Buying both from different vendors and never wiring the connector correctly.
  • Pushing every alert (including noise) into SOAR — triage the SIEM first.
  • Not testing what happens when the SOAR is down (alerts should queue, not vanish).
  • Forgetting to map users/asset criticality, so automation can't assess impact.
  • No owner for the integration — configuration drift silently breaks flows.
Practice Task: Draw the SIEM→SOAR data flow for your organization (or a hypothetical one) on paper. Label every step with its latency, owner, and failure behavior. Then write the JSON schema for the "minimum viable alert" your SOAR will accept, and list which three playbooks should trigger on which alert types. Identify one place where the closed loop could cause an infinite loop, and design the safeguard.
