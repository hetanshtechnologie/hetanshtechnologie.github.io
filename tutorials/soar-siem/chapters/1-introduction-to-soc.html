1. Security Operations & the SOC

Chapter 1

What is Security Operations?

Security operations is the set of processes, people, and technologies an organization uses to detect, investigate, respond to, and recover from cyber threats. It is the operational side of cybersecurity — the "always-on" layer that watches the environment, reacts to suspicious activity, and reduces the impact of attacks. The place where security operations happen is called a Security Operations Center (SOC).

A SOC is not just a room full of monitors. It is a coordinated team of analysts, engineers, and managers supported by a technology stack — of which SIEM (for visibility) and SOAR (for action) are the two most important components. Understanding how a SOC works is the essential foundation for everything else in this book.

The Security Operations Lifecycle

Security operations follow a continuous cycle. Different frameworks describe it slightly differently, but the core loop is the same:

PhaseWhat HappensPrimary Tool
PrepareDefine policies, procedures, use cases, and playbooks; staff and train the teamDocumentation, SOAR playbooks
CollectGather logs and telemetry from across the environmentSIEM, log management, agents
DetectCorrelate data to identify suspicious activity and generate alertsSIEM correlation rules, detection engineering
TriagePrioritize alerts, filter noise, determine severity and impactSOAR, analyst queues, enrichment
InvestigateDig into the alert, gather evidence, scope the incidentSIEM search, threat intel, case management
RespondContain, eradicate, and recover; block IOCs, isolate hosts, restore systemsSOAR automation, EDR, firewalls
LearnPost-incident review, tune detections, update playbooksMetrics, reporting, continuous improvement
Key Idea: The SOC lifecycle is a loop, not a line. Every incident teaches the team something that improves preparation, detection, and response for the next one. Mature SOCs run this loop continuously and measure every stage.

SOC Team Structure and Roles

Modern SOCs are typically organized into tiers, which distribute work by complexity and experience. The most common model is a three-tier structure, often compared to a medical response system:

TierRoleTypical Responsibilities
Tier 1Alert Analyst / L1Monitor dashboards, triage alerts, determine false positives, escalate real threats, initial incident logging
Tier 2Incident Responder / L2Deep investigation, threat hunting, forensics, containment and remediation actions, root-cause analysis
Tier 3Threat Hunter / Engineer / L3Advanced malware analysis, proactive hunting, detection engineering, playbook development, tooling maintenance

Around these tiers sit other key roles: a SOC Manager (people, process, metrics), a Detection Engineer (writes correlation rules and use cases), a Threat Intelligence Analyst (brings external context), a Security Engineer (maintains the SIEM/SOAR platform), and in larger teams a Cyber Threat Hunter and Forensics/IR specialist.

Follow-the-Sun Operations

Because threats do not sleep, many SOCs run 24x7 using shifts, or a follow-the-sun model where SOCs in different time zones (e.g., APAC, EMEA, Americas) hand work to each other at the end of each shift. SOAR platforms support this by ensuring case status, notes, and automation state are preserved so any analyst can pick up an investigation.

Why SIEM and SOAR Exist

Organizations generate enormous volumes of data: billions of log lines per day from servers, endpoints, firewalls, cloud platforms, identity systems, and applications. No human can watch this data directly. Two problems emerge:

  • The visibility problem: Raw data is spread across dozens of tools and formats. You cannot see an attack if its signals are hidden inside unrelated log noise. SIEM solves this by centralizing, normalizing, and correlating data.
  • The action problem: Even when a security team detects a threat, responding takes time — time spent investigating, querying tools, and performing manual steps while the attacker keeps moving. SOAR solves this by orchestrating tools and automating response actions.
Analogy: A SIEM is like a city-wide surveillance system with a control room that fuses thousands of camera feeds into a single view and raises alarms when something is out of place. A SOAR is the dispatch system that automatically routes responders, runs pre-planned procedures, and records what was done so it can be repeated faster next time.

Key SOC Metrics and KPIs

Security operations must be measurable. The most important metrics, which will appear again in the SIEM and SOAR chapters, are:

MetricMeaningGoal
MTTDMean Time to Detect — time from when an attack starts to when it is detectedLower is better
MTTAMean Time to Acknowledge — time from alert creation to when an analyst starts working itLower is better
MTTRMean Time to Respond / Resolve — time from detection to containment or resolutionLower is better
Alert VolumeTotal alerts generated in a periodManageable, not overwhelming
False Positive RatePercentage of alerts that turn out to be benignBelow ~20-30% is realistic
Dwell TimeHow long an attacker is present before being removedDays, then hours, then minutes
Cases Opened / ClosedThroughput of investigationsConsistent, documented workload

SIEM automation and SOAR playbooks are the two biggest levers for improving MTTD, MTTA, and MTTR. A well-instrumented environment can take MTTR from hours or days down to minutes for fully automated, well-scoped playbooks.

SOC Maturity Models

Not every SOC is equal. The CMMI-style maturity progression used in security operations looks roughly like this:

  • Level 1 - Initial: Ad-hoc processes, no SIEM, alerts handled by whoever happens to see them.
  • Level 2 - Repeatable: A SIEM is in place, basic detection rules exist, incident processes are documented.
  • Level 3 - Defined: Standardized workflows, defined use cases, metrics are tracked, basic automation appears.
  • Level 4 - Managed: Detection engineering is systematic, SOAR automates repetitive work, KPIs drive improvement.
  • Level 5 - Optimizing: Continuous tuning, threat hunting is routine, automation handles most repetitive cases, the team focuses on hard problems.

Most organizations today sit somewhere between levels 2 and 3. The journey from 3 to 4 is precisely the journey of adopting SOAR and mature detection engineering — which is what this book teaches.

Case Study: A Day in a Modern SOC

Here is a realistic scenario that ties the concepts together — and previews how SIEM and SOAR fit in:

  • 08:00 — A user clicks a phishing link. The email gateway logs the event; the endpoint agent logs a download attempt.
  • 08:03 — The SIEM collects both logs, normalizes them, and a correlation rule fires: "Suspicious download after phishing link click". An alert is created.
  • 08:03 — The SOAR platform receives the alert, enriches the file hash against threat intel, checks whether the endpoint is business-critical, and quarantines the file automatically.
  • 08:05 — A Tier-1 analyst is assigned the case, reviews the automation summary, and confirms the response was correct.
  • 08:20 — The case is documented and closed. Metrics show MTTR of 17 minutes for this alert type.

Without SIEM and SOAR, this same scenario might take hours: a missed email log, a manual search for the file, a ticket passed between teams, and manual containment while the attacker continues.
