3. SIEM Architecture & Data Pipeline

Chapter 3

Anatomy of a SIEM Data Pipeline

The heart of any SIEM is its data pipeline: the series of stages that move raw logs from source systems into normalized, searchable, actionable events. Understanding each stage matters because most SIEM problems — missing data, slow searches, bad correlations, alert gaps — are actually pipeline problems.

StageDescriptionExample Technologies
1. Log generationApplications, OSes, network devices produce raw log recordssyslog, Windows Event Log, JSON APIs, cloud audit logs
2. CollectionAgents or forwarders pull or push logs to the SIEMWinlogbeat, Filebeat, Splunk Universal Forwarder, Azure Agent, Syslog-ng
3. TransportLogs travel over the network, often with encryption and bufferingTLS, TCP/UDP, AMQP, Kafka, HTTP ingestion APIs
4. Parse & normalizeRaw text/JSON is parsed into structured fields on a common schemaCEF, LEEF, ECS, KV format, Grok, regex rules
5. EnrichAdd context: geo-location, asset owner, user info, threat-intel tagsGeoIP, CMDB/asset DB, Active Directory, TI feeds
6. Index / storeNormalized events are indexed and stored for fast searchLucene/inverted index, columnar store, hot/warm/cold tiers
7. Correlate & alertRules process events in real time and emit alertsCorrelation engine, detection rules, alert rules
8. InvestigateAnalysts search, visualize, and pivot through the dataQuery language, dashboards, notebooks

Common Log Sources

A SIEM is only as good as the data you feed it. The most important sources, roughly in order of security value:

  • Identity & authentication: Active Directory/Entra ID, Okta, VPN, MFA — detect credential abuse, account lockouts, privilege changes.
  • Endpoints: Windows Event Logs (Security, Sysmon), EDR telemetry, Linux auditd — the primary host-level visibility.
  • Network: Firewalls, proxies, DNS, NetFlow — detect scanning, C2 beaconing, data exfiltration.
  • Servers & applications: Web servers (IIS, nginx), databases, application logs — detect web attacks and data access.
  • Cloud: AWS CloudTrail, Azure Activity Log, Google Cloud Audit Logs — cloud-native events, API abuse, IAM changes.
  • Email: Exchange/M365 message tracking, email gateway logs — phishing detection.
  • Antivirus / EDR / EPP: Malware detections, blocked threats — high-fidelity signals.
Design Principle: Map log sources to the use cases you want to detect before building ingestion. If you cannot articulate what attack you will detect with a log source, question why you are collecting it. This keeps cost and noise under control.

Normalization: Making Apples Comparable to Apples

Different systems record the same event differently. A firewall might call the source IP src, an endpoint source_ip, and a web server client.ip. Correlation is impossible without a common schema. Normalization solves this by mapping every vendor's fields into standard names and formats.

The two dominant standardization efforts are:

  • Common Event Format (CEF) — an ArcSight-era key=value format still widely used: CEF:0|Vendor|Product|Version|SignatureID|Name|Severity|src=10.0.0.5 dhost=www.corp.com
  • Elastic Common Schema (ECS) — a modern, open, JSON-based schema: {"source": {"ip": "10.0.0.5"}, "destination": {"domain": "www.corp.com"}}
  • Vendor-specific schemas such as the ASIM (Advanced SIEM Information Model) used by Microsoft Sentinel.
# Example: three vendors, one normalized event
# Firewall log:      src=10.0.0.5 dst=8.8.8.8 sport=52341 dport=443
# Endpoint log:      Source IP: 10.0.0.5, Destination: 8.8.8.8:443
# Proxy log:         {"client_ip":"10.0.0.5","host":"8.8.8.8","port":443}

# After normalization (ECS-like):
# {"source.ip":"10.0.0.5","destination.ip":"8.8.8.8","destination.port":443}

A single correlation rule can now run against all three sources because they share one schema. This is the single most important architectural decision in SIEM design.

Storage Architecture and Tiers

SIEM data grows fast, and storage cost dominates TCO. Mature deployments use tiered storage:

TierPurposeSpeedCost
HotRecent data (days) for fast interactive search and dashboardsRAM/SSD, millisecondsHighest
WarmRecent weeks-months for investigationFast diskMedium
Cold / Long-termMonths-years for compliance, hunting, and legal holdObject storage, minutesLowest

Cloud-native SIEMs (Sentinel, Chronicle) blur these tiers by using cheap object storage with infinite retention and querying directly from it when needed. On-prem SIEMs require capacity planning; running out of space silently drops logs — a common cause of detection gaps.

Deployment Models

  • On-premises: Full control, data residency guaranteed, but expensive to scale and operate.
  • SaaS / Cloud-native: No infrastructure, elastic scale, consumption-based pricing, rapid feature updates. Data leaves your premises unless configured otherwise.
  • Hybrid: On-prem collectors feed a cloud SIEM, or a split of on-prem and cloud. Common during migration and for data-residency requirements.
  • Open source: Elastic/Wazuh self-hosted — flexible and cheap, but the team owns uptime, tuning, and upgrades.
Decision Factors: Ingestion volume and cost, retention requirements, data residency, available skills, detection needs, and integration depth with existing cloud providers. Compute per-GB-per-day cost for your projected volume and retention before choosing.

Capacity Planning in Practice

A rough planning process:

  1. Estimate events per day per source (typical: 5,000–50,000 EPS for a mid-size enterprise).
  2. Estimate average event size after parsing (0.5–2 KB).
  3. Calculate storage = events/day × size × retention days × replication factor.
  4. Decide hot vs cold split and cost of each tier.
  5. Plan for spikes (e.g., ransomware events produce huge log bursts).
# Back-of-envelope example
EPS = 10_000                 # events per second average
daily_events = EPS * 86400   # ≈ 864M events/day
bytes_per_event = 1024
daily_gb = daily_events * bytes_per_event / 1024**3   # ≈ 805 GB/day
retention_days = 90
total_gb = daily_gb * retention_days                  # ≈ 72 TB
print(f"Need ~{total_gb/1000:.0f} TB for 90-day retention")
Common Pitfall: Under-provisioning collection bandwidth or storage. When the SIEM cannot keep up, it drops events silently, and the security team never knows what it missed. Alert on ingestion lag and storage utilization before they become incidents themselves.
Practice Task: List the top 10 log sources you would feed into a SIEM for a mid-size company (500 users, 50 servers, cloud-first). For each, name the collection method (agent/API/syslog), the estimated events-per-day, and one specific use case that source enables. Then calculate rough storage for a 180-day retention policy.
