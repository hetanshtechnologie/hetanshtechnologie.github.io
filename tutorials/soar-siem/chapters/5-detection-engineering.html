5. Detection Engineering for SIEM

Chapter 5

What is Detection Engineering?

Detection engineering is the discipline of designing, implementing, testing, and maintaining the detections that turn raw security data into meaningful alerts. It is the bridge between "we have a SIEM" and "we can reliably detect attacks." A detection engineer decides what to detect, writes the rule, tests it, tunes it, and decommissions it when it no longer earns its place.

From Threat Model to Use Case

Good detection work starts before any rule is written. The process:

  1. Know your threats: map the organization's crown-jewel assets and the realistic attack paths to them (MITRE ATT&CK is the de facto framework).
  2. Define a use case: a plain-language statement of what you want to detect and why. Example: "Detect credential dumping via LSASS access on Windows endpoints."
  3. Identify data: which log sources and fields provide visibility into this behavior.
  4. Write the detection: encode the use case as a rule, query, or analytics model.
  5. Test and validate: prove it fires on known-bad data and stays quiet on normal traffic.
  6. Deploy and tune: ship, monitor false positives, iterate.
  7. Retire: review rules periodically; delete what is ineffective.

MITRE ATT&CK as a Detection Backbone

MITRE ATT&CK is a free, globally accessible knowledge base of adversary tactics and techniques. Tactics are the "why" (Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, C&C, Exfiltration, Impact); techniques are the "how" (e.g., T1003.001 OS Credential Dumping: LSASS Memory).

Detection engineers use ATT&CK to:

  • Prioritize techniques that map to the organization's risk.
  • Reference documented behaviors, examples, and detections from the community.
  • Track coverage: which techniques you can detect, and which are gaps.
  • Design "detect the behavior, not the signature" — technique-focused rules survive malware family churn.
Analogy: Rules tied to a specific malware sample are like a wanted poster for one person. Rules tied to a technique (e.g., "LSASS access without a legitimate reason") are like a description of the behavior that catches anyone doing it — even new criminals.

Detection as Code

Modern detection engineering treats rules like software: versioned in git, peer-reviewed, tested in CI, and deployed through pipelines. Benefits: auditability, rollback, collaboration, and portability.

# Example pipeline (concept)
# 1. Write rule in version control        (e.g., detection rule YAML/JSON)
# 2. Pull request -> peer review
# 3. CI runs the rule against test data    (expected true positive + false positive sets)
# 4. Merge to main -> deploy to SIEM via API
# 5. Alert telemetry feeds a tuning dashboard

Detection-as-code is the reason Sigma rules exist.

Sigma: The Portable Detection Format

Sigma is an open-source, generic signature format for detection rules. A Sigma rule describes a detection in a tool-agnostic way and can be converted to many SIEM query languages (Splunk SPL, KQL, Lucene, QRadar AQL, etc.).

title: Suspicious LSASS Access
logsource:
  category: process_access
  product: windows
detection:
  selection:
    TargetImage|endswith: '\lsass.exe'
    SourceImage|startswith: 'C:\Windows\'
  filter:
    SourceImage|startswith:
      - 'C:\Windows\system32\'
      - 'C:\Windows\SysWOW64\'
      - 'C:\Program Files\'
  condition: selection and not filter
falsepositives:
  - Legitimate system administration tools
level: high

The SigmaHQ/sigma repository hosts thousands of community-maintained rules that can be converted and deployed to your platform — a huge head start for new detection programs.

Writing Good Detection Rules

Characteristics of a high-quality rule:

  • Specific but not brittle: matches the technique across variants.
  • Low false positives: has filters for known-good activity.
  • Performant: uses indexed fields, avoids wildcard scans where possible.
  • Documented: title, description, references, assumptions, tuning notes.
  • Tested: validated against both true-positive and false-positive datasets.
  • Versioned and reviewed: lives in source control with change history.

Alert Triage and Classification

When an alert fires, the first human interaction is triage — the rapid determination of whether an alert is a true positive, false positive, or needs escalation. This is where the SOC's triage quality determines overall effectiveness.

ClassificationMeaningTypical Action
False Positive (FP)Benign activity that matched the ruleClose, log feedback, tune rule
True Positive (TP)Real malicious or policy-violating activityEscalate / respond per playbook
Benign True PositiveReal but harmless (policy violation, testing)Close, possibly tune severity
Unknown / Needs enrichmentCannot determine with current dataEnrich, investigate further

Every triage outcome should feed back into rule tuning. SOCs with mature feedback loops steadily reduce false positive rate and surface the true positives faster.

Reducing False Positives Systematically

  1. Track FP rate per rule — identify your worst offenders.
  2. Add filters for known-good sources, applications, and users.
  3. Raise thresholds or extend correlation windows.
  4. Use asset criticality to prioritize, not just count matches.
  5. Split one noisy rule into targeted variants.
  6. Use SOAR to auto-verify and auto-close common FPs before humans see them.
  7. Retire rules whose detection value does not justify their noise.

Testing Detections

You cannot trust a rule you have not tested. Approaches include:

  • Attack simulation: deliberately perform the technique (e.g., mimikatz, atomic tests) and confirm the alert fires. Atomic Red Team automates this.
  • Baseline testing: run the rule against a period of known-good traffic to measure false positive baseline.
  • Historical replay: run the rule across past incidents to see if it would have caught them.
  • CI-driven tests: automated validation in a test SIEM as part of detection-as-code.

Metrics for the Detection Program

  • Coverage: % of MITRE techniques with at least one active detection.
  • False positive rate: FPs as a fraction of all alerts.
  • Precision: true positives / (true positives + false positives).
  • Detection time / MTTD: how quickly detections catch real incidents.
  • Mean time to tune: how long between first alert and a tuned rule.
  • Rule freshness: how many rules are stale/untested/unreviewed.
Career Note: Detection engineering is currently one of the highest-demand SOC skills. It combines security knowledge, data engineering, software practices (git/CI), and analytic writing. If you want to grow beyond Tier-1 triage, learn detection engineering.
Practice Task: Pick a MITRE ATT&CK technique that applies to your environment (e.g., T1078 Valid Accounts, or T1059.001 PowerShell). Write a Sigma-style rule for it, convert it to your SIEM's query language, test it by generating a sample event, and log the result. Document your false-positive filter decisions and what data sources were required.
