Chapter 3: Core Concepts

3.1 Anatomy of a Bicep File

Every Bicep file is a plain text file (usually .bicep) made of declarations. There are only a few kinds, and you can read them in any order:

targetScope = 'resourceGroup'        // 1. Where does this deploy?

param environment string              // 2. Inputs you supply at deploy time
param location string = resourceGroup().location

var fullName = 'app-${environment}'   // 3. Values computed from params

resource appService 'Microsoft.Web/sites@2022-03-01' = {  // 4. The infrastructure
  name: fullName
  location: location
  ...
}

output url string = 'https://${appService.properties.defaultHostName}'  // 5. Values to read back
Block order (convention, not a requirement): targetScope ─────────► parameters ─────────► variables ─────────► resources ─────────► outputs

3.2 targetScope

Declares where the deployment is executed. The default is resourceGroup if you omit it.

ScopeWhere resources landCommon use
resourceGroupA single resource groupMost day-to-day deployments
subscriptionThe whole subscriptionRBAC roles, policies, resource groups themselves
managementGroupA management groupPolicy sets, budgets across subscriptions
tenantThe Azure AD tenantTenant-level policies/billing

3.3 Parameters

Parameters are the inputs to your template — the things that vary between environments (names, SKUs, regions).

Parameter types

param env string                    // string
param replicaCount int              // integer
param enabled bool                  // boolean
param endpoints array               // array
param tags object                   // object
param adminPassword secureString    // string, hidden in logs
param secretObject secureObject     // object, hidden in logs

Decorators add rules

@description('Environment: dev, test, or prod.')
@allowed([ 'dev', 'test', 'prod' ])
param environment string

@minLength(3)
@maxLength(24)
@pattern('^[a-z0-9]+$')              // lowercase letters & numbers only
param storageAccountName string

@minValue(1)
@maxValue(10)
@default(3)
param replicaCount int = 3
Secure types: secureString/secureObject are masked in deployment history and logs. Use them for any secret — and prefer keyVaultReference for production secrets (data decoded only at deploy time).

Supplying parameter values

// main.parameters.json (sits next to main.bicep)
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "environment": { "value": "prod" },
    "replicaCount": { "value": 3 }
  }
}

Deploy with: az deployment group create --resource-group RG --template-file main.bicep --parameters main.parameters.json

3.4 Variables

Variables are computed within the template — they cannot be overridden at deploy time. Use them to keep expressions out of your resources:

param environment string

var namePrefix = 'mgmt'
var rgName = 'rg-${namePrefix}-${environment}'       // interpolation
var fullName = toLower('${namePrefix}${environment}')

var skuMap = {                                        // object of values
  dev:  'Standard_LRS'
  prod: 'Premium_LRS'
}
var chosenSku = skuMap[environment]                   // object access

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: fullName
  sku: { name: chosenSku }
  ...
}

Variables are evaluated lazily, so a variable used nowhere costs nothing.

3.5 Resources — the Declaration Syntax

This is the heart of Bicep:

resource <symbolicName> '<namespace>/<type>@<apiVersion>' = {
  name: <value>
  <property>: <value>
  ...
}
  • symbolicName — the name you use to reference the resource elsewhere in the file (e.g. stg.id, appService.properties.defaultHostName)
  • type@apiVersion — the resource provider type and pinned API version. VS Code auto-completes both from the correct values.
resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'mydatalake12345'
  location: resourceGroup().location
  kind: 'StorageV2'
  sku: { name: 'Standard_LRS' }
  properties: {
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
    supportsHttpsTrafficOnly: true
  }
}

Referencing resources

output stgId string = stg.id                       // ARM resource ID
output stgName string = stg.name                   // the deployed name
output stgEndpoint string = stg.properties.primaryEndpoints.blob   // nested property
Access syntax: top-level properties like id, name, type are accessed directly (stg.id); body properties live under .properties for most resource types.

Child resources (nested under a parent)

resource server 'Microsoft.Sql/servers@2023-08-01-preview' = {
  name: 'sqlserver-${environment}'
  location: location
  properties: { administratorLogin: adminUser }
}

resource serverDb 'Microsoft.Sql/servers/databases@2023-08-01-preview' = {
  parent: server                       // ties to parent, builds full name automatically
  name: 'myapp-db'
  sku: { name: 'Basic' }
}

(In the examples above adminUser and location would be parameters — shown inline for brevity.)

3.6 Modules

A module is a Bicep file used as a component. The entry point passes parameters in and reads outputs back — like a function call in a programming language.

// main.bicep
param environment string
param location string

module storageMod 'modules/storage.bicep' = {
  name: 'storage-module-${environment}'    // deployment name, must be unique-ish
  params: {
    environment: environment
    location: location
  }
}

output storagePrimaryEndpoint string = storageMod.outputs.primaryEndpoint
// modules/storage.bicep
param environment string
param location string

var name = toLower('st${environment}${uniqueString(resourceGroup().name)}')

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: name
  location: location
  kind: 'StorageV2'
  sku: { name: 'Standard_LRS' }
}

output primaryEndpoint string = stg.properties.primaryEndpoints.blob

Modules can also be pulled from a registry (published Bicep in ACR or the public mcr.microsoft.com/bicep registry):

module app 'br/public:app-service-docs:3.0.1' = { ... }

3.7 Outputs

Outputs surface values after a deployment — useful for chaining modules together and for consuming values in scripts and pipelines.

output webUrl string = 'https://${webSite.properties.defaultHostName}'
output dbConnectionRaw string = 'Server=tcp:${server.name}.database.windows.net,1433;Database=${db.name};'
output rgName string = resourceGroup().name

Read outputs afterwards from the CLI:

az deployment group show -g myrg -n mydeployment --query properties.outputs

3.8 Built-in Functions (a useful subset)

resourceGroup().location        // get resource group info at deploy time
reference(resourceId(...))      // read live values from existing resources
uniqueString(arg1, arg2)        // deterministic short hash → for unique names
concat('a', 'b')                // concatenation (or use ${} interpolation)
format('{0}-{1}', a, b)         // printf-style formatting
toLower() / toUpper()           // string casing for names
if(condition, trueVal, falseVal)// inline conditional
array / length() / first()      // array helpers
empty() / contains()            // string/array checks
uniqueString is the standard trick for globally unique names: 'st${env}${uniqueString(subscription().subscriptionId, resourceGroup().name)}' produces the same name on every run (idempotent) but different across subscriptions.
Summary & Checklist:
  • Files are built from five declaration kinds: targetScope, param, var, resource, output, plus module
  • Parameters are deploy-time inputs; variables are internally computed
  • Resource syntax: resource name 'type@apiVersion' = { ... }
  • Reference resources by their symbolic name: stg.id, stg.properties...
  • Modules reuse whole Bicep files; outputs let modules hand values to each other
  • Use decorators (@allowed, @minLength, @pattern...) for input validation
