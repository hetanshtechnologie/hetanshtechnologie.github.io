Chapter 4: Hands-On Examples

This chapter is three practical exercises. Complete them in order — each builds on the last. You need the Azure CLI and Bicep from Chapter 2, plus any resource group:

az group create --name rg-bicep-demo --location eastus

4.1 Exercise 1 — Deploy a Simple Storage Account

Step 1: Write storage.bicep

targetScope = 'resourceGroup'

param storageAccountName string
param location string = resourceGroup().location

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageAccountName
  location: location
  kind: 'StorageV2'
  sku: {
    name: 'Standard_LRS'
  }
  properties: {
    minimumTlsVersion: 'TLS1_2'
    supportsHttpsTrafficOnly: true
    allowBlobPublicAccess: false
  }
}

output storageId string = stg.id
output blobEndpoint string = stg.properties.primaryEndpoints.blob

Step 2: Validate locally

bicep build storage.bicep        # writes storage.json; any error stops here
bicep lint storage.bicep          # check style + correctness rules

Step 3: Preview

az deployment group what-if \
  --resource-group rg-bicep-demo \
  --template-file storage.bicep \
  --parameters storageAccountName=demoStore1234

Output shows exactly what will be created ("+ Microsoft.Storage/storageAccounts") before anything runs.

Step 4: Deploy

az deployment group create \
  --resource-group rg-bicep-demo \
  --template-file storage.bicep \
  --parameters storageAccountName=demoStore1234 \
  --name deploy-storage

# Read the outputs
az deployment group show -g rg-bicep-demo -n deploy-storage \
  --query properties.outputs
Idempotency: run the same create again — it succeeds and reports no changes. That's declarative deployments in action.

4.2 Exercise 2 — Parameters and Variables

Now make the template reusable across dev, test, and prod with a validation-guarded parameter and computed variables.

Step 1: storage.env.bicep

targetScope = 'resourceGroup'

@description('Environment to deploy. Controls SKU and names.')
@allowed([ 'dev', 'test', 'prod' ])
param environment string

@minLength(3)
@maxLength(18)
@pattern('^[a-z0-9]+$')
param namePrefix string

param location string = resourceGroup().location

// Compute the storage name: prefix + env + short unique hash
var storageName = '${namePrefix}${environment}${uniqueString(subscription().subscriptionId, resourceGroup().name)}'

// SKU + tier vary by environment
var skuMap = {
  dev:  { name: 'Standard_LRS', tier: 'Standard' }
  test: { name: 'Standard_GRS', tier: 'Standard' }
  prod: { name: 'Premium_LRS',  tier: 'Premium' }
}
var sku = skuMap[environment]

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageName
  location: location
  kind: 'StorageV2'
  sku: sku
  properties: {
    accessTier: 'Hot'
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
  }
  tags: {
    environment: environment
    managedBy: 'bicep'
    builtBy: 'bicep-book'
  }
}

output storageNameOut string = stg.name
output skuOut string = '${stg.sku.name}-${stg.sku.tier}'

Step 2: Per-environment parameter files

// storage.parameters.prod.json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "environment": { "value": "prod" },
    "namePrefix":  { "value": "corpdata" }
  }
}

Step 3: Validate the parameter rules work

# This should FAIL fast:
az deployment group create -g rg-bicep-demo --template-file storage.env.bicep \
  --parameters environment=dev namePrefix="BAD-NAMES!"

# This should succeed:
az deployment group create -g rg-bicep-demo --template-file storage.env.bicep \
  --parameters storage.env.parameters.prod.json --name deploy-storage-env

Note the difference: interesting SKUs and tags per environment, stable names, and deploy-time validation — all without branching logic in the file.

4.3 Exercise 3 — Create a Reusable Module

Modules let you write the resource once and reuse it from many entry points. We'll refactor Exercise 2 into a module, then call it from a main.bicep.

Step 1: modules/storage.bicep — the module itself

targetScope = 'resourceGroup'

@description('Environment to deploy. Controls SKU and names.')
@allowed([ 'dev', 'test', 'prod' ])
param environment string

@minLength(3)
@maxLength(18)
@pattern('^[a-z0-9]+$')
param namePrefix string

param location string = resourceGroup().location

var storageName = '${namePrefix}${environment}${uniqueString(subscription().subscriptionId, resourceGroup().name)}'

var skuMap = {
  dev:  { name: 'Standard_LRS', tier: 'Standard' }
  test: { name: 'Standard_GRS', tier: 'Standard' }
  prod: { name: 'Premium_LRS',  tier: 'Premium' }
}
var sku = skuMap[environment]

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageName
  location: location
  kind: 'StorageV2'
  sku: sku
  properties: {
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
  }
  tags: { environment: environment }
}

output storageNameOut string = stg.name
output storageEndpoint string = stg.properties.primaryEndpoints.blob

Step 2: main.bicep — thin entry point calling the module

targetScope = 'resourceGroup'

param environment string
param namePrefix string
param location string = resourceGroup().location

module storageDeploy 'modules/storage.bicep' = {
  name: 'storage-module-${environment}'
  params: {
    environment: environment
    namePrefix: namePrefix
    location: location
  }
}

// A second module could consume the first module's output here.
output storageEndpoint string = storageDeploy.outputs.storageEndpoint

Step 3: Deploy the module-based project

bicep build main.bicep                       # compiles main + inlined module
az deployment group what-if -g rg-bicep-demo --template-file main.bicep \
  --parameters environment=dev namePrefix=corpdata
az deployment group create -g rg-bicep-demo --template-file main.bicep \
  --parameters environment=dev namePrefix=corpdata --name main-deploy

Step 4: Verify it's the same resource

Because we kept the same name algorithm, this deployment updates the account from Exercise 2 in place — no duplicate storage account. That is the payoff of deterministic naming + idempotent deployments:

az storage account list -g rg-bicep-demo --query "[].name"     # still one account
Execution flow when main.bicep runs: ┌─────────────────────┐ │ main.bicep │ │ targetScope rg │ └──────────┬──────────┘ │ params: environment, namePrefix, location ▼ ┌──────────────────────────────┐ │ module storageDeploy │ │ modules/storage.bicep │ │ └─ resource stg (Storage) │──► creates/updates in rg-bicep-demo └──────────────────────────────┘ │ outputs.storageEndpoint ▼ reported back by main.bicep output
Module naming: module X 'path' = { name: '...' } — the name is the ARM deployment name inside the parent deployment. Make it environment-scoped to keep deployments distinct ('storage-module-${environment}') or allow nested deployments to auto-name by omitting... actually you must provide it; prefix it with the environment.
Checks:
  • Storage account deploys with minimal JSON-equivalent (Bicep) code
  • what-if shows changes before applying
  • Parameters + decorators enforce valid input at deploy time
  • Variables compute names/SKUs per environment
  • Module publishes cleanly and is consumed from main.bicep
  • Redeploys are idempotent — resource count stays flat
