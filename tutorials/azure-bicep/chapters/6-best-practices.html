Chapter 6: Best Practices

6.1 Naming Conventions

Consistent naming makes resource groups, deployments, and resource names predictable across environments and teams. Two rules dominate Azure naming: prefix groups by purpose and let Bicep assemble full names from a few parameters.

Named resource groups

# pattern: rg-<name>-<env>
rg-networking-dev
rg-app-prod
rg-data-test

Resource names via a shared convention

Use short type codes + environment + unique suffix. Pull the pieces from parameters/variables so a name never contains a hard-coded env:

@description('Application/workload short name, e.g. "inventory"')
@minLength(3) @maxLength(10) @pattern('^[a-z0-9]+$')
param appName string

@allowed(['dev','test','prod'])
param environment string

var uniqueSuffix = uniqueString(subscription().subscriptionId, resourceGroup().name)

// standard codes per resource family
var codes = {
  storageAccount:     'st'
  appServicePlan:     'asp'
  appServiceSite:     'app'
  sqlServer:          'sql'
  sqlDatabase:        'sqldb'
  keyVault:           'kv'
  vnet:               'vnet'
}

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: '${codes.storageAccount}${appName}${environment}${uniqueSuffix}'   // stinventoryprodabc123
  ...
}

Official guidance: storage account names ≤ 24 chars, lowercase alphanumeric; web app names ≤ 60 chars using <descriptor><project><env><sequence>.

Never recreate: once a name is live, changing the formula can rename and recreate resources in a later deploy. Bake naming into variables at the start and keep them stable.

6.2 Modularization

Modules are Bicep's reuse mechanism — but reuse done badly creates a mess. Follow these rules:

  • Single responsibility — one module = one logical component (a storage account with its access policy, or an app service with its plan). Not "everything for the whole platform in one file".
  • Small surface area — expose only parameters that genuinely vary. Fewer params = fewer translation bugs.
  • Package them — publish stable modules to a private registry (ACR) or the public registry, then reference by version: br:myregistry.azurecr.io/bicep/modules/storage:1.2.0.
  • Test modules standalone — give each module a minimal main.bicep that calls it, so you can deploy the module in isolation.
  • Libraries not frameworks — prefer many small focused modules over one giant mega-module with 30 switches.
# A tidy registry-style layout
modules/
├── storage/
│   ├── main.bicep          # the module
│   └── version.json
├── app-service/
│   ├── main.bicep
│   └── version.json
└── sql/
    ├── main.bicep
    └── version.json

deployment/
├── main.bicep              # thin: parameters + module calls + outputs
├── main.parameters.dev.json
└── main.parameters.prod.json
Over-modularization: a module per resource with one-line files adds indirection, slows the compiler, and hurts readability. Group tightly-coupled resources; split only what is genuinely reusable or independently deployable.

6.3 Version Control Integration

Treat .bicep files like application code — commit them, review them, tag them.

Repo layout

infra/
├── deployment/        # environment-facing entry points
│   ├── main.bicep
│   └── main.parameters.*.json
├── modules/           # reusable building blocks
├── tests/             # standalone smoke files per module
└── .github/workflows/deploy.yml   # or azure-pipelines.yml

Guardrails in CI/CD

# Every PR should prove the templates compile and lint clean:
bicep build --stdout deployment/main.bicep > /dev/null          # compile check
bicep lint deployment/main.bicep --diagnostics-level error       # fail on lint violations

# Clean up local build artifacts — never commit generated *.json
echo "deployment/**/*.json" >> .gitignore
Versioning tracked infra: pin Bicep CLI versions in CI containers (e.g. Azure/cli:latest runs az bicep install) and tag module releases so br: references are exact and auditable.

Pipeline deployment (GitHub Actions style)

# .github/workflows/deploy.yml (trimmed)
on:
  push:
    branches: [ main ]
    paths: [ 'infra/**' ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}
      - name: Bicep what-if
        run: |
          az deployment group what-if --resource-group rg-app-prod \
            --template-file infra/deployment/main.bicep \
            --parameters infra/deployment/main.parameters.prod.json
      - name: Bicep deploy
        run: |
          az deployment group create --resource-group rg-app-prod \
            --template-file infra/deployment/main.bicep \
            --parameters infra/deployment/main.parameters.prod.json

The what-if step gates destructive changes before the create step, and the deployment history in Azure becomes your change log.

6.4 More Loose Ends

  • Secrets: never secureString params in a file. Use Key Vault references or managed identity — never commit passwords to the repo.
  • Tags everything: owner, environment, cost-center, created-by for the FinOps folks.
  • Use existing keyword to reference resources you don't own in the same pipeline (e.g. shared vnets): resource existingVnet 'Microsoft.Network/virtualNetworks@2023-06-01' existing = { name: 'shared-vnet' }.
  • Keep API versions explicit — pin them, and let the extension help you upgrade on your schedule, not Azure's.
  • Run bicep format on save and agree on a team baseline via editorconfig.
Checks:
  • Names derive from env + appName + type-code + uniqueSuffix variables
  • Modules are single-purpose, small, versioned, and registry-hosted for reuse
  • Templates compile & lint in CI before any what-if/create
  • Secrets stay out of repos; identities or Key Vault handle secrets
  • Every resource carries ownership tags
  • Generated ARM JSON is not committed
