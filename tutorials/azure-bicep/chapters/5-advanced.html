Chapter 5: Advanced Features

Real infrastructure is rarely one resource. This chapter covers the three features that turn Bicep from "nicer ARM" into a real programming language for infrastructure: loops, conditions, and dependencies — plus how they combine when you chain modules.

5.1 Loops

Loop over an array with for to create a variable number of resources (or a resource-nested loop for sub-resources).

Loop over a parameter array

param vmNames array = [ 'web-01', 'web-02', 'web-03' ]

resource vmResources 'Microsoft.Compute/virtualMachines@2023-09-01' = [for vmName in vmNames: {
  name: vmName
  location: resourceGroup().location
  properties: {
    // ... VM properties
  }
}]

Loop with an index (range)

param instanceCount int = 3
resource nsgRules 'Microsoft.Network/networkSecurityGroups/securityRules@2023-06-01' = [for i in range(0, instanceCount): {
  name: 'simpleRule-${i}'
  properties: {
    priority: 100 + i
    protocol: 'Tcp'
    access: 'Allow'
    direction: 'Inbound'
  }
}]

Loop over an object dict and use the key

param envs object = {
  dev:  { sku: 'Standard' }
  prod: { sku: 'Premium' }
}
resource plans 'Microsoft.Web/serverfarms@2022-03-01' = [for (key, value) in envs: {
  name: 'plan-${key}'
  sku: { name: value.sku }
}]
Naming: loops with range() keep index-based names stable so reordering your array doesn't rename (and destroy/recreate) resources. Prefer arrays of names that never change position.

5.2 Conditions

Make a resource (or a whole module) optional with if.

Conditional resource

param enableDiagnostics bool = true

resource diagSettings 'Microsoft.Insights/diagnosticSettings@2021-05-01-preview' = if (enableDiagnostics) {
  name: 'diag-${storageName}'
  scope: storageAccount
  properties: {
    workspaceId: workspaceId
    metrics: []
    logs: []
  }
}

Conditional module

module network 'modules/vnet.bicep' = if (createVNet) {
  name: 'vnet-module'
  params: { ... }
}

Combine loop + condition

@description('Subnet names to create')
param subnetNames array = [ 'subnet-a', 'subnet-b', 'subnet-c' ]

param restricted bool = false   // only open 3389/RDP when needed

resource subnets 'Microsoft.Network/virtualNetworks/subnets@2023-06-01' = [for (name, i) in subnetNames: {
  name: name
  properties: {
    addressPrefix: '10.0.${i}.0/24'
    networkSecurityGroup: restricted ? nsg.id : null     // ternary in an expression
  }
}]

// only add a RDP allow-rule when restricted is true
resource rdpRule 'Microsoft.Network/networkSecurityGroups/securityRules@2023-06-01' = if (restricted) {
  name: 'rdp-in'
  properties: { ... }
}

You can also filter inside a loop with an inline condition — Bicep supports for-each-if style iterators where you project only matching items:

resource needsAudit 'Microsoft.Storage/storageAccounts@2023-01-01' = [for env in environmentList: if (env != 'dev') {
  name: 'stg-${env}'
}]
Watch out: conditional outputs need care. If the resource may not exist, guard reads with ? ... : null or access through if(exists(...)) patterns; the compiler will warn when an output reads a possibly-missing resource.

5.3 Resource Dependencies

Bicep usually figures out ordering implicitly — if resource B references resource A (via A.id, A.properties...), B is deployed after A automatically. Only use dependsOn when there is a runtime ordering requirement that the compiler cannot see (e.g. a script or app expecting a sibling resource to be ready).

Implicit dependency

resource server 'Microsoft.Sql/servers@2023-08-01-preview' = { ... }

// references server.id → Bicep knows: db depends on server
resource db 'Microsoft.Sql/servers/databases@2023-08-01-preview' = {
  parent: server
  name: 'catalog'
  sku: { name: 'S1' }
}

Explicit dependency (rarely needed)

resource vm 'Microsoft.Compute/virtualMachines@2023-09-01' = {
  name: 'web-vm'
  dependsOn: [ storageAccount ]        // compiler wouldn't see a reason otherwise
  ...
}
Best practice: prefer implicit references. dependsOn hides the relationship from the compiler — if you refactor, you can end up with stale dependencies, slower deploys, and unnecessary churn.

5.4 Linking Multiple Modules

Modules can consume each other's outputs, creating a clean data-flow pipeline in your main file:

main.bicep │ ├──► module storage ── outputs (id, endpoint) ──► ├──► module vnet ── outputs (subnetId) ──────────► └──► module app consumes storage.endpoint + vnet.subnetId 
// main.bicep
targetScope = 'resourceGroup'

param environment string
param location string

module storage 'modules/storage.bicep' = {
  name: 'stg-${environment}'
  params: { environment: environment, location: location }
}

module vnet 'modules/vnet.bicep' = {
  name: 'vnet-${environment}'
  params: { location: location, environment: environment }
}

module app 'modules/app-service.bicep' = {
  name: 'app-${environment}'
  params: {
    environment: environment
    location: location
    storageAccountName: storage.outputs.name        // ← module → module wiring
    subnetId: vnet.outputs.subnetId
  }
}

output appUrl string = app.outputs.url

Each module below has a matching output — e.g. modules/vnet.bicep ends with output subnetId string = sub.id. Bicep resolves the chain at compile time: storage and vnet deploy in parallel, and app waits for both.

Passing whole objects between modules

If two modules need identical tags or config, you can pass an object parameter instead of a dozen scalars:

// modules/base.tags → consumed by many modules
module webApp 'modules/app-service.bicep' = {
  name: 'web-${environment}'
  params: {
    commonTags: { env: environment, team: 'platform', managedBy: 'bicep' }
  }
}

Cycle-safe design

  • Keep module graphs acyclic: if A needs B's output and B needs A's output, Bicep fails to compile. Break the cycle by hoisting the shared value to the caller.
  • Two modules that only name each other's resources should receive the name/ID, not create it twice.
Checks:
  • for loops over arrays, ranges, and object key/value pairs
  • if conditions on resources and modules, plus loop-and-condition filters
  • Implicit dependencies via symbolic references; dependsOn only for runtime ordering
  • Module outputs feed downstream module parameters
  • Keep the module graph acyclic
