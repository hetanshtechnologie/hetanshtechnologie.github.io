Chapter 1: Introduction to Azure Bicep

1.1 What is Bicep?

Bicep is a domain-specific language (DSL) created by Microsoft for declaratively deploying Azure infrastructure. You describe the infrastructure you want — storage accounts, app services, databases, virtual networks — in a clean, human-readable language, and Bicep translates it into an Azure Resource Manager (ARM) template behind the scenes.

The key phrase is declarative: you state the end state (what must exist), and Azure Resource Manager figures out the steps to get there. Bicep is also idempotent — running the same deployment twice produces the same result instead of stacking duplicates on top of each other.

The Bicep → ARM pipeline

┌──────────┐ build ┌──────────────────┐ HTTP ┌────────────────────┐ │ main.bicep│ ──────────▶ │ main.json (ARM) │ ───────▶ │ Azure Resource │ │ (you) │ bicep build │ (generated) │ deploy │ Manager + APIs │ └──────────┘ └──────────────────┘ └────────────────────┘ ▲ │ └── decompile ─────────────────┘ (optional, one-time)

1.2 Why Bicep? (Why Not Just ARM JSON?)

Before Bicep, deploying infrastructure to Azure meant writing ARM templates — enormous JSON documents with deep nesting. Bicep was released in 2020 as a response to the pain points of ARM JSON. The most often-cited comparison: a 1,800-line ARM template usually compresses to roughly 200 lines of Bicep.

Optional: See the Difference

Here is a minimal storage account as an ARM template and then as Bicep:

// ARM Template (abridged — this is already ~40 lines without the wrapping)
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "storageAccountName": { "type": "string" },
    "location": { "type": "string", "defaultValue": "[resourceGroup().location]" }
  },
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "2023-01-01",
      "name": "[parameters('storageAccountName')]",
      "location": "[parameters('location')]",
      "sku": { "name": "Standard_LRS" },
      "kind": "StorageV2"
    }
  ]
}
// Bicep (18 lines, same resource)
@description('Globally unique storage account name; lowercase letters and numbers only.')
param storageAccountName string

param location string = resourceGroup().location

resource stg 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageAccountName
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}
Key idea: Bicep always compiles down to a standard ARM template, so nothing has to change on the Azure side. You keep full compatibility with deployments, CI/CD pipelines, and the Azure portal's automation blade.

Other benefits worth knowing

  • What-if deployments — preview changes (az deployment group what-if) before applying them, like a terraform plan for Azure.
  • Modular by design — split infra into reusable modules and publish them to a private or public registry.
  • Free and open source — no license cost, works with any CI/CD system that can call Azure CLI.
  • Future-proof — Bicep is the recommended direction from Microsoft for ARM authoring.

Rule of thumb: if your infrastructure is Azure-only, Bicep is typically the simplest and most aligned choice. If you manage AWS + Azure + GCP in one codebase, use Terraform.

1.4 How You'll Work With Bicep

Typical Bicep workflow: 1. Write/edit main.bicep (VS Code + Bicep extension) │ 2. Validate bicep build main.bicep (compile to JSON, catch errors) │ 3. Preview az deployment group what-if --template-file main.bicep │ 4. Deploy az deployment group create --template-file main.bicep │ 5. Manage az group delete --name myRG (tear down when done)

Later chapters drill into each of these steps in detail, so you can follow along with a live Azure subscription.

Summary & Checklist:
  • Bicep is a declarative DSL that compiles to ARM templates
  • It is far more concise, readable, and type-safe than ARM JSON
  • Native support for loops, conditions, variables, and modules
  • Idempotent deployments managed by Azure Resource Manager
  • Bicep is Azure-only; choose Terraform for multi-cloud
  • Core workflow: build → what-if → deploy → manage
