Chapter 7: Real-World Scenario — Scalable Web App on App Service + SQL Database

Everything in this book comes together now. We'll build a production-shaped deployment: a scalable App Service (Linux, Node.js runtime) backed by a SQL Server + SQL Database, with a firewall rule so the app can talk to the database, sensible SKUs per environment, secure parameters for the SQL admin, and useful outputs to hand down the pipeline.

7.1 Architecture

Internet │ (HTTPS, port 443) ▼ ┌───────────────────────────────┐ │ App Service Plan (Linux) │ sku: P1v2 (scalable, prod) │ ┌─────────────────────────┐ │ │ │ App Service (webapp) │ │ linuxFxVersion: NODE|18-lts │ │ siteConfig.appSettings │ │ WEBSITE_RUN_FROM_PACKAGE │ └───────────┬─────────────┘ │ └──────────────┼────────────────┘ │ SQL connection (port 1433, TLS) ▼ ┌───────────────────────────────┐ │ SQL Server (FQDN ...sql...) │ minimalTlsVersion 1.2 │ ┌───────────────────────────┐ │ │ │ SQL Database (S1 tier) │ │ the app's data store │ └───────────────────────────┘ │ └───────────────────────────────┘ Firewall: Allow Azure services (start/end 0.0.0.0)

Everything is deployed into one resource group. The entry point is a single main.bicep; for a bigger team you'd split the plan, app, and SQL into modules (Chapter 6).

7.2 The Full main.bicep

1. Parameters

All environment-specific values are parameters with validation decorators. SQL admin credentials are secure so they never appear in plain text in deployment history.

targetScope = 'resourceGroup'

@description('Application short name, used as the base for all resource names.')
@minLength(3)
@maxLength(12)
@pattern('^[a-z][a-z0-9]*$')
param applicationName string

@description('Deployment environment.')
@allowed([ 'dev', 'test', 'prod' ])
param environment string

param location string = resourceGroup().location

@description('SQL server admin login.')
@minLength(4)
param sqlAdminLogin string

@description('SQL server admin password. Use the Azure CLI secure prompt or Key Vault in production.')
@secureString
@minLength(12)
param sqlAdminPassword string

@description('App Service plan SKU. Premium in prod, Standard elsewhere.')
@allowed([ 'B1', 'S1', 'P1v2' ])
param planSku string = 'S1'

2. Variables

One stable formula produces every resource name, satisfying Azure's length/charset rules and the no-recreation rule.

// Deterministic suffix keeps names unique to this subscription+RG
var uniqueSuffix = uniqueString(subscription().subscriptionId, resourceGroup().name)

var appPlanName  = 'asp-${applicationName}-${environment}-${uniqueSuffix}'
var webAppName   = 'app-${applicationName}-${environment}-${uniqueSuffix}'
var sqlServerName= 'sql-${applicationName}-${environment}-${uniqueSuffix}'
var sqlDbName    = 'sqldb-${applicationName}-${environment}'
var sqlFirewallName = 'AllowAllWindowsAzureIps'

3. The Resources

App Service Plan — the scale unit. reserved: true + kind: 'linux' signal a Linux plan; bumping sku.name to P1v2 in prod gives you more memory and burst capacity, and you can later enable autoscale on the ASP from the portal or a separate Bicep file.

resource appServicePlan 'Microsoft.Web/serverfarms@2022-03-01' = {
  name: appPlanName
  location: location
  kind: 'linux'
  sku: {
    name: planSku                     // B1 / S1 / P1v2
    tier: (planSku == 'P1v2') ? 'PremiumV2' : 'Standard'
    capacity: (planSku == 'B1') ? 1 : 2
  }
  properties: {
    reserved: true                    // required for Linux plans
  }
}

App Service site — the web host. It implicitly depends on the plan via serverFarmId: appServicePlan.id, and gets its SQL connection string injected as a connection-string app setting so the application code just reads DefaultConnection.

resource webApp 'Microsoft.Web/sites@2022-03-01' = {
  name: webAppName
  location: location
  properties: {
    serverFarmId: appServicePlan.id       // implicit dependency on the plan
    httpsOnly: true                       // force HTTPS
    siteConfig: {
      linuxFxVersion: 'NODE|18-lts'       // Node.js 18 LTS on Linux
      minTlsVersion: '1.2'
      alwaysOn: true                      // keep the app warm
      appSettings: [
        { name: 'WEBSITE_RUN_FROM_PACKAGE', value: '1' }
        { name: 'APPINSIGHTS_INSTRUMENTATIONKEY', value: '' }
      ]
      connectionStrings: [
        {
          name: 'DefaultConnection'
          connectionString: 'Server=tcp:${sqlServer.name}.database.windows.net,1433;Initial Catalog=${sqlDbName};User ID=${sqlAdminLogin};Password=${sqlAdminPassword};Encrypt=True;TrustServerCertificate=False;Connection Timeout=30;'
          type: 'SQLAzure'
        }
      ]
    }
  }
}
Production hardening: the connection string above is fine for a learning scenario. In real deployments prefer SQL authentication with an AAD-managed identity, or place the admin password in Key Vault and pull it via a Key Vault reference — that keeps secrets out of the template output entirely.

SQL Server + Database + firewall — the data tier. The database uses parent: sqlServer (implicit dependency). The firewall rule allows the default "Azure services" range so the App Service can reach the logical server.

resource sqlServer 'Microsoft.Sql/servers@2023-08-01-preview' = {
  name: sqlServerName
  location: location
  properties: {
    administratorLogin: sqlAdminLogin
    administratorLoginPassword: sqlAdminPassword
    minimalTlsVersion: '1.2'             // no TLS 1.0/1.1
    publicNetworkAccess: 'Enabled'
  }
}

resource sqlDatabase 'Microsoft.Sql/servers/databases@2023-08-01-preview' = {
  parent: sqlServer
  name: sqlDbName
  location: location
  sku: {
    name: (environment == 'prod') ? 'S1' : 'Basic'
    tier: (environment == 'prod') ? 'Standard' : 'Basic'
  }
  properties: {
    collation: 'SQL_Latin1_General_CP1_CI_AS'
    maxSizeBytes: (environment == 'prod') ? 268435456000 : 2147483648   // 250GB / 2GB
  }
}

resource sqlFirewall 'Microsoft.Sql/servers/firewallRules@2022-05-01-preview' = {
  parent: sqlServer
  name: sqlFirewallName
  properties: {
    startIpAddress: '0.0.0.0'
    endIpAddress: '0.0.0.0'              // special value = Azure services only
  }
}
Dependency check: webApp's connection string reads sqlServer.name and sqlDbName directly, so Bicep deploys SQL before the app — no dependsOn needed. That's the implicit-dependency feature from Chapter 5 doing its job.

4. Outputs

output webUrl string = 'https://${webApp.properties.defaultHostName}'
output appHostName string = webApp.properties.defaultHostName
output sqlServerFqdn string = '${sqlServer.name}.database.windows.net'
output sqlDatabaseName string = sqlDbName
output appServicePlanName string = appServicePlan.name

7.3 Parameter File for Prod

// main.parameters.prod.json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "applicationName": { "value": "inventory" },
    "environment":     { "value": "prod" },
    "location":        { "value": "eastus2" },
    "planSku":         { "value": "P1v2" },
    "sqlAdminLogin":   { "value": "dbadmin01" },
    "sqlAdminPassword":{ "value": "P@ss-injected-via-CLI-or-vault" }
  }
}
Seriously: in a real repo the password won't sit in a parameter file. Pass it as a CLI secret or inject it in your pipeline via --parameters sqlAdminPassword=$(secret-vault-value) so it never reaches disk.

7.4 Deploying the Solution

# 0. Prepare (once)
az group create --name rg-inventory-prod --location eastus2

# 1. Compile-check locally
bicep build main.bicep
bicep lint main.bicep

# 2. Preview every change
az deployment group what-if -g rg-inventory-prod \
  --template-file main.bicep \
  --parameters main.parameters.prod.json

# 3. Deploy (supply the secure param from your environment, not the file)
az deployment group create -g rg-inventory-prod \
  --template-file main.bicep \
  --parameters main.parameters.prod.json \
  --parameters sqlAdminPassword="$SQL_PASSWORD" \
  --name deploy-inventory-prod

# 4. Grab outputs
az deployment group show -g rg-inventory-prod -n deploy-inventory-prod \
  --query properties.outputs

Expected output (paraphrased):

{
  "webUrl":         "https://app-inventory-prod-xxxx.azurewebsites.net",
  "appHostName":    "app-inventory-prod-xxxx.azurewebsites.net",
  "sqlServerFqdn":  "sql-inventory-prod-xxxx.database.windows.net",
  "sqlDatabaseName":"sqldb-inventory-prod",
  "appServicePlanName":"asp-inventory-prod-xxxx"
}

7.5 Verifying and Scaling

  1. Open webUrl in a browser — if your Node app is deployed, the default page comes back over TLS.
  2. Connect to SQL from SSMS / Azure Data Studio using sqlServerFqdn and the admin login to confirm the DB exists.
  3. Redeploy with a changed planSku (S1 → P1v2); what-if shows a plan update, not a replacement, because the name didn't change.
Scaling the plan horizontally: az appservice plan update -g rg-inventory-prod -n asp-inventory-prod-xxxx \ --sku P1v2 --number-of-workers 3 → the site keeps its name, DNS, and settings — only capacity grows.

7.6 Cleanup

az group delete --name rg-inventory-prod --yes --no-wait   # removes all resources

7.7 What You Learned (Final Recap)

  • One declarative file builds a complete App Service + SQL tier
  • Parameters with decorators make the template safe across dev/test/prod
  • Deterministic naming (env + app + uniqueSuffix) keeps names stable and idempotent
  • Implicit dependencies order the deployment automatically
  • Secure strings, HTTPS-only, TLS pinning, and firewall rules bake security in by default
  • what-if + a CI/CD gate make every change reviewable before it lands
