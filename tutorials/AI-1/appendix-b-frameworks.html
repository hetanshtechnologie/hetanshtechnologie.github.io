Appendix B — Framework Comparison and Selection

How to read this comparison

Part II introduced five approaches to agent orchestration. This appendix puts them side by side and gives you a worksheet for choosing. The goal is not to declare a winner. Each framework embodies a different answer to the question "who controls the next step?", and the right answer depends on your workload, team, and need for predictability.

Names are descriptive. All framework names are trademarks of their respective owners and appear here for educational comparison only. Capabilities change between releases; verify current behaviour against official documentation before committing to a framework.

Selection worksheet

Work through these five questions in order. The answers usually narrow the field to one or two candidates.

  1. How variable is the path? If the steps are fixed, use ordinary code and skip the framework. If the path has a few branches, a graph works. If it truly emerges from dialogue, consider a conversational framework.
  2. Do you need to pause and resume? Long tasks with approvals need durable state. Choose a framework where checkpointing is explicit and well supported.
  3. How many agents cooperate? One agent with tools is simplest. Handoffs suit triage patterns. Role-based crews suit document work. Group conversations suit open-ended analysis.
  4. What does the team already run? Platform integration often outweighs elegance. A framework that fits your identity, telemetry, and deployment systems will be cheaper to maintain.
  5. Can you evaluate it? If you cannot trace spans or replay runs, you cannot debug or improve the system. Treat observability support as a hard requirement, not a nice-to-have.

Worked example: choosing for a support system

Imagine a support assistant that answers policy questions, looks up orders, and issues refunds above a threshold with human approval. The path is mostly predictable: retrieve, answer, optionally look up an order, optionally prepare a refund, wait for approval. Branches exist but they are known in advance. Refunds require a durable pause that survives a restart.

Question 1 points to a graph: the control flow is explicit and bounded. Question 2 reinforces it: the approval pause needs durable state. Question 3 suggests a single agent with tools rather than a crew — there is no meaningful division of labour. Question 4 depends on the existing stack; if the product is already on a particular cloud platform, that framework's runtime may reduce integration work. Question 5 requires trace replay so a refund decision can be reconstructed.

The likely outcome is a graph-based orchestrator, optionally with a provider SDK's agent used as one node for the answer-generation step. This illustrates an important point: frameworks compose. Choosing one does not forbid using another where it fits.

Common pitfalls in framework selection

  • Choosing by popularity. A framework's community activity says nothing about fit for your reliability and state requirements.
  • Starting with multi-agent. Add a second agent only when one agent demonstrably cannot do the job.
  • Ignoring the escape hatch. If you cannot drop to ordinary code for a deterministic step, the framework is too rigid.
  • Skipping a spike. Build a small end-to-end prototype with tracing before committing a quarter to a framework.
  • Confusing the demo with production. Ask about checkpointing, timeouts, and audit logs up front, not after the first incident.

A decision shortcut

If you are still undecided after the worksheet, use this heuristic: choose the framework that makes your hardest requirement the most explicit. If it is control flow, choose a graph. If it is speed of construction, choose an SDK. If it is enterprise integration, choose a platform framework. If it is collaboration, choose a roles or conversation model. Then build a spike and measure.
