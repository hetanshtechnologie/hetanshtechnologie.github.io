22. Inference Engineering and Self-Hosting

What inference engineering means

Most developers consume models through an API and never think about serving. Inference engineering is the discipline of running models efficiently: choosing hardware, batching requests, managing memory, quantising weights, and designing systems that serve production traffic within latency and cost targets. It is the layer beneath the agent conversation.

Interest in self-hosting grows for three reasons: data sovereignty, predictable cost at scale, and control over model versions. It also brings operational complexity that should not be underestimated. The right question is not "can we host it?" but "does hosting give us something we cannot get otherwise?"

The serving stack

  1. Model weights — stored in a registry or object store, versioned and checksummed.
  2. Serving engine — loads weights, manages KV cache, schedules requests.
  3. Batching layer — groups compatible requests to improve throughput.
  4. API layer — exposes a stable interface to applications.
  5. Autoscaling — adds or removes replicas based on load.
  6. Observability — tracks latency, throughput, GPU utilisation, and errors.

Popular engines optimise different trade-offs. Some prioritise throughput for offline batches; others prioritise low time-to-first-token for interactive use. Evaluate with your own traffic pattern, not a generic benchmark.

Batching strategies

Continuous batching allows new requests to join a running batch as slots free up. Static batching waits for a group, which can add latency. For interactive agents, a small batch window and careful scheduling usually work best. For offline evaluation or bulk processing, larger batches are efficient.

Prefix caching is another powerful optimisation. If many requests share a long system prompt or document prefix, the engine can reuse computed attention state. This is especially relevant for agents, where the same instructions appear in every call. Design prompts with stable prefixes to benefit from caching.

Quantisation and model size

Quantisation stores weights with fewer bits, reducing memory bandwidth and allowing larger models on smaller hardware. Common levels include 8-bit and 4-bit. Quality loss varies by model and task, so evaluate rather than assume. A quantised model that fails on structured output is a false economy.

Distilled models are another tool: smaller models trained to imitate larger ones. They can be excellent for routing, classification, and simple extraction. Keep a set of small models for cheap first-pass work.

Hardware and topology

GPU memory is the primary constraint for hosting. A model must fit in memory along with KV cache and runtime overhead. Multiple GPUs require parallel strategies such as tensor or pipeline parallelism, which add complexity. Start with a model that fits comfortably on one GPU, then scale out only when measurements justify it.

For teams without GPU operations experience, managed inference endpoints often provide most of the benefit with less risk. Self-hosting makes sense when you have steady high volume, strict data requirements, or a need for custom serving behaviour.

Sovereign and private infrastructure

Some organisations require that prompts and outputs never leave their environment. This is where self-hosting becomes strategic rather than purely technical. It also demands the full operational stack: model updates, security patching, capacity planning, and incident response. Budget for people, not just hardware.

Version everything. A self-hosted model needs the same version discipline as code. Record model hash, quantisation scheme, engine version, and serving configuration in every trace.

Cost model

Self-hosting cost is mostly fixed: GPUs, power, and operations. API cost is mostly variable. The break-even point depends on utilisation. If your GPUs sit idle half the time, the API may be cheaper. If you serve constant traffic, hosting can win. Model both scenarios with realistic utilisation before deciding.

Case study: sizing a self-hosted summarisation endpoint

A logistics company summarises eight million internal documents a month and is considering replacing an API with self-hosting. Each document produces roughly 2,000 input tokens and 500 output tokens, of which 1,200 input tokens are a shared system prompt. At API prices of ₹15 per million input tokens and ₹60 per million output tokens, the monthly bill is 16,000 million × ₹15 = ₹2,40,000 for input plus 4,000 million × ₹60 = ₹2,40,000 for output, or ₹4,80,000 in total. The team models four GPU nodes at ₹85,000 each plus ₹60,000 of operations effort, about ₹4,00,000 a month — but only if the fleet stays above roughly 70% utilisation. Below that, the API wins.

Cost is not the only driver. Regulation forbids sending certain documents outside the company network, so self-hosting is partly strategic. The team defines targets before choosing hardware: p95 time-to-first-token under one second, at least 40 output tokens per second per active request, and no structured-output failures on a 300-case quality set.

serving:
  model: "llama-3.1-13b-instruct"   # weights hash sha256:9f2a...
  quantisation: int8               # int4 failed the structured-output gate
  engine: vllm-0.6.x
  gpu: 1x A100 40GB per replica
  replicas: 4                      # throughput + one spare for failures
  batching: continuous, window 50ms
  prefix_cache: on (shared 1,200-token system prompt)
  max_concurrent: 8 per replica
  targets: p95 TTFT < 1.0s, >= 40 tok/s per request

The 13-billion-parameter model in 8-bit needs about 14 GB for weights, leaving room on a 40 GB card for KV cache and eight concurrent requests. Quantisation is chosen empirically: 8-bit passes the structured-output gate, while 4-bit drops extraction accuracy from 0.94 to 0.87 on the quality set — a false economy. Continuous batching with a 50 ms window keeps time-to-first-token low while still grouping requests, and prefix caching avoids recomputing the shared 1,200-token prompt on every call. Measured p95 TTFT lands at 0.8 seconds and aggregate throughput at about 900 tokens per second across the fleet.

Two operational details determine whether this stays healthy. First, every trace records the model hash, quantisation scheme, engine version, and serving configuration, so a quality change can be correlated with a serving change. Second, autoscaling is driven by queue depth and KV-cache pressure, not only by CPU usage — a GPU can be "busy" in ways CPU metrics miss. The team keeps the API as a burst fallback for traffic spikes, which is why the routers from Chapter 23 matter here too.

Rolling out a new model hash is handled like a deployment, not a file swap. The team keeps the previous weights loaded on one replica, shifts 10% of traffic to the new replica, and compares quality scores and latency for an hour before going to 100%. Because the serving configuration is recorded in every trace, any shift in output can be tied to the new hash or quantisation scheme. They also watch GPU-specific health signals — memory utilisation, KV-cache occupancy, queue depth, and preemption count — since a saturated cache silently increases time-to-first-token long before an error appears. Capacity planning uses these signals, not request counts alone. A failed comparison automatically shifts traffic back to the previous replica, so a bad hash never reaches the whole fleet.

Pitfalls and trade-offs

MistakeWhy it mattersWhat to do instead
Choosing hardware from parameter count aloneWeights, KV cache, and runtime overhead must all fit in memory; a model that does not fit cannot serve.Calculate total memory for your concurrency target and leave headroom.
Assuming quantisation is freeLower precision can break structured output or reasoning on specific tasks.Evaluate each quantisation level on your own quality set before adopting it.
Using generic benchmarksPublic benchmarks rarely match your prompt lengths, batch sizes, and latency needs.Benchmark with your real traffic pattern and target metrics.
Static batching for interactive trafficWaiting to fill a batch adds latency that users feel immediately.Use continuous batching with a small window for interactive workloads.
Scaling out before scaling upMulti-GPU parallelism adds complexity that a single larger GPU may avoid.Fit the model on one GPU first; add nodes only when measurements justify it.
Forgetting the people costPatching, capacity planning, and incident response are ongoing work.Budget operations effort explicitly, not just hardware.

The core trade-off is fixed versus variable cost. Self-hosting turns a per-token bill into a capacity commitment: excellent economics at steady high utilisation, wasteful at low or spiky load. A hybrid — self-host the baseline, burst to an API — often captures the best of both, at the price of a more complex router.

Summary

  • Inference engineering optimises model serving, not model training.
  • Latency, throughput, and memory are the core constraints.
  • Batching and prefix caching improve efficiency but require careful design.
  • Quantisation trades quality for memory and speed; evaluate it.
  • Self-hosting is a strategic and operational commitment, not just a technical one.
