30. Workshop: LangGraph and TypeScript

The closing lab

The final session of the event was a ninety-minute, hands-on workshop on creating AI agents with LangGraph and TypeScript. Where the talks explained ideas, the workshop asked attendees to build. It was structured in three modules that move from the fundamentals of a graph to an agent that remembers a conversation. This chapter reconstructs the learning path in original language and expands each module with the reasoning you need to reuse it.

The progression is deliberate. First you learn how state and nodes form a graph. Then you give the graph a tool-calling loop, the classic ReAct pattern. Finally you add memory so the agent can hold a multi-turn conversation. Each step builds on the previous one, which is exactly how you should approach learning a new orchestration library.

Module 1 — LangGraph basics

The first module introduced the core mental model from Chapter 8: an agent as a typed state machine. Attendees defined a state object, wrote nodes that transform it, and connected them with edges. The immediate goal was a working graph that takes an input, calls a model, and returns a result.

Key ideas to take away:

  • State is explicit. Define its shape before writing nodes.
  • Nodes return updates. Each node contributes a partial change to state.
  • Edges decide control flow. Conditional edges read state to choose the next node.
  • START and END bound the graph. Every path begins and finishes cleanly.
const State = z.object({
  messages: z.array(Message),
  step: z.number().default(0)
});

const graph = new StateGraph(State)
  .addNode('callModel', async (state) => ({
      messages: [...state.messages, await model.invoke(state.messages)],
      step: state.step + 1
  }))
  .addEdge(START, 'callModel')
  .addEdge('callModel', END)
  .compile();
Workshop habit. Print the graph's structure and trace one execution. Seeing the path makes abstract state transitions concrete.

Module 2 — Tool calling and a ReAct agent

The second module added tools. A node could now receive tool calls from the model, execute the requested functions, and append the results to state. A conditional edge checked the last message: if it contained tool calls, route to the tool node; otherwise finish. This is the ReAct loop from Chapter 7 made executable.

The module highlighted several practical lessons:

  • Tool descriptions drive selection, so write them precisely.
  • Validate arguments before execution; never trust the model's schema adherence blindly.
  • Guard the loop with a maximum step count to prevent endless tool calls.
  • Return compact, structured tool results so context stays readable.
function route(state) {
  if (state.step >= MAX_STEPS) return END;
  return lastMessageHasToolCalls(state.messages) ? 'tools' : END;
}

graph.addConditionalEdges('callModel', route, { tools: 'executeTools', [END]: END });
graph.addEdge('executeTools', 'callModel');

Notice that the loop is ordinary code. The model proposes; the graph decides. That separation is what makes the system testable and safe, and it is the central lesson of the workshop.

Module 3 — Stateful conversational memory

The final module made the agent remember. A checkpointer persisted state under a thread identifier, so a second invocation could continue an earlier conversation. Attendees learned that memory is not a special feature of the model — it is a property of the runtime storing state between calls.

Important details covered in this module:

  • Use a durable checkpointer in production, not an in-memory one.
  • Choose a thread ID convention: one thread per conversation or per work item.
  • Trim or summarise long histories so context does not grow forever.
  • Record thread ID in traces so a conversation can be replayed during debugging.
const app = graph.compile({ checkpointer: new SqliteSaver() });
const config = { configurable: { thread_id: 'user-42-session-1' } };
await app.invoke({ messages: [new HumanMessage('Hi')] }, config);
Memory hygiene. Persisting everything is easy and often wrong. Decide what should be remembered, for how long, and who can delete it — the same privacy discipline discussed in Chapter 10.

Learning outcomes

By the end of the workshop, participants had built a small but complete agent: a graph with explicit state, a guarded tool-calling loop, and memory across turns. More importantly, they had practised the way of thinking this book teaches — put control flow in code, keep state explicit, bound autonomy, and make runs observable.

If you work through these modules on your own, extend them with one of the evaluation habits from Part IV. Add a small test set, check that the tool loop terminates, and verify that memory does not leak between threads. A workshop demo becomes a portfolio project the moment you can show how you verified it.

Worked example: adding retrieval and a checkpoint to the lab

The three workshop modules produce a small agent, but a demo becomes a portfolio project when you add a realistic concern. This walkthrough extends the lab in two ways that mirror production systems: a retrieval node before the model call, and a human approval checkpoint before a mutating tool. Both use the same state-and-edge mechanics from Module 1, which is the point — new capabilities are new nodes, not a rewrite.

Extending the state

First the state grows two fields: retrieved context and a pending-action flag for approval. Keeping these explicit means every node sees them and traces can show how they changed.

const State = z.object({
  messages: z.array(Message),
  context: z.array(Document).default([]),
  pendingAction: z.string().nullable().default(null),
  step: z.number().default(0)
});

Adding the retrieval node

A retrieve node reads the latest user message, queries a small vector index, and writes the top four chunks into context. The model node then includes those chunks in its prompt. The edge chain becomes START to retrieve, retrieve to callModel, and the existing conditional edge handles tool calls. Because retrieval is a separate node, you can test it independently: given a query, does it return the right chunks? That testability is exactly what the graph structure buys you.

Adding an approval checkpoint

The mutating tool, say issueRefund, is made two-phase. The model first calls a proposeRefund tool that writes a description to pendingAction and returns to the user. A conditional edge routes to END when pendingAction is set, so the graph pauses. On the next turn, if the user's message is an explicit approval, the graph calls the real issueRefund tool; otherwise it clears the flag. The model never mutates state without a human confirmation in the loop.

Why the checkpoint belongs in the graph. It is tempting to ask the model to "be careful" with the refund tool, but a prompt is not a control. Routing through an explicit state flag and a conditional edge makes the pause a property of the runtime, so it cannot be skipped by a persuasive turn of phrase.

Guarding and observing the extended graph

With more nodes, two safeguards matter. Keep the MAX_STEPS guard from Module 2 so a tool loop cannot run forever, and record the thread ID and step count in every trace. Then write three checks: retrieval returns non-empty context for a known query, the approval gate blocks mutation until confirmation, and memory does not leak between two thread IDs. These checks turn the lab into something you can demonstrate with evidence.

Run those three checks in continuous integration, not just once on your machine. A graph is easy to break with an innocent-looking edit to a conditional edge, and the approval gate is precisely the kind of control that can fail silently — the demo still works, but the pause quietly disappears. A test that asserts the graph stays paused until an explicit token arrives is worth far more than a careful code review.

Exercise 30.3 — Test the gate. Write three test cases for the approval checkpoint: approved, rejected, and ambiguous confirmation. State the expected state after each and how you would detect a false approval.

Common pitfalls in graph and memory design

The workshop's mechanics are simple, which makes it easy to develop habits that do not survive contact with real usage. These are the ones to watch.

PitfallWhy it mattersWhat to do instead
Letting state grow without boundEvery message and tool result is replayed, so latency and cost rise each turn.Trim or summarise old turns and keep only the context the next node needs.
Omitting a step or token guardA confused model can call tools forever, running up cost and hanging the user.Enforce MAX_STEPS and a token budget in the conditional edge.
Using an in-memory checkpointer beyond the demoState vanishes on restart, so "memory" fails the moment the process recycles.Use a durable store and test a restart mid-conversation.
Poor thread-ID conventionsColliding IDs leak one conversation into another; random IDs lose history.Derive a stable ID from user and session, and include it in traces.
Trusting tool arguments blindlyA malformed or injected argument can make a tool do something harmful.Validate against a schema and scope credentials to the minimum needed.
Persisting everything with no retention policyStored histories become a privacy and storage liability over time.Decide what to keep, for how long, and who can delete it.
Not tracing intermediate nodesWhen an answer is wrong, you cannot tell which node introduced the error.Record node names, step counts, and state deltas in every trace.

The theme from the workshop holds: put control flow in code, keep state explicit, and make each run observable. Every pitfall above is a case of violating one of those three ideas.

Review questions: workshop concepts

These questions check that you understood the mechanics of the lab rather than just followed the code. Answer them by describing behaviour, not by naming APIs.

  1. Why is an agent modelled as a typed state machine useful for testing, compared with an unstructured loop around a model call?
  2. In the ReAct loop, what stops the agent from calling tools indefinitely, and where does that rule live?
  3. Explain why memory is a property of the runtime rather than the model, using the checkpointer as your example.
  4. If two users' conversations were mixed up, which part of the memory design would you inspect first and why?
  5. You add a retrieval node and a refund tool to the lab. Describe how you would verify that a refund cannot happen without an explicit human approval.

Summary

  • The workshop built a LangGraph and TypeScript agent in three modules.
  • Module 1 covered state, nodes, and edges; Module 2 added a tool-calling ReAct loop; Module 3 added checkpointer-based memory.
  • The loop is code-controlled: the model proposes tool calls, the graph decides what happens next.
  • Guard loops with step limits and manage memory deliberately.
  • Extending the lab with evaluation turns a demo into a portfolio project.
