18. Silent Failure and Drift Detection

The most dangerous failure is the quiet one

A crashed agent gets attention. A degraded agent does not. It still returns answers, still calls tools, still reports success — but the answers are subtly less grounded, the tool choices slightly worse, the explanations a little more generic. Users notice before dashboards do. This is silent failure, and it is the central operational challenge of agentic systems.

Silent failure arises because agent output is a distribution. A model update, a prompt tweak, a retrieved-document change, or a new tool description can shift that distribution without crossing any hard assertion. The system remains "working" while quality drifts.

Sources of drift

  • Model updates — a provider changes weights or serving behaviour behind the same model name.
  • Prompt changes — an innocent wording edit changes emphasis.
  • Data changes — the knowledge base is updated, re-indexed, or partially corrupted.
  • Tool changes — an upstream API alters fields or latency.
  • Traffic changes — users ask questions the system was never evaluated on.
  • Feedback loops — the agent's outputs become future inputs, amplifying small biases.

Each source has a different detector. The trick is to monitor enough signals that you can tell them apart.

Canary suites

A canary suite is a small, stable set of cases run continuously against production. Unlike the nightly eval set, canaries use a fixed input set and fixed expected properties. They run on a schedule — every few minutes or on every deployment — and their scores are tracked as a time series.

Pin canary inputs carefully. If you regenerate them, you lose comparability. Keep a long-lived core set and a rotating exploratory set. Alert when a canary score moves outside its historical range, not merely below an absolute threshold.

Score distributions, not just averages

An average groundedness score of 0.88 can hide a bimodal distribution: most answers are excellent, a small cluster is terrible. Track percentiles and shape. A sudden increase in low-score outliers is often the first sign of drift. Plot the distribution over time and segment by input type, user tier, and tool path.

Pairwise comparisons are also useful. Run the current build against a frozen reference build on the same inputs. If the new build wins less often than expected, investigate even if its absolute score looks fine.

Judge rationale logging

When an LLM judge scores an output, store its rationale. Aggregated rationales reveal patterns that numbers miss: "answer ignored the date filter", "citation pointed to an unrelated section", "agent apologised instead of answering". Cluster these rationales weekly and you will often discover a new failure mode before users report it.

Signal vs noise. Judge rationales are untrusted generated text. Use them to form hypotheses, then confirm with deterministic checks or human review.

Span-level tracing

End-to-end traces let you localise drift. If final answer quality drops but retrieval relevance is stable, look at generation. If retrieval relevance drops, look at the index or embedding model. If tool error rates rise, look upstream. Store per-span metrics: latency, token count, score, retry count, and error class.

Defend against the "silent loop" as well. Track the distribution of step counts and tool calls per request. A gradual increase often means the agent is compensating for a degraded tool or a changed prompt by trying more times.

Production traces as eval fuel

Sample real traces, anonymise them, and feed them into the eval set. This keeps evaluation aligned with actual usage. Prioritise traces where the user corrected the answer, rephrased the question, or abandoned the session. Those are implicit quality signals, and they are often more informative than a rating prompt nobody fills in.

Build a small human review loop: a reviewer looks at twenty sampled traces a week and labels failure categories. Over a month, this produces a high-value eval set and a shared vocabulary for quality discussions.

Alerting without fatigue

Alert on changes that are both statistically meaningful and operationally relevant. A one-point drop on a twenty-case canary is noise; a ten-point drop in groundedness for billing questions is not. Use rolling windows and minimum sample sizes. Route alerts to a human who can act, and include a link to the failing traces.

Every alert should have a runbook: what to check first, which version to roll back, and who to notify. An alert without a runbook creates anxiety, not reliability.

Case study: the Tuesday grounding drift

A research assistant at a mid-sized firm answers questions over an internal knowledge base. Its team runs a 40-case canary every five minutes against production. For three weeks the mean groundedness score sits at 0.90 with a tight band of ±0.02. On Tuesday morning the mean slides to 0.81 — not off a cliff, but steadily across thirty-six hours. No hard assertion fires, no tool errors rise, and the service stays fully "up". Users, however, start saying the answers feel "wordier and less sure of themselves".

The first useful signal comes from distribution, not the average. The tenth-percentile score has fallen from 0.78 to 0.45, meaning a small cluster of answers has become much worse while the majority remain fine. Segmenting by input type shows the drop is concentrated in questions that require a precise date, such as "what was the policy on remote work in 2023?".

canary: research-assistant
  cases: 40            # 20 normal, 8 no-answer, 6 injection, 6 tool-error
  schedule: every 5m
  baseline_window: 21d
alert: groundedness.p10
  condition: value < baseline.p10 - 0.10
  min_samples: 12
  window: 30m
  route: "#quality-oncall"
  runbook: "drift-triage/runbook#grounding"

Span-level tracing localises the fault. Retrieval relevance is flat at 0.86 and the index build hash has not changed, so the knowledge base is not the problem. The generation spans, however, show a 30% rise in output tokens and a different response pattern: the model now appends cautious caveats that cite no source. A pairwise run against a frozen reference build confirms the shift — the current build wins only 42% of head-to-head comparisons on the same inputs, well below the 50% that would indicate no change.

Judge rationales supply the hypothesis. Clustering the week's rationales surfaces one phrase repeatedly: "answer adds unsupported caveats". That matches the token increase and points to the model, not the data. Checking the provider's release notes reveals that the alias model-x had been repointed to a new snapshot on Monday evening; the team had been using the alias in production. They pin the exact snapshot ID, redeploy, and the canary returns to 0.90 within one canary cycle. The permanent fixes are threefold: pin model versions everywhere, alert on pairwise regression against a frozen reference (not only absolute thresholds), and keep production traces flowing back into the eval set so new failure modes enter the suite.

The team also writes a detector matrix so the next incident does not require the same detective work. A model change is caught by a pinned-alias diff and the pairwise canary; a prompt edit by the prompt hash recorded on every trace; a data change by the index build hash and a weekly count of chunks per source; a tool change by the tool schema version plus field-level validation errors; a traffic shift by monitoring the distribution of input topics; and a feedback loop by watching the distribution of step counts per request. Each detector has an owner and a runbook link. When the canary drifts again six weeks later, the matrix points to a schema change in the search tool within minutes rather than days.

Pitfalls and trade-offs in drift detection

MistakeWhy it mattersWhat to do instead
Watching only the mean scoreAverages hide bimodal failure, where a small cluster collapses while the headline stays healthy.Track percentiles and the share of low-score outliers, and plot the distribution over time.
Using a floating model alias in productionA provider repoint can change behaviour overnight with no deployment on your side.Pin immutable model snapshot IDs and record them in every trace.
Regenerating canary inputsFresh inputs destroy comparability, so the time series no longer measures drift.Keep a long-lived core set plus a separate rotating exploratory set.
Alerting on any small movementOne-point swings on a small sample create noise and train responders to ignore alerts.Require a rolling window, a minimum sample size, and a statistically meaningful change.
Trusting judge rationales as factRationales are generated text and can confidently name the wrong cause.Treat them as hypotheses and confirm with deterministic checks or human review.
Alerting without a runbookA page that does not say what to check or what to roll back produces anxiety, not reliability.Attach a runbook and a failing-trace link to every alert, and rehearse it.

A recurring trade-off is sensitivity versus fatigue. Alert too aggressively and the team mutes the channel; alert too conservatively and drift festers until users complain. A practical response is tiering: silent dashboard annotations for small movements, a ticket for sustained medium shifts, and a page only for a large change on a high-traffic segment with a confirmed runbook.

Summary

  • Silent failure is distributional drift that passes hard assertions.
  • Canaries provide a stable time series for quality signals.
  • Monitor distributions and outliers, not only averages.
  • Span-level tracing localises the drifting component.
  • Feed production traces back into evaluation with human review.
