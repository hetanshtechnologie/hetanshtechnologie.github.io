6. Tool Calling and Function Execution

From language to action

A tool call is a structured request from the model to the harness: "please run this named function with these arguments". The model does not execute anything. It proposes. The harness validates, authorises, executes, and returns the result as a new message. This separation is the single most important safety property in agent design.

Tool calling turns a chatbot into an agent. It also introduces a new failure surface: the model may request the wrong tool, supply malformed arguments, call a tool at the wrong time, or loop forever. A good tool layer makes those failures cheap to detect and recover from.

Designing a tool contract

A tool definition should be small, specific, and honest. It contains a name, a description, parameter schema, and a description of the output. The description is what the model reads to decide whether to call it. Vague descriptions cause misrouting.

{
  "name": "find_orders",
  "description": "Search the current user's orders by order id or date range.
                  Read-only. Returns at most 20 results.",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "pattern": "^ORD-[0-9]{6}$" },
      "from_date": { "type": "string", "format": "date" },
      "to_date": { "type": "string", "format": "date" }
    },
    "additionalProperties": false
  }
}

Notice the hints: "current user's", "read-only", "at most 20". These are not decorative. They tell the model about scope and cost, and they tell the implementer what to enforce. If the tool can only see the current user's records, the implementation must derive that identity from the session, never from a model-supplied user_id.

The execution loop

A single agent step follows a predictable sequence:

  1. Assemble messages: system instructions, history, current input, tool definitions.
  2. Call the model with a bounded maximum token count.
  3. If the response is plain text, return it.
  4. If the response contains tool calls, validate each call against the schema.
  5. Check policy: is this tool allowed for this user, in this state, with these arguments?
  6. Execute with a timeout and scoped credentials.
  7. Append results as tool messages and call the model again.
  8. Stop when a stop condition is met: final answer, step limit, or budget limit.

Step 8 is not optional. An agent without a step limit can spin for minutes and spend a surprising amount of money. Set a maximum number of tool rounds and a token budget, and treat hitting them as an observable event, not a silent truncation.

Validation and argument repair

Validate arguments with a real schema library. Reject unknown fields. Coerce obvious string-to-number cases only when it is safe, and log every repair. If an argument is missing, you have two choices: ask the model to revise the call, or ask the user. For low-risk, reversible tools, a single repair round is efficient. For high-risk actions, ask the user.

Never let the model supply identity or permissions. User ID, tenant ID, role, and account balance must come from trusted server state. A tool that accepts user_id from the model is an access-control bug waiting to happen.

Representing results back to the model

Tool results should be concise, structured, and labelled with status. A raw 50 KB JSON dump will consume context and confuse the model. Return the fields the next step needs, a success flag, and an error code when something fails. If the result is large, return a summary plus a reference the model can use in a follow-up call.

{ "ok": true, "count": 3, "orders": [
    { "id": "ORD-100245", "status": "shipped", "total": 2499 }
  ], "truncated": false }

For failures, distinguish retryable errors from permanent ones. "Timeout, try again" and "order not found, do not retry" should produce different model behaviour. Put that guidance in the tool result, but also enforce it in the harness — a model may ignore it.

Side effects and idempotency

Read-only tools are easy. Write tools need care. Give each mutating operation an idempotency key derived from the conversation and step, so a retry does not create duplicate refunds or emails. Require explicit confirmation for irreversible actions. A practical pattern is a two-phase tool: preview_refund followed by execute_refund, where the second call accepts a token produced by the first.

Some actions should never be fully autonomous. Above a value threshold, or when the target is external to the organisation, insert a human approval checkpoint. The agent prepares the action; a person approves it. This is not a limitation of the technology — it is a design choice that makes deployment possible.

Tool selection and description hygiene

Giving an agent fifty tools does not make it powerful; it makes selection unreliable. Keep the active toolset small for each task. If you have many tools, retrieve the relevant subset dynamically based on the user's request. Group related operations behind a single well-described tool with an action enum, and document each action clearly.

  • Use verbs in tool names: search_orders, not orders_tool.
  • State limits and scope in the description.
  • Avoid overlapping tools with nearly identical descriptions.
  • Version tool schemas and keep old versions during migration.
  • Log the tool name, arguments, latency, and result status for every call.

Errors, loops, and recovery

Common loop patterns include calling the same tool with the same arguments repeatedly, alternation between two tools without progress, and endless clarification questions. Detect these with a trace fingerprint: hash the last few tool calls and break if the pattern repeats. On break, either summarise what was learned and ask the user, or return a clear failure. Silent looping is worse than an honest failure.

A worked example: a refund tool that cannot hurt you

Refunds are a good stress test because they spend money and touch customer records. Suppose a support agent may issue refunds up to ₹2,000 autonomously and must seek approval above that. Here is a design that makes the dangerous paths difficult to reach by accident.

Step 1: split the operation. Instead of one issue_refund tool, expose preview_refund and execute_refund. The preview checks order eligibility, calculates the amount, and returns a short-lived token that encodes the exact amount and order id. Execute accepts only that token plus an idempotency key — not a free-form amount. A model that hallucinates a larger amount has no argument slot in which to put it.

Step 2: derive identity from the session. Neither tool accepts a customer id. The harness reads it from the authenticated session and cross-checks that the order belongs to that customer. If the model asks to refund someone else's order, the tool returns a permanent error with code NOT_YOUR_ORDER, and no approval path can override it.

Step 3: bound the loop. The agent is allowed six tool rounds and 8,000 output tokens. A trace fingerprint hashes the last three calls; if the same name-and-argument pair appears twice, the harness injects a tool result saying "no new information — stop repeating and summarise". Hitting the round limit is a logged event with a metric, not a silent cut-off.

Step 4: make retries safe. The idempotency key is hash(thread_id, step_number). If the same key arrives twice, the refund service returns the original result instead of creating a second refund. This matters because networks drop responses and harnesses retry — the exact situation in which duplicate charges happen.

Step 5: return compact results. The preview returns four fields and a token, never the full order history. Errors carry a retryable flag: a timeout is retryable, an ineligible order is not.

tools:
  preview_refund(order_id) -> {eligible, amount, token, expires_in: 300}
  execute_refund(token, idempotency_key) -> {ok, refund_id}
constraints:
  customer_id: from session ONLY
  amount: from preview token ONLY
  autonomous_limit: 2000 INR   above -> approval node
limits: 6 tool rounds | 8000 output tokens | 5s per tool
loop_guard: repeated(name+args) >= 2 -> inject "stop repeating"
idempotency: hash(thread_id, step)

Every rule in this design is enforceable in code. The tool description tells the model about the limits, but the limits do not depend on the model remembering them. That is the pattern to carry into every tool you design.

Tool design pitfalls

Tools are where language becomes action, so mistakes here have consequences outside the prompt. These are the recurring ones.

MistakeConsequenceFix
Accepting identity from the modelAny prompt injection becomes an access-control bypass.Derive user, tenant, and role from trusted session state.
One giant tool with fifteen actionsSelection degrades and descriptions become vague.Split by purpose, or use a small action enum with clear docs.
Returning raw API payloadsContext fills with noise and the model fixates on irrelevant fields.Return a summarised, typed result with a status flag.
No idempotency on writesA retry creates duplicate emails, charges, or records.Key every mutation and make repeated keys return the original result.
Describing a tool as "safe" without enforcing itThe model trusts the label while the implementation may not be safe.Make scope and limits true in code, then state them in the description.
Treating loop detection as optionalA confused agent can spin and spend for minutes.Fingerprint recent calls, break repeats, and emit a metric.

Validation is where a tool contract becomes real. A schema library rejects unknown fields and malformed types, but the interesting checks are semantic: is the date in the future, is the amount within the approved limit, does the order id belong to this customer? Each rejected call should produce an error message the model can act on, not a stack trace. Log both the raw proposed arguments and the validated ones, because the difference between them is often the clearest evidence of a confused plan or a manipulation attempt in the surrounding context.

A final trade-off: repair versus refusal. When arguments are slightly malformed, an automatic repair round is convenient for reversible tools but dangerous for write tools. Decide per tool, record every repair, and never repair identity or amount fields.

Description hygiene. Tool descriptions are read by the model as an interface contract. State scope, limits, and read-only status in the description — and then make each claim literally true in the implementation.

Review questions for tool design

These questions check whether you understand the execution loop rather than just its vocabulary. Answer them in your own words.

  1. Why is deriving a customer id from the session safer than accepting it as a tool argument, even if the model has been behaving well so far?
  2. Explain what an idempotency key protects against and why hashing the thread and step is a reasonable choice.
  3. A tool returns "error: timeout" and another returns "error: order not found". How should the harness and the model treat these differently?
  4. When would you choose a two-phase tool over a single mutating operation? What new state must you track?
  5. Describe a loop your fingerprint detector would miss, and propose an additional guard that would catch it.

Summary

  • The model proposes tool calls; the harness validates, authorises, and executes them.
  • Tool descriptions are part of the interface and must state scope and limits.
  • Identity and permissions never come from model-generated arguments.
  • Set step and token budgets, and detect repeated call patterns.
  • Mutating tools need idempotency, confirmation, and often human approval.
