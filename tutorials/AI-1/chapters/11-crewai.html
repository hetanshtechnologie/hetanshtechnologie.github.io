11. CrewAI

Teams as an abstraction

CrewAI models automation as a team. You define agents with roles, goals, and backstories; you define tasks with descriptions and expected outputs; then you assemble them into a crew that works through the tasks. The metaphor is more than cosmetic. It encourages you to think about division of labour, handoffs, and accountability — the same things you would consider when designing a human team.

This approach is appealing for knowledge-work workflows: market research, content production, analysis, and planning. These tasks naturally split into specialist roles, and the output of one role becomes the input of another. The framework provides structure for those relationships instead of leaving them implicit in a long prompt.

The building blocks

BlockMeaning
AgentA role with a goal, a backstory, tools, and a model
TaskA unit of work with an instruction and an expected output
CrewA collection of agents and tasks with a process
ProcessSequential or hierarchical coordination
ToolA capability an agent may use while performing a task
FlowEvent-driven orchestration around crews for more complex control

The "backstory" field often surprises engineers. It is simply a way of giving the model a consistent persona and vocabulary, which can improve style and decision consistency. It is not a substitute for clear instructions. A researcher with a vivid backstory but no source constraints will still invent facts.

Designing roles that work

Good roles are narrow and non-overlapping. "Researcher", "Analyst", and "Reviewer" are distinct. "Assistant", "Helper", and "Generalist" are not. Each role should have a clear deliverable: the researcher produces a list of sourced findings; the analyst produces a comparison table; the reviewer produces a checklist of gaps. When deliverables are concrete, handoffs carry useful information.

Avoid the common mistake of giving every agent every tool. If the reviewer can rewrite the report, it may do so instead of reviewing it. Give tools according to responsibility, exactly as you would in a real team. This also reduces the tool-selection problem described in Chapter 6.

Tasks and expected output

A task description should state the goal, the inputs, the constraints, and the output format. "Analyse the market" is too vague. "Using the ten sourced findings from the researcher, produce a three-column table comparing competitors on price, onboarding, and support, and flag any claim without a source" is testable.

Because tasks produce artefacts that other tasks consume, define the shape of those artefacts. If one agent's prose becomes another agent's input, ambiguity compounds. Structured output, as discussed in Chapter 4, keeps the chain clean.

Processes and delegation

In a sequential process, tasks run one after another. This is predictable and easy to debug. In a hierarchical process, a manager agent delegates and reviews. Hierarchical structures are more flexible but harder to evaluate because the path varies between runs. Start sequential; move to hierarchical only when the work genuinely requires dynamic delegation.

Cost warning. Team-shaped systems multiply model calls. A four-agent crew with two revision rounds can easily cost an order of magnitude more than a single well-prompted call. Measure before you commit.

Flows for real control

Flows add event-driven orchestration around crews, allowing you to listen for events, branch, and manage state across steps. If you find yourself trying to make a crew do something it was not designed for — complex approvals, long pauses, retries with backoff — a flow is the right place. The same principle applies across frameworks: keep the agent metaphor for collaboration, use explicit orchestration for control.

When CrewAI fits

  • Your work naturally divides into specialist roles.
  • You want a quick way to express collaboration without building a state machine.
  • The output is a document, analysis, or plan rather than a transactional decision.
  • You can tolerate variable paths and are willing to trace them.

For high-volume, low-latency, deterministic work, a simple pipeline is better. For a weekly research digest where quality matters more than milliseconds, a crew is a productive model.

Case study: a weekly competitive-intelligence digest

A product-marketing team publishes a Monday digest about competitors. It currently takes two people most of Friday: one gathers sources, the other writes and checks the summary. We will model this as a crew with four roles and a flow that handles the approval step. The output is a document, quality matters more than latency, and the team wants every claim traceable to a source — a good fit for the team abstraction.

Roles and deliverables

We define four agents with non-overlapping responsibilities. The researcher finds recent, sourced facts. The analyst turns them into a comparison table. The writer produces a short narrative. The reviewer checks that every claim in the narrative appears in the table with a source. Each role gets only the tools it needs: the researcher has web and knowledge-base search, the analyst has a calculation tool, the writer and reviewer have no external tools. Crucially, the reviewer cannot rewrite the digest — it can only produce a list of gaps.

researcher = Agent(
    role='Researcher',
    goal='Find 10 sourced facts about each competitor from the last 7 days',
    backstory='You are meticulous about dates and never cite an undated claim.',
    tools=[web_search, kb_search],
    allow_delegation=False
)

reviewer = Agent(
    role='Reviewer',
    goal='List every claim in the draft that lacks a source in the findings',
    backstory='You flag gaps; you do not edit the document.',
    tools=[],
    allow_delegation=False
)

Setting allow_delegation=False on the reviewer is the important line. In an earlier version, delegation was on for all roles and the reviewer quietly handed the draft back to the writer with edits, producing an unpredictable loop and roughly three times the expected calls. Disabling delegation kept the reviewer's output as an artefact the flow could handle explicitly.

Tasks as contracts

Each task states its inputs, constraints, and exact output shape. The analyst task, for example, names its input as "the researcher's ten findings per competitor" and requires a three-column table of price, onboarding time, and support, with a source ID in every row. Structured output keeps the chain clean; if the researcher's prose were passed directly to the writer, ambiguity would compound at each step.

analysis = Task(
    description=('Using the researcher findings, build a table comparing '
                 'competitors on price, onboarding, and support. '
                 'Include a source_id column. Flag any row without a source.'),
    expected_output='A markdown table with 4 columns and one row per competitor',
    agent=analyst
)

Process, flow, and cost

We run the crew sequentially — researcher, analyst, writer, reviewer — because the path is predictable and we want reproducible traces. Only after the draft passes review does a flow take over: it waits for a human editor's approval event, then publishes. If the reviewer returns gaps, the flow re-runs the writer once with the gap list attached; after one revision it escalates to the human regardless. The cost is explicit. Four agents, roughly 1,200 input and 400 output tokens per task, plus one revision round, comes to about 8,000 input and 2,400 output tokens per digest. At the configured model rates that is a few cents — trivial for a weekly job, but worth stating because the same crew run every hour would cost roughly 168 times as much.

Pitfalls and trade-offs

These are the mistakes that most often turn a productive crew into an unpredictable, expensive one. Each has a concrete fix.

  • Vague role names. "Assistant" and "Helper" overlap, so tasks drift between them. Use domain-specific roles — Researcher, Analyst, Reviewer — with one deliverable each that you can inspect after a run.
  • Giving every agent every tool. A reviewer that can rewrite the report will rewrite it instead of reviewing. Assign tools by responsibility, which also shrinks the tool-selection problem described in Chapter 6.
  • Backstory as a substitute for instructions. A vivid persona improves tone but will not stop invented facts. Pair it with explicit source constraints and a required source-ID field in the output.
  • Hierarchical process by default. A manager adds calls and makes the path vary between runs, which complicates evaluation. Start sequential and introduce delegation only when dynamic task selection is genuinely required.
  • Unbounded revision loops. A writer–reviewer pair can revise indefinitely. Cap revisions in the flow, and define exactly what is returned when the cap is reached.
  • Ignoring cost until scale. Team-shaped systems multiply model calls; a cheap weekly job can become an expensive per-request feature. Estimate tokens per role before committing to the pattern.
  • Using a crew for transactional work. Low-latency, deterministic decisions do not benefit from role-play. Use a simple pipeline and reserve crews for document- and analysis-shaped work.

Summary

  • CrewAI frames automation as a team of specialised roles.
  • Narrow roles, concrete deliverables, and scoped tools prevent drift.
  • Sequential processes are predictable; hierarchical ones are flexible but variable.
  • Flows provide explicit control when a crew alone is not enough.
  • Team-shaped systems cost more; justify them with quality gains.
