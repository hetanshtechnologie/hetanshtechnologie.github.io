14. MCP at Scale: Serverless and Stateless Patterns

What changes at scale

A single MCP server running on a laptop is straightforward. A fleet serving many users across many applications introduces new questions: how do you handle bursts, avoid stateful coupling, keep latency predictable, and control cost when most servers are idle? These are familiar infrastructure questions, but the protocol's session model gives them a particular shape.

One theme runs through this chapter: move state out of the server process. If a request can be handled without depending on memory from a previous request, you can scale horizontally, survive restarts, and run on serverless platforms. Where state is unavoidable, store it externally and reference it by ID.

Stateless design

A stateless MCP server treats every tool call as self-contained. Authentication context, task identifiers, and any needed state arrive with the request or are fetched from an external store. This has several benefits: instances are interchangeable, cold starts are less disruptive, and retries are safe.

Of course, agents are stateful. The state lives in the client, the graph checkpointer, or a durable workflow store — not in the MCP server. The server's job is to perform capability calls reliably. Keeping that boundary clean is the essence of scaling MCP.

Stateful serverStateless server
In-memory session affinityAny instance can serve any request
Restart loses in-flight workRestart is invisible
Hard to autoscaleNatural fit for serverless
Simpler for long-lived local toolsNeeds external stores for durable state

Serverless fit

Serverless platforms shine when traffic is bursty and tasks are short. MCP tool calls often are: a lookup, a query, a small transformation. You pay for execution time rather than idle capacity, and scaling is handled for you. The costs are cold-start latency and execution time limits.

Mitigations include keeping packages small, initialising clients outside the handler where possible, using provisioned concurrency for latency-sensitive paths, and designing tools to finish within the platform's timeout. Long-running tools should be converted into asynchronous jobs: accept the request, return a job ID, and let the agent poll or receive a callback.

Asynchronous patterns

Not every capability can return immediately. A report generation, a batch import, or an approval workflow may take minutes. Model an async tool as two or three calls: start_job, get_status, and optionally get_result. Return a compact status object that tells the agent whether to wait, retry, or ask the user.

{ "job_id": "job_8192", "status": "running",
  "poll_after_seconds": 5, "result_hint": "report_url" }

The poll_after_seconds field is a small but useful courtesy: it prevents tight polling loops that waste tokens and money. Your harness can enforce a maximum polling count and a deadline.

Availability and failure handling

MCP servers will fail. Networks partition, databases time out, and dependencies return errors. Design for it. Use timeouts on every call, exponential backoff for transient failures, and circuit breakers when a dependency is clearly unhealthy. Distinguish retryable errors from permanent ones in the response so the agent does not retry a malformed request forever.

From the agent's perspective, a tool failure is just another observation. The harness can route to a fallback tool, ask a clarifying question, or report a partial answer. These are control-flow decisions from Chapter 7; the protocol simply supplies a clean error signal.

Cost and tenancy

In a multi-tenant environment, one user's expensive tool call must not degrade everyone else's service. Apply rate limits and per-tenant budgets at the gateway or server. Record which tenant and which agent triggered each call. If you cache results, include tenant identity in the cache key to prevent cross-tenant leakage.

Cache carefully. Caching a read-only tool result can save a great deal of latency and cost. Caching anything that depends on permissions requires the permission set in the key and an invalidation strategy.

Observability

Emit structured logs and metrics for connection count, tool call volume, latency percentiles, error rates by type, and payload sizes. Trace IDs should flow from the agent through the MCP client into the server. Without that correlation, a slow response is a mystery: was it the model, the client, the network, or the tool?

Also log discovery events. Changes in a server's advertised tools can alter model behaviour even if no code in the agent changed. A new tool with a vague description may suddenly attract calls that used to go elsewhere.

Migration path

Moving a prototype to production is an incremental process. A practical sequence is: make handlers idempotent, move session state to an external store, add authentication and per-call authorisation, introduce timeouts and structured errors, add metrics, then consider serverless deployment. Doing serverless first usually exposes every hidden state dependency at once.

Case study: scaling a report-generation server

A team exposes a "generate sales report" tool through MCP. The first version runs on a single long-lived process: it holds a database connection, keeps a map of active jobs in memory, and streams a large CSV back in the tool result. It works for ten users. At two hundred concurrent users it fails in three ways — restarts lose in-flight jobs, latency spikes during bursts, and one tenant's huge report starves everyone else. We will refactor it into a stateless, asynchronous service.

Making the handler stateless

The first change is to remove in-memory job state. The handler now accepts a request, writes a job record to an external store with a generated ID, enqueues work, and returns immediately. Any instance can handle any call, so we can run on a serverless platform and scale to zero between bursts. Cold starts are mitigated by initialising the database client outside the handler and keeping the package small; provisioned concurrency is reserved for the status endpoint, which clients poll. The report itself is generated by a worker that writes the CSV to object storage.

def start_report(args, ctx):
    job_id = "job_" + uuid4().hex[:8]
    store.put(job_id, tenant=ctx.tenant_id,
              requester=ctx.user_id, status="queued",
              params=compact(args))
    queue.enqueue(job_id)
    return {"job_id": job_id, "status": "queued",
            "poll_after_seconds": 5}

The poll_after_seconds field is a small courtesy with a large effect. Without it, an agent polls as fast as it can, spending tokens and hammering the status endpoint. The harness now also enforces a maximum of twelve polls and a two-minute deadline.

Async status and result

We expose three tools: start_report, get_status, and get_result. Each status response tells the agent what to do next — wait, retry later, ask the user, or fetch a result. Errors distinguish retryable from permanent failures: a busy worker is retryable, a malformed date range is not. The result tool returns a signed URL valid for ten minutes, scoped to the requesting tenant, rather than embedding CSV content in the conversation.

{ "job_id": "job_8192", "status": "running",
  "poll_after_seconds": 5, "result_hint": "report_url",
  "trace_id": "tr_7c1f" }

Including the trace ID in every status response lets support follow one request across agent, client, queue, worker, and storage with a single search.

Failure handling is the other half of availability. Each dependency call carries a timeout, and transient failures use exponential backoff with jitter so a hundred clients do not retry in lockstep. When the object store is clearly unhealthy, a circuit breaker stops sending requests for a short window and the status response tells the agent the delay is temporary rather than permanent. Permanent errors — an invalid date range, a report type the tenant cannot access — are never retried. The agent's decision rules are written against these classes, so it knows whether to wait, ask the user, or give up.

Tenancy, caching, and observability

Per-tenant rate limits cap each customer at four concurrent reports and twenty starts per hour, enforced at the gateway before the handler runs. Caching applies only to the schema of a report, not its data; where we do cache read results, the key includes tenant ID and permission set. Metrics track connection count, tool volume, latency percentiles, error rates by type, and payload sizes. We also alert on discovery changes: when the server advertises a new tool, model behaviour can shift without any agent code changing. The migration happened in stages — idempotent handlers first, then external state, then auth, then timeouts and structured errors, and only then serverless. Doing serverless first would have exposed every hidden state dependency at once.

Pitfalls and trade-offs

MistakeWhy it mattersWhat to do instead
Keeping session state in the server processInstances are not interchangeable, restarts lose work, and autoscaling becomes unsafe.Store state externally and reference it by ID; keep the server's role to reliable capability calls.
Long calls inside a serverless timeoutThe platform kills the function, the agent sees a generic failure, and work is repeated.Convert long operations to start/status/result jobs with a documented deadline.
Tight polling without guidanceAn agent burns tokens and floods the status endpoint.Return poll_after_seconds and enforce a maximum poll count in the harness.
One error shape for every failureRetryable and permanent failures look identical, so agents retry forever or give up too soon.Classify errors explicitly and document the agent's action for each class.
Cache keys that ignore tenancy or permissionsOne customer's data can be served to another.Include tenant ID and permission set in the key, with an invalidation plan.
Trace IDs that stop at the clientA slow response becomes a mystery across agent, client, queue, and tool.Propagate one trace ID through every boundary and return it in status responses.
Serverless before the basicsHidden state dependencies all fail at once, making diagnosis slow.Follow the migration sequence: idempotency, external state, auth, errors, metrics, then serverless.

Summary

  • Scaling MCP means removing state from server processes.
  • Serverless fits short, bursty tool calls but requires cold-start planning.
  • Long operations should become asynchronous jobs with status calls.
  • Distinguish retryable from permanent errors and apply backoff.
  • Trace IDs must flow across agent, client, and server boundaries.
