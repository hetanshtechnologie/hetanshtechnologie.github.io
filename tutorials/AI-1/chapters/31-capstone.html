31. Capstone Projects and Next Steps

From reading to building

A book can give you a map, but only building gives you the terrain. This final chapter turns the themes of AI-1 into concrete projects and a practical plan. Pick one capstone that excites you, adapt it to a domain you know, and carry it far enough to include evaluation, failure cases, and a clear explanation of your trade-offs. That single project will teach you more than another month of passive reading.

Capstone brief A — Evaluated RAG assistant

Goal: Answer questions over a private document set with citations and an honest no-answer path.

  • Ingest and chunk documents with metadata and access levels.
  • Implement hybrid retrieval and reranking.
  • Measure recall@k, groundedness, and abstention separately.
  • Build a small eval harness with deterministic assertions and a calibrated judge.
  • Document three real failure cases and how you addressed them.

Chapters used: 4, 5, 16, 17, 18.

Capstone brief B — Guarded tool-using agent

Goal: Build an agent that can perform a useful multi-step task with tools, while enforcing least privilege and human approval.

  • Define three tools with precise contracts and scoped credentials.
  • Use a graph or SDK agent with a step and token budget.
  • Add a two-phase mutating tool with confirmation.
  • Produce a trace tree and a cost report for a sample run.
  • Write an eval suite covering tool misuse and prompt injection.

Chapters used: 6, 7, 8, 9, 20, 21.

Capstone brief C — Local and offline assistant

Goal: Deliver a useful AI feature that runs without a cloud call.

  • Assemble a local stack: runtime, open-weight model, embeddings, vector store.
  • Add guardrails and PII redaction locally.
  • Trace runs with a self-hosted observability tool.
  • Benchmark quality, latency, and memory against a small eval set.
  • Explain where you would escalate to the cloud and why.

Chapters used: 22, 23, 24, 25.

Capstone brief D — Routing and cost optimisation

Goal: Reduce the cost of an AI feature without hurting quality.

  • Instrument token use by prompt, history, retrieval, tools, and output.
  • Add a cheap-first cascade with a calibrated acceptance test.
  • Introduce a stable prompt prefix and measure caching effects.
  • Compare quality against a strong-model baseline using pairwise eval.
  • Report the blended cost per request and the escalation rate.

Chapters used: 3, 21, 23, 27.

Capstone brief E — Reusable assistant workflow

Goal: Create a rules-and-skills kit that makes an AI coding assistant genuinely useful on a real repository.

  • Write a concise project rules file with verification commands.
  • Define two skills for recurring tasks with clear definitions of done.
  • Design a plan–implement–test–review workflow with one human checkpoint.
  • Measure time and token savings against an unstructured baseline.
  • Version the kit and document how to improve it.

Chapters used: 26, 27, and the evaluation habits of Part IV.

Adjust the timeline to your schedule, but keep the order. It is always easier to add sophistication to a working system than to finish a system that was over-engineered from the start.

Final checklist

  • I can explain what my system does in one sentence.
  • I know which layer each component belongs to.
  • I can show a trace of a real run.
  • I have an eval suite with pass criteria and documented failures.
  • I have set budgets and know the cost per request.
  • I have limited tool permissions and added approval where needed.
  • I have documented what I would do next.

Where to go from here

The field will keep changing. Frameworks will be renamed, models will improve, and new protocols will appear. The durable skills are the ones this book has emphasised: thinking in layers, measuring distributions, bounding autonomy, controlling cost, and explaining trade-offs. Carry those with you and you will be able to evaluate any new tool on its merits rather than chasing it.

Return to the event chapters when you want a reminder of how these ideas were presented on stage, and to the workshop chapter when you want to build something with your hands. The gap between understanding and ability is closed one small experiment at a time.

Case study: shipping the routing capstone in thirty days

The 30-day plan above is a template; this walkthrough makes it concrete with capstone D, the cost-optimisation project. The goal is to cut the cost of a support-answer feature without degrading quality. The learner sets a target before writing code: reduce blended cost per request by at least 40% while keeping groundedness within two percentage points of the strong-model baseline.

Days 1–3 — Frame and measure

The one-page brief names the baseline model, the eval set of 120 questions, and the two metrics. Instrumentation is added first, because you cannot optimise what you do not measure. The first measurement shows an average of 9,800 tokens per request and a strong-model cost of about 12 cents each — roughly $2,400 a month at 20,000 requests.

Two details make this baseline usable later. The 120 questions are frozen before any optimisation begins, so later scores are comparable; changing the eval set mid-project would make improvement impossible to interpret. And the baseline run is saved in full, including its per-request token breakdown and its failures, so the learner can explain not just that the new system is cheaper but exactly which decisions produced the saving. A baseline you cannot replay is a number you cannot defend.

Days 4–10 — Build the simplest version

A cheap-first cascade is implemented: a small model answers first, and a calibrated acceptance test decides whether to escalate. The acceptance test is deliberately conservative at first, so quality holds while the learner gathers data. A config makes the thresholds explicit and reviewable:

router:
  cheap_model: small-v1
  strong_model: large-v1
  max_cheap_tokens: 600
  escalate_if_confidence_below: 0.80
  escalate_if_no_citations: true

Days 11–17 — Evaluate honestly

The eval harness compares the cascade to the strong baseline pairwise. Early results show a 55% escalation rate — cost savings are only 18%, short of target. The learner inspects failures and finds the confidence threshold is miscalibrated: many correct cheap answers score below 0.80. Recalibrating on a held-out set lowers escalation to 28% with groundedness just 1.4 points below baseline.

Days 18–27 — Harden and optimise

A stable prompt prefix is introduced, and cached-prefix billing is measured. Budgets are set per feature with an 80% alert. Tracing records which model answered each request, so escalation can be monitored in production. Blended cost settles near 6.8 cents per request — a 43% reduction — meeting the target.

Days 28–30 — Write it up

The final README states the goal, the architecture, the before and after numbers, and three failure cases, including the miscalibrated threshold. That honest failure note is the most valuable paragraph: it shows judgement, not just a successful metric.

Keep the baseline visible. Pin the original strong-model run and its cost in the README alongside the optimised result. Reviewers should be able to see both columns and the exact conditions under which each was measured; a claim without a baseline is just an opinion.

Design decisions for capstone scope

Most capstones fail on scope, not difficulty. The briefs above are deliberately bounded; the decisions below help you keep them that way.

DecisionWhy it mattersGuidance
Pick one brief and one domainTrying to cover all five themes produces five shallow demos and no evidence of depth.Choose the brief that excites you and apply it to a domain you understand.
Measure a baseline firstWithout a starting number you cannot claim improvement or detect regressions.Record cost, quality, and latency before you change anything.
Build the smallest working version before adding safetyOver-engineering a system that does not yet work wastes days.Follow the plan's order: demo, eval, then guardrails and budgets.
Document failures, not just successesA flawless report looks rehearsed; honest failures demonstrate judgement.Keep three real failure cases and the fix or mitigation for each.
Set budgets and alerts earlyDiscovering cost after the invoice is too late to control it.Add per-feature caps and an 80% alert from the first working version.
Write the README as you goA write-up assembled at the end omits decisions you have already forgotten.Keep a short log of decisions and measurements throughout.

A capstone is judged on the clarity of its reasoning, not the number of frameworks it uses. A small system that you can explain, measure, and criticise beats an ambitious one you cannot defend.

Scope is a feature you can change. If you reach day ten without a working demo, cut a feature rather than extending the deadline. A narrowed project that is finished and measured teaches more, and demonstrates more discipline, than a sprawling one that never reaches the evaluation stage.

Review questions: capstone planning

Use these before you start building. Honest answers here will save you days of rework later.

  1. State your capstone's goal in one sentence, then name the single measurement that would tell you whether you succeeded.
  2. Which chapters are genuinely required for your brief, and which are optional? Justify the cut.
  3. Describe the first working demo you will aim for in four to ten days, and the feature you will deliberately leave out.
  4. How will you know your eval suite is telling the truth rather than rewarding a shortcut?
  5. What is one limitation you will volunteer in your write-up, and why does naming it strengthen the project?

Summary

  • Five capstone briefs turn the book's themes into portfolio projects.
  • Each capstone demands evaluation, failure documentation, and cost awareness.
  • A 30-day plan moves from a brief to a shared write-up in stages.
  • The final checklist is a definition of done for an AI project.
  • Durable skills — layers, measurement, bounded autonomy, cost, trade-offs — outlast any framework.
