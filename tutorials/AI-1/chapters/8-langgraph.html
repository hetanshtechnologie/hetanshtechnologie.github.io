8. LangGraph Deep Dive

Why a graph

LangGraph models an agent as a state machine. You define a state shape, a set of nodes that transform that state, and edges that decide which node runs next. The model's output is one input to those decisions, but it is not the only one. This makes control flow explicit: you can look at a graph and see every possible path, including loops and human checkpoints.

The graph abstraction is valuable when reliability matters. If a tool fails, you can route to a recovery node. If a confidence score is low, you can route to a clarification node. If an approval is required, you can pause and resume. None of that requires inventing a new prompt; it requires an edge.

Core concepts

ConceptRole
StateA typed object passed between nodes. Every node reads and returns updates.
NodeA function that does work: call a model, run a tool, transform data.
EdgeA transition. Conditional edges inspect state and choose the next node.
START / ENDVirtual entry and exit points of the graph.
CheckpointerPersists state after each step, enabling memory and resume.
ThreadAn identifier for one conversation or one long-running task.

Building a first graph

A minimal graph has one node that calls a model and writes the response into state. In TypeScript-like pseudocode:

const State = z.object({
  messages: z.array(Message),
  next: z.enum(['agent','end']).default('agent')
});

const graph = new StateGraph(State)
  .addNode('agent', async (state) => {
      const reply = await model.invoke(state.messages);
      return { messages: [...state.messages, reply] };
  })
  .addEdge(START, 'agent')
  .addConditionalEdges('agent', (s) => s.next === 'end' ? END : 'agent')
  .compile({ checkpointer });

The important part is not the syntax. It is that next is part of state and can be computed from a schema, a policy check, or a model decision. The graph does not care which. That is why graphs are a good home for hybrid autonomy.

Nodes should be small and testable

Resist the temptation to build one giant node that does retrieval, reasoning, and tool execution. Split nodes by responsibility: retrieve, decide, execute, observe, summarise. Small nodes are easier to unit test, easier to trace, and easier to reroute. They also make evaluation precise: you can measure retrieval quality without running the whole agent.

Each node should be pure enough to reason about: given this state, it produces that update and a set of side effects. Side effects such as sending an email still happen, but they are isolated in a node whose contract you can audit.

Conditional edges and loops

Conditional edges are where policy lives. A typical agent graph has a loop between call_model and execute_tools. The condition examines the last message: if it contains tool calls, go to execution; otherwise finish. Add guards for step count and budget. Without them, a confused model can loop indefinitely.

function shouldContinue(state) {
  if (state.steps >= MAX_STEPS) return 'finish';
  if (state.spend >= BUDGET) return 'finish';
  if (lastMessageHasToolCalls(state.messages)) return 'tools';
  if (needsApproval(state)) return 'approve';
  return 'finish';
}

This function is ordinary code. You can unit test it, log its decisions, and change it without touching the model. That is the central benefit of graph-based orchestration.

Checkpointers and threads

A checkpointer stores state snapshots keyed by a thread ID. This gives you conversational memory across sessions, but also much more: the ability to inspect a past step, replay a trace in evaluation, or resume after a process restart. Choose a checkpointer that matches your durability needs — in-memory for experiments, a database for production.

Thread ID discipline matters. Reusing a thread across unrelated tasks mixes contexts; creating a new thread for every message destroys continuity. A common convention is one thread per user session for chat, and one thread per work item for background tasks.

Human checkpoints in a graph

To pause for approval, route to a node that records a pending action and then ends the current invocation. When the approval arrives, a new invocation resumes from the saved state with the approval written in. This pattern requires an external store for the pending action and an ID that links approval to thread. It is more work than a synchronous form, but it survives restarts and gives you a clean audit trail.

Streaming and observability

Long graphs should stream progress: node entered, node completed, tool called, state delta. Users tolerate waiting much better when they can see what is happening. Streaming also helps debugging: a stuck node is obvious. Emit structured events with thread ID, node name, step number, and latency. Feed those events into your tracing system.

Testing tip. Replace the model node with a deterministic stub in unit tests. Feed it scripted responses to force every branch of your graph, including error and approval paths. This is how you test control flow without burning tokens.

When to choose LangGraph

  • You need explicit, inspectable control flow with loops and branches.
  • You need durable state, pause/resume, or trace replay.
  • You want to mix deterministic policy code with model decisions.
  • You are comfortable defining state and edges rather than relying on conventions.

If your task is a single model call with no memory, a graph is unnecessary ceremony. Start simple and introduce a graph when you need the control it provides.

A worked example: a document-review graph with a durable pause

To see why graphs earn their keep, build a review workflow that must survive restarts. A legal team submits contract drafts for review. The system retrieves similar clauses, drafts a redline, critiques it against a rubric, revises once if needed, and pauses for a human approver before sending. Approvals may arrive hours later, after the process that started the job has exited.

Step 1: define the state. The state object holds the draft text, retrieved clauses, critique scores, a revision count, an approval field, and a step counter. Each field is typed. Because everything the graph needs lives in state, a snapshot is a complete description of the job — there is no hidden local variable to lose.

Step 2: split the nodes. There are six: retrieve, draft, critique, revise, approve, and send. The model is called only in draft, critique, and revise. Retrieval and sending are ordinary code. Small nodes mean you can test retrieval quality without calling a model at all.

Step 3: write the conditional edges. After critique, a function reads the critique scores. If every rubric item scores at least 4 out of 5, go to approve. Otherwise, if the revision count is below 2, go to revise; if it is 2 or more, go to approve with a warning flag rather than looping forever. The approve node records a pending action and ends the invocation. When the reviewer responds, a new invocation resumes from the saved thread with the approval written in.

Step 4: pick the checkpointer. Experiments use an in-memory checkpointer. Production uses a database-backed one so snapshots survive a restart. The thread id is the contract id, which gives one thread per work item — reusing it for unrelated drafts would mix contexts.

Step 5: guard and observe. A step limit of 20 and a token budget of 40,000 are checked in every conditional edge. Each node emits a structured event with thread id, node name, step number, and latency. In a two-week trial, 62% of drafts pass critique first time, 31% after one revision, and 7% go to approval with a warning — numbers that would be invisible without explicit state.

State = { draft, clauses[], critique{clarity,citations,tone},
          revisions:int, approval:pending|approved|rejected,
          steps:int, spend:int }
edges:
  START -> retrieve -> draft -> critique
  critique -- min(scores)>=4 --> approve
  critique -- revisions<2 --> revise -> critique
  critique -- else --> approve(warn=true)
  approve -- pending --> END        # wait for external event
  resume -- approved --> send --> END
  resume -- rejected --> revise
checkpointer: DB-backed   thread_id: contract_id
guards: steps < 20 | spend < 40000 tokens

The pause is the important part. It is not a form displayed by the UI; it is a node that ends an invocation and relies on a saved snapshot. That is why an approval arriving the next morning can resume exactly where the graph stopped.

Graph design pitfalls

Graphs make control flow explicit, but they do not automatically make it correct. These mistakes show up in real implementations.

MistakeWhy it hurtsBetter practice
One giant node doing retrieve, reason, and actHard to test, trace, or reroute; a failure is difficult to localise.Split by responsibility and keep side effects isolated.
Putting control decisions only in the modelBranches become untestable and unpredictable.Compute routing in ordinary functions that read state.
Loops without step or budget guardsA confused model can run for minutes and spend heavily.Check limits in every conditional edge and emit a metric on exit.
In-memory checkpointer in productionState vanishes on restart; paused approvals are lost.Use a durable store and test a resume after process death.
Reusing a thread for unrelated tasksContexts bleed into each other and replay becomes meaningless.Adopt a clear convention: one thread per session or work item.
Testing only the happy pathError and approval branches rot silently.Use a deterministic stub model to force every branch in unit tests.

A final trade-off: a graph adds ceremony. If your task is one model call with no memory and no tools, a state machine is unnecessary. Introduce a graph when you need explicit branches, durable state, pause and resume, or precise evaluation of intermediate steps — not because it looks sophisticated.

Test the edges, not just the nodes. Conditional-edge functions are ordinary code. Feed them crafted states in unit tests to hit every branch, including budget exhaustion and approval rejection, before you ever call a model.

Summary

  • LangGraph represents an agent as a typed state machine.
  • Nodes do work; conditional edges encode policy and control flow.
  • Checkpointers and threads provide memory, replay, and resume.
  • Small nodes make testing and evaluation precise.
  • Always guard loops with step and budget limits.
