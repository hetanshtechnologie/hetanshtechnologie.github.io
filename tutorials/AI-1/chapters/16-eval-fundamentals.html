16. Evaluation Fundamentals: Why Demos Lie

The demo trap

A demo succeeds when one carefully chosen input produces one impressive output. A production system must succeed across a distribution of inputs, over time, after changes, and under adversarial conditions. Evaluation is the discipline of measuring that distribution rather than admiring a single example.

This is why an agent can pass its evals and still fail in production. The eval set may not represent real traffic. It may contain easier cases. It may reward surface features — confident tone, correct format — while missing deeper failures such as wrong tool choice or unsupported claims. A passing eval is evidence under a specific distribution, not proof of correctness.

Evaluation is a distribution problem

Classic software testing assumes deterministic functions and known-correct answers. Given input X, the output should equal Y. Agent systems violate both assumptions: the same input can produce different outputs, and often no single Y exists. Instead of asking "did it return the expected string?", we ask "what fraction of runs satisfy these properties, and how confident are we about that fraction?"

That shift has practical consequences. You need repeated trials for non-deterministic cases. You need confidence intervals, not just percentages. You need to stratify results by input category so a strong average does not hide a weak segment. And you need to evaluate trajectories, not only final answers.

What to evaluate

DimensionExample question
Answer qualityIs the final response correct and complete?
GroundednessAre claims supported by retrieved evidence?
Tool behaviourWere the right tools called with valid arguments?
Control flowDid the agent take a reasonable path without loops?
SafetyWere permissions and policies respected?
EfficiencyTokens, latency, and tool calls within budget?
RobustnessDoes it degrade gracefully on odd or adversarial inputs?

Most teams start with answer quality and stop there. That is a mistake. A wrong tool call can produce a correct-looking answer for the wrong user. A safe-looking answer can hide an unauthorised side effect. Evaluate the whole trajectory.

Building an eval set without golden data

You do not need a hand-labelled dataset of thousands of examples. Useful sets can be bootstrapped from several sources:

  • Production traces — sample real requests, anonymise them, and review a small set.
  • Model disagreement — run two models or two prompts and inspect cases where they differ; these are often informative boundaries.
  • Generated variations — paraphrase known cases, add typos, change formatting, and translate.
  • Failure reports — every user-reported bug becomes a permanent regression case.
  • Adversarial probes — prompt injection, conflicting instructions, missing evidence, and ambiguous requests.

Fifty well-chosen cases beat five hundred random ones. Cover the main intents, the known failure modes, edge cases, and explicit no-answer scenarios.

Assertions before judges

Start with checks that can be computed exactly. Did the output parse as JSON? Is the cited source in the allowed set? Was the tool name on the allowlist? Did the agent stay under ten steps? Are all required fields present? These assertions are cheap, deterministic, and catch a large share of regressions.

Only after exhausting deterministic checks should you introduce an LLM as judge. A judge is an instrument with its own error profile; it must be calibrated, as we will see in Chapter 17.

Pass criteria and thresholds

Define what "good" means before you run the suite. For a support assistant: groundedness at least 0.9, no unauthorised tool calls, abstention on all no-answer cases, median latency under four seconds, p95 token spend under a budget. Thresholds should be tied to product requirements, not rounded numbers that look nice.

Small-sample caution. If you have twenty cases, a single failure moves the score by five percentage points. Report counts alongside percentages and avoid declaring victory over a one-point change.

A failure taxonomy

When an eval fails, categorise the failure. Useful categories include retrieval miss, wrong tool, malformed arguments, hallucinated claim, instruction drift, loop, timeout, policy violation, and format error. A taxonomy turns a list of failures into a map of system weaknesses. It also prevents the common pattern of fixing every failure by rewriting the system prompt.

Evals as communication

An eval suite encodes what the team values. If the suite rewards short answers, the system will become short. If it rewards citation coverage, the system will cite more. Make those values explicit and revisit them with product and legal stakeholders. Evaluation is not a purely technical activity.

A worked example: evaluating a support assistant

A team is about to ship a support assistant that answers questions from a knowledge base and never invents policy. Before launch, they need an eval suite that would actually catch a bad change. We will build one around a distribution of forty cases, deterministic assertions, a failure taxonomy, and thresholds tied to product requirements — not to round numbers.

Constructing the set

The forty cases are allocated deliberately: twelve cover the three most common intents (four each), eight cover edge cases such as typos and unusual formatting, eight are adversarial probes including prompt injection and conflicting instructions, six are no-answer cases where the knowledge base has no relevant document, and six come from past user-reported failures. Every reported bug becomes a permanent regression case, so the set grows over time. Cases are labelled by category, which lets us stratify results instead of hiding a weak segment behind a strong average.

{
  "id": "na_04", "category": "no_answer",
  "input": "What is our refund window for gift cards in Brazil?",
  "evidence_available": false,
  "assertions": ["abstain=true", "no_policy_claim=true"],
  "expected_tool_calls": ["search_kb"]
}

Assertions before judges

For each case we define checks that can be computed exactly. Did the output parse as expected? Is every cited source in the allowed set? Was the tool name on the allowlist? Did the agent abstain on no-answer cases? Did it stay under ten steps and four tool calls? These assertions are cheap, deterministic, and catch a surprising share of regressions. Only after exhausting them would we add an LLM judge for answer quality, and that judge would itself need calibration — the subject of the next chapter. Because the agent is non-deterministic, each case runs three times; we report the fraction of passing trials with a confidence interval rather than a single percentage.

thresholds = {
    "groundedness": 0.90,       # at least 90% of trials
    "abstention_no_answer": 1.00,
    "unauthorised_tool_calls": 0,
    "median_latency_ms": 4000,
    "p95_tokens": 1200
}

With forty cases run three times, a single failing trial shifts a rate by less than one percentage point. We report counts alongside percentages and refuse to celebrate a one-point improvement that could be noise.

Stratification is where distribution thinking pays off. Suppose the overall pass rate is 0.92, which looks healthy, but the no-answer segment passes at 0.60. A single headline number would have hidden a serious tendency to invent policy when evidence is missing. We report each category separately and set a threshold for the weakest segment, not just the mean. We also keep the set frozen during a comparison: if you add new cases at the same time you change a prompt, you cannot tell which change moved the score. New failure cases are appended with a date, and older results are recomputed on the full set before a release decision.

Failure taxonomy and thresholds

When the suite fails, each failure is tagged: retrieval miss, wrong tool, malformed arguments, hallucinated claim, instruction drift, loop, timeout, policy violation, or format error. In the first run, twelve failures break down as five retrieval misses, three hallucinated claims on no-answer cases, two wrong-tool calls, and two format errors. That map directs fixes to the right layer: improve retrieval for the first group, tighten the abstention instruction for the second, rewrite tool descriptions for the third, and add schema enforcement for the fourth. The tempting alternative — rewriting the system prompt for all twelve — would fix almost nothing. Thresholds come from product requirements: legal requires zero unauthorised actions, support requires a four-second median response, and finance caps token spend. A passing eval is evidence under this distribution, not proof of correctness on all traffic.

Summary

  • Demos show one point; evaluation measures a distribution.
  • Evaluate answer quality, trajectory, safety, and efficiency.
  • Build small, diverse sets from traces, disagreements, and failures.
  • Use deterministic assertions before LLM judges.
  • A failure taxonomy directs fixes to the right layer.
