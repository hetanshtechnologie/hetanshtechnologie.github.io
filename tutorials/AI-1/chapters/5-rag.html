5. Retrieval-Augmented Generation

Why retrieval exists

A model's parameters are a compressed, outdated snapshot of the internet. They do not contain your private documents, yesterday's policy change, or the customer record in your database. Fine-tuning can change style and embed knowledge, but it is slow and expensive to keep current. Retrieval-augmented generation solves this by looking up relevant material at request time and placing it in the context window.

RAG is often described as "search plus prompt". That is accurate but incomplete. A good RAG system is a pipeline with measurable quality at each stage. If the answer is wrong, you need to know whether retrieval failed to find the evidence, found it but ranked it low, or the model misread the evidence it was given.

The pipeline, stage by stage

  1. Ingest — collect documents from sources, track versions, handle deletions.
  2. Parse — extract clean text from PDFs, HTML, wikis, and scanned pages.
  3. Chunk — split text into passages small enough to be useful and large enough to be meaningful.
  4. Embed — convert each chunk into a vector using an embedding model.
  5. Index — store vectors plus metadata in a vector store or search engine.
  6. Retrieve — find candidate chunks for a query, often combining keyword and vector search.
  7. Rerank — reorder candidates with a stronger model or cross-encoder.
  8. Compose — place selected chunks into the prompt with labels and source identifiers.
  9. Generate — produce an answer that cites the evidence used.

Every arrow in that list is a place to add evaluation. Retrieval quality is usually the dominant factor in answer quality, yet most teams spend their time tuning the final prompt. Start with retrieval.

Chunking is a design decision

Chunks should align with semantic boundaries: paragraphs, sections, or logical units. A fixed 500-token split that cuts a table in half will produce bad retrieval no matter how good the embedding model is. Practical guidance:

  • Prefer structure-aware splitting based on headings and paragraphs.
  • Add a small overlap between chunks so context is not lost at boundaries.
  • Store metadata: source, title, section, effective date, access level.
  • Keep a parent–child relationship so a retrieved sentence can be expanded to its full section.
  • Index summaries for long documents and link them to detailed chunks.
Access control belongs in retrieval. If a user cannot read a document, that document must never be a retrieval candidate. Filter by permission at query time, not after generation.

Embeddings and similarity

An embedding model maps text to a vector such that semantically similar text lands nearby. Retrieval computes a similarity score between the query vector and stored vectors. Cosine similarity is common. This works well for paraphrases and conceptual matches, but poorly for exact identifiers, error codes, and rare names. That is why hybrid retrieval matters.

MethodStrong atWeak at
Vector searchMeaning, paraphrase, conceptual similarityExact tokens, numbers, acronyms
Keyword / BM25Exact terms, codes, namesSynonyms and conceptual queries
HybridCovering both casesRequires score fusion tuning
RerankingPrecision on the shortlistCost and latency on large candidate sets

Reranking and context composition

A first-stage retriever optimises recall: give me twenty plausible chunks. A reranker optimises precision: which three actually answer the question? Cross-encoders and LLM-based rerankers are slower but much more accurate than vector similarity alone. A common pattern is to retrieve 30 candidates with hybrid search, rerank to 5, and place those 5 in the prompt.

Composition matters as much as selection. Label each chunk with its source and order it by relevance. Ask the model to cite source identifiers. If two chunks contradict each other, include both and instruct the model to surface the conflict rather than silently choosing one. This turns a failure into a useful answer.

Evaluating RAG

Measure the stages separately. Useful metrics include:

  • Recall@k — did the correct chunk appear in the top k results?
  • Precision@k — how much of the retrieved context was relevant?
  • Faithfulness — is every claim in the answer supported by the supplied context?
  • Answer relevance — does the answer actually address the question?
  • Abstention rate — does the system say "I don't know" when evidence is missing?

Build a small labelled set of query–source pairs. You do not need thousands. Fifty carefully chosen queries, including adversarial and no-answer cases, will reveal more than a large random sample. Chapters 16 and 17 show how to expand this into a full harness.

Freshness and deletion

RAG systems rot quietly. Source documents change, pages are removed, and permissions are revoked. Your index must support updates and deletions, and deletion must be verifiable. Track a content hash or version for every chunk. On re-ingest, replace changed chunks and remove missing ones. Log the index version with each answer so you can reproduce a result.

Common RAG anti-patterns

  • Embedding entire documents as single vectors and wondering why retrieval is vague.
  • Using the same embedding model for indexing and querying without checking that it is symmetric.
  • Retrieving ten chunks and stuffing all of them into context "just in case".
  • Allowing retrieved text to contain instructions the model might follow.
  • Celebrating answer quality while never measuring retrieval quality.

A worked example: a policy-search assistant

Imagine an internal assistant that answers questions from 1,200 HR policy documents. The team has 60 days, a corpus that changes weekly, and a requirement that every answer cite a document and section. They decide to build the pipeline stage by stage and measure each one before moving on.

Ingest and parse. Documents arrive as PDFs and wiki pages. Parsing yields clean text plus metadata: source id, title, section path, effective date, and access level. About 5% of pages are scans and need OCR; the team flags those for manual review rather than trusting the output silently.

Chunk. A first attempt uses fixed 500-token windows with 50-token overlap. On 40 test questions, recall@5 is 71%. Switching to heading-aware chunks averaging 320 tokens raises recall@5 to 86%, because policy tables and numbered clauses stay intact. They keep a parent–child link so a matched sentence can be expanded to its full section at composition time.

Retrieve and rerank. Hybrid search combines BM25 and vector similarity. On exact-code queries such as "form HR-42", BM25 alone finds the right chunk; on paraphrases like "can I work from a café abroad", the vector side wins. The team fuses the two lists with reciprocal rank fusion, takes the top 30, and reranks to 5 with a cross-encoder. Reranking lifts precision@5 from 0.6 to 0.82 and adds about 180 ms.

Compose and generate. Each of the five chunks is labelled with source id, section, and effective date. The system prompt instructs the model to cite these identifiers and to surface contradictions rather than silently choosing one. A retrieval score threshold of 0.72 causes the system to abstain when no strong evidence exists, which cuts invented answers on the no-answer test set from 22% to 3%.

Freshness. Every chunk carries a content hash. A weekly job re-ingests sources, replaces changed chunks, deletes missing ones, and records an index version. Answers log that version, so a stale result from last month can be reproduced during an investigation.

The configuration fits in a short block:

corpus: 1200 docs | weekly refresh | hash-based diff
chunk: heading-aware, avg 320tok, overlap 40tok
retrieve: hybrid(BM25 + vector), rrf_k=60, top 30
rerank: cross-encoder -> top 5, +180ms
threshold: score < 0.72 -> abstain
compose: label(source_id, section, effective_date)
eval: recall@5 0.86 | precision@5 0.82 | faithfulness 0.93

The numbers tell a story: most of the gain came from chunking and hybrid retrieval, not from the final prompt. That is typical, and it is why this chapter insists on measuring stages separately. A team that only tunes the prompt would have missed both improvements entirely.

Retrieval design trade-offs

Every retrieval decision buys one property at the cost of another. Naming the trade-off out loud makes the choice reviewable.

Trade-offWhy it is temptingWhat to consider instead
Smaller chunksSharper similarity scores and less irrelevant text.Too small and the answer loses its surrounding context; keep a parent–child link.
More chunks in contextFeels safer because "the answer is probably in there somewhere".Extra chunks dilute attention and raise cost; rerank to a few and measure precision.
Vector search onlySimple to build and handles paraphrases well.Fails on exact codes and names; add BM25 for hybrid coverage.
Filtering permissions after generationEasier to implement as a final check.Too late — the restricted text already entered the prompt; filter at query time.
Skipping deletion trackingRe-ingest seems sufficient as long as new documents are added.Deleted or revoked documents persist silently; verify deletion with content hashes.

Freshness deserves the same scrutiny as accuracy. A retrieval system that was correct last quarter can be quietly wrong today if a policy was replaced and the old chunk was never removed. Schedule a weekly reconciliation job that compares source hashes against the index, and alert on unexpected additions, deletions, or unchanged sources that should have changed. Record the index version with each answer so a reported error can be reproduced against the exact corpus state that produced it. Without that record, a complaint that "the assistant quoted the old rule" is nearly impossible to investigate.

One more subtlety: retrieved text is untrusted data, not instruction. Delimit it and label it, but do not imagine that delimiters are a security boundary. Real protection lives in tool permissions and output checks, which are covered in later chapters.

Measure the retriever first. If retrieval recall is 70%, no prompt can lift answer accuracy beyond that ceiling. Fix the ceiling before polishing the sentence that sits on top of it.

Questions to test your pipeline thinking

Use these as a self-check on RAG design. Try to answer each from memory before looking back.

  1. A user asks about error code "E-4471" and retrieval returns unrelated text. Which search method would you add, and why does vector similarity struggle here?
  2. Explain why recall@5 and faithfulness can move in opposite directions when you change chunk size.
  3. Why must access-level filtering happen before generation rather than after it? What is the consequence of getting this wrong?
  4. Your index contains a document that was legally deleted last month. Name two mechanisms that should have prevented this and one log field that would help you investigate.
  5. Give a scenario where surfacing a contradiction between two retrieved chunks is more useful than silently choosing one.

Summary

  • RAG supplies fresh, private evidence at request time.
  • Chunking, metadata, and access filtering determine retrieval quality.
  • Hybrid search plus reranking usually beats vector search alone.
  • Evaluate retrieval and generation separately.
  • Freshness and deletion are operational requirements, not optional polish.
