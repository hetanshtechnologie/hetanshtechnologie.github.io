15. Production Integration Patterns

Agents do not live alone

An agent is rarely the whole application. It sits inside a product with authentication, databases, queues, webhooks, monitoring, and business processes. The integration patterns you choose determine whether the agent behaves like a well-behaved service or a unpredictable script that occasionally locks a table.

This chapter collects the patterns that recur in production systems: synchronous request–response, background jobs, event-driven triggers, streaming interfaces, and identity propagation. The goal is not to prescribe one architecture but to help you match the pattern to the workload.

Pattern 1: synchronous request–response

The simplest integration is an HTTP request that waits for the agent's final answer. It works for short tasks with predictable latency: classification, extraction, simple Q&A. Its weakness is long agent loops. A user-facing request that can take two minutes needs timeouts, progress streaming, and a fallback message.

Set a hard deadline at the gateway, a shorter deadline inside the agent, and a separate timeout for each tool. When the deadline approaches, return a partial result with a clear status rather than a generic error. Users forgive "still working" far more than a spinner that dies.

Pattern 2: background jobs

For tasks that can take minutes — report generation, bulk analysis, multi-step research — put the agent behind a queue. The API accepts the request, returns a job ID, and a worker performs the work. State is persisted after each step so the job can resume after a failure.

  • Store the input, agent version, and prompt version with the job.
  • Write checkpoints after each node or tool call.
  • Make workers idempotent using a job ID and step number.
  • Emit progress events that the UI can display.
  • Define a dead-letter path for jobs that fail repeatedly.

This pattern also makes evaluation easier: a completed job is a complete trace you can replay.

Pattern 3: event-driven triggers

Some agents should react to the world: a new support ticket, a failed deployment, a changed document. An event bus decouples the producer from the agent. The agent subscribes to relevant events, performs its work, and publishes resulting events.

Event-driven agents need careful idempotency because events may be delivered more than once. Include an event ID in your processing record and skip duplicates. Also define ordering assumptions explicitly; if two events about the same entity arrive out of order, the agent should not produce conflicting actions.

Pattern 4: streaming interfaces

Streaming improves perceived latency and gives users visibility. Stream not only final tokens but structured progress: "searching knowledge base", "found 5 sources", "drafting answer", "awaiting approval". This is especially valuable for long agent runs where silence feels like failure.

Be careful about what you stream. Intermediate reasoning may contain sensitive details or misleading half-conclusions. Many teams stream tool statuses and final answer tokens, but keep internal reasoning private. Choose deliberately.

Identity and permission propagation

The agent should act with the permissions of the user who invoked it, or with an explicitly defined service identity. There is no third acceptable option. If the agent uses a powerful shared credential, every user effectively gains that credential's reach.

Propagation rule. Pass a signed user context into tool calls and validate it at the tool boundary. Never accept a user ID or role from model-generated text.

For background jobs, the invoking user's identity must be captured at submission time and carried through the job. If permissions can change while the job runs, re-check before mutating actions. A user who lost access halfway through a long task should not have data written on their behalf afterwards.

Data boundaries

Define what data may enter the model context. Even with a trusted provider, sending unnecessary customer data increases risk and cost. Redact where possible, retrieve only the minimum needed, and keep raw records behind resource references. If a tool returns a full record, summarise it before placing it in context.

Retention rules should cover traces as well as primary data. A trace that contains prompts, tool arguments, and outputs can be as sensitive as the database itself. Apply the same access controls and deletion policies.

Deployment topology

A typical production topology includes an API gateway, an orchestration service, a model gateway or provider client, tool servers, a state store, a vector store, and an observability backend. Each boundary should have a clear contract and a failure mode you can describe.

Model gateways are worth considering even when you use one provider. They give you a single place to enforce budgets, log prompts, route between models, and swap providers. The same logic applies to tool gateways: centralised policy is easier to audit than policy scattered across dozens of agents.

Change management

Agent systems change in more ways than ordinary software: model versions, prompt versions, tool schemas, retrieval indexes, and policies. Treat each as a deployable artefact with a version number. Record all of them in every trace. When behaviour changes, you can identify which dimension moved.

Rollouts should be gradual. Canary a new prompt or model for a small share of traffic and compare eval metrics and production signals. Chapter 18 covers canaries and drift detection in detail.

A worked example: an invoice-processing service

A finance team receives thousands of supplier invoices as email attachments. They want an assistant that classifies each invoice, extracts line items, checks them against a purchase-order system, and flags mismatches for a human. Some steps are quick, some take minutes, and the whole flow must act with the permissions of the department that submitted the invoice. One architecture will not fit every step, so we combine four patterns deliberately.

Mapping steps to patterns

Classification — "is this an invoice, a receipt, or something else?" — is short and predictable, so it runs as a synchronous request–response call at the API edge with a two-second deadline. Extraction and purchase-order matching can take a minute or more, so those run as a background job: the API returns a job ID, a worker performs the steps, and progress events stream to the UI. When a mismatch is found, the worker publishes an invoice.flagged event to a bus; a separate approval agent subscribes to that event. This decoupling means the approval agent does not need to know anything about the extraction worker.

{
  "job_id": "inv_4471", "tenant": "finance-eu",
  "steps": ["classify", "extract", "match_po", "flag"],
  "checkpoint": "match_po", "agent_version": "3.2.1",
  "prompt_version": "extract-1.4", "invoker_id": "usr_981"
}

The stored job record captures versions and the invoking user. That matters for two reasons: a completed job becomes a replayable trace for evaluation, and if permissions change mid-run we can re-check invoker_id before any mutating action.

Identity and streaming

The agent acts with the submitting user's identity, captured at submission time and carried in a signed context. Tool calls validate that context at the boundary; no user ID or role is ever taken from model-generated text. Before the worker writes a flag to the purchase-order system, it re-checks that the user still has the invoice.write scope — a user whose access was revoked during a long job must not have data written on their behalf. The UI streams structured progress — "extracting line items", "matched against PO", "mismatch found" — but never internal reasoning. Tool statuses and final tokens are safe to show; intermediate thoughts may contain sensitive details or misleading half-conclusions.

def write_flag(job, ctx):
    if not permissions.has(ctx.user_id, "invoice.write"):
        return dead_letter(job, reason="permission_revoked")
    po_client.post_flag(job.mismatch, idempotency_key=job.job_id)

The dead-letter path is deliberate. A job that fails repeatedly because of a revoked permission should not spin; it goes to a queue a human can inspect. Because events may be delivered more than once, the approval agent also records each invoice.flagged event ID and skips duplicates.

Data boundaries are part of this topology too. The extractor sees the raw invoice, but only the minimum fields needed for matching enter the model context; the full document stays behind a reference in the state store. Traces are treated as sensitive data because they contain prompts, tool arguments, and outputs, so they inherit the same access controls and deletion policy as the invoices themselves. A model gateway enforces budgets centrally, while a tool gateway centralises policy for the extraction and purchase-order servers — one place to audit rather than rules scattered across agents.

Topology and change management

The deployed topology has an API gateway, the orchestration service, a model gateway, tool servers for extraction and purchase-order access, a state store, an event bus, and an observability backend. The model gateway gives us one place to enforce budgets and route between models. We canary each new prompt version for five percent of invoices and compare eval metrics against the current version before widening the rollout. Because model, prompt, tool schema, and policy versions are all recorded in the job record, any behaviour change can be traced to the dimension that moved.

Summary

  • Match integration pattern to latency and durability needs.
  • Background jobs need idempotency, checkpoints, and dead-letter paths.
  • Event-driven agents must handle duplicates and ordering.
  • Act with the invoking user's identity or a deliberate service identity.
  • Version models, prompts, tools, indexes, and policies together in traces.
