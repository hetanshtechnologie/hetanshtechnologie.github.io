26. AI Skills, Rules, and Workflows for Claude Code and Cursor

From chatting to engineering your workflow

Most developers start with AI coding assistants by typing questions into a chat panel. That works, but it leaves the biggest gains on the table. The real productivity jump comes when you treat the assistant as a programmable teammate: you give it persistent rules, reusable skills, and defined workflows so that it understands your codebase, your standards, and your definition of done.

Tools such as Claude Code and Cursor support this through project-level instruction files, reusable skill definitions, and configurable workflows. The names differ between tools, but the idea is the same: encode context once, in a versioned file, and have every AI interaction benefit from it.

Three reusable artefacts

ArtefactPurposeAnalogy
RulesAlways-on instructions about the project and its conventionsA team handbook the assistant always reads
SkillsReusable, task-specific playbooks the assistant can invokeA runbook for a recurring job
WorkflowsMulti-step processes with checks and approvalsA pipeline with defined stages

Rules are passive and global; skills are active and on-demand; workflows coordinate several steps. Keeping them separate makes each easier to write, review, and improve.

Writing effective rules

A project rules file should state the things a new teammate would need in their first week: the stack, the folder structure, naming conventions, testing requirements, forbidden patterns, and how to run the project. Keep it concise and concrete. Vague rules such as "write good code" are ignored; specific rules such as "all database access goes through the repository layer" are followed.

# Project rules
- TypeScript strict mode; no `any` in new code.
- All API calls go through src/lib/api.ts.
- Every new endpoint needs a test in tests/api/.
- Never commit secrets; use environment variables.
- Run `npm test` before declaring a task complete.

Scope rules narrowly. A handful of precise rules beats a wall of text. Remember from Chapter 3 that context is finite: a huge rules file eats tokens on every request and dilutes attention.

Designing reusable skills

A skill is a packaged playbook for a recurring task: "add an endpoint", "write a migration", "review a pull request", "create a component". A good skill declares when it should be used, the inputs it needs, the steps to follow, and the output it should produce. It can reference scripts, templates, and docs in the repository.

  • Trigger — a clear description of when to invoke it.
  • Inputs — what the assistant must gather before starting.
  • Steps — an ordered procedure, with decision points.
  • Definition of done — tests, checks, and artefacts required.

Store skills in the repository alongside code. Version them, review changes, and measure whether they actually improve output. A skill that encodes a bad habit spreads that habit at machine speed.

Workflows with checkpoints

For larger tasks, define a workflow: plan, implement, test, review, summarise. Each stage has a clear handoff. For example, the planning stage produces a short written plan for human approval before code is written. The test stage must run the suite and report results. The review stage checks the diff against the project rules. This is the same human-in-the-loop thinking from Chapter 7, applied to your development process.

Approve the plan, not every line. Reviewing a short plan before implementation catches misunderstandings early without interrupting at every step. This is the pattern from Chapter 12, applied to coding assistants.

Context engineering for assistants

The quality of an assistant's work depends heavily on what it can see. Give it the right files, the relevant tests, and the project rules. Avoid dumping the entire repository into context — that wastes tokens and buries the signal. Point it at specific paths, ask it to read the relevant modules first, and require it to state its assumptions before changing code.

When a task is complex, ask for a plan first. A one-paragraph plan reveals whether the assistant understood the codebase. If the plan is wrong, correct it before any code is written. This is far cheaper than reviewing a large, misguided patch.

Token reduction that actually helps

  • Keep rules files short and specific.
  • Reference file paths instead of pasting file contents.
  • Ask for diffs and summaries rather than whole-file rewrites.
  • Clear or scope conversation history between unrelated tasks.
  • Reuse skills instead of repeating long instructions in every prompt.

These habits reduce cost and latency, but more importantly they improve focus. A lean context produces better answers. Chapter 27 develops the economics in detail.

Verification is not optional

An AI assistant can produce plausible, broken code. Your workflow must include verification: tests, type checks, linters, and human review of the diff. Never accept a change because it "looks right". Define done in the workflow and make the assistant prove it. This mirrors the evaluation discipline of Part IV — you are evaluating generated code against objective gates.

Worked example: onboarding a rules-and-skills kit

Consider a small backend team that maintains a TypeScript service with about 200 endpoints. They decide to standardise how a coding assistant contributes. Rather than let each developer improvise, they treat the assistant configuration as versioned project code, reviewed like any other change. The rollout has four steps.

Step 1 — Write a short, enforceable rules file

The team drafts a rules file of 32 lines. Every line is either a convention, a forbidden pattern, or a verification command. Nothing is aspirational.

# .assistant/rules (illustrative)
- Language: TypeScript strict; never introduce `any`.
- All database access via src/repo/*; no raw queries in handlers.
- New endpoints: register in routes.ts and add tests/api/<name>.test.ts.
- Never print secrets; read config via env.ts only.
- Done means: npm run typecheck && npm test -- --changed pass.

The last line is the important one. It gives the workflow an objective definition of done, so "complete" is a test result rather than an opinion.

Step 2 — Define two skills with clear contracts

The team adds a skill for the most frequent task, adding a REST endpoint. Its trigger, inputs, steps, and definition of done are written explicitly:

  • Trigger: a request to add, update, or remove an HTTP endpoint.
  • Inputs: method, path, request and response shapes, and the owning resource.
  • Steps: locate the nearest sibling endpoint, propose a plan, implement handler plus repository call, add a test, run typecheck and the targeted test.
  • Definition of done: route registered, test present and passing, no forbidden patterns.

A second skill handles database migrations, including a mandatory check that the migration is reversible. Both skills live in the repository, so changes are reviewed in pull requests.

Step 3 — Put a checkpoint in the workflow

For any change touching more than three files, the workflow requires a one-paragraph plan before code is written. The developer approves the plan or corrects it. In practice this catches the most expensive class of error: the assistant confidently modifying the wrong subsystem. A wrong plan costs one paragraph to fix; a wrong patch costs a full review cycle.

Step 4 — Measure the effect

The team records three numbers for ten comparable tasks before and after: tokens spent per task, wall-clock time to a passing test, and the fraction of changes that needed rework. Their baseline is about 18,000 tokens and 22 minutes per endpoint, with four of ten needing rework. After the kit, tokens fall to roughly 9,000 (the rules and skills replace repeated instructions), time to about 14 minutes, and only one of ten needs rework. The gain comes from focus and a clear definition of done, not from a faster model.

Exercise 26.3 — Audit your rules. Take a rules file you have used and mark each line as convention, forbidden pattern, or verification command. Delete every line that is none of these, then add one objective definition of done.

Common pitfalls in assistant configuration

The configuration artefacts from this chapter are small, but small files are easy to get wrong. These are the mistakes that most often turn an assistant from a help into a liability.

PitfallWhy it mattersBetter approach
A 300-line rules fileIt consumes tokens on every request and dilutes the important instructions among noise.Keep it under about 40 lines; move task-specific guidance into skills.
Vague instructions like "write good code"They give the model no testable target, so behaviour varies run to run.State conventions and forbidden patterns you can point to in the repository.
Skills with no trigger or overlapping scopeThe assistant cannot tell when to use them, so it either never invokes them or invokes the wrong one.Give each skill one clear trigger and a distinct job.
No objective definition of done"Complete" becomes a matter of opinion, and broken changes get accepted because they look plausible.End every skill and workflow with a command that must pass.
Reusing one long conversation across unrelated tasksStale context from a previous task leaks into the next one and wastes tokens.Scope or clear history between tasks; start fresh for unrelated work.
Pasting whole files or the entire repositoryIt buries the relevant code and inflates cost without improving focus.Reference paths and ask the assistant to read specific modules first.
Never versioning the configurationA bad rule spreads to every developer with no review and no rollback.Commit rules and skills; review changes like production code.

A useful habit is to treat the rules-and-skills kit as a product with users — your teammates. When a rule causes confusion, fix the rule rather than working around it in every prompt.

Review questions: assistant workflow design

These questions test whether you can design an assistant workflow, not just use one. Work through them without looking back at the tables.

  1. Why does a shorter rules file often produce better code than a longer one, even though it contains less information?
  2. A skill for adding endpoints keeps producing handlers that bypass the repository layer. Which part of the skill would you change first, and how would you verify the fix?
  3. When would you choose a multi-step workflow with a human checkpoint over a single skill, and what does the checkpoint cost you?
  4. Your team's token bill rises after adopting an assistant. Name three configuration changes you would try before switching models, and predict which saves the most.
  5. Describe a situation in which trusting a plausible-looking generated patch would be dangerous, and the objective gate you would put in place.

Summary

  • Productivity comes from programmable context, not one-off chat prompts.
  • Rules are global instructions; skills are on-demand playbooks; workflows coordinate steps.
  • Keep rules concise — they consume context on every request.
  • Review the plan before the code, and verify with objective gates.
  • Store these artefacts in version control and improve them with measurement.
