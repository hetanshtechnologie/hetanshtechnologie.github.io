12. AutoGen

Conversation as computation

AutoGen approaches multi-agent work through conversations. Agents are "conversable": they exchange messages, call tools, and react to one another until a termination condition is met. A group chat can include a user proxy, an assistant, a critic, and a tool executor, with a manager deciding who speaks next. The model of computation is a dialogue, and many real tasks really do look like one.

This framing is particularly useful for problems where nobody knows the full plan in advance. In a debugging session, the first agent reads the error, the second suggests a hypothesis, the third runs a test, and the group reacts to the result. The sequence emerges from the conversation rather than being fixed at design time.

Core objects

ObjectRole
Conversable agentAn entity that can send, receive, and generate messages
User proxyAn agent that represents the human or the local execution environment
Assistant agentA model-driven reasoning and generation agent
Group chatA shared conversation with multiple participants
ManagerA component that selects the next speaker
Termination conditionThe rule that ends the conversation

The user proxy deserves special attention. It can be configured to require human input, to execute code automatically, or to ask before each execution. That choice is a security decision. Automatic code execution inside a conversation is powerful and dangerous; treat it as you would any untrusted code path.

Code execution and the tool loop

AutoGen became popular partly because it made tool use conversational: an agent could write code, a proxy could execute it, and the result could be returned into the dialogue. This is excellent for analysis and prototyping. In production, wrap that capability in the controls from Chapters 6 and 20: sandboxed execution, timeouts, no ambient credentials, and explicit approval for anything with side effects.

# Pseudocode: a guarded code-execution step
result = sandbox.run(
    code=agent_proposed_code,
    timeout_seconds=10,
    network_access=False,
    env=minimal_env
)
conversation.post(tool_result(summarise(result)))

Return a summary, not a raw dump. Large outputs consume context and can push earlier instructions out of the window. If the full output is needed, store it and give the agent a reference.

Human in the loop

Because the user proxy can require input, human participation is natural. A human can correct a wrong assumption, choose between options, or approve code before execution. Use this deliberately: specify at which points the human is consulted and what information they need. A checkpoint without context is just an interruption.

Design pattern. Ask the human to approve a plan before execution rather than every tool call. Fewer interruptions, better oversight.

Termination and cost control

Conversations must end. Common conditions include a maximum number of messages, a detected final answer, a cost ceiling, or a human decision. Combine them. A model may claim to be finished while still being wrong, so pair the "final answer" signal with a validator. Track tokens per participant; a chatty critic can dominate the bill.

Also watch for polite loops: agents thanking each other, restating the plan, or asking permission repeatedly. A simple detector looks at message similarity over the last few turns. When triggered, a manager should summarise and force a decision.

Group chat management

The manager's speaker-selection strategy matters. Round-robin is predictable but wastes turns. Model-based selection is flexible but adds cost and can favour the same agent. A hybrid works well: deterministic rules for obvious transitions, model choice only when ambiguous. Log the reason for each selection so you can debug surprising paths.

When AutoGen fits

  • The task is exploratory: debugging, analysis, research, or design review.
  • You want human participation woven into the loop.
  • Code execution is part of the workflow and can be sandboxed.
  • You are comfortable with variable conversation paths.

For transactional workflows with strict SLAs, a deterministic graph is usually a better fit. AutoGen's strength is open-ended problem solving, not repeatable high-throughput processing.

A worked example: debugging a failing data pipeline

Consider a nightly ETL job that started failing after a schema change. A data engineer wants an assistant that can investigate, propose a fix, and verify it — but nothing may be executed against production without approval. This is a natural AutoGen scenario: the investigation path is not known in advance, code execution is useful, and a human should approve the final patch. We will assemble a group chat with four participants and combine several termination conditions.

Participants and the manager

The group contains an assistant agent that reasons about the error, a tool executor that runs diagnostic code in a sandbox, a critic that challenges hypotheses, and a user proxy representing the engineer. A manager selects the next speaker with a hybrid rule: after a tool result, the assistant speaks next; after the assistant proposes a hypothesis, the critic speaks; the human is invited once, before any patch is applied. Round-robin would waste turns here, while pure model selection would sometimes let the critic dominate. The hybrid rule makes transitions predictable without hard-coding the whole investigation.

group = GroupChat(
    agents=[assistant, executor, critic, user_proxy],
    manager=GroupChatManager(
        selector=hybrid_selector,
        system_message="After a tool result, the assistant speaks. " +
                       "After a hypothesis, the critic speaks. " +
                       "The human is asked only before applying a patch."
    ),
    max_round=14
)

Sandboxed execution

The executor never runs code with ambient credentials. Every proposed snippet goes through a sandbox with a ten-second timeout, no network access, a minimal environment, and a read-only mount of the sample data. We return a summary of the result into the conversation, not a raw dump: a short stack trace and the shape of the offending dataframe. A full log is stored and referenced by ID. In an earlier trial we posted the entire log into the chat; it consumed most of the context window and the assistant started reasoning about stale lines from the beginning of the file.

result = sandbox.run(
    code=proposed_snippet,
    timeout_seconds=10,
    network_access=False,
    env={"PYTHONPATH": "/sandbox/lib"},
    mounts=[("sample.parquet", "ro")]
)
conversation.post(tool_result(summarise(
    {"exit": result.code, "error": result.tail(12), "log_ref": result.id}
)))

Notice that the human proxy is configured to require input for the patch step but not for diagnostics. Approval fatigue is real: if the engineer is asked to confirm every read-only command, they will start clicking through without looking.

Track tokens per participant as the conversation runs. In the debugging chat, the critic initially produced nearly as many tokens as the assistant because it restated the whole error on every turn. A simple per-agent budget made that visible, and we shortened the critic's instruction to respond only to the specific hypothesis on the table. Logging the reason for each speaker selection also helped: when the manager chose the critic three times in a row, the log showed it was reacting to the same unresolved question rather than looping arbitrarily.

Termination and the review checkpoint

We combine four termination conditions: a maximum of fourteen rounds, a cost ceiling of two dollars, a detected final answer that has passed validation, and a human decision at the checkpoint. The "final answer" signal alone is not trusted — the critic must confirm that the proposed patch addresses the actual schema mismatch, not just makes the test pass. If the cost ceiling is reached first, the run returns the best hypothesis so far with a "needs review" flag. Once the human approves the patch, a separate, non-conversational step applies it; the group chat itself never writes to production. That boundary is deliberate: exploratory dialogue is good at forming hypotheses and poor at being an authority for side effects.

Design decisions and pitfalls

Conversation-based systems fail in predictable ways. The table below names the decisions that most affect safety and cost.

DecisionRisk if handled casuallyBetter approach
Automatic vs. approved code executionUntrusted generated code with ambient credentials can exfiltrate data or mutate systems.Sandbox by default; require approval only for steps with side effects, not for every read.
Raw tool output in the conversationLarge dumps push instructions out of the context window and confuse later reasoning.Post a compact summary and a reference to stored full output.
Round-robin speaker selectionPredictable but wasteful; agents speak when they have nothing to add.Use deterministic rules for obvious transitions and model selection only when ambiguous.
Single termination signalA model may declare victory while wrong; a turn limit alone may cut off a good investigation.Combine turn, cost, time, validated-answer, and human conditions.
Approval on every tool callFatigue leads to rubber-stamping, which is worse than no review at all.Ask the human to approve a plan or a patch at one meaningful checkpoint.
Conversation used as the execution authorityA dialogue is not an audit trail or an authorisation layer; side effects are hard to govern.Keep application of changes in a separate, validated, non-conversational step.

Summary

  • AutoGen treats multi-agent work as a structured conversation.
  • The user proxy can represent a human or a local execution environment.
  • Code execution must be sandboxed, summarised, and often approved.
  • Combine termination conditions and watch for polite loops.
  • Best suited to exploratory tasks, not strict transactional pipelines.
