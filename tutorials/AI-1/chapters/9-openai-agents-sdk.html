9. OpenAI Agents SDK

A different centre of gravity

Where a graph library starts from control flow, the OpenAI Agents SDK starts from the idea of an agent: a model, a set of instructions, tools, and optional handoffs. You describe agents as objects, give them capabilities, and let the SDK run the loop. The abstractions are small, which makes them approachable, and they are designed to work with the provider's tracing and guardrail facilities.

This does not mean the SDK is only for simple demos. Its strength is that common patterns — a triage agent handing off to a specialist, guardrails on input and output, traced execution — are first-class concepts rather than things you build from scratch. When your architecture matches those concepts, you can move quickly.

The core objects

ObjectPurpose
AgentName, instructions, model, tools, handoffs, guardrails
RunnerExecutes an agent synchronously or as a stream
HandoffA transfer of control to another agent, with optional argument transformation
GuardrailA check on input or output that can allow, block, or transform
ToolA function or hosted capability exposed to the agent
Session / memoryConversation history across runs
TracingSpans for runs, agent steps, tool calls, and handoffs

Defining an agent

A minimal definition reads almost like a job description: you state who the agent is, what it should do, and what it may use. Instructions are natural language, so the same clarity rules from Chapter 4 apply. Tools are typed functions with docstrings that become the tool description.

const billing = new Agent({
  name: 'Billing specialist',
  instructions: 'Answer billing questions using the policy tool. Never issue refunds.',
  tools: [searchPolicy, findInvoice],
  model: 'gpt-4.1-mini'
});

Notice the explicit negative constraint. Agents are eager to be helpful, so "never" statements matter when a neighbouring agent owns that capability. Without the constraint, the billing agent might try to refund anyway.

Handoffs

A handoff transfers control from one agent to another. In a customer-service system, a triage agent decides whether the request is about billing, technical support, or something else, then hands off to the appropriate specialist. The SDK typically represents a handoff as a callable tool, which means the model sees it alongside other tools and can choose it.

Handoffs are powerful but easy to overuse. Two agents with overlapping instructions can pass a request back and forth. Prevent this by giving each agent a narrow scope, by including the reason for transfer in the handoff arguments, and by capping handoff count. Trace handoffs explicitly; they are a common source of latency and confusion.

Some handoffs should carry structured context: the summary so far, the customer's tier, the reason for escalation. Design that payload deliberately. A bare "transfer to specialist" loses information and forces the specialist to re-ask questions.

Guardrails

Guardrails are checks that run around agent behaviour. Input guardrails examine the user's request before it reaches the model; output guardrails examine the response before it is returned. A guardrail can block, transform, or route. Examples include PII detection, policy classification, banned-topic filters, and schema validation.

Guardrails are not a security boundary. They are a useful control layer, but a determined prompt-injection attempt can sometimes shape output that passes a classifier. Enforce permissions in tools and runtime, as discussed in Chapter 20.

Good guardrails are specific and measured. "Detect potentially harmful content" is too vague to evaluate. "Reject requests that ask for another user's order details, using the policy classifier with confidence above 0.8" is testable. Track false positives: an overzealous guardrail that blocks legitimate users is a product failure.

Tracing as a built-in

The SDK's tracing captures the run as a tree: agent invocation, model call, tool execution, handoff, guardrail result. This is valuable because agent failures are often cross-step. An answer may be wrong because a handoff carried the wrong context, not because the final model call was poor. Without a full trace, you will blame the wrong component.

Adopt a naming convention for traces and spans before you have many agents. Include environment, agent version, prompt version, and thread ID in metadata. Then a spike in handoff failures can be correlated with a prompt change in minutes.

Tools and hosted capabilities

Tools can be your own functions or provider-hosted capabilities such as web search or code interpretation. Hosted tools reduce infrastructure work but change the data boundary: content may leave your environment. For regulated workloads, prefer tools you control or configure retention explicitly.

Keep tool descriptions precise, as in Chapter 6. The SDK will surface them to the model, and ambiguity will cause misselection. If you expose a hosted tool and a custom tool with similar purposes, write descriptions that make the distinction obvious.

When the SDK fits

  • You want a fast path from an idea to a working agent.
  • Your control flow is mostly the standard loop plus handoffs.
  • You value integrated tracing and guardrails.
  • You are already invested in the provider's model and tooling ecosystem.

If you need unusual control flow — nested loops, complex approval state machines, or deterministic branching based on arbitrary state — a graph approach may serve you better. Nothing prevents using both: an SDK agent can be one node inside a larger graph.

A worked example: a support triage desk

Consider a support assistant for a mid-sized SaaS product. Requests arrive through a web form and a chat widget. About 60 percent are billing questions, 25 percent are technical how-to questions, and the rest are account or security concerns. Today a single prompt handles everything and produces inconsistent results: it sometimes promises refunds it cannot issue, and it never knows when to involve a human. We will rebuild it as a small SDK application with one triage agent, two specialists, an escalation path, and guardrails around the whole run.

Defining the agents

We start with three agents and a handoff target for humans. The triage agent has no tools; its only job is classification and routing. Each specialist gets a narrow instruction set and only the tools it needs. Notice that the billing agent is explicitly forbidden from issuing refunds, because that action belongs to a human escalation queue.

const triage = new Agent({
  name: 'Triage',
  instructions: 'Classify the request as billing, technical, or security. ' +
    'Hand off once, with a one-line reason. Never answer policy questions ' +
    'yourself.',
  tools: [],
  handoffs: [billing, technical, security, escalate]
});

const billing = new Agent({
  name: 'Billing',
  instructions: 'Answer billing questions using searchPolicy and findInvoice. ' +
    'Never issue refunds or promise credits; escalate those requests.',
  tools: [searchPolicy, findInvoice],
  model: 'gpt-4.1-mini'
});

The triage agent has no tools, which is deliberate. With nothing else to call, the model's only available action is a handoff, so routing becomes reliable. In an early prototype we gave triage the same tools as the specialists; it answered directly about 30 percent of the time and skipped the handoff payload entirely.

Guardrails and the run

Next we add guardrails. An input guardrail checks for requests that name another customer's account; an output guardrail checks that the response contains no commitment to a refund or credit. Both record a decision in the trace even when they allow the request through, so we can measure false positives later. We then run the agent with a session so follow-up questions keep context.

const result = await run(triage, userMessage, {
  session: conversationSession,
  inputGuardrails: [detectCrossAccountAccess],
  outputGuardrails: [detectRefundPromise],
  maxTurns: 8,
  tracing: { workflowName: 'support-v2', metadata: { env: 'prod' } }
});

The maxTurns cap is a cost and safety control. In testing, a pair of agents once looped for eleven turns because the billing specialist kept handing back to triage after an ambiguous answer. With the cap in place, the run terminates and returns a "connecting you to a person" message instead of burning tokens.

Reading the trace

A single failed run illustrates why tracing matters. A user asked why an invoice was higher than expected. The final answer quoted the wrong policy tier. The trace showed the sequence: triage handed off to billing with the reason "invoice question" but no customer tier; the billing agent called findInvoice correctly, then called searchPolicy with a generic query; the policy tool returned two tiers, and the model picked the first. The fix was not a new model. We changed the handoff payload to include customerTier from trusted session state and made searchPolicy require that field. A trace turned a vague "the answer is wrong" into a two-line change.

Pitfalls and trade-offs

MistakeWhy it mattersWhat to do instead
Giving triage the same tools as specialistsThe router answers directly, skips the handoff payload, and defeats the specialisation you designed.Give routing agents no domain tools; their only action should be a handoff.
Handoffs without structured contextThe receiving agent re-asks questions or guesses missing facts, adding latency and errors.Define a typed payload with the reason, summary, and any trusted fields such as tier or locale.
Overlapping agent instructionsTwo agents with similar scopes pass a request back and forth until the turn cap is hit.Write explicit "never" constraints that name the neighbouring agent's responsibility.
Vague guardrails"Detect bad content" cannot be measured, so you cannot tell whether it is helping or blocking real users.State the exact pattern, the threshold, the failure action, and a false-positive test case.
Treating guardrails as authorisationA classifier can be bypassed; a determined injection can shape output that passes.Enforce permissions in tools and the runtime, and keep guardrails as a secondary layer.
Hosted tools without a data reviewContent may leave your environment, which can violate retention rules.Prefer tools you control for regulated data, or configure retention explicitly before launch.
Tracing everything with no naming schemeSpans become unsearchable, so cross-step failures stay invisible.Adopt a convention with environment, agent version, prompt version, and thread ID from day one.

Summary

  • The SDK centres on agents, runners, handoffs, guardrails, and tracing.
  • Handoffs are tools; narrow scopes and payload design prevent loops.
  • Guardrails are measurable controls, not a substitute for tool-level security.
  • Built-in tracing is essential for diagnosing cross-step failures.
  • The SDK is ideal for standard loops; graphs win for unusual control flow.
