27. Token Economics and Context Engineering

Tokens are the budget

In an AI system, tokens are the unit of cost, latency, and attention. Every token you send costs money, every token generated takes time, and every irrelevant token competes for the model's focus. Token economics is the practice of treating context as a scarce resource and spending it where it changes the outcome.

Developers often focus on the price per million tokens and miss the bigger lever: how many tokens your architecture consumes per task. A well-designed system can be an order of magnitude cheaper than a careless one using the same model. That difference comes from context engineering, not from haggling over prices.

Where tokens go

SourceTypical wasteRemedy
System promptOver-long, repeated on every callTrim to essential rules; use stable prefix for caching
Conversation historyGrows without boundSummarise, trim, or store externally
Retrieved documentsToo many chunks, low relevanceRerank, cap count, compress
Tool definitionsDozens exposed when few are neededDynamic tool selection
Tool resultsRaw dumps of large dataSummarise and reference
Model outputVerbose reasoning and explanationsConcise formats, max tokens, stop sequences

Notice that output tokens are often the largest controllable cost. They cost more per token than input and scale with how chatty your prompts allow the model to be.

Context engineering principles

  1. Relevance over volume. Three precise chunks beat twenty marginal ones.
  2. Structure over prose. Labelled sections and delimiters help the model parse evidence.
  3. Stability where possible. A stable prompt prefix enables caching and predictable behaviour.
  4. Freshness where needed. Load dynamic data at request time; do not bake it into static instructions.
  5. Minimality with intent. Remove tokens that do not influence the decision.

These principles echo Chapter 2's context layer and Chapter 4's prompting patterns. Token economics is the quantitative view of the same ideas.

Compression techniques

Several practical techniques reduce token use without losing meaning:

  • Summarisation — compress long histories or documents into key facts, keeping references to the originals.
  • Extractive selection — keep only the sentences relevant to the query.
  • Reference instead of paste — store large artefacts externally and pass an ID the model can use in a follow-up tool call.
  • Structured formats — tables and compact JSON carry more information per token than prose.
  • Dynamic examples — retrieve a few relevant few-shot examples rather than embedding a large fixed set.
Measure quality after compression. Every compression technique risks removing the detail that mattered. Run your eval suite before and after. Saving tokens is not a saving if the answer becomes wrong.

Caching and prefixes

Many providers offer prompt caching: if a long prefix is unchanged, its computed state is reused at lower cost and latency. Design prompts with a stable prefix — system instructions, policy, and tool definitions first — and put variable content at the end. A cache that invalidates on every request because a timestamp sits in the system message is useless. Chapter 22 covers the serving side of prefix caching.

Budgets at every level

Set token budgets in three places:

  1. Per request — a hard cap that stops runaway loops.
  2. Per feature — so one expensive feature cannot dominate the bill.
  3. Per user or tenant — to prevent abuse and enable tiered pricing.

Record actual spend against each budget with your traces from Chapter 21. Alert at 80% usage. A budget that is discovered only after the invoice arrives is not a control.

The productivity multiplier

Token economics is not only about cloud bills. It applies to your daily use of AI coding assistants too. A lean rules file, a focused skill, and a scoped request produce better work faster than a huge context dump. The developer who writes precise prompts and reuses well-designed skills will outpace the one who pastes entire repositories into every conversation.

The compounding effect matters: a skill that saves five minutes and two thousand tokens on every use, used twenty times a week, is a meaningful advantage. Treat your prompt and skill library as an asset you invest in.

A cost-reduction workflow

When a feature is too expensive, work in this order: measure where tokens go; remove obvious waste in prompts and tool results; add caching for stable prefixes; introduce routing from Chapter 23; compress retrieved context; and only then consider a cheaper model. Changing the model first is tempting but often the smallest lever, and it can quietly reduce quality.

Worked example: diagnosing an expensive support assistant

A support team runs an assistant that answers questions from a product manual. At 20,000 tickets a month the bill is unexpectedly high, and latency is creeping up. The team instruments one representative request and attributes tokens to the six sources from the table above. The result looks like this:

SourceTokens per requestObservation
System prompt1,200Includes a live timestamp, so nothing caches.
Conversation history3,400Entire 12-turn history replayed every time.
Retrieved documents2,800Eight chunks, several only loosely relevant.
Tool definitions900Twelve tools exposed; most requests need two.
Tool results1,500Raw API responses pasted in full.
Model output1,100Verbose explanations with no length cap.

Total: 10,900 tokens per request. At the team's blended rate this is roughly 11 cents a ticket, or about $2,200 a month — and most of it is waste. The team works through the fixes in the recommended order.

Fix 1 — Stabilise the prefix

The timestamp is moved out of the system message into the final user turn. The system prompt, policy, and tool definitions now form a byte-identical prefix, so prompt caching applies. A refactored prompt separates stable and variable content:

[stable prefix: system rules + policy + tool schemas]
---
[variable tail: retrieved chunks | last 3 turns | current query]

Cached prefix tokens are billed at a fraction of the normal input rate, and first-token latency drops noticeably.

Fix 2 — Trim history and retrieval

The full 12-turn history is replaced by a rolling summary plus the last three turns, cutting about 2,600 tokens. Retrieved chunks are capped at four after reranking, removing roughly 1,400 tokens of marginal context. Quality on the eval set is unchanged, which the team verifies before proceeding.

Fix 3 — Summarise tool results

Tool results are reduced to the fields the answer needs, with an ID for the full record, saving about 1,100 tokens. Output is constrained to a compact format with a 300-token cap, saving another 700.

The result

Per-request tokens fall from 10,900 to roughly 4,400 — a 60% reduction — with no measurable quality loss and lower latency. Notice the order: no model change was needed. The team only changed how context was assembled, which is the point of context engineering.

Watch the trend, not a single snapshot. Token use drifts as conversation features and document sets grow. Re-run this attribution monthly and after every prompt or retrieval change. A per-request budget that looked healthy at launch can quietly double as histories accumulate, so the instrumentation you added for this exercise should stay in production rather than being removed once the optimisation is done. The same traces that reveal waste also tell you when a previous fix has stopped working.

Design decisions in context budgeting

Reducing token use is full of trade-offs: every technique that saves tokens can, in the wrong place, remove the detail that makes an answer correct. Treat the following as decisions to reason about, not rules to apply blindly.

DecisionTrade-offGuidance
Compress conversation historySaves tokens but can drop a detail the user still expects you to remember.Keep a rolling summary plus recent turns; store older facts externally.
Cap retrieved chunksFewer chunks are cheaper and often more relevant, but recall can suffer.Rerank first, then cap; verify recall@k on your eval set.
Use prompt cachingCheap repeated prefixes, but any change in the prefix breaks the cache.Put timestamps and user data at the end, never in the system prefix.
Constrain output lengthCaps cost and latency, but overly tight caps truncate useful answers.Use structured formats and set the cap from observed answer lengths.
Expose tools dynamicallyFewer tool definitions save tokens, but a needed tool may be missing.Select tool sets by request type, with a fallback set for ambiguity.
Switch to a cheaper modelLargest headline saving, but often the smallest real lever and a quiet quality risk.Do it last, after routing and compression, and compare with pairwise eval.
Summarise tool resultsCuts large dumps, but a summary may discard the field the answer needs.Keep required fields plus an ID for the full record on demand.

The common thread is measurement. Each choice has a quality cost that is invisible until you run the eval suite, which is why the discipline from Part IV matters as much here as the arithmetic.

Review questions: token economics

Use these to check that you understand where savings come from and what they cost. Try to answer with numbers or a concrete feature in mind.

  1. Why can architecture changes save more money than negotiating a lower price per million tokens?
  2. A prompt caches perfectly on Monday but not on Tuesday. What are the likely causes, and how would you find the one that changed?
  3. Output tokens cost more than input tokens. What prompt and format changes reduce them without making the answer less useful?
  4. You cut a feature's token use by half but an eval shows more wrong answers. How do you decide whether the saving is real?
  5. Describe how you would divide a per-feature token budget among system prompt, history, retrieval, tools, and output, and where you would alert first.

Summary

  • Tokens are the unit of cost, latency, and attention.
  • Context engineering — not price negotiation — is the main cost lever.
  • Output tokens are often the largest controllable expense.
  • Stable prefixes enable caching; variable content belongs at the end.
  • Set and monitor budgets at request, feature, and user levels.
