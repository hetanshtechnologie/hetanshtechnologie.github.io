1. Welcome to AI-1

Why this book exists

A conference talk gives you a spark. It compresses months of hard-won engineering experience into thirty or forty minutes, and it leaves you with a list of terms you want to understand better. This book is built to turn that spark into a working mental model. It takes the themes from the AI-India first edition — autonomous agents, retrieval, tool use, protocols, evaluation, inference engineering, guardrails, local AI, developer productivity, and careers — and gives each one the space it deserves.

The goal is not to collect names of frameworks. The goal is to help you make decisions: when to reach for a graph-based agent, when a simple prompt is enough, why your evaluation suite can report success while users still see failures, and what a model router actually buys you. By the end you should be able to read a production AI architecture and explain why each component is there.

What makes this different from a workshop transcript

This is an original study guide. The session descriptions were rewritten in new language from the event information supplied to the author. You will not find copied talk abstracts or pasted biography paragraphs here. Where an idea from the event is discussed, it is presented as a concept you can learn from and then expanded with explanation and example. Individual speaker names and affiliations are deliberately omitted.

Who this book is for

  • Software engineers who can write code and want to move from calling an LLM API to designing systems that behave reliably.
  • Data and ML engineers who understand models but want the orchestration, serving, and evaluation picture.
  • Technical leads and architects who need to judge trade-offs, set guardrails, and control cost before approving an AI feature.
  • Students and career switchers who want a map of the AI engineering landscape and a portfolio plan that gets noticed.

You do not need to be an expert in machine learning. You should be comfortable with APIs, JSON, and at least one programming language. Every code-oriented section explains the idea before showing syntax, so you can translate the examples into your preferred stack.

What you will be able to do

Each part ends with capabilities rather than vague "awareness". After completing the book you should be able to:

  1. Explain the difference between a model, a prompt, an agent, and an agentic system.
  2. Design a RAG pipeline and justify chunking, embedding, and retrieval choices.
  3. Implement tool calling with validation, retry, and safe side-effect handling.
  4. Choose between LangGraph, the OpenAI Agents SDK, Microsoft Agent Framework, CrewAI, and AutoGen for a given problem.
  5. Expose and consume tools through MCP, including serverless and stateless deployment considerations.
  6. Build an evaluation harness that does not depend on a perfect golden dataset.
  7. Detect silent degradation, calibrate an LLM judge, and use canaries and trace replay.
  8. Recognise where self-improving agent loops plateau and what raises the ceiling.
  9. Design least-privilege tool access, isolation boundaries, and human approval checkpoints.
  10. Run or route inference with cost, latency, quality, and privacy in mind.
  11. Set up local models and offline-first AI for constrained or disconnected environments.
  12. Create reusable rules and workflows for AI coding assistants while managing token spend.
  13. Build a portfolio and network that makes you visible to teams hiring AI talent.

How to read actively

Passive reading creates familiarity; active reading creates skill. For each chapter, do three things:

  1. Write the one-sentence summary before you move on. If you cannot, reread the section.
  2. Answer the review question in your own words, without looking back.
  3. Do the small lab. Most chapters include a compact exercise. A fifteen-minute experiment beats an hour of highlighting.
Exercise 1.1 — Your starting map. On a blank page, draw the last AI feature you used or built. Label four things: the model, the data it could see, the actions it could take, and the way someone verified it worked. Leave the gaps blank. Those gaps are the parts of this book most relevant to you.

A note on terminology

The field uses overlapping words. An agent is usually a loop: observe, decide, act, observe again. An agentic system is the larger application around that loop — tools, memory, policies, evaluation, and interfaces. A workflow is a prescribed path where the developer controls the transitions; an agent has more say over the next step. Neither is automatically better. Most production systems are careful mixtures of both.

Through the book we will use model for the underlying LLM, tool for a callable function or external capability, harness for the code that surrounds the model, and runtime for the infrastructure that executes the loop. Keeping these separate will save you from a lot of confused design conversations.

A worked example: following one question through the vocabulary

Abstract definitions become useful when you can point to them in a real system. Imagine an employee asking a leave-management assistant: "How many casual leaves do I have left this year?" On the surface this is one sentence. Underneath, it exercises almost every term introduced in this chapter.

Start with the model. Something has to turn the question into an answer, and that something is a language model called through an API. It does not know the employee's balance; its training data ended long before this person joined the company. The only way it can answer correctly is if the current balance is placed in its context for this request.

Next comes the harness: the code surrounding the model. The harness takes the employee's identity from the authenticated session, decides that a balance lookup is required, and calls a tool named get_leave_balance. The tool queries the HR database and returns a number — say 8. Notice that the model never sees a database credential and never supplies the employee ID; the harness does both. That separation is a recurring theme throughout this book.

The runtime is whatever executes this loop: the container or serverless function running the harness, the timeout on the database query, and the queue if the request is slow. The agentic system is the whole assembly — model, context, tool, harness, runtime, plus the evaluation that checks the answer and the audit log that records it. The workflow is the prescribed path for this request: authenticate, look up balance, compose answer. There is little or no open-ended agency here, and that is a feature: a balance question should not invite creative behaviour.

Finally, verification. Before the answer is shown, an eval check confirms two properties: the number returned by the tool appears in the answer, and the answer names the policy source. If either fails, the response is flagged for review. This is what it means to say that quality is a layer rather than a moment.

Here is the same request written as a compact trace, the kind of artefact you will learn to read throughout the book:

request_id: req_8f21
user: "How many casual leaves do I have left this year?"
session.employee_id: E-1042        // from auth, not from the model
steps:
  1. classify     -> intent: leave_balance        (fixed)
  2. tool.call    -> get_leave_balance(E-1042, type=casual)
  3. tool.result  -> { balance: 8, as_of: "2026-11-21" }
  4. generate     -> "You have 8 casual leaves remaining."
  5. evaluate     -> cites_source: true, number_matches: true
answer_latency_ms: 940    total_tokens: 612

Read the trace as a sentence. Each step is a node, each arrow a hand-off, and the fields at the bottom are the numbers you would watch in production. When a user later complains that the assistant reported the wrong balance, this trace tells you where to look: did step 2 query the right employee, did step 3 return the right number, or did step 4 misstate it?

Exercise 1.3 — Annotate the trace. Take the trace above and label each of the five steps with exactly one vocabulary term from this chapter: model, tool, harness, runtime, or evaluation. Then add a sixth step that inserts a human approval node, and state which field in the trace would record the approver's decision.

Reading traps and terminology pitfalls

Most readers do not struggle with the ideas in this book; they struggle with habits that make the ideas harder to see. The table below lists common traps and a concrete replacement for each.

Reading habitWhy it failsWhat to do instead
Collecting framework namesFrameworks change faster than the underlying ideas; a list of tools ages badly and does not help you choose between them.For each tool, write down the problem it solves and the assumption it makes.
Skipping the labConcepts that feel clear in prose collapse the moment you have to implement them.Run the small experiment even if it takes only fifteen minutes.
Treating "agent" and "workflow" as synonymsThis hides the central design question of who controls the next step.Label each step fixed, bounded, or open before discussing tools.
Blaming the model for system failuresMost surprises come from context, tool design, or missing evaluation rather than from weights.Walk the trace and locate the failing layer first.
Reading chapters in isolationRetrieval, tools, evaluation, and governance are connected; isolated reading misses the seams where systems break.Keep a running diagram and update it after each chapter.

Two terminology traps deserve special mention. First, people often say "the prompt" when they mean the entire context: system instructions, retrieved documents, history, and tool results together. Second, they say "the agent" when they mean the whole application around a small loop. Precision here is not pedantry; it is what lets you ask a useful debugging question instead of a vague one.

A note on pace. You do not need to master every chapter before building something. Read the foundations, attempt a small project, then return to the chapters that your project made relevant. The book is a reference to revisit, not a linear exam to survive.

Check your understanding

These questions are for self-checking. Answer each one in your own words before looking back at the chapter; if you cannot, revisit the relevant section.

  1. A colleague says, "The model gave the wrong answer, so we need a better model." What would you examine before accepting that diagnosis?
  2. Explain the difference between an agent and an agentic system using a product you know. Where exactly does the loop end and the surrounding system begin?
  3. Why does the book treat prompts as part of context rather than part of the model? What practical consequence follows from that choice?
  4. Give one example of a task better implemented as a fixed workflow and one that genuinely benefits from model-driven choice. What distinguishes them?
  5. Of the three active-reading habits, which is most likely to reveal a misunderstanding you did not know you had, and why?

Summary

  • This book converts conference themes into a structured, self-paced engineering curriculum.
  • All event-derived material is originally paraphrased and independently presented.
  • The book is organised around decisions you need to make, not a catalogue of tools.
  • Active reading — summary, review question, small lab — is the fastest path to competence.
