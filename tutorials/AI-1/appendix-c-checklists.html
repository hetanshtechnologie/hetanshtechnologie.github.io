Appendix C — Production Readiness Checklists

How to use these checklists

Each checklist is a set of questions to ask before a stage gate: before calling a RAG feature done, before enabling a tool-using agent, before shipping a change, and before going live. They are deliberately practical. An unchecked item is not a moral failing — it is a known risk that should be recorded and owned.

Checklist 1 — RAG pipeline

  • Chunks follow semantic boundaries and carry source, section, version, and access metadata.
  • Retrieval is evaluated separately from generation, with recall@k measured on labelled queries.
  • Hybrid search is in place where exact identifiers matter.
  • Reranking is applied to a shortlist before context composition.
  • Access filtering happens at query time, not after generation.
  • No-answer cases are included in the eval set and the system abstains on them.
  • Answers cite source identifiers present in the supplied context.
  • Deletion and re-indexing are tested; removed documents stop appearing.
  • Index version is recorded in every trace.
  • Freshness requirements are documented and monitored.

Checklist 2 — Tool-using agent

  • Every tool has a precise name, description, parameter schema, and stated limits.
  • Arguments are validated with a real schema library; unknown fields are rejected.
  • Identity, tenant, and role come from trusted session state, never from the model.
  • Mutating tools are idempotent and use a two-phase confirm/execute pattern.
  • Irreversible actions require human approval at a defined control-flow node.
  • Step and token budgets are set and hitting them is an observable event.
  • Repeated-call detection breaks loops and reports an honest failure.
  • Tool results are compact, structured, and labelled with status.
  • Tools use the narrowest credential that works.
  • Every call logs name, arguments, decision, latency, and result status.

Checklist 3 — Evaluation suite

  • Cases assert properties, not exact output strings.
  • The set covers common intents, edge cases, adversarial inputs, and no-answer cases.
  • Deterministic assertions are exhausted before an LLM judge is introduced.
  • Judge rubric is decomposed into atomic questions and calibrated against human spot-checks.
  • Traces can be replayed with stored model responses for deterministic debugging.
  • Failures are categorised with a shared taxonomy.
  • A fast smoke set runs on every change; the full suite runs on a schedule.
  • Canaries track quality as a time series with historical baselines.
  • Distribution and outliers are monitored, not only averages.
  • Reports show counts, per-tag scores, and changes since the last run.

Checklist 4 — Safety and security

  • Threat model covers goal hijacking, tool misuse, privilege abuse, and code execution.
  • Untrusted text is treated as data and never granted instruction authority.
  • Sandboxes have no ambient credentials, minimal network access, and short timeouts.
  • Third-party tools and MCP servers are reviewed like code dependencies.
  • Upstream tool-schema changes are monitored.
  • Approval UI shows the action, target data, impact, and reason.
  • A kill switch exists and has been tested.
  • Audit logs include prompt, model, tool, policy, and approval versions.
  • Traces are redacted, access-controlled, and covered by retention rules.
  • Permissions are rechecked before mutating actions in long-running jobs.

Checklist 5 — Cost and operations

  • Token use is measured by prompt, history, retrieval, tools, and output.
  • Stable prompt prefixes enable caching and are not invalidated by variable data.
  • Budgets exist per request, per feature, and per user or tenant.
  • Alerts fire before budgets are exhausted.
  • Model, prompt, tool, index, and policy versions are recorded in traces.
  • Spans are defined for each step with latency and token attributes.
  • p50 and p95 latency are tracked per span against a stated budget.
  • Routing decisions are logged with reason and confidence.
  • Canary rollouts compare new and reference builds before full deployment.
  • Each alert has a runbook naming the first check, the rollback path, and the owner.

Checklist 6 — Going live

  • The system's purpose can be stated in one sentence.
  • Known limitations are documented and visible to users where relevant.
  • A fallback exists for model unavailability and deadline expiry.
  • Streaming progress is shown for long-running runs.
  • Human support has an escalation path from an agent interaction.
  • Rollback is rehearsed for prompts, models, and tool schemas.
  • Sample traces have been reviewed by someone outside the building team.
  • The first-week monitoring plan names the metrics and the person watching them.
Exercise C.1 — Gate review. Apply Checklists 1–3 to a current project. Mark each item as done, partially done, or missing, and choose the three missing items with the highest risk.
